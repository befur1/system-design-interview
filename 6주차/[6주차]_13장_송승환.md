### 데이터 수집 서비스 & 질의 서비스 - 참고용

#### 1. 데이터 수집 서비스

사용자가 `twitch` → `twitter` → `twitter` → `twillo` 순으로 검색했다고 하면, 빈도 테이블이 이렇게 변함

```
① twitch 검색              ② twitter 검색
┌─────────┬───────┐        ┌─────────┬───────┐
│ query   │ freq  │        │ query   │ freq  │
├─────────┼───────┤        ├─────────┼───────┤
│ twitch  │   1   │        │ twitch  │   1   │
└─────────┴───────┘        │ twitter │   1   │
                           └─────────┴───────┘

③ twitter 또 검색           ④ twillo 검색
┌─────────┬───────┐        ┌─────────┬───────┐
│ query   │ freq  │        │ query   │ freq  │
├─────────┼───────┤        ├─────────┼───────┤
│ twitch  │   1   │        │ twitch  │   1   │
│ twitter │   2   │ ← 증가  │ twitter │   2   │
└─────────┴───────┘        │ twillo  │   1   │
                           └─────────┴───────┘
```

테이블은 `query`(질의문)와 `frequency`(빈도) 두 칸이면 끝임

#### 2. 질의 서비스

빈도 테이블이 이렇게 쌓여 있다고 하면

| query | frequency |
| --- | --- |
| twitter | 35 |
| twitch | 29 |
| twilight | 25 |
| twin peak | 21 |
| twitch prime | 18 |
| twitter search | 14 |
| twillo | 10 |
| twin peak sf | 8 |

사용자가 `tw` 를 입력하면 **빈도 상위 5개**를 돌려줌

```
tw  →  twitter, twitch, twilight, twin peak, twitch prime
```

SQL 로 쓰면 이 한 문장임

```sql
SELECT * FROM frequency_table
WHERE query LIKE 'tw%'
ORDER BY frequency DESC
LIMIT 5;
```

#### 3. 이 설계가 안 되는 이유

데이터가 적으면 위 SQL 로 충분한데, 규모가 커지면 **이 질의 자체가 병목**이 됨

- `LIKE 'tw%'` 는 접두어 검색이라 인덱스를 타도 **해당 접두어로 시작하는 행을 전부 훑어야 함**
- 거기서 다시 `ORDER BY frequency DESC` 로 **정렬까지** 해야 함
- 자동완성은 **타이핑 한 글자마다** 요청이 날아감 → 질의 횟수가 검색 횟수의 몇 배

### 트라이(trie)

이름은 re**trie**val 에서 왔음. 문자열을 **트리 형태로 저장**해서 접두어 검색을 빠르게 하는 자료구조

#### 기본 구조

- 루트 노드는 **빈 문자열**을 나타냄
- 각 노드는 **글자 하나**를 저장하고, 영어 기준 최대 26개의 자식을 가짐
- 루트에서 어떤 노드까지 내려오며 글자를 이으면 **하나의 단어 또는 접두어**가 됨

`tree, try, true, toy, wish, win` 을 담고 빈도까지 얹으면

```
root
├─ t
│  ├─ o ── y (14)         → toy
│  └─ r
│     ├─ e ── e (10)      → tree
│     ├─ y (29)           → try
│     └─ u ── e (35)      → true
└─ w
   └─ i
      ├─ s ── h (25)      → wish
      └─ n (50)           → win
```

**같은 접두어를 공유하는 단어들이 경로를 함께 씀.** `tr` 까지는 tree·try·true 가 같은 길을 타고 내려옴

#### 기호 정리

| 기호 | 뜻 | `tr` 을 입력한 경우 |
| --- | --- | --- |
| **p** | **입력한 접두어의 글자 수** (prefix) | `tr` 이니까 **p = 2** |
| **c** | **그 접두어 노드 아래에 달린 하위 노드 수** (children) | e, e, y, u, e → **c = 5** |
| **k** | 돌려줄 자동완성 개수 | 보통 5~10 |
| **n** | 트라이 전체 크기 (저장된 단어 수 또는 전체 노드 수) | 저장 공간을 따질 때 씀 |
- **p 는 단어 하나의 길이가 아니라 사용자가 친 글자 수**임. `t` 면 1, `twitter` 면 7
- **c 는 접두어마다 다름.** `t` 를 치면 t 아래 전부라 거대하고, `twitt` 까지 치면 몇 개 안 됨

#### 자동완성 알고리즘

`tr` 을 입력해 상위 2개를 찾는 과정

| 단계 | 하는 일 | 복잡도 | 왜 그 복잡도인가 |
| --- | --- | --- | --- |
| 1 | 접두어 `tr` 노드를 찾음 | **O(p)** | 루트에서 **한 글자씩** 내려가니까 글자 수만큼 단계를 밟음 |
| 2 | 하위 트리를 훑어 유효 노드를 모음 → tree(10), try(29), true(35) | **O(c)** | 아래 달린 노드를 **전부** 봐야 함 |
| 3 | 빈도로 정렬해 상위 k 개를 뽑음 → true(35), try(29) | **O(c log c)** | 최대 c 개를 정렬 |

전체 **O(p) + O(c) + O(c log c)**

#### 이대로는 느림

병목은 **c** 임. **접두어가 짧을수록 c 가 폭발함**

- `t` 하나만 쳐도 t 로 시작하는 모든 검색어가 c 에 들어감
- 최악의 경우 **트라이 전체를 탐색**
- 자동완성은 **글자 하나 칠 때마다** 요청이 날아가는데, 가장 짧은 접두어일 때가 제일 비쌈

#### 최적화 ① 접두어 최대 길이 제한

사용자가 아주 긴 검색어를 넣는 일은 드무니까 **p 를 상수(예: 50)로 제한**

→ p 가 입력에 따라 늘어나지 않고 **아무리 길어도 50단계**로 고정됨. 상수는 big-O 에서 상수라 **O(p) → O(1)**

#### 최적화 ② 노드마다 상위 k 개를 미리 저장

각 노드에 **그 아래에서 가장 많이 검색된 k 개를 캐시**해둠

```
노드 "tr"  →  top: [true(35), try(29)]     ← 미리 저장해둠
노드 "t"   →  top: [try(29), toy(14), ...]
```

→ **c 가 아예 식에서 사라짐.** 하위 트리를 훑을 일도(2단계), 정렬할 일도(3단계) 없어짐

대신 같은 검색어가 조상 노드마다 중복 저장돼서 **저장 공간을 훨씬 많이 씀 — 시간을 벌려고 공간을 내준 것**

#### 정리

|  | 복잡도 | 남아 있는 변수 |
| --- | --- | --- |
| 최적화 전 | O(p) + O(c) + O(c log c) | p, c |
| ① 적용 | O(1) + O(c) + O(c log c) | c |
| ② 까지 적용 | **O(1)** | 없음 |

### 데이터 수집 서비스

기존 서비스의 단점

- 질의가 입력될 때마다 트라이를 갱신하면 질의 서비스는 심각하게 느려질 것임
- 용례에 따라 다르겠지만, 구글과 같은 서비스는 인기 검색어가 자주 바뀌지는 않음

#### 데이터 분석 서비스 로그 & 로그 취합 서버

검색창에 입력된 질의에 관한 원본 데이터를 **데이터 분석 서비스 로그**에 저장하며, 데이터 수정이 이뤄지지는 않음

데이터 분석 서비스로부터 나오는 로그를 취합하는 주기마다 로그를 취합하는데, 용례에 따라 주기를 다르게 설정하면 됨

#### 작업 서버 & 트라이 캐시

**작업 서버**는 주기적으로 비동기적 작업을 실행하는 서버의 집합으로, 트라이 자료구조를 만들고 트라이 DB에 이를 저장함

**트라이 캐시**는 분산 캐시 시스템으로 트라이 DB의 스냅샷을 떠서 트라이 데이터를 메모리에 유지함

#### 트라이 DB

#### ① 문서 저장소 (MongoDB 등)

**트라이를 통째로 직렬화해서 문서 하나로 저장**

- 주기적으로 새 트라이를 만들어 직렬화 → 저장
- 서버가 뜨거나 갱신할 때 그 문서를 읽어 **역직렬화해서 메모리에 복원**

|  |  |
| --- | --- |
| 장점 | 다루는 단위가 "트라이 하나"라 **구현이 단순함**. 통째로 교체하면 끝 |
| 단점 | 일부만 바꾸기 어려움. 갱신하려면 **전체를 다시 쓰고 다시 읽어야 함** |

#### ② 키-값 저장소

**트라이를 해시 테이블 형태로 펼쳐서 저장.** 변환 규칙이 두 줄임

- 트라이 안의 **모든 접두어를 키**로
- 각 노드에 저장해둔 **top k 질의어를 값**으로

```
트라이                              키-값 저장소
root                               ┌───────┬──────────────────────┐
├─ t                               │ key   │ value (top k)        │
│  ├─ o ── y                       ├───────┼──────────────────────┤
│  └─ r          ───변환──>         │ t     │ [try, toy, tree, …]  │
│     ├─ e ── e                    │ tr    │ [true, try, tree]    │
│     ├─ y                         │ tre   │ [tree]               │
│     └─ u ── e                    │ tru   │ [true]               │
└─ w                               │ w     │ [win, wish]          │
   └─ i                            │ wi    │ [win, wish]          │
      ├─ s ── h                    │ wis   │ [wish]               │
      └─ n                         └───────┴──────────────────────┘
```

**노드 하나가 행 하나가 됨.** 키는 루트부터 그 노드까지 이어 붙인 문자열

|  |  |
| --- | --- |
| 장점 | 접두어로 **한 번 조회하면 끝**. 6장에서 본 키-값 저장소의 장점(확장·낮은 지연)을 그대로 가져옴 |
| 단점 | 행 수가 접두어 개수만큼 늘어남. 같은 검색어가 조상 노드마다 중복 저장됨 |

#### 핵심 — 트리 구조가 읽기에는 필요 없어짐

최적화 ② 로 **각 노드에 top k 를 이미 캐시해뒀기 때문에**, 조회할 때는 트리를 타고 내려갈 일이 없음

- 트리 구조가 필요한 건 **트라이를 만들 때**(빈도 집계, top k 계산)
- 서비스할 때 필요한 건 **"접두어 → 결과 목록" 매핑 하나뿐**

그게 정확히 해시 테이블이 하는 일이라, **키-값 저장소로 바꿔도 아무것도 잃지 않음**

> 자료구조를 고를 때 "만들 때 필요한 구조"와 "쓸 때 필요한 구조"가 다를 수 있다는 것. 여기선 빌드는 트리로, 서빙은 해시 테이블로 나눠 가져감
> 

#### DB 에 넣는 건 캐시가 아님

"서빙은 해시 테이블"이라는 게 캐시를 뜻하는 건 아님. **같은 모양이 세 군데에 따로 있고, 역할이 다름**

```
브라우저 캐시         "tr" → [true, try, …]     사용자 PC, 1시간
     │ 미스
     ▼
트라이 캐시 (서버 RAM) "tr" → [true, try, …]     빠름, 휘발성
     │ 미스
     ▼
키-값 저장소 (DB)      "tr" → [true, try, …]     느림, 영속   ← 원본
```

|  | 어디에 | 왜 있나 |
| --- | --- | --- |
| 브라우저 캐시 | 사용자 PC | 서버에 요청 자체를 안 보내게 (`Cache-Control: max-age=3600`) |
| 트라이 캐시 | 서버 메모리 | 빠른 응답. 죽으면 날아감 |
| 문서 저장소 / 키-값 저장소 | DB | **원본 보관.** 서버가 죽거나 늘어나도 남아야 함 |

**셋 다 "접두어 → 결과" 조회라 생김새는 같음.** 다른 건 어디 있고 얼마나 오래 사느냐뿐

> 그래서 ①②는 "캐시를 뭘로 할까"가 아니라 **"원본을 어떤 형태로 남길까"**를 고르는 문제임. 캐시는 그걸 메모리에 올려둔 사본일 뿐
> 

### 질의 서비스

개략 설계에서는 `LIKE 'tr%' ORDER BY frequency DESC LIMIT 5` SQL 한 방이었는데, 규모가 커지면 그게 병목이라 **트라이 캐시 + 트라이 DB** 구조로 바뀜

#### 흐름

```
사용자가 "tr" 입력
   │ ①
   ▼
로드밸런서
   │ ②
   ▼
API 서버
   │ ③  조회
   ▼
트라이 캐시 ──── ④ 미스 ────> 트라이 DB
   │   ▲                        │
   │   └──── 캐시에 채워넣음 ─────┘
   ▼
자동완성 검색어 목록 반환
```

**캐시 미스가 나는 경우** — 캐시 서버 메모리가 부족하거나, 캐시 서버에 장애가 있을 때

#### 최적화 세 가지

질의 서비스는 **번개처럼 빨라야 함.** 사용자가 글자를 칠 때마다 요청이 나가니까

#### ① AJAX 요청

브라우저가 AJAX 로 자동완성 목록을 받아옴

→ **요청을 보내고 받는 데 페이지를 새로고침할 필요가 없음.** 타이핑 중에 화면이 그대로 유지됨

#### ② 브라우저 캐싱

자동완성 결과는 **짧은 시간 안에는 거의 바뀌지 않음**. 그래서 받아온 결과를 브라우저에 캐시해두면 후속 질의는 **서버에 가지 않고 끝남**

구글이 쓰는 방식이고, 응답 헤더가 이렇게 날아옴

```
cache-control: private, max-age=3600
```

- `private` — 중간 프록시가 아니라 **그 사용자 브라우저에만** 저장
- `max-age=3600` — 1시간 동안 유효

#### ③ 데이터 샘플링

모든 질의를 로깅하면 **CPU 와 저장 공간이 감당이 안 됨**. 자동완성은 글자 하나마다 요청이 가니까 로그가 실제 검색 횟수의 몇 배로 쌓임

→ **N 개 요청 중 1 개만 로깅**

인기 검색어는 어차피 많이 들어오니까 **샘플링해도 순위는 거의 그대로임.** 정확도를 조금 내주고 비용을 크게 줄이는 것

### 트라이 연산

트라이는 검색어 자동완선 시스템의 핵심 컴포넌트임

#### 트라이 생성

트라이 생성은 작업 서버가 담당하며, 데이터 분석 서비스의 로그나 데이터베이스로부터 취합된 데이터를 사용

#### 트라이 갱신

1. 매주 한 번 갱신하는 방법: 새로운 트라이를 만든 다음에 기존 트라이를 대체
2. 트라이의 각 노드를 개별적으로 갱신하는 방법: 대규모 서비스에서 성능이 좋지 않음. 하위 노드의 이용 빈도가 갱신되면 모든 상위 노드도 갱신해야하기 때문에

### 검색어 삭제

혐오성 / 폭력적 / 성적 / 노골적인 질의어를 자동완성 결과에서 제거해야하는데 이는 트라이 캐시에 API 서버로 Return되는 파이프라인에 필터 계층을 두어 검색 결과를 자유롭게 변경할 수 있음

### 저장소 규모 확장

트라이가 커져서 **서버 한 대에 들어가지 않을 때** 어떻게 나눌 것인가

#### 방안 1 — 첫 글자 기준 분할

```
서버 1   a ~ m
서버 2   n ~ z

더 필요하면 더 잘게
서버 1   a ~ i
서버 2   j ~ r
서버 3   s ~ z
```

**한계 두 가지**

#### 방안 2 — 검색어 대응 샤드 관리자 (shard map manager)

**과거 질의 데이터의 패턴을 분석해서** 양이 비슷해지도록 묶는 방식

예를 들어 `s` 로 시작하는 질의가 `u~z` 로 시작하는 질의를 전부 합친 것과 비슷하다면

```
s 로 시작    ████████████
u~z 전부     ████████████     ← 양이 비슷

→ 샤드 A :  s
   샤드 B :  u, v, w, x, y, z
```

**어떤 검색어가 어느 샤드에 있는지를 관리하는 컴포넌트**가 검색어 대응 샤드 관리자임. 질의가 오면 여기서 먼저 샤드를 찾고 그 샤드로 보냄
