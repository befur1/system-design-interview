# 검색어 자동완성 시스템 (Search Autocomplete System)
1. 데이터 수집 서비스

사용자가 tw라는 단어를 검색창에 치면

SELECT * FROM frequency_table
WHERE query LIKE 'tw%'
ORDER BY frequency DESC
LIMIT 5;

이런 sql문을 통해 조회하게 된다.

근데 Like ‘tw%’는 tw로 시작하는 행을 전부 찾고 → 빈도수 테이블을 정렬 하는 과정이 필요한데 tw로 시작하는 단어는 엄청 많다 → 비효율적

(query, frequency) 테이블

이런 관계형 데이터베이스를 검색어 자동완성에서 쓰기 꺼려하는 이유

1. 트라이는 노드가 자식을 계속 갖는 트리 구조라고 하는데,  이걸 테이블로 저장하면 `(node_id, parent_id, char)` 같은 형태가 되는데, `twi`를 찾으려면 `t → w → i`를 따라 **조인이나 재귀 쿼리를 여러 번** 해야하는 비효율적 구조
2. 트랜잭션 정합성( 관계형 DB는 ACID 트랜잭션을 보장하는 특징이 있음) 이 사실 검색어 자동 완성에서는 굳이 필요하지 않음. 빈도가 살짝 늦거나, 내용이 틀려도 크게 문제되지 않는다.
    1. 자동완성은 결국 접두사를 통해 top 5의 내용만 가져오면 되는데 이는 키를 통해 값을 조회하는 방식으로 충분(조인, 복잡한 조건 검색, 정렬 같은 관계형 DB의 장점이 굳이 필요하지 않음).

데이터 분석 서비스 로그

검색창에 입력된 내용의 원본 데이터가 보관될 때, 하루에 수십억건의 인덱스가 추가된다.

1. 데이터 분석 서비스 로그는 **사용자가 검색할 때마다 그 검색어와 시각을 한 줄씩 기록해 둔 원본 기록이다.**

→ 단점: 양이 엄청나다…

원본 저장하는 방법

**Kafka: 원본 (임시 보관)**

- 검색 서버가 검색이 생길 때마다 Kafka에 로그를 보냄.
- Kafka도 받은 데이터를 디스크에 저장하긴 하지만, **보존 기간(예: 7일)이 지나면 지우고,** 그래서 영구 저장소라기보다 버퍼 역할로 사용.
- 쓰는 이유는, 검색 서버가 로그 저장소에 직접 쓰다가 저장소가 느려지거나 장애가 나면 검색까지 영향을 받기 때문이다. 중간에 Kafka를 두면 검색 서버는 던지고 끝내도록 함.

**S3·HDFS: 원본을 오래 쌓아 두는 곳 (영구 보관)**

- Kafka에서 로그를 읽어 일정량씩 묶어 파일로 S3나 HDFS에 저장한다.
- 보통 날짜·시간별 폴더로 나눠 쌓는다.

→ 관계형 DB에 넣지 않는 이유도 앞에서 말한 것과 같다. 조인이나 트랜잭션이 필요 없고, 순서대로 쌓고 나중에 몰아서 읽기만 하면 되기 때문

1. 따라서 취합 서버가 → 트라이 구조에 필요한 빈도수를  같은 검색어끼리 묶어서 저장하도록 한다.

→ 트라이가 실시간으로 변하는 것은 조상 노드의 top-k까지 계속 다시 계산해야 해서 감당이 안 된다.

→ 취합 주기는 서비스에 맞게 조절해야한다. 트랜드에 민감하면 짧아도 된다.

1. 트라이 캐시: 매주 트라이 데이터베이스의 스냅샷을 떠서 갱신.
2. 트라이 데이터 베이스: 문서 저장소, 키-값 저장소

AJAX 요청이란?

AJAX(Asynchronous JavaScript and XML)는 
**페이지를 새로고침하지 않고, 자바스크립트로 서버에 요청을 보내 필요한 데이터만 받아 화면 일부를 바꾸는 방식.**

실시간으로 변하는 검색어의 추이 반영

1. **샤딩으로 작업 대상 줄이기**: 트라이를 나눠 두면 바뀐 부분만 빠르게 다시 만들 수 있다.
2. **랭킹 모델 바꾸기**: 단순 누적 빈도 대신 **최근 검색에 가중치**를 더 둔다.
3. **스트림 처리 도입**: 데이터가 한꺼번에 오는 게 아니라 계속 흘러들어오므로, Kafka, Spark Streaming, Flink, Storm 같은 스트림 처리 시스템으로 즉시 집계하도록 설계한다.
