# [6주차] 11장 - 뉴스 피드 시스템 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

이번 장은 읽으면서 계속 내 프로젝트가 떠올랐다. 특가 메일을 구독자에게 보내는 쪽은 쓰기 시점 팬아웃이고, 홈 화면 인기 전시를 뽑는 쪽은 읽기 시점 팬아웃이었다. 책이 둘을 나란히 놓고 비교하는 걸 보고서야 내가 두 방식을 각각 쓰고 있었다는 걸 알았다.

## 책 내용 뼈대

### 규모와 요구사항

| 항목 | 값 |
| --- | --- |
| 일간 방문자 | 1,000만 명 |
| 한 사용자의 최대 친구 수 | 5,000명 |
| 피드 정렬 | 시간 역순 |
| 피드에 들어가는 것 | 텍스트, 이미지, 비디오 |

API는 두 개다.

| | 경로 | 하는 일 |
| --- | --- | --- |
| 피드 발행 | POST /v1/me/feed | 새 포스팅을 쓴다 |
| 피드 읽기 | GET /v1/me/feed | 내 뉴스 피드를 가져온다 |

### 피드 발행 흐름

```
사용자 -> 로드밸런서 -> 웹 서버 -> 포스팅 저장 서비스 -> DB, 캐시
                                        |
                                        v
                                   팬아웃 서비스
```

팬아웃 서비스가 하는 일이 이 장의 핵심이다.

1. 그래프 DB에서 친구 ID 목록을 가져온다
2. 사용자 정보 캐시에서 친구 정보를 가져온다 (뮤트해둔 친구, 특정인에게만 공개 같은 설정을 여기서 걸러낸다)
3. 친구 목록과 새 포스팅 ID를 메시지 큐에 넣는다
4. 팬아웃 작업 서버가 큐에서 꺼내 뉴스 피드 캐시에 기록한다

메시지 큐를 끼우는 이유는 컴포넌트 간 결합도를 낮추는 것이다. 10장에서 알림 종류별로 큐를 둔 것과 같은 자리다.

### 팬아웃 두 방식

| | 쓰기 시점 팬아웃 (push) | 읽기 시점 팬아웃 (pull) |
| --- | --- | --- |
| 언제 피드를 만드나 | 글이 올라올 때 미리 | 사용자가 읽을 때 |
| 장점 | 피드가 실시간으로 갱신된다. 읽기가 빠르다 (이미 만들어져 있으므로) | 비활성 사용자에게 리소스를 안 쓴다. 핫키 문제가 생기지 않는다 |
| 단점 | 친구가 많으면 갱신할 피드가 그만큼 많아진다 (핫키 문제). 안 읽는 사용자 몫까지 미리 만든다 | 읽을 때 시간이 걸려 사용자 경험이 나빠진다 |

책의 선택은 혼합이다. 대부분 사용자는 push로 가고, 친구나 팔로워가 많은 사용자의 포스팅은 팔로워가 읽는 시점에 가져가게(on-demand) 한다. 그리고 요청과 데이터를 고르게 분산하려고 안정 해시를 쓴다. 5장이 또 나온다.

### 뉴스 피드 캐시

캐시에는 `<postId, userId>` 순서 쌍만 저장한다. 포스팅 데이터를 통째로 넣지 않는다.

이유가 두 개다.

- 포스팅 전체를 넣으면 메모리가 낭비된다
- 사용자는 보통 최신 피드만 확인하므로 캐시 미스가 적다. 캐시 크기는 적정선을 유지하도록 조정한다

### 캐시를 다섯 계층으로 나눈다

| 계층 | 보관하는 것 |
| --- | --- |
| 뉴스 피드 | 뉴스 피드 ID |
| 콘텐츠 | 포스팅 데이터. 인기 콘텐츠는 따로 보관 |
| 소셜 그래프 | 사용자 간 관계 정보 |
| 행동 | 좋아요, 답글 등 포스팅에 대한 행위 |
| 횟수 | 좋아요 수, 답글 수, 팔로워 수, 팔로잉 수 |

### 마무리에서 언급되는 것

- 미디어 콘텐츠는 CDN에서 받는다 (1장, 2장과 이어진다)
- DB 수직 규모 확장과 수평 규모 확장
- SQL과 NoSQL
- 주-부 다중화, 복제에 대한 읽기 연산
- 데이터 센터 간 데이터 다중화

## 개인적인 질문

### 1. 피드 캐시에 ID만 넣으면 결국 두 번 다녀오는 게 아닌가

처음에 이해가 안 된 부분이다. 피드 캐시에 `<postId, userId>`만 있으면, 화면에 보여줄 때 포스팅 20개의 본문과 작성자를 또 조회해야 한다. 그러면 캐시를 쓰는 의미가 없는 게 아닌가 싶었다.

답은 캐시 다섯 계층에 있었다. 포스팅 본문을 가져오는 곳도 DB가 아니라 콘텐츠 캐시다. 즉 두 번 다녀오는 건 맞지만 둘 다 캐시다.

그리고 ID만 넣는 게 손해가 아니라 이득이다.

| | 포스팅 전체를 캐시에 | ID 쌍만 캐시에 |
| --- | --- | --- |
| 한 항목 크기 | 본문 + 이미지 URL + 작성자 정보 | 정수 두 개 |
| 같은 메모리에 담을 수 있는 양 | 적다 | 훨씬 많다 |
| 같은 포스팅이 100명 피드에 있으면 | 본문이 100번 중복 저장된다 | ID만 100번, 본문은 콘텐츠 캐시에 한 번 |

마지막 줄이 결정적이다. 인기 포스팅일수록 여러 사람의 피드에 들어가는데, 본문을 피드 캐시에 넣는 설계는 인기 포스팅일수록 메모리를 많이 먹는다. ID만 넣으면 그 중복이 사라진다. 정규화를 캐시에 적용한 셈이다.

### 2. 읽기 시점 팬아웃이 비활성 사용자에게 유리하다는 게 무슨 뜻인가

처음에는 "접속을 안 하니까 서버가 한가하다" 정도로 읽었는데 그게 아니었다.

쓰기 시점 팬아웃은 글이 올라오는 순간 친구 5,000명의 피드를 전부 갱신한다. 그중 오늘 접속하는 사람이 50명이면 4,950명 몫의 계산과 메모리는 통째로 버려진다. 한 번도 읽히지 않을 피드를 미리 만든 것이다.

읽기 시점 팬아웃은 읽는 사람 몫만 만든다. 그래서 비활성 사용자 비율이 높을수록 유리해진다.

그리고 책이 적은 두 번째 장점이 더 중요해 보였다. 읽기 시점 방식은 핫키 문제가 아예 생기지 않는다. 데이터를 친구 각각에게 밀어넣는 단계가 없으니, 팔로워가 100만이든 10명이든 쓰기 비용이 똑같다. 쓰기 시점 방식의 비용은 팔로워 수에 비례하고 읽기 시점 방식은 상수다. 책이 셀럽만 pull로 돌리는 이유가 이것이다.

### 3. 구독자 명단을 저장하지 않고 매번 다시 계산하면 어떻게 되나

내 프로젝트가 그렇게 돼 있어서 생긴 질문이다. 책은 친구 ID 목록을 그래프 DB에서 가져오는데, 내 프로젝트는 구독자 명단을 아무데도 저장하지 않고 발송할 때마다 메일함을 처음부터 다시 훑어서 계산한다. 아래 프로젝트 항목에 자세히 적었다.

## 내 프로젝트에 팬아웃이 양쪽으로 다 있었다

| 책의 자리 | 특가 알림 프로젝트 (파이썬) | 전시 커뮤니티 프로젝트 (스프링부트) |
| --- | --- | --- |
| 팬아웃 방식 | 쓰기 시점 (push) | 읽기 시점 (pull) |
| 친구 목록 저장소 (그래프 DB) | 구독자 명단을 매번 메일함에서 재계산 | 좋아요 테이블 조인 |
| 팬아웃 서비스 | 크론이 구독자별로 매칭 후 메일 발송 | 없음 |
| 피드 캐시 | 없음 (만든 즉시 발송) | 없음 (매 요청마다 집계) |
| 중복 방지 | 발송 로그 테이블 | 해당 없음 |

### 특가 알림은 쓰기 시점 팬아웃이다

발송 로직의 흐름이 책의 팬아웃 서비스와 순서까지 같다.

```
크론 실행
 -> 구독자 명단 계산          (책: 그래프 DB에서 친구 ID 목록)
 -> 오늘의 특가 계산          (책: 새 포스팅)
 -> 구독자별로 노선 매칭      (책: 사용자 설정에 따라 걸러내기)
 -> 이미 보낸 것 제외         (책에는 없음. 10장 알림 로그)
 -> 메일 발송                 (책: 뉴스 피드 캐시에 기록)
```

구독자 설정을 보고 걸러내는 부분이 특히 같다. 책은 뮤트한 친구를 빼는데, 내 쪽은 구독 노선을 보고 맞는 특가만 고른다. 전체 구독자가 특정 노선만 제외한 경우까지 표기로 구분한다.

그 판정을 발송 쪽이 아니라 구독 모듈에 둔 이유를 코드 주석에 적어뒀는데, 다시 읽어보니 이게 책의 팬아웃 서비스 설계와 같은 이야기였다. 제외 표기를 아는 곳이 둘이 되면 언젠가 하나가 틀리고, 틀리면 해지한 사람에게 메일이 간다. 책이 사용자 설정 확인을 팬아웃 서비스 한 곳에 모아둔 것도 같은 이유로 보인다.

### 전시 커뮤니티 홈은 읽기 시점이다

홈 화면은 배너, 다가오는 팝업, 인기 전시 6개를 합쳐서 돌려준다. 그런데 인기 전시를 뽑는 쿼리가 매 요청마다 좋아요를 세서 정렬한다.

```
order by count(좋아요) desc, id desc
```

미리 만들어둔 게 없다. 요청이 올 때마다 집계한다. 책의 읽기 시점 팬아웃 그대로다.

지금은 데이터가 적어서 문제가 안 되는데, 책을 읽고 나니 이게 왜 위험한지 보였다. 이 쿼리는 모든 사용자에게 같은 결과를 준다. 즉 같은 집계를 1,000명이 들어오면 1,000번 한다. 개인화된 피드가 아니라 전체 공통 랭킹이니까, 미리 한 번 계산해서 캐시에 올려두면 1,000번이 1번이 된다. 책이 인기 콘텐츠는 따로 보관한다고 적은 자리가 정확히 여기다.

반대로 전시 커뮤니티에 개인 피드(내가 팔로우한 사람의 글)가 생기면 그때는 사용자마다 결과가 달라지므로 공통 캐시로 안 되고, 책의 push/pull 선택 문제가 그대로 들어온다.

### 내 구조에 있는 구멍 세 개

책을 읽고 다시 보니 지금 안 터지는 이유가 규모가 작아서일 뿐인 자리가 셋 있었다.

첫째, 발송이 순차 루프다. 구독자를 하나씩 돌면서 SMTP 연결 하나로 보낸다. 구독자가 1만 명이면 메일 1만 통을 한 줄로 보낸다. 책이 팬아웃 작업 서버를 여러 대 두고 메시지 큐에서 꺼내 쓰게 한 이유가 이것이다. 내 구조에는 큐가 없어서 병렬화할 접합부 자체가 없다. 10장 문서에 적은 "큐를 프로세스 밖에 둬야 하는 이유"와 같은 결론이다.

둘째, 구독자 명단을 매번 메일함 전체에서 재계산한다. 신청과 취소 메일을 시간순으로 다시 적용해서 현재 명단을 만든다. 이렇게 한 이유는 구독자 이메일을 공개 저장소에 남기지 않는 것이었고, 그 목적은 잘 달성된다. 다만 비용이 받은 메일 전체 개수에 비례한다. 구독자가 늘어나는 게 아니라 메일이 쌓이는 것만으로 느려진다. 책이 친구 목록을 그래프 DB에 두는 이유를 뒤집어서 본 셈이다. 관계 정보는 조회될 모양으로 저장해둬야 한다.

셋째, 중복 발송 방어가 조회 후 삽입이다. 발송 로그에서 같은 조합이 있는지 SELECT하고 없으면 보낸 뒤 INSERT한다. 유니크 제약이 아니다. 지금은 크론이 하나만 돌아서 안 터지는데, 두 개가 겹치면 같은 특가가 두 번 갈 수 있다. 4주차에 정리한 멱등성 키와 10장 중복 알림이 같은 자리에서 또 나왔고, 결론도 같다. 최종 방어선은 DB 유니크 제약이어야 한다.

## 5장, 10장, 4주차와 연계해서 생각해보자

이 장은 앞에서 읽은 것들이 거의 다 한 번씩 나온다.

| 이전 내용 | 11장에서 쓰이는 자리 |
| --- | --- |
| 5장 안정 해시 | 핫키 문제에서 요청과 데이터를 고르게 분산 |
| 10장 메시지 큐 | 팬아웃 서비스와 팬아웃 작업 서버 사이 |
| 10장 알림 로그 | 책에는 없지만 내 프로젝트의 발송 로그가 같은 자리 |
| 4주차 멱등성 키 | 같은 특가를 두 번 보내지 않기 |
| 1장, 2장 CDN | 피드의 이미지와 비디오 |

특히 핫키라는 말이 5장에서 서버 분포가 치우치는 문제였다가, 여기서는 한 사용자의 팔로워가 많아서 쓰기가 치우치는 문제로 나온다. 쏠림을 어디서 받아내느냐만 다르고 구조는 같다.

## 스스로 확인해본 것

쓰기 시점과 읽기 시점의 비용이 어디에 비례하는지를 정리해보니 책의 혼합 설계가 왜 그 모양인지 바로 보였다.

| | 쓰기 비용 | 읽기 비용 |
| --- | --- | --- |
| 쓰기 시점 (push) | 팔로워 수에 비례 | 상수 (만들어져 있다) |
| 읽기 시점 (pull) | 상수 | 팔로우하는 수에 비례 |

사람마다 팔로워 수는 천차만별인데(10명에서 1억까지) 팔로우하는 수는 대체로 비슷하다(수백에서 수천). 그래서 읽기 비용은 누구나 비슷하고 쓰기 비용만 극단적으로 벌어진다. 혼합 설계는 "쓰기 비용이 터지는 소수만 pull로 뺀다"는 뜻이고, 그 소수가 셀럽이다.
