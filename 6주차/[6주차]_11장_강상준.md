### 뉴스 피드 API
둘 다 Autorization 헤더를 쓰는 걸로 봐서는 토큰 인증 방식을 채택함

피드 발행 API: 파라미터로 Body에 콘텐츠 내용을 남아서 Post
피드 조회 API: 토큰만 헤더에 실어서 GET 요청

### 피드 발행
사용자가 POST 요청을 보내면 ->  로드밸런서가 적절하게 처리해서 웹서버로 보내주고 -> 웹서버에서 다시 포스팅 저장 서비스, 팬아웃 서비스, 알림 서비스라는 비즈니스 로직을 호출하는 방식으로 보인다.

**근데 어차피 GET 요청 보내서 피드를 조회하는 방식일텐데 포스팅 전송 서비스는 왜 필요하지?**
-> 매번 팔로우 하는 사람들의 목록을 조회 + 포스팅한 글 조회 및 정렬 + 반환하면 너무 무거워지니까 미리미리 캐시에 넣어주는 역할
-> 근데 캐시가 비싸고 유한한 자원인데 어떻게 캐시에 다 보관해놓는다는 것임?
    -> post_id만 저장, 활성 유저만 저장, 개수 상한을 정해놓는 등으로 관리한다.

### 뉴스 피드 생성

사용자가 GET 요청을 보내면 -> 로드밸런서가 트래픽을 분산해서 웹 서버로 보내주고 -> 뉴스 피드 서비스가 실행

## 3단계 - 상세 설계

### 피드 발행 흐름 상세 설계

#### 웹서버
클라이언트와 통신뿐만 아니라 인증, 처리율 제한 등의 기능도 수행해야 한다.
스팸을 막고 유해한 콘텐츠가 자주 올라오는 것을 방지하기 위해서 사용자 요청의 제한을 두어야 한다.

#### 포스팅 전송(팬아웃) 서비스

어떤 사용자의 새 포스팅을 그 사용자와 친구 관계에 있는 모든 사용자에게 전달하는 과정.
각 이용자의 캐시에 post_id를 넣어주는 시점이 다른 것임.

- 쓰기 시점에서 팬아웃: 포스팅이 완료되면 바로 해당 사용자의 캐시에 해당 포스팅을 기록
    장점: 
    - 뉴스 피드가 실시간으로 갱신되며 친구 목록에 있는 사용자에게 즉시 전송
    - 새 포스팅이 기록되는 순간에 뉴스 피드가 이미 갱신되므로 읽는 데 드는 시간이 짧아진다.

    단점:
    - 친구가 많은 사용자의 경우 친구 목록을 가져오고 그 목록에 있는 사용자 모두의 뉴스 피드를 갱신하는 데 많은 시간이 소요될 수도 있음. - 핫키라고 부름
    - 서비스를 자주 이용하지 않는 사용자의 피드까지 갱신해야함 **<- 이게 읽기 시점이랑 가장 큰 차이일듯**

- 읽기 시점에서 팬아웃: on-demand 모델
    장점: 
    - 비활성화된 사용자, 또는 이용이 드문 사용자를 생각할 때 이 모델이 자원관리에서 유리할 수 있다.
    - 데이터를 친구 각각에 푸시하는 작업이 필요 없으므로 핫키 문제도 생기지 않는다.

    단점: 
    - 뉴스 피드를 읽는 데에 많은 시간이 소요될 수 있다.

두 개의 모델로 나뉜다

팬아웃 쓰는 거 자체가 그 팔로우한 사람들 다 조회해서 게시글 머지소트 시켜서 정렬하고, 상위 게시물 가져오는 게 서버에 부담이 되니까 그거 안 하려고 하는 건데 읽기시점팬아웃 방식은 그냥 팬아웃 안 쓰는 거랑 다른게 뭘까 대체??
-> 이거 그냥 팬아웃 안 쓰는 거랑 똑같은 거였음..

실무에서 팔로워가 평범한 일반 사용자들은 쓰기 시점 팬아웃 + 셀럽들은 읽기 시점에서 팬아웃 = 하이브리드로 쓴다.

### 캐시 구조
서비스에서 캐시를 되게 많이 쓰는 것 같은데 좀 real-time 서비스의 측면이 있어서 반응성을 중요하게 생각하는 건가?

뉴스 피드 - 뉴스 피드 캐시
콘텐츠 - 인기 콘텐츠 | 일반 콘텐츠
소셜 그래프 - 팔로워 | 팔로잉
행동 - 좋아요 | 답글 | 기타
횟수 - 좋아요 | 답글 횟수 | 기타

소셜미디어 서비스는 UX적인 측면에서 반응성이 너무너무 중요한 서비스이고 읽기 트래픽과 쓰기 트래픽의 차이가 극단적으로 차이가 난다. 그래서 읽기 트래픽을 DB로 다 보내면 DB가 살 수가 없음.. -> 그래서 피드 하나에 들어가는 정보를 다 찢어서 캐시에 담아두고 조립해서 보내주는 거임.

인기 콘텐츠와 일반 콘텐츠의 캐시를 나누는 이유는
1. TTL을 길게 잡아 따로 관리한다
2. 인기 컨텐츠에 대한 트래픽을 격리시켜서 장애시 다른 일반 컨텐츠들에 대한 접근은 원활하게 유지한다.
3. 하나의 캐시에 섞어뒀을 때 인기 콘텐츠가 캐시에서 밀리면 트래픽이 다 디비로 향함 -> 디비 터짐.
