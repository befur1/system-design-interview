# [6주차] 11장 정리 - 원지현
# 11장_ 뉴스 피드 시스템 설계

## 뉴스 피드란
뉴스 피드는 홈 화면에 지속적으로 업데이트되는 사용자 자신과 친구들의 게시물 목록임.
- 예: 페이스북 뉴스 피드, 인스타그램 피드, 트위터 타임라인

## 설계 범위
- 모바일 앱과 웹 모두 지원함.
- 사용자는 게시물을 올리고, 친구들의 게시물을 뉴스 피드에서 볼 수 있음.
- 피드는 시간 역순으로 정렬함.
- 한 사용자는 최대 5,000명의 친구를 가질 수 있음.
- 일간 능동 사용자(DAU)는 천만 명이며, 게시물에는 텍스트뿐 아니라 이미지와 비디오도 포함될 수 있음.

## 개략적 설계
설계는 피드 발행과 뉴스 피드 생성 두 가지 흐름으로 나뉨.

API
- 피드 발행: POST /v1/me/feed (인자: 게시물 내용, 인증 토큰)
- 피드 읽기: GET /v1/me/feed

피드 발행 흐름
- 사용자가 게시물을 올리면 로드밸런서를 거쳐 웹 서버로 전달됨.
- 웹 서버는 인증과 처리율 제한을 수행함.
- 포스팅 저장 서비스: 게시물을 DB와 캐시에 저장함.
- 포스팅 전송(팬아웃) 서비스: 새 게시물을 친구들의 뉴스 피드 캐시에 전달함.
- 알림 서비스: 친구들에게 새 게시물이 올라왔음을 알림. (10장과 연결)

뉴스 피드 생성 흐름
- 사용자가 피드를 요청하면 로드밸런서와 웹 서버를 거쳐 뉴스 피드 서비스로 전달됨.
- 뉴스 피드 서비스는 뉴스 피드 캐시에서 피드를 가져와 반환함.

## 상세 설계

웹 서버
- 인증 토큰으로 인증된 사용자만 게시물을 올릴 수 있도록 함.
- 스팸을 막기 위해 일정 기간 동안 올릴 수 있는 게시물 수에 처리율 제한을 둠. (4장과 연결)

팬아웃 방식
- 쓰기 시점 팬아웃 (푸시 모델)
    - 게시물을 올리는 시점에 친구들의 뉴스 피드 캐시에 바로 기록함.
    - 장점: 피드가 미리 만들어져 있어 읽기가 빠르고, 새 게시물이 즉시 반영됨.
    - 단점: 친구가 많은 사용자의 게시물은 수많은 캐시에 기록해야 해 핫키 문제가 생기며, 서비스를 자주 이용하지 않는 사용자의 피드까지 갱신해 자원이 낭비됨.
- 읽기 시점 팬아웃 (풀 모델)
    - 사용자가 피드를 열 때 친구들의 최근 게시물을 가져옴.
    - 장점: 비활성 사용자를 위한 자원 낭비가 없고, 핫키 문제가 생기지 않음.
    - 단점: 피드를 읽을 때마다 게시물을 모으고 정렬해야 해 읽기가 느림.
- 하이브리드 방식
    - 빠른 피드 읽기가 중요하므로 대부분의 사용자에게는 푸시 모델을 사용함.
    - 팔로워가 매우 많은 유명인은 풀 모델을 적용해, 피드를 읽을 때 유명인 게시물만 따로 가져와 합침.
    - 안정 해시로 요청과 데이터를 고르게 분산해 핫키 문제를 완화함. (5장과 연결)

팬아웃 서비스 동작 과정
- 그래프 DB에서 친구 ID 목록을 가져옴.
- 사용자 캐시와 DB에서 사용자 설정을 확인해, 피드 업데이트를 원하지 않도록 설정된 친구 등은 걸러냄.
- 친구 목록과 게시물 ID를 메시지 큐에 넣음.
- 팬아웃 작업 서버가 큐에서 데이터를 꺼내 뉴스 피드 캐시에 <게시물 ID, 사용자 ID>를 기록함.
- 뉴스 피드 캐시에는 게시물 전체가 아닌 ID만 저장해 메모리를 아끼며, 사용자는 오래된 피드를 거의 보지 않으므로 최근 일정 개수만 보관함.

피드 읽기 과정
- 뉴스 피드 서비스가 뉴스 피드 캐시에서 게시물 ID 목록을 가져옴.
- 사용자 캐시와 포스팅 캐시에서 사용자 이름, 프로필 사진, 게시물 내용 등을 채워 완전한 피드를 만듦.
- 이미지, 비디오 같은 미디어는 CDN에 저장해 빠르게 전달함.

캐시 구조
- 캐시는 5개 계층으로 나누어 관리함.
    - 뉴스 피드: 뉴스 피드의 게시물 ID
    - 콘텐츠: 게시물 데이터 (인기 콘텐츠는 별도 캐시에 보관)
    - 소셜 그래프: 사용자 간 관계 정보
    - 행동: 좋아요, 답글 등 사용자 행위 정보
    - 횟수: 좋아요 수, 응답 수, 팔로워 수 등의 카운터

## 마무리: 더 생각해보면 좋을듯한 부분

피드 캐시에 ID만 저장하는 설계의 숨은 장점
- 뉴스 피드 캐시에는 게시물 ID만 있고 실제 내용은 읽을 때 포스팅 캐시에서 채워 넣으므로, 게시물이 수정되면 별도 처리 없이 모든 친구의 피드에 수정된 내용이 반영됨.
- 게시물 삭제, 친구 차단이나 언팔로우가 생겨도 이미 팬아웃된 수많은 피드 캐시를 일일이 고칠 필요 없이, 피드를 읽을 때 삭제된 게시물이나 차단한 사용자의 게시물을 걸러내면 됨.
- 즉 쓰기 시점에 미리 만들어두되, 변경 가능성이 있는 부분은 읽기 시점에 처리해 두 방식의 장점을 함께 가져감.

유명인의 기준은 어떻게 정할까?
- 하이브리드 방식에서 "팔로워가 많은 사용자"를 풀 모델로 처리하는데, 그 기준(예: 팔로워 1만 명? 10만 명?)은 고정값으로 둘지, 서버 부하에 따라 동적으로 바꿀지 고민이 필요함.
- 팔로워가 적어도 갑자기 게시물이 폭발적으로 공유되는 사용자처럼, 팔로워 수만으로는 판단하기 어려운 경우도 있음.

시간순 피드 vs 추천 피드
- 책은 시간 역순 피드를 가정하지만, 실제 서비스는 관심도 기반 추천 피드를 많이 사용함.
- 추천 피드는 사용자의 반응에 따라 순위가 계속 바뀌므로, 미리 만들어두는 쓰기 시점 팬아웃과 잘 맞지 않음. 후보 게시물은 미리 모아두고 순위는 읽을 때 계산하는 식의 절충이 필요함.
