# 11장: 뉴스 피드 시스템 설계

## 뉴스 피드란?

뉴스 피드는 내가 친구를 맺거나 팔로우한 사람들이 올린 글을 한 화면에 모아 보여주는 기능이다. 작성자가 게시물을 저장하는 일과 다른 사람의 피드에 그 게시물이 나타나는 일은 구분해서 생각해야 한다.

예를 들어 A가 사진을 올렸고 B와 C가 그 사진을 볼 수 있다고 하자. 게시물 원본은 한 건이지만, B의 피드와 C의 피드에는 각각 그 게시물이 들어갈 수 있다. 이때 모든 사람의 피드에 미리 넣어둘지, 각자가 피드를 열었을 때 가져올지에 따라 서버가 일을 하는 시점이 달라진다.

## 1단계: 문제 이해 및 설계 범위 확정

### 요구사항

- 웹과 모바일에서 사용할 수 있어야 한다.
- 사용자는 텍스트, 이미지, 동영상이 포함된 게시물을 올릴 수 있어야 한다.
- 사용자는 친구가 올린 게시물을 최신순으로 볼 수 있어야 한다.
- 사용자는 최대 5,000명의 친구를 가질 수 있다.
- 일간 활성 사용자 수는 1,000만 명으로 가정한다.

피드를 최신순으로 보여준다는 조건이 중요하다. 친구 관계의 친밀도나 게시물의 인기도를 함께 반영한다면 게시물 후보를 가져온 뒤 사용자별로 점수까지 계산해야 한다. 이번 설계에서는 게시물의 작성 시각으로 순서를 정한다.

### 어느 쪽에서 부하가 생길까?

DAU가 1,000만 명이라는 수치만으로는 초당 요청 수를 알 수 없다. 피드 조회량을 추정하려면 한 사람이 하루에 피드를 몇 번 여는지, 한 번 열 때 몇 페이지를 읽는지 알아야 한다.

피드에 미리 넣어두는 구조에서는 게시물 한 건이 몇 명에게 전달되는지도 중요하다. 초당 100개의 게시물이 올라오고 각 게시물을 평균 200명이 볼 수 있다고 가정하면, 게시물 원본은 초당 100건을 저장하지만 피드에는 초당 약 2만 건의 항목을 추가해야 한다. 게시물 생성 API의 요청 수와 실제 피드 저장소의 쓰기량이 크게 달라질 수 있다.

## 2단계: 개략적 설계안 제시 및 동의 구하기

### API 엔드포인트

#### 게시물 발행

- 요청: `POST /v1/me/feed`
- 입력: 게시물 본문과 첨부 미디어 정보
- 처리: 게시물을 저장하고 친구들의 피드에 반영할 작업을 시작한다.

#### 뉴스 피드 조회

- 요청: `GET /v1/me/feed`
- 처리: 로그인한 사용자에게 보여줄 게시물을 최신순으로 가져온다.
- 반환: 게시물 내용, 작성자 정보, 미디어 주소 등이 포함된 목록

두 API 모두 `Authorization` 헤더를 사용해 사용자를 확인한다. `/me`는 서버가 인증 정보에서 현재 사용자를 알아낸다는 의미다.

### 주요 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| 로드밸런서 | 웹 서버 여러 대에 요청을 분산한다. |
| 웹 서버 | 사용자 인증, 처리율 제한, 내부 서비스 호출을 담당한다. |
| 포스팅 저장 서비스 | 게시물 원본을 데이터베이스에 저장하고 캐시에서도 조회할 수 있게 한다. |
| 포스팅 전송 서비스 | 새 게시물을 누구의 피드에 반영할지 결정한다. |
| 뉴스 피드 서비스 | 사용자별 게시물 목록을 가져와 응답을 구성한다. |
| 알림 서비스 | 새 게시물이 올라왔음을 알려주는 별도의 알림을 처리한다. |

### 피드 발행과 피드 읽기

글을 올릴 때는 **게시물 원본을 저장하는 경로**와 **친구들의 피드에 반영하는 경로**가 생긴다. 친구가 많은 사용자의 글이 올라오면 수신자별로 작업해야 할 양이 커지므로, 게시물 작성 요청이 모든 피드 갱신을 기다리지 않도록 메시지 큐와 작업 서버를 둘 수 있다.

피드를 읽을 때는 먼저 사용자에게 보여줄 게시물 ID를 구하고, 각 게시물의 본문과 작성자 정보를 붙인다. 이미지나 동영상은 클라이언트가 응답에 포함된 주소를 이용해 CDN을 통해 가져올 수 있다.

10장에서 다룬 푸시 알림과 이 장에서 말하는 푸시는 가리키는 대상이 다르다. 푸시 알림은 사용자의 단말에 알림을 보내는 기능이고, 피드의 푸시 모델은 서버에서 사용자별 피드 목록을 미리 채워두는 방식이다. 알림이 뜨지 않아도 사용자가 앱을 열었을 때 피드에 새 글이 보일 수 있다.

## 3단계: 상세 설계

### 쓰기 시점에 팬아웃하는 방식

팬아웃(fanout)은 게시물 한 건을 여러 사용자의 피드에 반영하는 과정이다. 쓰기 시점 팬아웃에서는 작성자가 글을 올렸을 때 그 글을 볼 수 있는 사람들의 피드 목록에 게시물 ID를 추가한다.

A가 `post_101`을 올리고 B, C, D가 볼 수 있다면 다음처럼 기록한다.

| 피드의 주인 | 추가할 게시물 ID |
| --- | --- |
| B | `post_101` |
| C | `post_101` |
| D | `post_101` |

B가 피드를 열면 B의 목록을 바로 가져올 수 있으므로 조회가 빠르다. 대신 A의 친구가 5,000명이라면 글 하나로 최대 5,000개의 피드 항목이 생긴다. 그중 오랫동안 접속하지 않는 사람의 피드도 미리 갱신하게 된다.

큐를 두면 이 작업을 작성 요청과 분리할 수 있다. 발행 API는 먼저 응답할 수 있지만, 큐에 쌓인 5,000건을 처리할 용량은 여전히 필요하다.

### 읽기 시점에 팬아웃하는 방식

읽기 시점 팬아웃에서는 사용자별 피드를 미리 만들어두지 않고, 사용자가 피드를 열었을 때 친구들의 최근 게시물을 가져와 합친다.

예를 들어 B가 A와 C의 글을 볼 수 있다고 하자. B가 피드를 열면 A의 최근 글과 C의 최근 글을 각각 가져와 작성 시각 순서로 합친다. B가 피드를 열지 않으면 이 작업도 발생하지 않는다.

대신 B가 볼 수 있는 작성자가 많아질수록 여러 목록을 읽고 합치는 비용이 커진다. 인기 작성자의 글을 수많은 사용자가 동시에 조회한다면 그 작성자의 최근 게시물 목록에 읽기 요청이 집중될 수도 있다.

### 두 방식의 결합

| 구분 | 쓰기 시점 팬아웃 | 읽기 시점 팬아웃 |
| --- | --- | --- |
| 피드 목록을 만드는 시점 | 글이 올라왔을 때 | 사용자가 피드를 열었을 때 |
| 주요 부담 | 수신자별 피드 갱신 | 작성자별 최근 글 조회 및 병합 |
| 장점 | 피드 조회가 빠름 | 읽히지 않을 피드를 미리 계산하는 비용을 줄임 |
| 부담이 커지는 상황 | 한 작성자의 글을 볼 사람이 매우 많음 | 한 사용자가 볼 작성자가 많거나 인기 글에 읽기가 몰림 |

책에서는 대부분의 작성자에게 쓰기 시점 팬아웃을 적용하고, 팔로워가 특히 많은 작성자의 글은 읽을 때 가져오는 혼합 방식을 제안한다.

예를 들어 B의 피드 캐시에 친구 A의 글이 미리 들어가 있고, B가 팔로우하는 인기 작성자 C의 글은 따로 관리한다고 하자. B가 피드를 열 때 두 목록을 가져와 최신순으로 합친다. 방식이 바뀌는 기간에 같은 게시물이 두 경로에서 잡힐 수 있으므로 게시물 ID로 중복을 제거할 수 있다.

어느 작성자부터 읽기 방식으로 바꿀지는 팔로워 수만 보고 정하기 어렵다. 글을 얼마나 자주 올리는지, 팔로워가 얼마나 자주 피드를 여는지, 큐 작업을 얼마나 빨리 처리할 수 있는지도 영향을 준다.

### 포스팅 전송 서비스의 동작 과정

1. 웹 서버가 발행 요청을 인증하고 필요한 경우 게시물 작성 횟수를 제한한다.
2. 포스팅 저장 서비스가 새 글을 저장한다.
3. 포스팅 전송 서비스가 그래프 데이터베이스에서 작성자의 친구 ID 목록을 가져온다.
4. 사용자 정보와 설정을 바탕으로 공개 범위에 포함되지 않은 사용자나 작성자를 뮤트한 사용자를 걸러낸다.
5. 게시물 ID와 수신자 목록을 메시지 큐에 넣는다.
6. 작업 서버가 큐에서 데이터를 꺼내 수신자별 뉴스 피드 캐시를 갱신한다.

수신자가 많다면 목록을 여러 묶음으로 나눠 처리할 수 있다. 한 묶음에서 오류가 발생했을 때 어떤 범위를 다시 처리할지도 함께 결정해야 한다.

### 뉴스 피드 캐시에 ID를 저장하는 이유

게시물 본문과 작성자 프로필을 모든 피드에 복사하면 같은 데이터가 수천 번 저장될 수 있다. 게시물을 수정하거나 작성자가 프로필 사진을 바꾸었을 때 어느 복사본까지 갱신됐는지도 추적해야 한다.

그래서 책에서는 뉴스 피드 캐시에 게시물 ID와 사용자 ID의 관계를 저장한다. 피드의 주인이 B라면 `B → [post_103, post_101, post_97]` 같은 목록으로 이해할 수 있다.

다만 ID만 저장하면 피드를 조회할 때 본문과 작성자 정보가 추가로 필요하다. 한 페이지에 글이 20개 있을 때 글마다 따로 조회하면 호출 횟수가 늘어나므로, 필요한 게시물 ID와 작성자 ID를 모아 한 번에 읽는 방식도 생각해볼 수 있다.

### 뉴스 피드 읽기 흐름

1. 클라이언트가 `GET /v1/me/feed`로 피드를 요청한다.
2. 로드밸런서가 요청을 웹 서버로 전달하고, 웹 서버가 뉴스 피드 서비스를 호출한다.
3. 뉴스 피드 서비스가 캐시에서 해당 사용자의 게시물 ID 목록을 읽는다.
4. 필요한 게시물 본문과 작성자 정보를 각 캐시에서 읽는다. 해당 항목이 없으면 원본 저장소에서 조회한다.
5. 피드 목록을 JSON으로 반환한다.
6. 브라우저나 앱이 받은 데이터를 게시물 카드로 화면에 그린다. 이 과정이 렌더링이다.

### 캐시 구성

| 캐시 | 저장하는 정보 |
| --- | --- |
| 뉴스 피드 | 사용자별로 최근에 보여줄 게시물 ID |
| 콘텐츠 | 게시물 본문과 미디어 정보 등. 인기 콘텐츠를 따로 관리할 수 있다. |
| 소셜 그래프 | 친구, 팔로워, 팔로잉 관계 |
| 행동 | 내가 특정 게시물에 좋아요를 눌렀는지, 어떤 답글을 남겼는지 등 |
| 횟수 | 게시물의 좋아요 수, 답글 수, 계정의 팔로워 수 등 |

예를 들어 피드 카드에 표시되는 하트의 색은 ‘내가 좋아요를 눌렀는가’를 기준으로 하고, 옆의 숫자는 ‘총 몇 명이 좋아요를 눌렀는가’를 기준으로 한다. 두 값은 조회에 사용하는 키와 필요한 갱신 주기가 다를 수 있다.

## 4단계: 설계 후 추가로 고려할 사항

### 캐시 용량과 오래된 피드 조회

대부분의 사용자가 최신 글을 먼저 보기 때문에 사용자별 최근 항목에 메모리를 집중할 수 있다. 다만 캐시에 최근 100개만 보관한다면 101번째부터는 어디서 조회할지 정해야 한다. 과거 피드를 어떤 방식으로 재구성할지, 어느 시점까지만 제공할지에 따라 필요한 저장 구조가 달라진다.

### 핫키와 트래픽 분산

피드 데이터를 사용자 ID로 나누면 서로 다른 사용자의 요청을 여러 노드에 분산할 수 있다. 안정 해시는 노드가 추가되거나 빠졌을 때 옮겨야 하는 키를 줄이는 데 도움이 된다.

특정 인기 작성자의 최근 글 목록 하나에 읽기 요청이 집중되는 상황은 별도로 살펴야 한다. 같은 키에 대한 읽기를 여러 서버에 분산할 수 있도록 결과를 복제하거나 별도의 캐시를 둘 수 있다.

### 가용성과 모니터링

웹 계층을 무상태로 운영하면 요청을 다른 서버가 이어서 처리하기 쉽다. 데이터가 늘어나면 읽기 복제본이나 샤딩을 고려할 수 있지만, 어느 정도의 복제 지연을 허용할지 먼저 정해야 한다.

피드 조회 시간과 게시물 반영 시간은 따로 측정한다. 피드가 100ms 만에 열려도 방금 작성한 글이 친구에게 10분 뒤에 보인다면 팬아웃 경로가 늦은 것이다. 이 경우 큐 대기량, 가장 오래 기다리는 작업의 대기 시간, 작업 서버 처리량을 함께 확인할 수 있다.

## 생각해본 질문

### 팬아웃 작업이 중간에 끊겼을 때 같은 글이 두 번 뜨지 않게 하려면?

`post_101`을 B와 C에게 반영하는 도중, B까지만 처리하고 작업 서버가 종료됐다고 하자. 큐에서 같은 작업을 다시 받으면 B도 다시 처리 대상에 들어갈 수 있다.

피드 항목을 `(recipient_id, post_id)`로 식별하고 같은 조합이 한 번만 저장되도록 하면, B에게 이미 들어간 항목을 유지하면서 C의 항목을 추가할 수 있다. MySQL에 피드 항목을 저장한다면 복합 기본키나 `UNIQUE` 제약조건으로 구현할 수 있다.

10장의 알림과 연결하면, 피드에서는 우리가 쓰는 저장소에서 중복을 제어할 수 있다. 알림이 외부 서비스로 넘어간 경우에는 내부 DB에 유일 제약을 걸어도 외부 서비스가 실제로 몇 번 발송했는지까지 통제할 수 있는지는 따로 확인해야 한다.

### 게시물이 저장된 뒤 큐에 넣기 전에 서버가 종료되면 어떻게 할까?

게시물은 작성자의 화면에 보이지만 친구의 피드에는 전달되지 않을 수 있다. 큐가 정상이어도 아직 큐에 들어가지 않은 작업은 큐가 복구할 수 없다.

게시물 원본과 팬아웃 이벤트를 같은 DB 트랜잭션에 기록하고, 별도 작업 서버가 커밋된 이벤트를 큐에 전달하는 아웃박스 패턴을 적용할 수 있다. 이 경우 이벤트를 큐에 보낸 뒤 처리 완료를 기록하기 전에 서버가 종료되면 같은 이벤트가 다시 들어갈 수 있으므로, 피드 항목의 중복 방지도 함께 필요하다.

### 공개했던 글을 비공개로 바꾸면 이미 피드에 들어간 글은 어떻게 할까?

A가 글을 공개했을 때 B의 피드에 게시물 ID가 들어갔다고 하자. 이후 A가 공개 범위를 바꾸면 B의 목록에 옛 ID가 남아 있을 수 있다.

이때 조회 응답을 만들 때 현재 공개 범위를 확인하면 캐시 정리가 끝나기 전에도 B에게 본문을 숨길 수 있다. 남은 피드 항목은 뒤에서 정리한다. 이미지와 동영상도 비공개로 전환해야 한다면 예전에 발급한 미디어 주소의 유효기간과 접근 방식도 함께 살펴야 한다.

### 새 글이 올라오는 도중 다음 페이지를 조회하면 왜 같은 글이 또 보일까?

한 페이지에 두 개씩 보여준다고 하자. 첫 요청에서 105번, 104번을 본 직후 106번이 맨 위에 추가되면, 두 번째 요청에서 앞의 두 개를 건너뛰어도 104번이 다시 나온다.

마지막으로 본 게시물의 `(created_at, post_id)`를 커서로 넘기고, 그 정렬 기준에서 104번보다 뒤에 있는 글만 조회하면 경계가 덜 흔들린다. 같은 시각에 작성된 글을 구분하기 위해 ID를 같이 사용한다. 쓰기와 읽기 경로의 결과를 섞는 경우에도 두 경로가 같은 정렬 기준을 사용해야 한다.

### 친구가 5,000명인 사용자의 글은 무조건 읽기 시점에 가져오는 편이 좋을까?

글을 드물게 올리고 친구들이 피드를 자주 연다면 한 번 미리 갱신하는 비용을 감수할 만하다. 반대로 글을 자주 올리는데 실제로 피드를 여는 친구는 적다면 대부분의 쓰기가 사용되지 않을 수 있다.

실제로 기준을 정하려면 작성자별 발행 빈도, 수신자의 피드 조회 빈도, 게시물 반영까지 허용하는 시간, 작업 서버의 처리 용량을 함께 볼 필요가 있다. 팔로워 수는 기준을 단순하게 만드는 데는 유용하지만 비용 전부를 설명해주지는 않는다.

### 몽글에 공개 꿈 피드를 붙인다면 처음부터 팬아웃 큐가 필요할까?

공개로 설정한 꿈을 모든 사용자가 최신순으로 보는 화면이라면, 사용자마다 다른 피드를 미리 만드는 구조가 필요하지 않다. 공개 게시물만 최신순으로 조회하고 커서 기반으로 다음 페이지를 가져오는 것부터 시작할 수 있다.

팔로우한 사람의 꿈만 보여주게 되면 사용자별 후보가 달라진다. 그때도 팔로우 수와 조회량이 적다면 DB에서 읽을 때 합칠 수 있다. 실제로 조회 병목이 생기면 어떤 사용자나 작성자부터 미리 계산할지 판단할 수 있다.
