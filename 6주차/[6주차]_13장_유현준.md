# [6주차] 13장 - 검색어 자동완성 시스템

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

이 장은 내 프로젝트에 자동완성이 없기 때문에 오히려 읽을 게 많았다. 전시 커뮤니티 프로젝트의 검색이 `like '%키워드%'`로 돼 있는데, 책이 트라이를 쓰는 이유가 정확히 그 반대편에 있었다. 왜 내가 트라이를 쓸 수 없는 모양으로 만들었는지가 이 장의 논점과 그대로 겹쳤다.

## 책 내용 뼈대

### 규모 추정

| 항목 | 값 | 계산 근거 |
| --- | --- | --- |
| DAU | 1,000만 명 | 전제 |
| 사용자당 하루 검색 | 10회 | 전제 |
| 질의당 평균 크기 | 20바이트 | 4단어 x 평균 5글자, ASCII 기준 1글자 1바이트 |
| 검색 1회당 백엔드 요청 | 20건 | 글자를 입력할 때마다 요청이 나간다 |
| 평균 QPS | 약 24,000 | 1,000만 x 10 x 20 / 86,400 |
| 최대 QPS | 약 48,000 | 평균의 2배 |
| 하루 신규 검색어 | 약 0.4GB | 1억 질의 x 20바이트 = 2GB, 그중 20%가 신규 |

이 표에서 제일 중요한 줄은 네 번째다. 검색 한 번에 요청이 20번 나간다는 전제가 QPS를 20배로 만든다. 자동완성이 어려운 이유의 절반이 여기서 나온다.

그리고 응답은 100밀리초 안에 와야 한다. 그러지 않으면 사용자가 불편을 느낀다.

### 시스템은 두 부분이다

| | 하는 일 |
| --- | --- |
| 데이터 수집 서비스 | 사용자 질의를 수집해서 질의문과 사용 빈도를 담은 빈도 테이블을 갱신한다 |
| 질의 서비스 | 입력된 접두어에 대해 인기 검색어 5개를 정렬해서 돌려준다 |

실시간으로 수집하고 반영하는 건 부담이 커서, 설계의 출발점을 그렇게 잡지 않는다.

### 왜 SQL로는 안 되나

빈도 테이블에서 `LIKE` 로 접두어를 찾고 `ORDER BY` 로 빈도 정렬하는 방식은 데이터가 많아지면 DB가 병목이 된다. 그래서 트라이로 넘어간다.

### 트라이

- 루트는 빈 문자열이다
- 각 노드는 글자 하나를 저장하고 최대 26개 자식을 가진다
- 노드에 빈도 정보를 함께 저장해서 인기순 결과를 낸다

접두어에 대한 top k를 찾는 비용은 세 단계로 쪼개진다.

| 단계 | 비용 |
| --- | --- |
| 접두어에 해당하는 노드 찾기 | O(p) |
| 그 하위 트리에서 유효 노드 전부 찾기 | O(c) |
| 정렬해서 상위 k개 뽑기 | O(c log c) |
| 합계 | O(p) + O(c) + O(c log c) |

### 최적화 두 가지

| 최적화 | 무엇을 하나 | 효과 | 대가 |
| --- | --- | --- | --- |
| 접두어 최대 길이 제한 | 접두어 길이에 상한을 둔다 | O(p) -> O(1) | 아주 긴 접두어는 자동완성이 안 된다 |
| 노드마다 인기 검색어 캐시 | 각 노드에 상위 5개를 미리 저장한다 | O(c) + O(c log c) -> O(1) | 저장 공간이 더 든다 |

둘을 다 적용하면 전체가 상수 시간이 된다. 접두어가 길어도, 하위에 검색어가 아무리 많아도 조회 비용이 같다. 응답 100밀리초가 요구사항이니 저장 공간을 더 쓰는 대가는 치를 만하다고 책은 적는다.

### 트라이를 어디에 저장하나

| 방식 | 어떻게 |
| --- | --- |
| 문서 저장소 (MongoDB 등) | 매주 새로 만든 트라이를 직렬화해서 저장 |
| 키-값 저장소 | 트라이의 모든 접두어를 키로, 노드에 저장된 데이터를 값으로 바꿔서 해시 테이블처럼 |

### 트라이 샤딩

- 첫 글자로 쪼개는 것이 기본이다. 알파벳이 26자이므로 서버는 최대 26대까지 쓸 수 있다
- 그 이상이 필요하면 계층적 샤딩으로 간다. 예를 들어 'a'로 시작하는 검색어를 두 글자 범위로 더 나눈다
- 글자별 검색어 분포가 고르지 않다. 그래서 과거 질의 패턴을 분석해서 데이터가 균등해지도록 나눈다
- 어떤 검색어가 어느 저장소 서버에 있는지는 샤드 관리자가 관리한다

### 글자마다 요청이 나가는 문제를 어떻게 줄이나

| 방법 | 무엇을 줄이나 |
| --- | --- |
| AJAX 요청 | 페이지를 새로고침하지 않고 목록만 주고받는다 |
| 브라우저 캐싱 | 제안 결과는 짧은 시간 동안 잘 안 바뀌므로 브라우저에 두고 재사용한다 |
| 데이터 샘플링 | 모든 질의를 로깅하면 CPU와 저장 공간을 많이 쓰므로 N개 중 1개만 로깅한다 |

세 번째는 읽을 때 한 번 멈췄던 부분이다. 데이터 샘플링은 요청 수를 줄이는 방법이 아니다. 요청은 그대로 다 오고, 그중 일부만 기록하는 것이다. 즉 질의 서비스의 부담이 아니라 데이터 수집 서비스의 부담을 줄인다. 같은 "줄인다"로 묶으면 헷갈린다.

## 개인적인 질문

### 1. 내 프로젝트 검색이 `like '%키워드%'`인데, 이게 트라이로 바꿀 수 있는 모양인가

전시 커뮤니티 프로젝트의 검색 쿼리가 이렇게 돼 있다.

```sql
where lower(u.nickname) like lower(concat('%', :keyword, '%'))
```

책을 읽고 나서 이게 트라이와 호환되지 않는다는 걸 알았다. 이유는 와일드카드 위치다.

| 쿼리 | 인덱스를 타나 | 트라이로 되나 |
| --- | --- | --- |
| `like '덕%'` | 탄다 (B-tree 범위 스캔) | 된다 |
| `like '%덕%'` | 못 탄다 (풀스캔) | 안 된다 |

트라이는 루트에서 글자를 하나씩 따라 내려가는 자료구조다. 앞에서부터 일치하는 것만 찾을 수 있다. "덕"이 중간에 있는 "오리덕후"를 찾으려면 트라이를 어느 노드에서 시작해야 할지 알 수 없다. B-tree 인덱스가 `'%덕%'`에서 못 쓰이는 이유와 완전히 같은 이유다. 둘 다 앞에서부터 정렬된 구조이기 때문이다.

그래서 이건 내가 실수한 게 아니라 요구사항이 다른 것이었다. 닉네임이나 굿즈 이름은 사용자가 중간 단어로 찾으려 한다. "덕"을 치면 "오리덕후"가 나와야 한다. 그 요구사항을 받은 순간 트라이와 B-tree 인덱스를 둘 다 포기한 셈이다. 지금 데이터가 적어서 풀스캔이 티가 안 나는 상태다.

중간 일치를 유지하면서 풀스캔을 피하려면 트라이가 아니라 전문 검색 인덱스(MySQL full-text, 엘라스틱서치)로 가야 한다. 책이 다루는 자동완성과는 다른 도구다.

정리하면 질문의 답은 "바꿀 수 없다"이고, 그 이유가 이 장에서 트라이를 선택한 이유와 같은 성질이라는 게 내가 얻은 것이다.

### 2. 책은 질의마다 수집하는데 내 프로젝트는 클릭할 때만 기록한다

전시 커뮤니티의 검색 기록 API 문서에 이렇게 적혀 있다.

> 검색 결과에서 유저를 클릭했을 때 호출하세요. 타이핑만으로는 기록되지 않습니다.

책의 데이터 수집 서비스는 반대다. 질의마다 빈도 테이블을 갱신한다. 글자마다 요청이 가니 사실상 타이핑마다다. 왜 다른지 생각해보니 목적이 달랐다.

| | 내 프로젝트 | 책 |
| --- | --- | --- |
| 무엇을 만드나 | 그 사람의 최근 검색 3개 | 전체 사용자의 인기 검색어 랭킹 |
| 누구에게 보이나 | 본인에게만 | 모두에게 |
| 타이핑 중간값이 필요한가 | 필요 없다 ("오", "오리", "오리덕"은 기록 가치가 없다) | 필요하다 (접두어별 인기도가 곧 결과다) |
| 쓰기 주체 | 사용자 한 명의 클릭 | 전체 질의 |

개인화 기록은 완성된 의도만 남기면 되고, 그 의도는 클릭에 드러난다. 반면 접두어 자동완성은 "오"까지 쳤을 때 뭘 보여줄지가 결과물이니 중간값이 데이터 그 자체다.

그런데 책도 모든 질의를 다 기록하지는 않는다. 데이터 샘플링으로 N개 중 1개만 로깅한다. 결국 둘 다 "타이핑마다 쓰기를 날리면 터진다"는 같은 결론에 도달했고, 피하는 방법이 달랐을 뿐이다. 내 쪽은 기록 시점을 클릭으로 늦췄고, 책은 기록 비율을 낮췄다.

### 3. 트라이를 주 1회 재생성하면 그 사이에 뜬 검색어는 어떻게 되나

책은 매주 새로 만든 트라이를 저장한다고 적는다. 그러면 월요일에 생긴 신조어는 다음 주까지 자동완성에 안 나온다.

책도 이걸 알고 조건을 달아둔다. 트라이가 만들어지고 나면 인기 검색어는 그다지 자주 바뀌지 않을 것이라는 전제다. 구글 검색 같은 서비스는 맞는 전제다. 반면 실시간 트렌드를 다루는 서비스는 주 1회로 감당이 안 된다. 책도 트위터처럼 실시간성이 필요한 경우를 따로 언급한다.

그러니 이건 자료구조 문제가 아니라 갱신 주기를 요구사항에서 뽑아내는 문제다. 주기를 줄이면 재생성 비용이 올라가고, 늘리면 신선도가 떨어진다. 어느 쪽 비용을 받을지는 서비스가 결정한다. 9장에서 크롤러 재방문 주기를 정하는 문제와 같은 모양이다.

## 내 프로젝트에서 자동완성을 안 만든 자리

| 책의 구성요소 | 내 프로젝트에 있는 것 |
| --- | --- |
| 질의 서비스 | `like '%키워드%'` 쿼리 (유저 탭, 전시 탭) |
| 트라이 캐시 | 없음 |
| 트라이 DB | 없음 |
| 데이터 수집 서비스 | 검색 기록 저장. 단 클릭 시점에만, 개인별 최대 3개 |
| 빈도 테이블 | 없음 (빈도를 세지 않는다) |

### 자동완성을 붙이려면 무엇이 필요한가

책을 읽고 나서, 내 프로젝트에 자동완성을 붙이는 작업이 생각보다 큰 일이라는 걸 알았다. 지금 있는 걸로는 시작조차 못 한다.

1. 빈도 테이블이 없다. 지금 저장하는 건 "누가 누구를 클릭했다"이고, 자동완성에 필요한 건 "어떤 문자열이 몇 번 검색됐나"다. 데이터 모양이 다르다
2. 검색어 문자열 자체를 저장하지 않는다. 클릭된 대상의 ID만 저장한다. 그래서 과거 데이터로 트라이를 만들 수 없다. 처음부터 다시 모아야 한다
3. 중간 일치 요구사항을 접두어로 바꿀지 결정해야 한다. 자동완성은 접두어 전용이라, 검색 결과는 중간 일치로 두고 자동완성만 접두어로 가는 식의 분리가 필요하다

그래서 지금 규모에서 할 일은 자동완성이 아니라, `%키워드%` 풀스캔이 데이터가 늘었을 때 먼저 터진다는 걸 알고 있는 것이다. 책의 교훈을 그대로 가져오면 "응답 시간 기준을 정하고, 넘으면 자료구조를 바꾼다"가 된다.

### 검색 기록 3개를 유지하는 쪽에서 겪은 것

책과 직접 관련은 없지만 데이터 수집 쪽에서 실제로 겹친 부분이 있다. 검색 기록을 최대 3개로 유지하려면 새로 넣을 때 초과분을 지워야 하는데, 이걸 "개수를 세고 가장 오래된 것 하나를 지운다"로 반복했을 때 동시 요청에서 깨졌다. 두 요청이 같은 행을 지우려 하고, 진 쪽이 예외를 받았다. 지금은 한 번의 벌크 삭제로 바꿔서 몇 건이 지워지든 조용히 끝나게 돼 있다.

책의 데이터 수집 서비스도 같은 성질의 문제를 안고 있다. 전체 질의가 한 빈도 테이블로 쏟아지는데, 그걸 실시간 갱신하지 않고 주기 배치로 미루는 이유에 이 경합 문제도 포함된다고 본다. 쓰기를 모아서 한 번에 하는 쪽이 건드리는 행 수와 무관하게 안전하다.

## 9장, 11장과 연계해서 생각해보자

| 이전 내용 | 13장에서 다시 나오는 자리 |
| --- | --- |
| 9장 블룸 필터 (싼 필터 먼저) | 데이터 샘플링. N개 중 1개만 로깅해서 뒤쪽 부담을 줄인다 |
| 9장 크롤러 재방문 주기 | 트라이 주 1회 재생성. 신선도와 비용의 교환 |
| 11장 읽기 시점 vs 쓰기 시점 | 노드마다 top 5를 미리 저장하는 것이 쓰기 시점 계산이다 |
| 5장 샤딩 | 첫 글자 샤딩의 불균형. 과거 패턴으로 균등 분할 |
| 4주차 쓰기 모아서 날리기 | 빈도 테이블을 주기 배치로 갱신 |

11장과의 연결이 가장 선명했다. 노드마다 인기 검색어 5개를 미리 저장하는 것은, 읽을 때 계산하지 않도록 쓸 때 미리 만들어두는 것이다. 11장의 쓰기 시점 팬아웃과 같은 선택이다. 대가도 같다. 저장 공간을 더 쓰고, 원본이 바뀌면 미리 만든 걸 갱신해야 한다. 그 갱신을 실시간으로 안 하고 주 1회로 미룬 것이 책의 결정이다.

## 스스로 확인해본 것 - QPS가 20배가 되는 지점

규모 추정 표를 다시 계산해보니 이 장의 난이도가 어디서 오는지 분명해졌다.

```
질의 수      = 1,000만 x 10        = 1억 건/일
백엔드 요청  = 1억 x 20            = 20억 건/일
평균 QPS     = 20억 / 86,400       = 약 23,000
```

검색 자체는 하루 1억 건이고 QPS로 치면 1,200 정도다. 그런데 글자마다 요청이 나가면서 24,000이 된다. 20배가 자동완성이라는 기능 하나 때문에 붙는다.

그래서 이 장의 해법이 전부 "요청 하나를 싸게 만들기"에 몰려 있다. 상수 시간 조회(두 가지 최적화), 캐시 계층, 브라우저 캐싱이 다 같은 방향이다. 요청 수를 줄이는 건 포기하고 요청당 비용을 줄이는 쪽을 택한 것이다.

요청 수를 줄이려면 디바운스(입력이 멈추면 보내기)가 떠오르는데 책은 그걸 다루지 않는다. 100밀리초 응답을 요구사항으로 걸어둔 것과 맞물려 보면, 타이핑 중에도 바로 반응하는 경험 자체가 요구사항이었기 때문이라고 이해했다.
