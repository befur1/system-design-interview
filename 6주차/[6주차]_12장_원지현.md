# [6주차] 12장 정리 - 원지현
# 12장_ 채팅 시스템 설계

## 설계 범위
- 1:1 채팅과 최대 100명의 그룹 채팅을 지원함.
- 모바일 앱과 웹을 모두 지원함.
- DAU 5천만 명을 처리할 수 있어야 함.
- 텍스트 메시지만 지원하며, 메시지 길이는 100,000자 이하임.
- 채팅 이력은 영원히 보관함.
- 접속 상태 표시, 여러 기기 동시 접속, 푸시 알림을 지원함.

## 개략적 설계

통신 방식 비교
- 클라이언트는 서로 직접 통신하지 않고 채팅 서비스를 통해 메시지를 주고받음.
- 서버가 새 메시지를 클라이언트에게 먼저 보내야 하므로, 요청-응답 방식의 HTTP만으로는 부족함.
- 폴링: 클라이언트가 주기적으로 새 메시지가 있는지 물어봄. 대부분 새 메시지가 없어 자원 낭비가 심함.
- 롱 폴링: 새 메시지가 생기거나 타임아웃될 때까지 연결을 유지함.
    - 메시지를 받은 서버와 클라이언트가 연결된 서버가 다를 수 있음.
    - 서버가 클라이언트의 연결 종료 여부를 알기 어렵고, 메시지가 없어도 주기적으로 재연결해야 해 비효율적임.
- 웹소켓: 한 번 맺은 연결을 계속 유지하며, 서버와 클라이언트 모두 언제든 먼저 메시지를 보낼 수 있는 양방향 통신 방식임.
    - HTTP 연결로 시작해 웹소켓으로 전환하므로 80, 443 포트를 그대로 사용해 방화벽 환경에서도 잘 동작함.
    - 메시지 송수신 모두 웹소켓을 사용하고, 그 외 기능(로그인, 회원가입, 프로필 관리 등)은 일반 HTTP를 사용함.

서비스 구성
- 무상태 서비스: 로그인, 회원가입, 프로필 관리 등 요청-응답형 서비스로, 로드밸런서 뒤에서 자유롭게 확장함.
    - 서비스 탐색: 클라이언트가 접속할 채팅 서버를 골라주는 핵심 무상태 서비스임.
- 상태 유지 서비스: 채팅 서비스로, 클라이언트는 하나의 채팅 서버와 웹소켓 연결을 유지하며 서버가 죽지 않는 한 다른 서버로 옮기지 않음.
- 제3자 서비스 연동: 앱이 실행 중이지 않아 연결이 없을 때 푸시 알림으로 새 메시지를 알림. (10장과 연결)

저장소
- 일반 데이터(사용자 프로필, 설정, 친구 목록): 관계형 DB에 저장하고 다중화와 샤딩으로 확장함.
- 채팅 이력: 키-값 저장소에 저장함.
    - 수평적 규모 확장이 쉬움.
    - 데이터 접근 지연 시간이 짧음.
    - 관계형 DB는 오래된 데이터를 무작위로 접근하는 롱 테일 부분을 잘 처리하지 못함.
    - 실제로 페이스북 메신저는 HBase, 디스코드는 Cassandra를 사용함.

데이터 모델
- 1:1 채팅 메시지 테이블: message_id(기본 키), message_from, message_to, content, created_at
- 그룹 채팅 메시지 테이블: (channel_id, message_id)를 복합 기본 키로 사용하며, channel_id가 파티션 키 역할을 함.
- 메시지 ID는 고유해야 하고 시간 순서대로 정렬 가능해야 함. created_at은 같은 시각에 여러 메시지가 생길 수 있어 사용할 수 없음.
    - 방법 1: 스노플레이크 같은 전역적 64비트 ID 생성기 사용 (7장과 연결)
    - 방법 2: 채널 안에서만 고유하면 되는 지역적 순서 번호 생성기 사용. 같은 채널 안의 순서만 보장하면 되므로 구현이 더 쉬움.

## 상세 설계

서비스 탐색
- 클라이언트의 위치, 서버 용량 등을 기준으로 가장 적합한 채팅 서버를 추천함.
- 아파치 주키퍼 같은 오픈소스를 사용해, 사용 가능한 채팅 서버를 등록해두고 그중에서 골라줌.
- 동작 흐름
    - 사용자가 로그인을 시도하면 로드밸런서가 API 서버로 요청을 보내고, API 서버가 인증을 처리함.
    - 서비스 탐색이 적합한 채팅 서버를 골라 사용자에게 알려줌.
    - 사용자는 해당 채팅 서버와 웹소켓 연결을 맺음.

1:1 메시지 흐름
- 사용자 A가 채팅 서버 1로 메시지를 보냄.
- 채팅 서버 1이 ID 생성기로 메시지 ID를 받고, 메시지 동기화 큐로 전송함.
- 메시지는 키-값 저장소에 저장됨.
- 사용자 B가 접속 중이면 B가 연결된 채팅 서버 2로 전달되어 웹소켓으로 B에게 전송됨.
- 사용자 B가 접속 중이 아니면 푸시 알림 서버로 알림을 보냄.

여러 기기 간 메시지 동기화
- 각 기기는 해당 기기에서 마지막으로 받은 메시지 ID를 cur_max_message_id로 기억함.
- 수신자가 현재 사용자이고, ID가 cur_max_message_id보다 큰 메시지를 새 메시지로 판단해 가져옴.

소규모 그룹 채팅 흐름
- 그룹 구성원마다 메시지 동기화 큐(수신함)를 두고, 메시지를 각 구성원의 큐에 복사함.
- 각 구성원은 자기 큐만 보면 되므로 동기화가 단순함.
- 구성원 수만큼 메시지를 복사해야 하므로 대규모 그룹에는 비효율적임. (예: 위챗은 그룹 인원을 500명으로 제한함)

접속 상태 표시
- 로그인 시 접속 상태 서버가 상태를 온라인으로 바꾸고, 마지막 활동 시각을 키-값 저장소에 기록함.
- 로그아웃 시 상태를 오프라인으로 바꿈.
- 연결이 끊긴 경우: 클라이언트가 일정 주기로 박동(heartbeat) 이벤트를 보내고, 정해진 시간 동안 박동이 오지 않으면 오프라인으로 바꿈. 순간적인 연결 끊김마다 상태가 바뀌는 문제를 막음.
- 상태 정보 전송: 친구 관계마다 채널을 두는 발행-구독 모델로 상태 변화를 전달함. 그룹이 클 경우에는 사용자가 그룹에 들어가거나 새로고침할 때만 상태를 가져옴.

## 마무리: 궁금해서 더 찾아본 부분들

읽음 표시(카카오톡의 숫자 "1")는 어떻게 구현할까?
- 사용자마다 채팅방별로 마지막으로 읽은 메시지 ID(last_read_message_id)를 저장함.
- 안 읽은 메시지 수는 "채팅방의 최신 메시지 ID - 내가 마지막으로 읽은 메시지 ID"로 계산할 수 있어, 메시지마다 읽음 여부를 따로 저장할 필요가 없음.
- 그룹 채팅에서 각 메시지 옆의 숫자는 "그 메시지 ID보다 last_read_message_id가 작은 구성원 수"로 구할 수 있음.
- 메시지 ID가 채팅방 안에서 순서대로 증가한다는 성질(지역적 순서 번호) 덕분에 가능한 방식임.

앱을 보고 있는데 푸시 알림이 또 오는 문제
- 사용자가 웹소켓으로 이미 메시지를 받았는데 푸시 알림까지 오면 중복으로 느껴짐.
- 접속 상태와 현재 보고 있는 채팅방 정보를 활용해, 해당 채팅방을 보고 있는 동안에는 푸시를 보내지 않도록 처리함.
- 반대로 여러 기기 중 하나만 접속해 있다면 나머지 기기에는 푸시를 보낼지 결정해야 함. (10장 알림 설정과 연결)

대규모 그룹 채팅은 어떻게 할까?
- 책의 방식은 그룹 구성원마다 메시지를 복사하므로 인원이 많아지면 비용이 커짐. (위챗은 500명으로 제한)
- 수천 명 이상의 오픈채팅방 같은 경우에는, 11장의 읽기 시점 팬아웃처럼 메시지를 채널에 한 번만 저장하고 구성원이 읽을 때 가져오는 방식이 더 적합함.
- 즉 11장의 "푸시 vs 풀" 트레이드오프가 채팅 시스템에서도 그룹 크기에 따라 똑같이 나타남.
