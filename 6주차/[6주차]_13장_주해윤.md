## 13장 검색어 자동완성 시스템

---

### 문제 이해 및 설계 범위 확정

- 빠른 응답 속도, 연관성, 정렬, 규모 확장성, 고가용성 필요
- 일간 능동 사용자: 천만명
- 평균적으로 한 사용자는 매일 10건의 검색을 수행
- 질의할 때마다 평균적으로 20바이트의 데이터를 입력
- 검색창에 글자를 입력할 때마다 클라이언트는 검색어 자동완성 백엔드에 요청을 보냄, 평균적으로 1회 검색당 20건의 요청이 백엔드로 전달
- 대략 초당 24,000건의 질의(QPS) 발생
- `최대 QPS = QPS X 2 = 대략 48,000`
- 질의 가운데 20% 정도는 신규 검색어라고 가정, 대략 0.4GB 정도

### 개략적 설계안 제시 및 동의 구하기

**데이터 수집 서비스**

- 사용자가 입력한 질의를 실시간으로 수집하는 시스템
- 빈도 테이블: 질의문과 사용빈도를 저장

**질의 서비스**

- 주어진 질의에 다섯 개의 인기 검색어를 정렬해 내놓는 서비스
- 빈도 테이블은 두 개의 필드로 구성
    - `query`: 질의문을 저장
    - `frequency`: 질의문이 사용된 빈도를 저장
- 사용자가 검색창에 접두어를 입력하면 해당 접두어로 시작하는 검색어 가운데 사용빈도가 가장 높은 다섯 개를 반환

```
SELECT * FROM frequency_table
WHERE query LIKE 'prefix%'
ORDER BY frequency DESC
LIMIT 5
```

- 데이터 양이 적을 때는 사용할 수 있지만 데이터가 많아지면 데이터베이스가 병목이 될 수 있음

### 상세 설계

- 상세 설계에서 다룰 컴포넌트
    - 트라이 자료구조
    - 데이터 수집 서비스
    - 질의 서비스
    - 규모 확장이 가능한 저장소
    - 트라이 연산

**트라이 자료구조**

- 관계형 데이터베이스에서 인기 검색어 다섯 개를 골라내는 방식은 효율적이지 않으므로 트라이를 사용
- 트라이는 문자열을 간략하게 저장할 수 있는 트리 형태의 자료구조
- 문자열을 꺼내는 연산에 초점을 맞추어 설계됨

```
root
├─ t
│  ├─ tr
│  │  ├─ tre ─ tree
│  │  ├─ tru ─ true
│  │  └─ try
│  └─ to ─ toy
└─ w
   └─ wi
      ├─ wis ─ wish
      └─ win
```

- 트라이의 특징
    - 루트 노드는 빈 문자열을 나타냄
    - 각 노드는 글자 하나를 저장하며, 26개의 자식 노드를 가질 수 있음
    - 각 노드는 하나의 단어 또는 접두어 문자열을 나타냄
- 기본 트라이에 사용빈도를 기준으로 정렬된 결과를 제공하기 위해 노드에 빈도 정보도 저장
    
    ```
    root
    ├─ t
    │  ├─ tr
    │  │  ├─ tre ─ tree: 10
    │  │  ├─ tru ─ true: 35
    │  │  └─ try: 29
    │  └─ to ─ toy: 14
    └─ w
       └─ wi
          ├─ wis ─ wish: 25
          └─ win: 50
    ```
    
- 용어
    - `p`: 접두어의 길이
    - `n`: 트라이 안에 있는 노드의 개수
    - `c`: 주어진 노드의 자식 노드 개수
- 가장 많이 사용된 검색어 `k`개를 찾는 과정
    1. 접두어를 표현하는 노드를 찾음
        - 시간 복잡도: `O(p)`
    2. 해당 노드부터 시작하는 하위 트리를 탐색하여 모든 유효 노드를 찾음
        - 시간 복잡도: `O(c)`
    3. 유효 노드를 정렬하여 가장 인기 있는 검색어 `k`개를 찾음
        - 시간 복잡도: `O(c log c)`
- 전체 시간 복잡도: `O(p) + O(c) + O(c log c)`
- 최악의 경우 `k`개의 결과를 얻기 위해 전체 트라이를 검색해야 할 수 있음
    
    ```
    입력: 접두어 "be", k=2
    
    1. 접두어 노드 be를 찾음
    2. be의 하위 트리에서 유효 노드를 탐색
       ├─ bee: 20
       ├─ beer: 10
       ├─ best: 35
       └─ bet: 29
    3. 빈도순으로 정렬
    4. 상위 2개 반환
    
    결과: best: 35, bet: 29
    ```
    

**트라이 최적화**

1. 접두어의 최대 길이 제한
    - 사용자가 검색창에 긴 검색어를 입력하는 일은 거의 없다고 가정
    - 접두어의 최대 길이를 작은 상수값으로 제한하면 접두어 노드를 찾는 시간 복잡도는 `O(p)`에서 `O(1)`로 변경
2. 노드에 인기 검색어 캐시
    - 각 노드에 `k`개의 인기 검색어를 저장하면 전체 트라이를 탐색하지 않아도 됨
    - 자동완성 제안은 보통 5~10개 정도이므로 `k`는 작은 값
    - 각 노드에 질의어를 저장할 공간이 많이 필요하지만 응답속도가 중요할 때는 저장공간을 희생할 가치가 있음
    - 접두어 노드를 찾는 시간 복잡도: `O(1)`
    - 인기 검색어 `k`개를 찾는 시간 복잡도: `O(1)`
    - 최적화 적용 후 전체 알고리즘의 시간 복잡도: `O(1)`

**데이터 수집 서비스**

- 사용자가 검색창에 문자를 입력할 때마다 트라이를 실시간으로 갱신하는 방식은 실용적이지 않음
    - 매일 수천만 건의 질의가 입력될 때마다 트라이를 갱신하면 질의 서비스가 느려짐
    - 트라이가 만들어지고 나면 인기 검색어는 자주 바뀌지 않으므로 자주 갱신할 필요가 없음
- 데이터의 출처와 사용 방식에 따라 갱신 주기를 결정
    - 실시간 애플리케이션은 제안 검색어를 신선하게 유지해야 할 수 있음
    - 검색 엔진은 제안 검색어를 자주 갱신하지 않아도 될 수 있음
- 트라이를 만드는 데이터는 데이터 분석 서비스나 로깅 서비스에서 가져옴

```
데이터 분석 서비스 로그
        ↓
    로그 취합 서버
        ↓
     취합된 데이터
        ↓
      작업 서버
        ↓ 매주 갱신
   트라이 데이터베이스
        ↓ 매주 상태 스냅샷
      트라이 캐시
```

**데이터 분석 서비스 로그**

- 검색창에 입력된 질의에 관한 원본 데이터를 보관
- 새로운 데이터가 추가되기만 하며 수정은 이루어지지 않음
- 로그 데이터에는 인덱스를 걸지 않음

**로그 취합 서버**

- 데이터 분석 서비스의 로그는 양이 많고 데이터 형식도 제각각일 수 있으므로 시스템이 쉽게 소비할 수 있도록 취합
- 데이터 취합 주기는 서비스 용도에 따라 달라짐
    - 실시간 애플리케이션은 짧은 취합 주기가 필요할 수 있음
    - 대부분의 경우 일주일에 한 번 정도 취합해도 충분할 수 있음

**취합된 데이터**

- 일정 기간 동안 질의문이 사용된 횟수를 합산하여 저장
- `time` 필드는 해당 주가 시작된 날짜
- `frequency` 필드는 해당 질의가 그 주에 사용된 횟수의 합

**작업 서버**

- 주기적으로 비동기 작업을 실행하는 서버 집합
- 트라이 자료구조를 만들고 트라이 데이터베이스에 저장

**트라이 캐시**

- 분산 캐시 시스템
- 트라이 데이터를 메모리에 유지하여 읽기 연산 성능을 높임
- 매주 트라이 데이터베이스의 스냅샷을 가져와 갱신

**트라이 데이터베이스**

- 트라이를 저장하는 지속성 저장소
- 저장 방법
    1. 문서 저장소
        - 새 트라이를 매주 만들기 때문에 주기적으로 트라이를 직렬화하여 데이터베이스에 저장
        - MongoDB 같은 문서 저장소를 사용할 수 있음
    2. 키-값 저장소
        - 트라이에 보관된 모든 접두어를 해시 테이블의 키로 변환
        - 각 트라이 노드에 보관된 데이터를 해시 테이블의 값으로 변환

**질의 서비스**

1. 검색 질의가 로드밸런서로 전송됨
2. 로드밸런서는 질의를 API 서버로 전송
3. API 서버는 트라이 캐시에서 데이터를 가져와 자동완성 검색어 제안 응답을 구성
4. 데이터가 트라이 캐시에 없으면 트라이 데이터베이스에서 가져와 캐시에 채움
    - 캐시 메모리가 부족하거나 캐시 서버에 장애가 있으면 캐시 미스가 발생할 수 있음
- 최적화
    - AJAX 요청
        - 브라우저는 AJAX 요청을 보내 자동완성 검색어 목록을 가져옴
        - 요청과 응답을 위해 페이지를 새로고침할 필요가 없음
    - 브라우저 캐싱
        - 자동완성 검색어 제안 결과는 짧은 시간 동안 자주 바뀌지 않음
        - 제안 검색어를 브라우저 캐시에 저장하면 후속 질의 결과를 캐시에서 가져올 수 있음
        - `cache-control` 헤더의 `private`는 응답이 해당 사용자의 캐시에만 보관될 수 있다는 의미
        - `max-age=3600`은 캐시 항목이 3,600초 동안 유효하다는 의미
    - 데이터 샘플링
        - 대규모 시스템에서 모든 질의를 로깅하면 CPU 자원과 저장공간이 많이 소모됨
        - `N`개 요청 가운데 1개만 로깅하도록 함

**트라이 연산**

- 트라이는 검색어 자동완성 시스템의 핵심 컴포넌트
- 트라이 생성
    - 작업 서버가 담당
    - 데이터 분석 서비스의 로그나 데이터베이스에서 취합된 데이터를 사용
- 트라이 갱신
    1. 매주 한 번 갱신
        - 새로운 트라이를 만든 다음 기존 트라이를 대체
    2. 각 노드를 개별적으로 갱신
        - 성능이 좋지 않아 본 설계에서는 선택하지 않음
        - 트라이가 작을 때 고려할 수 있음
        - 특정 노드를 갱신하면 인기 검색어 질의 결과를 저장한 모든 상위 노드도 갱신해야 함
- 검색어 삭제
    - 혐오성, 폭력적, 성적으로 노골적이거나 위험한 질의어는 자동완성 결과에서 제거
    - 트라이 캐시 앞에 필터 계층을 두어 부적절한 질의어가 반환되지 않도록 함
    - 필터 계층을 사용하면 필터 규칙에 따라 검색 결과를 자유롭게 변경할 수 있음
    - 데이터베이스에서 검색어를 물리적으로 삭제하는 작업은 다음번 업데이트 사이클에 비동기로 처리

**저장소 규모 확장**

- 트라이의 크기가 한 서버에 넣기에 너무 큰 경우 샤딩으로 해결
- 영어만 지원한다면 첫 글자를 기준으로 샤딩할 수 있음
    - 서버 두 대: `a~m`, 나머지 글자로 분할
    - 서버 세 대: `a~i`, `j~r`, 나머지 글자로 분할
- 영어 알파벳은 26자이므로 이 방식으로 사용할 수 있는 서버는 최대 26대로 제한
- 더 많은 서버가 필요하면 검색어의 두 번째 글자까지 이용해 계층적으로 샤딩
- 각 글자로 시작하는 검색어의 수가 다르므로 데이터를 균등하게 분배하기 어려움
- 과거 질의 데이터 패턴을 분석하여 샤딩
    - 검색어 대응 샤드 관리자가 검색어가 어느 저장소 서버에 저장되는지 관리
    - 검색어 분포에 따라 여러 시작 문자를 하나의 샤드에 묶을 수 있음

```
웹 서버
   │
   ├─ 1. 검색어가 어느 샤드에 있는지 질의
   ↓
검색어 대응 샤드 관리자
   │
   └─ 샤드 위치 반환
   ↓
웹 서버
   │
   └─ 2. 해당 샤드에서 데이터 추출
   ↓
샤드 1 / 샤드 2 / ... / 샤드 N
```

### +) 논의할 사항 및 경험과 연결

- 사용자가 검색어를 입력하는 프로젝트에서 자동완성 기능을 구현한다면, 데이터베이스에서 매번 `LIKE` 검색을 수행하는 방식과 트라이를 사용하는 방식 중 무엇이 적합할까요?
    - 데이터가 적을 때는 데이터베이스의 `LIKE 'prefix%'` 검색으로도 구현할 수 있습니다. 하지만 검색어와 요청량이 많아지면 데이터베이스가 병목이 될 수 있으므로 접두어를 빠르게 탐색할 수 있는 트라이가 적합합니다. 각 트라이 노드에 인기 검색어를 캐시하면 하위 트라이 전체를 탐색하지 않고도 빠르게 결과를 반환할 수 있습니다.
- 프로젝트를 여러 국가에 제공한다면 모든 사용자에게 하나의 자동완성 결과를 보여줘도 될까요? 국가마다 다른 트라이를 운영하면 어떤 장단점이 있을까요?
    - 국가마다 검색 경향과 인기 검색어가 다르므로 국가별 트라이를 사용하면 사용자에게 더 연관성 높은 검색어를 제공할 수 있습니다. 트라이를 CDN에 저장하면 사용자와 가까운 위치에서 결과를 제공하여 응답속도를 높일 수 있습니다. 다만 국가별 트라이를 별도로 생성하고 갱신해야 하므로 관리할 데이터와 작업량이 증가합니다.
- 한글과 영어가 함께 입력되는 기능에서 영문 알파벳을 기준으로 한 샤딩을 그대로 사용할 수 있을까요? 다국어 자동완성을 지원하려면 무엇이 달라져야 할까요?
    - 여러 문자 체계를 지원하려면 트라이에 유니코드 데이터를 저장해야 합니다. 영문 첫 글자만으로 샤딩하면 다국어 검색어를 적절히 분산하기 어려울 수 있으므로, 지원할 언어와 문자 체계를 고려하여 저장 및 분할 기준을 정해야 합니다.
- 인기 검색어를 매주 한 번 집계하는 방식과 사용자의 입력을 실시간으로 반영하는 방식 중 각자 프로젝트에는 무엇이 적합할까요?
    - 검색 경향이 자주 바뀌지 않는 기능이라면 주기적으로 로그를 취합하여 트라이를 갱신하는 방식으로 충분할 수 있습니다. 반면 코템포에서 갑자기 특정 콘텐츠가 화제가 되거나 코지에서 특정 그룹의 검색량이 급증하는 상황을 빠르게 반영하려면 실시간 처리가 필요합니다. 이 경우 샤딩으로 처리할 데이터의 양을 줄이고 최근 검색어에 더 높은 가중치를 주는 순위 모델을 고려할 수 있습니다.
- 자동완성 시스템을 운영한다면 `QPS`, 응답시간, 캐시 적중률, 트라이 갱신 주기 중 무엇을 우선 확인해야 할까요?
    - 응답시간은 사용자가 검색창에 문자를 입력할 때 직접 체감하는 성능이므로 우선 확인하는 것이 적절합니다. 이후 `QPS`를 통해 요청이 몰렸는지, 캐시 적중률을 통해 트라이 탐색이나 저장소 접근이 증가했는지 확인할 수 있습니다. 자동완성 결과가 현재 검색 추이를 제대로 반영하는지 판단하려면 트라이의 마지막 갱신 시점도 함께 확인해야 합니다.

**질문: 인기 검색어가 갑자기 바뀌어도 매주 한 번만 트라이를 갱신해도 될까?**

가정:

- 자동완성 질의는 트라이 캐시를 통해 빠르게 처리한다.
- 작업 서버는 검색 로그를 취합하여 매주 한 번 새로운 트라이를 생성한다.
- 특정 이벤트로 새로운 검색어의 빈도가 갑자기 높아졌다.

**기존 갱신 주기를 유지한다고 생각한다면**

새롭게 인기를 얻은 검색어가 자동완성 결과에 늦게 반영되는 문제를 허용할 수 있을까요?

**실시간으로 반영해야 한다고 생각한다면**

지속적으로 들어오는 검색 데이터를 처리하면서 트라이와 캐시를 어떻게 갱신할까요?
