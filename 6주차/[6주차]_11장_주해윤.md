## 11장 뉴스 피드 시스템 설계

---

> 뉴스 피드는 홈 페이지 중앙에 지속적으로 업데이트되는 스토리들로, 사용자 상태 정보 업데이트, 사진, 비디오, 링크, 앱 활동, 그리고 팔로하는 사람들, 페이지, 또는 그룹으로부터 나오는 ‘좋아요’ 등을 포함한다.
> 

### 문제 이해 및 설계 범위 확정

- 모바일 앱, 웹 모두 지원해야 함
- 중요한 기능: 뉴스 피드 페이지에 새로운 스토리 올릴 수 있어야 함, 친구들이 올리는 스토리를 볼 수 있어야 함
- 스토리는 시간 흐름 역순으로 표시
- 한 명의 사용자는 최대 5,000명의 친구를 가질 수 있음
- 트래픽 규모: 매일 천만 명이 방문
- 스토리에는 이미지나 비디오 등의 미디어 파일 포함 가능

### 개략적 설계안 제시 및 동의 구하기

(1) 피드 발행: 사용자가 스토리를 포스팅하면 해당 데이터를 캐시와 데이터베이스에 기록, 새 포스팅은 친구와 뉴스 피드에도 전송됨

(2) 뉴스 피드 생성: 지면 관계상 뉴스 피드는 모든 친구의 포스팅을 시간 흐름 역순으로 모아서 만든다고 가정

**뉴스 피드 API**

- 클라이언트가 서버와 통신하기 위해 사용하는 수단
- 피드 발행 API: `POST /v1/me/feed`
    - 인자: 바디 - 포스팅 내용, Authorization 헤더 - API 호출을 인증하기 위해 사용
- 피드 읽기 API: `GET /v1/me/feed`
    - 인자: Authorization 헤더 - API 호출을 인증하기 위해 사용

**피드 발행**

- 사용자: 모바일 앱이나 브라우저에서 새 포스팅을 올리는 주체
    
    `POST /v1/me/feed` API 사용
    
    ↓
    
- 로드 밸런서: 트래픽을 웹 서버들로 분산
    
    ↓
    
- 웹 서버: HTTP 요청을 내부 서비스로 중계하는 역할 담당
    
    ↓
    
- 포스팅 저장 서비스: 새 포스팅을 데이터베이스와 캐시에 저장
- 포스팅 전송 서비스: 새 포스팅을 친구의 뉴스 피드에 푸시함, 뉴스 피드 데이터는 캐시에 보관하여 빠르게 읽어갈 수 있도록 함
- 알림 서비스: 친구들에게 새 포스팅이 올라왔음을 알리거나, 푸시 알림을 보내는 역할을 담당

**뉴스 피드 생성**

- 사용자: 뉴스 피드를 읽는 주체
    
    `GET /v1/me/feed` API 사용
    
    ↓
    
- 로드 밸런서: 트래픽을 웹 서버들로 분산
    
    ↓
    
- 웹 서버: 트래픽을 뉴스 피드 서비스로 보냄
    
    ↓
    
- 뉴스 피드 서비스: 캐시에서 뉴스 피드를 가져옴
- 뉴스 피드 캐시: 뉴스 피드를 렌더링할 때 필요한 피드 ID를 보관

### 상세 설계

**피드 발행 흐름**

```
사용자 단말(웹 브라우저·모바일 앱)
  ├─ DNS
  └─ 요청: /v1/me/feed?content=hello&auth_token={auth_token}
      ↓
	로드밸런서
      ↓
웹 서버(인증·처리율 제한)
  ├─ 알림 서비스
  ├─ 포스팅 저장 서비스 → 포스트 캐시 → 포스팅 데이터베이스
  └─ 포스팅 전송 서비스
      ├─ 1. 친구 ID 목록 추출 → 그래프 데이터베이스
      ├─ 2. 친구 데이터 추출 → 사용자 정보 캐시 → 사용자 정보 데이터베이스
      └─ 3. 메시지 큐
          ↓
          4. 포스팅 전송 작업 서버
          ↓
          5. 뉴스 피드 캐시
```

- 웹 서버: 클라이언트와 통신할 뿐 아니라 인증이나 처리율 제한 등의 기능도 수행
    - 올바른 인증 토큰을 Authorization 헤더에 넣고 API를 호출하는 사용자만 포스팅할 수 있어야 함
    - 스팸을 막고 유해한 콘텐츠가 자주 올라오는 것을 방지하기 위해서 특정 기간 동안 한 사용자가 올릴 수 있는 포스팅의 수에 제한을 두어야 함
- 포스팅 전송(팬아웃) 서비스: 어떤 사용자의 새 포스팅을 그 사용자와 친구 관계에 있는 모든 사용자에게 전달하는 과정
    - 쓰기 시점에 팬아웃하는 모델: 포스팅이 완료되면 바로 해당 사용자의 캐시에 해당 포스팅을 기록
        - 장점: 뉴스 피드 실시간으로 갱신됨 → 뉴스 피드를 읽는 데 드는 시간 단축
        - 단점: 친구가 많은 사용자의 경우 친구 목록을 가져오고 그 목록에 있는 사용자 모두의 뉴스 피드를 갱신하는 데 많은 시간이 소요될 수 있음(핫키 문제), 컴퓨팅 자원 낭비
    - 읽기 시점에 팬아웃하는 모델: 피드를 읽어야 하는 시점에 뉴스 피드 갱신
        - 장점: 비활성화된 사용자에 경우에 유리, 핫키 문제 발생 x
        - 단점: 읽는 데 많은 시간 소요
- 팬아웃 서비스 동작 흐름
    1. 그래프 데이터베이스에서 친구 ID 목록을 가져옴
    2. 사용자 정보 캐시에서 친구들의 정보를 가져온 후 사용자 설정에 따라 친구 가운데 일부 거름
    3. 친구 목록과 새 스토리의 포스팅 ID를 메시지 큐에 넣음
    4. 팬아웃 작업 서버가 메시지 큐에서 데이터를 꺼내어 뉴스 피드 데이터를 뉴스 피드 캐시에 넣음, <포스팅 ID, 사용자 ID>의 순서쌍을 보관하는 매핑 테이블

**피드 읽기 흐름**

```
사용자 단말(웹 브라우저·모바일 앱)
  ├─ DNS
  ├─ CDN: 이미지·비디오 등 미디어 콘텐츠
  └─ 1. 요청: /v1/me/feed
      ↓
	로드밸런서
      ↓ 2
웹 서버(인증·처리율 제한)
      ↓ 3
뉴스 피드 서비스
  ├─ 4. 뉴스 피드 캐시
  ├─ 5. 사용자 정보 캐시 → 사용자 정보 데이터베이스
  └─ 5. 포스팅 캐시 → 포스팅 데이터베이스
      ↓
6. 사용자 단말에 뉴스 피드 반환
```

**캐시 구조**

```
뉴스 피드: 뉴스 피드
-----
콘텐츠: 인기 콘텐츠, 일반 콘텐츠
-----
소셜 그래프: 팔로어, 팔로잉
-----
행동: '좋아요', 답글, 기타
-----
횟수: 좋아요 횟수, 답글 횟수, 기타
```

### +) 논의할 사항 및 경험과 연결

- 프로젝트에서 피드·게시글 목록처럼 조회가 많은 기능을 구현했다면, 원본 데이터는 `SQL`에 저장하고 조회 결과는 `NoSQL`이나 캐시에 두는 방식이 적합했을까요? 하나의 저장소만 사용했을 때 어떤 한계가 있었을지 이야기해 봅시다.
    - SQL: 관계형 데이터베이스로, 데이터를 정해진 스키마에 따라 테이블 형태로 저장
    - NoSQL: 비관계형 데이터베이스로, 정해진 테이블 구조에 얽매이지 않고 다양한 형태로 데이터를 저장
    - 사용자·게시물처럼 관계와 일관성이 중요한 원본 데이터는 SQL에 저장하는 것이 적합합니다. 반면 뉴스 피드처럼 빠른 조회가 중요하고 `<사용자 ID, 포스팅 ID>` 형태로 단순하게 접근하는 데이터는 NoSQL이나 캐시에 저장할 수 있습니다. 하나의 저장소만 사용하면 관계형 조회 또는 대규모 분산과 빠른 조회 중 한쪽 요구사항을 만족시키기 어려울 수 있습니다.
- 새로운 게시물을 모든 사용자에게 미리 전달하는 **쓰기 시점 팬아웃**과, 사용자가 조회할 때 피드를 만드는 **읽기 시점 팬아웃** 중 각자 프로젝트에는 어떤 방식이 적합할까요? 사용자 수와 팔로어 수가 늘어나면 선택이 달라질까요?
    - 일반 사용자는 쓰기 시점에 피드를 미리 만들어 빠르게 조회하도록 하고, 팔로어가 매우 많은 사용자는 읽기 시점에 게시물을 합치는 혼합 방식이 적합할 수 있습니다. 사용자 수와 팔로어 수가 적을 때는 쓰기 시점 팬아웃이 단순하지만, 규모가 커지면 한 번의 게시물 작성으로 너무 많은 피드를 갱신하는 핫키 문제가 발생할 수 있으므로 선택이 달라질 수 있습니다.
- 게시물 저장에는 성공했지만 메시지 큐나 팬아웃 작업에 실패했다면 사용자에게 성공 응답을 보내도 될까요? 재시도 과정에서 피드가 누락되거나 중복 생성되는 문제는 어떻게 처리할 수 있을까요?
    - 게시물 원본이 정상적으로 저장되었다면 게시물 작성 자체는 성공한 것으로 응답하고, 피드 반영은 메시지 큐를 통해 다시 시도할 수 있습니다. 다만 재시도로 같은 피드가 중복 생성되지 않도록 `<사용자 ID, 포스팅 ID>` 조합을 기준으로 중복 여부를 확인해야 합니다. 재시도 횟수를 초과한 작업은 별도로 기록하고 모니터링하여 피드 누락을 확인할 수 있어야 합니다.
- 웹 서버를 무상태로 운영하고 메시지 큐로 포스팅 저장과 피드 생성을 분리한다면 어떤 장점이 있을까요? 반대로 처리 결과가 즉시 반영되지 않는 문제를 사용자가 어떻게 인지하게 해야 할까요?
    - 웹 서버가 사용자 상태를 직접 보관하지 않으면 서버를 자유롭게 추가하거나 제거할 수 있어 수평적 확장이 쉬워집니다. 메시지 큐로 게시물 저장과 피드 생성을 분리하면 팬아웃 작업이 느리거나 일시적으로 실패해도 게시물 작성 요청을 계속 처리할 수 있습니다. 다만 피드 반영이 지연될 수 있으므로 사용자에게 게시물이 등록되었지만 피드 반영에는 시간이 걸릴 수 있음을 표시하거나, 작성한 게시물을 본인의 화면에는 우선 보여주는 방식이 필요합니다.
- 피드 시스템을 운영한다면 `QPS`, 피드 조회 지연시간, 캐시 적중률, 메시지 큐 대기량 중 무엇을 가장 먼저 확인해야 할까요? 각자 프로젝트에서 실제 장애나 성능 저하를 가장 빠르게 발견할 수 있었던 지표와 연결해 이야기해 봅시다.
    - 피드 조회 지연시간은 사용자가 직접 체감하는 성능이므로 우선 확인하는 것이 적절합니다. 이후 `QPS`로 트래픽이 몰렸는지, 캐시 적중률 저하로 데이터베이스 부하가 증가했는지, 메시지 큐 적체로 피드 반영이 늦어졌는지 확인할 수 있습니다. 따라서 조회 지연시간을 중심으로 원인을 파악할 수 있는 지표들을 함께 모니터링해야 합니다.

**질문: 포스팅 저장에 성공하면 사용자에게 성공 응답을 보내도 될까?**

가정:

- 포스팅 데이터베이스 저장은 완료되었다.
- 친구들의 뉴스 피드에 반영하는 작업은 메시지 큐를 통해 비동기로 처리한다.
- 메시지 큐에 이벤트를 넣는 과정에서 오류가 발생했다.

**바로 성공 응답을 보낸다고 생각한다면**

피드에 반영되지 않은 포스팅은 어떻게 복구할까요?

**성공 응답을 보내면 안 된다고 생각한다면**

클라이언트의 재시도로 포스팅이나 피드가 중복 생성되는 문제는 어떻게 막을까요?
