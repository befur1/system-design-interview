## 12장 요약

채팅 시스템도 일대일 채팅 앱이냐 그룹 채팅 앱이냐에 따라 설계가 달라져야함. 그래서 요구사항이 뭐고 어떤 채팅 시스템을 설계해야하는지 확실히 하는 게 중요함

메시지 송신 클라이언트 → 채팅 서비스(메시지 저장 및 전달) → 메세지 수신 클라이언트

메세지 송신 시나리오:

- 송신 클라이언트는 메세지를 채팅 서비스에 보낼 때, 책에서는 웹에서 쓰이는 HTTP 프로토콜을 사용하여 접속함.
- 채팅 서비스와의 접속에는 keep-alive 헤더를 사용하여 클라이언트와 서버 사이의 연결을 끊지 않고 유지할 수 있고, TCP 핸드셰이크 횟수를 줄일 수 있게 됨

메세지 수신 시나리오:

- HTTP는 클라이언트가 연결을 만드는 프로토콜이지만, 서버에서 클라이언트로 보내는 데는 쉽게 쓸 수 없음
- 서버가 연결을 만드는 것처럼 동작할 수 있도록 하는 기법에 폴링(polling), 롱 폴링(long polling), 웹소켓(WebSocket) 등이 있음

### 폴링

클라이언트가 주기적으로 서버에게 새 메시지가 있느냐고 물어보는 방법

- 폴링을 자주하면 비용이 올라감
- 답해줄 메세지가 없을 때 폴링을 하면 서버 자원이 낭비되는 꼴임

### 롱 폴링

폴링이 비효율적이어서 나온 기법으로, 클라이언트가 폴링을 시도하고 새 메시지를 대기하다가 새 메시지를 받거나 TTL이 되면 연결이 종료되고 다시 새로운 요청을 보내는 방식

단점:

- 메시지를 보내는 클라이언트와 수신하는 클라이언트가 같은 채팅 서버에 접속되지 않을 수 있음
- 서버는 클라이언트가 연결을 해제했는지 알 좋은 방법이 없음
- 메시지를 많이 받지 않는 클라이언트도 타임아웃이 일어날 때마다 주기적으로 다시 접속하게 됨

### 폴링 vs 롱 폴링 - 참고 자료

책이 롱 폴링 단점으로 든 세 가지 중 **폴링과 공유하는 건 ③ 하나뿐임**. ①②는 롱 폴링 특유의 문제

| 단점 | 폴링 | 롱 폴링 |
| --- | --- | --- |
| ① 송신자·수신자가 다른 서버에 붙음 | 해당 없음 | **핵심 문제** |
| ② 연결 해제를 알 방법이 없음 | 거의 해당 없음 | 문제 |
| ③ 조용한 클라이언트도 주기적 재접속 | **더 심함** | 문제 |

#### 구조가 다름 — 여기서 ①②가 갈림

```
폴링      클라이언트 "새 거 있어?" → 서버가 DB 읽고 → "이거"
          어느 서버에 물어보든 DB는 같으니 상관없음      ← 당겨오는(pull) 구조

롱 폴링   클라이언트 ──연결 유지──> 서버 A (메시지 도착을 기다리는 중)
          그런데 메시지는 서버 B 로 들어옴
          서버 A 는 그걸 모름                          ← 기다리는(wait) 구조
```

**폴링은 저장소만 보면 되는데, 롱 폴링은 서버가 "메시지가 왔다"는 이벤트를 알아야 함.** HTTP 서버는 무상태라 로드밸런서가 요청을 아무 서버에나 보내는데, 폴링은 그래도 되지만 롱 폴링은 안 됨 — 연결을 붙잡고 있는 서버가 특정돼 있으니까

→ 그래서 **서버끼리 알려주는 장치(pub/sub 같은)가 추가로 필요해짐**

#### ② 도 같은 뿌리

롱 폴링은 연결을 붙잡고 있어서, **클라이언트가 죽어도 서버는 모르고 계속 자원을 쥐고 있음**

폴링은 애초에 연결을 안 들고 있음. 요청이 안 오면 그냥 안 오는 거라 낭비가 없음

#### ③ 은 오히려 폴링이 더 나쁨

|  | 재접속 주기 |
| --- | --- |
| 폴링 | **설정한 주기마다 무조건** (5초면 5초마다) |
| 롱 폴링 | 메시지가 오거나 **타임아웃될 때만** |

### 웹소켓

웹소켓 연결은 클라이언트가 시작하며, 처음에 HTTP 연결이 되면 서버는 클라이언트에게 비동기적으로 메세지를 전송할 수 있음

- 웹소켓은 80이나 443처럼 HTTP(S)가 쓰는 기본 포트를 그대로 사용하여 방화벽이 있는 환경에서도 동작이 가능
- 또한, 웹소켓은 양방향 메세지 전송까지 가능함
- 웹소켓을 통해 송신과 수신을 동일한 프로토콜로 사용할 수 있음
- 유의할 점은 웹소켓 연결이 오랫동안 유지되어야 하기 때문에 서버 측에서 연결 관리를 효율적으로 해야함

#### 무상태 서비스

무상태 서비스는 로드밸런서 뒤에 위치하고, 로드밸런서가 요청을 그 경로에 맞는 서비스로 정확하게 전달하는 것임

- LB 뒤에 오는 서비스는 상당수가 시장에 완제품으로 나와 있어서 우리가 직접 구현하지 않아도 됨
- 서비스 탐색이라는 서비스는 클라이언트가 접속할 채팅 서버의 DNS 호스트명을 클라이언트에게 알려주는 역할을 함

#### 상태 유지 서비스

많은 서비스가 제공하는 기능이 무상태 서비스가 제공하는 기능이며, 이 교제에서 채팅 서비스만이 상태 유지가 필요한 서비스임

→ 각 클라이언트가 채팅 서버와 독립적인 네트워크 연결을 유지해야하기 때문임

1. 클라이언트가 요청하지 않아도 서버가 메세지를 보낼 수 있어야 함
2. 채팅은 속도가 생명인데 무상태 서비스이면 핸드쉐이크를 계속 해야하는 문제
3. 어떤 사용자가 접속해 있는지, 그 사용자가 어느 채팅방에 들어가 있는지 확인해야 함

### 제3자 서비스 연동 & 규모 확장성 & 저장소

제3자 서비스로는 푸시 알림을 사용함

규모 확장성 측면에서는 서버 한 대는 SPOF 문제가 발생할 수 있으니 초기 서버 한 대에서 점차 늘려가는 것이 이상적임

저장소에 저장되는 데이터는 보통 두 가지임

1. 사용자 프로파일, 설정, 친구 목록과 같은 일반적인 데이터로 이는 RDB에 저장함
2. 채팅이력과 같은 채팅 시스템에 고유한 데이터
    - 양이 어마어마한데, 보통은 최근 메세지가 사용되고 오래된 메세지는 잘 사용되지 않음
    - 1:1 채팅의 경우 읽기와 쓰기 비율이 1:1임
    - 빠른 접근을 위해서 키-값 저장소에 저장을 함(지연시간과 수평적 규모확장이 쉬움)
    
    #### 롱테일(long tail)이란
    
    데이터를 **접근 빈도 순으로 줄 세웠을 때 생기는 모양**임
    
    ```
    접근
    빈도
     │█
     │█
     │█ █
     │█ █ █
     │█ █ █ █ ▄ ▄ ▂ ▂ ▁ ▁ ▁ ▁ ▁ ▁ ▁ ▁ ▁ ▁ ▁ ▁ ▁ ...
     └────────────────────────────────────────────────>
       최근                                      오래된 메시지
       └─머리─┘└───────────── 꼬리(롱테일) ─────────────┘
       양은 적고          양은 압도적으로 많고
       자주 읽힘           하나하나는 거의 안 읽힘
    ```
    
    원래는 서점 비유에서 나온 말. 베스트셀러 몇 권이 많이 팔리고(머리), 안 팔리는 책 수백만 종이 조금씩 팔리는데(꼬리) **합치면 무시 못 할 양**이 된다는 것
    
    #### 채팅에 적용하면
    
    - **머리** — 어제·오늘 메시지. 사용자가 앱을 켜면 거의 이것만 봄
    - **꼬리** — 3년 전 메시지. 거의 안 읽히는데 **쌓인 양은 압도적**
    
    꼬리가 아예 안 읽히면 문제가 없음. 그냥 어딘가 던져두면 되니까. 그런데 **검색, 특정 메시지로 점프, 오래된 대화 다시 열기** 같은 걸로 **가끔, 그리고 예측 불가능하게** 접근이 일어남
    
    #### 그래서 RDB가 왜 못 버티나
    
    머리만 있으면 **캐시로 끝남**. 자주 쓰는 것만 메모리에 올려두면 되니까
    
    문제는 꼬리임
    
    1. 꼬리는 양이 많아서 캐시에 올릴 수 없음 → 요청이 오면 **디스크로 감**
    2. 어디로 튈지 모르는 접근이라 **무작위 접근(random access)**
    3. 데이터가 쌓일수록 **B-tree 인덱스가 커져서 메모리에 다 안 올라감**
    4. 그러면 인덱스를 타는 것조차 디스크 I/O 가 여러 번 발생 → 비용이 급격히 올라감

### 데이터 모델

1:1 채팅을 위한 메세지 테이블: message(<u>message_id</u>, <u>message_from</u>, message_to, content, created_at)

그룹 채팅을 위한 메세지 테이블: group message(<u>channel_id</u>, <u>message_id</u>, user_id, content, created_at)

### 메세지 ID

메세지 ID의 값이 고유해야하고, 시간의 순서에 따라서 이전 ID보다 새로운 ID 값이 커야하는 조건

→ 이를 auto_increment나 snowflake 같은 기법을 사용함

OR 지역적 순서 번호 생성기로서 채팅 새션 안에서만 ID가 나뉘어지면 되어서 구현이 간단함

### 서비스 탐색

서비스 탐색의 주된 기능은 클라이언트에게 가장 적합한 채팅 서버를 추천하는 것임

클라이언트 → LB → API 서버(여기서 사용자 인증을 처리하고, 최적의 채팅 서버를 찾음) → 서버가 최적의 채팅 서버를 반환 → 클라이언트가 채팅 서버와 웹소켓 연결을 함

### 메시지 흐름

#### 1. 1:1 채팅 메시지 처리 흐름

```
사용자 A
   │ ①  메시지 전송
   ▼
채팅 서버 1 ──②──> ID 생성기   (메시지 ID 발급)
   │ ③
   ▼
메시지 동기화 큐 ──④──> 키-값 저장소  (보관)
   │
   ├─ ⑤-1  B 가 접속 중   ──> 채팅 서버 2 ──⑥──> 사용자 B
   │                              (B 와 웹소켓 연결이 있는 서버)
   └─ ⑤-2  B 가 오프라인  ──> 푸시 알림 서버
```

#### 2. 여러 단말 사이의 메시지 동기화

```
사용자 A ─┬─ 폰     (웹소켓 연결 1)   cur_max_message_id = 1002
          └─ 노트북 (웹소켓 연결 2)   cur_max_message_id = 1005
```

- **단말 하나하나가 각자 웹소켓 연결을 유지함.** 같은 계정이어도 연결은 따로
- 각 단말은 `cur_max_message_id` 를 들고 있음 — **그 단말이 본 가장 최신 메시지의 ID**

새 메시지로 판정하는 조건 두 가지

1. 수신자 ID 가 현재 로그인한 사용자 ID 와 같을 것
2. 메시지 ID 가 그 단말의 `cur_max_message_id` 보다 클 것

단말마다 `cur_max_message_id` 가 다르니까 **각자 자기가 못 본 것부터 가져오면 됨**. 폰으로 먼저 읽었어도 노트북은 자기 기준으로 다시 받아올 수 있음

#### 3. 소규모 그룹 채팅에서의 메시지 흐름

```
사용자 A 가 메시지 전송
   │
   ├──> 사용자 B 의 메시지 동기화 큐   (사본)
   ├──> 사용자 C 의 메시지 동기화 큐   (사본)
   └──> 사용자 D 의 메시지 동기화 큐   (사본)

각 사용자는 자기 큐(받은 편지함)만 보면 됨
```

- 메시지 하나가 **그룹 내 모든 사용자의 큐에 복사됨**
- 수신자 입장에서는 **여러 사람에게서 온 메시지를 자기 큐 하나에서** 받게 됨

|  |  |
| --- | --- |
| 장점 | 새 메시지 확인이 단순함 — **자기 큐만 보면 됨** |
| 장점 | 그룹이 작으면 복사 비용이 크지 않음 |
| 한계 | 그룹이 커지면 **사본 수가 인원수만큼 늘어남** |

그래서 이 방식은 **소규모 그룹 전제**임. 위챗이 그룹 인원을 500명으로 제한하는 게 이 이유

> **11장 fanout-on-write 와 같은 구조.** 쓰기 시점에 수신자별로 복사해서 각자 칸에 넣어두고, 읽을 땐 자기 칸만 보는 것. 그래서 **커지면 복사 비용이 터진다는 약점까지 똑같이 물려받음**. 11장은 인플루언서를 예외 처리하는 하이브리드로 풀었는데, 12장은 아예 인원을 제한하는 쪽을 택한 셈
> 

### 접속상태 표시

접속상태 서버를 통해 사용자의 상태를 관리하며 웹소켓으로 통신하는 실시간 서비스의 일부임

#### 사용자 로그인

로그인을 한 후, 클라이언트가 접속상태 서버와 웹소켓 연결을 맺음 → 접속상태 서버는 클라이언트의 상태를 last_active_at 타임스탬프 값을 키-값 저장소에 보관

#### 로그아웃

로그아웃 시 API 서버가 접속상태 서버에 요청을 해 K-V 저장소에 있는 클라이언트 상태 값을 offline으로 변경

#### 접속 장애

일상에서 터널이나 엘리베이터에서 네트워크 접속이 끊기는 일이 종종 있음. 이때 마다 클라이언트와 서버 사이에 맺은 웹소켓 같은 지속성 연결도 끊어지는데, 끊어질 때 마다 상태를 오프라인으로 바꿨다가 다시 새로운 연결을 맺으면 온라인으로 바꾸는 것은 너무 비효율적임

→ 온라인 상태의 클라이언트에게 주기적으로 박동 이벤트를 접속상태 서버로 보내게 하여, 박동 이벤트 메세지가 TTL 이내에 안 오면 오프라인 상태로 변경함
