# 채팅 시스템 설계 (Chat System)

이번 데모데이에서, 채팅 서비스를 맡았기 때문에 좀 더 자세하게 보자

채팅 서비스: 웹 소캣으로 구현했고, 웹소캣 또한 처음 연결은 HTTP 연결로 시작한다.

HTTP 요청, 응답 방식으로 계속 주고받지 않는 이유

1. HTTP는 기본적으로 클라이언트의 요청 → 응답 구조이다.

A사용자가 안녕이라고 보내는 요청을 함 → HTTP는 200 ok 로 응답하고 연결하면 끝

(즉 보내는 클라이언트는 HTTP 문제가 없다)

다만 B사용자가 안녕을 받는 상황에서, B는 안녕을 받고싶다는 요청을 하지 않는다.

근데 서버는 안녕을 보내야하는데… 요청이 오지 않으므로, 보낼 방법이 없어진다.

따라서 HTTP 규칙으로는 B가 받을 수 없어서 억지로라도 받게하는 방법이

1. 폴링: 특정 시간(2초,3초) 마다 새 메시지가 있는지? 물어보는 구조이다. → 최대 2초 지연이겠다.
2. 롱 폴링: B가 먼저 물어보도록 해서 서버가 대기하고 있다가, 실제 메시지가 오면 응답을 하는거다.

결국 B가 서버에 물어보도록 설계해야한다.

근데 우리 프로젝트에서는 서버 1대 기준으로 했기 때문에 딱 HTTP 규칙에 알맞는 기본적인 상황이고,

1. 서버가 여러대였다면 → 메시지를 받는 서버와, 클라이언트의 서버가 다를 수 있다.
2. 클라이언트가 끊겼는지 서버가 알기 어렵다

“HTTP는 무상태 즉 서버가 이전 요청을 기억하지 않는다. 요청마다 모든 필요한 정보를 붙여서 보낸다” 가 가장 큰 특징이었음.

라운드 로빈: 서버가 여러 대일 때, 로드 밸런서가 요청을 차례대로 돌아가며 나누는 방식

근데 채팅에서는: 연결 자체가 하나의 상태로 유지되어야하고, B의 연결은 특정 서버 한 대에 붙어있어야한다

즉: A가 서버 1에서 요청을 보냈는데, B가 서버2에 있다면, 서버가 달라서 문제가 생긴다.

해결법:

1. 그래서 누가, 어느 서버에 붙어있는지 redis에 기록하거나
2. 서버와 서버 사이를 메시지 큐로 연결해 전달

웹소켓: 클라이언트가 GET /ws에 Upgrade: websocket 헤더를 붙이면 → 양방향 메시지 전송이 되게끔 하는데

핸드세이크: 데이터를 주고받기 전 양쪽의 통신할 준비가 되었는지 검증하는 절차가 있음.

우리 서비스에서는

1. TCP 3-way로 서로 양쪽이 메시지를 보내고, 받을 수 있는지 확인하는 과정
2. TLS 핸드세이크: 1:1 채팅에 다른사람이 들어오면 안되므로, 암호키를 생성해서 방을 잠근다.(없으면 데이터가 평문으로 노출됨)
3. websocket 핸드세이크: 여기서부터 websocket으로 변경해

채팅 서비스에서의 저장소

1. 사용자 프로파일,설정, 친구 목록과 같은 일반적인 데이터 → 안정성을 보장해야함 → 관계형 데이터베이스
2. 채팅 이력(고유한 데이터)

→ 채팅 이력은 양도 많고, 검색하면 그 특정 부분으로 이동하고… 등등 1:1채팅에서는 읽기와 쓰기 비율이 1:1일정도로 많다.

키-값 저장소 사용

1. 수평적 확장이 넓다
2. 데이터 접근 지연시간이 낮다
3. 관계형 DB는 인덱스가 메모리에 올라가있을 때 빠르다.

→ 롱 테일에 해당하는 부분을 잘 처리하지 못한다고 나와있는데, 채팅에서 하루, 이틀전 내용은 비교적 최근 메시지이지만, 채팅방을 열면 3년전까지 다 불러온다. 1년 → 2년 갈수록 계속 내용이 쌓인다.

여기서 옛날 그 메시지로 가려면..  엄청난 양의 데이터를 가져와야하고, 거의 사용되지 않는다.

→ 이렇게 오래된 데이터는 메모리에 남아있지 않고 → 보통 디스크에 남아있는데 이걸 여러번 무작위로 읽어서 사용자에게 줘야한다. 그만큼 느려진다…

따라서 키-값 저장소 이용시

(channel_id, message_id) 키로 두면, 어떤 방의 어떤 시점이든 키 하나로 해당 위치를 바로 찾을 수 있다.

서버를 늘리기 쉽다. : 키를 해시하고 → 여러 서버에 나누고.. 데이터가 늘어나면 서버를 추가하면 된다.

즉 꼬리가 커져도 → 서버 여러대에 흩어져 있을 뿐

정리하자면 채팅 서비스에서 키 - 값 저장소를 사용하는 이유

1. 수평 확장이 쉬움
2. 데이터 접근 지연이 낮음
3. 관계형 DB는 데이터의 롱 테일을 잘 처리하지 못함 (인덱스가 커지면 무작위 접근이 느려짐)
4. 실제로 페이스북(HBase)과 디스코드(Cassandra)가 그렇게 씀

메시지 ID를 만들때

1. autoincrement는 noSql에서 불가능
2. 전역 ID 생성기 (스노플레이크) → 서버마다 번호가 달라서 각자 만들어도 안겹치는 방식(디스코드)
3. 지역 순번 생성하기

→ 스노플레이크도 좋은 방법이지만, 채팅은 1:1 방 안에서만 유일하면 되기 때문에 굳이 서버마다 다를 필요가 없다.

여러 단말 사이의 메시지 동기화

기기마다 websocket은 따로 연결하지만, 서버는 그 두개의 연결을 기억한다.

핸드폰에서 가면사배대시설기 방에 “ 배고파 “ 라고 보낸다면 서버가 숫자를 매겨 저장하고, 연결된 모든 기기에

cur_max_message_id(마지막으로 받은 번호)를 저장한다.

이후 랩톱에서 메시지를 보내려고 들어가면, 마지막으로 받은 번호를 통해 어디까지 보냈는지 서버에 말해 최근 메시지부터 시작할 수 있다.

그룹 채팅에서

소규모

A가 "안녕" → 서버가 멤버 수만큼 복사(메시지 동기화 큐 여러개)

B 받은편지함 ← "안녕"

C 받은편지함 ← "안녕"

D 받은편지함 ← "안녕"

- 500명 방에서 1초에 10개씩 오가면 초당 5,000번 써야한다. 그래서 책도 소규모 그룹(위챗은 최대 500명) 으로 정해둠.

대규모

A가 "안녕" → 채널 123 에 딱 1번 저장 (seq 1001)

B: "채널 123, 1000번 다음 줘"  → 1001

C: "채널 123, 980번 다음 줘"   → 981 ~ 1001

→ 메시지는 채널에 한 번만 저장하고, 각자의 사람들이 어디까지 읽었는지를 따로 저장한다.

근데 지금 접속해서 보고있는 사람들은?

서버는 받은 메시지를 저장소에 1번, 그 채널에 1번 공유한다.

그 채널에서 실시간으로 보고있는 사람들은 서버가 발행해주는걸 통해 보고,

오프라인 사람들은 나중에 접속해서 last_read_seq를 통해 메시지를 받는다.

디스코드 엔지니어링 담당 블로그에서 밝힌 것.

- 채널 단위로 묶어서 저장: 파티션 키를 (channel_id, 시간 버킷) 으로 두고 한 채널 메시지가 시간순으로 붙어 있어 "최근 50개"를 한 번에 읽고, 오래된 채널이 한 파티션에 무한히 커지지 않게 기간별로 나눈다. 디스코드는 Cassandra를 쓰다가 ScyllaDB로 옮겼다.
- 서버(길드)마다 담당 프로세스: 길드마다 그 길드의 이벤트를 모아서 접속한 멤버 세션들에게 나눠 주는 프로세스가 있다. 길드가 아주 크면 이것도 중간 전달 단계(relay)로 쪼개서, 한 프로세스가 수십만 명에게 직접 보내지 않게 구분한다.
- 필요한 것만 보내기: 안 보고 있는 채널의 메시지 전체를 모두에게 밀지 않는다. "새 메시지 있음" 정도만 알리고, 채널을 열면 그때 내용을 보여준다. 멤버 목록도 화면에 보이는 부분만 보내는 방식이다.
- 타이핑·접속 상태는 가볍게: "누가 입력 중"이나 온라인 표시 같은 건 저장하지 않고 잃어버려도 되는 이벤트로 처리한다. 큰 방에서는 아예 줄이거나 생략함.

접속 장애

박동 검사: 주기적으로 박동 이벤트를 만들어서 접속 상태를 서버에 보내고, 마지막 이벤트 뒤로 몇 초안에 또 오면 접속하고 있는 것, 오지 않는다면 접속이 끊긴 것이다.

→ 박동은 30초와 같이 시간 텀을 두는데, 너무 짧으면 잠깐의 연결 끊김에 대해 너무 많은 온,오프라인 변경이 일어난다.

나도 채팅 서비스에서 박동 검사를 통해, 게임중인 사람이 이탈했는지를 검사하도록 했고, 게임이 약 4분이내라서 10초로 짧게 설정했다.

10초라는 유예시간을 주고, 그 이내에 돌아오면 게임 진행, 돌아오지 않으면 상대방이 이탈했다는 메시지를 주도록 했다.

클라이언트와 서버가 서로 박동을 보낸다.(STOMP 규약에 들어있는 기능이었다)

책은 사람 단위고, 나는 연결 단위로 바라보았다. 책에서의 박동은 온, 오프라인을 위한 것이고, 나는 신호 없이 끊긴 연결을 잡는 것이었기에 조금은 다르지만 엮어보았다.
