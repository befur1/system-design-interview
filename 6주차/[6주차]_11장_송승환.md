## 11장 요약

### 뉴스 피드 API

클라이언트가 서버와 통신하기 위한 수단으로 뉴스 피드를 가져오거나, 친구를 추가하는 드으이 다양한 작업을 수행함

#### 피드 발행 API

```sql
POST /v1/me/feed

인자:
- 바디: 포스팅 내용에 해당
- Authorization 헤더: API 호출을 인증하기 위해 사용
```

#### 피드 읽기 API

```sql
GET /v1/me/feed

인자:
- Authorization 헤더: API 호출을 인증하기 위해 사용 
```

### 피드 발행

- 사용자: 새 포스팅을 올리는 주체로 `POST /v1/me/feed` API를 사용
- 로드밸런서: 트래픽을 웹 서버들로 분산
- 웹 서버: HTTP 요청을 내부 서비스로 중계하는 역할을 담당
- 포스팅 저장 서비스: 새 포스팅을 DB와 캐시에 저장
- 포스팅 전송 서비스: 새 포스팅을 친구의 뉴스 피드에 푸시. 뉴스 피드 데이터는 캐시에 보관하여 빠르게 읽어갈 수 있도록 함
- 알림 서비스: 푸시 알림을 보내는 역할을 담당

### 뉴스 피드 생성

- 사용자: 뉴스 피드를 읽는 주체로 `GET/v1/me/feed` API를 사용
- 로드밸런서: 트래픽을 웹 서버들로 분산
- 웹 서버: 트래픽을 뉴스 피드 서비스로 보냄
- 뉴스 피드 서비스: 캐시에서 뉴스 피드를 가져오는 서비스
- 뉴스 피드 캐시: 뉴스 피드를 랜더링할 때 필요한 피드 ID를 보관

### 피드 발행 흐름 상세 설계

#### 웹 서버

- 클라이언트와 통신할 뿐 아니라 인증이나 처리율 제한 등의 기능도 수행
- 스펨을 막고 유해한 콘텐츠가 자주 올라오는 것을 방지

#### 포스팅 전송 서비스

포스팅 전송, 즉 팬아웃(fanout)은 어떤 사용자의 새 포스팅을 그 사용자와 친구 관게에 있는 모든 사용자에게 전달하는 과정

- 쓰기 시점에 팬아웃(fanout-on-write): 새로운 포스팅을 기록하는 시점에 뉴스 피드를 갱신
    
    장점
    
    - 뉴스 피드가 실시간으로 갱신되며 친구 목록에 있는 사용자에게 즉시 전송
    - 새 포스팅이 기록되는 순간에 뉴스 피드가 이미 갱신되므로 뉴스 피드를 읽는 데 드는 시간이 짧아짐
    
    단점
    
    - 친구가 많은 사용자의 친구 목록을 가져와 그 목록에 있는 전체 사용자의 뉴스 피드를 갱신하는데 많은 시간이 소요
    - 서비스를 잘 이용하지 않는 사용자 피드까지 갱신
- 읽기 시점에 팬아웃(fanout-on-demand): 피드를 읽어야 하는 시점에 뉴스 피드를 갱신
    
    장점
    
    - 비활성화된 사용자는 로그인하기 전까지 어떤 컴퓨팅 자원도 소모하지 않음
    - 데이터를 친구 각각에게 push하는 작업이 필요 없음
    
    단점
    
    - 뉴스 피드를 읽는 데 많은 시간이 소모
    
    ### 피드 읽기 흐름 상세 설계 (그림 11-7)
    
    ```
    사용자 단말 (웹 브라우저 · 모바일 앱)
       │ ①  GET /v1/me/feed
       ▼
    로드밸런서
       │ ②
       ▼
    웹 서버  ── 인증 · 처리율 제한
       │ ③
       ▼
    뉴스 피드 서비스
       │
       │ ④  포스팅 ID 목록을 꺼냄
       ├────────────> 뉴스 피드 캐시
       │
       │ ⑤  그 ID 로 실제 내용을 채움
       ├────────────> 사용자 정보 캐시 ──(미스)──> 사용자 정보 DB
       └────────────> 포스팅 캐시      ──(미스)──> 포스팅 DB
       │
       │ ⑥  완성된 피드를 JSON 으로 반환
       ▼
    사용자 단말
    
    * 이미지·비디오 같은 미디어는 CDN 에서 단말이 직접 받아감
    ```
    
    | 단계 | 하는 일 |
    | --- | --- |
    | ① | 사용자가 `/v1/me/feed` 로 피드 조회 요청 |
    | ② | 로드밸런서가 웹 서버 중 하나로 보냄 |
    | ③ | 웹 서버가 **인증·처리율 제한**을 통과시킨 뒤 뉴스 피드 서비스로 넘김 |
    | ④ | 뉴스 피드 캐시에서 **포스팅 ID 목록**만 꺼냄 |
    | ⑤ | 그 ID 로 **사용자 정보 캐시**와 **포스팅 캐시**를 조회해 완전한 피드를 조립. 캐시에 없으면 각 DB 로 |
    | ⑥ | 완성된 뉴스 피드를 클라이언트에 반환 |
    
    #### 캐시가 세 개로 나뉘어 있음
    
    | 캐시 | 들고 있는 것 |
    | --- | --- |
    | 뉴스 피드 캐시 | `<post_id, user_id>` — **누가 쓴 몇 번 글인지만** |
    | 포스팅 캐시 | 본문, 작성 시각, `author_id` |
    | 사용자 정보 캐시 | 이름, 프로필 사진, 설정 |
    
    **각 계층이 다음 계층을 가리키는 ID 만 들고 있어서 3단으로 타고 감.** 그래서 ⑤ 에서 두 캐시를 동시에 조회하는 것
    
    #### 왜 ID 만 저장하나
    
    **① 복사하면 중복이 터짐**
    
    피드 캐시는 `사용자 수 × 피드 길이` 만큼 쌓임. 사용자 100만 명이 각자 100개면 1억 행.
    여기에 본문을 복사하면 친구 1,000명인 사람이 글 하나 쓸 때마다 같은 본문이 1,000벌 복사됨
    
    **② 수정·삭제가 한 군데로 끝남**
    
    - 본문을 복사해뒀으면 → 그 글이 들어간 **모든 피드**를 찾아가 고쳐야 함
    - 작성자 이름·프사를 포스팅에 복사해뒀으면 → 프사 한 번 바꿀 때 **자기가 쓴 글 전부**를 고쳐야 함
    - ID 만 두면 원본 하나만 고치면 전부 반영됨
    
    > 6장의 복제 트레이드오프와 같은 구조. "복사해두면 읽기가 빠른데 바뀔 때 전부 맞춰야 한다"를, 여기선 **조회 한 번을 더 내주고 중복을 피하는 쪽**으로 푼 것
    > 
    
    #### 사용자 정보 캐시를 왜 거치나 — 헷갈렸던 부분
    
    뉴스 피드 캐시엔 `post_id` 와 `user_id` 뿐이고, 포스팅 캐시에도 `author_id` 만 있음. 그런데 화면에 그려야 하는 건 **이름과 프로필 사진**이라서 한 번 더 가야 함
    
    그리고 **친구 목록 조회와는 다른 일**임
    
    |  | 언제 | 무엇을 묻나 |
    | --- | --- | --- |
    | 발행(fanout) | 글 쓸 때 | "이 사람 **친구가 누구**냐" → 누구 피드에 넣을지 결정 |
    | 조회 | 피드 볼 때 | "**304번이 누구**냐" → 화면에 표시할 정보 |
    
    fanout-on-write 를 쓰면 친구 목록 조회는 **글 쓰는 시점에 이미 끝나 있음**. 그래서 읽을 때는 작성자 정보만 가져오면 되고, 이게 "뉴스 피드를 읽는 데 드는 시간이 짧다"는 장점의 실체임
