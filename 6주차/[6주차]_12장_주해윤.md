## 12장 채팅 시스템 설계

---

### 문제 이해 및 설계 범위 확정

- 1:1 채팅 및 그룹 채팅 모두 지원
- 모바일/웹 앱
- 일별 능동 사용자 수 기준 5천만명 처리 가능
- 그룹 채팅은 최대 100명까지 참가 가능
- 1:1 채팅, 그룹 채팅, 사용자 접속상태 표시를 지원해야 하며 텍스트 메시지만 주고받을 수 있음
- 메시지 길이 최대 100,000자
- 종단 간 암호화는 시간이 허락한다면 논의
- 채팅 이력 영원히 보관

### 개략적 설계안 제시 및 동의 구하기

메시지 송신 클라이언트 ——> 채팅 서비스 ——> 메시지 수신 클라이언트

- 채팅을 시작하려는 클라이언트는 네트워크 통신 프로토콜을 사용하여 서비스에 접속
- 클라이언트는 채팅 서비스에 HTTP 프로토콜로 연결한 다음 메시지를 보내어 수신자에게 해당 메시지를 전달하라고 알림
- 접속에는 keep-alive 헤더를 사용하면 효율적 → 클라이언트와 서버 사이의 연결을 끊지 않고 계속 유지할 수 있고 TCP 접속 과정에서 발생하는 핸드셰이크 횟수를 줄일 수 있음

**폴링**

- 클라이언트가 주기적으로 서버에게 새 메시지가 있냐고 물어보는 방법
- 단점
    - 폴링을 자주 할수록 비용이 올라감
    - 답해줄 메시지가 없는 경우 서버 자원이 불필요하게 낭비됨

**롱 폴링**

- 새 메시지가 반환되거나 타임아웃 될 때까지 연결을 유지
- 클라이언트는 새 메시지를 받으면 기존 연결을 종료하고 서버에 새로운 요청을 보내어 모든 절차를 다시 시작함
- 단점
    - 메시지를 보내는 클라이언트와 수신하는 클라이언트가 같은 채팅 서버에 접속하게 되지 않을 수도 있음
    - 서버 입장에서는 클라이언트가 연결을 해제했는지 아닌지 알 좋은 방법이 없음
    - 메시지를 많이 받지 않는 클라이언트도 타임아웃이 일어날 때마다 주기적으로 서버에 다시 접속할 것

**웹소켓**

- 서버가 클라이언트에게 비동기 메시지를 보낼 때 가장 널리 사용하는 기술
- 클라이언트가 연결 시작 → 특정 핸드셰이크 절차를 거쳐 웹소켓 연결로 업그레이드 → 이 항구적인 연결이 만들어지고 나면 서버는 클라이언트에게 비동기적으로 메시지 전송 가능
- 웹소켓은 일반적으로 80이나 443처럼 HTTP 혹은 HTTPS 프로토콜이 사용하는 기본 포트번호를 그대로 쓰기 때문에 방화벽이 있는 환경에서도 잘 동작함
- 양방향 메시지 전송까지 가능하므로 웹소켓 대신 HTTP를 굳이 고집할 이유가 없음

메시지 전송 클라이언트 ↔ 채팅 서비스 ↔ 메시지 수신 클라이언트

- 메시지를 보낼 때나 받을 때 동일한 프로토콜을 사용할 수 있으므로 설계 뿐 아니라 구현도 단순하고 직관적

**무상태 서비스**

- 로드밸런서 뒤에 위치 → 로드밸런서는 요청을 그 경로에 맞는 서비스로 정확하게 전달

```
[무상태 서비스]

사용자 단말
  ↓ HTTP
로드밸런서
  ├─ 서비스 탐색
  ├─ 인증 서비스
  ├─ 그룹 관리
  └─ 사용자 프로파일

[상태 유지 서비스]

사용자 1 ← 웹소켓 → 채팅 서비스 ← 웹소켓 → 사용자 2

[제3자 서비스 연동]

푸시 알림
```

**규모 확장성**

```
사용자 단말
├─ HTTP → 로드밸런서 → API 서버
│                      ├─ 알림 서버
│                      ├─ 채팅 서버
│                      └─ 접속 상태 서버
│
└─ 웹소켓 → 실시간 서비스
             ├─ 채팅 서버
             └─ 접속 상태 서버

알림 서버 ───────────→ 키-값 저장소
API 서버 ────────────→ 키-값 저장소
채팅 서버 ───────────→ 키-값 저장소
접속 상태 서버 ──────→ 키-값 저장소
```

- 실시간으로 메시지를 주고받기 위해 클라이언트는 채팅 서버와 웹소켓 연결을 끊지 않고 유지함
- 채팅 서버는 클라이언트 사이에 메시지를 중계하는 역할
- 접속상태 서버는 사용자의 접속 여부를 관리
- API 서버는 로그인, 회원가입, 프로파일 변경 등 그 외 나머지 전부를 처리
- 알림 서버는 푸시 알림을 보냄
- 키-값 저장소에는 채팅 이력을 보관, 시스템에 접속한 사용자는 이전 채팅 이력을 전부 보게 됨

**저장소**

- 채팅 시스템이 다루는 데이터
    - 사용자 프로파일, 설정, 친구 목록처럼 일반적인 데이터 → 안정성을 위해 관계형 데이터베이스에 저장
    - 채팅 이력
        - 양이 엄청남
        - 빈번하게 사용되는 것은 최근에 주고받은 메시지
        - 검색 기능을 이용하거나 언급된 메시지를 보는 등 무작위적인 데이터 접근을 하는 경우도 있음
        - 1:1 채팅 앱의 경우 읽기:쓰기 비율은 대략 1:1
        
        → 키-값 저장소 추천
        
- 키-값 저장소 추천 이유
    - 수평적 규모확장이 쉬움
    - 데이터 접근 지연시간이 낮음
    - 관계형 데이터베이스는 데이터 가운데 롱 테일에 해당하는 부분을 잘 처리하지 못함, 인덱스가 커지면 데이터에 대한 무작위적 접근을 처리하는 비용이 늘어남

**데이터 모델**

- 1:1 채팅을 위한 메시지 테이블
    - **`message_id`**, `message_from`, `message_to`, `content`, `created_at`
- 그룹 채팅을 위한 메시지 테이블
    - **`channel_id`**, **`message_id`**, `user_id`, `content`, `created_at`

**메시지 ID**

- message_id의 값은 고유해야 함
- ID 값은 정렬 가능해야 하며 시간 순서와 일치해야 함
1. RDBMS의 auto_increment
2. 스노플레이크 같은 전역적 64-bit 순서 번호 생성기 이용
3. 지역적 순서 번호 생성기 사용

### 상세 설계

**서비스 탐색**

[주키퍼로 구현한 서비스 탐색 기능]

1. 사용자 A가 시스템에 로그인 시도
2. 로드밸런서가 로그인 요청을 API 서버들 가운데 하나로 보냄
3. API 서버가 사용자 인증을 처리하고 나면 서비스 탐색 기능이 동작하여 해당 사용자를 서비스할 최적의 채팅 서버를 찾음 → 채팅 서버 2가 선택되어 사용자 A에게 반환된다고 하자.
4. 사용자 A는 채팅 서버 2와 웹소켓 연결을 맺음

**메시지 흐름**

- 1:1 채팅
    1. 사용자 A가 채팅 서버 1로 메시지 전송
    2. 채팅 서버 1은 ID 생성기를 사용해 해당 메시지의 ID 결정
    3. 채팅 서버 1은 해당 메시지를 메시지 동기화 큐로 전송
    4. 메시지가 키-값 저장소에 보관됨
    5. (a) 사용자 B가 접속 중인 경우 메시지는 사용자 B가 접속 중인 채팅 서버로 전송됨
        
        (b) 사용자 B가 접속 중이 아니라면 푸시 알림 메시지를 푸시 알림 서버로 보냄
        
    6. 채팅 서버 2는 메시지를 사용자 B에게 전송, 사용자 B와 채팅 서버 2 사이에는 웹소켓 연결이 있는 상태이므로 그것을 이용
- 여러 단말 사이의 메시지 동기화
    - 사용자 A는 전화기와 랩톱 두 대 단말을 이용 중
    - 전화기에서 채팅 앱에 로그인한 결과로 채팅 서버 1과 해당 단말 사이에 웹소켓 연결이 만들어져 있고, 랩톱에서 로그인한 결과로 역시 별도 웹소켓이 채팅 서버에 연결되어 있음
    - 각 단말은 `cur_max_message_id`라는 변수를 유지 → 해당 단말에서 관측된 가장 최신 메시지의 ID를 추적
        - 수신자 ID가 현재 로그인한 사용자 ID와 같고
        - 키-값 저장소에 보관된 메시지로서, 그 ID가 `cur_max_message_id`보다 큼
            
            → 새 메시지로 간주
            
- 소규모 그룹 채팅
    - 사용자 A가 그룹 채팅 방에서 메시지를 보냈을 때 (해당 그룹 A, B, C 사용자 존재)
    - 사용자 A가 보낸 메시지가 사용자 B와 C의 메시지 동기화 큐에 복사됨
    
    → 새로운 메시지가 왔는지 확인하려면 자기 큐만 보면 되니 메시지 동기화 플로 단순하고, 그룹이 크지 않으면 메시지를 수신자별로 복사해서 큐에 넣는 작업의 비용이 문제가 되지 않으므로 소규모 그룹 채팅에 적합한 설계안
    

**접속 상태 표시**

- 사용자 로그인
    - 클라이언트와 실시간 서비스 사이에 웹소켓 연결이 맺어지고 나면 접속상태 서버는 A의 상태와 `last_active_at` 타임스탬프 값을 키-값 저장소에 보관
        
        → 해당 사용자는 접속 중인 것으로 표시될 것
        
- 로그아웃
    - 키-값 저장소에 보관된 사용자 상태가 `online`에서 `offline`으로 변경
- 접속 장애
    - 사용자의 인터넷 연결이 끊어지면 클라이언트와 서버 사이에 맺어진 웹소켓 같은 지속성 연결도 끊어짐 → 사용자를 오프라인 상태로 표시하고 연결이 복구되면 온라인 상태로 변경하면 되지만, 인터넷 연결이 끊어지는 일은 흔하므로 바람직하지 않음
    - 박동 검사: 온라인 상태의 클라이언트로 하여금 주기적으로 박동 이벤트를 접속상태 서버로 보내게 하고, 마지막 이벤트를 받은 지 x초 이내에 또 다른 박동 이벤트 메시지를 받으면 해당 사용자의 접속상태를 계속 온라인으로 유지
- 상태 정보의 전송
    - 발행-구독 모델: 각각의 친구관계마다 해널을 하나씩 둠 → 친구 관계에 있는 사용자가 상태정보 변화를 쉽게 통지 받게 됨
        
        → 그룹 크기가 작을 때 효과적
        
    - 그룹 크기가 클 경우: 사용자가 그룹 채팅에 입장하는 순간에만 상태 정보를 읽어가게 하거나, 친구 리스트에 있는 사용자의 접속상태를 갱신하고 싶으면 수동으로 하도록 유도

### +) 논의할 사항 및 경험과 연결

- 실시간 상호작용이 필요한 기능을 구현한다면, `HTTP`, 폴링, 롱 폴링, 웹소켓 중 어떤 통신 방식을 선택하는 것이 적합할까요? 모든 기능을 웹소켓으로 처리해야 할까요?
    - 로그인, 회원가입, 프로필 변경처럼 요청과 응답으로 끝나는 기능은 HTTP가 적합합니다. 반면 채팅 메시지나 접속 상태처럼 서버가 변경 사항을 즉시 전달해야 하는 기능은 양방향 통신이 가능한 웹소켓이 적합합니다. 모든 기능을 웹소켓으로 처리하기보다는 일반 기능은 HTTP, 실시간 기능은 웹소켓으로 분리하는 것이 단순합니다.
- 채팅 시스템에서 사용자·그룹 정보는 `SQL`에 저장하고 채팅 이력과 접속 상태는 키-값 저장소에 보관하는 방식이 적합할까요? 하나의 저장소만 사용하면 어떤 한계가 있을까요?
    - 사용자 프로필, 친구 목록, 그룹 구성처럼 관계와 안정성이 중요한 데이터는 관계형 데이터베이스에 저장하는 것이 적합합니다. 채팅 이력과 접속 상태는 데이터의 양이 많고 빠른 읽기·쓰기가 필요하므로 키-값 저장소를 사용할 수 있습니다. 하나의 관계형 데이터베이스만 사용하면 채팅 이력이 증가하면서 인덱스가 커지고 무작위 접근 비용이 증가할 수 있습니다.
- 사용자가 로그인할 때 서비스 탐색 기능이 적절한 채팅 서버를 선택하고, 이후 해당 서버와 웹소켓 연결을 유지하는 구조에서 채팅 서버가 장애를 일으키면 어떻게 해야 할까요?
    - 기존 웹소켓 연결이 끊어지면 클라이언트는 서비스 탐색을 통해 사용 가능한 다른 채팅 서버를 선택해 다시 연결해야 합니다. 메시지는 채팅 서버 자체가 아닌 키-값 저장소에 보관하여 다른 서버로 연결되더라도 이전 채팅 이력을 확인할 수 있어야 합니다. 채팅 서버가 사용자 상태를 독점적으로 보관하면 장애 시 복구하기 어려우므로 필요한 상태는 별도 저장소에서 관리하는 것이 적합합니다.
- 한 사용자가 모바일과 웹에 동시에 접속한다고 가정하면, 여러 단말 사이에서 메시지의 순서와 중복 수신을 어떻게 관리할 수 있을까요?
    - 각 단말이 자신이 확인한 최신 메시지 ID인 `cur_max_message_id`를 관리할 수 있습니다. 수신자 ID가 현재 사용자와 같고 메시지 ID가 `cur_max_message_id`보다 큰 경우에만 새로운 메시지로 처리합니다. 이를 위해 메시지 ID는 고유해야 하며 생성된 시간 순서대로 정렬할 수 있어야 합니다.
- 사용자 접속 상태를 웹소켓 연결 여부만으로 판단해도 될까요? 일시적인 네트워크 장애와 실제 로그아웃은 어떻게 구분할 수 있을까요?
    - 인터넷 연결은 일시적으로 끊어질 수 있으므로 웹소켓이 끊어지는 즉시 사용자를 오프라인으로 표시하는 것은 적절하지 않을 수 있습니다. 클라이언트가 접속 상태 서버에 주기적으로 박동 이벤트를 보내고, 마지막 박동 이후 일정 시간 안에 다음 이벤트가 도착하면 온라인 상태를 유지할 수 있습니다. 상태 변화는 소규모 그룹에서는 발행·구독 방식으로 전달하고, 큰 그룹에서는 입장 시점이나 사용자의 요청 시 조회할 수 있습니다.

**질문: 메시지가 저장되면 사용자에게 전송 성공으로 표시해도 될까?**

가정:

- 사용자 A가 보낸 메시지는 키-값 저장소에 정상적으로 저장되었다.
- 사용자 B가 접속한 채팅 서버로 메시지를 전달하는 과정에서 오류가 발생했다.
- 사용자 A는 메시지 전송 결과를 기다리고 있다.

**저장 직후 성공으로 표시한다고 생각한다면**

사용자 B에게 전달되지 않은 메시지는 어떻게 복구할까요?

**수신자에게 전달된 후 성공으로 표시한다고 생각한다면**

사용자 B가 오프라인이거나 네트워크 상태가 좋지 않을 때 사용자 A는 계속 기다려야 할까요?
