## 3단계 - 상세 설계

### 트라이 자료구조
RDS를 사용할 때 가장 인기 있었던 다섯 개 질의문을 골라내는 방안은 효율적이지 않다.
-> 한 글자 칠 때마다 수백만 개를 sort시키는 게 말이 안 됨.

트라이는 문자열들을 간략하게 저장할 수 있는 자료구조이다. 접두어 트리라고도 함.
- 트리 형태의 자료구조
- 루트 노드는 빈 문자열
- 각 노드는 글자 하나를 저장하며 26(a-z)개의 자식 노드를 가질 수 있다.
- 각 트리 노드는 하나의 단어, 또는 접두어 문자열을 나타낸다.

자식노드 쭉 순회하면서 빈도수 제일 높은거 리스트로 정렬하면 되나? BFS ,DFS로 해결이 되나?

p: 접두어 길이
n: 트라이 안에 있는 노드 수
c: 주어진 노드의 자식 노드 개수 일 때
가장 많이 사용된 질의어 k는 다음과 같이 찾을 수 있다.
1. 해당 접두어를 표현하는 노드를 찾는다. O(p)
2. 해당 노드부터 시작하는 하위 트리를 탐색해 모든 유효 노드를 찾는다. O(c)
3. 유효 노드들을 정렬하여 가장 인기 있는 검색어 k개를 찾는다. O(clogc)

O(p) + O(c) + O(clogc) 면 O(clogc) 시간에 끝나는데 이러면 괜찮은 거 아닌가?..
근데 대규모에서는 c가 몇천만 단위 + QPS가 수만건이니까 터지겠다.

**생각해야할 부분**

**알고리즘에서는 O(n^2) 아니면 다 괜찮은 느낌이었는데 좀 다른 것 같기도하네?**
-> 현실 시스템에서는 한 번의 요청만 일어나는 게 아니기 때문, 동일한 요청이 초당 수만번씩 요구된다. 그래서 선형시간복잡도가 드는 알고리즘도 무거워질 수 있다.

현실 시스템에서는 공간(메모리) 와 레이턴시가 trade-off라서 잘 생각해야한다.
사용자가 요청하는 순간에 무조건 O(1)이나 O(logN)으로 끝나야되니까 무거운 작업은 미리 계산해 두는 게 항상 최선의 방식이었다.

이 방식은 최악의 경우 k개의 결과를 얻으려고 전체 트라이를 다 검색해야 하는 일이 생길 수 있다.. <- 편향트리일때 말하는 건가?
-> 아니다. 예를 들어 빈 문자열 검색, **너무 흔한 한 글자만 쳤을 때 등 루트노드와 가까운 prefix를 고를 때를 말하는 거인듯.** 추가로 접두어가 너무 특이해서 요구하는 K개보다 작으면 다 뒤져보는 경우가 생길 수도 있음

다음의 문제를 해결하는 방식

#### 접두어의 최대 길이를 제한
검색어의 최대 길이를 제한할 수 있다면(100자 200자는 드무니까) 접두어 노드를 찾는 단계의 시간 복잡도는 O(p)에서 상수시간으로 줄일 수 있다.

근데 상한을 두는 거 보다 루트 노드에서 가깝게 안 하려면 최소 prefix를 둬야되는 거 아닌가?
-> 이것도 좋은데 음.. 영역이 조금 다름. 접두어 최대 길이 제한은 prefix 찾는 단계의 시간복잡도를 낮추는 거고 이건 전체 트라이 순회를 방지하기 위한 건데 실제로 많이 쓰고 좋다! 이 문제는 인기 검색어 캐시로 해결되고 이는 1글자도 지원이 가능하다.

#### 각 노드에 인기 검색어를 캐시

노드에 k개의 인기 검색어를 저장해 두면 전체 트라이를 검색하는 일을 방지할 수 있다.
**저장공간 vs 레이턴시 trade-off가 또 또 또 나온다**

두 개를 저장하면 상수시간에 끝난다.

### 데이터 수집 서비스
타이핑 할 때마다 실시간으로 데이터를 수정하는 건 다음 두 가지 문제로 그다지 실용적이지 않다.

- 매일 입력되는 수천만 건의 질의 때마다 트라이를 갱신하면 서비스가 느려진다
- 인기 검색어는 그다지 자주 바뀌지 않으니 갱신의 주기가 그렇게 짧지 않아도 된다

트위터같은 실시간 트렌드가 중요한 서비스면 검색어가 항상 신선하게 유지되어야 하지만 구글검색 같은 서비스는 그정도는 아니다. <- **서비스의 특성을 고려해야함**


```mermaid
flowchart LR
    Log["데이터 분석<br/>서비스 로그"] --> AggServer["로그 취합 서버"]
    AggServer --> AggData[("취합된 데이터")]
    AggData --> Worker["작업 서버"]
    Worker -->|매주 갱신| TrieDB[("트라이 데이터베이스")]
    TrieDB -->|매주 상태 스냅샷| TrieCache["트라이 캐시"]
```

#### 데이터 분석 서비스 로그
검색창에 입력된 질의에 관한 원본 데이터가 보관된다.
- 새로운 데이터가 추가(Append-only)될 뿐 수정은 이루어지지 않는다.
- 빠른 쓰기 속도를 위해 로그 데이터에는 인덱스를 걸지 않는다.

| query | time |
| :--- | :--- |
| tree | 2019-10-01 22:01:01 |
| try | 2019-10-01 22:01:05 |
| tree | 2019-10-01 22:01:30 |
| toy | 2019-10-01 22:02:22 |
| tree | 2019-10-02 22:02:42 |
| ... | 2019-10-03 22:03:03 |

#### 로그 취합 서버 & 취합된 데이터
- 주기를 정해(예: 매주 또는 매일) 쏟아지는 원본 로그를 취합한다.
- 취합된 데이터 테이블에는 `(query, time, frequency)` 형태로 단어별 빈도수를 합산하여 보관한다.

#### 작업 서버 & 트라이 DB / 트라이 캐시
- **작업 서버**: 취합된 빈도 데이터를 바탕으로 새로운 트라이(Trie)를 빌드하는 비동기 배치 일꾼.
- **트라이 DB**: 트라이 데이터를 직렬화하여 영구 보관하는 저장소. 선택지는 다음과 같다
    - 문서 저장소 : 새 트라이를 매주 만들 것이므로, 주기적으로 트라이를 직렬화하여 데이터베이스에 저장
    - 키-값 저장소: 트라이는 아래 로직을 적용하면 해시 테이블 형태로 변환이 가능
        - 모든 접두어를 키, 노드에 보관된 모든 데이터(캐시된 top 5 자료, 노드의 빈도수)를 밸류로..
- **트라이 캐시**: 메모리(RAM)에 트라이를 올려두고 실제 사용자의 자동완성 조회를 초고속 처리. 매주 트라이 DB의 스냅샷을 떠서 캐시를 갈아 끼운다.

### 질의 서비스
개략적 설계(RDS에서 검색)의 개선안
1. 검색 질의가 로드밸런서로 전송
2. 로드밸런서는 해당 질의를 알맞게 API 서버로 전송
3. 트라이캐시에서 데이터를 가져와 응답을 구성
4. 캐시에 없다면 디비에서 가져와 캐시에 채움

**질의 서비스는 반응성이 빨라야하므로 다음의 최적화 방안을 고려할 수 있다**

- AJAX 요청 : 브라우저는 보통 AJAX 요청을 보내 자동완성된 검색어 목록을 가져오는데 장점이 **페이지를 새로고침 할 필요가 없다**는 것임.
- 브라우저 캐싱: 제안된 검색어들을 브라우저 캐시에 저장해 서버를 거치지 않게 함
- 데이터 샘플링 : 대규모 시스템의 경우에, 모든 질의 결과를 로깅하도록 하면 엄청난 자원을 소모한다. N개 요청 중 1개만 로깅하도록 처리

### 트라이 연산

#### 트라이 생성
트라이 생성은 작업 서버가 담당. 데이터 분석 서비스의 로그나 데이터베이스로부터 취합된 데이터를 이용

#### 트라이 갱신

1. 매주 한 번 갱신하는 방법 - **새로운 트라이를 만들어 기존 트라이를 대체**
    -> 근데 이러면 그 기간에 일어난 비일상적인 상황에 대한 질의가 주요 랭크가 되고 일상적인 질의들은 묻히는 거 아닌가? 즉, 오염되는 거 아닌가?
       > 이를 방지하기 위해 실무에서는 다음 전략들을 사용한다:  
            > 1. **지수 감쇄 (Exponential Decay)**: 과거 누적 점수를 버리지 않고 매주 감쇄율(예: 0.7)을 곱해 누적 합산한다.  
            >    - `새로운 점수 = (기존 누적 점수 × 0.7) + 이번 주 검색량`  
            >    - 일상어는 매주 꾸준히 유입되므로 상위권을 굳건히 지킨다.  
            >    - 반짝 이슈는 이번 주에 검색이 멈추면 점수가 급감하여 자연스럽게 순위권 밖으로 내려간다.  
            > 2. **슬라이딩 윈도우 (Moving Average)**: 딱 1주일치만 보지 않고 최근 4주~8주의 이동 평균을 집계하여 단기 노이즈를 완충(Smoothing)한다.  
            > 3. **스파이크(Spike) 필터링**: 특정 날짜에만 비정상적으로 치솟은 단발성 검색어는 이상치로 판단하여 가중치를 깎는다.
            
2. 트라이의 각 노드를 개별적으로 갱신하는 방법 - 성능이 좋지 않다.
트라이 노드를 갱신할 때는 모든 상위 노드도 갱신해야 한다. -> 통으로 교체하는 것보다 연산량이 많을 것 같다
