# 12장: 채팅 시스템 설계

## 채팅 시스템이란?

채팅 시스템은 발신자의 메시지를 받아 수신자에게 전달하고, 나중에 다시 접속해도 대화 내역을 볼 수 있게 해주는 시스템이다. 서버는 메시지 저장과 실시간 전달을 모두 담당한다.

예를 들어 내가 노트북에서 메시지를 보낼 때 상대가 휴대폰으로 채팅방을 보고 있다면 바로 전달되어야 한다. 상대가 앱을 꺼둔 상태라면 메시지를 저장해두고, 상대가 다시 들어왔을 때 놓친 내용을 가져올 수 있어야 한다.

## 1단계: 문제 이해 및 설계 범위 확정

### 요구사항

- 웹과 모바일에서 사용할 수 있어야 한다.
- 응답 지연이 낮은 1:1 채팅과 최대 100명의 그룹 채팅을 지원한다.
- 메시지는 텍스트로 제한하고, 한 건의 최대 길이는 100,000자다.
- 사용자 접속 상태를 표시한다.
- 한 계정으로 여러 단말에 동시에 접속할 수 있다.
- 푸시 알림을 지원한다.
- 채팅 이력은 기간 제한 없이 보관한다고 가정한다.
- 일간 활성 사용자는 5,000만 명으로 가정한다.

사진과 영상 등 첨부 파일, 종단 간 암호화는 기본 구조를 잡은 뒤 추가로 검토한다.

### DAU와 동시 접속 수

5,000만 DAU는 하루 동안 서로 다른 사용자 5,000만 명이 서비스를 사용한다는 의미다. 한 사람이 하루에 열 번 접속해도 한 명으로 센다.

채팅 서버가 유지해야 하는 웹소켓 수는 특정 시점의 동시 연결 수로 계산한다. 한 사람이 같은 계정으로 휴대폰과 노트북에서 동시에 접속했다면 DAU에서는 한 명이고, 동시 연결은 두 개다.

책에서는 동시 연결 100만 개와 연결당 10KB를 가정해 약 10GB를 계산한다. 이 수치는 연결 관리에 쓰이는 메모리의 개략치다. 실제로 서버 대수를 정하려면 메시지 처리량, 네트워크 대역폭, 연결 버퍼, 장애가 났을 때 남은 서버가 맡아야 할 연결 수도 따로 봐야 한다.

## 2단계: 개략적 설계안 제시 및 동의 구하기

### 폴링

클라이언트가 주기적으로 서버에 새 메시지가 있는지 물어보는 방식이다. 예를 들어 5초마다 요청하면 새 메시지는 다음 요청이 오기 전까지 화면에 나타나지 않을 수 있다.

주기를 1초로 줄이면 평균적으로 더 빠르게 확인할 수 있지만, 대화가 없는 시간에도 요청을 반복한다. 연결을 재사용하더라도 새 메시지를 받기 위해 클라이언트가 주기적으로 요청한다는 점은 같다.

### 롱 폴링

서버가 요청을 받았을 때 새 메시지가 없으면 바로 빈 응답을 보내지 않고 기다린다. 대기 중 새 메시지가 생기면 그 요청에 응답한다. 일정 시간 동안 메시지가 없으면 타임아웃으로 응답하고, 클라이언트가 다시 요청한다.

일반 폴링에 비해 빈 응답을 줄일 수 있다. 다만 사용자의 대기 요청이 서버 2에 있고 새 메시지는 서버 1에서 받았다면, 서버 1이 서버 2에 메시지가 생겼다는 사실을 전달할 방법이 필요하다.

### 웹소켓

웹소켓은 클라이언트와 서버가 한 번 연결을 맺은 뒤, 같은 연결을 통해 양쪽에서 필요한 시점에 데이터를 보낼 수 있게 한다. HTTP/1.1을 이용하는 경우에는 클라이언트가 HTTP 요청으로 연결을 시작한 뒤 웹소켓으로 전환한다.

책에서 말하는 ‘항구적인 연결’은 메시지 한 건을 처리한 뒤에도 연결을 열어두고 계속 사용한다는 뜻이다. 앱을 열어둔 채로 10분 동안 아무 대화가 없어도 연결이 살아 있다면, 서버는 친구의 메시지를 받는 즉시 그 연결로 전달할 수 있다.

와이파이에서 모바일 데이터로 바뀌거나 서버가 재시작하면 연결은 끊길 수 있다. 이 경우 앱이 새로 연결하고, 연결이 없었던 동안의 메시지는 저장소에서 가져온다.

| 방식 | 새 메시지가 생겼을 때 | 서버가 관리할 것 |
| --- | --- | --- |
| 폴링 | 클라이언트의 다음 요청에서 반환 | 반복되는 HTTP 요청 |
| 롱 폴링 | 대기 중인 HTTP 요청에 응답 | 열린 요청과 타임아웃 |
| 웹소켓 | 이미 열린 연결로 전송 | 단말별 연결과 재접속 |

### 무상태 서비스와 상태 유지 서비스

로그인, 회원가입, 프로필 수정처럼 요청과 응답으로 끝나는 기능은 일반 HTTP API에서 처리할 수 있다. 서버 여러 대가 공유 저장소를 사용하면 연속된 두 요청을 서로 다른 API 서버가 처리할 수 있다.

채팅 서버는 자신과 연결된 단말의 소켓을 보관한다. 휴대폰이 서버 2에 연결되어 있다면 서버 1은 그 소켓에 직접 쓸 수 없다. 서버 1이 서버 2로 메시지를 보내면, 서버 2가 휴대폰에 연결된 소켓으로 전달한다.

| 구성 요소 | 역할 |
| --- | --- |
| API 서버 | 로그인, 회원가입, 프로필, 그룹 관리 |
| 서비스 탐색 | 새 연결을 받을 채팅 서버를 선택 |
| 채팅 서버 | 웹소켓 연결 유지, 메시지 송수신 |
| 접속 상태 서버 | 온라인 여부와 마지막 활동 시각 관리 |
| 알림 서버 | 미접속 사용자에게 새 메시지 알림 요청 |
| 메시지 저장소 | 채팅 이력을 지속적으로 보관 |

## 3단계: 상세 설계

### 서비스 탐색과 수신자 찾기

1. 사용자가 로그인하면 로드밸런서가 API 서버로 요청을 전달한다.
2. 인증이 끝나면 서비스 탐색이 사용자의 위치와 각 서버의 여유 용량을 고려해 채팅 서버를 선택한다. 책에서는 ZooKeeper에 서버를 등록하는 구조를 예로 든다.
3. 클라이언트가 선택된 서버에 웹소켓을 연결한다.
4. 채팅 시스템이 어느 사용자와 단말이 어느 서버에 연결됐는지 알 수 있도록 세션 정보를 관리한다.

새로 접속할 서버를 선택하는 것과 이미 접속한 수신자의 서버를 찾는 것은 별개의 작업이다. 예를 들어 A에게 새 서버를 배정하는 데는 서버별 여유 용량이 필요하다. A가 B에게 메시지를 보낼 때는 B의 휴대폰과 노트북이 현재 어느 서버에 연결됐는지가 필요하다.

### 채팅 이력에 필요한 조회 방식

사용자 프로필과 설정은 관계형 데이터베이스에 저장할 수 있다. 채팅 이력은 메시지가 계속 쌓이고, 보통 채팅방에 들어갈 때 최근 메시지부터 조회한다. 스크롤하거나 특정 메시지로 이동할 때는 오래된 이력도 읽어야 한다.

책에서는 채팅 이력에 수평 확장이 쉬운 키-값 저장소 계열을 선택한다. 저장소를 정할 때는 메시지 ID 하나로 조회하는 기능과 방별 최근 메시지를 순서대로 읽는 기능을 모두 확인해야 한다. 메시지 본문 검색까지 지원한다면 방별 이력 조회와는 별도로 검색 인덱스를 고려할 수 있다.

### 1:1 채팅과 그룹 채팅의 데이터 모델

| 구분 | 책의 기본키 예시 | 그 외에 저장할 값 |
| --- | --- | --- |
| 1:1 채팅 | `message_id` | 발신자, 수신자, 메시지 본문, 작성 시각 |
| 그룹 채팅 | `(channel_id, message_id)` | 발신자, 메시지 본문, 작성 시각 |

그룹 채팅의 파티션 키로 `channel_id`를 쓰면 같은 채팅방의 메시지를 논리적으로 함께 찾을 수 있다. `message_id`를 함께 사용하면 방 안에서 특정 메시지를 구분할 수 있다. 저장소가 파티션 안에서 ID 순으로 범위 조회를 지원하면 최근 메시지를 가져오거나 특정 지점부터 이어서 읽는 데도 유리하다.

메시지를 오래 보관할 때 한 채팅방의 데이터가 특정 파티션에 과도하게 쌓일 수 있다. 그런 방은 시간 범위를 추가해 데이터를 나눌 수 있지만, 범위를 넘나들며 페이지를 읽는 방식도 함께 설계해야 한다.

### 메시지 ID와 정렬

서로 다른 두 메시지의 `created_at`이 같을 수 있으므로 작성 시각만으로는 두 메시지의 순서를 하나로 정하기 어렵다. 책에서는 고유하면서도 순서를 비교할 수 있는 ID를 사용한다.

- `AUTO_INCREMENT`는 하나의 DB에서 순번을 발급하는 경우에 사용할 수 있다.
- 7장에서 다룬 스노플레이크 방식은 여러 서버가 독립적으로 고유 ID를 만들 때 사용할 수 있다. 서버 시계 차이와 네트워크 지연까지 포함한 실제 전달 순서는 별도로 다뤄야 한다.
- 채팅방별 순번은 같은 방 안에서만 유일하고 증가하면 된다. 방 사이에서 메시지의 순서를 비교할 필요가 없다면 발급 범위를 좁힐 수 있다.

예를 들어 A방과 B방에 각각 15번 메시지가 있어도 `(방 ID, 순번)`으로 식별하면 충돌하지 않는다. 다만 이런 번호를 사용한다면 단말에서 ‘모든 방을 합쳐 마지막으로 받은 순번’을 하나만 저장하는 방식은 사용할 수 없다.

### 1:1 메시지 전송 흐름

1. 사용자 A가 웹소켓으로 채팅 서버 1에 메시지를 보낸다.
2. 채팅 서버 1이 메시지 ID를 부여하고 메시지 동기화 큐에 넣는다.
3. 메시지가 채팅 이력 저장소에 기록된다.
4. B가 온라인이면 B의 세션이 있는 채팅 서버 2로 메시지를 전달한다. 채팅 서버 2는 B의 웹소켓에 메시지를 보낸다.
5. B가 오프라인이면 알림 서버에 푸시 알림을 요청한다. B가 다시 접속하면 채팅 이력에서 메시지를 조회할 수 있다.

여기서 발신자에게 언제 성공으로 표시할지 정해야 한다. 채팅 서버가 요청을 받았을 때, 메시지를 지속성 있는 저장소에 기록했을 때, B의 기기가 받았을 때는 서로 다른 단계다. 10장에서 알림 서버의 접수와 단말의 수신을 구분한 것과 같다.

### 여러 단말에서 메시지 동기화

책에서는 단말이 자신이 어디까지 메시지를 받았는지 `cur_max_message_id`로 관리한다. 같은 계정으로 로그인해도 휴대폰과 노트북의 동기화 진도는 다를 수 있다.

예를 들어 휴대폰이 653번까지 받고 노트북이 842번까지 받았다면, 휴대폰은 재접속했을 때 653 이후의 자기 메시지를 요청하고 노트북은 842 이후를 요청한다.

다만 이 방식이 안전하려면 커서 이전에 받아야 할 메시지가 뒤늦게 나타나지 않도록 동기화 순서를 보장해야 한다. 방별 번호를 쓰는 설계라면 방마다 커서를 관리하거나 사용자 수신함에 별도의 순서를 둬야 한다.

### 소규모 그룹 채팅

A, B, C가 같은 방에 있을 때 A가 메시지를 보내면 책의 설계에서는 B와 C의 동기화 큐에 각각 넣는다. B는 자신에게 도착한 메시지를 확인하기 위해 여러 발신자의 큐를 각각 확인할 필요 없이 자기 수신함을 보면 된다.

최대 100명인 방에서는 한 번의 전송으로 발신자를 제외한 최대 99개의 수신자 작업이 생긴다. 11장의 쓰기 시점 팬아웃과 구조가 비슷하다.

방의 규모가 훨씬 커지면 방별 공용 이력에 메시지를 한 번 기록하고 사용자가 자기 커서부터 가져가는 방식도 고려할 수 있다. 이때 접속 중인 사람에게 어떤 경로로 새 메시지를 전달할지와 개인별 안 읽은 수를 어떻게 계산할지는 따로 설계해야 한다.

### 접속 상태와 하트비트

사용자가 연결을 맺으면 접속 상태 서버가 온라인 상태와 마지막 활동 시각을 기록한다. 연결 중인 단말은 주기적으로 하트비트 신호를 보내고, 서버는 최근 신호가 들어온 시각을 갱신한다.

책에서는 5초에 한 번 신호를 보내고 30초 동안 받지 못하면 오프라인으로 바꾸는 예시를 든다. 잠깐 지하철에서 인터넷이 끊긴다고 온라인 표시가 계속 깜빡이는 일을 줄일 수 있다. 반면 대기 시간을 길게 잡으면 앱을 꺼도 일정 시간 동안 온라인으로 보일 수 있다.

여러 단말이 접속할 수 있다면 단말마다 상태를 관리하고, 유효한 연결이 하나라도 있으면 계정을 온라인으로 표시할 수 있다. 친구들에게 상태가 바뀌었다는 사실은 발행·구독 방식으로 전달할 수 있다. 수만 명이 상태를 볼 수 있는 방에서는 상태 변경을 전원에게 즉시 알리는 대신, 입장 시 조회하거나 화면에 보이는 사용자만 갱신하는 방식을 고려한다.

## 4단계: 설계 후 추가로 고려할 사항

### 채팅 서버 장애와 재접속

채팅 서버가 종료되면 해당 서버와 연결된 단말은 새 서버를 찾아 웹소켓을 다시 맺어야 한다. 새 서버에 연결된 뒤 마지막으로 동기화한 위치를 보내면 저장소에서 놓친 메시지를 가져올 수 있다.

한 서버의 연결이 한꺼번에 끊기면 많은 클라이언트가 같은 순간에 재접속할 수 있다. 각 클라이언트가 재시도 간격을 조금씩 다르게 잡으면 로그인 서버와 채팅 서버에 요청이 몰리는 현상을 줄일 수 있다.

### 미디어 첨부와 로딩 속도

사진이나 영상은 파일 저장소에 두고, 채팅 메시지에는 그 파일을 가리키는 정보를 담을 수 있다. 큰 파일의 업로드나 썸네일 생성은 채팅 본문 전송과 별개로 처리한다.

클라이언트가 최근 이력을 캐시해두면 채팅방을 다시 열었을 때 기존 메시지를 먼저 보여주고 이후 새 메시지만 가져올 수 있다. 지역이 멀어 접속 시간이 길어진다면 사용자 가까이에서 연결을 받고 필요한 데이터를 가져오는 구조도 검토할 수 있다.

### 종단 간 암호화

종단 간 암호화는 발신 단말이 메시지를 암호화하고 수신 단말이 복호화하는 방식이다. 채팅 서버는 암호문을 저장하고 전달한다.

이를 적용하면 서버가 메시지 내용을 읽어 검색하거나 푸시 미리보기를 만드는 방식을 그대로 쓰기 어렵다. 새 휴대폰에서 이전 대화를 읽으려면 메시지 이력뿐 아니라 복호화에 필요한 키도 어떤 방식으로 옮길지 정해야 한다.

## 생각해본 질문

### HTTP 연결을 유지하는 것과 웹소켓을 유지하는 것은 어떻게 다를까?

HTTP에서 기존 연결을 재사용하면 요청을 보낼 때마다 처음부터 연결을 다시 맺는 비용을 줄일 수 있다. 일반적인 HTTP 요청·응답 방식에서 새 메시지를 받으려면 클라이언트가 조회 요청을 보내거나 미리 보낸 요청을 열어둬야 한다.

웹소켓은 연결이 열린 뒤 서버도 필요한 시점에 메시지를 보낼 수 있다. 채팅에서 중요한 건 친구가 메시지를 보낸 순간 서버가 이미 열린 연결로 전달할 수 있다는 점이다.

### 보내기 버튼을 한 번 눌렀는데 재시도로 메시지가 두 개 저장되면 어떻게 할까?

메시지는 저장됐지만 성공 응답을 받기 전에 앱 연결이 끊길 수 있다. 앱이 재전송할 때마다 서버가 새 ID를 발급하면 수신자의 화면에는 같은 문장이 두 번 나타날 수 있다.

클라이언트가 전송을 처음 시도할 때 `client_message_id`를 만들고 재시도에도 같은 값을 보내게 할 수 있다. 서버에서는 `(conversation_id, sender_id, client_message_id)`에 유일성을 보장하고, 이미 저장한 요청이라면 기존 `message_id`를 돌려준다. 사용자가 같은 문장을 의도적으로 두 번 보낸 경우에는 각각 다른 요청 ID를 쓰므로 두 건 모두 저장할 수 있다.

### 단말이 본 메시지 중 가장 큰 번호만 기록해도 될까?

101번 메시지의 저장이 늦고 102번이 먼저 도착했다고 하자. 단말이 커서를 바로 102로 올린다면 다음 조회에서 101번을 놓칠 수 있다.

동기화 커서는 단말이 받아야 할 메시지를 순서대로 모두 확인한 위치까지 전진시켜야 한다. 서버가 안정적인 동기화 순서를 제공하고, 실시간 전달과 재접속 조회에서 같은 메시지가 겹치면 메시지 ID를 기준으로 합치는 방식도 생각할 수 있다.

### 읽음 상태와 단말 동기화 커서를 하나로 관리해도 될까?

휴대폰이 백그라운드에서 120번까지 받아두었지만 사용자는 대화방을 100번까지만 봤을 수 있다. 이때 동기화 기준은 120이고 읽음 기준은 100이다.

동기화 위치는 단말에 어떤 데이터를 더 보내야 하는지 알려주고, 읽음 위치는 사용자가 어디까지 읽었는지 표시하는 데 사용한다. 노트북이 아직 90번까지만 받아뒀더라도 휴대폰에서 읽은 위치를 계정 전체에 반영할지, 각 단말에서 따로 관리할지는 서비스 정책에 따라 정할 수 있다.

### 온라인으로 표시되는데 상대가 메시지를 못 받는 경우도 있을까?

마지막 하트비트가 들어온 직후 상대의 인터넷이 끊겼다면, 서버가 오프라인으로 바꾸기 전까지는 온라인으로 표시될 수 있다. 이때 웹소켓으로 보낸 메시지가 상대의 앱에 실제로 도착했는지는 별도로 확인해야 한다.

서비스에서 도착 상태를 표시하려면 단말이 메시지를 받은 뒤 확인 응답을 보내는 방법을 쓸 수 있다. 확인 응답도 유실될 수 있으므로, 재접속하면 저장소에서 이력을 맞추고 메시지 ID로 중복을 처리한다.

### 몽글에서 이미지 생성 완료를 화면에 보여주려면 채팅처럼 웹소켓이 필요할까?

사용자는 이미지 생성을 요청하고, 결과가 준비됐다는 상태를 한 번 받으면 된다. 화면을 열어둔 동안 상태 조회 API를 폴링하는 방식부터 구현할 수 있고, 서버에서 브라우저로 상태만 계속 전달해야 한다면 SSE도 검토할 수 있다.

양쪽이 연결을 열어두고 수시로 메시지를 주고받는 채팅이라면 웹소켓의 장점이 크다. 이미지 생성처럼 작업 상태가 몇 번만 바뀌는 기능에서는 요청 빈도, 연결 유지 비용, 사용자가 화면을 떠났을 때의 알림 요구사항을 먼저 확인할 수 있다.
