# [6주차] 12장 - 채팅 시스템 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

세 장 중에 제일 할 말이 많은 장이었다. 내 프로젝트에 1:1 채팅이 있는데, 책이 권하는 웹소켓을 안 쓰고 폴링으로 만들어 뒀다. 그래서 읽는 동안 "이걸 안 썼으면 뭐가 필요 없어지나"를 계속 따라가게 됐고, 그게 이 장에서 얻은 것의 대부분이다.

## 책 내용 뼈대

### 요구사항과 규모

| 항목 | 값 |
| --- | --- |
| DAU | 5,000만 명 |
| 그룹 채팅 최대 인원 | 100명 |
| 메시지 길이 | 100,000자 이하 |
| 채팅 이력 | 영원히 보관 |
| 단말 | 하나의 계정으로 여러 단말 동시 접속 |
| 그 외 | 푸시 알림 지원, 모바일과 웹 모두 |

동시 접속 100만 명이면 접속당 10KB 메모리로 총 10GB면 모든 연결을 처리할 수 있다고 본다.

### 폴링, 롱 폴링, 웹소켓

| | 어떻게 | 단점 |
| --- | --- | --- |
| 폴링 | 클라이언트가 주기적으로 새 메시지가 있는지 묻는다 | 자주 물을수록 비용이 커진다. 메시지가 없어도 서버 자원이 낭비된다 |
| 롱 폴링 | 새 메시지가 오거나 타임아웃될 때까지 연결을 유지한다 | 무상태 HTTP 서버와 라운드 로빈 때문에 송신자와 수신자가 같은 채팅 서버에 붙지 않을 수 있다. 서버가 연결 해제를 알기 어렵다. 메시지를 적게 받는 클라이언트도 타임아웃마다 재접속한다 |
| 웹소켓 | 클라이언트가 시작하고 한 번 맺어지면 유지되는 양방향 연결 | 항구적 연결을 서버가 효율적으로 관리해야 한다 |

책은 웹소켓으로 간다. 서버가 비동기로 메시지를 보낼 수 있고, 80/443 포트를 쓰기 때문에 방화벽 환경에서도 잘 동작한다는 점을 장점으로 든다.

### 시스템은 세 부분으로 나뉜다

| | 무엇 |
| --- | --- |
| 무상태 서비스 | 로그인, 회원가입, 프로파일. 로드밸런서 뒤에 둔다 |
| 상태 유지 서비스 | 채팅 서버. 클라이언트와 독립적인 연결을 유지해야 하므로 상태를 가진다 |
| 제3자 서비스 | 푸시 알림. 앱이 꺼져 있어도 알림을 받게 한다 (10장과 같은 자리) |

서비스 탐색이 클라이언트 위치와 서버 용량을 기준으로 가장 적합한 채팅 서버를 추천한다. 아파치 주키퍼 같은 솔루션을 예로 든다.

흐름은 로그인 다음에 API 서버가 인증하고, 서비스 탐색이 채팅 서버를 골라주면, 클라이언트가 그 서버에 웹소켓으로 연결하는 순서다.

### 어떤 데이터베이스를 쓰나

일반 데이터(프로파일, 설정, 친구 목록)는 관계형 DB에 두고 복제와 샤딩으로 확장한다. 그런데 채팅 이력은 키-값 저장소를 고른다.

| 이유 | |
| --- | --- |
| 데이터가 방대하다 | 영원히 보관한다는 요구사항 때문 |
| 최근 메시지 위주로 읽힌다 | 오래된 메시지는 거의 안 읽힌다 |
| 무작위 접근도 필요하다 | 검색, 특정 메시지로 점프 |
| 수평 확장이 쉽고 지연이 낮다 | |
| 관계형 DB는 롱 테일을 잘 못 다룬다 | 인덱스가 커지면 무작위 접근 비용이 증가한다 |

### 메시지 ID를 어떻게 만드나

| 방식 | 특징 |
| --- | --- |
| auto_increment | 관계형 DB에서 쓸 수 있지만 NoSQL은 보통 지원하지 않는다 |
| 스노플레이크 같은 전역 64비트 시퀀스 생성기 | 전체 시스템에서 유일성과 시간 순서를 보장한다 (7장) |
| 지역적 순서 번호 생성기 | 유일성을 같은 그룹이나 채널 안에서만 보장하면 된다. 전역 생성기보다 구현이 쉽다 |

### 메시지 테이블과 동기화 큐

| | 컬럼 | 기본키 |
| --- | --- | --- |
| 1:1 | message_id, message_to, content, created_at | message_id |
| 그룹 | channel_id, message_id, message_to, content, created_at | (channel_id, message_id) 복합키. channel_id는 파티션 키로도 쓴다 |

동기화 큐는 소규모 그룹에서 사용자마다 메시지 수신함 큐를 두고 메시지를 수신자별로 복사한다. 위챗이 이 방식을 쓰며 그룹을 500명으로 제한한다. 대규모 그룹에는 맞지 않는다.

단말 동기화는 단말마다 `cur_max_message_id`를 유지해서, 수신자 ID가 자신과 같고 ID가 그 값보다 큰 메시지를 새 메시지로 판단한다.

### 접속 상태 표시

| 상황 | 처리 |
| --- | --- |
| 로그인 | 상태와 last_active_at을 키-값 저장소에 저장하고 온라인으로 표시 |
| 로그아웃 | online에서 offline으로 |
| 접속 장애 | 짧은 단절이 흔하므로 심박으로 처리. 5초마다 박동, 30초간 없으면 오프라인 |
| 상태 전송 | 발행-구독 모델. 친구 관계마다 채널을 둔다 (A-B, A-C). 그룹이 커지면 입장 시에만 읽거나 수동 갱신으로 바꾼다 |

## 개인적인 질문

### 1. 채팅은 왜 P2P로 안 만드나

책이 설명 없이 클라이언트-서버를 전제로 깔고 지나가서 생긴 질문이다. 이유가 두 개고 두 번째가 결정적이었다.

첫째, 서로에게 닿을 수 없다. 두 단말이 모두 공유기와 통신사 NAT 뒤에 있어서 외부에서 접속 가능한 주소가 없다. 직접 연결하려면 STUN(내 공인 주소 알아내기), TURN(안 되면 중계), ICE(되는 경로 고르기)가 필요한데, TURN이 결국 서버다. 서버를 없애려고 P2P로 갔는데 서버가 다시 생긴다. 책이 웹소켓의 장점으로 80/443 포트를 적은 것이 이 문제를 가장 쉽게 피한 것이다.

둘째, 메시지를 맡아둘 곳이 없다. 상대가 앱을 꺼놨을 때 어디로 보낼지에 P2P는 답이 없다. 책의 요구사항과 대조하면 분명하다.

| 책의 요구사항 | P2P에서 |
| --- | --- |
| 채팅 이력을 영원히 보관 | 누구 기기에 두나. 양쪽이 지우면 사라진다 |
| 푸시 알림 지원 | 상대가 꺼져 있으면 보낼 주체가 없다 |
| 한 계정으로 여러 단말 | 나중에 켠 단말이 그 사이 대화를 받을 길이 없다 |
| 그룹 최대 100명 | 연결이 4,950개. 메시지 한 통에 99번 전송 |

마지막 줄은 11장과 이어진다. 서버가 있으면 한 번 보내고 서버가 팬아웃하는데, P2P는 그 팬아웃을 발신자 단말이 떠안아서 배터리와 대역폭이 터진다.

결론은 한 줄이다. 메시지를 보관해야 하고 그 보관소는 양쪽이 다 꺼져 있어도 살아 있어야 한다. 그게 서버다.

그리고 짚어야 할 구분이 있다. P2P와 종단간 암호화는 다르다. 시그널과 왓츠앱은 종단간 암호화지만 P2P가 아니다. 서버를 거치되 서버가 암호문만 들고 있어서, 오프라인 전송과 다중 단말과 이력 보관이 모두 된다. 서버가 내 메시지를 읽는 게 싫다는 문제는 P2P가 아니라 암호화로 푸는 것이다.

P2P가 실제로 쓰이는 곳은 영상과 음성 통화다. 차이가 한 줄로 정리된다. 보관이 필요한가. 통화는 흘려보내고 끝이라 보관할 게 없으니 P2P가 성립한다. 같은 앱에서도 텍스트는 서버로, 통화는 P2P로 갈라지는 이유다.

### 2. 1:1도 채널로 보고 channel_id에 auto_increment를 쓰면 안 되나

지역적 순서 번호 생성기를 읽으면서 든 생각이다. 1:1도 참여자가 2명인 채널로 보면 테이블과 코드 경로가 하나로 합쳐지니 더 깔끔한 게 아닌가 싶었다. 실제로 책의 그룹 테이블 기본키가 (channel_id, message_id)이고, 슬랙과 디스코드의 DM도 채널로 구현돼 있다. 아이디어 자체는 맞았는데 두 군데서 걸렸다.

첫째, InnoDB에서는 채널별 auto_increment를 만들 수 없다. MyISAM은 복합 인덱스의 두 번째 컬럼에 걸면 그룹별 번호가 되지만 트랜잭션이 없어서 쓸 수 없다. InnoDB에서는 번호를 직접 발급해야 하고, `SELECT MAX(...) + 1` 은 경합으로 깨지므로 채널 행에 카운터를 두고 UPDATE로 올려야 한다. 즉 지역적 순서 번호 생성기는 채널당 행 락이다.

다만 치명적이지 않은 이유가 지역적이라는 말에 있다. 경합 범위가 채널로 한정되므로 다른 채널끼리는 서로 막지 않는다. 전역 생성기와 달리 분산 시스템이 필요 없고 DB 안의 행 락으로 끝난다. 책이 구현이 쉽다고 적은 것이 이것이다. 4주차에 정리한 시퀀스를 채널마다 하나씩 두는 모양이고, 그때 샤딩하면 시퀀스를 못 쓴다고 했던 문제가 여기서는 채널이 한 샤드에 들어가므로 생기지 않는다.

둘째, 복합키의 비용이 연산이 아니라 I/O에 있다. 정수 두 개를 비교하는 것과 하나를 비교하는 것은 CPU상 차이가 없다. InnoDB는 기본키 순서로 행을 물리적으로 저장하므로 기본키 선택이 디스크 배치를 결정한다.

| | 복합키 (channel_id, msg_id) | 스노플레이크 단일키 |
| --- | --- | --- |
| 키 크기 | 16B (msg_id를 INT로 하면 12B) | 8B |
| 방 조회용 추가 인덱스 | 필요 없음. 기본키가 이미 그 순서 | 필요. 행당 약 24B |
| 한 방 메시지 읽기 | 순차 읽기. 디스크에 붙어 있다 | 보조 인덱스 거친 뒤 본문 랜덤 액세스 |
| 삽입 위치 | 채널마다 흩어짐. 페이지 분할 | 오른쪽 끝 고정. 분할 없음 |
| 번호 발급 | 채널당 행 락 | 없음 |
| 샤딩 | channel_id가 그대로 파티션 키 | 방 조회가 전 샤드 조회가 된다 |
| 구현 | DB 안에서 끝 | 생성기 + 머신 ID + 시계 동기화 |

조회는 복합키가 이기고 삽입은 스노플레이크가 이긴다. 채팅은 조회 패턴이 한 방의 최근 메시지로 고정돼 있어서 복합키의 클러스터링이 정확히 맞고, 그래서 책이 그룹 테이블을 복합키로 잡고 channel_id를 파티션 키로 명시한 것이라고 이해했다.

그런데 정리하다 보니 이 둘이 배타적인 선택이 아니었다. 기본키를 어떻게 묶느냐와 숫자를 어디서 받느냐는 서로 다른 축이다.

| | 값을 지역 카운터로 | 값을 스노플레이크로 |
| --- | --- | --- |
| 기본키 = (channel_id, msg_id) | 책의 설계. 락 있음 | 클러스터링 유지 + 락 없음 |
| 기본키 = msg_id 단독 | 전역 유일성이 깨진다 | 내 프로젝트 방식 |

오른쪽 위 칸이 둘의 장점을 합친 조합이다. 기본키는 복합으로 묶고 msg_id 자리에 스노플레이크 값을 넣으면, 클러스터링을 유지하면서 번호 발급 락이 사라진다. 비용의 출처를 분리하면 이렇게 된다.

```
클러스터링 이득   <- channel_id 를 선두에 둔 것에서 온다
삽입 흩어짐 비용  <- 같은 선택에서 온다. 떼어낼 수 없다
번호 발급 락      <- 지역 카운터를 쓴 것에서 온다. 떼어낼 수 있다
```

락은 떼어낼 수 있고 삽입 흩어짐은 못 떼어낸다. 이슈로 올린 질문이 이것이다.

### 3. 기기 제한은 서버 부하 때문인가

요구사항의 "하나의 계정으로 여러 단말 동시 접속"을 보고, 카카오톡은 기기 제한이 있는데 디스코드는 없는 게 떠올라서 생긴 질문이다.

부하는 이유가 아니다. 책의 추정으로 계산하면 연결당 10KB이므로 동시 접속 100만 명이 10GB이고, 기기가 두 배면 20GB다. 기능을 금지할 이유가 아니라 서버를 몇 대 더 둘 이유다.

진짜 이유는 메시지 정본이 어디 있느냐였다. 2014년 감청 논란 당시 다음카카오는 서버 저장 기간을 2~3일로 줄였다고 발표하면서, 메시지는 서버에서 지워져도 스마트폰에는 계속 남아 있고 암호키도 단말에만 저장된다고 설명했다. 즉 카카오톡 서버는 저장소가 아니라 중계소다.

| | 카카오톡 | 디스코드, 책의 설계 |
| --- | --- | --- |
| 메시지 정본 | 단말 | 서버 |
| 서버의 역할 | 중계 (2~3일) | 영구 저장소 |
| 기기란 무엇인가 | 사본을 들고 있는 복제본 | 서버를 보는 창 |
| 기기를 추가하면 | 복제본이 하나 더 생긴다 | 창이 하나 더 생긴다 |
| 기기를 바꾸면 | 대화가 사라진다 (백업 필요) | 그대로 다 보인다 |

마지막 줄이 관찰로 검증된다. 2014년 자료라 현재 정책은 확인하지 못했지만, 기기를 바꾸면 대화가 안 넘어가서 백업을 따로 해야 하는 게 정본이 단말에 있다는 증거다.

그래서 기기 제한은 복제본 수를 묶어서 충돌 범위를 최소화하는 선택이다. 정본이 단말에 있고 단말이 여럿이면 그게 다중 마스터 복제이고, 폰에만 있는 메시지와 노트북에만 있는 메시지가 갈라진다. 4주차에 본 충돌 해결 문제가 그대로 들어온다.

반대로 책의 요구사항에 이력을 영원히 보관한다는 것과 여러 단말 동시 접속이 나란히 있는 건 우연이 아니었다. 같은 결정의 앞뒷면이다. 영구 보관을 서버가 하기로 정했으니 단말 여러 개가 공짜가 된 것이고, 책이 채팅 이력을 키-값 저장소에 넣는 이유를 길게 설명하는 자리가 바로 그 결정이다.

`cur_max_message_id` 단말 동기화도 서버에 이력이 있다는 전제가 있어야 성립한다. 나중에 켠 단말이 자기 커서 이후를 요청하면 서버가 그 사이 대화를 전부 줘야 하는데, 카카오톡 구조에서는 2~3일이 지났으면 줄 것이 없다.

### 4. 정족수(W+R>N)를 기기에 쓸 수 있나, 기기끼리 동기화는 안 하나

3번에서 기기를 복제본으로 보고 나니 생긴 질문이다.

정족수는 쓸 수 없고 이유가 명확하다. 정족수는 복제본이 켜져 있다는 전제에서 성립하는데 기기의 가용성은 제어되지 않는다. 노트북은 꺼져 있고 폰은 비행기 모드다. 응답을 세는 조정자도 없다.

기기 2대에 4주차 공식을 대입해보면 답이 바로 나온다.

| 설정 | W+R>N 만족? | 실제로 쓰면 |
| --- | --- | --- |
| W=2, R=1 | 3>2 만족 | 노트북이 꺼져 있으면 메시지 수신이 실패한다 |
| W=1, R=2 | 3>2 만족 | 메시지를 읽으려면 두 기기를 다 켜야 한다 |
| W=1, R=1 | 2>2 불만족 | 동작한다 |

위의 둘은 서비스가 성립하지 않는다. 유일하게 가능한 W=1, R=1은 정의상 W+R>N을 만족하지 못한다. 즉 기기 간 복제는 선택의 여지 없이 최종적 일관성이다. 4주차 CAP 정리에서 네트워크 장애를 막을 수 없어 일관성을 포기한다고 정리했는데, 여기서는 네트워크 장애 자리에 기기가 꺼져 있음이 들어간다.

기기끼리 직접 동기화하지 않는 이유는 1번과 같다. 내 폰과 내 노트북도 서로에게 못 닿는다. 그리고 더 근본적으로 직접 동기화는 둘이 동시에 켜져 있어야 한다.

```
기기끼리 (메시) - 안 쓴다            서버 경유 (스타) - 책의 방식
   폰 ------ 노트북                   폰    노트북   태블릿
    \        /                          \     |     /
     \      /                            \    |    /
      태블릿                                서버
```

| | 연결 수 | 동시에 켜져 있어야 하나 |
| --- | --- | --- |
| 메시 | N(N-1)/2 | 그렇다 |
| 스타 (서버) | N | 아니다 |

서버는 기기들이 서로 다른 시간에 만날 수 있게 해주는 장소다. 그리고 여기서 3번의 2~3일이 설명된다. 그 기간은 저장이 아니라 기기가 따라잡을 수 있는 유예 기간이다. 영구 보관을 안 하기로 했으면 이 기간을 0으로 만들 수 없다. 기기 동기화가 아예 깨지기 때문이다.

책의 단말 동기화가 정확히 스타 구조다. 기기마다 `cur_max_message_id`를 각자 들고 서버에만 묻고, 기기끼리는 서로를 모른다. 그래서 기기가 몇 대든 간섭하지 않고 충돌도 생기지 않는다.

## 내 프로젝트에 채팅이 이미 있었다

| 책의 자리 | 내 프로젝트 (전시 커뮤니티, 스프링부트) |
| --- | --- |
| 폴링 / 롱 폴링 / 웹소켓 | 폴링 3초 |
| 상태 유지 채팅 서버 | 없음. 일반 REST 컨트롤러 |
| 서비스 탐색 (주키퍼) | 없음 |
| 채팅 이력 저장소 | MySQL |
| 메시지 ID | auto_increment 전역 단독 + 보조 인덱스 (room_id, id) |
| 동기화 큐 / cur_max_message_id | `after` 커서 |
| 지난 대화 조회 | `before` 커서 |
| 읽음 확인 | 참여자별 마지막 읽은 메시지 ID 컬럼 두 개 |
| 접속 상태 표시, 심박 | 없음 |

### 폴링을 택했더니 책의 절반이 필요 없어졌다

이게 이 장을 읽으면서 제일 크게 얻은 것이다. 책은 웹소켓을 고르고 나서 그 뒤에 따라오는 것들을 길게 설명하는데, 폴링을 쓰면 그게 통째로 사라진다.

| 책의 구성요소 | 폴링을 쓰면 |
| --- | --- |
| 웹소켓 연결 관리 | 필요 없다 |
| 상태 유지 채팅 서버 | 필요 없다. 무상태 서버로 끝난다 |
| 서비스 탐색 (주키퍼) | 필요 없다. 어느 서버에 붙어도 된다 |
| 송신자와 수신자를 같은 서버에 모으기 | 문제 자체가 없다 |
| 심박으로 연결 끊김 감지 | 유지할 연결이 없다 |

책이 롱 폴링의 단점으로 무상태 HTTP 서버와 라운드 로빈 때문에 송신자와 수신자가 같은 채팅 서버에 붙지 않을 수 있다고 적는데, 폴링은 애초에 서버가 메시지를 밀어주지 않으니 이 문제가 없다. 받는 쪽이 자기가 가져간다.

대가는 전부 요청 수로 간다. 책이 폴링의 단점으로 적은 메시지가 없어도 서버 자원이 낭비된다는 것이 그대로다. 3초 폴링이면 사용자 한 명이 분당 20번, 시간당 1,200번 묻는다. 대화가 없는 동안에도 계속 묻는다.

### 커서가 책의 cur_max_message_id였다

메시지 조회 API가 커서 두 개로 세 방향을 처리한다.

| 커서 | 쓰임 | 책의 대응 |
| --- | --- | --- |
| 둘 다 없음 | 최초 진입 | - |
| `after` | 폴링. 그 ID 이후만 | `cur_max_message_id` 그 자체 |
| `before` | 위로 스크롤. 그 ID 이전만 | - |

엔티티 주석에 이렇게 적혀 있다.

> 폴링 조회가 where room_id = ? and id > ? 형태라 (room_id, id) 복합 인덱스를 둡니다. id가 단조 증가하므로 시각 대신 id를 커서로 씁니다.

읽고 나서야 id가 단조 증가하므로라는 부분이 왜 중요한지 알았다. 7장의 ID 생성기 요구사항에 시간 순서가 들어 있었던 이유가 이것이다.

| ID 방식 | `after` 커서가 |
| --- | --- |
| auto_increment (현재) | 동작한다. 단일 DB라서 |
| 스노플레이크 | 동작한다. 시간 순서를 보장하니까 |
| UUID | 완전히 깨진다. 크기 비교에 의미가 없다 |

즉 지금 구조는 ID가 전역에서 단조 증가한다는 데 의존하고 있고, 샤딩하면 깨진다. 책이 메시지 ID 생성 방식을 따로 한 절로 다루는 이유를 내 코드에서 확인한 셈이다.

커서를 시각이 아니라 ID로 쓴 것도 중요했다. 시각으로 하면 같은 밀리초에 들어온 메시지가 둘이면 하나를 건너뛰거나 두 번 받는다. ID는 중복이 없으니 그 문제가 없다. 9장에서 시계 때문에 중복 판정이 깨지던 것과 같은 성질의 문제다.

### 방 생성 경합에서 4주차가 또 나왔다

두 사람이 동시에 대화하기를 누르면 양쪽 다 방이 없다고 보고 INSERT를 시도한다. 이 구조가 4주차 멱등성 키와 10장 중복 알림과 같은 자리다.

방어가 세 겹이다.

1. 참여자 두 명의 ID를 정렬해서(작은 쪽을 항상 A) 저장한다. 순서에 상관없이 같은 방이 되게 한다
2. (userA, userB)에 유니크 제약을 건다. 최종 방어선이다
3. 유니크 위반이 나면 실패한 트랜잭션을 버리고 새 트랜잭션으로 다시 조회한다

3번이 왜 그렇게 돼 있는지는 코드 주석을 읽고 알았다. 같은 트랜잭션에서 재조회하면 두 가지 이유로 안 된다. 제약 위반이 나면 하이버네이트가 세션을 오염된 상태로 표시해서 이어지는 조회가 죽고, MySQL 기본 격리수준(REPEATABLE READ)에서는 재조회가 최초 SELECT 시점 스냅샷을 그대로 보므로 상대가 방금 커밋한 방이 여전히 안 보인다.

두 번째가 4주차에 정리한 내용과 직접 이어진다. 그때 트랜잭션은 시작 시점 스냅샷을 본다는 것을 배웠는데, 그게 실제로 버그를 만드는 지점을 여기서 봤다.

결론은 4주차와 같다. 정렬과 재시도는 편의고, 진짜 방어는 DB 유니크 제약이다.

### 읽음 확인은 전진 전용 UPDATE다

방 테이블에 참여자별로 마지막 읽은 메시지 ID 컬럼이 있다. 읽음 처리를 할 때 원자적 UPDATE로 처리해서 읽음 위치가 뒤로 밀리지 않게 한다.

그리고 세 방향 중 읽음 처리를 하는 건 최초 진입과 폴링뿐이다. 위로 스크롤은 하지 않는다. 지난 대화는 이미 읽은 지점보다 과거라 읽음 위치가 움직일 일이 없기 때문이다. 전진 전용이라 호출해도 아무 일이 안 일어나지만 쿼리가 낭비돼서 뺐다.

책은 읽음 확인을 따로 설명하지 않는데, 구현해보니 읽음 위치는 단조 증가한다는 게 핵심이었다. 그 덕분에 동시 요청이 와도 경합이 안 생긴다. 큰 값으로 덮어쓰는 UPDATE는 순서가 바뀌어도 결과가 같다. 4주차에 본 LWW와 같은 성질이다.

### 내 구조의 한계

책과 비교하면서 알게 된 것들이다.

1. 방이 1:1 전용이다. 참여자를 userA, userB 컬럼으로 들고 있어서 3명이 되는 순간 스키마를 바꿔야 한다. 책처럼 channel_id와 참여자 테이블로 가면 1:1이 특수 케이스가 되는데, 지금은 1:1이 구조 자체다
2. 접속 상태 표시가 없다. 상대가 지금 온라인인지 모른다
3. 푸시 알림이 없다. 앱이 꺼져 있으면 메시지가 온 걸 모른다. 10장에서 정리한 제3자 서비스 자리가 비어 있다
4. 폴링 비용이 접속자 수에 비례해서 계속 든다. 대화가 없어도 든다

2번은 바로 할 수 있는 것으로 보인다. 폴링 요청 자체가 이 사람이 지금 보고 있다는 신호이므로, 마지막 폴링 시각을 기록하면 책의 심박과 같은 정보가 나온다. 책이 심박을 따로 만들어야 하는 건 웹소켓에서는 연결이 살아 있어도 클라이언트가 죽었는지 알 수 없기 때문인데, 폴링은 요청이 오는 것 자체가 살아 있다는 증거다. 폴링을 택해서 잃은 게 많지만 이건 공짜로 얻은 쪽이다.

## 4주차, 7장, 10장, 11장과 연계해서 생각해보자

| 이전 내용 | 12장에서 나오는 자리 |
| --- | --- |
| 4주차 CAP, 최종적 일관성 | 기기 간 복제는 정족수를 못 써서 필연적으로 최종적 일관성 |
| 4주차 멱등성 키, 유니크 제약 | 방 생성 경합의 최종 방어선 |
| 4주차 LWW | 읽음 위치를 큰 값으로 덮어쓰는 전진 전용 UPDATE |
| 4주차 REPEATABLE READ 스냅샷 | 같은 트랜잭션에서 재조회가 안 되는 이유 |
| 7장 ID 생성기의 시간 순서 요구사항 | 커서 기반 동기화가 ID의 크기 순서에 의존 |
| 7장 스노플레이크 | 메시지 ID 생성 세 방식 중 하나 |
| 10장 제3자 서비스 (APNS/FCM) | 앱이 꺼져 있을 때의 푸시 알림 |
| 11장 팬아웃 | 그룹 메시지를 수신자별 큐에 복사하는 동기화 큐 |
| 5장 샤딩 | channel_id를 파티션 키로 |

7장과의 연결이 가장 뜻밖이었다. ID 생성기에서 시간 순서를 보장한다는 것이 왜 요구사항인지 그때는 막연했는데, 커서 기반 동기화가 그것에 전적으로 의존한다는 걸 내 코드에서 봤다.

## 스스로 확인해본 것 - 폴링은 어디까지 되나

내 프로젝트가 폴링인데 책은 웹소켓으로 가니, 어디서 갈리는지 계산해봤다.

```
폴링 3초 = 사용자당 분당 20요청 = 초당 1/3 요청

동시 접속자 100명   -> 초당 33 요청       문제 없음
동시 접속자 1만 명  -> 초당 3,333 요청    서버를 늘려야 함
동시 접속자 100만   -> 초당 333,000 요청  불가능
```

마지막 줄이 책의 규모다. 참고로 13장 자동완성의 최대 QPS가 48,000이었는데 그보다 7배 크다. 그러니 책이 폴링을 바로 버리는 게 당연했다.

그리고 비용의 성질이 다르다는 게 핵심이었다.

| | 비용이 무엇에 비례하나 |
| --- | --- |
| 폴링 | 접속자 수 x 폴링 빈도. 대화량과 무관 |
| 웹소켓 | 연결 유지 메모리 + 실제 메시지 수 |

폴링은 아무도 말을 안 해도 돈이 든다. 웹소켓은 조용하면 메모리만 든다(책 기준 연결당 10KB). 즉 접속자가 많고 대화는 드문 서비스일수록 폴링이 불리하다.

내 프로젝트는 동시 접속자가 적어서 폴링이 합리적이고, 무엇보다 구현과 운영이 단순하다. 다만 언제 바꿔야 하는가의 기준을 이제 숫자로 말할 수 있게 됐다. 동시 접속자가 수천 단위로 올라가면 폴링 간격을 늘리는 것으로 버티다가, 그게 사용자 경험을 해치는 지점에서 웹소켓으로 가야 한다.
