# [6주차] 13장 정리 - 원지현
# 13장_ 검색어 자동완성 시스템

## 설계 범위
- 사용자가 입력한 단어로 시작하는 검색어만 자동완성 결과로 보여줌.
- 결과는 검색어 인기도(검색 빈도) 기준 상위 5개를 보여줌.
- 맞춤법 검사나 자동 수정은 지원하지 않으며, 영어 소문자만 지원한다고 가정함.
- 응답 속도: 사용자가 입력하는 속도를 따라잡을 수 있도록 100밀리초 이내에 결과를 보여줘야 함.
- DAU 천만 명 기준

## 개략적 규모 추정
- 사용자 1명이 하루 평균 10번 검색하고, 검색어 1개는 평균 20바이트이며, 글자를 입력할 때마다 요청이 발생한다고 가정함.
- QPS: 천만 × 10 × 20 / 86,400초 ≈ 초당 약 24,000건, 최대 QPS는 약 48,000건
- 질의 중 20%가 신규 검색어라고 가정하면 매일 약 0.4GB의 신규 데이터가 추가됨.

## 개략적 설계
시스템은 데이터 수집 서비스와 질의 서비스로 나뉨.
- 데이터 수집 서비스: 사용자가 입력한 검색어를 실시간으로 수집해 <검색어, 빈도>를 저장하는 빈도 테이블을 만듦.
- 질의 서비스: 주어진 접두어로 시작하는 검색어 중 빈도가 높은 상위 5개를 반환함.
- 데이터가 적을 때는 SQL의 LIKE와 ORDER BY로 처리할 수 있지만, 데이터가 많아지면 DB가 병목이 됨.

## 상세 설계

트라이(Trie) 자료구조
- 문자열을 한 글자씩 트리 형태로 저장하는 자료구조로, 접두어 검색에 적합함.
- 루트 노드는 빈 문자열이며, 각 노드는 글자 하나를 나타내고 자식 노드를 가짐.
- 각 노드에 해당 검색어의 빈도 정보를 함께 저장함.
- 기본 트라이로 상위 K개를 찾으려면 접두어 노드를 찾은 뒤 그 아래 모든 노드를 탐색하고 정렬해야 해서, 짧은 접두어일수록 매우 느림.

트라이 최적화
- 접두어 최대 길이 제한: 사용자가 매우 긴 검색어를 입력하는 경우는 드물므로 길이를 제한해, 접두어 노드를 찾는 시간을 사실상 상수 시간으로 만듦.
- 노드에 인기 검색어 캐시: 각 노드에 그 접두어로 시작하는 상위 K개 검색어를 미리 저장함.
    - 저장 공간을 더 사용하는 대신, 접두어 노드에 도착하는 즉시 결과를 반환할 수 있음.
    - 빠른 응답 속도가 중요한 자동완성에서는 합리적인 트레이드오프임.

데이터 수집 서비스
- 검색할 때마다 실시간으로 트라이를 수정하면 비용이 크고, 인기 검색어 순위가 자주 바뀔 필요도 없으므로 주기적으로 갱신함.
- 동작 흐름
    - 데이터 분석 서비스 로그: 검색창에 입력된 질의에 관한 원본 데이터가 쌓임. 데이터를 추가만 하고 수정하지 않음.
    - 로그 취합 서버: 대량의 로그를 서비스에 맞게 취합함. 실시간성이 중요한 서비스가 아니라면 주 단위로 취합함.
    - 취합된 데이터: <검색어, 해당 주의 시작 날짜, 빈도> 형태로 저장함.
    - 작업 서버: 주기적으로 비동기 작업을 실행해 트라이를 만들고 트라이 DB에 저장함.
    - 트라이 캐시: 트라이 데이터를 메모리에 유지하는 분산 캐시로, 매주 트라이 DB의 스냅숏을 떠서 갱신함.
- 트라이 DB 선택지
    - 문서 저장소: 매주 새 트라이를 직렬화해 저장함. (예: MongoDB)
    - 키-값 저장소: 트라이의 각 접두어를 키로, 노드에 저장된 데이터를 값으로 저장함.
- 상위 K개 계산: 트라이를 새로 만들 때 자식 노드부터 위로 올라오며, 자식 노드들의 상위 K개끼리만 비교해 부모 노드의 상위 K개를 정함. 모든 검색어를 매번 다시 정렬할 필요가 없음.

질의 서비스
- 동작 흐름: 로드밸런서 → API 서버 → 트라이 캐시에서 결과 조회 → 캐시에 없으면 트라이 DB에서 가져와 캐시에 채움
- 최적화 방안
    - AJAX 요청: 페이지 전체를 새로고침하지 않고 결과만 받아옴.
    - 브라우저 캐싱: 자동완성 결과는 짧은 시간 동안 잘 바뀌지 않으므로 브라우저에 캐시함. (예: 구글은 1시간 동안 캐시함)
    - 데이터 샘플링: 모든 질의를 로그로 남기면 자원 소모가 크므로 N개 중 1개만 기록함.

트라이 연산
- 생성: 작업 서버가 취합된 데이터로 트라이를 만듦.
- 갱신
    - 매주 한 번 새로운 트라이를 만들어 기존 트라이를 교체함. (주로 사용하는 방법)
    - 노드를 직접 갱신할 수도 있지만, 노드를 갱신하면 상위 K개를 저장한 모든 상위 노드도 갱신해야 해서 트라이가 크면 성능이 나쁨.
- 삭제: 혐오, 폭력, 성적 표현 등 위험한 검색어는 트라이 캐시 앞에 필터 계층을 두어 걸러내고, 트라이에서도 물리적으로 삭제함.

저장소 규모 확장
- 트라이가 커서 한 서버에 담을 수 없으면 샤딩함.
- 첫 글자 기준으로 나눌 수 있지만, 글자마다 시작하는 단어의 수가 달라 데이터가 고르게 분산되지 않음. (예: c로 시작하는 단어는 많고 x로 시작하는 단어는 적음)
- 과거 질의 데이터의 분포를 분석해 샤딩하는 방법이 효과적이며, 검색어 대응 샤드 관리자가 어떤 검색어를 어느 샤드에 저장할지 관리함.

## 마무리: 추가로 논의할 요소
- 다국어 지원: 트라이에 유니코드 데이터를 저장함.
- 국가별 인기 검색어: 국가마다 다른 트라이를 사용하고, CDN에 저장해 응답 속도를 높임.
- 실시간으로 변하는 검색어 추이 반영
    - 샤딩으로 작업 대상 데이터의 양을 줄임.
    - 최근 검색어에 더 높은 가중치를 주도록 순위 모델을 바꿈.
    - 데이터가 스트림 형태로 올 수 있으므로 카프카, 스파크 스트리밍 등 스트림 프로세싱 시스템을 사용함.

## 한국어 자동완성으로 확장해보기
영어는 알파벳 하나가 입력 단위라 그대로 트라이에 넣으면 되지만, 한국어는 화면에 보이는 글자(음절)와 실제 입력 단위(자모)가 달라 추가 고려가 필요함.

자모 단위 트라이
- 음절 단위로 저장하면 "하"와 "할", "한"이 서로 다른 글자로 인식되어, "하"를 입력했을 때 "할로윈", "한국"이 추천되지 않음.
- 검색어를 키보드 입력 순서대로 자모 분리해 저장하면, "하(ㅎㅏ)" 입력 시 하이마트, 할로윈, 한국이 모두 같은 접두어 아래에 위치함.
- 겹받침과 겹모음도 분리해야 입력 중간 상태와 맞음. (예: ㄺ → ㄹ + ㄱ, ㅘ → ㅗ + ㅏ)
- 화면에는 원래 단어를 보여줘야 하므로, 노드의 상위 K개는 자모가 아닌 원래 단어 형태로 저장함.

입력 중간 상태와 모호성
- 입력기가 "닭 → 달갸 → 달걀"처럼 받침을 다음 글자의 초성으로 넘기더라도, 자모로 보면 ㄷㅏㄹㄱ → ㄷㅏㄹㄱㅑ → ㄷㅏㄹㄱㅑㄹ로 접두어 관계가 유지되어 자동완성이 자연스럽게 이어짐.
- 단, 자모를 이어 붙여 비교하면 "닭" 입력 시 "달걀"도 함께 걸리는 모호성이 생김.
- 해결 방향: 입력과 정확히 일치하는 결과를 우선 정렬하거나, 글자 경계를 지켜 마지막 글자 안에서만 자모로 비교함. (네이버는 "닭"에서 달걀을 보여주지 않고, "달갸"에서 달걀을 보여주는 방식으로 보임)

초성 검색
- "ㅎㄱ"처럼 초성만 입력하는 검색을 지원하려면, 초성만 뽑아 만든 초성 전용 트라이를 따로 둠.
- 초성 트라이는 한 글자당 노드 하나라 크기가 작고, 같은 빈도 데이터로 함께 생성할 수 있음.
- 모음만으로는 단어를 구분하기 어렵고 사용하는 사람도 없으므로, 모음 전용 트라이는 만들지 않음.

소규모 프로젝트에 적용한다면
- 책의 설계는 초대규모 서비스 기준이므로, 소규모 프로젝트에서는 트라이를 직접 만들 필요가 없음. <-- 이게 포인트 ^.^
- DB 인덱스와 접두어 검색(LIKE '하%')으로 충분하며, 한국어는 자모 분리 컬럼과 초성 컬럼을 추가하고 인덱스를 걸어 비슷한 효과를 낼 수 있음.
- 데이터가 더 커지면 Elasticsearch 같은 검색 엔진의 자동완성 기능이나 Redis를 활용함.

## 그럼에도 불구하고 실제 서비스(데모데이 플젝: resay)에 적용해보기
팀 프로젝트 resay(대화 녹음 분석 보고서 서비스)에 13장 내용을 적용한다면 아래 두 가지 검색 기능을 생각해볼 수 있음.

1) 보관함에서 대화 상대 이름 찾기 → 접두어 + 초성 검색
- 사용자는 이름을 앞에서부터 입력하므로 13장의 접두어 검색 방식이 잘 맞음.
- "ㅇㅈ"만 입력해도 "우진"이 나오도록 초성 검색을 함께 지원함.
- 한 사용자의 보고서 수는 많지 않으므로, 트라이 없이 프론트엔드에서 자모·초성 분리 후 필터링해도 충분함.
- 이름은 대화 본문에서 추출하지 않고 별도 필드로 저장해, 대화 내용 속 단어("인정" 등)가 섞이지 않게 함.
- 초성 검색은 짧고 구분이 잘 되는 이름에만 적용함.

2) 대화 내용에서 특정 단어 찾기 → 포함 검색
- 단어가 문장 중간에 있어도 찾아야 하므로 접두어 검색(트라이)이 아닌 포함 검색이 필요함.
- 보고서 하나 안에서는 프론트엔드에서 단어 위치를 찾아 하이라이트하고 스크롤 이동함. 타임스탬프가 있다면 해당 녹음 위치로 이동할 수도 있음.
- 전체 보고서에서 찾을 때는 사용자 ID로 범위를 먼저 좁힌 뒤 LIKE '%단어%'로 검색하고, 데이터가 커지면 역색인 기반 전문 검색(MySQL FULLTEXT, Elasticsearch 등)을 사용함.
- 대화 내용이 민감해 암호화해 저장한다면, 보고서를 열어 복호화한 상태에서 프론트엔드가 검색하는 방식이 적합함.

정리
- 이름 찾기는 13장의 응용(접두어 + 초성), 대화 내용 찾기는 13장과 성격이 다른 포함 검색 문제임.
- 검색 대상을 이름과 내용으로 분리해 관리해야 결과가 정확해짐.
