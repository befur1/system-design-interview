# 뉴스 피드 시스템 설계 (News Feed System)

뉴스 피드 시스템에서 사용할 수 있는 캐시 구조.
1. 뉴스 피드 → 사용자별 피드의 게시물ID 목록

2. 콘텐츠: 인기 콘텐츠, 일반 콘텐츠 → 하이드레이션 시 실제 글 내용 ( 밑에서 설명함)

3. 소셜 그래프: 팔로어, 팔로잉 → 팬 아웃 시점, 피드 조회시 누구글을 가져올지?

4. 행동: 좋아요, 댓글달기, 기타

5. 횟수: 좋아요 횟수, 답글 횟수, 기타 → 자주 바뀌는 값은 따로 관리하자


뉴스 피드 캐시는 <포스팅 ID, 사용자ID> 순서쌍의 매핑 테이블로 저장
→ 내용은 어디서?
내용은 따로 관리한다. 뉴스 피드는 ID만 갖고 있고, 클라이언트가 조회하는 순간 다른 곳에 저장되어있던 피드의 내용이 뜬다.
이게 하이드레이션임


피드 열때 생기는 일

1. 내 피드의 게시물 ID 목록 가져오고, 이 ID로 게시물 캐시에서 글 본문, 작성 시각 조회

2. 작성자 ID로 사용자 캐시에서 이름, 프로필 사진 가져옴

3. 좋아요 수, 댓글 수는 카운터 캐시에서 가져옴

4. 설계안에서 CDN이 나오는데, 피드의 사진 동영상은 URL만 넘기고, 실제 파일은 앱이 CDN에서 직접 받는다.

이를 조립해 JSON으로 클라이언트에게 보내면 완성된 피드.

→ 카운터 캐시는 개수를 따로 저장하는 캐시임.
정확도 타협: 화면에 보이는 숫자가 실제랑 차이나도 사용자는 신경 쓰지 않으므로, 약간의 지연 오차가 있가.
그래서 12.8만과 같이 대략적인 표시 사용
핫 카운터: 유명 게시물에 좋아요가 폭주하면, 이때는 카운터를 여러개로 쪼갠다. 다시 한번에 읽을때는 샤딩된 카운터 사용



피드 발행 흐름

1. 웹 서버의 역할: 인증, 처리율 제한 기능. 인증 토큰 처리 → API 호출을 통해 포스팅
2. 쓰기 시점에 팬아웃, 읽기 시점에 팬아웃

인스타그램: 팔로워의 수를 기준으로 임계값을 설정, 그보다 아래면 쓰기시점 팬아웃, 위면 읽기시점 팬아웃
몇만명 정도의 팔로워: 피드 발행 → 팔로워 피드 캐시에 미리 써두는 방식
수백만 이상의 유명 계정: 팔로워가 피드를 열 때 그 계정의 최신 글을 가져와 합치도록 함.
임계값 자체는 서비스마다 트래픽과 인프라에 맞춰 정한다고 한다.
