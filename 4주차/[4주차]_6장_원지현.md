# [4주차] 6장 정리 - 원지현
# 6장_ 분산 키-값 저장소

## 분산 키-값 저장소의 필요성
- 단일 서버 키-값 저장소는 속도는 빠르지만 메모리 용량의 한계가 있음.
- 데이터 압축, 자주 쓰지 않는 데이터 디스크 저장 등의 개선책이 있으나 결국 대규모 트래픽을 감당하려면 분산 키-값 저장소(분산 해시 테이블)가 필수적임.

## CAP 정리
데이터 일관성(Consistency), 가용성(Availability), 파티션 감내(Partition Tolerance)라는 세 가지 요구사항을 동시에 만족하는 분산 시스템을 설계하는 것은 불가능하다는 정리.
- 데이터 일관성: 분산 시스템에 접속하는 모든 클라이언트는 어떤 노드에 접속했느냐에 관계없이 언제나 같은 데이터를 보아야 함.
- 가용성: 분산 시스템에 접속하는 클라이언트는 일부 노드에 장애가 발생하더라도 항상 응답을 받을 수 있어야 함.
- 파티션 감내: 두 노드 사이에 통신 장애(네트워크 파티션)가 발생하더라도 시스템은 계속 동작해야 함.
- 네트워크 파티션은 피할 수 없으므로 실무에서는 CP(일관성+파티션 감내) 또는 AP(가용성+파티션 감내) 시스템 중 하나를 선택해야 함.

## 핵심 컴포넌트 설계 기법
- 데이터 파티셔닝: 데이터를 여러 서버에 고르게 분산하기 위해 안정 해시(Consistent Hashing)를 사용함. 서버 추가/삭제 시 데이터 이동을 최소화할 수 있음.
- 데이터 다중화: 높은 가용성과 안정성을 위해 데이터를 N개의 서버에 비동기적으로 복제함.
- 데이터 일관성: 정족수 합의(Quorum Consensus) 프로토콜을 사용해 읽기/쓰기 연산의 일관성을 맞춤 (W + R > N 이면 강한 일관성 보장).
- 일관성 불일치 해소: 데이터 다중화로 인해 발생하는 데이터 변형 문제를 해결하기 위해 '데이터 버저닝'과 '벡터 시계(Vector Clock)'를 사용해 충돌을 발견하고 해소함.

## 장애 처리 로직
- 장애 감지: 두 대의 서버가 서로를 감시하는 것보다, 가십 프로토콜(Gossip Protocol) 같은 분산형 장애 감지 솔루션을 사용하는 것이 효율적임.
- 일시적 장애 처리: 단서 후 임시 위탁(Hinted Handoff) 기법을 사용해, 장애가 난 서버를 대신해 임시 서버가 쓰기 연산을 처리하고 나중에 복구되면 데이터를 밀어넣어 일관성을 맞춤.
- 영구적 장애 처리: 머클 트리(Merkle Tree, 해시 트리)를 사용해 사본 간의 일관성이 망가진 상태를 빠르게 탐지하고 동기화함.

## 적용 가능 사례 1. 실시간 대화 데이터 수집 아키텍처 방어 논리
- 현재 기획 중인 '대화 분석 서비스'는 끊임없이 쏟아지는 대화 데이터를 유실 없이 빠르게 받아내는 것이 가장 중요하다. 책에서 배운 CAP 정리 중 일관성(C)보다 쾌적한 채팅 환경을 위한 가용성(A)을 우선시하는 AP 모델이 우리 서비스 성격에 맞다.
  물론 당장은 단일 MySQL로도 충분하지만, 향후 유저가 늘어나고 대화 트래픽이 1초에 수만 건씩 쏟아지는 규모로 확장된다면 지금 구조로는 DB 병목이 올 수밖에 없다. 이때 가용성이 높고 쓰기 속도가 빠른 인메모리 분산 키-값 저장소(Redis 등)를 앞단에 두어 채팅 트래픽을 임시로 빠르게 수집하고, 백그라운드 스케줄러가 이를 묶어서 MySQL로 안전하게 비동기 저장하는 구조로 개선해 볼 수 있겠다. 
- 창업 대회에서 심사위원이 트래픽 처리나 DB 과부하에 대해 공격적인 질문을 던지면, 이런 식의 스케일업 로드맵을 6장의 논리로 방어하면 아주 좋은 포인트가 될 것 같다.
