# 분산 시스템을 위한 유일 ID 생성기 설계 (Unique ID Generator)

# 분산 시스템에서 유일 ID 설계하기

## 1. 왜 분산 환경에서는 auto_increment를 쓸 수 없을까

DB 서버가 한 대라면 관계형 DB의 auto_increment 기본키를 쓰면 된다. 하지만 분산 환경에서는 이 방식이 통하지 않는다.

- 단일 장애점(SPOF)과 병목
    - DB가 하나면 고가용성이 깨진다.
    - 모든 ID 발급 요청이 하나의 DB 서버로 몰려 병목이 생긴다.
- 데이터 분산과 확장의 어려움
    - DB를 여러 대로 샤딩하면 서버 A와 서버 B가 만든 ID가 충돌할 수 있다.
- 네트워크 지연
    - ID를 얻을 때마다 DB와 네트워크 통신을 해야 한다.

## 2. 분산 환경에서도 남는 과제

분산 시스템을 쓰더라도 ID 생성의 지연 시간(Latency)을 낮추는 것은 아키텍처 관점에서 까다로운 문제다.

- 네트워크 통신 오버헤드
- 동기화와 락 경합: 여러 프로세스가 동시에 ID를 만들 때 일관성을 지키려면 락이 필요하다.
- 시간 동기화 문제

그래도 분산 시스템은 써야 하므로, 유일한 ID를 만드는 방법들을 알아본다.

## 3. 유일 ID 생성 방법

### 3-1. 다중 마스터 복제

특징: 기존 DB의 auto_increment 기능을 활용한다.

개념: 두 개 이상의 DB 노드가 모두 읽기와 쓰기 권한을 가지며, 한 노드의 변경 사항을 다른 노드와 서로 동기화하는 분산 DB 아키텍처.

작동 원리
- 마스터가 N대일 때 각 서버의 auto_increment 증가 간격을 N으로 설정한다.
- 시작값(offset)은 서버마다 다르게 지정한다.
- 결과적으로 기본키 충돌이 나지 않는다.

```sql
-- Master A
SET GLOBAL auto_increment_increment = 3;
SET GLOBAL auto_increment_offset = 1;

-- Master B
SET GLOBAL auto_increment_increment = 3;
SET GLOBAL auto_increment_offset = 2;
```

한계점
- 스케일 아웃이 어렵다: 마스터를 3대에서 4대로 늘리면 모든 서버의 offset과 increment를 바꿔야 한다.
- 시간 순서 보장이 안 된다: A는 트래픽이 많고 B는 적다면 ID 순서가 생성 시간 순서와 어긋날 수 있다.

### 3-2. UUID

특징: 서버나 DB의 도움 없이 각자 독립적으로 ID를 생성할 수 있다.

대표 버전
- v4
    - 128비트로 길다.
    - 시간 순 정렬이 되지 않는다.
    - 숫자가 아닌 값이 포함될 수 있다.
    - 주 용도: API 토큰, 비밀 링크, 비-RDBMS
- v7
    - 시간 순 정렬을 지원한다.

### 3-3. 티켓 서버

특징: 중앙집중식 서버가 ID를 발급해 중복 없는 ID를 제공한다.

한계점
- 티켓 서버 자체가 SPOF가 된다. 이 서버에 장애가 나면 나머지 시스템 전체가 영향을 받는다.

### 3-4. 트위터 스노플레이크

64비트 ID를 여러 구역으로 나눠 구성한다.

```
1 bit   41 bits: Timestamp (ms)        10 bits: Node ID   12 bits: Sequence
┌───┬──────────────────────────────────┬──────────────┬──────────────┐
│ 0 │ 00000000000000000000000000000... │  0000000000  │ 000000000000 │
└───┴──────────────────────────────────┴──────────────┴──────────────┘
```

| 비트 범위 | 용도 | 설명 |
| --- | --- | --- |
| 1 bit | Sign bit (부호) | 항상 0으로 고정해 양수로 유지 |
| 41 bits | Timestamp (밀리초) | 기준 시점(Epoch) 이후 경과한 밀리초 |
| 10 bits | Node ID (서버 식별자) | ID를 생성하는 노드의 고유 ID, 최대 2^10 = 1,024대 구별 |
| 12 bits | Sequence Number | 같은 서버, 같은 밀리초 안에서 증가하는 카운터, 밀리초당 최대 2^12 = 4,096개 |

참고
- 41비트 타임스탬프는 약 69년까지 표현 가능하다. 그 이후에는 기원 시각(Epoch)을 바꾸거나 ID 체계를 바꿔야 한다.

## 4. 시계 동기화

### 4-1. 분산 시스템에서 시계 동기화가 중요한 이유

여러 서버가 협력하는 환경에서 시계가 어긋나면 다음 문제가 생긴다.

- 분산 ID 생성 오류 (스노플레이크처럼 시간 기반 ID에서 중복이나 순서 역전 발생)
- 데이터 일관성 파괴
- 로그 분석과 트랜잭션 추적 불가

### 4-2. 시계 동기화를 처리하는 대표적 방법

NTP (Network Time Protocol)
- 원자시계나 GPS 기반 표준시를 가진 시간 서버로부터 네트워크로 시간을 받아 각 서버의 시계를 맞추는 가장 보편적인 프로토콜이다.
- 일반적인 인터넷 환경에서는 수 밀리초(ms) 오차 범위로 시계를 맞춘다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 다중 마스터 복제 | 기존 DB 기능 그대로 활용 | 서버 증설 어려움, 시간 순서 보장 안 됨 |

| 스노플레이크 | 64비트, 시간 순 정렬, 확장 용이 | 시계 동기화에 의존 |
