## 6장 요약 - 키-값 저장소 설계

키-값 저장소는 비관계형 데이터베이스이며, 저장되는 값은 고유 식별자인 키를 통해서만 접근할 수 있음

```
put(key, value)   키-값 쌍을 저장소에 저장
get(key)          키에 매달린 값을 꺼냄
```

### 1. 문제 이해 및 설계 범위 확정

읽기/쓰기 성능과 일관성 사이에는 반드시 타협이 필요하므로, 어떤 특성을 우선할지 먼저 정해야 함

이 장에서 설계할 저장소의 요구사항

- 키-값 쌍의 크기는 10KB 이하
- 큰 데이터를 저장할 수 있어야 함
- 높은 가용성 - 장애가 있어도 빠르게 응답해야 함
- 높은 규모 확장성 - 트래픽에 따라 서버를 늘릴 수 있어야 함
- 데이터 일관성 수준을 조정할 수 있어야 함
- 응답 지연시간이 짧아야 함

### 2. 단일 서버 키-값 저장소

한 대에서 도는 저장소는 구현이 쉬움. 키-값 쌍 전부를 메모리에 해시 테이블로 저장하면 됨

But, 메모리는 용량 한계가 있고 서버가 하나뿐이라 장애에 취약함

개선책으로는

- 데이터 압축
- 자주 쓰는 데이터만 메모리에 두고 나머지는 디스크에 저장

→ 그래도 한 대로 감당할 수 없는 지점이 오면 분산 저장소로 가야 함

### 3. 분산 키-값 저장소

분산 키-값 저장소는 분산 해시 테이블이라고도 부름. 여러 서버에 키-값 쌍을 분산시키는 구조임

#### CAP 정리

데이터 일관성(Consistency), 가용성(Availability), 파티션 감내(Partition tolerance) 세 요구사항을 동시에 만족하는 분산 시스템을 만들 수 없다는 정리

- 일관성 - 어떤 노드에 접속하든 같은 데이터를 봐야 함
- 가용성 - 일부 노드에 장애가 생겨도 응답을 받을 수 있어야 함
- 파티션 감내 - 네트워크 파티션(두 노드 사이 통신 장애)이 생겨도 시스템이 동작해야 함

분산 시스템에서 네트워크 장애는 피할 수 없으므로 파티션 감내는 반드시 지원해야 함

→ 그래서 실질적으로는 CP(일관성 우선)냐 AP(가용성 우선)냐의 선택이 됨

- CP 시스템 - 파티션이 생기면 일관성이 깨진 노드의 응답을 막음. 은행 잔고처럼 틀린 값을 주면 안 되는 경우
- AP 시스템 - 파티션이 생겨도 일단 응답함. 오래된 데이터를 반환할 수 있고, 파티션이 복구되면 데이터를 동기화함

#### 데이터 파티션

데이터를 하나의 서버에 다 넣을 수 없으므로 작은 파티션으로 나눠 여러 서버에 저장해야 함

이때 두 가지를 고려해야 함

1. 데이터를 여러 서버에 고르게 분산할 수 있는가
2. 노드가 추가되거나 삭제될 때 데이터 이동을 최소화할 수 있는가

→ 5장에서 본 안정 해시가 이 문제를 푸는 방법임. 서버를 해시 링에 배치하고 키의 위치에서 시계 방향으로 탐색해 만나는 첫 서버에 저장함

안정 해시를 쓰면 얻는 이점

- 규모 확장 자동화 - 시스템 부하에 따라 서버를 자동으로 추가/삭제할 수 있음
- 다양성 - 서버 용량에 따라 가상 노드 수를 조절해 부하를 차등 배분할 수 있음

#### 데이터 다중화

높은 가용성과 안정성을 위해 데이터를 N개 서버에 비동기적으로 다중화해야 함

해시 링에서 키를 시계 방향으로 탐색하면서 만나는 첫 N개 서버에 사본을 저장함

But, 가상 노드를 쓰면 시계 방향으로 만나는 노드가 실제로는 같은 물리 서버일 수 있음
→ 이 경우 사본이 한 서버에 몰려 다중화의 의미가 사라지므로, 중복되는 물리 서버는 건너뛰고 서로 다른 서버 N개를 고름

또한 같은 데이터 센터에 있는 노드는 정전, 네트워크 장애, 자연재해 등의 문제를 동시에 겪을 수 있으므로, 사본은 여러 데이터 센터에 분산하는 것이 안정적임

#### 데이터 일관성

여러 노드에 다중화된 데이터는 적절히 동기화되어야 함. 이때 쓰는 것이 정족수 합의(Quorum Consensus) 프로토콜임

```
N = 사본 개수
W = 쓰기 연산에 대한 정족수. W개 서버로부터 쓰기 성공 응답(ack)을 받아야 성공으로 간주
R = 읽기 연산에 대한 정족수. R개 서버로부터 응답을 받아야 성공으로 간주
```

중재자(coordinator)는 클라이언트와 노드 사이에서 프록시 역할을 함

- 쓰기 - 중재자가 사본 노드들에 값을 뿌리고, W개의 ack가 모이면 성공으로 확정함
- 읽기 - 중재자가 사본 노드들에 값을 물어보고, R개의 응답이 모이면 그중 최신 버전을 골라 반환함

W와 R, N을 어떻게 잡느냐가 곧 지연시간과 일관성 사이의 타협임

- R = 1, W = N → 빠른 읽기에 최적화
- W = 1, R = N → 빠른 쓰기에 최적화
- W + R > N → 강한 일관성 보장 (보통 N=3, W=R=2)
- W + R ≤ N → 강한 일관성이 보장되지 않음

W + R > N 이면 강한 일관성인 이유는, 쓴 서버 집합(W개)과 읽은 서버 집합(R개)의 합이 N보다 크면 두 집합이 반드시 최소 한 대에서 겹치기 때문임(비둘기집 원리). 겹친 노드가 최신 값을 갖고 있으므로 읽기 결과에 최신 값이 반드시 포함됨

#### 일관성 모델

- 강한 일관성 - 모든 읽기 연산은 가장 최근에 쓴 결과를 반환. 최신 값을 볼 때까지 읽기를 허용하지 않음
- 약한 일관성 - 읽기 연산이 최신 값을 반환한다는 보장이 없음
- 결과적 일관성 - 약한 일관성의 한 형태. 갱신 결과가 결국에는 모든 사본에 반영됨

강한 일관성은 모든 사본에 쓰기가 반영될 때까지 읽기를 막으므로 고가용성 시스템에는 부적합함

→ 다이나모와 카산드라는 결과적 일관성을 채택함. 이 장에서 설계하는 저장소도 마찬가지임

결과적 일관성을 택하면 쓰기 연산이 병렬로 일어났을 때 사본마다 값이 달라질 수 있고, 이 불일치를 클라이언트가 읽어서 해결해야 함

#### 일관성 불일치 해소 - 데이터 버저닝

다중화는 가용성을 높이지만 사본 간 불일치를 낳음. 버저닝은 값을 덮어쓰지 않고 변경마다 새로운 버전을 만들어 보존하는 기법임

벡터 시계는 `[서버, 버전]`의 순서쌍을 데이터에 매단 것임. 어떤 버전이 앞서는지, 충돌하는지, 다른 버전과 호환되는지 판별하는 데 쓰임

```
D([S1, v1], [S2, v2], ..., [Sn, vn])
```

동작 규칙

- 데이터 D를 서버 Si가 기록하면
  - Si 항목이 이미 있으면 vi를 증가시킴
  - 없으면 [Si, 1]을 새로 추가함
- 한번 생긴 항목은 지우지 않음

예시

```
D1([Sx, 1])                       Sx 가 최초로 기록
D2([Sx, 2])                       Sx 가 또 기록 → 자기 항목만 증가
   ├─ Sy 가 기록 → D3([Sx, 2], [Sy, 1])
   └─ Sz 가 기록 → D4([Sx, 2], [Sz, 1])
```

D3와 D4는 같은 D2에서 갈라져 나왔지만 서로 다른 서버가 처리했으므로 충돌임. 충돌을 클라이언트가 해결한 뒤 Sx가 다시 기록하면 `D5([Sx, 3], [Sy, 1], [Sz, 1])`이 됨

버전 비교 규칙

- 어떤 버전 X의 모든 항목이 Y의 대응 항목보다 작거나 같으면, X는 Y의 조상(이전 버전)임 → 충돌 아님
- 항목마다 앞서는 쪽이 엇갈리면 충돌임
- 상대에게 없는 항목은 0으로 간주함

벡터 시계의 단점

1. 충돌 감지 및 해소 로직이 클라이언트에 들어가므로 클라이언트 구현이 복잡해짐
2. `[서버, 버전]` 순서쌍의 개수가 계속 늘어남
   → 임계치를 정해 오래된 항목을 제거하는 방법이 있지만, 조상 관계를 정확히 판단할 수 없게 되어 충돌 해소 효율이 떨어짐

#### 장애 처리

대규모 시스템에서 장애는 흔한 일이므로, 감지하고 대응하는 전략이 필요함

**1) 장애 감지 - 가십 프로토콜**

한 노드의 의견만으로 장애를 단정할 수 없고, 그렇다고 모든 노드가 모든 노드에게 알리는 전체 전송(all-to-all)은 트래픽이 너무 큼

→ 가십 프로토콜을 사용함

- 각 노드는 멤버십 목록을 유지함. 멤버 ID와 박동 카운터(heartbeat counter) 쌍의 목록임
- 각 노드는 주기적으로 자기 박동 카운터를 증가시킴
- 각 노드는 무작위로 선정된 노드들에게 주기적으로 박동 카운터 목록을 보냄
- 목록을 받은 노드는 자기 멤버십 목록을 최신 값으로 갱신함
- 어떤 멤버의 박동 카운터가 지정된 시간 동안 갱신되지 않으면 장애 상태로 간주함

**2) 일시적 장애 처리 - 느슨한 정족수와 힌티드 핸드오프**

장애 상태인 서버로 가야 할 요청을 다른 서버가 임시로 처리함. 정족수 요구사항을 엄격히 지키지 않고 쓰기/읽기 연산을 수행할 수 있는 건강한 서버를 골라 쓰는 것을 느슨한 정족수(sloppy quorum)라고 함

장애 서버가 복구되면 임시로 받아둔 데이터를 일괄 반영하는데, 이를 힌티드 핸드오프(hinted handoff)라고 함

**3) 영구 장애 처리 - 반엔트로피와 머클 트리**

사본 간 비일관성을 검출하고 동기화하는 반엔트로피(anti-entropy) 프로토콜을 사용함. 이때 전송량을 줄이기 위해 머클 트리(Merkle tree)를 씀

머클 트리는 각 노드에 자식 노드들의 해시를 저장한 트리임

```
        [루트 해시]
        /        \
   [해시AB]    [해시CD]
   /    \      /     \
 [A]    [B]  [C]    [D]
  A      B    C      D
```

- 루트 해시가 같으면 두 사본은 완전히 동일함 → 비교 종료
- 다르면 아래로 내려가며 비교하되, 해시가 같은 가지는 통째로 건너뜀
- 결국 차이 나는 데이터만 찾아내어 그것만 동기화함

→ 동기화해야 할 데이터 양이 실제 차이의 크기에 비례하게 되어, 전체를 비교하는 것보다 훨씬 효율적임

**4) 데이터 센터 장애 처리**

정전, 네트워크 장애, 자연재해 등으로 데이터 센터 전체가 죽을 수 있으므로, 데이터를 여러 데이터 센터에 다중화해야 함

#### 시스템 아키텍처 다이어그램

주요 특징

- 클라이언트는 `get(key)`, `put(key, value)` 두 가지 API로 통신함
- 중재자는 클라이언트에게 키-값 저장소에 대한 프록시 역할을 하는 노드임
- 노드는 안정 해시의 해시 링 위에 분포함
- 노드를 자동으로 추가/삭제할 수 있도록 완전히 분산(decentralized)되어 있음
- 데이터는 여러 노드에 다중화됨
- 모든 노드가 같은 책임을 지므로 SPOF(단일 장애 지점)가 없음

#### 쓰기 경로

1. 쓰기 요청이 커밋 로그 파일에 기록됨
2. 데이터가 메모리 캐시에 기록됨
3. 메모리 캐시가 가득 차거나 임계치에 도달하면 데이터는 디스크의 SSTable에 기록됨

SSTable(Sorted-String Table)은 키-값 쌍을 정렬된 상태로 저장하는 테이블임

#### 읽기 경로

1. 데이터가 메모리 캐시에 있는지 먼저 확인함. 있으면 바로 반환
2. 없으면 디스크에서 가져와야 하는데, 어떤 SSTable에 있는지 알아내기 위해 블룸 필터를 사용함
3. 블룸 필터가 지목한 SSTable에서 데이터를 가져와 반환함

블룸 필터는 "확실히 없다"는 것을 빠르게 판단해주는 자료구조임. 모든 SSTable을 뒤지지 않고 후보를 좁혀 디스크 접근 횟수를 줄여줌

## 읽으면서 든 질문

### Q1. CAP에서 가용성(A)과 파티션 감내(P)는 왜 별개인가?

둘 다 "장애에도 살아남는다"로 읽혀서 구분이 안 됐는데, 가리키는 대상이 다름

- P는 사고 자체 - 네트워크가 끊기는 상황을 견디는 능력
- A와 C는 그 사고가 났을 때의 선택 - 응답을 줄 것인가(A), 정확한 값만 줄 것인가(C)

```
네트워크 단절 발생 (P 가 시험받는 순간)
   │
   ├─ A 선택 : 확신은 없지만 일단 응답함 (옛 값일 수 있음)
   └─ C 선택 : 정확하지 않을 바엔 응답을 거부함
```

즉 셋이 동급으로 나열되지만 실제로는 P가 먼저 터지고 A냐 C냐를 고르는 구조임. 그리고 분산 시스템에서 네트워크 단절은 선택이 아니라 필연이므로 P는 버릴 수 없음

### Q2. 읽기 연산을 하면 다른 서버에 "읽었다"고 알리는 것인가?

정족수를 처음 봤을 때 "s1에서 읽으면 s2, s3, s4에게 읽었다고 통보하는 건가" 싶었는데 방향이 반대였음. 알림이 아니라 질의임

```
1. 클라이언트가 s1 에 "key X 읽어줘" 요청
2. s1 이 중재자가 됨. X 를 해싱해 사본이 s2, s3, s4 임을 계산
3. s1 → s2, s3, s4   "너희가 가진 X 값이 뭐야?"
4. R = 2 라면 응답 2개가 도착한 시점에 성공으로 간주
5. 받은 응답 중 최신 버전을 골라 클라이언트에 반환
```

읽기는 데이터를 바꾸지 않으므로 남에게 알릴 이유가 없음. 정족수는 "몇 명에게 알렸나"가 아니라 "몇 명에게 물어 몇 개의 답을 받았나"임

한 대에만 묻지 않는 이유는 그 한 대가 오래된 값을 갖고 있을 수 있기 때문임. R개에 물어 최신을 고르는 것이 W + R > N이 성립하는 이유와 직결됨

읽기 복구(read repair)는 응답을 비교하다가 뒤처진 사본을 발견하면 그 자리에서 최신 값으로 갱신해 주는 것임. 즉 읽은 뒤 다른 서버로 가는 메시지가 있기는 한데, 그 내용은 "읽었다"가 아니라 "네 값이 오래됐다"임

쓰기와 읽기를 대비하면

- 쓰기 - 중재자가 값을 뿌림. ack는 "저장했다"는 뜻
- 읽기 - 중재자가 값을 물어봄. 응답은 "내 값은 이것이다"라는 뜻

그리고 정족수만으로는 부족함. 받은 응답 중 어느 것이 최신인지 판단하려면 값과 함께 버전 정보(벡터 시계)가 있어야 함 → 정족수와 데이터 버저닝은 한 세트로 봐야 함

### Q3. 저장소에 없는 키를 물어봐도 되는가? 삭제는 어떻게 처리되는가?

물어볼 수 있고 "없음"도 정상적인 응답이며 R에 포함됨

But, "없다"가 세 가지 의미일 수 있음

1. 애초에 저장된 적이 없다
2. 저장은 됐는데 이 사본만 아직 받지 못했다
3. 저장됐다가 삭제됐다

1번과 2번은 정족수로 어느 정도 걸러지지만 3번이 문제임

```
X 를 삭제 → s2, s3 에서 지워짐. s4 는 그때 장애 상태라 받지 못함
s4 복구
반엔트로피로 동기화 → s2 는 "없음", s4 는 "있음"
→ "있는 쪽이 최신"으로 판단하면 삭제한 데이터가 부활함
```

그래서 분산 저장소는 삭제 시 실제로 지우지 않고 "삭제됨(시각 T)"이라는 표식을 남김. 이를 툼스톤(tombstone)이라고 함. 그래야 동기화 시 "s4의 값은 삭제보다 이전 것"이라고 판단할 수 있음

→ 벡터 시계 충돌 해소에서 장바구니를 합집합으로 합칠 때 "삭제한 상품이 되살아나지 않는가"라는 문제와 같은 뿌리임

### Q4. 약한 일관성과 결과적 일관성의 차이는?

차이는 "언젠가 수렴한다"는 보장의 유무 하나임

- 약한 일관성 - 최신 값을 본다는 보장이 전혀 없음. 영원히 못 볼 수도 있음
- 결과적 일관성 - 지금은 못 봐도, 추가 쓰기가 없으면 결국 모든 사본이 같은 값으로 수렴함

순수한 약한 일관성의 예로는 실시간 스트리밍이나 인터넷 전화가 있음. 네트워크가 끊겨 놓친 2초는 나중에 따라잡히지 않고 그대로 사라짐

반면 결과적 일관성은 지금 오래된 값이 보여도 잠시 뒤에는 맞춰짐

중요한 것은 저절로 수렴하는 게 아니라는 점임. 수렴시키는 장치가 따로 있어야 함

- 읽기 복구 - 읽는 김에 뒤처진 사본을 갱신
- 힌티드 핸드오프 - 복구된 노드에 밀린 데이터를 넘겨줌
- 반엔트로피 + 머클 트리 - 사본끼리 주기적으로 비교해 차이를 맞춤

→ 6장이 장애 처리를 길게 다루는 이유가 여기 있음. "결과적 일관성을 택했다"는 것은 곧 "수렴시킬 책임을 시스템이 진다"는 뜻이고, 그 책임을 이행하는 구체적 방법이 장애 처리 절의 내용임

다만 결과적 일관성은 수렴한다는 것만 보장하지 얼마나 걸리는지는 약속하지 않음. 그래서 결제 직후 잔액 조회 같은 곳에는 쓸 수 없음

### Q5. 벡터 시계에서 순서쌍이 왜 갑자기 두 개가 되는가?

`D2([Sx, 2])`에서는 쌍이 하나였는데 `D3([Sx, 2], [Sy, 1])`에서 두 개가 되는 게 이해되지 않았음

순서쌍의 개수는 이 데이터를 건드린 서버의 가짓수임. 덮어쓰는 게 아니라 칸을 늘려가는 구조임

```
같은 서버가 또 기록  →  그 서버 항목의 숫자만 증가  (쌍 개수 그대로)
새 서버가 기록       →  새 항목을 추가             (쌍 개수 증가)
한번 생긴 항목은 지우지 않음
```

D1, D2는 Sx 혼자 처리했으므로 쌍이 하나였고, Sy가 이어받아 처리하면서 자기 항목이 새로 생긴 것임

Sx 항목을 지우면 안 되는 이유는, 지우는 순간 D3와 D4가 같은 조상에서 갈라졌다는 사실을 알 수 없게 되기 때문임. 순서쌍 목록이 곧 그 값이 거쳐온 경로 기록임

그리고 Sy와 Sz 입장에서는 둘 다 정상적으로 성공한 쓰기라는 점이 중요함. 에러가 난 것이 아니며, 충돌은 두 결과가 나중에 만났을 때 비로소 드러남. Git에서 두 브랜치가 각자 잘 커밋했는데 머지할 때 conflict가 나는 것과 같음

```
D3([Sx,2], [Sy,1])
D4([Sx,2], [Sz,1])

Sx 항목  2 = 2      같음
Sy 항목  1 > 0      D3 우세   ← 상대에게 없는 항목은 0 으로 봄
Sz 항목  0 < 1      D4 우세
→ 앞서는 쪽이 엇갈림 = 충돌
```

이 구조를 이해하면 책이 말한 "항목을 제거하면 조상 관계를 정확히 판단할 수 없다"는 단점도 자연히 이해됨. 갈라진 지점을 잃으면 조상 관계인데도 충돌로 오판하게 되고, 불필요한 충돌 해소가 늘어남

## AWS와 연결해보기

SAA 준비하며 배운 서비스로 6장 개념을 엮어보면

- 분산 키-값 저장소 → ElastiCache (Redis). Redis 자체가 분산 인메모리 키-값 저장소임
- 데이터 파티션 → Redis Cluster. 키를 고정된 슬롯에 배정하고 슬롯을 노드에 나눠 맡김. 노드가 늘어도 슬롯 일부만 옮기면 되는데, 5장 가상 노드와 같은 발상임
- 데이터 다중화 → RDS Multi-AZ, Aurora. 서로 다른 AZ에 두는 것은 "데이터 센터 장애 처리"에 해당
- 정족수 (N·W·R) → Aurora. 아래 참조
- 일관성 모델 → Multi-AZ와 Read Replica의 대비. 동기 복제는 강한 일관성, 비동기 복제는 결과적 일관성
- 장애 감지 (가십) → ElastiCache Redis Cluster. 클러스터 모드의 노드들이 서로 상태를 주고받으며 죽은 노드를 알아냄
- 고가용성 → ELB + ASG, 다중 AZ. 한 대가 죽어도 로드밸런서가 제외하고 ASG가 새로 채움

### Aurora - 책의 정족수가 실제로 돌아가는 곳

Aurora는 데이터를 3개 AZ에 6벌 저장하고

```
쓰기 - 6개 중 4개의 응답을 기다림      W = 4
읽기 - 6개 중 3개의 응답을 기다림      R = 3

N = 6, W = 4, R = 3
W + R = 7 > N = 6      ← 책의 정족수 조건
```

쓴 4개와 읽은 3개는 6개 중에서 고른 것이므로 최소 한 대는 반드시 겹치고, 그 노드가 최신 값을 갖고 있음

거기에 노드끼리 복제하며 손상된 사본을 스스로 복구하기까지 함
→ 6장이 따로따로 설명한 다중화, 정족수, 장애 복구가 한 서비스 안에 다 들어 있는 셈임

### RDS 복제 - 두 일관성 모델

- Multi-AZ - 동기(synchronous) 복제. 강한 일관성. 6장의 데이터 다중화와 데이터 센터 장애 처리에 해당
- Read Replica - 비동기(asynchronous) 복제. 결과적 일관성. 읽기 확장이 목적

```
t0  원본 DB 에 write
t1  Read Replica 에서 read  →  아직 옛 값 (복제 지연)
t2  복제 완료               →  이제 최신값  = 결과적 일관성
```

방금 쓴 데이터가 Read Replica에서 아직 보이지 않는 것이 책이 말한 결과적 일관성의 실제 사례임

주의할 점이 둘 있음

- Multi-AZ의 대기 인스턴스는 읽기를 받지 않음. 확장용이 아니라 순수하게 장애 복구용이며, 읽기를 나누려면 Read Replica를 따로 붙여야 함
- Multi-AZ는 복제이지 샤딩이 아님. 이름에 Multi가 붙어 "여러 개로 쪼갠다"로 읽히지만 같은 데이터를 통째로 한 벌 더 두는 것임. 사본이 여러 개면 복제, 조각이 여러 개면 샤딩으로 구분하면 됨

### ElastiCache - 복제와 파티션의 선택

- Redis - Multi-AZ와 자동 장애 조치, 읽기 복제본을 지원함. 클러스터 모드를 켜면 샤딩도 가능. AOF 로그로 디스크에 기록할 수 있음
- Memcached - 다중 노드로 데이터를 분할하는 샤딩만 지원. 복제와 고가용성이 없고 영속성도 없음

흔히 "Redis는 복제, Memcached는 샤딩"으로 대비시키지만 정확히는 Redis는 둘 다 되고 Memcached는 샤딩만 됨

Redis 클러스터 모드는 데이터를 여러 샤드로 쪼갠 뒤 각 샤드를 다시 복제하는데, 이것이 6장에서 말한 "파티션으로 쪼갠 각 조각을 다시 복제한다"는 구성 그 자체임

## 정리

- 키-값 저장소는 JOIN과 트랜잭션을 포기한 대신 수평 확장을 얻었고, 그 대가로 파티션·다중화·일관성·장애 처리를 직접 풀어야 함
- CAP에서 파티션 감내는 필수이므로 실질적으로 CP냐 AP냐의 선택이며, W·R 값이 그 손잡이 역할을 함
- 결과적 일관성을 택한다는 것은 수렴시킬 책임을 시스템이 진다는 뜻이고, 장애 처리 절이 그 책임의 이행 방법임
