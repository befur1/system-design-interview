    - 키-값 저장소는 get(key), put(key, value) 연산만 지원하고 DB입장에서 값에 관심이 없음
2. 관계와 조인이 없음

# 문제 이해 및 설계 범위 확정
읽기,쓰기 vs 메모리 사용량
데이터 일관성 vs 가용성
의 tradeOff를 생각해서 타협적 결정을 내린 설계를 만들어야한다.

다음의 특성을 갖는 키-값 저장소 설계를 예시로 공부한다
- 키-값 쌍의 크기는 10KB 이하
- 큰 데이터를 저장할 수 있어야함
- 높은 가용성을 제공
- 높은 규모 확장성을 제공 -> 트래픽 양에 따라 자동적으로 서버 증설/삭제가 이루어져야 한다.
- 데이터 일관성 수준은 조정이 가능해야 한다.
- latency가 짧아야 한다.

# 단일 서버 키-값 저장소
가장 직관적인 방법은 키-값 쌍 전부를 메모리에 해시 테이블로 저장하는 것이다. 레이턴시를 줄이는 데에는 적합하지만 모든 데이터를 메모리 안에 두는 것이 불가능한 경우가 있다. 따라서 다음의 방식을 사용할 수 있다.
- 데이터 압축
- 자주 쓰이는 데이터만 메모리에, 나머지는 디스크에 저장

해시 테이블이란?
키를 해시 함수에 넣어서 인덱스를 알아낸 뒤 그 방에 (key, value)쌍을 저장하는 자료구조이다. 해시 충돌이 일어날 수 있기 때문에 key도 같이 보관한다.

# 분산 키-값 저장소
분산 해시 테이블이라고도 불린다.
분산 시스템을 설계할 때는 CAP 정리( Consistency, Availabilty, Partition Tolerance theorem)을 고려해야한다.

## CAP 정리
CAP 정리는 데이터 일관성(consistency), 가용성(availability), 파티션 감내(partition tolerance) 세 가지 요구사항 모두를 동시에 만족할 수 없다는 정리이다. 
분산 시스템이니까 DB가 수평 확장이 되어있는 상태에서 동기화 필요성이 있다는 걸 전제로 생각해야함!

- 데이터 일관성: 모든 클라이언트는 어느 노드에 접속하든 같은 데이터를 보게 되어야 한다.
- 가용성: 클라이언트는 일부 노드에 장애가 발생하더라도 항상 응답을 받을 수 있어야 한다.
- 파티션 감내: 네트워크에 파티션(두 노드 간 통신 장애)이 발생하더라도 시스템은 계속 동작해야 한다. 
여기서 네트워크 파티션은 클라이언트와 서버 사이의 통신이 아니라 데이터를 복제하고 나눠 갖는 DB서버들끼리의 내부 네트워크를 의미한다(동기화).

CAP 정리는 이들 가운데 어떤 두 가지를 충족하려면 나머지 하나는 반드시 희생되어야 한다는 것을 의미한다. 

- CP 시스템: 일관성과 파티션 감내를 지원하는 시스템. 파티션 발생 시 응답을 거부함으로써 일관성을 유지한다.
- AP 시스템: 가용성과 파티션 감내를 지원하는 시스템. 파티션 발생 시 응답을 반환함으로써 가용성을 유지한다.
- CA 시스템: 일관성과 가용성을 지원하는 시스템. 파티션 감내를 지원하지 않는다.

네트워크 장애가 0%인 완벽한 네트워크는 물리적으로 불가능하다. 파티션 감내는 그냥 자연재해고 이걸 전제한 뒤 A와 C의 tradeOff가 남는 것이다. 

이론상의 CA 시스템?
P가 발생하지 않는 단일 서버 시스템을 의미함. 서버가 1대니까 P가 일어날 수 없고 그 안에서 트랜잭션으로 C와 A를 보장할 수 있음.

## 시스템 컴포넌트
키-값 저장소 구현에 사용될 핵심 컴포넌트 및 기술들

### 데이터 파티션
대규모 애플리케이션의 경우 전체 데이터를 한 대의 서버에만 저장하는 것은 불가능하다. 따라서 데이터를 파티션으로 분할해 여러 서버에 분산 저장해야 한다. 데이터를 분할 할 때 다음 두 가지 문제를 중요하게 따져봐야 한다.
핵심 목적이 용량 확장 & 부하 분산이다.

- 데이터를 여러 서버에 고르게 분산할 수 있는가?
- 노드가 추가되거나 삭제될 때 데이터의 이동을 최소화할 수 있는가?

안정해시는 다음 두 조건을 푸는 데 적합한 기술이다. 다음의 이점을 얻을 수 있다.
- 규모 확장 자동화: 시스템 부하에 따라 서버가 자동으로 추가되거나 삭제되도록 만들 수 있다. (서버 증감에 따른 데이터 재배치 최소화)
- 다양성: 각 서버의 용량에 맞게 가상노드의 수를 조정할 수 있다. 고성능 서버는 더 많은 가상 노드를 갖도록 설정할 수 있다.

### 데이터 다중화
높은 가용성과 안정성 확보를 위해 데이터를 N개 서버에 비동기적으로 다중화 할 필요가 있다. 동일한 데이터의 사본을 만드는 일이다.

가상 노드를 사용한다면 선택한 N개 노드가 대응될 실제 물리 서버의 개수가 N보다 작아질 수 있다.

-> 
이게 이해가 안 됐었다. 나는 A서버의 레플리카를 담당할 A-1, A-2 서버가 고정되어서 존재하는 줄 알고 해시 링을 대체 왜 사용할까? 그냥 전파하면 되는데 라는 생각이었는데 고정된 레플리카 서버가 존재하는 게 아니고 오히려 그걸 지양하기 위한 방법이었음. 
해시링 사용시 키마다 복제본을 맡는 서버 조합이 전부 달라지고 이는 곧 특정 서버가 죽었을 때 연쇄 서버 장애를 막아줌.

샤드마다 primary 1대 + Replica 2대와같은 식으로 고정 복제 세트를 두는 방식도 많이 쓰이긴하는데 다음의 치명적인 약점을 가진다.
- 메인 서버가 죽었을 때 누가 마스터 서버가 될지 선출하는 지연이 발생한다
- 서버가 망가졌을 때 새로운 서버를 투입하면 남아있는 서버와 1:1로 데이터를 복사해와야한다.
- 서버 증설시에 고정 백업 방식은 무조건 세트단위로 구매/증설 해야하는데 해시 링 방식은 그냥 링 위에 1대만 추가하면 알아서 분산되어 저장된다.

해시링 방식은 중앙 관리 서버가 필요 없다고 하는데 그럼 프라이머리 A에 붙은 레플리카 A-1, A-2가 정해저있는 고정 복제 방식도 필요 없는 거 아닌가?
-> 반드시 필요함.
복제본 위치는 고정되있어도 상태 변화를 관리할 중앙 장부가 반드시 필요하다.

다시 돌아와서 노드를 선택할 때 같은 물리 서버를 중복으로 선택하지 않도록 관리가 필요하다. 또한 데이터 사본은 다른 센터의 서버에 보관하는 게 안정성을 보장하기 좋다. 

### 데이터 일관성
여러 노드에 다중화된 데이터는 적절히 동기화가 되어야한다.

분산 키-값 저장소에서 쓰기 데이터를 복제/전파하는 방법은 **누가 주도해서 보내는가(방식)** 과 **언제 응답을 줄 것인가** 두 가지 영역으로 나뉜다.

1. 누가 전파하는가?
- 코디네이터 노드 방식
    - 클라이언트가 보낸 요청을 처음 받는 노드가 코디네이터 역할을 맡아 자기 로컬에 먼저 저장한 뒤, 해시 링 상의 다음 복제 대상 노드에게 쓰기 요청을 직접 네트워크로 쏜다.
- 리더-팔로워 방식
    - 오직 쓰기만 전담하는 리더와 읽기만 전담하는 팔로워로 나뉜다. 리더가 쓰기를 수행하면서 생성된 변경 로그를 백그라운드 스트림으로 리더에게 전송하여 동기화한다.
- 가십 프로토콜
    - 쓰기 요청을 받은 노드가 모든 노드에 즉시 전파하는 대신, 주기적으로 무작위 이웃 노드 몇 개에 자신의 변경사항을 전파하고, 이웃 노드들 역시 주기적으로 무작위 이웃들에게 같은 행동을 반복하는 방식. -> 최종 결과물이 전파되는 데 시간이 걸리지만 코디네이터 노드에 과부하가 걸리지 않는다.

2. 언제 완료되었다고 클라이언트에게 응답할 것인가?
- 동기식
    - 일관성이 완벽하지만 레플리카 중 하나라도 네트워크 지연/장애가 나면 쓰기 전체가 멈춤(가용성 저하)
- 비동기식
    - 가용성이 극대화되지만 레플리카에게 복제되기 전에 주 노드가 죽어버리면 데이터가 유실될 수 있음
- 정족수 합의
    - 과반수만 저장에 성공하면 성공 응답. C와 A 사이의 밸런스 조절이 가능

#### 정족수 합의 프로토콜이란

N: 사본 개수
W: 쓰기 정족수(Write Quorum), 쓰기 성공으로 인정할 노드 수
R: 읽기 정족수(Read Quorum) , 읽기 성공으로 인정할 노드 수

W, R, N의 값을 정하는 것은 응답 지연과 데이터 일관성 사이의 타엽점을 찾는 과정이다.

R=1, W=N: 빠른 읽기 연산에 최적화된 시스템
R=N, W=1: 빠른 쓰기 연산에 최적화된 시스템
W+R > N: 강한 일관성이 보장됨. 적어도 한 개의 노드는 겹치게 되므로 최신 데이터를 읽을 수 있음
W+R <= N: 강한 일관성이 보장되지 않음

**Q. R=N, W=1이라면 낡은 데이터의 응답도 일단 오기만 하면 된다는 것인가?**
-> N개 노드의 응답을 전부 모아서 가장 최신 데이터를 골라내기 위해 다 받는 것임(강한 일관성). 추가로 중재자가 낡은 데이터를 가진 노드에게 최신 데이터를 덮어씌워주는 읽기 복구(Read Repair)가 일어남.

#### 일관성 모델

- 강한 일관성: 모든 읽기 연산은 가장 최근에 갱신된 결과를 반환한다. 클라이언트는 절대로 낡은 데이터를 보지 못한다.
    - 일반적인 방법으로 모든 사본에 현재 쓰기 연산의 결과가 반영될 때까지 해당 데이터에 대한 읽기/쓰기를 금지한다.
    - 고가용성 시스템에는 적합하지 않음.
**Q. 데이터에 락을 잡아두는 게 다중화된 서버에서 너무 비용이 크지 않을까? 어떻게 구현되는 건가?**
-> 
2단계 커밋이나 Paxos / Raft같은 복잡한 분산 프로토콜을 사용한다.
1단계로 락 체결을 시키고 2단계로 커밋하고 락을 해제하는 방식이다.
다음의 치명적인 문제를 가지는데
1. 지연 시간의 폭증
2. 가용성이 너무 저하됨
그래서 최종 일관성을 많이 사용함.

- 약한 일관성: 읽기 연산은 가장 최근에 갱신된 결과를 반환하지 못할 수 있다.
- 결과적 일관성: 약한 일관성의 한 형태로, 갱신 결과가 결국에는 모든 사본에 반영되는 모델이다.
    - 쓰기 연산이 병렬적으로 발생하면 시스템에 저장된 값의 일관성이 꺠질 수 있는데 이 문제는 클라이언트 레벨에서 버전관리를 통해 해결할 수 있음.

**Q. 결과적 일관성은 어떻게 실현되는 걸까?**
-> 시스템 백그라운드에서 끊임없이 데이터를 일치시켜주는 4가지 동기화 기법이 맞물려 돌아가며 실현됨.
1. 비동기 복제 - 기본
2. 읽기 복구(Read Repair)
    - 정족성 합의 프로토콜 과정에서 비교
3. 단서 달린 위임(Hinted Handoff) - 임시 장애 상황
4. 안티-엔트로피와 머클 트리
    - 만약에 데이터가 동기화 과정에 네트워크 장애가 생겼고, 서버가 다운된 게 아니라 멀쩡이 살아있어 단서 달린 위임 상황을 사용할 상황도 발생하지 않았으며, 노드를 오래 조회하지 않아 읽기 복구도 일어나지 않았을 때 이 방법이 정기적으로 정합성을 유지한다.


### 비 일관성 해소 기법: 데이터 버저닝
데이터를 다중화하면 가용성은 높아지지만 사본 간 일관성이 깨질 가능성은 높아짐.
**버저닝(versioning)** 과 **벡터 시계(vector cloeck)**은 그 문제를 해소하기 위해 등장한 기술이다.

버저닝은 데이터를 변경할 때마다 해당 데이터의 새로운 버전을 만드는 것을 의미한다. 따라서 각 버전의 데이터는 변경 불가능하다.
쓰기 연산이 동시에 서로 다른 노드에서 발생하면 마지막 두 버전 사이의 충돌은 해소하기 어렵다. 이 문제를 해결하려면, 충돌을 발견하고 자동으로 해결해 낼 버저닝 시스템이 필요한데 이 때 보편적으로 사용되는 기술이 벡터 시계이다.

벡터 시계는 [서버, 버전]의 순서쌍을 데이터에 매단 것이다. <- 다른 속성으로 들어가는 게 아니라 그냥 밸류에 데이터셋이 들어가는 것이다
데이터를 서버에 기록하면 시스템은 다음 작업을 수행해야 한다.
- [서버, 버전]이 있댜면 버전을 증가시킨다.
- 없다면 [서버, 1]을 만든다.

벡터 시계를 사용하면 어떤 버전 X가 버전 Y의 이전 버전인지(충돌이 없는지) 쉽게 판단 가능함. Y의 모든 구성요소 값이 X의 요소값보다 같거나 크면 됨. 예로 D([s0, 1], [s1, 1]) 은 D([s0, 1], [s1, 2])보다 이전 버전이다.
어떤 버전 X와 Y사이에 충돌이 있는지 보려면(두 버전이 같은 이전 버전에서 파생된 다른 버전인지 보려면) Y의 벡터 시계 구성요소 가운데 X의 벡터 시계 동일 서버 구성요소보다 작은 값을 가지는 것이 있는지 보면 됨. -> 간단하게 서로가 서로보다 큰 숫자를 하나씩 쥐고있는 상황임.

벡터 시계를 사용해 충돌을 감지하고 해소는 방법에는 **두 가지 분명한 단점**이 있음
- 충돌 감지 및 해소 로직이 클라이언트에 들어가야 하므로 구현이 복잡해진다.
- [서버: 버전] 순서쌍의 개수가 굉장히 빨리 늘어난다. 오래된 순서쌍을 벡터 시계에서 제거하도록 하면 버전 간 선후 관계가 정확하게 결정될 수 없기 때문에 해소 과정의 효율성이 낮아질 수 있다. 다만 실제 서비스에서 그런 문제가 벌어지는 것을 발견한 적이 없다는 문헌이 있다. 

**Q. 클라이언트는 어떻게 충돌을 해소하는가?**
-> 
1. 비즈니스 로직에 맞춰 합치기
2. 마지막 쓰기 승리
3. 사용자에게 직접 질의

### 장애 처리

#### 장애 감지
분산 시스템에서는 보통 두 대 이상의 서버가 똑같이 장애를 보고해야 해당 서버에 실제로 장애가 발생했다고 간주하게 된다.
모든 노드 사이에 멀티캐스팅 채널을 구축하는 것이 서버 장애를 감지하는 가장 쉬운 방법이지만 서비스가 많을 때는 비효율적이다.
<- O(N^2)의 메시지를 보내야 하기 때문에

- 유니캐스트 : 특정 1 노드에게만 메시지 전송
- 브로드캐스트 : 네트워크에 연결된 모든 노드에 메시지를 전송(웹, 캐시 등 네트워크 망에 연결된 모든 곳에 전달)
- 멀티캐스트 : 네트워크에 연결된 노드 중 특정 노드 그룹(DB)에 메시지를 전송

가십 프로토콜 같은 분산형 장애 감지 솔루션을 채택하는 게 효율적이다.

가십 프로토콜의 동작 원리는 다음과 같다.
- 각 노드는 멤버십 목록을 유지한다. 멤버십 목록은 각 멤버 ID와 박동 카운터 쌍의 목록이다.
- 각 노드는 주기적으로 자신의 박동 카운터를 증가시킨다.
- 각 노드는 임의의 다른 노드를 선택해 주기적으로 자신의 박동 카운터 목록을 전달한다.
- 수신한 노드는 자신의 멤버십 목록과 비교해 최신 값으로 갱신한다.
- 어떤 멤버의 박동 카운터 값이 지정된 시간 동안 갱신되지 않으면 해당 멤버는 장애 상태로 간주한다.

#### 일시적 장애 처리
가십 프로토콜로 장애를 감지한 시스템은 가용성을 보장하기 위해 필요한 조치를 해야함.
엄격한 정족수 접근법을 쓴다면 읽기와 쓰기 연산을 금지해야 할 것이다.
- 해당 데이터를 담당하기로 정해진 진짜 원본 노드들 사이에서만 정족수를 채워야 한다고 고집하는 방식이다.
- N=3, W=2일 때 서버 2대가 죽으면 W=2를 충족할 수 없기 때문에 더 이상의 읽기/쓰기 연산을 허용하지 않게 됨.

느슨한 정족수 접근법은 이 조건을 완화해 가용성을 높임. 정족수 요구사항을 강제하는 대신, 쓰기 연산을 수행할 W개의 건강한 서버와 읽기 연산을 수행할 R개의 건강한 서버를 해시 링에서 고름.
장애 상태인 서버로 가는 요청은 다른 서버가 임시로 맡아 처리하고 그동한 변경사항은 해당 서버가 복구되었을 때 일괄 반영해 데이터 일관성을 보존함. 
임시로 쓰기 연산을 한 서버에는 그에 관한 단서(hint)를 남겨두는 데 이런 장애 처리 방안을 **단서 후 임시위탁(hinted handoff)기법**이라 부른다.
- 별도의 임시 디렉터리나 테이블에 메타데이터 형태로 기록함

**Q. 임시 처리한 노드는 정상화된 노드에 데이터를 넘긴 뒤 그 데이터를 지우는가?**
-> 넵

#### 영구 장애 처리
**반-엔트로피 프로토콜** 구현을 통해 사본들을 동기화해 노드의 영구 장애 상황을 처리한다.

반 엔트로피 프토토콜은 사본들을 비교하여 최신 버전으로 갱신하는 과정을 포함한다. 
사본 간의 일관성이 망가진 상태를 탐지하고 전송 데이터 양을 줄이기 위해 **머클 트리**를 사용한다.

**Q. 영구 장애 상황이라는 게 한 노드가 복구 불가능하게 죽은 상태를 말하는 것이 맞는가?**
-> 물리적으로 하드가 타버렸거나, 메인보드가 고장났거나, ec2서버가 삭제되는 등 복구 불가능 한 상태를 말한다.
    **Q. hinted handoff 방식이 사용 불가능하다는데 결국에 죽은 서버로 들어오는 요청을 정상 서버가 처리하긴 해야하지 않나?**
    -> 당연히 처리해야한다. 실제 영구 장애 처리 타임라인은 다음과 같다.
    ```text
    timeline
        서버 A 영구 장애 발생 시 시스템의 대처
        1. 사건 발생 (0초) : 서버 A 하드디스크 폭발 (사망)
        2. 직후 (0초 ~ 1시간) : 일시 장애로 생각하고 다른 노드가 임시 대리 처리 (Hinted Handoff) + 다른 복제본(B, C)이 요청 소화
        3. 판정 (1시간 경과) : 영구 장애 확정.
        4. 영구 복구 : 새 서버 A-New 투입 -> 머클 트리로 데이터 복사 -> 임시 데이터 인계
    ```

**Q. 근데 어찌됐든 새 서버에는 데이터가 존재하지 않을 텐데 기존 서버의 데이터를 복사하는 동안 정족수 계산을 위해서는 임시 노드가 들어오는 데이터를 모두 저장해야 하는 것 아닌가? 이 상황에서 임시 노드가 죽으면 영구 장애 처리 자체가 불가능해지는 것 아닌가?**
-> 임시 노드가 죽더라도 영구 장애 처리가 불가능해지지 않고 데이터는 안전하게 복구된다. 그 이유는 임시 노드가 들고 있는 데이터가 유일한 원본이 아니기 때문이다. (중재자에게 쓰기 요청이 들어온 거고 다른 정상 노드에 데이터가 동기화되고 있기 때문)

**Q. 새 서버는 가진 데이터가 없는데 초기에는 연관 노드의 데이터를 통채로 복제해야 하는 거 아닌가? 머클트리가 사용되는 때를 잘 모르겠음.**
-> 데이터가 아예 0개인 새 서버는 기존 서버의 데이터파일을 통채로 스트리밍 하는 게 훨씬 빠름. 장시간 꺼져 있다가 돌아온 서버의 경우나, 살아있는 정상 복제본 간의 정기적인 데이터 동기화 때에 사용함!!

머클트리란?
전형적인 이진 트리 구조인 것 같음.

전체 키 공간을 4개의 버킷으로 나눴다면

```text
                     ┌──────────┐
                     │ 루트 노드 │ (Root Hash)
                     └──────────┘
                      /        \
                ┌──────┐      ┌──────┐
                │ 부모 │      │ 부모 │
                └──────┘      └──────┘
                 /    \        /    \
               [L1]   [L2]   [L3]   [L4]  <── 리프 노드 (버킷 대표 해시)
                │      │      │      │
────────────────┼──────┼──────┼──────┼────────────────────────
 [실제 데이터]
              버킷 1  버킷 2  버킷 3  버킷 4
             (100만개)(80만개)(120만개)(90만개)
```

머클트리는 Down->Up 으로 전개

1. 리프 노드들은 각자 담당하는 데이터 버킷들의 키 해시를 사용해 계산한 hash값을 가짐.
2. 그 상위의 부모 노드들은 자식 노드들의 hash값을 사용해 계산한 hash값을 가짐.
3. 루트 노드는 모든 리프 노드의 hash값을 사용해 계산한 hash값을 가짐.

사본들의 동기화 원리
루트 노드의 해시값을 비교하는 것으로 시작해 자식 노드로 타고 나가면서 비교한다.
결국 이진 트리니까 비교에 O(logN) (= height이므로)번의 비교만으로 일치하는 버킷을 찾을 수 있는 것.

한 데이터 센터에 db를 두지말고 여러 데이터센터에 물리적으로 분산하는 게 낫다.

### 시스템 아키텍처 다이어그램

### 쓰기 경로
1. 쓰기 요청이 커밋 로그 파일에 기록된다.
    - 로그 파일은 서버 전원이 갑자기 꺼졌을 때 메모리에 있던 데이터를 복구하기 위한 보험이다.
    - 로그 파일은 순차 쓰기이므로 속도가 빠름
    - SStable로 안전하게 데이터를 옮겨 적고 나면 과거의 커밋 로그는 지워진다.
**Q. 근데 커밋 로그가 그렇게 빠르면 그냥 SStable 대신 쓰면 되는 거 아님??**
-> 정렬되지 않아서 read가 지옥이 된다.
2. 데이터가 메모리 캐시에 기록된다.
3. 메모리 캐시가 가득차거나 정의된 임계치에 도달한다면 디스크에 있는 SSTable에 기록된다.

### 읽기 경로
메모리 캐시에 있는 경우 그대로 반환

메모리 캐시에 없는 경우 어느 SSTable에 찾는 키가 있는지 알아낼 방법이 필요함 -> **블룸 필터**
- 각 SSTable 입구에 메모리로 된 가벼운 문지기 같은 개념임
- 0과 1로 된 작은 비트 배열만 사용하고 키당 여러 개의 해시 함수를 사용(해시 충돌을 줄이기 위해)해 해당 비트를 1로 바꿈
- 데이터가 없다는 건 100% 확실한데 해시 충돌로 없는데 있다고 할 수는 있음(적은 확률)

1. 메모리 캐시 검사. 없으면 블룸 필터로
2. 블룸 필터 검사를 통해 어느 SSTable에 키가 보관되어있는지 알아냄
3. SSTable에서 데이터를 가져와 반환
