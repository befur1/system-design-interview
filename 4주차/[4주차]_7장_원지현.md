# [4주차] 7장 정리 - 원지현
# 7장_ 분산 ID 생성기

## 분산 환경에서 auto_increment의 한계
- 데이터베이스가 여러 대인 분산 환경에서는 단일 DB에서 사용하던 auto_increment를 사용할 수 없음.
- 서버마다 식별자를 독립적으로 생성하면 아이디가 충돌(유일성 파괴)하며, 하나의 중앙 DB에 몰아주면 단일 장애점(SPOF)과 병목 현상이 발생함.

## 4가지 분산 ID 생성 기법 비교
- 다중 마스터 복제: DB 서버 수만큼 k씩 더해가며 ID를 생성함. 확장성이 떨어지고 시간순 정렬이 불가능함.
- UUID: 128비트 크기로 서버 간 조율 없이 독립적으로 생성 가능하나, 용량이 너무 크고 숫자 외의 문자가 포함되며 시간순 정렬이 안 됨.
- 티켓 서버: 중앙 집중형 DB 1대로 번호를 발급함. 구현이 쉽고 시간순 정렬이 되지만, 이 서버가 다운되면 전체 시스템이 멈추는 SPOF 문제가 발생함.
- 트위터 스노플레이크(Snowflake): 64비트 숫자를 조합하여 중앙 서버 없이도 유일하고 시간순 정렬이 가능한 ID를 생성함.

## 트위터 스노플레이크 구조 (총 64비트)
- 부호 비트 (1비트): 양수임을 보장하기 위해 항상 0으로 고정함.
- 타임스탬프 (41비트): 밀리초(ms) 단위의 시간을 기록하여 아이디만으로 완벽한 시간순 정렬을 보장함. 기원 시각(epoch)을 커스텀하면 약 69년간 사용 가능함.
- 데이터센터 및 서버 ID (10비트): 분산된 서버들을 구분하여 동시에 요청이 들어와도 물리적으로 아이디가 겹치지 않게 방어함 (최대 1,024대).
- 일련번호 (12비트): 같은 서버, 같은 1밀리초 내에 여러 요청이 들어올 경우 1씩 증가시켜 순서를 매김. 1밀리초당 최대 4,096개 생성 가능.

## 적용 가능 사례 2. 무한 스크롤 페이징 성능 최적화
- 대화 분석 서비스의 특성상 과거 채팅 내역이나 분석 리포트를 위로 계속 올려보는 '무한 스크롤(커서 페이징)' 기능이 필수적이다. 초기 단계인 지금은 데이터가 적어서 생성 시간(created_at) 컬럼으로 커서를 잡아도 문제없지만, 서비스가 확장되어 채팅 데이터가 억 단위로 쌓이게 되면 기존 페이징 방식으로는 DB 조회 성능이 크게 떨어진다. 
- 이런 한계점이 올 때 메시지 엔티티의 기본키(@Id)를 스노플레이크 알고리즘을 차용한 64비트 정수로 교체하면 문제를 해결할 수 있다. 굳이 별도의 발급 서버를 둘 필요 없이, Spring Boot 서버 내부에 스노플레이크 유틸리티 클래스를 만들어 엔티티가 저장될 때 고유 ID가 부여되게끔 구현하는 것이다. 이렇게 하면 아이디 자체가 시간순 정렬을 완벽하게 보장하므로, 복잡한 시간 정렬 없이 기본키 인덱스만 타고도 대규모 데이터를 엄청나게 빠른 속도로 조회할 수 있다.
