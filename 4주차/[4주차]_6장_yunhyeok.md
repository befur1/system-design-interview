# 키-값 저장소 설계 (Key-Value Store)

## 🧭 한눈에 보는 연결 흐름

> 모든 주제는 "앞 단계의 해결책이 새로운 문제를 만든다"는 흐름으로 이어진다.

1. 단일 서버 → 메모리 용량 한계, 휘발성 때문에 데이터를 여러 서버에 나눠야 한다.
2. 분산 → 서버가 여러 대면 네트워크 장애(파티션)는 피할 수 없다. 그러면 일관성과 가용성 중 무엇을 포기할지 정해야 한다. → CAP 정리
3. 데이터 파티션 → 여러 서버에 "어떤 키를 어디에 둘지" 정해야 한다. → 안정 해시
4. 데이터 다중화 → 나눠 놓은 데이터는 서버 하나가 죽으면 사라진다. → 해시 링을 그대로 이용해 사본을 N개 둔다.
5. 데이터 일관성 → 사본이 여러 개면 사본끼리 값이 달라질 수 있다. → 정족수(N, W, R)로 일관성과 속도를 조절한다. (CAP에서 C와 A 사이를 조절하는 다이얼)
6. 데이터 버저닝 → 가용성을 택하면(결과적 일관성) 동시 쓰기 충돌이 생긴다. → 벡터 시계로 충돌을 감지하고 해결한다.
7. 장애 감지 → 사본을 유지하려면 어떤 서버가 죽었는지 알아야 한다. → 가십 프로토콜
8. 장애 처리 → 죽은 서버 대신 누가 일할지 정한다(일시적 장애). 복구된 서버의 사본은 어긋나 있으므로 효율적으로 맞춘다(영구 장애). → 머클 트리

| 해결하려는 문제 | 사용하는 기술 |
|---|---|
| 대규모 데이터 저장, 점진적 확장 | 안정 해시로 데이터 파티션 |
| 서버 장애 시에도 데이터 보존, 읽기 가용성 | 데이터 다중화 |
| 일관성과 속도의 균형 조절 | 정족수 합의 (N, W, R) |
| 동시 쓰기 충돌 해결 | 데이터 버저닝, 벡터 시계 |
| 장애 노드 감지 | 가십 프로토콜 |
| 일시적 장애 처리 | 느슨한 정족수, 단서 후 임시 위탁 |
| 영구 장애 후 사본 동기화 | 반 엔트로피 프로토콜, 머클 트리 |

## 1. 키-값 저장소란?

- 키-값 데이터베이스라고도 불리는 비관계형 데이터베이스
- 고유한 키(key)에 값(value)을 짝지어 저장한다.

## 2. 단일 서버 키-값 저장소

- 서버 한 대만 쓰는 키-값 저장소는 쉽다. 키-값 쌍 전부를 메모리에 해시 테이블로 저장하면 된다.
- 해시 테이블: 키를 해시 함수에 넣어 배열의 인덱스(주소)로 바꾼 뒤, 그 위치에 값을 저장하는 자료구조
- 장점: 매우 빠르다.
- 한계
    1. 휘발성: 서버가 꺼지면 메모리 데이터가 사라진다.
    2. 메모리 용량 한계: 모든 데이터를 메모리에 둘 수 없다.
- 개선책: 데이터 압축, 자주 쓰는 데이터만 메모리에 두고 나머지는 디스크에 저장
- 그래도 서버 한 대로는 한계가 있다. → 분산 키-값 저장소가 필요하다.

## 3. CAP 정리

> 데이터 일관성(C), 가용성(A), 파티션 감내(P)를 동시에 모두 만족하는 분산 시스템은 없다.

- 일관성 (Consistency): 어떤 노드에 접속하든 모든 클라이언트는 언제나 같은 데이터를 본다.
- 가용성 (Availability): 일부 노드에 장애가 나도 클라이언트는 항상 응답을 받는다.
- 파티션 감내 (Partition tolerance): 노드 사이 통신이 끊겨도 시스템은 계속 동작한다.

### 시스템 분류
- CP 시스템: 일관성 + 파티션 감내 → 가용성 희생
- AP 시스템: 가용성 + 파티션 감내 → 일관성 희생
- CA 시스템: 네트워크 장애는 피할 수 없으므로 분산 시스템은 파티션 감내를 반드시 지원해야 한다. 따라서 실세계에 CA 시스템은 존재하지 않는다.

### 예시: 노드 N1, N2, N3 중 N3가 고장나면?
- CP 선택 (일관성 우선): N1, N2의 쓰기 연산을 중단해 데이터 불일치를 막는다. 대신 그동안 가용성이 떨어진다.
    - 예: 은행 시스템. 잔고가 노드마다 다르게 보이면 절대 안 된다.
- AP 선택 (가용성 우선): N1, N2는 낡은 데이터라도 읽기를 허용하고, 쓰기도 계속 받는다. N3가 복구되면 새 데이터를 N3에 동기화한다.

→ 키-값 저장소를 설계할 때는 요구사항에 맞춰 CAP 정리를 적용해야 한다.

## 4. 분산 키-값 저장소의 핵심 컴포넌트

### 4-1. 데이터 파티션
- 대규모 데이터를 서버 한 대에 넣는 건 불가능하므로 작은 파티션으로 나눠 여러 서버에 저장한다.
- 고려할 점
    - 데이터를 여러 서버에 고르게 분산해야 한다.
    - 노드가 추가·삭제될 때 데이터 이동을 최소화해야 한다.
- → 안정 해시로 해결한다. (앞 장에서 배운 해시 링 + 가상 노드)
    - 규모 확장 자동화: 서버 추가·삭제에 따라 자동으로 확장된다.
    - 다양성: 성능 좋은 서버에 가상 노드를 더 많이 배정할 수 있다.

### 4-2. 데이터 다중화 (Replication)
- 높은 가용성과 안정성을 위해 데이터를 N개 서버에 비동기적으로 복제한다.
- 방법: 키를 해시 링에 배치한 뒤, 그 지점에서 시계 방향으로 돌며 처음 만나는 N개 서버에 사본을 저장한다.
- ⚠️ 가상 노드 문제: 가상 노드를 쓰면 처음 만나는 N개 노드의 실제 물리 서버 수가 N보다 적을 수 있다.
    - 예: 링 순서가 A_1 → B_1 → A_2 → C_1이고 N = 3일 때, 그냥 고르면 A_1, B_1, A_2 → 물리 서버는 A, B 두 대뿐
    - 해결: 노드를 고를 때 이미 선택한 물리 서버는 건너뛴다. → A_1, B_1, (A_2 건너뜀), C_1 → 물리 서버 A, B, C
- 같은 데이터센터 전체가 정전·지진 등으로 한꺼번에 죽을 수 있으므로, 사본은 다른 데이터센터에도 보관하는 것이 좋다.

### 4-3. 데이터 일관성
여러 노드에 복제된 데이터는 적절히 동기화되어야 한다. → 정족수 합의 (Quorum Consensus)

- N = 사본 개수
- W = 쓰기 정족수. 쓰기가 성공했다고 보려면 최소 W개 서버에서 쓰기 성공 응답을 받아야 한다.
- R = 읽기 정족수. 읽기가 성공했다고 보려면 최소 R개 서버에서 응답을 받아야 한다.
- 중재자(coordinator)가 클라이언트와 노드 사이에서 프록시 역할을 한다.

W, R 값의 의미
- W = 1 또는 R = 1: 서버 한 대 응답만 기다리면 되므로 빠르다.
- W 또는 R이 1보다 크면: 일관성은 올라가지만, 여러 서버의 응답(그중 느린 서버 포함)을 기다려야 하므로 느려진다.
- W + R > N: 읽기 서버와 쓰기 서버가 최소 1대 겹치므로 강한 일관성 보장

| 설정 | 특징 |
|---|---|
| R = 1, W = N | 빠른 읽기에 최적화 |
| W = 1, R = N | 빠른 쓰기에 최적화 |
| W + R > N | 강한 일관성 보장 (보통 N = 3, W = R = 2) |
| W + R ≤ N | 강한 일관성 보장 안 됨 |

일관성 모델
- 강한 일관성: 모든 읽기는 가장 최근에 갱신된 결과를 반환한다.
- 약한 일관성: 읽기가 가장 최근 결과를 반환하지 못할 수도 있다.
- 결과적 일관성: 약한 일관성의 한 형태. 갱신 결과가 시간이 지나면 결국 모든 사본에 반영된다.
    - Dynamo, Cassandra가 채택한 방식
    - 쓰기를 병렬로 받다 보니 사본 간 불일치(충돌)가 생길 수 있다. → 버저닝으로 해결

### 4-4. 비일관성 해소: 데이터 버저닝과 벡터 시계
- 버저닝: 데이터를 변경할 때마다 새 버전을 만든다. 각 버전은 변경 불가능(immutable)하다.
- 벡터 시계: `[서버, 버전]` 쌍을 데이터에 붙여, 어떤 버전이 먼저인지 또는 서로 충돌하는지 판단한다.

예시: 키 `greeting`을 N1, N2가 복제 중

① 초기 상태
- 데이터: `"hello"`
- 벡터 시계: `[N1: 1, N2: 1]`

② 동시 쓰기 발생
- 클라이언트 A → N1에 `"not hello"`로 수정 요청
    - N1이 자기 카운터를 1 증가 → `[N1: 2, N2: 1]`
- 클라이언트 B → N2에 `"world"`로 수정 요청
    - N2가 자기 카운터를 1 증가 → `[N1: 1, N2: 2]`

③ 충돌 감지 (벡터 시계 비교)
- 비교 규칙
    - 한쪽의 모든 항목이 다른 쪽보다 크거나 같다 → 선후 관계가 명확함 → 최신 쪽으로 덮어쓰기 가능
    - 어떤 항목은 A가 크고 어떤 항목은 B가 크다 → 동시 변경 = 충돌
- `[N1: 2, N2: 1]` vs `[N1: 1, N2: 2]`
    - N1 항목은 앞쪽이 크고(2 > 1), N2 항목은 뒤쪽이 크다(2 > 1).
    - → 어느 쪽도 최신이라 단정할 수 없으므로 충돌

④ 충돌 해결
1. 시스템은 데이터를 임의로 지우지 않고 두 버전을 모두 형제(sibling)로 보존한다.
2. 클라이언트가 `GET greeting`을 하면 두 값을 벡터 시계와 함께 모두 반환한다.
    - `"not hello"` `[N1: 2, N2: 1]`
    - `"world"` `[N1: 1, N2: 2]`
3. 클라이언트(애플리케이션)가 비즈니스 규칙에 따라 병합한다.
    - 예: 문자열 결합 → `"not hello / world"`
4. 병합 결과를 다시 저장한다. 벡터 시계는 두 시계의 항목별 최댓값을 합친다.
    - 최종 데이터: `"not hello / world"`
    - 새 벡터 시계: `[N1: 2, N2: 2]`
    - 저장을 처리한 서버가 자기 카운터를 1 더 올린다(예: N1이 처리하면 `[N1: 3, N2: 2]`).

→ 이후 읽기부터는 병합된 값 하나만 반환된다.

벡터 시계의 단점
- 충돌 해결 로직이 클라이언트에 들어가야 해서 구현이 복잡해진다.
- `[서버, 버전]` 쌍이 계속 늘어난다. → 임계치를 넘으면 오래된 쌍을 제거한다. (정확도는 조금 떨어지지만 실무에서 큰 문제는 없었음)

## 5. 장애 처리

### 5-1. 장애 감지: 가십 프로토콜
- 서버 한 대가 "A가 죽었다"고 해서 바로 장애로 판단하지 않는다. 보통 두 대 이상이 같은 보고를 해야 장애로 간주한다.
- 모든 노드가 서로 상태를 확인(멀티캐스팅)하면 서버가 많을 때 비효율적이다. → 가십 프로토콜처럼 분산형 방식을 쓴다.

동작 방식
1. 각 노드는 멤버십 목록을 가진다. 목록에는 각 멤버의 ID와 박동 카운터(heartbeat counter)가 있다.
2. 각 노드는 자기 박동 카운터를 주기적으로 증가시킨다.
3. 각 노드는 무작위로 고른 노드들에게 주기적으로 자기 박동 카운터 목록을 보낸다.
4. 목록을 받은 노드는 멤버십 목록을 최신 값으로 갱신한다.
5. 어떤 멤버의 박동 카운터가 지정된 시간 동안 증가하지 않으면 → 그 멤버를 장애 노드로 간주한다. 이 정보가 가십을 통해 퍼져 결국 모든 노드가 알게 된다.

### 5-2. 일시적 장애 처리
- 느슨한 정족수 (sloppy quorum): 정족수를 엄격하게 강제하지 않고, 해시 링에서 장애가 없는 서버 W개(쓰기), R개(읽기)를 골라 처리한다.
- 단서 후 임시 위탁 (hinted handoff): 장애 서버로 갈 요청을 다른 서버가 잠시 대신 처리하고, 그 변경 내역을 단서(hint)로 남긴다. 장애 서버가 복구되면 변경분을 일괄 인계한다.

### 5-3. 영구 장애 처리: 반 엔트로피 프로토콜과 머클 트리
- 반 엔트로피 프로토콜: 사본들을 비교해 최신 버전으로 갱신하는 과정
- 사본 간 차이를 효율적으로 찾고 전송 데이터를 줄이기 위해 머클 트리(해시 트리)를 쓴다.

머클 트리 구조
1. 키 공간을 버킷(블록) 단위로 나눈다.
2. 버킷 안의 각 키를 해시하고, 버킷별 해시값을 리프 노드에 둔다.
3. 위로 올라가며 두 자식 노드의 해시를 합쳐 다시 해시해서 부모 노드를 만든다. → 최종적으로 루트 해시 하나가 남는다.

비교 방식
- 두 서버의 루트 해시가 같으면 → 그 아래 데이터가 몇 개든 전부 일치한다.
- 루트 해시가 다르면 → 자식 노드를 비교하며 해시가 다른 가지(branch)만 골라 내려간다.

### ❓ 왜 동기화할 데이터 양이 "데이터 총량"이 아니라 "실제 차이의 크기"에 비례할까?

① 루트 해시 하나로 전체 일치 여부를 즉시 확인: O(1)
- 데이터가 완전히 같다면 루트 해시 한 번만 비교하면 끝난다.
- 루트가 같으면 하위의 수억 개 데이터가 모두 같다는 뜻이므로 바로 동기화를 종료한다.

② 차이가 있는 가지만 골라서 내려감: O(log N)
- 루트 R이 다름 → 왼쪽 자식 L과 오른쪽 자식을 비교
- L은 같고 오른쪽만 다르면 → L 아래 수백만 개 데이터는 검사도 하지 않고 건너뛴다.
- 해시가 다른 쪽으로만 내려가며 같은 비교를 반복한다.
- 이진 탐색과 비슷하게 진행되므로 탐색 깊이는 데이터 총량 N이 아니라 트리 높이 O(log N)이다.

③ 결국 실제로 바뀐 블록만 전송한다
- 예: 전체 데이터 100억 개 중 1개만 바뀐 경우
    1. 루트 비교 → 다름 확인
    2. 트리 높이(약 30단계)를 따라 달라진 가지로만 내려감 (비교 약 30 × 2회)
    3. 달라진 블록 1개만 전송해 동기화 완료

정리
- 같은 대량의 데이터 영역은 상위 노드 해시 비교 한 번으로 통째로 건너뛴다.
- 탐색할 노드 수 ≈ 차이가 난 지점 수 × 트리 높이(log N)
- 실제 전송 데이터 양 = 실제로 바뀐 부분의 크기
