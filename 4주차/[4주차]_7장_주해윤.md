## 7장 분산 시스템을 위한 유일 ID 생성기 설계

---

### 1) 문제 이해 및 설계 범위 확정

- ID는 유일해야 함
- ID는 숫자로만 구성되어야 함
- ID는 64비트로 표현될 수 있는 값이어야 함
- ID는 발급 날짜에 따라 정렬 가능해야 함
- 초당 10000개의 ID를 만들 수 있어야 함

### 2) 개략적 설계안 제시 및 동의 구하기

**다중 마스터 복제**

- 데이터베이스의 `auto_increment` 기능 활용
    - 값을 구할 때 1만큼 증가시켜 얻는 것이 아니라, 현재 사용 중인 데이터베이스 서버의 수 k만큼 증가 시킴
        
        → 규모 확장성 문제를 어느 정도 해결
        
    - 단점: 여러 데이터 센터에 걸쳐 규모를 늘리기 어려움, ID의 유일성은 보장되겠지만 그 값이 시간 흐름에 맞추어 커지도록 보장할 수 없음, 서버를 추가하거나 삭제할 때도 잘 동작하도록 만들기 어려움
- UUID: 컴퓨터 시스템에 저장되는 정보를 유일하게 식별하기 위한 128비트짜리 수
    - 서버 간 조율 없이 독립적으로 생성 가능
    - 장점: 만드는 것 단순, 규모 확장 쉬움
    - 단점: ID가 128비트로 긺, 시간순 정렬 불가능, 숫자 아닌 값이 포함될 수 있음
- 티켓 서버: 분산 기본 키를 만듦
    - `auto_increment` 기능을 갖춘 데이터베이스 서버를 중앙 집중형으로 하나만 사용함
    - 장점: 유일성이 보장되는 오직 숫자로 구성된 ID 쉽게 만들 수 있음, 구현이 쉽고 중소 규모 애플리케이션에 적합
    - 단점: 티켓 서버가 SPOF가 됨 → 이 서버에 장애 발생 시 해당 서버를 이용하는 모든 시스템이 영향을 받음
- **트위터 스노플레이크 접근법**
    - 각개 격파 전략 적용
        - 사인 비트: 1비트 할당
        - 타임스탬프: 41비트 할당, 기원 시각 이후로 몇 밀리초가 경과했는지를 나타냄
        - 데이터센터 ID: 5비트 할당, 32개 데이터센터 지원 가능
        - 서버 ID: 5비트 할당, 데이터센터 당 32개 서버 사용 가능
        - 일련번호: 12비트 할당, ID를 생성할 때마다 1씩 증가 시킴, 1밀리초 경과할 때마다 0으로 초기화

### 3) 상세 설계

**데이터센터 ID, 서버 ID**

- 시스템이 시작될 때 결정, 운영 중 바뀌지 않음

**타임스탬프**

- 시간이 흐름에 따라 더 큰 값을 갖게 되므로 시간 순으로 정렬 가능
- 최댓값: 대략 69년

**일련번호**

- 어떤 서버가 같은 밀리초 동안 하나 이상의 ID를 만들어 낸 경우에만 큰 값을 가지게 됨

### +) 논의할 사항 및 경험과 연결

**유일 ID랑 멱등성 키 무슨 차이?**

유일 ID: 생성한 데이터 한 건을 식별

멱등성 키: 같은 요청이 반복되었는지 식별

ex) 예매 요청

Idempotency-Key: 같은 논리적 요청에서는 동일

Reservation ID: 실제 생성된 예매 데이터를 식별
