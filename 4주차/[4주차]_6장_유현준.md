# [4주차] 6장 - 키-값 저장소 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

## 책 내용 뼈대

키-값 저장소를 만들려면 읽기/쓰기 성능, 데이터 크기, 일관성 수준 사이에서 타협해야 한다. 단일 서버는 메모리에 해시 테이블 하나로 끝나지만, 데이터가 많아지면 압축하고 자주 쓰는 것만 메모리에 두는 식으로 버티다가 결국 분산으로 간다.

### CAP 정리

데이터 일관성(Consistency), 가용성(Availability), 파티션 감내(Partition tolerance) 셋 중 둘만 만족할 수 있다는 정리. CP, AP, CA로 나눈다.

### 데이터 파티션

안정 해시로 데이터를 여러 서버에 나눈다. 5장에서 배운 게 여기서 그대로 쓰인다.

### 데이터 다중화

안정 해시 링에서 시계 방향으로 만나는 N개 서버에 사본을 저장한다. 가상 노드를 쓸 때는 같은 물리 서버가 겹칠 수 있으니 유일한 서버만 골라야 한다.

### 일관성과 정족수 합의

N은 사본 개수, W는 쓰기 연산이 성공하려면 응답받아야 하는 사본 수, R은 읽기 연산이 응답받아야 하는 사본 수다.

- W + R > N 이면 강한 일관성
- W = 1, R = 1 이면 빠르지만 일관성 보장 없음
- W = N, R = 1 이면 읽기가 빠름
- W = 1, R = N 이면 쓰기가 빠름

### 비일관성 해소 - 버저닝과 벡터 시계

[서버, 버전] 쌍으로 어느 버전이 어느 버전의 조상인지 판정한다. 아래 개인적인 질문에서 자세히 파봤다.

### 장애 처리

- 장애 감지: 가십 프로토콜로 멤버십 정보를 주고받으며 판정한다
- 일시적 장애: 임시 위탁(hinted handoff)으로 다른 서버가 대신 받아두고, 돌아오면 넘겨준다
- 영구 장애: 머클 트리로 사본 간 차이를 찾아 그 부분만 동기화한다
- 데이터센터 장애: 여러 데이터센터에 다중화한다

### 쓰기 경로와 읽기 경로

쓰기는 커밋 로그에 기록하고 메모리 캐시에 저장한 뒤, 차면 SSTable로 디스크에 쓴다. 읽기는 메모리를 먼저 보고, 없으면 블룸 필터로 어느 SSTable에 있을지 추린 다음 그 SSTable만 뒤진다.

# 개인적인 질문 - 벡터 시계

벡터 시계 예시(D1~D5, 서버 Sx/Sy/Sz)를 보다가 하나가 걸려서 따라가봤는데, 결국 "충돌을 누가 해결하는가"라는 더 큰 질문으로 이어졌다.

## 1. D5의 충돌 해소를 Sx가 아닌 다른 서버 Sa가 처리하면?

책의 예시는 D3([Sx,2],[Sy,1])과 D4([Sx,2],[Sz,1])가 충돌하고, Sx가 처리한 결과가 D5([Sx,3],[Sy,1],[Sz,1])였다. 그러면 Sa가 처리하면 D5([Sx,1],[Sy,1],[Sz,1],[Sa,1])이 되나 싶었는데 틀렸다.

정답은 D5([Sx,2],[Sy,1],[Sz,1],[Sa,1])이다. Sx가 1이 아니라 2다.

### 병합 규칙은 두 단계였다

1단계, 원소별 최대값을 취한다.

```
D3([Sx,2],[Sy,1])
D4([Sx,2],        [Sz,1])
─────────────────────────
   ([Sx,2],[Sy,1],[Sz,1])
```

2단계, 쓰기를 처리한 서버의 카운터만 올린다. Sx가 처리하면 [Sx,3]이 되고, Sa가 처리하면 Sa가 1로 새로 붙되 Sx는 쓰기를 안 했으니 2 그대로 남는다.

### Sx를 1로 낮추면 무슨 일이 생기나

벡터 시계가 하는 일은 조상 관계 판정이다. 모든 서버에 대해 X의 값이 Y보다 작거나 같으면 X는 Y의 조상이고, 하나라도 크고 하나라도 작으면 충돌이다.

내가 답한 D5([Sx,1],...)를 D2([Sx,2])와 비교하면

| | Sx | Sy | Sz | Sa |
| --- | --- | --- | --- | --- |
| D2 | 2 | 0 | 0 | 0 |
| D5 (내 답) | 1 | 1 | 1 | 1 |

D2가 Sx에서 크고 D5가 나머지에서 크니 충돌로 판정된다. 그런데 D5는 D2의 후손이다. 이미 해결한 충돌이 다시 충돌로 잡히는 셈이다.

정답 버전은 전부 작거나 같으므로 D2가 D5의 조상으로 올바르게 판정된다.

결국 최대값을 유지하는 게 벡터 시계의 핵심이었다. 카운터 숫자 자체에는 의미가 없고 "이 버전이 어디까지의 역사를 포함하는가"를 기록하는 게 목적이라서, 값을 낮추면 역사가 지워진다.

여기서 벡터 시계의 단점 하나가 바로 보인다. Sa가 들어오면서 쌍이 3개에서 4개로 늘었다. 여러 노드가 돌아가며 쓰기를 처리하면 벡터가 무한히 커진다. Dynamo는 임계치를 두고 넘으면 오래된 쌍부터 버리는데, 대신 조상 관계 판정이 부정확해지는 걸 감수한다.

## 2. 그러면 Sa가 충돌을 해결해주는 것인가

아니었다. 서버는 충돌을 해결하지 않는다.

| 주체 | 하는 일 |
| --- | --- |
| 저장소(서버) | 충돌을 감지만 한다. 충돌 버전을 둘 다 클라이언트에 돌려준다 |
| 클라이언트 | 둘을 보고 어떻게 합칠지 결정한다 |
| 쓰기를 받은 서버 | 합쳐진 결과를 저장하고 자기 카운터를 올린다 |

Sx가 D5에서 한 일은 충돌을 해결한 게 아니라 해결된 결과를 받아 저장한 것이다. Sa가 그 자리에 있어도 완전히 같은 역할이다.

### 왜 서버가 못 하는가

합치는 규칙을 서버가 알 수 없다. 한쪽에 [사과], 다른 쪽에 [바나나]가 있다면 무엇이 정답인가.

- 장바구니라면 합집합 [사과, 바나나]
- 마지막 수정이 이기는 규칙이면 타임스탬프 늦은 쪽
- 카운터라면 더하기
- 사용자 프로필이라면 사용자에게 물어봐야 할 수도

전부 애플리케이션 사정이다. 키-값 저장소는 값을 바이트 덩어리로 보니 판단할 근거가 없다. 그래서 던져주고 정하라고 하는 것이다.

이게 책이 꼽는 벡터 시계의 단점 첫 번째(클라이언트 구현 복잡도)에 해당한다.

참고로 어느 서버가 코디네이터가 되는지는 의미 있는 선택이 아니다. 안정 해시 링에서 그 키를 담당하는 노드 중 하나가 받는다. 벡터 시계는 "누가 합칠지 정했나"를 기록하지 않고 "누가 그 쓰기를 처리했나"만 기록한다.

# 더 생각해본 것 - 실무에서는 충돌을 어떻게 다루나

책은 벡터 시계를 비일관성 해소 기법으로 소개하고 단점 두 가지(클라이언트 구현 복잡도, 벡터 크기 증가)를 짚고 넘어간다. 그런데 그러면 실제로는 이걸 쓰는지가 궁금해서 더 알아봤다. 책에 없는 내용이라 따로 정리해둔다.

## 클라이언트가 받는 것

먼저 오해를 하나 풀었다. 충돌이 나면 버전 이름만 오는 게 아니라 값이 다 온다.

```
D3 = { 값: [사과],   시계: [Sx,2],[Sy,1] }
D4 = { 값: [바나나], 시계: [Sx,2],[Sz,1] }
```

벡터 시계는 "이 둘은 조상 관계가 아니다, 즉 충돌이다"를 알려주는 역할만 하고, 실제 판단 재료인 값은 양쪽 다 온다. 클라이언트가 맨땅에서 추측하는 게 아니라 두 버전을 다 보고 규칙대로 합친다. 그래도 그 규칙을 짜는 건 클라이언트 몫이다.

## 실무는 대체로 이 부담을 피한다

| 방식 | 하는 일 | 대가 |
| --- | --- | --- |
| 벡터 시계 | 충돌을 클라이언트에 던진다 | 정확하지만 구현이 어렵다 |
| LWW (Last Write Wins) | 타임스탬프가 늦은 쪽이 이긴다 | 간단하지만 데이터가 조용히 사라진다 |

Cassandra는 기본이 LWW다. 충돌이 나면 나중 것으로 덮어쓴다. 잃어버린 쓰기가 생기지만 개발자가 아무것도 하지 않아도 된다.

Riak은 Dynamo처럼 충돌 버전을 모두 돌려주는 방식(siblings)을 제공했는데, 쓰는 사람들이 힘들어해서 나중에는 LWW를 기본으로 바꿨다고 한다.

즉 책이 설명하는 건 이론적으로 정확한 해법인데, 업계는 대체로 정확함보다 편함을 골랐다. 벡터 시계가 교과서에는 나오지만 실무에서 자주 보이지 않는 이유라고 이해했다.

## 내가 이미 써본 것과 같은 구조였다

스프링의 @Version 낙관적 락이 같은 철학이다.

```java
@Version
private Long version;
```

동시에 수정하면 OptimisticLockException이 터지고, 애플리케이션이 그걸 받아 "다시 시도하세요"라고 사용자에게 던진다. DB가 알아서 합쳐주지 않는다.

이것도 충돌을 감지만 하고 해결은 위로 던지는 것이다. 벡터 시계와 구조가 같고, 차이는 버전을 세는 방식뿐이다.

| | 낙관적 락 (@Version) | 벡터 시계 |
| --- | --- | --- |
| 버전 표현 | 숫자 하나 | 서버마다 하나씩 |
| 충돌 감지 | 버전이 다르면 | 조상 관계가 아니면 |
| 해결 주체 | 애플리케이션 | 클라이언트 |
| 흔한 처리 | 사용자에게 재시도 요청 | LWW로 덮어쓰기 |

낙관적 락이 버전을 숫자 하나로 쓸 수 있는 건 DB가 한 대라서다. 쓰기가 한 곳을 지나가니 순서가 확정된다. 반면 분산 키-값 저장소는 여러 노드가 각자 쓰기를 받으니 순서를 하나의 숫자로 표현할 수 없고, 그래서 서버별로 카운터를 따로 든다. 벡터 시계가 왜 벡터여야 하는지가 여기서 납득됐다.

## 그래서 실무에서 벡터 시계를 쓰는 데가 있나

클라이언트가 "해소"를 도대체 어떻게 하는지 감이 안 잡혀서 더 알아봤다.

### Dynamo 장바구니 - 원조 사례

Amazon이 벡터 시계를 만든 이유 자체가 장바구니였다. 해소 규칙은 합집합이다.

```
D3: [사과, 우유]
D4: [사과, 바나나]
→ 합집합: [사과, 우유, 바나나]
```

왜 합집합이냐 하면, "담긴 물건이 사라지는 것"보다 "안 담은 게 있는 것"이 덜 나쁘다고 판단했기 때문이다. 주문을 놓치는 게 최악이니까.

그런데 여기에 알려진 버그가 있다. 삭제를 표현할 수 없다. 사과를 장바구니에서 지웠는데 다른 복제본에 아직 사과가 남아 있으면 합집합에서 되살아난다. Amazon은 이걸 알고도 감수했다고 한다.

### 해소 코드는 별거 아니다

```java
// 서버가 충돌 버전들을 다 준다
List<Cart> siblings = client.get("cart:user1");

// 클라이언트가 합친다 - 이 규칙이 애플리케이션 몫
Set<Item> merged = siblings.stream()
    .flatMap(c -> c.getItems().stream())
    .collect(toSet());

client.put("cart:user1", new Cart(merged), mergedClock);
```

toSet() 한 줄이 해소의 전부다.

### 문제는 이게 되는 자료형이 얼마 없다는 것

| 자료형 | 병합 규칙 | 가능? |
| --- | --- | --- |
| 장바구니, 좋아요 목록 | 합집합 | 됨 |
| 조회수, 카운터 | 증가량 합 | 됨 |
| 최고 점수 | 최대값 | 됨 |
| 닉네임 | ??? | 안 됨 |
| 주소 | ??? | 안 됨 |
| 문서 본문 | ??? | 매우 어려움 |

닉네임을 한쪽에서 "철수", 다른 쪽에서 "영희"로 바꿨다면 정답이 없다. 자동으로 합칠 방법이 아예 없다. 이런 자료형이 대부분이라서 결국 LWW로 가거나 사용자에게 묻게 된다.

### 현대적인 답은 CRDT

그래서 나온 게 CRDT다. "충돌을 감지해서 물어보자"가 아니라 "어떤 순서로 합쳐도 같은 결과가 나오는 자료형을 설계하자"는 접근이다. Riak이 나중에 CRDT 자료형(카운터, 집합, 맵)을 추가했고, Figma나 Linear 같은 협업 툴의 실시간 동기화도 이 계열(Yjs, Automerge)이다.

벡터 시계의 후계자는 클라이언트에 떠넘기지 않는 방향으로 갔다.

### 매일 쓰는 것 중에 이게 있었다 - Git

```
<<<<<<< HEAD
내가 쓴 코드
=======
남이 쓴 코드
>>>>>>> feature
```

이게 정확히 "충돌을 감지했으니 네가 해소해"다. Git은 합칠 수 있는 건(다른 파일, 다른 줄) 자동으로 합치고, 같은 줄이 다르면 사람에게 던진다.

- 자동 병합 가능 → 알아서 함 (벡터 시계의 조상 관계 판정에 해당)
- 진짜 충돌 → 마커 박고 손 뗌 (벡터 시계의 siblings에 해당)

그리고 내가 그걸 어떻게 해소하는지 생각해보면, 눈으로 보고 고른다. 자동 규칙 같은 건 없다.

## 정리하면서 생각한 것

실제 개발에서 제일 흔한 충돌 해소 로직은 합치는 게 아니라 사용자에게 다시 하라고 하는 것이다. Git 컨플릭트가 그 증거라고 생각한다. 자동 병합은 병합 규칙이 명확한 자료구조(장바구니의 합집합, 카운터의 덧셈)일 때만 가능하고, 그 외에는 사람이 판단해야 한다.

책이 벡터 시계를 "비일관성 해소 기법"으로 분류하는데, 엄밀히는 해소가 아니라 감지 기법이라는 생각이 들었다. 해소는 그 위 계층에서 한다.

# 스스로 확인해본 것 - CAP과 정족수

읽으면서 막히지 않아 그냥 넘어간 부분인데, 확인차 스스로 답해봤더니 하나가 어긋나 있었다.

## CAP에서 P를 포기할 수 있나

내 답은 "포기 안 된다"였다. 네트워크 장애는 통상적으로 막을 수 없으니 CA는 실무에서 안 쓰고, 포기하면 네트워크 장애 때 사용자가 이용을 못 한다.

이건 맞았고, 오히려 책의 "셋 중 둘" 그림이 오해를 부르는 지점이라는 걸 알게 됐다. P는 선택지가 아니라 전제다. 네트워크는 끊긴다. 그래서 실제 선택은 "파티션이 났을 때 C냐 A냐" 하나뿐이고, CA 시스템이라는 건 사실상 분산이 아닌 시스템이다.

## W + R > N이 왜 강한 일관성을 보장하나

내 답은 "두 개 이상의 서버가 동기화되어야 하기 때문"이었는데 틀렸다. 진짜 이유는 동기화가 아니라 겹침(overlap)이다.

N=3, W=2, R=2에서 쓰기를 {s1, s2}에 했다면 읽을 때 2대를 어떻게 고르든

| 읽는 집합 | 최신 쓰기 포함? |
| --- | --- |
| {s1, s2} | 둘 다 있음 |
| {s1, s3} | s1이 있음 |
| {s2, s3} | s2가 있음 |

어떻게 골라도 최소 한 대가 겹친다. 그 한 대가 최신 값을 가지고 있으니 읽기가 최신을 본다. 비둘기집 원리로, W+R>N이면 두 집합이 안 겹칠 수가 없다.

W=1, R=1이면 쓰기는 {s1}, 읽기는 {s3}에서 할 수 있으니 겹치지 않고 오래된 값을 읽는다.

이 차이가 중요하다고 생각한 이유는, 내 설명대로면 "서버들이 서로 데이터를 맞춘다"는 뜻이 되는데 실제로는 서버끼리 아무 조율도 하지 않기 때문이다. 읽는 쪽이 여러 대에서 받아와 버전이 최신인 것을 고르는 것뿐이다. 조율 없이 정확성을 보장하는 게 정족수의 핵심이었다.

# 더 생각해본 것 - 머클 트리는 어디서 봤더라

장애 처리 절에서 머클 트리가 나오는데 이상하게 익숙했다. 생각해보니 지금 듣고 있는 블록체인 수업에서 배운 개념이었다.

## 같은 자료구조를 다른 목적으로 쓰고 있었다

| | 블록체인 수업 | 6장 키-값 저장소 |
| --- | --- | --- |
| 묶는 것 | 블록 안의 거래들 | 복제본의 데이터들 |
| 루트 해시로 아는 것 | 바뀌었나 (무결성) | 어디가 다르나 (동기화) |
| 트리를 쓰는 이유 | 거래 하나만 바꿔도 루트가 달라진다 | 다른 가지만 파고들어 비교 횟수를 줄인다 |

블록체인에서는 변조를 잡아내는 게 목적이다. 블록 헤더에 머클 루트만 넣어두면 거래 하나를 바꿔도 루트가 안 맞으니 바로 들킨다. 머클 증명으로 특정 거래가 그 블록에 포함됐다는 것을 해시 몇 개만으로 증명할 수 있고, 라이트 클라이언트가 블록 전체를 받지 않고 검증하는 게 이 원리다.

6장은 목적이 다르다. 어긋난 데이터를 싸게 찾아내는 것이다.

```
1. 두 복제본의 루트 해시 비교 → 같으면 끝
2. 다르면 자식 비교 → 같은 가지는 버림
3. 다른 가지만 파고 내려감
4. 결국 실제로 다른 데이터만 찾아내 그것만 전송
```

비교 횟수가 n에서 log n으로 줄어든다.

## 정리하며 생각한 것

블록체인은 "루트만 보고 변조를 안다"에서 멈추는데, 6장은 "루트가 다르면 내려가며 범인을 찾는다"까지 간다. 같은 구조를 한 단계 더 쓰는 셈이다.

수업에서는 머클 트리를 보안 장치로만 이해하고 있었는데, 애초에 이게 "큰 데이터 두 덩어리를 싸게 비교하는" 자료구조이고 블록체인이 그중 한 가지 용도였다는 걸 알게 됐다.
