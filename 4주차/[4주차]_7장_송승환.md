## 7장 요약 - 분산 시스템을 위한 유일 ID 생성기 설계

분산 환경에서는 여러 서버가 동시에 ID를 만들기 때문에, 데이터베이스의 `auto_increment` 같은 방식을 그대로 쓸 수 없음. 서버마다 따로 번호를 매기면 중복이 발생하기 때문임

### 1. 문제 이해 및 설계 범위 확정

이 장에서 만들 ID 생성기의 요구사항

- ID는 **유일**해야 함
- ID는 **숫자로만** 구성되어야 함
- ID는 **64비트**로 표현될 수 있는 값이어야 함
- ID는 발급 날짜에 따라 **정렬 가능**해야 함
- 초당 **10,000개**의 ID를 만들 수 있어야 함

### 2. 개략적 설계안 제시 및 동의 구하기

분산 환경에서 유일성이 보장되는 ID를 만드는 방법은 여러 가지임

#### 1) 다중 마스터 복제

데이터베이스의 `auto_increment` 기능을 활용하되, **다음 ID의 값을 1이 아니라 k만큼 증가**시킴 (k는 사용 중인 DB 서버의 수)

- 서버 1: 1, 3, 5, 7, ...
- 서버 2: 2, 4, 6, 8, ...

이렇게 하면 서버 대수만큼 규모 확장이 가능해짐

**단점**

- 여러 데이터 센터에 걸쳐 규모를 늘리기 어려움
- ID의 유일성은 보장되지만 **시간 흐름에 맞춰 커지도록 정렬하기 어려움**
- 서버를 추가하거나 삭제할 때 잘 동작하지 않음

#### 2) UUID

UUID는 컴퓨터 시스템에 저장되는 정보를 유일하게 식별하기 위한 **128비트짜리 수**임

```
09c93e62-50b4-468d-bf8a-c07e1040bfb2
```

**장점**

- UUID를 만드는 것이 단순함. **서버 간 조율이 전혀 필요 없으므로** 동기화 이슈도 없음
- 각 서버가 자기 ID를 스스로 만들면 되므로 **규모 확장이 쉬움**

**단점**

- **128비트**로, 요구사항인 64비트보다 김
- **시간 순으로 정렬할 수 없음**
- 숫자가 아닌 값(문자)이 포함됨

#### 3) 티켓 서버

`auto_increment` 기능을 갖춘 **데이터베이스 서버 한 대**를 티켓 서버로 지정하고, 모든 ID 발급을 그 서버에 몰아주는 방식임 (Flickr가 사용한 방식)

**장점**

- 유일성이 보장되는 **숫자 ID**를 쉽게 만들 수 있음
- 구현이 단순하여 중소 규모 애플리케이션에 적합함

**단점**

- 티켓 서버가 **SPOF(단일 장애 지점)** 가 됨. 이 서버에 장애가 생기면 시스템 전체가 영향을 받음
- SPOF를 피하려고 티켓 서버를 여러 대 두면, 이번엔 서버 간 데이터 동기화 문제가 생김

#### 4) 트위터 스노플레이크 접근법 (채택)

위 방법들의 요구사항을 모두 만족시키지 못하므로, **ID의 구조를 여러 절(section)로 나누는** 방식을 씀

```
 1        41          5        5         12
부호   타임스탬프     DC      서버     일련번호
```

- 사인(sign) 1비트 - 항상 0. 향후 사용을 위해 예약해 둔 비트
- 타임스탬프 41비트 - 기준 시각(epoch) 이후 흐른 밀리초
- 데이터센터 ID 5비트 - 2^5 = 32개 데이터센터
- 서버 ID 5비트 - 데이터센터당 2^5 = 32개 서버
- 일련번호 12비트 - 같은 밀리초 안에서 2^12 = 4096개까지 발급

### 3. 상세 설계

**데이터센터 ID와 서버 ID**는 시스템 시작 시 결정되며, 운영 중에는 바뀌지 않음. 이 값을 바꾸면 ID 충돌 위험이 생기므로 신중해야 함

**타임스탬프**는 이 설계에서 가장 중요한 절임. 상위 비트에 위치하므로 시간이 흐를수록 ID 값이 커지고, 따라서 시간순 정렬이 가능해짐

41비트로 표현 가능한 시간은

```
2^41 - 1 = 2,199,023,255,551 밀리초  ≈  69년
```

→ 기준 시각으로부터 69년간 쓸 수 있고, 69년이 지나면 기준 시각을 다시 정하거나 다른 방법으로 ID를 만들어야 함

**일련번호**는 12비트로 4096개의 값을 가질 수 있음. 어떤 서버가 **같은 밀리초 동안 하나 이상의 ID를 만든 경우에만** 0보다 큰 값을 가짐

### 4. 마무리

추가로 논의해볼 수 있는 것들

#### 시계 동기화

이 설계에서는 ID 생성 서버들이 모두 같은 시계를 쓴다고 가정했음

But, 하나의 서버가 여러 코어에서 돌거나 여러 서버가 물리적으로 독립된 환경에서 돌면 이 가정은 성립하지 않을 수 있음
→ NTP(Network Time Protocol)로 시계를 동기화해야 함

#### 각 절의 길이 최적화

동시성이 낮고 수명이 긴 애플리케이션이라면 일련번호 절의 길이를 줄이고 타임스탬프 절의 길이를 늘리는 것이 효과적임

#### 고가용성

ID 생성기는 필수 컴포넌트이므로 아주 높은 가용성을 제공해야 함

## 읽으면서 든 질문

### Q1. "각 절의 길이 최적화"가 무슨 뜻인가?

"동시성이 낮고 수명이 긴 애플리케이션은 일련번호 절을 줄이고 타임스탬프 절을 늘려라"는 문장이 바로 와닿지 않았음

핵심은 **64비트가 고정된 예산**이라는 것임. 어딘가를 늘리려면 **반드시 다른 곳에서 빼와야 함**

각 절이 사는 것을 다시 보면

- 타임스탬프 41비트 → 2^41 밀리초 ≈ 69년 (서비스 수명)
- DC + 서버 10비트 → 32 × 32 = 1024대 (서버 대수)
- 일련번호 12비트 → 4096개 (같은 밀리초 안에서 한 서버가 만들 수 있는 ID 수)

일련번호 4096개는 곧 **서버 한 대당 초당 409만 개**임. 트위터 규모라서 이만큼 잡은 것임

**동시성이 낮다** = 같은 밀리초에 ID를 몇 개 만들지 않는다
**수명이 길다** = 서비스를 오래 운영할 계획이다

예를 들어 초당 100개면 충분한 사내 시스템이라면

```
초당 100개 = 밀리초당 0.1개
그런데 일련번호 12비트는 밀리초당 4096개를 감당하는 크기 → 과잉
```

이 남는 공간을 타임스탬프로 옮기면

```
조정 전   타임스탬프 41  |  일련번호 12
조정 후   타임스탬프 47  |  일련번호  6

일련번호 6비트   = 밀리초당 64개 = 초당 6만 4천개   ← 여전히 충분
타임스탬프 47비트 = 2^47 밀리초  ≈ 4,400년        ← 69년에서 크게 늘어남
```

**쓰지도 않을 처리량을 위해 잡아둔 비트를, 실제로 필요한 수명으로 옮긴 것**이 전부임

반대 경우도 성립함. 동시성이 아주 높고 수명은 짧아도 되는 서비스라면

```
타임스탬프 35  |  일련번호 18
타임스탬프 35비트 ≈ 1년           일련번호 18비트 = 밀리초당 26만개
```

**DC·서버 비트도 거래 대상임.** 1024대까지 둘 일이 없다면 그쪽을 줄여 다른 절에 보탤 수 있음

또 하나의 방법은 **타임스탬프의 단위 자체를 바꾸는 것**임. 밀리초 대신 10밀리초 단위로 세면 같은 41비트로 10배 긴 기간을 커버함(69년 → 690년). But, 시간 구간이 굵어진 만큼 한 구간에 몰리는 ID가 많아지므로 일련번호가 더 필요해짐 → 결국 또 맞바꿈임

→ 결국 이 절의 메시지는 **책이 제시한 41/5/5/12는 트위터의 선택이지 법칙이 아니라는 것**임. 내 서비스의 처리량과 수명을 따져 64비트를 다시 나눠야 함

### Q2. NTP란 무엇인가?

**NTP(Network Time Protocol)** 는 네트워크를 통해 컴퓨터들의 시계를 맞추는 규약임. UDP 123번 포트를 사용함

**왜 필요한가** - 컴퓨터 시계는 수정 발진자로 도는데 온도나 개체 차이 때문에 미세하게 빠르거나 느림. 하루에 몇 초씩 밀리는 것이 보통이라, 서버 여러 대를 방치하면 서로 시간이 벌어짐

**Stratum 계층 구조**로 정확한 시간을 아래로 전달함

- Stratum 0 - 원자시계, GPS 수신기 (기준 시계 그 자체)
- Stratum 1 - Stratum 0에 직접 연결된 서버
- Stratum 2 - Stratum 1과 동기화된 서버
- Stratum 3 - 보통 우리 서버가 붙는 곳

동작은 주기적으로 상위 서버에 시간을 묻고, **왕복에 걸린 시간을 계산해 보정**한 뒤 자기 시계를 맞추는 방식임

**7장에서 왜 중요한가**

스노플레이크는 상위 41비트가 타임스탬프이므로 **숫자 크기순 = 시간순**이라고 믿는 구조임. 그런데 서버 시계가 어긋나면

```
s1 의 시계  12:00:05  (3초 빠름)
s2 의 시계  12:00:02  (정확)

s2 가 실제로는 나중에 만든 ID 인데
s1 이 먼저 만든 ID 보다 작은 숫자가 나옴  →  정렬이 어긋남
```

→ **NTP 동기화가 스노플레이크의 전제 조건**임. "시간으로 정렬한다"는 설계가 성립하려면 그 시간을 믿을 수 있어야 하기 때문임

**But, NTP가 오히려 문제를 만들기도 함**

NTP가 시계를 맞추는 방식이 두 가지임

- **slew** - 차이가 작으면 시계 속도를 미세하게 조절해 슬금슬금 따라잡음 (안전)
- **step** - 차이가 크면 한 번에 점프시킴. 문제는 **이 점프가 뒤로 갈 수도 있다는 것**

```
내 시계가 5초 빨랐음
NTP: "5초 빼"  →  12:00:10 이었다가 갑자기 12:00:05 로

그런데 12:00:07 에 이미 발급한 ID 가 있었다면?
→ (같은 밀리초 + 같은 서버 + 같은 일련번호) 조합이 다시 나올 수 있음  →  ID 중복
```

**시계를 믿게 만들어주는 장치가 그 믿음을 깨는 순간을 만드는 셈**임

그래서 실제 구현은 **시계가 뒤로 간 것을 감지하면 ID 발급을 멈추고, 시계가 원래 지점을 따라잡을 때까지 기다림**. 틀린 ID를 주느니 잠시 주지 않는 쪽을 택한 것임

→ 이것 역시 **정확성과 가용성 사이의 선택**이므로, 6장 CAP에서 본 구조와 같음

## AWS와 연결해보기

7장은 6장만큼 직접적인 대응이 많지는 않지만, 배운 서비스로 보면

- 티켓 서버 → RDS의 `auto_increment`. 중앙 DB 한 대가 ID를 발급하는 구조 그 자체이며, 따라서 SPOF 위험도 그대로 따라옴
- 다중 마스터 복제의 한계 → Read Replica. 복제본 여러 대가 각자 ID를 만들면 중복과 순서 문제가 생김
- 시간순 정렬 ID의 이점 → DynamoDB 정렬 키 등. 정렬 키에 시간순 ID를 쓰면 시계열 조회가 쉬워짐. 스노플레이크가 시간 정렬을 중요하게 본 이유와 통함

---

## 정리

- 분산 환경에서 ID를 만드는 방법은 여러 가지지만, **유일성·숫자·64비트·시간순 정렬**을 모두 만족하는 것은 스노플레이크 방식임
- 스노플레이크의 핵심은 **64비트를 의미 단위로 쪼개는 것**이고, 상위 비트에 시간을 둠으로써 조율 없이도 시간순 정렬을 얻음
- 다만 **시간에 기대는 설계**이므로 시계를 믿을 수 있어야 성립하며, 그 믿음을 만들어주는 것이 NTP임
- 그리고 41/5/5/12는 정답이 아니라 **트위터의 선택**이므로, 내 서비스의 처리량과 수명에 맞춰 다시 나눠야 함
