# [4주차] 7장 - 분산 시스템을 위한 유일 ID 생성기 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

## 책 내용 뼈대

분산 환경에서 유일한 ID를 만드는 방법 네 가지를 비교하고 스노플레이크로 수렴한다.

| 방식 | 되는 점 | 안 되는 점 |
| --- | --- | --- |
| 다중 마스터 복제 | auto_increment를 그대로 쓴다 | 서버 추가/삭제 시 깨짐, 시간순 정렬 안 됨 |
| UUID | 서버 간 조율이 아예 필요 없어 확장이 쉽다 | 128비트로 길다, 시간순 정렬 안 됨, 숫자가 아니다 |
| 티켓 서버 | 단순하고 숫자 ID를 얻는다 | 티켓 서버가 SPOF |
| 스노플레이크 | 64비트, 시간순 정렬, 조율 불필요 | 시계 동기화에 의존 |

### 스노플레이크의 비트 배분

| 구역 | 비트 | 표현 범위 |
| --- | --- | --- |
| 사인 비트 | 1 | 미사용 (미래 대비) |
| 타임스탬프 | 41 | 약 69년 (밀리초 단위) |
| 데이터센터 ID | 5 | 32개 |
| 서버 ID | 5 | 32개 |
| 일련번호 | 12 | 같은 밀리초에 4,096개 |

데이터센터 ID와 서버 ID는 시작할 때 정해지고, 일련번호는 같은 밀리초 안에서만 증가하고 그 다음 밀리초에 0으로 돌아간다.

### 마무리에서 언급되는 것

시계 동기화(NTP) 문제, 각 구역 길이 조정, 고가용성.

# 개인적인 질문

## 1. 도입부의 auto_increment 기본 키가 스프링부트에서 @Id로 하던 그건가

맞는데 정확히는 @Id가 아니라 @GeneratedValue의 전략이었다.

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)   // 이게 AUTO_INCREMENT
private Long id;
```

@Id는 "이게 기본 키다"라는 표시고, IDENTITY 전략이 MySQL의 AUTO_INCREMENT로 매핑된다.

### JPA 전략이 7장 선택지와 거의 1:1이었다

| 7장 | JPA 전략 |
| --- | --- |
| auto_increment 기본 키 | IDENTITY |
| 티켓 서버 (중앙에서 키 발급) | TABLE |
| UUID | UUID (Hibernate 6) |
| 스노플레이크 | 직접 구현 |

TABLE 전략이 7장의 티켓 서버와 사실상 같은 개념이었다. 별도 키 테이블을 두고 거기서 번호를 받아오는 방식이다. 7장이 "티켓 서버"라고 이름 붙인 걸 JPA는 전략으로 제공하고 있었다. SEQUENCE는 Hibernate가 allocationSize로 여러 개를 미리 받아두는 최적화를 하는데, 이것도 티켓 서버 절의 배치 발급 아이디어와 같다.

책을 읽기 전에는 IDENTITY 말고 다른 전략이 왜 있는지 생각해본 적이 없었는데, 전략 목록이 곧 분산 ID 발급 방식의 목록이었다.

## 2. IDENTITY의 함정 - 2주차와 이어지는 부분

찾아보다가 알게 된 건데, IDENTITY를 쓰면 Hibernate가 배치 insert를 못 한다.

IDENTITY는 DB가 ID를 만들어줘야 아는 값인데, JPA는 persist() 시점에 영속성 컨텍스트에 넣으려면 ID가 있어야 한다. 그래서 persist()를 부르는 순간 INSERT를 바로 날린다. @Transactional 안에서 1000건을 저장하면 보통은 커밋 시점에 모아 보내지만(쓰기 지연), IDENTITY면 1000번 따로 나간다.

2주차에 강상준 님이 3장 문서에 "단건 저장을 반복하면 네트워크 왕복 지연과 DB 락 경합으로 서버가 터질 수 있다"고 쓴 게 이것과 이어진다. IDENTITY는 구조적으로 그 상황을 강제한다. 그래서 대량 삽입이 필요하면 SEQUENCE로 바꾸거나 JDBC로 직접 벌크 삽입한다.

내가 지금까지 쓴 프로젝트는 전부 IDENTITY였는데, 대량 삽입을 한 적이 없어서 문제를 겪지 않았던 것 같다.

## 3. 다중 마스터 복제가 무한 호텔 역설과 비슷한 것 같은데

읽다가 떠오른 비유인데, 실제로 쓰는 트릭이 같았다.

무한 호텔에서 방이 다 찼는데 무한 명이 또 오면 n번 손님을 2n번 방으로 옮겨 홀수 방을 전부 비운다. 다중 마스터 복제가 하는 게 정확히 이것이다.

```
서버 1 → 1, 3, 5, 7, ...   (홀수)
서버 2 → 2, 4, 6, 8, ...   (짝수)
```

하나의 수열을 겹치지 않는 부분수열 k개로 쪼개는 것이고, 둘 다 mod k로 잉여류를 나눠 쓴다.

### 한계도 같았다

무한 호텔에서 홀짝으로 나눠놨는데 세 번째 무한 그룹이 오면 전원을 다시 옮겨야 한다. 이미 홀짝으로 자리가 굳었으니 3n 체계로 재배치해야 한다.

다중 마스터 복제도 서버를 3대로 늘리면 증가폭 k가 2에서 3으로 바뀌어 기존 체계가 깨진다. 책이 "서버를 추가하거나 삭제하면 잘 동작하지 않는다"고 하는 게 이것이다.

## 5장과 연계해서 생각해보자

이 구조를 5장에서 이미 봤다.

| | 나누는 방법 | N이 바뀌면 |
| --- | --- | --- |
| 5장 해시 키 재배치 | hash(key) % N | 거의 전부 재배치 |
| 7장 다중 마스터 복제 | 증가폭 k | 체계 자체가 깨짐 |

둘 다 mod N에 기대는 방식이고, 둘 다 N이 바뀌는 순간 무너진다.

5장은 이 문제를 안정 해시로 풀었다. 7장은 다른 길로 간다. 스노플레이크는 ID 안에 데이터센터 번호와 서버 번호를 비트로 박아넣어서 서버가 늘어도 남의 번호를 건드리지 않게 한다. mod N으로 나누는 대신 각자에게 고정된 자리를 주는 접근이다.

같은 문제에 두 가지 해법이 있는 셈인데, 안정 해시는 "옮겨야 할 양을 최소화"하고 스노플레이크는 "애초에 옮길 일이 없게" 만든다.

## 스스로 확인해본 것 - 타임스탬프가 왜 맨 앞인가

시간 순서 정렬 때문이라고 답했는데, 이유를 한 단계 더 볼 수 있었다.

ID를 정수로 비교하면 상위 비트가 먼저 비교된다. 타임스탬프가 맨 위에 있으면 숫자 정렬이 곧 시간 정렬이 된다. 데이터센터 ID를 앞에 두면 데이터센터별로 뭉친 다음 시간순이 되어 전역 정렬이 깨진다.

실무 효과가 하나 더 있다. 단조 증가하는 키는 B-tree 인덱스에 유리하다. 삽입이 항상 오른쪽 끝에서만 일어나니 페이지 분할이 적다. 반면 UUID v4는 랜덤이라 인덱스 곳곳에 꽂히며 파편화된다. 위에서 본 IDENTITY와 UUID 선택에 이 이유도 들어간다.
