> - **주제**: 7장 - 분산 시스템을 위한 유일 ID 생성기 설계

## 문제 이해 및 설계 범위 확정

데이터베이스가 한 대라면 `auto_increment`를 이용해 새 레코드의 ID를 쉽게 생성할 수 있다. 그러나 여러 데이터베이스나 서버가 독립적으로 ID를 만든다면 **중복 없이 생성하는 방법**을 따로 고민해야 한다.

책의 예시에서 ID 생성기가 만족해야 할 조건은 다음과 같다.

- ID는 전체 시스템에서 유일해야 한다.
- 숫자로만 구성해야 한다.
- 64비트로 표현할 수 있어야 한다.
- 발급 시각에 따라 대체로 정렬할 수 있어야 한다.
- 초당 약 10,000개의 ID를 생성할 수 있어야 한다.

여기서 “시간에 따라 정렬된다”는 것은 **모든 생성기가 발급한 ID가 반드시 1씩 증가해야 한다**는 뜻이 아니다. 오전에 발급한 ID가 저녁에 발급한 ID보다 대체로 작은 값을 갖는 정도가 요구사항이다.

기존 백엔드 프로젝트에서 DB의 자동 증가 키를 사용했다면 ID의 중복 방지는 데이터베이스가 맡아준 셈이다. 이번 장은 데이터 저장소와 애플리케이션이 여러 곳으로 나뉘었을 때 그 책임을 어디에 둘지 묻는다.

---

## 여러 ID 생성 방식 비교

### 다중 마스터 복제

여러 데이터베이스에서 각각 자동 증가 ID를 생성하되, 데이터베이스 수만큼 간격을 띄워 값을 증가시키는 방식이다.

예를 들어 데이터베이스가 두 대라면 한쪽은 `1, 3, 5, ...`, 다른 쪽은 `2, 4, 6, ...`을 생성하도록 설정할 수 있다. 서로 다른 데이터베이스가 같은 ID를 만드는 문제를 피할 수 있다.

하지만 여러 데이터센터로 확장하거나 데이터베이스 수를 변경할 때 조정하기 어렵다. 또한 전체 ID가 발급 시각 순서대로 증가한다고 보장할 수 없다.

### UUID

UUID는 각 서버가 별도의 중앙 생성기와 통신하지 않고도 독립적으로 ID를 만들 수 있는 방법이다. 충돌 가능성이 극히 낮고 서버를 확장하기도 쉽다.

그러나 책의 요구사항과는 맞지 않는다.

- 일반적인 UUID는 128비트이므로 64비트 제한을 넘는다.
- 문자열 형태로 표현되는 UUID는 숫자로만 구성된 ID라는 조건과 맞지 않는다.
- 책에서 비교하는 일반적인 UUID는 발급 시각 순으로 정렬되지 않는다.

UUID가 나쁜 방법이라는 뜻은 아니다. **이 면접 문제에서 합의한 요구사항과 맞지 않는 것**이다.

### 티켓 서버

자동 증가 기능이 있는 별도의 데이터베이스를 **중앙 ID 발급 서버**로 사용하는 방식이다. 다른 웹 서버들은 새 ID가 필요할 때마다 티켓 서버에 요청한다.

숫자로만 된 유일한 ID를 만들기 쉽고 구조도 이해하기 쉽다. 하지만 티켓 서버가 하나뿐이면 장애 지점이 되고, 많은 서버가 동시에 ID를 요청하면 병목이 될 수 있다. 티켓 서버를 여러 대로 늘리면 다시 발급 범위 조정과 동기화 문제가 생긴다.

### 트위터 스노플레이크

스노플레이크(Snowflake)는 하나의 64비트 정수를 여러 부분으로 나누어 ID를 만드는 방식이다. 발급 시각과 생성 위치, 같은 시각에 발급한 순서를 ID 안에 담는다.

중앙 데이터베이스에 ID를 요청하지 않고 각 생성기가 독립적으로 값을 만들 수 있으면서, 책의 숫자·길이·시간순 정렬·처리량 요구사항을 만족시키는 대안이다.

---

## 스노플레이크 ID의 구성

책에서 사용하는 64비트 ID는 다음과 같이 나뉜다.

| 구성 요소 | 비트 수 | 역할 |
| :--- | ---: | :--- |
| 부호 비트 | 1 | 현재 설계에서는 사용하지 않으며 `0`으로 둔다. |
| 타임스탬프 | 41 | 정해둔 기준 시각(epoch)부터 지난 밀리초를 저장한다. |
| 데이터센터 ID | 5 | ID를 발급한 데이터센터를 구분한다. |
| 서버 ID | 5 | 해당 데이터센터의 생성 서버를 구분한다. |
| 일련번호 | 12 | 같은 서버가 같은 밀리초에 만든 ID를 구분한다. |

`1 + 41 + 5 + 5 + 12 = 64`비트다.

- 데이터센터 ID 5비트로 최대 32개의 데이터센터를 구분할 수 있다.
- 서버 ID 5비트로 데이터센터당 최대 32개의 생성 서버를 구분할 수 있다.
- 일련번호 12비트로 서버 한 대가 같은 밀리초에 최대 4,096개의 ID를 구분할 수 있다.
- 타임스탬프 41비트는 밀리초 단위로 약 69년에 해당한다.

이는 책에서 채택한 **비트 배분 예시**다. 실제 서비스에서는 데이터센터·서버의 수, 순간 생성량, ID 체계의 예상 수명을 보고 각 영역의 길이를 다시 정할 수 있다.

## ID 생성 과정

하나의 서버가 ID를 생성한다고 가정하면 흐름은 다음과 같다.

1. 현재 시각에서 미리 정한 기준 시각을 빼 타임스탬프 값을 구한다.
2. 자신에게 할당된 데이터센터 ID와 서버 ID를 확인한다.
3. 같은 밀리초 안에서 ID를 만들 때마다 일련번호를 증가시킨다.
4. 각 값을 정해진 비트 위치에 배치해 하나의 64비트 정수를 만든다.
5. 다음 밀리초가 되면 일련번호를 다시 초기화한다.

타임스탬프가 높은 비트에 있으므로 나중 시각에 만든 ID가 대체로 더 큰 값을 갖는다. 하지만 **서로 다른 서버에서 같은 밀리초에 생성한 ID의 크기까지 실제 생성 순서와 일치하는 것은 아니다.** 이 방식은 전역적인 엄격한 발급 순서를 보장하는 중앙 카운터가 아니다.

## 데이터센터 ID와 서버 ID의 관리

스노플레이크의 유일성은 타임스탬프와 일련번호만으로 보장되지 않는다. 같은 시각에 두 생성기가 **동일한 데이터센터 ID와 서버 ID**를 사용하면 중복 ID가 발생할 수 있다.

따라서 생성 서버를 추가하거나 재시작할 때 이 조합이 중복 할당되지 않도록 관리해야 한다. 컨테이너나 서버를 자동으로 늘리는 환경이라면 “새 서버는 자신의 ID를 어디서 받아오는가?”도 설계의 일부가 된다.

5장의 안정 해시는 여러 데이터 서버 가운데 **키를 보낼 위치**를 결정했다. 반면 스노플레이크의 서버 ID는 여러 생성 서버가 **같은 ID를 만들지 않도록 발급자를 구별**한다. 둘 다 서버를 식별하지만 해결하는 문제가 다르다.

## 운영할 때 생각해야 할 문제

### 시계 동기화와 시간 역행

스노플레이크는 서버의 시계를 이용한다. 서버의 시간이 앞뒤로 어긋나거나 이전에 사용한 시각으로 되돌아가면 ID의 정렬 성질이 깨질 수 있고, 조건에 따라 중복 위험도 생긴다.

따라서 서버 시간을 동기화하고, 현재 시각이 마지막으로 사용한 시각보다 과거라면 **생성을 잠시 멈추거나 오류로 처리하는 등의 정책**이 필요하다. 책에서는 시계 동기화의 일반적인 수단으로 NTP를 언급한다.

### 같은 밀리초의 일련번호 소진

12비트 일련번호에는 한 밀리초에 4,096개의 값이 들어간다. 서버 한 대가 같은 밀리초 안에 이를 모두 사용하면 다음 밀리초가 올 때까지 기다리거나 별도 처리를 해야 한다.

“초당 10,000개를 생성한다”는 평균 요구사항만으로는 안전하다고 단정할 수 없다. 2장에서 QPS를 계산할 때처럼 **평균뿐 아니라 순간 최대 생성량**도 확인해야 한다.

### 비트 길이의 조정

데이터센터와 서버의 수가 적은데 생성량이 아주 많다면 서버 식별자에 할당한 비트 일부를 일련번호에 사용할 수 있다. 반대로 서버 수가 많다면 서버 ID의 길이를 늘려야 할 수 있다.

타임스탬프 비트의 길이는 ID 체계의 수명과도 연결된다. 구조를 정한 뒤에는 시스템을 운영하는 도중 마음대로 바꾸기 어려우므로 예상 사용 기간을 고려해야 한다.

### 생성기의 가용성

ID가 있어야 데이터를 저장할 수 있는 시스템이라면 생성기 장애가 곧 쓰기 장애가 될 수 있다. 스노플레이크는 서버별로 독립적인 생성이 가능하지만, 각 생성기의 시계 상태와 서버 ID 할당이 올바른지도 함께 관리해야 한다.

## 생각해본 질문

### 데이터베이스의 `auto_increment`가 있는데 굳이 별도의 ID 생성 방식이 필요할까?

데이터베이스 한 대에서 ID를 발급하고 성능도 충분하다면 그대로 사용하는 편이 간단하다. 하지만 여러 데이터베이스가 독립적으로 쓰기를 받거나 중앙 발급 지점이 병목이 되는 규모라면, 전체에서 중복되지 않는 ID를 만드는 별도 전략이 필요하다. **분산 ID 생성이 항상 기본값인 것은 아니다.**

### 일련번호는 2^12개의 값을 가질 수 있는데, 같은 밀리초 동안 하나 이상의 ID를 만들어 낸 경우에만 0보다 큰 값을 갖게 된다면, 사실상 실무에서는 2^12에 근접할 일이 있을까? 타임스탬프를 41비트를 주고 일련번호를 12비트를 준 이유가 따로 있을까? 만약 타임스탬프를 42비트, 일련번호를 11비트를 준다면 실무에서 문제 없이 약 140년 동안 정상 동작하게 할 수 있는 거 아닐까? 라고 생각했는데 마무리에서 각 절의 길이 최적화에서 언급하네요.

일련번호는 서버 한 대가 같은 1밀리초에 만든 ID를 구분한다. 첫 ID가 0, 두 번째가 1이므로, 12비트면 한 서버에서 밀리초당 0~4095, 총 4,096개를 만들 수 있다.
책의 요구량인 초당 10,000개가 전체 시스템에 고르게 들어온다면, 평균은 밀리초당 10개 수준이니 4,096개에 근접하기 어렵지만 서버별 요청 분포와 순간 최대량은 평균과 다를 수 있어서 여유를 둔 것이다. 따라서 서버당 순간 생성량이 2,048개/ms를 넘지 않는다고 판단하면 42비트·11비트 설계도 가능하다. 다만 약 139년은 미리 정한 기준 시각부터 계산한 기간이고, 이미 사용 중인 ID의 비트 구조를 나중에 바꾸는 일은 호환성 문제를 낳는다. 41·12는 긴 수명과 높은 순간 처리량 사이에서 잡은 설계값으로 보면 된다.

### ID 생성 서버들이 전부 같은 시계를 사용한다고 가정했지만, 하나의 서버가 여러 코어에서 실행되거나 여러 서버가 물리적으로 독립된 여러 장비에서 실행되는 경우에 유효하지 않을 수도 있다고 했는데, 이게 무슨 뜻이지..?

물리적으로 다른 서버는 각자 자기 컴퓨터의 시계를 읽는다. 둘 다 같은 실제 시각을 가리킨다고 가정하지만, 시계가 조금씩 어긋나거나 시간 보정 과정에서 뒤로 움직일 수 있다.
- 서버 간 시각 차이: 실제로 나중에 만든 ID인데 타임스탬프가 더 작아져, ID 순서가 실제 생성 순서와 달라질 수 있다.
- 한 서버의 시계가 뒤로 감: 이미 사용한 밀리초를 다시 사용하게 되므로, 일련번호 상태까지 잘못 다루면 중복 ID가 생길 수 있다. 원래 Snowflake 구현에서도 이 문제를 지적한 이슈가 있었다.
여러 코어 이야기는 조금 구분해서 읽어야 한다. 코어가 여러 개라고 반드시 서로 다른 시계를 쓰는 건 아니다. 다만 여러 스레드가 같은 생성기를 동시에 호출하면 같은 밀리초에 같은 일련번호를 받지 않도록 동시성을 제어해야 한다. 서로 다른 물리 서버의 시계 동기화 문제와, 한 서버 안의 일련번호 동시성 문제는 별개이다.

### ID 생성기는 필수 불가결 컴포넌트인데, 우리가 쉽게 이해할만한 필수적으로 쓰이는 예시가 뭐가 있을까? 유저 ID? 특정 쿼리에 대한 ID?

가장 쉬운 예시는 게시물 ID와 주문 ID이다. 서로 다른 서버가 동시에 새 게시물이나 주문을 만들어도 같은 ID를 발급하면 안 된다. 사용자 ID도 해당한다.
다만 모든 서비스에 별도 분산 ID 생성기가 필수라는 뜻은 아니다. MySQL 테이블의 AUTO_INCREMENT 기본키를 써왔다면 MySQL이 이미 ID 생성기 역할을 해준 것이다. 7장의 질문은 여러 서버나 데이터베이스가 독립적으로 생성해야 할 만큼 확장했을 때, 그 역할을 어떻게 수행할지에 가깝다
“특정 쿼리에 대한 ID”는 용도에 따라 달라. SQL 쿼리마다 영구적인 Snowflake ID가 필요한 건 아니지만, 요청을 로그에서 추적하기 위한 요청 ID 또는 추적 ID를 붙일 수는 있다. 이것은 게시물·주문처럼 저장되는 데이터의 ID와 목적이 다르므로 반드시 같은 생성 방식을 쓸 필요는 없다.
