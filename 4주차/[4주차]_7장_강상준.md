**앞선 정리**
데이터가 있고, 그 고유 키가 있는데 이를 해시해서 해시 링 시계방향에서 처음 만나는 서버에 저장하는 것.
7장 내용은 그 고유 키를 어떻게 만들 것인지에 대해 알아보는 내용이라고 생각하고 접근해보겠습니다.

auto_increment 속성이 설정된 rds의 기본키는 분산 환경에서 통하지 않는다.

대규모 분산 시스템에서의 ID는 다음의 조건을 만족해야한다.
1. 정렬 가능해야 한다.
2. 숫자(64비트 정수)여야 한다.
3. 분산 환경에서 생성에 병목이 없어야 한다.

# 1단계 - 문제 이해 및 설계 범위 확정
이번에 만족해야할 요구사항은 다음과 같다.
1. ID는 유일해야 한다.
2. 숫자로만 구성되어야 한다.
3. 64비트로 표현 가능한 값이어야한다.
4. 발급 날짜에 따라 정렬이 가능해야한다.
5. 초당 10,000개의 ID를 만들 수 있어야한다(병목없이)

# 2단계 - 개략적 설계안 제시 및 동의 구하기

## 다중 마스터 복제
데이터베이스의 auto_increment 기능을 활용하는 것이다.
다만 1씩 증가시키는 게 아니라 k(서버 수)만큼 증가시킨다. -> 규모 확장성 문제를 어느정도 해결할 수 있음. 데이터 베이스 수를 늘리면 초당 생성 가능한 ID 수가 늘어나기 때문.
ID를 만드는 주체가 DB이다. -> ID를 뽑으려면 DB랑 통신해야 한다.

단점: 
- 여러 데이터 센터에 걸쳐 규모를 늘리기 어렵다.
    - 지역마다 서버를 유연하게 늘리고 줄여야 하는데 전 세계 DB 서버 총합에 모든 설정이 묶여버림
- ID의 유일성은 보장되나, 그 값이 시간 흐름에 맞추어 커지도록 보장할 수 없다
    - 트래픽이 몰리는 노드가 다른 노드에 비해 더 큰 ID를 만들게 되기 때문
- 서버를 추가하거나 삭제할 때 잘 동작하도록 만들기 어렵다.
    - 기존 모든 서버의 증가 폭 규칙을 다 고쳐야 하기 때문에

## UUID
UUID는 컴퓨터 시스템에 저장되는 정보를 유일하게 식별하기 위한 128비트짜리 수다.
충돌 가능성이 극히 낮다. 때문에 서버 간 조율 없이 독립적으로 생성 가능하다.
각 웹 서버는 별도의 ID 생성해 독립적으로 ID를 만들어낼 수 있다 -> DB레벨과 무관.

장점:
- 단순하고 동기화 이슈도 없다.
- 각 서버가 독립적으로 ID를 만드는 구조여서 확장도 쉽다.

단점:
- 128비트로 너무 길다.
- 시간순 정렬이 불가능하다(랜덤 문자열이므로)
- 숫자가 아닌 값이 포함될 수 있다.

## 티켓 서버
auto_increment 기능을 갖춘 데이터베이스 서버(티켓 서버)를 중앙 집중형으로 하나만 사용하는 방식이다.

장점:
- 유일성이 보장되는 정렬 가능한 숫자 ID를 생성할 수 있음
- 구현이 쉽고, 중소 규모 애플리케이션에 적합하다.

단점:
- 티켓 서버가 SPOF가 된다. 이를 피하기 위해 티켓 서버를 여러대 준비한다면 동기화 문제가 생긴다.

**DB가 ID 생성의 주체가 되는 방식들은 다 별로인 것 같음. 통신을 해야되니까 너무 느리고 의존적인 것 같다**
DB는 전체 시스템에서 가장 비싸고, 확장 하기 어려운 병목임.
따라서 굳이 안 해도 되는 영역은 애플리케이션 레벨에서 처리하는 게 좋겠다.

## 트위터 스노플레이크 접근법
다음의 64비트 ID 구조를 사용한다
```text

 1bit          41bit              5bit        5bit        12bit
┌──────┬────────────────────────┬───────────┬───────────┬──────────────┐
│ Sign │       타임스탬프        │ 데이터센터 │  서버 ID  │   일련번호    │
└──────┴────────────────────────┴───────────┴───────────┴──────────────┘
```

타임스탬프 : 기원 시각 이후로 몇 밀리초가 경과했는지를 나타내는 값이다. 41비트를 할당받고있어 대략 69년 동안 초 단위의 시간 정보를 저장할 수 있다.
데이터센터/서버 ID : 각 5비트로 최대 32개의 데이터센터와 각 데이터센터마다 32대의 서버를 운영할 수 있다.
일련번호 : 각 서버에서 ID를 생성할 때마다 1만큼 증가시킨다. 타임스탬프가 바뀔 때마다 0으로 초기화됨

# 마무리
다음 문제를 더 논의해볼 수 있다.
- 시계 동기화
    - 컴퓨터 1대 안에서도 CPU 코어마다 초정밀 하드웨어 타이머가 각자 따로 돌아가기 때문에, 스레드가 다른 코어로 옮겨가는 순간 시간이 과거로 돌아가는 현상이 생겨 중복 ID가 만들어질 위험이 있다.
    - 이를 방어하는 로직이 스노플레이크 오픈소스 코드에 있음.
    - 모든 컴퓨터 메인보드에는 시간을 재는 부품이 있는데 이 차이떄문에 물리 서버마다 시간이 다를 수 있다.
        - 중복은 서버 ID때문에 안 생기지만 정렬시 타임스탬프가 꼬일 수 있음.
    - NTP는 이 문제를 해결하는 가장 보편적 수단이다.
        - 주기적으로 인터넷을 통해 표준시를 동기화하는 기술
- 각 ID 부분의 길이 최적화
    - 동시성이 낮고 수명이 긴 애플리케이션이라면 타임스탬프 절의 길이를 늘리고 일련번호 절의 길이를 줄이는 게 나을 수 있다.
