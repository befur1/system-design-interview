# 15장: 구글 드라이브 설계

## 파일 저장 및 동기화 서비스란?

파일을 클라우드에 저장하고, 같은 계정의 여러 단말에서 열거나 다른 사용자와 공유할 수 있게 하는 서비스다. 노트북에서 `보고서.pdf`를 수정하면 휴대폰에서도 변경된 버전을 볼 수 있어야 한다. 이전 버전이 필요하다면 갱신 이력에서 찾아 복원할 수 있어야 한다.

14장에서는 원본 영상 한 개로 여러 화질의 **재생용 파일**을 만들었다. 이번 장에서는 파일을 **여러 블록**으로 나누고, 버전마다 어떤 블록을 어떤 순서로 읽어야 하는지 기록한다. 이렇게 하면 파일 일부가 바뀌었을 때 전체를 다시 저장하거나 전송하는 비용을 줄일 수 있다.

## 1단계: 문제 이해 및 설계 범위 확정

### 요구사항

- 웹과 모바일에서 파일을 업로드하고 다운로드할 수 있어야 한다.
- 한 단말에서 추가하거나 수정한 파일이 다른 단말에도 동기화되어야 한다.
- 파일을 공유하고 이전 버전의 이력을 조회할 수 있어야 한다.
- 파일이 수정되거나 삭제되거나 새로 공유되면 관련 사용자에게 알려야 한다.
- 파일을 암호화하고, 파일 한 개의 최대 크기는 10GB로 가정한다.
- 파일 손실을 막고, 동기화 지연과 불필요한 네트워크 전송을 줄여야 한다.
- 일부 서버나 네트워크에 장애가 생겨도 계속 사용할 수 있어야 한다.

이번 설계에서는 파일 단위로 변경을 반영한다. 여러 사람이 같은 문서 안에서 문장을 동시에 수정하는 구글 문서의 실시간 공동 편집은 범위에서 제외한다.

### 개략적 규모 추정

가입 사용자 5,000만 명, 일간 활성 사용자 1,000만 명을 가정한다. 활성 사용자 한 명이 하루에 평균 2개의 파일을 업로드하고, 파일 평균 크기는 500KB다. 읽기와 쓰기의 비율은 1:1로 둔다.

| 항목 | 계산 | 추정치 |
| --- | --- | --- |
| 전체 저장 공간 할당량 | 5,000만 명 × 10GB | 500PB |
| 하루 업로드 건수 | 1,000만 명 × 2건 | 2,000만 건 |
| 하루 신규 업로드 데이터 | 2,000만 건 × 500KB | 약 10TB |
| 평균 업로드 QPS | 2,000만 건 ÷ 86,400초 | 약 231. 책에서는 약 240으로 추정 |
| 피크 업로드 QPS | 책의 평균 추정치 × 2 | 약 480 |

500PB는 모든 가입자가 무료 할당량을 전부 사용한다고 가정한 값이다. 실제 사용량은 사용자별 저장량과 버전 보존 정책에 따라 달라진다. 업로드 QPS도 파일 단위의 추정치다. 파일 하나를 이어 올리면서 여러 요청을 보내거나, 블록마다 저장소에 쓰면 실제 요청 수는 더 많아진다.

## 2단계: 개략적 설계안 제시 및 동의 구하기

### 한 대의 서버에서 시작하기

처음에는 웹 서버, MySQL, 파일을 보관할 디스크를 한 대에 둘 수 있다. `drive/user1/`처럼 사용자별 디렉터리를 만들고 그 아래에 파일을 저장한다. 여기서 **네임스페이스(namespace)**는 파일과 폴더의 경로를 해석하는 기준이 되는 공간이다. 서로 다른 사용자가 같은 `보고서.pdf`라는 이름을 써도 네임스페이스가 다르면 별개 파일로 찾을 수 있다.

파일이 늘어나면 한 대의 디스크 용량이 먼저 부족해질 수 있다. `user_id % 4`처럼 사용자별로 서버를 나누면 저장 공간을 늘릴 수 있지만, 각 서버에 파일 사본이 하나씩만 있다면 해당 서버가 고장 났을 때 그 파일을 제공할 수 없다. 샤딩은 서로 다른 데이터를 나누는 데 쓰고, 복제는 같은 데이터의 사본을 두어 장애에 대비하는 데 쓴다.

책에서는 파일 본문을 S3 같은 객체 저장소에 보관하고, API 서버와 메타데이터 DB를 분리한다. 로드밸런서 뒤에서 API 서버를 늘릴 수 있고, 메타데이터의 규모가 커지면 DB의 복제와 샤딩을 검토할 수 있다. 파일 블록도 필요한 복구 수준에 따라 같은 리전이나 다른 리전에 복제할 수 있다.

### 주요 API

| 기능 | 책의 경로 예시 | 처리 |
| --- | --- | --- |
| 파일 업로드 | `/files/upload?uploadType=resumable` | 이어 올리기 세션을 만들고 파일을 전송한다. |
| 파일 다운로드 | `/files/download` | 지정한 파일을 읽을 권한을 확인하고 데이터를 제공한다. |
| 갱신 이력 조회 | `/files/list_revisions` | 지정한 파일의 이전 버전 목록을 반환한다. |

작은 파일은 한 번의 요청으로 올릴 수 있다. 큰 파일은 먼저 이어 올리기 URL을 받고, 중단되면 서버에 성공적으로 저장된 위치를 확인한 뒤 그 지점부터 다시 보낸다. API는 HTTPS로 호출하고, 파일을 읽거나 수정할 때는 해당 파일에 대한 권한을 확인한다.

### 주요 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| 클라이언트 | 파일을 올리고, 변경된 블록을 받아 로컬 파일을 갱신한다. |
| API 서버 | 인증, 공유 권한, 파일·폴더의 메타데이터와 버전 이력을 관리한다. |
| 로드밸런서 | API 요청을 정상 서버로 분산한다. |
| 블록 저장소 서버 | 파일 분할, 블록 압축·암호화, 업로드와 다운로드를 처리한다. |
| 클라우드 저장소 | 실제 파일 블록을 객체로 보관한다. |
| 메타데이터 DB와 캐시 | 파일 경로, 최신 버전, 버전별 블록 순서 등을 관리하고 자주 쓰는 정보를 캐시한다. |
| 알림 서비스와 오프라인 사용자 큐 | 파일 변경을 관련 단말에 알리고, 연결되지 않은 단말이 나중에 변경을 확인할 수 있게 한다. |
| 아카이빙 저장소 | 오래 사용하지 않은 데이터나 이전 버전을 보관한다. |

## 3단계: 상세 설계

### 파일을 블록으로 나누는 이유

책에서는 파일을 최대 4MB 크기의 블록으로 나누고, 블록마다 해시값을 계산해 저장한다. 한 파일이 10개의 블록으로 구성되어 있고 2번과 5번 블록만 달라졌다면, 그 두 블록만 보내면 된다. 그대로인 나머지 블록은 새 버전에서도 재사용한다. 이 방식이 **델타 동기화(delta sync)**다.

| 파일 버전 | 블록 순서 |
| --- | --- |
| 버전 1 | `A → B → C → D` |
| 버전 2 | `A → X → C → D` |

이 예시에서는 버전 1을 가진 단말이 `X`만 내려받아 버전 2를 만들 수 있다. 서버도 기존의 `A`, `C`, `D`를 재사용하면 된다. 단, 사용자의 업로드 대역폭까지 줄이려면 클라이언트가 블록을 나누고 해시를 비교해 **어떤 블록을 보내야 하는지 전송 전에** 알아야 한다. 서버가 파일 전체를 받은 뒤 블록을 나누는 방식으로는 서버에서 저장소로 보내는 양을 줄일 수 있다.

책의 블록 저장소 서버는 블록을 압축한 뒤 암호화해 저장소로 보낸다. 텍스트처럼 압축 효과가 큰 파일도 있고, 이미 압축된 사진이나 영상처럼 효과가 작은 파일도 있다. 블록을 작게 잡으면 조금만 바뀐 파일에서 다시 보낼 양을 줄이기 쉽지만, 블록 수가 늘어 해시와 메타데이터 관리 비용이 커진다.

### 메타데이터 설계

| 테이블 | 보관하는 정보 |
| --- | --- |
| `user` | 사용자 ID, 이름, 계정 정보 |
| `device` | 사용자에 연결된 단말과 마지막 접속 정보 |
| `namespace` | 파일과 폴더가 속한 공간, 소유자와 공유 여부 |
| `file` | 파일 또는 폴더의 이름과 경로, 최신 버전 |
| `file_version` | 파일별 갱신 이력, 버전 번호, 변경한 단말 |
| `block` | 파일 버전에 속하는 블록과 그 순서 |

`file`은 지금 어떤 버전이 최신인지 알려주고, `file_version`은 이전 버전까지 남긴다. 특정 버전의 파일을 열려면 해당 버전이 참조하는 블록들을 순서대로 읽어야 한다. 실제 공유 권한을 관리하려면 어떤 사용자에게 읽기나 수정 권한을 주었는지도 별도로 기록해야 한다.

### 동기화 충돌 처리

노트북과 휴대폰이 모두 버전 3을 가지고 있다고 하자. 노트북에서 수정한 파일이 먼저 반영되면 서버의 최신 버전은 4가 된다. 이후 오프라인이었던 휴대폰이 버전 3을 기준으로 수정한 내용을 올리면 두 변경이 충돌한다.

책에서는 먼저 반영된 변경을 유지하고, 나중 요청에는 충돌이 생겼음을 알린다. 사용자는 서버의 최신 파일과 자신이 수정한 파일을 비교한 뒤, 하나를 택하거나 별도 파일로 보관할 수 있다.

구현할 때는 클라이언트가 **어느 버전을 기준으로 수정했는지** 함께 보내고, DB에서 최신 버전이 여전히 그 값일 때만 갱신하도록 할 수 있다. 두 요청이 동시에 최신 버전을 읽고 차례로 덮어쓰는 상황을 막으려면 버전 비교와 갱신을 원자적으로 처리해야 한다.

### 메타데이터의 일관성

파일의 최신 버전과 접근 권한은 이후 저장과 다운로드의 기준이 된다. 예를 들어 최신 버전이 4인데 캐시에 남은 버전 3을 기준으로 수정 요청을 처리하면, 이미 반영된 변경을 덮어쓸 수 있다.

책은 메타데이터에 관계형 DB를 사용한다. 한 트랜잭션에서 새 버전 기록과 최신 버전 참조를 함께 갱신하면, 파일이 아직 기록되지 않은 버전을 가리키는 상태를 방지할 수 있다. 캐시나 읽기 복제본에는 갱신 지연이 생길 수 있으므로, 최신 버전 확인과 권한 판단처럼 정확해야 하는 요청은 최신 상태를 보장하는 경로에서 처리할 필요가 있다.

오프라인 단말에는 이전 버전이 남아 있을 수 있다. 다시 연결되면 서버의 변경 내용을 받아 따라잡고, 로컬의 미전송 수정이 있으면 기준 버전을 비교해서 충돌 여부를 판단한다.

### 업로드 절차

1. 클라이언트가 API 서버에 새 파일의 메타데이터를 등록한다. API 서버는 파일을 `pending` 상태로 기록한다.
2. 파일을 전송하는 경로에서는 블록 저장소 서버가 파일을 나누고, 필요한 블록을 압축·암호화해 클라우드 저장소에 보낸다. 책에서는 메타데이터 등록과 파일 업로드를 병행할 수 있게 설계한다.
3. 파일 버전에 필요한 블록이 모두 저장되면 완료 콜백을 처리한다. API 서버는 버전과 블록 목록을 확정하고 업로드 상태를 `uploaded`로 바꾼다.
4. 알림 서비스는 같은 계정의 다른 단말이나 공유 대상에게 변경을 알린다. 책의 흐름처럼 처리 중 상태를 먼저 알릴 수 있고, 새 버전의 다운로드는 완료가 확인된 뒤 시작한다.

객체 저장소와 메타데이터 DB는 따로 동작한다. 파일을 다 올린 직후 API 서버가 종료되면 블록은 남아 있지만 상태는 `pending`일 수 있다. 같은 업로드 ID의 완료 요청을 재처리해도 버전이 한 번만 생성되도록 하고, 오래 남은 `pending` 항목은 저장된 블록을 확인해 복구할 수 있다.

### 다운로드와 단말 동기화

1. 단말이 변경 알림을 받으면 API 서버에 변경 내용을 요청한다.
2. API 서버가 현재 권한을 확인하고, 변경된 파일과 최신 버전의 블록 목록을 반환한다.
3. 단말은 이미 보유한 블록과 목록을 비교한다. 없는 블록만 블록 저장소 서버에 요청한다.
4. 필요한 블록을 모두 받으면 순서에 맞춰 파일을 재구성하고 로컬 파일을 갱신한다.

단말이 오프라인이면 책의 설계에서는 변경 정보를 큐에 보관하고 재접속했을 때 동기화한다. 구현할 때는 12장의 메시지 동기화처럼 단말별로 **마지막으로 반영한 변경 위치**를 기록할 수도 있다. 예를 들어 휴대폰이 변경 번호 40번부터 오프라인이었다면 재접속 후 40번 다음부터 조회한다. 이때 삭제도 변경 내역에 남겨야, 휴대폰에 남은 파일을 제대로 지울 수 있다.

### 알림 서비스와 롱 폴링

12장의 채팅은 사용자가 수시로 메시지를 보내고 받는다. 드라이브의 알림 경로는 서버가 단말에 파일 변경을 알려주는 일이 중심이다. 책에서는 이 용도에 롱 폴링을 선택한다.

1. 단말이 알림 서버에 변경 여부를 묻는 요청을 보낸다.
2. 서버는 변경이 없으면 잠시 응답을 보류한다. 변경이 생기거나 타임아웃이 되면 응답한다.
3. 단말은 변경 내용을 동기화하고 다음 알림 요청을 연다.

알림에는 어떤 파일이 바뀌었는지 알려주는 정보를 담고, 파일 자체는 별도의 다운로드 경로에서 받는다. 알림이 겹치거나 연결 중간에 빠질 수 있으므로 단말은 재접속 때 마지막으로 반영한 변경 위치를 기준으로 다시 확인할 수 있다.

### 저장 공간 절약

- **중복 제거**. 동일한 블록은 여러 버전에서 참조할 수 있게 한다. 버전 1을 삭제하더라도 버전 2가 같은 블록을 참조하면 그 블록은 유지한다.
- **버전 보존 정책**. 최근 버전은 촘촘하게 남기고, 오래된 버전은 개수나 기간을 기준으로 정리할 수 있다. 자주 수정하는 파일에 모든 버전을 계속 남길 때의 비용을 줄인다.
- **아카이빙**. 읽는 빈도가 낮은 이전 버전은 저렴한 저장소로 옮길 수 있다. 이전 버전을 복원할 때 어느 정도 기다려도 되는지에 따라 보관 위치를 정한다.

### 장애 처리

| 장애 | 대응 |
| --- | --- |
| 로드밸런서 또는 API 서버 장애 | 상태를 확인해 정상 인스턴스로 요청을 보내고, 필요하면 대기 중인 로드밸런서로 전환한다. |
| 블록 저장소 서버 장애 | 업로드 진행 상태를 확인하고, 다른 서버에서 미완료 블록을 이어 처리한다. |
| 객체 저장소의 리전 장애 | 복제가 끝난 블록은 다른 리전의 사본으로 제공한다. 최신 버전이 참조하는 모든 블록이 준비됐는지도 확인해야 한다. |
| 메타데이터 DB 장애 | 복제본으로 전환한다. 장애 직전의 변경이 복제됐는지 확인하고, 그 결과에 맞춰 최신 파일을 제공한다. |
| 알림 서버 또는 오프라인 큐 장애 | 단말이 연결을 다시 열고 마지막 동기화 위치부터 변경을 재조회한다. 동시에 재연결하는 단말이 몰리지 않도록 재시도 간격을 분산할 수 있다. |

## 4단계: 설계 후 추가로 고려할 사항

### 클라이언트가 저장소에 직접 업로드한다면?

14장의 미리 서명된 URL처럼, API 서버가 업로드를 승인하고 클라이언트가 파일 데이터를 객체 저장소에 직접 보내는 구조도 가능하다. 대용량 데이터를 블록 저장소 서버가 모두 전달하는 부담을 줄일 수 있다.

다만 클라이언트가 블록 분할, 압축, 암호화를 담당하면 웹·모바일·데스크톱이 같은 방식으로 블록을 만들도록 관리해야 한다. 파일 처리를 서버에 모으면 클라이언트 구현은 단순해지고, 서버는 파일 전송량과 처리 비용을 감당해야 한다. 어느 쪽이든 업로드 완료 확인과 최신 버전 반영은 서버에서 검증한다.

### 동기화 성능은 무엇으로 판단할까?

업로드 요청의 응답 시간만 재면 다른 단말에서 파일이 열리는 데 걸린 시간을 놓친다. 예를 들어 노트북에서 업로드가 끝난 뒤 휴대폰에 알림은 바로 도착해도, 변경된 블록을 다 받기까지 30초가 걸릴 수 있다. 업로드 완료 시간, 다른 단말 반영까지의 시간, 업데이트 한 건당 전송 바이트, 충돌 횟수를 함께 보면 병목을 구분할 수 있다.

## 생각해본 질문

### 파일을 4MB 단위로 자르면 한 글자를 추가할 때도 블록 하나만 바뀔까?

항상 그런 것은 아니다. 파일 앞부분에 한 바이트를 삽입하면 이후 데이터 위치가 한 칸씩 밀린다. 고정 위치에서 4MB마다 자르면 뒤쪽 내용이 거의 같아도 블록 경계가 달라져 많은 블록의 해시가 바뀔 수 있다.

데이터 내용에 따라 경계를 잡는 방법을 사용하면 삽입 지점 뒤에서 기존 경계와 다시 맞춰질 가능성이 있다. 블록을 비교하는 계산 비용이 생기므로, 파일이 얼마나 크고 어떤 방식으로 자주 수정되는지에 따라 효과가 달라진다.

### 두 기기가 같은 버전을 수정하면 마지막에 올린 파일을 최신 버전으로 두면 될까?

노트북과 휴대폰이 버전 3을 각각 수정했다고 하자. 노트북의 수정이 먼저 버전 4로 저장된 뒤 휴대폰 파일을 그대로 최신으로 덮으면, 두 수정이 다른 부분에 있었어도 노트북에서 변경한 내용이 사라질 수 있다.

휴대폰이 보낸 기준 버전이 여전히 3이라는 사실을 이용하면 서버가 충돌을 판별할 수 있다. 그 뒤 파일 형식상 병합할 수 있으면 병합을 시도하고, 병합 기준을 정하기 어려운 경우에는 두 사본을 남겨 사용자에게 선택권을 줄 수 있다.

### 변경 알림을 놓치면 다른 단말은 계속 예전 파일을 보게 될까?

알림을 변경 확인의 계기로 쓰고, 서버에 변경 내역을 별도로 남기면 복구할 수 있다. 단말은 연결할 때 마지막으로 반영한 위치 이후의 내역을 조회한다. 예를 들어 40번까지 반영한 단말이 41번 알림을 놓치고 42번 알림만 받았어도, 변경 내역 조회로 41번과 42번을 함께 가져올 수 있다.

변경 로그의 보존 기간보다 오래 오프라인이었다면, 단말의 파일 목록과 서버의 최신 목록을 비교해 다시 동기화할 수 있다.

### 파일의 이전 버전을 지울 때 그 버전의 블록도 전부 지워도 될까?

버전 1이 `A, B, C`를 사용하고 버전 2가 `A, X, C`를 사용한다면, 버전 1을 삭제할 때 `A`와 `C`도 지우면 버전 2를 열 수 없게 된다. 남겨둔 버전들이 어떤 블록을 참조하는지 확인하고, 어떤 버전도 사용하지 않는 블록만 정리해야 한다. 업로드 중이거나 새 버전에 연결될 블록도 정리 작업과 겹치지 않도록 관리할 필요가 있다.
