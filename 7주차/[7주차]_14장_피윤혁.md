# 유튜브 설계 (Design YouTube)

BLOB: 덩치 큰 이진 데이터 저장소

유튜브 설계에서 영상은 CDN이나 BLOB라는 저장소를 통해 저장한다.

→ 유튜브에서 하루에 올라오는 영상들은 어마어마 하기에, CDN이나  BLOB 저장소를 사용할 때 드는 비용을 생각해야한다.

→CDN과 같은 저장소는 아마존 클라우드 서비스나, 아카마이와 같은 외부 회사에서 만든걸 사용하자 ( 넷플릭스, 페이스북도 스스로 구축하지 않는다네?)

비디오 업로드

사용자가 비디오 업로드 할 때

→ 로드밸런서: API 서버 각각으로 고르게 요청 분산

→ API 서버는 비디오 스트리밍을 제외한 다른 요청을 처리

→ 메타데이터 데이터베이스는 영상에 대한 정보 ex). 썸네일, 업로더 정보 ,제목 등등을 저장하기 위해 샤딩과 다중화 사용

→ 메타데이터 캐시는: 유튜브 특성상 쓰기보다 읽기가 훨씬 많기에 , 그리고 인기 데이터에 몰리는 문제때문에 캐시가 필수다

→ 원본 저장소: 이진 데이터를 하나의 개체로 보관하는 데이터베이스 관리 시스템

→ 트랜스코딩 서버: 영상 원본을 BLOB 저장소에 저장한다면 , 원본에서 가져와서 여러 해상도로 변환한다.

→ 트랜스코딩 비디오 저장소: 트랜스코딩 완료된 비디오 즉 여러 해상도로 저장되는 BLOB 저장소다.

스트리밍 프로토콜

사용자는 영상을 틀었을 때, 대기 시간이 길어질 수록 영상의 이탈률이 크게 늘어난다. 따라서 이 대기 시간을 줄이기 위해서 용량이 큰 영상을 한번에 다 가져오는 것이 아니라, 나눠서 스트리밍 한다. 또한 시청자들의 비율중 앞부분만 보고 넘기는 사용자가 많기에 영상을 한번에 가져오지 않는다.

요즘 주로 쓰는 프로토콜의 방식

1. 트랜스코딩 단계에서 영상을 **화질별로 여러 벌** 만든다.(360p, 720p, 1080p 등).
2. 각 화질을 2~10초짜리 작은 조각으로 자른다.
3. 어떤 화질의 몇 번째 조각이 어디 있는지 적은 목록 파일(매니페스트)을 만들고
4. 플레이어는 목록 파일을 먼저 받고, 거기 적힌 대로 조각을 하나씩 HTTP로 받아 재생한다.

적응형 비트레이트(ABR): 핵심 기능

각 조각을 받을 때 사용자의 네트워크 속도를 측정한다. 와이파이가 빠르면 1080p 조각을, 지하철에서 느려지면 360p 조각을 받게해 영상이 끊기지 않게 조절하는 기능이 들어간다.

DAG는 Directed Acyclic Graph(방향성 비순환 그래프).

유튜브 설계에서는 **동영상 트랜스코딩 작업을 여러 단계로 쪼개고, 그 순서를 정하는 방식**

**이름 뜻부터 보면**

- **Graph(그래프)**: 작업(노드)들과 그 사이의 연결선(간선)
- **Directed(방향성)**: 연결선에 방향이 있고, “A가 끝나야 B를 할 수 있다”는 순서를 나타난다.
- **Acyclic(비순환)**: 화살표를 따라가도 다시 출발점으로 돌아오지 않기에 무한 반복 없이 작업이 언젠가 반드시 끝난다

**유튜브에서 왜 쓰나**

업로드된 원본 영상 하나로 할 일이 많음.

→ 화질별 인코딩, 썸네일 생성, 워터마크 넣기, 오디오 처리, 검사 등. 이걸 하나로 처리하면 너무 오래걸림

그래서 작업을 작은 단위로 나누고, 서로 의존하지 않는 작업은 **동시에 병렬로** 돌리고 의존 관계가 있는 작업만 순서를 지킨다

→ 이 작업 순서를 사용자가 직접 설정할 수 있는 것이 가장 큰 메리트이다.

클라이언트 프로그래머가 실행할 작업을 직접 정의할 수 있도록" DAG 모델을 쓴다.

인기 없던 비디오가 서버를 통해 재생하다가 갑작스럽게 너무 인기가 많아져 하루도 안돼서 조회수가 1억회 이상이 나온다면 바로 cdn으로 옮길 수 있나?

있다. 보통 이 전환이 수 분정도면 가능하다.

**어떻게 넘어가나: CDN 방식에 따라 다름**

1. **Pull 방식(가장 흔함)**: 시청자가 가까운 CDN 엣지 서버에 요청했는데 그 영상이 없으면(캐시 미스), 
엣지가 원본 서버에서 가져와서 저장한 뒤 보냄. 그다음부터 그 지역 요청은 엣지가 처리. 그래서 따로 옮기는 작업이 없고 인기가 생기면 요청이 들어오는 지역마다 자연스럽게 캐시가 채워짐
2. **Push 방식**: 시스템이 미리 CDN에 파일을 올려둬야 한다. 이 경우에는 **조회수 급증을 감지하는 모니터링**이 필요함. 예를 들어 "최근 10분 조회수가 평소의 100배 이상"이면 
자동으로 CDN에 밀어 넣는 식. 감지하고 업로드하는 데 시간이 조금 걸림.

근데 pull 방식에서

영상이 갑자기 뜨면 전 세계 수많은 엣지 서버가 **동시에 캐시 미스**를 내고, 한꺼번에 원본 서버로 요청이 들어올 수 있지 않을까?

실제로 가능하다

1. 그래서 같은 요청이 들어오면 합쳐서 요청을 줄이거나
2. 엣지 서버와 원본 사이에 계층을 만들어 원본의 요청은 1번만 이루어지고, 나머지는 중간계층을 통해 요청하도록 함.
3. 조각 단위 캐시: 영상을 조각으로 나눠 저장하기에 전체 파일을 다 받을때까지 기다리지 않게함.
4. 예측해서 CDN에 미리 올려두는 방법도 있음.
