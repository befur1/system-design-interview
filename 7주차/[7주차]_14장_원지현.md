# [7주차] 14장 정리 - 원지현
# 14장_ 유튜브 설계

## 설계 범위
- 비디오 업로드와 시청(스트리밍) 기능을 지원하며, 시청 중 화질을 바꿀 수 있어야 함.
- 모바일 앱, 웹, 스마트 TV를 모두 지원함.
- DAU 500만 명, 사용자 1명이 하루 평균 5개 시청, 10%는 하루 1개 업로드, 비디오 평균 크기 300MB로 가정함.
- 매일 필요한 저장 용량: 500만 × 10% × 300MB = 약 150TB
- CDN 비용: GB당 0.02달러로 가정하면 매일 약 15만 달러가 듦. → 비용 최적화가 중요한 설계 요소임.
- BLOB 저장소와 CDN은 직접 만들지 않고 클라우드 서비스를 활용함.

## 개략적 설계
- 클라이언트, CDN, API 서버로 구성됨.
    - CDN: 비디오를 저장하고, 재생 버튼을 누르면 CDN에서 스트리밍됨.
    - API 서버: 피드 추천, 업로드 URL 생성, 메타데이터 갱신, 회원가입 등 스트리밍을 제외한 모든 요청을 처리함.

비디오 업로드 절차
- 비디오 파일과 메타데이터는 두 갈래로 병렬 처리됨.
- 비디오 흐름: 원본 저장소 업로드 → 트랜스코딩 서버에서 변환 → 트랜스코딩 비디오 저장소 → CDN
- 메타데이터 흐름: 로드밸런서 → API 서버 → 메타데이터 캐시와 DB에 파일 이름, 크기, 포맷 등을 저장함.
- 트랜스코딩이 끝나면 완료 이벤트를 완료 큐에 넣고, 완료 핸들러가 메타데이터 DB와 캐시를 갱신함.

```
[비디오 흐름]
클라이언트
  → 원본 저장소
  → 트랜스코딩 서버
  → 트랜스코딩 비디오 저장소
  → CDN

[메타데이터 흐름] (비디오 흐름과 동시에 진행)
클라이언트 → 로드밸런서 → API 서버 → 메타데이터 DB·캐시

[두 흐름을 이어주는 부분]
트랜스코딩 완료 → 완료 큐 → 완료 핸들러 → 메타데이터 DB·캐시 갱신 (처리 중 → 재생 가능)
```

비디오 스트리밍 절차
- 비디오를 다 받은 뒤 재생하는 게 아니라, 스트리밍 프로토콜로 조금씩 받아 바로 재생함.
- 대표 프로토콜: MPEG-DASH, 애플 HLS, 마이크로소프트 스무드 스트리밍, 어도비 HDS
- 프로토콜마다 지원하는 인코딩과 플레이어가 다르므로, 서비스에 맞는 프로토콜을 골라야 함.

```
클라이언트 → API 서버: 영상 정보 요청
  → 메타데이터에서 화질별 CDN 주소 반환
클라이언트 → CDN: 조각 단위로 스트리밍 받으며 재생
```

## 상세 설계

비디오 트랜스코딩
- 원본 비디오를 다른 포맷과 비트레이트로 변환하는 과정임.
- 필요한 이유
    - 원본은 저장 공간을 많이 차지함.
    - 단말과 브라우저마다 지원하는 포맷이 다름.
    - 네트워크 상황에 따라 화질을 바꿔 끊김 없는 재생을 보장해야 함.
- 인코딩 포맷은 컨테이너(.mp4, .mov 등 파일을 담는 바구니)와 코덱(압축·압축 해제 알고리즘)으로 구성됨.

DAG 모델
- 원본을 비디오, 오디오, 메타데이터로 나눈 뒤, 인스펙션, 인코딩, 섬네일, 워터마크 같은 작업을 유향 비순환 그래프(DAG)로 정의함.
- 영상마다 필요한 작업만 골라 구성할 수 있고, 서로 의존하지 않는 작업은 병렬로 처리할 수 있음.

```
원본 비디오
 ├─ 비디오 → 인스펙션, 인코딩, 섬네일, 워터마크
 ├─ 오디오 → 오디오 인코딩
 └─ 메타데이터
      ↓ (각 결과를 모아서)
    병합 → 출력
```

트랜스코딩 아키텍처
- 전처리기: 비디오를 GOP 단위로 분할하고, 설정 파일에 따라 DAG를 생성하며, 분할된 데이터를 임시 저장소에 캐시함.
- DAG 스케줄러: DAG를 단계별 작업으로 나눠 자원 관리자의 작업 큐에 넣음.
- 자원 관리자: 작업 큐, 작업 서버 큐, 실행 중인 작업 큐를 두고, 우선순위가 가장 높은 작업을 가장 적합한 작업 서버에 할당함.
- 작업 서버: DAG에 정의된 인코딩, 섬네일, 워터마크 등의 작업을 실제로 수행함.
- 임시 저장소: 작은 메타데이터는 메모리에, 비디오와 오디오는 BLOB 저장소에 둠.

```
원본 비디오
  ↓
전처리기: GOP 분할, DAG 생성, 임시 저장소에 캐시
  ↓
DAG 스케줄러: DAG를 단계별 작업으로 나눠 작업 큐에 넣음
  ↓
자원 관리자: 우선순위 높은 작업을 꺼내 → 적합한 작업 서버 선택 → 실행 지시
  ↓
작업 서버: 인코딩, 섬네일, 워터마크 등 수행
  ↓
인코딩된 비디오 → 트랜스코딩 비디오 저장소
```

## 시스템 최적화

속도 최적화
- 클라이언트에서 비디오를 GOP 단위로 분할해 병렬로 업로드하고, 실패한 부분만 다시 올릴 수 있게 함.
- 업로드 센터를 사용자와 가까운 지역에 둬 전송 지연을 줄임.
- 단계 사이에 메시지 큐를 둬 앞 단계가 끝나길 기다리지 않고 병렬로 처리함.

안전성 최적화
- 사전 서명 URL: 클라이언트가 API 서버에 업로드 URL을 요청하면, API 서버가 권한이 부여된 URL을 발급하고 클라이언트는 그 URL로 저장소에 직접 업로드함.
- 저작권 보호: DRM(디지털 저작권 관리), AES 암호화, 워터마크를 사용함.

```
[사전 서명 URL 업로드]
① 클라이언트 → API 서버: 업로드 URL 요청 (POST)
② API 서버 → 클라이언트: 권한이 담긴 사전 서명 URL 발급
③ 클라이언트 → 원본 저장소: 발급받은 URL로 비디오 직접 업로드 (API 서버 거치지 않음)
```

비용 최적화
- 시청 수는 롱테일 분포를 따르므로, 인기 비디오만 CDN으로 제공하고 나머지는 자체 비디오 서버에서 제공함.
- 인기 없는 비디오는 미리 여러 버전으로 인코딩하지 않고, 짧은 영상은 필요할 때 인코딩함.
- 특정 지역에서만 인기 있는 비디오는 다른 지역 CDN으로 옮기지 않음.
- 규모가 커지면 ISP와 협력해 CDN을 직접 구축하는 것이 더 저렴할 수 있음.

```
재생 요청
 ├─ 인기 비디오 → CDN에서 제공
 └─ 비인기 비디오 → 자체 비디오 서버에서 제공
```

## 오류 처리
- 회복 가능한 오류(일부 구간 트랜스코딩 실패 등)는 재시도하고, 계속 실패하면 오류 코드를 반환함.
- 회복 불가능한 오류(잘못된 비디오 포맷 등)는 작업을 중단하고 오류 코드를 반환함.
- 무상태 API 서버는 다른 서버로 요청을 넘기고, 메타데이터 캐시와 DB는 다중화해 장애에 대비함.

## 마무리: 추가로 논의할 요소
- API 계층과 DB 계층의 규모 확장
- 라이브 스트리밍: 지연 시간이 더 짧아야 하고, 작은 단위로 실시간 처리하므로 병렬화 필요성이 낮고 오류 처리 방식도 달라짐.
- 저작권 침해, 음란물 등 부적절한 비디오의 삭제

## 더 생각해볼 점
적응형 비트레이트 스트리밍 (ABR)
- 같은 영상을 여러 화질로 미리 인코딩해 몇 초 단위 조각으로 나눠두고, 플레이어가 현재 네트워크 속도를 보며 다음 조각의 화질을 고르는 방식임.
- 유튜브에서 지하철에 들어가면 화질이 잠깐 떨어졌다가 다시 올라가는 이유이며, 트랜스코딩이 필요한 이유 중 "대역폭에 따른 화질 조정"이 바로 이거임.

resay에 적용해본다면
- 녹음 파일도 비디오처럼 크기가 클 수 있으므로, API 서버를 거치지 않고 사전 서명 URL로 저장소에 직접 업로드하면 서버 부담을 줄일 수 있음.
- 녹음 업로드 후 음성 인식, 분석, 보고서 생성처럼 오래 걸리는 작업은 트랜스코딩처럼 큐로 분리해 비동기로 처리하고, 메타데이터에 처리 중/완료 상태를 두어 화면에 "분석 중"을 보여주는 구조로 생각해볼 수 있음.
