# [7주차] 15장 정리 - 원지현
# 15장_ 구글 드라이브 설계

## 설계 범위
- 파일 업로드와 다운로드, 여러 단말 간 파일 동기화, 파일 갱신 이력 조회, 파일 공유를 지원함.
- 파일이 편집, 삭제, 공유되면 알림을 보냄.
- 구글 문서처럼 여러 사용자가 동시에 편집하는 기능은 다루지 않음.
- 파일 크기는 최대 10GB이며, 저장소의 파일은 암호화해야 함.
- 사용자 5천만 명, DAU 천만 명, 사용자당 10GB 무료 저장 공간 제공
- 필요한 저장 공간: 5천만 × 10GB = 500PB
- 업로드 QPS: 천만 × 하루 2회 / 86,400초 ≈ 초당 240건, 최대 약 480건

## 개략적 설계
- 처음에는 서버 한 대(웹 서버, DB, 파일 저장 디렉터리)로 시작하고, 저장 공간이 부족해지면 확장함.
- 확장 과정
    - 파일은 S3 같은 클라우드 저장소에 두고, 여러 지역에 다중화해 데이터 손실을 막음.
    - 로드밸런서와 여러 대의 웹 서버를 둬 트래픽을 분산함.
    - 메타데이터 DB는 다중화와 샤딩으로 가용성과 확장성을 확보함.

주요 API
- 파일 업로드: 작은 파일은 단순 업로드, 큰 파일은 중단된 지점부터 다시 올릴 수 있는 이어 올리기 사용
- 파일 다운로드: 파일 경로를 받아 해당 파일을 내려줌.
- 파일 갱신 이력: 파일 경로와 최대 개수를 받아 이전 버전 목록을 반환함.

동기화 충돌
- 두 사용자가 같은 파일을 동시에 수정하면, 먼저 처리된 변경이 반영되고 나중 변경은 충돌로 처리함.
- 충돌이 나면 두 버전을 모두 보관하고, 사용자가 직접 합치거나 하나를 선택하게 함.

```
사용자1, 사용자2가 같은 파일을 동시에 수정
  → 사용자1의 변경이 먼저 처리됨 → 반영
  → 사용자2의 변경 → 충돌 발생
  → 두 버전 모두 보관 → 사용자2가 직접 합치거나 선택
```

주요 컴포넌트
- 블록 저장소 서버: 파일을 블록으로 나눠 클라우드 저장소에 올림. 블록은 최대 4MB이며, 각 블록에는 고유한 해시 값이 할당됨.
- 클라우드 저장소: 블록 단위로 나뉜 파일을 저장함.
- 아카이빙 저장소(콜드 스토리지): 오랫동안 사용하지 않은 데이터를 저장함.
- 메타데이터 DB와 캐시: 사용자, 파일, 블록, 버전 정보를 저장함. 파일 자체는 클라우드에 두고 메타데이터만 관리함.
- 알림 서비스: 파일이 추가, 편집, 삭제되면 관련 클라이언트에게 알림.
- 오프라인 사용자 백업 큐: 접속하지 않은 클라이언트에 대한 변경 정보를 보관했다가, 접속하면 동기화하게 함.

```
클라이언트
 ├─ 파일 → 블록 저장소 서버 → 클라우드 저장소
 │                              └─ 오래 안 쓰면 → 콜드 스토리지
 └─ 그 외 요청 → 로드밸런서 → API 서버 → 메타데이터 캐시·DB
                                ↓
                           알림 서비스 → 다른 클라이언트
                                └─ 오프라인이면 → 오프라인 백업 큐에 보관
```

## 상세 설계

블록 저장소 서버
- 큰 파일을 수정할 때마다 전체를 전송하면 대역폭을 많이 쓰므로, 두 가지 최적화를 사용함.
    - 델타 동기화: 파일이 수정되면 수정된 블록만 동기화함.
    - 압축: 블록 단위로 압축하며, 텍스트와 이미지·비디오처럼 파일 유형에 따라 다른 압축 알고리즘을 사용함.
- 블록 저장소 서버에서 블록 분할, 압축, 암호화를 수행한 뒤 클라우드 저장소에 올림.

```
[처음 업로드]
파일 → 블록 분할 (최대 4MB, 블록마다 해시) → 압축 → 암호화 → 클라우드 저장소

[파일 수정 시]
블록별 해시 비교 → 바뀐 블록만 압축·암호화해 전송 (델타 동기화)
```

높은 일관성 요구사항
- 같은 파일이 단말마다 다르게 보이면 안 되므로 강한 일관성을 보장해야 함.
- 메모리 캐시는 보통 결과적 일관성을 따르므로, 캐시와 DB 원본이 일치하도록 DB가 바뀌면 캐시를 즉시 무효화함.
- ACID를 기본으로 보장하는 관계형 DB를 메타데이터 저장소로 사용함.

메타데이터 DB 주요 테이블
- user: 사용자 정보
- device: 단말 정보와 푸시 알림용 ID. 한 사용자가 여러 단말을 가질 수 있음.
- namespace: 사용자의 루트 디렉터리 정보
- file: 파일의 최신 정보
- file_version: 파일의 갱신 이력. 이력이 훼손되면 안 되므로 읽기 전용임.
- block: 파일 블록 정보. 블록들을 순서대로 조합하면 특정 버전의 파일을 복원할 수 있음.

업로드 절차
- 메타데이터 추가와 파일 업로드가 병렬로 진행됨.
- 메타데이터 흐름: 메타데이터를 상태 pending으로 저장하고, 알림 서비스가 다른 클라이언트에게 업로드 중임을 알림.
- 파일 흐름: 블록 저장소 서버가 블록 분할, 압축, 암호화 후 클라우드에 업로드하고, 완료 콜백을 받은 API 서버가 상태를 uploaded로 바꾸고 다른 클라이언트에게 알림.

```
[메타데이터 흐름]
클라이언트1 → API 서버
  → 메타데이터 DB에 저장 (상태: pending)
  → 알림 서비스 → 클라이언트2 "업로드 중"

[파일 흐름] (메타데이터 흐름과 동시에 진행)
클라이언트1 → 블록 저장소 서버 (분할·압축·암호화)
  → 클라우드 저장소
  → 완료 콜백 → API 서버
  → 메타데이터 DB 상태 변경 (상태: uploaded)
  → 알림 서비스 → 클라이언트2 "업로드 완료"
```

다운로드 절차
- 다른 클라이언트가 파일을 변경하면 알림 서비스가 알려주고, 접속 중이 아니면 변경 정보를 캐시에 보관했다가 접속 시 전달함.
- 클라이언트는 먼저 메타데이터를 받아 변경된 블록을 확인한 뒤, 해당 블록만 내려받아 파일을 재구성함.

```
알림 서비스 → 클라이언트2 "파일 변경됨"
  (오프라인이었다면 접속할 때 백업 큐에서 변경 정보 수신)
  → API 서버에 새 메타데이터 요청 → 메타데이터 DB 조회 → 반환
  → 메타데이터로 바뀐 블록 확인
  → 블록 저장소 서버에 블록 요청 → 클라우드 저장소에서 블록 반환
  → 클라이언트2가 블록을 순서대로 조합해 파일 재구성
```

알림 서비스
- 웹소켓 대신 롱 폴링을 사용함.
    - 채팅과 달리 양방향 통신이 필요 없고, 서버가 클라이언트에게 변경 사실만 알리면 됨.
    - 알림은 자주 발생하지 않고 한 번에 많은 데이터를 보낼 일도 없음.

저장소 공간 절약
- 중복 제거: 해시 값이 같은 블록은 같은 블록으로 판단해 한 번만 저장함.
- 지능적 백업: 보관할 파일 버전 수에 상한을 두고, 중요한 버전만 골라 저장함.
- 콜드 스토리지: 자주 쓰지 않는 데이터는 S3 Glacier처럼 저렴한 아카이빙 저장소로 옮김.

## 장애 처리
- 로드밸런서: 박동 신호로 장애를 감지하고 부 로드밸런서가 트래픽을 넘겨받음.
- 블록 저장소 서버: 다른 서버가 미완료 작업을 이어받음.
- 클라우드 저장소: 여러 지역에 다중화해 둔 데이터를 사용함.
- API 서버: 무상태이므로 다른 서버로 요청을 우회함.
- 메타데이터 DB: 주 서버가 죽으면 부 서버를 주 서버로 승격함.
- 알림 서비스: 서버 한 대가 많은 롱 폴링 연결을 유지하므로, 장애 시 모든 클라이언트가 다시 연결해야 해서 복구가 느림.

## 더 생각해볼 점

블록 서버를 거치지 않고 클라이언트가 직접 업로드하면?
- 14장 유튜브는 사전 서명 URL로 클라이언트가 저장소에 직접 업로드했는데, 구글 드라이브는 블록 저장소 서버를 거침.
- 직접 업로드하면 서버를 한 번 덜 거쳐 빠르지만, 블록 분할, 압축, 암호화 로직을 웹, 모바일, 데스크톱 클라이언트마다 각각 구현해야 함.
- 또 클라이언트는 조작될 수 있으므로, 암호화처럼 보안에 중요한 로직을 클라이언트에 맡기는 것은 위험함.
- 즉 유튜브는 원본만 올리면 서버가 트랜스코딩하니 직접 업로드가 적합하고, 구글 드라이브는 업로드 단계에서 보안 처리가 중요해 서버를 거치는 것이 적합함.

블록 크기는 어떻게 정할까?
- 블록이 작으면 수정된 부분만 정확히 보낼 수 있어 델타 동기화 효율이 좋지만, 블록 개수가 늘어 메타데이터와 해시 관리 부담이 커짐.
- 블록이 크면 메타데이터는 줄지만, 조금만 수정해도 큰 블록 전체를 다시 보내야 함.
- 책의 4MB는 이 둘 사이의 절충값임.

중복 제거의 범위
- 같은 해시의 블록을 사용자 구분 없이 전체에서 중복 제거하면 저장 공간을 더 아낄 수 있음.
- 하지만 업로드가 순식간에 끝나는지를 보고 다른 누군가가 이 파일을 이미 갖고 있다는 사실을 추측할 수 있어 개인정보 측면에서 위험할 수 있음.
- 그래서 중복 제거를 같은 계정 안으로 제한하는 것이 더 안전한 선택이 될 수 있음.
