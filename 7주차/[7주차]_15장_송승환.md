## 이 시스템에서 제공하는 API

### 1. 파일 업로드 API

단순 업로드: 파일 크기가 작을 때 사용

이어 올리기: 파일 사이즈가 크고 네트워크 문제로 업로드가 중단될 가능성이 높다고 생각되면 사용

```json
이어 올리기 API의 예시
https://api.example.com/files/upload?uploadType=resumable

인자
uploadType=resumable
data: 업로드할 로컬 파일
```

이어 올리기 URL을 받기 위한 최초의 요청 → 데이터를 업로드하고 업로드 상태 모니터링 → 업로드에 장애가 발생하면 장애 발생시점부터 업로드를 재시작

### 2. 파일 다운로드 API

```json
파일 다운로드 API의 예시
https://api.example.com/files/download

인자
path: 다운로드할 파일의 경로

{
	"path": "/recipes/soup/best_soup.txt"
}
```

### 3. 파일 갱신 히스토리 API

```json
파일 다운로드 API의 예시
https://api.example.com/files/list_revisions

인자
path: 갱신 히스토리를 가져올 파일의 경로
limit: 히스토리 길이의 최대치

{
	"path": "/recipes/soup/best_soup.txt",
	"limit": 20
}
```

위의 세 API는 HTTPS 프로토콜을 사용하여 클라이언트와 백엔드 서버가 주고받는 데이터를 보호하기 위한 것임

## 동기화 충돌

### 동기화 충돌 — 책이 참고문헌으로 넘긴 부분

책은 "먼저 처리된 변경이 이기고 나중 것은 충돌로 표시, 사용자에게 두 버전을 보여줘 고르게 함"까지만 말하고 해결 알고리즘은 [4][5]로 넘김. 찾아보니 네 갈래였음.

| 방식 | 핵심 | 쓰는 곳 |
| --- | --- | --- |
| **① 수동 해결** | 시스템이 해결을 포기하고 사람에게 넘김 | 책의 구글 드라이브, 드롭박스 |
| **② Last-Write-Wins** | 나중 것이 덮어씀 | 카산드라 기본값 |
| **③ Operational Transformation** | 뒤에 온 연산의 **위치를 보정**해서 적용 | 구글 Docs |
| **④ CRDT** | 자료구조 자체가 **합치는 순서와 무관**하게 설계됨 | Figma, Linear, Yjs |

①②는 **합치기를 포기**하는 쪽, ③④가 **진짜로 합치는** 쪽임.

**① 수동 해결** — 드롭박스에서 `문서 (철수의 충돌된 사본).docx`가 생기는 게 이거. 멍청해 보이지만 **이미지·zip 같은 바이너리는 자동으로 합칠 방법이 아예 없음.** 파일 단위 동기화엔 이게 현실적.

**③ OT** — 편집을 "연산"으로 표현하고 위치를 보정함.

```
원본 "ABC"
사용자1: 위치 0에 'X' 삽입
사용자2: 위치 2에 'Y' 삽입

그냥 적용하면
  1의 결과에 2의 연산 → "XAYBC"   ✗
  2의 결과에 1의 연산 → "XABYC"   ✓   양쪽이 갈라짐

OT: "위치 2에 Y"를 "위치 3에 Y"로 변환
  → 양쪽 다 "XABYC"
```

앞에 글자가 하나 끼어들었으니 위치를 한 칸 밀어주는 것. 대신 **연산 순서를 정해줄 중앙 서버가 필요**하고 구현이 악명 높게 까다로움.

**④ CRDT** — 핵심은 **위치를 숫자로 안 쓰는 것**. 글자마다 고유 ID를 붙이고 `"B 다음에 Y"`처럼 상대적으로 표현함. 앞에 뭐가 끼어들어도 "B 다음"은 그대로니까 순서가 섞여도 결과가 같아짐. 중앙 조율이 필요 없어 오프라인 편집에 강한데, 글자마다 ID를 들고 다녀서 **메타데이터가 커짐**.

## 블락 저장소 서버

큰 파일들은 업데이트가 일어날 때마다 전체 파일을 보내면 네트워크 대역폭을 많이 잡아 먹음

- 델타 동기화: 파일이 수정되면 수정이 일어난 블록만 동기화
- 압축: 블록 단위로 압축을 하면 데이터 크기를 많이 줄일 수 있음

이 시스템에서는 블록 단위로 압축을 하고 암호화를 진행함

## 높은 일관성 요구사항

이 시스템은 강한 일관성 모델을 기본으로 지원해야 함. 메모리 캐시는 보통 결과적 일관성 모델을 지원

강한 일관성을 달성하려면 다음 사항을 보장

- 캐시에 보관된 사본과 DB에 있는 원본이 일치
- DB에 보관된 원본에 변경이 발생하면 캐시에 있는 사본을 무효화

관계형 DB는 ACID를 보장하지만, NoSQL DB는 기본적으로 ACID를 지원하지 않아서 따로 프로그램을 설치해야 함

### 업로드 절차 (그림 15-9)

핵심은 **두 요청이 병렬로 나간다**는 것. 메타데이터 추가와 실제 파일 업로드가 별개 흐름임.

```
[① 메타데이터 흐름]

클라이언트1
   │ 1. 메타데이터 추가 요청
   ↓
 API 서버 ──2. 저장 (상태: pending)──→ 메타데이터 DB
   │
   │ 3. 통지
   ↓
알림 서비스 ──4. "업로드 중"──→ 클라이언트2

[② 파일 흐름]

클라이언트1
   │ 1. 파일 업로드
   ↓
블록 저장소 서버
   │ 2. 블록 분할 → 압축 → 암호화
   ↓
클라우드 저장소
   │ 3. 업로드 완료 콜백
   ↓
 API 서버 ──4. 상태 변경 (uploaded)──→ 메타데이터 DB
   │
   │ 5. 통지
   ↓
알림 서비스 ──6. "업로드 완료"──→ 클라이언트2
```

①과 ②는 **동시에** 출발함. 그래서 클라이언트2는 알림을 **두 번** 받음 — "올라가는 중"과 "다 올라감".

### 다운로드 절차 (그림 15-10)

파일이 추가/편집되면 시작됨. 먼저 **"변경이 있었다"를 어떻게 아느냐**가 선행 문제.

| 클라이언트 상태 | 알림 처리 |
| --- | --- |
| 접속 중 | 알림 서비스가 바로 알려줌 |
| 접속 중 아님 | 변경분을 캐시에 쌓아뒀다가, 접속되면 그때 가져감 |

```
알림 서비스
   │ 1. "파일 변경됨"
   ↓
클라이언트2
   │ 2. 새 메타데이터 요청
   ↓
 API 서버
   │ 3. 조회
   ↓
메타데이터 DB
   │ 4. 메타데이터 반환
   ↓
 API 서버
   │ 5. 메타데이터 반환
   ↓
클라이언트2
   │ 6. 블록 다운로드 요청
   ↓
블록 저장소 서버
   │ 7. 블록 요청
   ↓
클라우드 저장소
   │ 8. 블록 반환
   ↓
블록 저장소 서버
   │ 9. 블록 반환
   ↓
클라이언트2  →  블록 모아서 파일 재구성
```

**메타데이터 먼저, 블록은 그다음.** 메타데이터에 "이 파일이 어떤 블록들로 이뤄졌는지"가 들어있어서, 그걸 알아야 무슨 블록을 받을지 정할 수 있음.

### 왜 상태를 `pending` → `uploaded` 2단계로 쪼개나

메타데이터 등록과 실제 업로드가 **병렬**이라, 그 사이에 "파일은 존재하는데 내용은 아직 없는" 구간이 생김. 이 구간을 `pending`으로 명시해두면

- 다른 클라이언트가 **반쯤 올라간 파일을 내려받는 사고**를 막을 수 있음
- 업로드가 중간에 실패하면 `pending`으로 남아서 **정리 대상인지 바로 구분**됨

상태를 안 두면 "메타데이터는 있는데 블록이 없는 파일"을 정상 파일과 구별할 방법이 없음.

### 14장이랑 겹치는 구조

유튜브 비디오 업로드도 똑같은 모양이었음.

|  | 14장 유튜브 | 15장 구글 드라이브 |
| --- | --- | --- |
| 병렬 흐름 1 | 메타데이터 업데이트 | 메타데이터 추가 (`pending`) |
| 병렬 흐름 2 | 비디오 → 트랜스코딩 → CDN | 파일 → 블록 분할·압축·암호화 → 클라우드 저장소 |
| 완료 신호 | 완료 큐 | 완료 콜백 → 상태 `uploaded` |

**무거운 데이터와 가벼운 메타데이터를 분리해서 병렬로 처리하고, 무거운 쪽이 끝나면 콜백으로 상태를 맞춘다** — 이 패턴이 두 장에 걸쳐 똑같이 나옴. 10장 알림 시스템에서 제3자 서비스 호출을 비동기로 떼어낸 것도 결이 같음.

## 알림 서비스 및 저장소 절약

알림 서비스에서는 소켓 대신에 롱 폴링을 사용함

→ 채팅 서비스와 달리, 양방향 서비스/실시간성이 필요하지 않기 때문에

저장소 절약을 위해서

1. 파일 블록 중복을 제거
2. 백업 때문에 보관해야 하는 파일 버전 개수에 상한을 두어, 가장 오래된 버전을 하나씩 버림
3. 하나 고친 것도 버전으로 저장하면 불필요한 버전들이 많이 생성됨. 이를 방지하고자 중요한 것만 골라서 버전으로 생성해야함

## 장애 처리

| 컴포넌트 | 장애 시 대응 |
| --- | --- |
| **로드밸런서** | 부(secondary) LB가 대신 트래픽을 받음. LB끼리 **박동(heartbeat)** 신호를 주고받다가, 일정 시간 응답이 없으면 장애로 간주 |
| **블록 저장소 서버** | 다른 서버가 **미완료·대기 상태의 작업을 이어받음** |
| **클라우드 저장소** | S3 버킷을 여러 **지역(region)에 다중화**해 뒀으니 다른 지역에서 가져옴 |
| **API 서버** | **무상태(stateless)**라 LB가 알아서 다른 서버로 우회시킴. 파일 처리에 영향 없음 |
| **메타데이터 캐시** | 캐시 서버도 다중화. 다른 노드에서 가져오고, 죽은 노드는 새 서버로 교체 |
| **메타데이터 DB (주)** | 부 서버 중 하나를 **주로 승격**하고, 빈 부 서버 자리를 새로 하나 채움 |
| **메타데이터 DB (부)** | 다른 부 서버가 읽기를 받고, 죽은 서버는 교체 |
| **알림 서비스** | 아래 따로 |
| **오프라인 사용자 백업 큐** | 큐도 다중화. 장애 나면 구독 중인 클라이언트들이 **백업 큐로 구독을 재설정** |

### 알림 서비스만 결이 다름

나머지는 전부 "다중화해 뒀으니 옆에것 쓰면 됨"인데, 여기만 그게 안 통함.

- 접속 중인 모든 사용자가 **롱 폴링 연결을 붙잡고 있음**
- 드롭박스 자료 기준 **서버 한 대가 100만 개 이상 연결을 유지**
- 서버 한 대가 죽으면 그 100만 명이 **전부 동시에 연결을 다시 맺어야 함**
- 100만 개를 *유지*하는 건 되지만 100만 개를 동시에 *새로 맺는* 건 불가능 → **복구가 느림**

**연결을 들고 있는 서버는 상태를 들고 있는 것**이라 무상태 서버처럼 그냥 갈아끼울 수가 없음. 그래서 연결을 복구하는데 오래 걸림,,
