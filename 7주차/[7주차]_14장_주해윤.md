## 14장 유튜브 설계

---

> 유튜브와 같은 비디오 스트리밍 서비스의 핵심 기능인 비디오 업로드와 재생을 중심으로 시스템을 설계한다.
> 

### 문제 이해 및 설계 범위 확정

- 주요 기능
    - 빠른 비디오 업로드
    - 원활한 비디오 재생
    - 재생 품질 선택
    - 낮은 인프라 비용
    - 높은 가용성, 규모 확장성, 안정성
- 지원 클라이언트
    - 모바일 앱
    - 웹 브라우저
    - 스마트 TV
- 어떤 언어로도 이용 가능해야 함
- 현존하는 비디오 종류와 해상도를 대부분 지원
- 비디오 암호화 필요
- 작은 비디오 또는 중간 크기 비디오에 초점을 맞춤
- 비디오 크기는 최대 1GB로 제한
- 기존 클라우드 서비스 활용 가능
- 핵심 기능
    - 비디오 업로드
    - 비디오 시청

**유튜브 관련 통계**

- 월간 능동 사용자 수: 20억 명
- 매일 재생되는 비디오 수: 50억 개
- 미국 성인 가운데 73%가 유튜브 이용
- 창작자 수: 5천만 명
- 2019년 광고 수입: 151억 달러
    - 2018년 대비 36% 증가
- 모바일 인터넷 트래픽 가운데 유튜브가 차지하는 비율: 37%
- 80개 언어로 이용 가능

**개략적 규모 추정**

- 일간 능동 사용자 수: 5백만 명
- 한 사용자는 하루 평균 5개의 비디오 시청
- 사용자의 10%가 하루에 비디오 1개 업로드
- 비디오 평균 크기: 300MB
- 매일 새로 요구되는 비디오 저장 용량
    
    `5백만 × 10% × 300MB = 150TB`
    
- CDN 비용
    - 클라우드 CDN을 통해 비디오를 서비스하면 CDN에서 나가는 데이터의 양에 따라 과금
    - 1GB당 요금을 0.02달러로 가정
    - 매일 발생하는 비용
        
        `5백만 × 5개 × 0.3GB × $0.02 = $150,000`
        

→ CDN을 통해 비디오를 서비스하면 비용이 매우 크므로 비용을 줄이는 방법을 고려해야 함

### 개략적 설계안 제시 및 동의 구하기

- CDN과 BLOB 저장소는 기존 클라우드 서비스를 활용
- 규모 확장이 쉬운 BLOB 저장소나 CDN을 직접 구축하는 것은 복잡하고 많은 비용이 들기 때문
- 개략적으로 시스템은 세 가지 컴포넌트로 구성됨
    - 단말
    - CDN
    - API 서버

```
사용자 단말
├─ 비디오 스트리밍 요청 ─────────────→ CDN
└─ 그 외 요청 ─→ 로드밸런서 ─→ API 서버
                                  ├─ 메타데이터 캐시
                                  └─ 메타데이터 데이터베이스
```

- 단말
    - 컴퓨터, 모바일 폰, 스마트 TV를 통해 비디오 시청
- CDN
    - 비디오를 저장
    - 사용자가 재생 버튼을 누르면 CDN으로부터 스트리밍
- API 서버
    - 비디오 스트리밍을 제외한 모든 요청 처리
    - 피드 추천
    - 비디오 업로드 URL 생성
    - 메타데이터 데이터베이스와 캐시 갱신
    - 사용자 가입

**설계할 주요 영역**

1. 비디오 업로드 절차
2. 비디오 스트리밍 절차

### 상세 설계

#### 1. 비디오 업로드

**주요 컴포넌트**

- 사용자
    - 컴퓨터, 모바일 폰, 스마트 TV를 통해 비디오를 이용
- 로드밸런서
    - 요청을 API 서버에 고르게 분산
- API 서버
    - 비디오 스트리밍을 제외한 요청 처리
- 메타데이터 데이터베이스
    - 비디오의 메타데이터 보관
    - 샤딩과 다중화를 적용하여 성능 및 가용성 요구사항 충족
- 메타데이터 캐시
    - 비디오 메타데이터와 사용자 객체를 캐시
- 원본 저장소
    - 원본 비디오를 보관하는 BLOB 저장소
- 트랜스코딩 서버
    - 비디오의 포맷을 변환하여 단말이나 대역폭 요구사항에 맞는 비디오 스트림 생성
- 트랜스코딩 비디오 저장소
    - 트랜스코딩이 완료된 비디오를 저장하는 BLOB 저장소
- CDN
    - 트랜스코딩된 비디오를 캐시하고 스트리밍
- 트랜스코딩 완료 큐
    - 비디오 트랜스코딩 완료 이벤트를 보관하는 메시지 큐
- 트랜스코딩 완료 핸들러
    - 완료 이벤트를 큐에서 꺼내 메타데이터 캐시와 데이터베이스 갱신

```
사용자 단말
    │
    ▼
로드밸런서
    │
    ▼
API 서버
├─ 메타데이터 캐시
├─ 메타데이터 데이터베이스
└─ 원본 저장소
       │
       ▼
트랜스코딩 서버
├─ 트랜스코딩 비디오 저장소 ─→ CDN
└─ 트랜스코딩 완료 큐
       │
       ▼
트랜스코딩 완료 핸들러
       ├─ 메타데이터 캐시 갱신
       └─ 메타데이터 데이터베이스 갱신
```

**비디오 업로드 처리 흐름**

1. 비디오를 원본 저장소에 업로드
2. 트랜스코딩 서버가 원본 저장소에서 비디오를 가져와 트랜스코딩 시작
3. 트랜스코딩이 완료되면 다음 두 절차를 병렬로 수행
    - 완료된 비디오를 트랜스코딩 비디오 저장소에 업로드
    - 트랜스코딩 완료 이벤트를 완료 큐에 저장
4. 트랜스코딩이 끝난 비디오를 CDN에 업로드
5. 완료 핸들러가 큐에서 이벤트 데이터를 꺼냄
6. 완료 핸들러가 메타데이터 데이터베이스와 캐시 갱신
7. API 서버가 단말에 비디오 업로드가 끝나 스트리밍 준비가 되었음을 알림

```
원본 비디오 업로드
        ↓
원본 저장소
        ↓
트랜스코딩 서버
        ├─→ 트랜스코딩 비디오 저장소 ─→ CDN
        │
        └─→ 트랜스코딩 완료 큐
                    ↓
           트랜스코딩 완료 핸들러
                    ├─→ 메타데이터 캐시
                    └─→ 메타데이터 데이터베이스
```

**메타데이터 갱신**

- 원본 저장소에 비디오를 업로드하는 동안 단말은 별도로 메타데이터 갱신 요청을 API 서버에 전송
- 메타데이터
    - 파일 이름
    - 크기
    - 포맷
    - 사용자 정보
- API 서버는 전달받은 정보로 메타데이터 캐시와 데이터베이스 갱신

```
사용자 단말
    │ 메타데이터 갱신 요청
    ▼
로드밸런서
    ▼
API 서버
├─ 메타데이터 캐시
└─ 메타데이터 데이터베이스
```

#### 2. 비디오 스트리밍

- 다운로드
    - 비디오를 단말로 내려받은 뒤 재생
- 스트리밍
    - 원격지에서 비디오 스트림을 지속적으로 전송받아 즉시 재생
    - 비디오 전체가 다운로드될 때까지 기다릴 필요가 없음
- 비디오는 사용자와 가까운 CDN 엣지 서버에서 전송되어 전송 지연이 낮음

```
사용자 단말
    │ 스트리밍 요청
    ▼
가장 가까운 CDN 엣지 서버
    │ 비디오 스트림
    ▼
사용자 단말에서 재생
```

**스트리밍 프로토콜**

- 비디오 스트리밍을 위해 데이터를 전송할 때 사용하는 표준화된 통신 방법
- 프로토콜마다 지원하는 비디오 인코딩과 플레이어가 다르므로 용도에 맞는 프로토콜을 선택해야 함
- 널리 사용되는 프로토콜
    - MPEG-DASH
        - Dynamic Adaptive Streaming over HTTP
    - 애플 HLS
        - HTTP Live Streaming
    - Microsoft Smooth Streaming
    - Adobe HTTP Dynamic Streaming
        - HDS

#### 3. 비디오 트랜스코딩

- 비디오를 녹화하면 단말은 특정 포맷으로 저장
- 다양한 단말에서 원활하게 재생하려면 여러 비트레이트와 포맷으로 변환해야 함
- 비트레이트
    - 비디오를 구성하는 비트가 얼마나 빨리 처리되어야 하는지를 나타내는 단위
    - 비트레이트가 높은 비디오는 일반적으로 고화질
    - 정상 재생을 위해 더 높은 성능과 빠른 인터넷 회선 필요

**트랜스코딩이 필요한 이유**

- 가공되지 않은 원본 비디오는 저장 공간을 많이 차지함
- 단말과 브라우저별로 지원하는 비디오 포맷이 다름
- 네트워크 대역폭에 따라 서로 다른 화질을 제공해야 함
    - 대역폭이 부족한 사용자에게 저화질 비디오 제공
    - 대역폭이 충분한 사용자에게 고화질 비디오 제공
- 모바일 네트워크 상황은 계속 변할 수 있으므로 화질을 자동 또는 수동으로 변경할 수 있어야 함

**인코딩 포맷**

- 컨테이너
    - 비디오 파일, 오디오, 메타데이터를 담는 바구니
    - `.avi`, `.mov`, `.mp4` 등의 파일 확장자
- 코덱
    - 비디오 화질을 보존하면서 파일 크기를 줄이기 위한 압축 및 압축 해제 알고리즘
    - H.264
    - VP9
    - HEVC

**트랜스코딩 작업**

- 검사
    - 비디오 품질과 손상 여부 확인
- 비디오 인코딩
    - 다양한 해상도, 코덱, 비트레이트 조합으로 인코딩
- 섬네일 추출
    - 업로드한 이미지나 비디오에서 섬네일 생성
- 워터마크
    - 비디오 식별 정보를 이미지 위에 오버레이 형태로 표시
- 오디오 인코딩
- 비디오와 오디오 병합
- 메타데이터 추출

```
                         ┌─ 검사
                         ├─ 비디오 인코딩
원본 비디오 ─→ 비디오 ──┼─ 섬네일 추출
      │                  └─ 워터마크
      │
      ├─→ 오디오 ─→ 오디오 인코딩 ─┐
      │                              ├─→ 병합
      └─→ 메타데이터                 │
                                     ┘
```

- 하나의 비디오를 다양한 해상도로 인코딩할 수 있음

```
비디오 인코더
├─ 360p.mp4
├─ 480p.mp4
├─ 720p.mp4
├─ 1080p.mp4
└─ 4k.mp4
```

#### 4. 유향 비순환 그래프(DAG) 모델

- 비디오 트랜스코딩은 많은 컴퓨팅 자원과 시간이 필요한 작업
- 콘텐츠 창작자마다 서로 다른 비디오 처리 요구사항을 가질 수 있음
    - 워터마크 추가
    - 직접 만든 섬네일 사용
    - 고화질 또는 저화질 비디오 선호
- 서로 다른 처리 파이프라인을 지원하고 병렬성을 높이기 위해 DAG 프로그래밍 모델 도입
- 클라이언트 프로그래머가 실행할 작업을 정의할 수 있음
- 작업을 순차적 또는 병렬적으로 실행 가능

```
원본 비디오
├─ 1단계
│  ├─ 비디오 추출
│  ├─ 오디오 추출
│  └─ 메타데이터 추출
│
└─ 2단계
   ├─ 비디오 인코딩
   ├─ 섬네일 생성
   └─ 오디오 인코딩
```

**트랜스코딩 아키텍처**

```
전처리기
   ↓
DAG 스케줄러
   ↓
자원 관리자
   ↓
작업 실행 서버
   ↓
인코딩된 비디오

전처리기·작업 실행 서버
   ↕
임시 저장소
```

- 전처리기
- DAG 스케줄러
- 자원 관리자
- 작업 실행 서버
- 임시 저장소

**전처리기**

1. 비디오 분할
    - 비디오 스트림을 GOP 단위로 분할
    - GOP는 특정 순서로 배열된 프레임 그룹
    - 각각 독립적으로 재생 가능하며 보통 몇 초 길이
    - 오래된 단말이나 브라우저가 GOP 단위 분할을 지원하지 않으면 전처리기가 대신 분할
2. DAG 생성
    - 클라이언트 프로그래머가 작성한 설정 파일을 기준으로 DAG 생성
3. 데이터 캐시
    - 분할된 비디오의 캐시 역할
    - GOP와 메타데이터를 임시 저장소에 보관
    - 인코딩 실패 시 임시 저장된 데이터를 사용해 작업 재개

**DAG 스케줄러**

- DAG 그래프를 여러 단계로 분할
- 각 단계를 자원 관리자의 작업 큐에 등록

```
전처리기
    ↓
DAG 스케줄러
    ↓
1단계: 비디오·오디오·메타데이터 분리
    ↓
2단계: 비디오 인코딩·섬네일·오디오 인코딩
```

**자원 관리자**

- 자원을 효율적으로 배분
- 작업 큐
    - 실행할 작업을 보관하는 우선순위 큐
- 작업 서버 큐
    - 작업 서버의 가용 상태를 보관하는 우선순위 큐
- 실행 큐
    - 현재 실행 중인 작업과 작업 서버 정보를 보관
- 작업 스케줄러
    - 최적의 작업과 서버 조합 선택
    - 작업 서버에 작업 실행 지시

**자원 관리자 동작**

1. 작업 큐에서 가장 높은 우선순위의 작업을 꺼냄
2. 작업에 적합한 작업 서버를 선택
3. 작업 서버에 작업 실행을 지시
4. 작업과 서버의 할당 정보를 실행 큐에 저장
5. 작업이 완료되면 실행 큐에서 제거

```
작업 큐 ───────────────┐
작업 서버 큐 ─────────┼─→ 작업 스케줄러 ─→ 작업 서버
실행 큐 ← 작업·서버 정보┘
```

**작업 서버**

- DAG에 정의된 작업을 수행
- 작업 종류에 따라 별도의 작업 서버로 구분
    - 워터마크
    - 인코딩
    - 섬네일
    - 병합

**임시 저장소**

- 데이터의 유형, 크기, 이용 빈도, 유효기간 등을 기준으로 저장소 선택
- 메타데이터
    - 작업 서버가 자주 참조하며 크기가 작으므로 메모리에 캐시 가능
- 비디오와 오디오
    - BLOB 저장소에 보관
- 비디오 처리가 끝나면 임시 저장 데이터 삭제

#### 5. 시스템 최적화

**속도 최적화: 비디오 병렬 업로드**

- 한 번에 비디오 전체를 업로드하면 비효율적
- 비디오를 작은 GOP 단위로 분할하여 병렬로 업로드
- 일부 업로드에 실패해도 실패한 부분만 다시 업로드 가능
- GOP 경계에 따라 비디오를 분할하는 작업은 단말에서 수행

```
원본 비디오
    ↓ GOP 경계에 따라 분할
GOP 1 ─┐
GOP 2 ─┼─ 병렬 업로드 ─→ 원본 저장소
  ...  │
GOP N ─┘
```

**속도 최적화: 업로드 센터를 사용자 근거리에 지정**

- 여러 지역에 업로드 센터를 배치
- 사용자가 가까운 업로드 센터에 비디오를 업로드하도록 함
    - 미국 사용자는 북미 업로드 센터 이용
    - 중국 사용자는 아시아 업로드 센터 이용
- CDN을 업로드 센터로 이용

**속도 최적화: 모든 절차 병렬화**

- 절차 사이의 의존성이 있으면 병렬성을 높이기 어려움
- 메시지 큐를 이용해 시스템의 결합도를 낮춤

**메시지 큐 도입 전**

```
원본 저장소
    ↓
다운로드 모듈
    ↓
인코딩 모듈
    ↓
업로드 모듈
    ↓
인코딩 비디오 저장소
    ↓
CDN
```

- 인코딩 모듈은 다운로드 모듈의 작업이 끝날 때까지 기다려야 함

**메시지 큐 도입 후**

```
원본 저장소
    ↓
메시지 큐
    ↓
다운로드 모듈
    ↓
메시지 큐
    ↓
인코딩 모듈
    ↓
메시지 큐
    ↓
업로드 모듈
    ↓
인코딩 비디오 저장소
    ↓
CDN
```

- 다운로드 모듈의 모든 작업이 끝날 때까지 인코딩 모듈이 기다릴 필요가 없음
- 큐에 보관된 이벤트를 여러 인코딩 모듈이 병렬로 처리 가능

**안전성 최적화: 미리 사인된 업로드 URL**

- 허가받은 사용자만 지정된 위치에 비디오를 업로드하도록 함
- 업로드 절차
    1. 클라이언트가 HTTP 서버에 `POST /upload` 요청을 보내 미리 사인된 URL을 받음
    2. API 서버가 미리 사인된 URL 반환
    3. 클라이언트가 해당 URL이 가리키는 위치에 비디오 업로드

```
사용자 단말 ── 1. POST /upload ──→ API 서버
사용자 단말 ←─ 2. 미리 사인된 URL ─ API 서버
사용자 단말 ── 3. 비디오 업로드 ─→ 원본 저장소
```

**안전성 최적화: 비디오 보호**

- DRM 시스템 도입
    - 애플 FairPlay
    - 구글 Widevine
    - 마이크로소프트 PlayReady
- AES 암호화
    - 비디오를 암호화하고 접근 권한 설정
    - 재생 시에만 복호화
    - 허락된 사용자만 비디오 시청 가능
- 워터마크
    - 소유자 정보를 포함하는 이미지 오버레이
    - 회사 로고나 이름 등에 활용

**비용 최적화**

- CDN은 시스템의 핵심이지만 데이터가 클수록 비용 증가
- 비디오 스트리밍은 롱테일 분포를 따름
    - 인기 있는 비디오는 빈번하게 재생
    - 나머지 비디오는 보는 사람이 거의 없음
- 최적화 방안
    1. 인기 비디오는 CDN을 통해 재생하고 나머지 비디오는 비디오 서버에서 재생
    2. 인기가 낮은 비디오는 인코딩하지 않고 필요할 때 인코딩
    3. 특정 지역에서만 인기 있는 비디오는 다른 지역으로 옮길 필요가 없음
    4. CDN을 직접 구축하고 ISP와 제휴할 수 있으나 초대형 프로젝트에 해당

```
사용자 단말
├─ 인기 비디오 ─→ CDN
└─ 나머지 비디오 ─→ 비디오 서버
```

#### 6. 오류 처리

- 대형 시스템에서 오류는 불가피
- 장애를 잘 감내하는 시스템을 만들려면 오류를 우아하게 처리하고 빠르게 복구해야 함

**오류 유형**

- 회복 가능 오류
    - 특정 비디오 세그먼트의 트랜스코딩 실패 등
    - 몇 번 재시도하여 해결
    - 계속 실패하면 클라이언트에 적절한 오류 코드 반환
- 회복 불가능 오류
    - 잘못된 비디오 포맷 등
    - 비디오 관련 작업 중단
    - 클라이언트에 적절한 오류 코드 반환

**컴포넌트별 오류 처리**

- 업로드 오류
    - 몇 번 재시도
- 비디오 분할 오류
    - 오래된 클라이언트가 GOP 경계에 따라 분할하지 못하면 전체 비디오를 서버로 전송하고 서버가 분할
- 트랜스코딩 오류
    - 재시도
- 전처리 오류
    - DAG 그래프 재생성
- DAG 스케줄러 오류
    - 작업 재스케줄링
- 자원 관리자 큐 장애
    - 사본 이용
- 작업 서버 장애
    - 다른 서버에서 작업 재시도
- API 서버 장애
    - 무상태 서버이므로 신규 요청을 다른 API 서버로 우회
- 메타데이터 캐시 서버 장애
    - 데이터가 다중화되어 있으므로 다른 노드에서 데이터를 가져옴
    - 장애가 난 캐시 서버 교체
- 메타데이터 데이터베이스 서버 장애
    - 주 서버 장애: 부 서버 가운데 하나를 주 서버로 교체
    - 부 서버 장애: 다른 부 서버를 통해 읽기 처리 후 장애 서버 교체

#### 마무리

- API 계층
    - 무상태 서버이므로 수평적 규모 확장 가능
- 데이터베이스 계층
    - 다중화와 샤딩을 통해 규모 확장
- 라이브 스트리밍
    - 비디오를 실시간으로 녹화하고 방송하는 절차
    - 일반 비디오 스트리밍과 마찬가지로 업로드, 인코딩, 스트리밍 필요
    - 더 낮은 응답 지연 필요
    - 작은 단위의 데이터를 실시간으로 처리해야 하므로 병렬화 필요성이 높음
    - 시간이 많이 걸리는 오류 처리 방법은 사용하기 어려움
- 비디오 삭제
    - 저작권 위반 비디오
    - 선정적 비디오
    - 불법 행위 관련 비디오
    - 업로드 과정에서 식별하거나 사용자 신고를 통해 판별 가능
