# [7주차] 15장 - 구글 드라이브 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

14장과 나란히 읽으니 구도가 보였다. **유튜브는 여러 사람이 한 영상을 보기 위한 설계고, 구글 드라이브는 한 사람이 여러 기기에서 꺼내 보기 위한 설계였다.** 책의 규모 추정이 그걸 그대로 말해준다. 14장은 읽기가 압도적인데 15장은 읽기 대 쓰기가 1대 1이다. 같은 "파일을 맡아두는 서비스"인데 최적화 목록이 완전히 다른 이유가 그 한 줄에 있었다.

## 책 내용 뼈대

### 규모와 요구사항

| 항목 | 값 | 계산 근거 |
| --- | --- | --- |
| 가입자 | 5,000만, DAU 1,000만 | 전제 |
| 할당 저장공간 | 500PB | 5,000만 x 10GB |
| 하루 업로드 | 사용자당 2개, 평균 500KB | 전제 |
| 읽기 대 쓰기 | 1 대 1 | 전제 |
| 업로드 QPS | 240 (최대 480) | 1,000만 x 2 / 86,400 |

기능 요구사항은 파일 추가, 내려받기, 여러 단말 간 동기화, 파일 이력 조회, 공유, 변경 알림이다. 비기능은 안정성, 빠른 동기화, 대역폭 효율, 규모 확장성, 높은 가용성이다.

### API 세 가지

- **업로드** - 파일이 작으면 단순 업로드, 크면 `uploadType=resumable`로 이어 올리기(요청 받기, 데이터 전송, 상태 확인의 3단계)
- **내려받기** - `path`를 받는다
- **갱신 이력** - `path`와 `limit`을 받는다

### 한 대에서 시작해서 늘려간다

책이 서버 한 대에서 출발해서 문제가 생길 때마다 늘린다. 저장공간이 부족해지면 `user_id`로 샤딩하고, 데이터 유실이 걱정되면 S3로 옮겨 여러 지역에 다중화하고, 그 다음 로드밸런서와 웹 서버, 메타데이터 DB를 분리한다.

### 블록 저장소 서버

파일을 **4MB 블록**으로 쪼갠 다음 분할, 압축, 암호화해서 클라우드에 올린다. **블록마다 고유 해시**를 매긴다.

여기서 **델타 동기화**가 나온다. 파일이 수정되면 전체를 다시 보내지 않고 **바뀐 블록만** 보낸다. 블록 분할과 해시가 먼저 있어야 성립하는 기법이다.

### 스키마

`user` / `device`(push_id 보관) / `namespace` / `file` / `file_version`(읽기 전용) / `block`

`file_version`을 읽기 전용으로 둔 게 눈에 띈다. 이력이 덮어쓰기로 사라지지 않는다.

### 업로드 흐름

메타데이터를 "대기중"으로 먼저 적고, 클라우드 저장과 병렬로 진행한 다음 "완료"로 바꾼다. 그리고 알림 서비스가 다른 단말에 변경을 알려서 그쪽이 내려받게 한다.

### 동기화 충돌

먼저 처리된 변경이 성공하고, 나중 것은 **충돌 표시**를 받는다. 두 버전을 모두 보존해서 사용자에게 보여주고 **해결은 사용자가 한다.** 책이 Differential Synchronization을 언급하고 넘어간다.

### 알림 서비스

**롱 폴링**을 쓴다. 이유를 세 가지로 든다. 통신이 한 방향이고, 알림 빈도가 낮고, 대량 전송이 없다. 웹소켓은 양방향 실시간에 적합하다고 하면서 **채팅을 예로 든다.**

### 저장공간 절약

1. **중복 제거** - 같은 해시를 가진 블록을 **계정 차원에서** 제거한다
2. **지능적 백업 전략** - 보관할 버전 수를 제한하고, 가치 있는 버전만 남긴다
3. **아카이빙** - 오래 쓰지 않는 데이터를 콜드 스토리지로 옮긴다

### 장애 처리

API 서버는 **무상태**라서 장애가 나면 격리하면 된다. 메타데이터 DB는 마스터-슬레이브 다중화, 블록 저장소는 여러 지역 다중화다.

## 개인적인 질문

### 1. 14장과 15장은 정확히 무엇이 다른가

같은 "파일 맡아두기"인데 설계가 반대로 간다. 내가 정리한 구도는 이렇다.

| | 14장 유튜브 | 15장 구글 드라이브 |
| --- | --- | --- |
| 누가 읽나 | 올린 사람과 무관한 수백만 명 | 대개 **올린 본인의 다른 기기** |
| 읽기 대 쓰기 | 압도적으로 읽기 | **1 대 1** |
| 병목 | 전송 (하루 150,000달러) | 저장 (500PB) |
| 전략 | **미리 여러 벌 만들어둔다** (트랜스코딩) | **안 보내고 안 쌓는다** (델타 동기화, 중복 제거) |
| 그래서 필요한 것 | 적응형 스트리밍, 코덱 선택 | `device` 테이블, 알림 서비스, 충돌 처리 |

**유튜브에 트랜스코딩이 있고 드라이브에 없는 이유가 읽기 횟수다.** 한 번 가공해두면 수백만 번 재사용되는 쪽에서만 선투자가 회수된다. 1대 1이면 미리 가공해둘 이유가 없다.

그리고 "여러 기기"가 중요하다. `device` 테이블이 왜 있는지, 알림 서비스와 델타 동기화가 왜 필요한지가 전부 **같은 사람의 여러 기기** 때문이다. 유튜브에는 그런 게 하나도 없다.

반박이 나올 수 있는 지점은 공유다. 드라이브도 한 파일을 여러 사람이 본다. `namespace` 테이블이 그 자리인데, **책의 설계 범위에서 공유는 깊게 다루지 않고 규모 추정이 1대 1이다.** 공유가 중심이 되면 설계가 유튜브 쪽으로 옮겨간다. 한 파일을 수백만 명이 읽으면 CDN이 필요해진다.

### 2. 롱 폴링과 웹소켓을 가르는 기준이 뭔가

세 장이 서로 다른 답을 냈다.

| 장 | 선택 | 왜 |
| --- | --- | --- |
| 12장 채팅 | **웹소켓** | 양방향, 고빈도, 연결 유지가 전제 |
| 15장 드라이브 | **롱 폴링** | 한 방향, 저빈도, 대량 전송 없음 |
| 14장 유튜브 | **그냥 HTTP 파일** | 서버가 먼저 말할 일이 없다 |

세 개를 갈라보니 기준이 **방향, 빈도, 전송량** 세 개였다. 15장은 세 조건 중 하나도 웹소켓 쪽이 아니라서 더 단순한 도구로 충분했다. **도구를 고른 게 아니라 조건을 센 것이다.**

### 3. 충돌 해결을 사용자에게 넘기는 기준은 뭔가

책이 "해결은 사용자가 한다"로 넘어가는데, 같은 회사의 구글 독스는 같은 문서를 동시에 고쳐도 서버가 알아서 합친다. 같은 문제를 다르게 처리하는 것이다.

갈리는 기준은 **서버가 변경의 의미를 아는가**였다.

| | 구글 독스 | 구글 드라이브 |
| --- | --- | --- |
| 서버가 받는 것 | "3번째 글자 뒤에 a 삽입" | "4MB 블록 7번이 바뀜" |
| 합칠 수 있나 | 된다 (연산을 재배열) | 안 된다 (바이너리) |

편집 연산을 알면 순서를 바꿔 적용할 수 있다. 4주차에 본 CRDT가 그걸 한다. 블록 해시만 알면 둘 중 하나를 버리는 것 말고 할 게 없다.

기준이 둘 더 있다고 본다. **잘못 합쳤을 때 비용**이 큰 경우(코드 파일을 자동 병합하면 조용히 깨진다)와 **동시 편집이 흔한지**다. 독스는 동시 편집이 전제고 드라이브는 예외다. 예외를 위해 복잡도를 넣지 않는 선택이다.

## 내 프로젝트와 비교

### 내 알림도 롱 폴링 쪽이지만 근거가 달랐다

전시 커뮤니티 채팅은 3초마다 조회하는 **폴링**이다. 결과만 보면 15장이 롱 폴링을 고른 것과 비슷한 자리에 있는데, **고른 이유가 달랐다.**

- 나: 구현이 단순해서 골랐다
- 책: 방향과 빈도와 전송량을 세고 골랐다

그런데 내 쪽은 **채팅**이라서 책 기준으로는 웹소켓이 맞는 자리다. 12장에서 이미 계산해봤는데, 3초 폴링은 사용자당 분당 20요청이라 동시 접속 100만 명이면 333,000 QPS가 된다. 책 규모에서는 성립하지 않는다. **같은 선택을 했지만 한쪽은 조건을 세서 맞았고 한쪽은 안 세고 우연히 괜찮았다.**

### 내 충돌 처리는 서버가 해결한다

채팅방 생성 경합을 이렇게 처리했다. 참여자 ID를 정렬해서 키를 만들고, 유니크 제약을 걸고, 충돌하면 `REQUIRES_NEW`로 새 트랜잭션에서 재조회해 기존 방을 쓴다.

**서버가 판정한다.** 드라이브와 반대인데, 가능한 이유가 3번 질문의 기준에 딱 맞는다. **나는 두 요청의 의미가 같다는 걸 알고 있었다.** A와 B의 방을 만들자는 요청 두 개는 어느 쪽이 이겨도 결과가 같다. 드라이브는 두 사람이 고친 파일 내용이 같은 의미인지 알 방법이 없다.

### 내 업로드에는 델타 동기화가 없다

사진을 수정하면 전체를 다시 올린다. 지금은 그게 문제가 안 되는데, 이유를 적어보면

- 파일이 작다 (이미지 수백 KB)
- 수정이 드물다 (대개 새로 올린다)
- **블록 분할을 안 했으니 델타를 할 수가 없다**

세 번째가 핵심이다. **델타 동기화는 블록 분할과 해시가 먼저 있어야 가능하다.** 나중에 붙이고 싶어도 저장 구조를 먼저 바꿔야 한다. 책이 블록 저장소 서버를 먼저 설명하고 델타 동기화를 뒤에 설명한 순서가 그 의존 관계였다.

## 12장, 14장, 4주차와 연계해서 생각해보자

| 이전 내용 | 15장에서 쓰이는 자리 |
| --- | --- |
| 12장 웹소켓과 롱 폴링 | 알림 서비스에서 반대 선택을 한다 |
| 12장 무상태 서비스 | API 서버가 무상태라서 장애를 격리할 수 있다 |
| 14장 메타데이터와 바이트 분리 | 메타데이터 DB와 블록 저장소. 같은 구조가 또 나온다 |
| 14장 BLOB 저장소 | 여기서는 S3를 직접 쓴다 |
| 6장 해시 | 블록마다 해시를 매겨 같은지 비교한다 |
| 4주차 벡터 시계 | 충돌을 서버가 판정하지 않고 사용자에게 넘기는 것 |
| 5장 샤딩 | `user_id` 기준 메타데이터 DB 샤딩 |

4주차 벡터 시계와의 연결이 제일 선명하다. 그때도 **서버는 충돌을 감지만 하고 해결은 클라이언트에 넘겼다.** 책이 두 번 같은 선택을 했고, 두 번 다 이유가 "서버가 어느 쪽이 맞는지 알 수 없다"였다.

## 스스로 확인해본 것 - 저장이 병목이라는 게 숫자로 보이나

500PB와 업로드 QPS 240을 나란히 놓으니 이상했다. 트래픽은 작은데 용량은 거대하다. 하루 신규 유입을 계산해봤다.

```
하루 신규 = 1,000만 x 2개 x 500KB = 약 10TB

책의 할당 저장공간 500PB = 500,000TB
10TB / 500,000TB = 약 0.002%
```

(500PB는 가입자 5,000만에 10GB씩 할당한 값이라 실제 사용량과는 다르다. 그래도 자릿수 비교는 된다.)

**하루 들어오는 양이 쌓여 있는 양에 비하면 거의 없다.** 그러니까 드라이브의 비용은 "오늘 들어오는 것"이 아니라 **"이미 쌓여 있는 것"**이다.

그래서 15장의 저장공간 절약 세 가지가 전부 **이미 있는 데이터**를 겨냥한다. 중복 블록 제거, 오래된 버전 정리, 오래 안 쓰는 데이터 아카이빙. 하나도 "새로 들어오는 걸 줄이자"가 아니다.

**14장과 정확히 반대다.** 14장은 매일 새로 나가는 전송을 줄이려고 했고, 15장은 이미 쌓인 보관을 줄이려고 한다. 규모 추정에서 어느 수가 큰지가 최적화 목록을 결정했다.
