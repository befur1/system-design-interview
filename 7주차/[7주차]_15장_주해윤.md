## 15장 구글 드라이브 설계

---

> 구글 드라이브와 같은 파일 저장 및 동기화 서비스를 설계한다. 사용자는 여러 단말에서 파일을 저장하고 자동으로 동기화할 수 있으며, 파일을 다른 사용자와 공유할 수 있어야 한다.
> 

### 문제 이해 및 설계 범위 확정

- 가장 중요하게 지원해야 할 기능
    - 파일 업로드와 다운로드
    - 여러 단말 사이의 파일 동기화
    - 파일 갱신 이력 조회
    - 파일 공유
    - 파일이 추가·편집·삭제되거나 새롭게 공유되었을 때 알림
- 모바일 앱과 웹 앱 모두 지원
- 파일 암호화 필요
- 파일 크기 제한: 10GB
- 일간 능동 사용자 수: 천만 명
- 높은 안정성 필요
    - 데이터 손실이 발생하면 안 됨
- 빠른 동기화 속도 필요
- 네트워크 대역폭을 불필요하게 많이 사용하지 않아야 함
- 규모 확장성 필요
- 높은 가용성 필요

**개략적 규모 추정**

- 가입 사용자: 5천만 명
- 일간 능동 사용자: 천만 명
- 모든 사용자에게 10GB의 무료 저장 공간 제공
- 한 사용자는 매일 평균 2개의 파일 업로드
- 파일의 평균 크기: 500KB
- 읽기와 쓰기의 비율: `1:1`
- 필요한 저장 공간
    
    `5천만 명 × 10GB = 500PB`
    
- 업로드 API의 평균 QPS
    
    `1천만 명 × 2회 / 24시간 / 3,600초 = 약 240`
    
- 최대 QPS
    
    `240 × 2 = 480`
    

### 개략적 설계안 제시 및 동의 구하기

초기에는 한 대의 서버에 다음 기능을 모두 두는 구조로 시작할 수 있다.

- 파일 업로드와 다운로드를 처리하는 웹 서버
- 사용자 정보, 로그인 정보, 파일 메타데이터를 저장하는 데이터베이스
- 실제 파일을 저장하는 로컬 저장소

```
사용자
  ↓
웹 서버
  ├─ 데이터베이스
  └─ 로컬 파일 저장소
```

하지만 업로드되는 파일이 늘어나면 저장 공간이 부족해지므로 규모를 확장해야 한다.

- 파일 데이터는 클라우드 저장소에 보관
- 메타데이터 데이터베이스는 파일 저장 서버에서 분리
- 웹 서버는 로드밸런서 뒤에 여러 대를 배치
- 자주 사용하는 메타데이터는 캐시에 보관
- 파일 변경 알림을 위한 알림 서비스 사용
- 오프라인 상태의 변경 사항은 백업 큐에 보관

**개선된 개략적 구조**

```
사용자 단말
     ↓
로드밸런서
     ↓
API 서버
  ├─ 메타데이터 캐시
  ├─ 메타데이터 데이터베이스
  ├─ 클라우드 파일 저장소
  ├─ 알림 서비스
  ├─ 오프라인 사용자 백업 큐
  └─ 아카이빙 저장소
```

**주요 컴포넌트**

- 사용자 단말: 웹 브라우저나 모바일 앱 등의 클라이언트
- 블록 저장소 서버: 파일 블록을 클라우드 저장소에 업로드
- 클라우드 저장소: 파일을 블록 단위로 보관
- API 서버: 파일 업로드를 제외한 사용자 인증, 사용자 프로파일 관리, 파일 메타데이터 갱신 등을 처리
- 메타데이터 데이터베이스: 사용자, 파일, 블록, 파일 버전 등의 메타데이터를 관리
- 메타데이터 캐시: 자주 사용하는 메타데이터를 캐시
- 알림 서비스: 파일의 추가·편집·삭제 사실을 클라이언트에게 전달
- 오프라인 사용자 백업 큐: 클라이언트가 오프라인일 때 변경 사항을 보관했다가 다시 접속하면 동기화
- 아카이빙 저장소: 오랫동안 사용되지 않은 데이터를 저장

**클라우드 저장소**

- 규모 확장성, 가용성, 보안성이 높은 객체 저장소를 사용
- 파일은 Amazon S3와 같은 클라우드 저장소에 보관 가능
- 같은 지역 안에서 다중화하거나 여러 지역에 걸쳐 다중화할 수 있음
- 여러 지역에 걸쳐 다중화하면 데이터 손실을 막고 가용성을 높일 수 있음
- 버킷은 파일 시스템의 폴더와 비슷한 역할을 함

```
같은 지역 내 다중화

지역 A
버킷 ─┬─ 사본
      ├─ 사본
      └─ 사본

여러 지역에 걸친 다중화

지역 A 버킷 ─┬─ 지역 B 사본
             ├─ 지역 B 사본
             └─ 지역 B 사본
```

**저장 계층 분리**

- 파일 저장소와 메타데이터 데이터베이스를 분리하여 단일 장애 지점을 피함
- 데이터베이스에 다중화와 샤딩을 적용하여 가용성과 규모 확장성을 확보
- 파일 저장소는 여러 지역에 데이터를 다중화하여 가용성과 데이터 무손실을 보장

### API

기본적으로 세 가지 API가 필요하다.

#### 1. 파일 업로드 API

- 단순 업로드
    - 파일 크기가 작을 때 사용
- 이어 올리기
    - 파일 크기가 크거나 네트워크 문제로 업로드가 중단될 가능성이 높을 때 사용

`https://api.example.com/files/upload?uploadType=resumable`

- 인자
    - `uploadType=resumable`
    - `data`: 업로드할 로컬 파일

**이어 올리기 절차**

1. 이어 올리기 URL을 받기 위한 최초 요청을 보냄
2. 데이터를 업로드하면서 업로드 상태를 모니터링
3. 장애가 발생하면 장애가 발생한 시점부터 업로드를 다시 시작

#### 2. 파일 다운로드 API

`https://api.example.com/files/download`

- 인자
    - `path`: 다운로드할 파일의 경로

```
{
  "path": "/recipes/soup/best_soup.txt"
}
```

#### 3. 파일 갱신 이력 API

`https://api.example.com/files/list_revisions`

- 인자
    - `path`: 갱신 이력을 가져올 파일의 경로
    - `limit`: 반환할 이력 개수의 최댓값

```
{
  "path": "/recipes/soup/best_soup.txt",
  "limit": 20
}
```

- 모든 API는 사용자 인증이 필요
- HTTPS 프로토콜을 사용해 클라이언트와 서버가 주고받는 데이터를 보호

### 한 대 서버의 제약 극복

**파일 저장소**

- 파일을 클라우드 저장소에 보관
- 두 개 이상의 지역에 파일을 다중화하여 가용성과 데이터 무손실을 보장

**로드밸런서**

- 요청을 여러 API 서버로 고르게 분산
- 특정 API 서버에 장애가 발생하면 해당 서버로 요청을 보내지 않음

**API 서버**

- 로드밸런서 뒤에 여러 대를 배치하여 손쉽게 추가 가능
- 무상태 서버로 구성

**메타데이터 데이터베이스**

- 실제 파일이 아니라 메타데이터만 저장
- 데이터베이스 다중화와 샤딩을 적용
- 관계형 데이터베이스를 사용하여 강한 일관성 요구사항에 대응

**메타데이터 캐시**

- 자주 사용하는 메타데이터를 캐시
- 캐시를 다중화하여 특정 노드 장애에도 데이터를 가져올 수 있도록 함

**알림 서비스**

- 파일이 추가·편집·삭제되었음을 클라이언트에 알림
- 클라이언트가 변경된 파일의 최신 상태를 가져가도록 함

**오프라인 사용자 백업 큐**

- 클라이언트가 오프라인이라 최신 상태를 확인할 수 없을 때 변경 정보를 보관
- 클라이언트가 다시 접속하면 동기화

### 상세 설계

#### 블록 저장소 서버

- 파일을 작은 블록으로 분할하여 클라우드 저장소에 업로드
- 파일을 재구성할 때는 블록을 원래 순서대로 결합
- 블록의 최대 크기는 4MB
- 각 블록은 독립적인 객체로 취급됨

**블록 처리 과정**

```
파일
  ↓
작은 블록으로 분할
  ↓
각 블록 압축
  ↓
각 블록 암호화
  ↓
클라우드 저장소에 업로드
```

**델타 동기화**

- 파일 전체가 아니라 변경된 블록만 동기화
- 파일이 수정되면 변경된 블록의 해시값을 비교하여 수정된 부분을 찾음
- 변경된 블록만 압축·암호화하여 클라우드 저장소로 전송
- 네트워크 대역폭 사용량을 줄일 수 있음

```
로컬 파일

블록 1
블록 2  ← 변경
블록 3
블록 4
블록 5  ← 변경
블록 6
   ↓
변경된 블록 2, 5만 전송
   ↓
클라우드 파일 갱신
```

**압축**

- 블록 단위로 압축하여 데이터 크기를 줄임
- 압축 알고리즘은 파일 유형에 따라 선택

**암호화**

- 클라우드 저장소로 전송하기 전에 블록을 암호화
- 클라이언트가 암호화 기능을 담당하는 구조도 고려할 수 있음

#### 메타데이터 데이터베이스

강한 일관성 요구사항을 지원해야 한다.

- 같은 파일이 사용자나 단말에 따라 다르게 보이면 안 됨
- 메타데이터 캐시는 결과적 일관성을 지원할 수 있음
- 데이터베이스의 원본이 변경되면 캐시의 사본을 무효화

**주요 테이블**

- `user`: 사용자 기본 정보
- `device`: 사용자의 단말 정보
- `namespace`: 사용자의 루트 디렉터리 정보
- `file`: 파일의 최신 정보
- `file_version`: 파일의 갱신 이력
- `block`: 파일 버전을 구성하는 블록 정보

```
user
- user_id
- user_name
- created_at

device
- device_id
- user_id
- last_logged_in_at

namespace
- id
- owner_id
- is_shared
- created_at

file
- id
- file_name
- relative_path
- is_directory
- latest_version
- checksum
- namespace_id
- created_at
- last_modified

file_version
- id
- file_id
- device_id
- version_number
- last_modified

block
- block_id
- file_version_id
- block_order
```

- `file_version` 테이블은 파일의 갱신 이력을 보관
- `file_version`의 레코드는 갱신 이력이 훼손되는 것을 막기 위해 읽기 전용으로 관리
- `block` 테이블의 블록을 순서대로 결합하면 특정 버전의 파일을 복원할 수 있음

### 업로드 절차

파일 메타데이터를 추가하는 요청과 실제 파일을 업로드하는 요청은 병렬로 전송할 수 있다.

```
클라이언트 1
  ├─ 파일 메타데이터 추가
  │      ↓
  │   API 서버
  │      ↓
  │   메타데이터 데이터베이스
  │
  └─ 파일 업로드
         ↓
      블록 저장소 서버
         ↓
      클라우드 저장소
```

**파일 메타데이터 추가**

1. 클라이언트가 새 파일의 메타데이터 추가 요청 전송
2. API 서버가 메타데이터를 데이터베이스에 저장하고 업로드 상태를 `pending`으로 변경
3. 새 파일이 추가되었음을 알림 서비스에 통지

**파일 업로드**

1. 클라이언트가 파일을 블록 저장소 서버에 업로드
2. 블록 저장소 서버가 파일을 블록으로 나눈 뒤 압축하고 암호화
3. 블록을 클라우드 저장소에 전송
4. 업로드가 끝나면 클라우드 저장소가 완료 콜백을 API 서버에 전송
5. API 서버가 데이터베이스의 파일 상태를 `uploaded`로 변경
6. 알림 서비스에 파일 업로드가 끝났음을 통지
7. 알림 서비스가 관련된 클라이언트에게 변경 사실 전달

### 다운로드 절차

파일이 새로 추가되거나 편집되면 다른 클라이언트에 변경 사실을 전달해야 한다.

- 접속 중인 클라이언트
    - 알림 서비스로부터 파일 변경 알림을 받음
    - 새로운 메타데이터와 변경된 블록을 요청
- 오프라인 클라이언트
    - 변경 정보가 오프라인 사용자 백업 큐에 보관됨
    - 다시 접속하면 최신 상태로 동기화

**다운로드 흐름**

```
알림 서비스
  ↓ 변경 알림
클라이언트
  ↓ 변경 내역 요청
API 서버
  ↓
메타데이터 데이터베이스
  ↓ 변경 내역 반환
클라이언트
  ↓ 필요한 블록 요청
블록 저장소 서버
  ↓ 블록 요청
클라우드 저장소
  ↓ 블록 반환
블록 저장소 서버
  ↓ 블록 반환
클라이언트
  ↓
파일 재구성
```

1. 알림 서비스가 클라이언트에게 파일 변경 사실을 알림
2. 클라이언트가 API 서버에 변경 내역 요청
3. API 서버가 메타데이터 데이터베이스에 변경 내역 요청
4. 메타데이터 데이터베이스가 변경 내역 반환
5. API 서버가 클라이언트에 변경 내역 반환
6. 클라이언트가 블록 저장소 서버에 블록 다운로드 요청
7. 블록 저장소 서버가 클라우드 저장소에서 블록 다운로드
8. 클라우드 저장소가 요청된 블록 반환
9. 블록 저장소 서버가 클라이언트에 블록 반환
10. 클라이언트가 블록을 결합하여 파일 재구성

### 알림 서비스

- 다른 클라이언트에 파일 변경 사실을 전달하여 동기화를 시작하도록 함
- 알림에는 파일 전체 내용이 아니라 변경 사실만 포함
- 클라이언트가 알림을 받으면 API 서버에 최신 메타데이터와 변경 내역을 요청
- 선택할 수 있는 통신 방식
    - 롱 폴링
    - 웹소켓
- 본 설계에서는 롱 폴링 사용

**롱 폴링을 사용하는 이유**

- 채팅처럼 양방향 실시간 통신이 필요하지 않음
- 서버가 파일 변경 사실을 클라이언트에 전달하는 단방향 통신이면 충분
- 알림이 자주 발생하지 않음
- 한 번에 많은 데이터를 전송할 필요가 없음
- 클라이언트는 알림 서버와 롱 폴링 연결 유지
- 변경 알림을 받으면 연결을 종료하고 최신 데이터를 요청
- 요청이 끝나거나 타임아웃되면 새로운 롱 폴링 연결 생성

### 동기화 충돌

두 명 이상의 사용자가 같은 파일이나 폴더를 동시에 갱신할 때 발생한다.

**충돌 처리 방법**

- 먼저 처리된 변경은 성공한 것으로 기록
- 나중에 처리된 변경은 충돌이 발생한 것으로 표시
- 충돌이 발생하면 동일한 파일의 두 가지 버전을 보관
- 사용자가 두 파일을 하나로 합치거나 둘 중 하나를 선택하도록 함

```
사용자 1 ── 파일 갱신 ──→ 시스템
사용자 2 ── 파일 갱신 ──→ 시스템

먼저 처리된 변경 → 정상 반영
나중 변경       → 충돌 발생

결과
├─ 최신 서버 버전
└─ 사용자 2의 충돌 사본
```

### 저장 공간 절약

파일 갱신 이력과 안정성을 위해 여러 버전을 보관하면 저장 용량이 빠르게 증가할 수 있다.

**중복 제거**

- 계정 차원에서 중복 파일 블록 제거
- 두 블록의 해시값을 비교하여 같은 블록인지 판단

**지능적 백업**

- 보관할 수 있는 파일 버전 수에 상한 설정
    - 상한을 초과하면 가장 오래된 버전 삭제
- 중요한 버전만 보관
    - 자주 갱신되는 파일의 모든 버전을 보관하지 않음
- 자주 사용하지 않는 데이터는 아카이빙 저장소로 이동
    - 수개월 또는 수년간 사용되지 않은 데이터가 해당
    - 일반 저장소보다 저렴한 아카이빙 저장소 사용

### 장애 처리

**로드밸런서 장애**

- 부 로드밸런서가 활성화되어 트래픽을 이어받음
- 박동 신호를 주기적으로 보내 상태를 모니터링

**블록 저장소 서버 장애**

- 다른 서버가 미완료 또는 대기 중인 작업을 이어받음

**클라우드 저장소 장애**

- 여러 지역에 파일이 다중화되어 있으므로 다른 지역에서 파일을 가져옴

**API 서버 장애**

- API 서버는 무상태 서버
- 로드밸런서가 장애 서버로 요청을 보내지 않도록 함

**메타데이터 캐시 장애**

- 캐시는 여러 노드에 다중화
- 한 노드에 장애가 발생해도 다른 노드에서 데이터를 가져옴
- 장애가 발생한 캐시 서버는 새 서버로 교체

**메타데이터 데이터베이스 장애**

- 주 데이터베이스 장애
    - 부 데이터베이스 중 하나를 주 데이터베이스로 승격
    - 새로운 부 데이터베이스 추가
- 부 데이터베이스 장애
    - 다른 부 데이터베이스가 읽기 연산 처리
    - 장애 서버를 새 서버로 교체

**알림 서비스 장애**

- 클라이언트가 알림 서비스와 롱 폴링 연결 유지
- 하나의 서버에서 너무 많은 연결을 관리하지 않도록 여러 서버로 분산
- 서버 장애가 발생하면 클라이언트가 다시 연결

**오프라인 사용자 백업 큐 장애**

- 큐도 다중화
- 장애 발생 시 구독 중인 클라이언트가 백업 큐를 이용해 구독 관계를 복원

### 마무리

- 메타데이터 관리와 파일 동기화 처리로 시스템을 구분
- 알림 서비스는 파일 상태를 최신으로 유지하도록 클라이언트에 변경 사실 전달
- 롱 폴링을 사용하여 클라이언트와 알림 서버를 연결
- 블록 단위 저장과 델타 동기화를 통해 네트워크 사용량 절감
- 관계형 데이터베이스를 사용하여 메타데이터의 강한 일관성 보장
- 파일은 클라우드 저장소에 보관하고 여러 지역에 다중화
- 필요에 따라 블록 저장소 서버를 거치지 않고 클라이언트가 클라우드 저장소에 직접 업로드하는 방식도 고려 가능
