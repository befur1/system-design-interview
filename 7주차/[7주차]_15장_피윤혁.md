# 구글 드라이브 설계 (Design Google Drive)

클라우드 서비스에서 고려할 점 (생각해본다면)

1. 파일 저장
2. 동기화
3. 다운로드
4. 업로드 할때의 속도
5. 저장한 내용이 깨지지 않아야함..?
- 알림까지

책에서는

1. 안정성: 저장소 시스템에서 안정성은 중요
2. 빠른 동기화 속도: 파일 동기화에 시간이 너무 많이 걸리면 안됨
3. 네트워크 대역폭: 네트워크를 너무 많이 소모하면 휴대폰과 같은 단말에서 사용하면 사용자 입장에서 통신요금 부담됨
4. 규모 확장성: 아주 많은 트래픽도 처리해야함
5. 높은 가용서이: 일부 서버에 장애가 발생해도 계속 사용할 수 있어야함.

파일 업로드의 API

1. 단순 업로드
2. 이어 올리기: 업로드 하는 과정을 모니터링하고, 장애가 발생하면 그 시점부터 다시 시도한다.

한대의 서버로 업로드 하다보면, 저장공간이 꽉 찰것이고… 이를 데이터 샤딩을 통해 여러 서버에 나누어 저장해 일시적으로 해결할 수 있지만 완벽한 해결은 아니다.

→ S3 저장소는 규모 확장성과 보안, 가용성 등을 제공하는 객체 저장소 서비스라 이런거 사용하자.

이 저장소는 지역내 다중화 혹은 지역 외 다중화까지 지원한다.

여기까지는 데이터 손실 걱정이 없게 설계되었다.

이제 더 고민할 지점은?

1. 네트워크 트래픽 분산 → 로드밸런서
2. 로드밸런서 추가를 통해 웹 서버를 추가
3. 데이터베이스를 파일 저장 서버에서 분리해 SPOF 회피, 올리는 사람의 정보, 제목 등등을 저장할 메타데이터 데이터베이스
4. 저장한 데이터도 두 개 이상의 지역에 데이터 다중화를 통해 무손실을 보장하는 파일 저장소

동기화: 먼저 수정된 파일이 우선권을 가진다고 생각하면 된다. 로컬 사본과 서버의 버전에 id를 붙여 버전 번호를 확인하는 방식

블록 저장소 서버

이 서버는 어떤 일을 하냐

1. 사용자가 올린 파일을 4MB 정도의 블록으로 쪼갬
2. 블록마다 해시값을 붙여, 압축 후 암호화
3. 그 블록들을 클라우드 저장소에 각각 하나의 객체로 올림.

→ 블록: 파일을 나눈다.

→ 저장: 객체 저장소(S3 같은 곳이다)

사용자가 올린 파일에서 일부가 업데이트 될때도 유용하다.

1. 델타 동기화: 파일 수정이 일어난 블록만 동기화한다.
2. 압축: 블록 단위로 압축하면 데이터의 크기를 많이 줄인다. ex) gzip,bzip2 등

1. 클라우드 저장소: 파일을 블록 단위로 나눠 클라우드 저장소에 보관
2. 아카이빙 저장소: 오랫동안 사용되지 않은 비활성 데이터 저장
3. 로드밸런서
4. API 서버: 파일 업로드 외 다른 요청 처리: 사용자 인증, 사용자 프로파일 관리 등등
5. 메타데이터 데이터베이스
6. 메타데이터 캐시
7. 알림 서비스
8. 오프라인 사용자 백업 큐: 이게 사용자가 접속 중인지 아닌지에 따라 최신 상태를 확인할 수 없을 때는
해당 정보를 이 큐에 두어 나중에 클라이언트가 접속했을 때 동기화될 수 있도록 함

알림 서비스에서는 롱 폴링 방식 사용이 좋다

롱 폴링은 **클라이언트가 서버에 요청을 보내면, 서버가 새 소식이 생길 때까지 응답을 미루고 연결을 붙잡는 방식인데**

여기서는 실시간 양방향 소통이 굳이 필요하지 않기 때문이다.

드롭박스도 이 방식을 사용하고, 알림 서비스 서버가 관리하는 연결의 수는 1백만개가 넘는다고 한다. (2012년 기준)

이유

1. 보내는 데이터가 굉장히 작고
2. 여기서의 알림 연결은 기다리기만 하는 연결이다
3. **이벤트 기반 I/O**
4. 서버의 수를 줄여 비용을 아낄 수 있다.

또한 드롭박스는 쪼개기를 블록 저장소 서버에서 하지 않고, 클라이언트에서 한다.

데스크톱 앱이 파일을 4MB 블록으로 나누고 해시를 계산해서, 서버에 없는 블록만 올린다. 
책에서는 설명을 단순하게 하려고 블록 서버를 그렸지만, 클라이언트가 이 일을 맡을 수도 있다.
다만 이 경우에도 블록 암호화 자체는 서버 쪽에서 하기 때문에, 회사는 원본에 접근할 수 있다는게 함정.


예전 방식처럼 연결마다 스레드를 하나씩 두면 스레드 100만 개가 필요하고, 
메모리와 문맥 전환 비용 때문에 서버가 버티지 못했는데 지금은 
**epoll(리눅스), kqueue 같은 이벤트 기반 I/O**를 써서 스레드 몇 개로 수많은 연결을 지켜보다가, 
이벤트가 생긴 연결만 처리하므로 가능하다고 한다.

업로드 절차

두개의 요청이 병렬적으로 처리됨

1. 파일 메타데이터 추가용 요청
2. 클라우드 저장소로 추가하는 요청

→  블록 단위로 쪼개고, 압축, 암호화 후 저장소로 전송한다.

저장소 공간 절약

파일 갱신 상황에서 안정성을 보장하기 위해 여러 버전을 보관해야하는데 이 모든 버전을 자주 백업하면 용량이 빠르게 찬다.

따라서 용량을 절약하기 위해

1. 중복 제거: 블록마다 해시값이 있으니, 비교하여 판단
2. 지능적 백업 전략: 한도를 설정해 버전의 개수를 제한
3. 중요한 버전만 보관한다.

→ 전략1: 가장 많이 쓰는 기준으로  최근 버전은 자세히, 오래된 버전은 대표만 남긴다

→ 전략2: 편집 세션 단위로 묶기: 자동 저장이 1분마다 일어나도, 사람 입장에서 의미 있는 단위는 한 번 앉아서 작업한 결과이다.
그래서 **일정 시간(예: 30분) 동안 수정이 없으면 세션이 끝났다**고 보고, 세션마다 마지막 버전만 남긴다.

→ 전략3: 변경이 큰 버전 남기기
