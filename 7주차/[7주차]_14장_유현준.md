# [7주차] 14장 - 유튜브 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

이번 장은 내가 발표를 맡았다. 읽으면서 가장 오래 멈춘 곳은 비용 최적화에 나오는 "인기 없는 비디오는 인코딩을 생략한다"는 한 줄이었다. 나는 인코딩을 압축이라고만 알고 있었으니까, 압축을 안 하면 재생이 어떻게 되는지부터 막혔다. 그 한 줄을 파다 보니 코덱이 뭔지, 인코딩 비용이 어디서 나가는지, 유튜브가 그 비용을 어떻게 감당하는지까지 따라왔다. 책이 한 줄로 넘어간 자리에 설계 결정이 들어 있었다.

## 책 내용 뼈대

### 규모와 요구사항

| 항목 | 값 | 계산 근거 |
| --- | --- | --- |
| DAU | 500만 | 전제 |
| 하루 시청 | 사용자당 5개, 평균 30분 | 전제 |
| 업로더 비율 | 10% | 전제 |
| 하루 신규 저장 용량 | 150TB | 500만 x 10% x 300MB |
| 하루 CDN 비용 | 150,000달러 | 500만 x 5 x 0.3GB x 0.02달러 |

기능 요구사항은 비디오 업로드와 재생, 화질 변경, 낮은 비용, 높은 가용성과 안정성, 다양한 단말 지원이다. 숫자 중에서 **CDN 비용이 저장 비용을 압도한다.** 그래서 이 장의 비용 최적화는 곁가지가 아니라 본체다.

### 설계는 세 부분뿐이다

- **단말** - 컴퓨터, 모바일, 스마트 TV
- **CDN** - 비디오를 저장하고 스트리밍한다
- **API 서버** - 스트리밍을 제외한 나머지 전부

여기서 "스트리밍을 제외한"이라는 조건이 중요하다. **비디오 데이터는 우리 서버를 지나가지 않는다.** 하루 150TB가 올라오고 그보다 훨씬 많은 양이 나가는데, 그게 API 서버를 통과하면 서버 대수가 전송량에 비례해서 늘어나야 한다.

### 업로드 흐름

```
원본 비디오 바이트  ->  원본 저장소(BLOB)  ->  트랜스코딩 서버  ->  트랜스코딩 비디오 저장소 + CDN
                                                            \
                                                             ->  완료 큐  ->  완료 핸들러
비디오에 대한 사실   ->  메타데이터 DB와 캐시
```

바이트 흐름과 메타데이터 흐름이 **나란히 간다.** 바이트 복사가 끝날 때까지 메타데이터 행이 기다릴 이유가 없다.

### 트랜스코딩이 왜 필요한가

책이 네 가지를 든다.

1. 원본 비디오는 용량이 너무 크다
2. 단말과 대역폭이 기기마다 다르다
3. 네트워크 상황에 맞춰 화질을 바꿔야 한다
4. 지원하는 코덱이 기기마다 다르다

그리고 용어를 가른다. **컨테이너**는 `.mp4` `.avi` `.mov` 같은 포장 방식이고, **코덱**은 H.264, VP9, HEVC 같은 압축 방식이다. 비트레이트는 초당 처리하는 비트 수다.

### 트랜스코딩 아키텍처

```
전처리기  ->  DAG 스케줄러  ->  자원 관리자  ->  작업 실행 서버
```

전처리기가 하는 일이 세 개다.

- 비디오를 **GOP 단위로 분할**한다 (병렬 처리와 중단 지점 재개가 가능해진다)
- 클라이언트가 지정한 설정대로 **DAG를 만든다**
- 분할한 데이터와 메타데이터를 **임시 저장소에 보관**한다 (실패하면 여기서 재개하고, 작업이 끝나면 삭제한다)

자원 관리자는 작업 큐, 작업 서버 큐, 실행 큐와 작업 스케줄러로 되어 있다.

### 최적화

| 목표 | 방법 |
| --- | --- |
| 속도 | 업로드 센터를 가까이 두기, GOP 단위 병렬 업로드, 메시지 큐로 느슨하게 연결 |
| 안전 | 미리 사인된 업로드 URL, DRM(FairPlay, Widevine, PlayReady), AES 암호화, 워터마크 |
| 비용 | 인기 비디오만 CDN, 인기 없는 비디오는 인코딩 생략, 지역 한정 배포, 자체 CDN과 ISP 제휴 |

오류는 회복 가능한 것과 불가능한 것으로 나눈다. 회복 가능하면 재시도하고, 몇 번 해도 안 되면 중단하고 알린다.

## 개인적인 질문

### 1. 인코딩을 생략하면 재생은 어떻게 되나

내 오해부터 적는다. 나는 인코딩을 압축이라고만 알고 있었다. 그러면 생략했을 때 용량이 큰 채로 남는 거니까 재생은 되지만 느릴 거라고 생각했다. 틀렸다.

**사용자가 올리는 원본은 이미 압축돼 있다.** 아이폰으로 찍은 영상도 H.264로 인코딩된 mp4다. 날것의 픽셀 덩어리가 올라오는 게 아니다. 그래서 책이 말하는 트랜스코딩은 "압축한다"가 아니라 **"여러 벌로 만든다"**다.

```
원본 1벌 (사용자가 올린 그대로)
  +-- 240p H.264
  +-- 480p H.264
  +-- 720p H.264
  +-- 1080p VP9
  ...
```

인코딩 생략은 **이 가지들을 미리 만들지 않는 것**이고, 재생은 원본 한 벌로 한다. 그래서 아끼는 건 전송이 아니라 **연산 시간과 저장 용량**이다.

그런데 가지가 없으면 화질이 하나뿐이라 적응형 스트리밍이 고를 게 없고, 원본 비트레이트가 높으면 모바일에서 버벅인다. 그래서 책이 바로 뒤에 조건을 붙인다.

> 짧은 비디오는 필요할 때 인코딩해서 보여준다

**완전 생략이 아니라 지연이다.** 요청이 오면 그때 만든다. 짧은 비디오로 한정한 건 그때 만들어도 사용자가 기다릴 만한 시간 안에 끝나기 때문이다.

### 2. 인코딩 비용은 어디서 발생하나

책 그림에 이미 있었다. 트랜스코딩 아키텍처 맨 끝의 **작업 실행 서버**다. 비용은 서버 대수 곱하기 시간이다. 부수 비용도 둘 있다. 코덱을 추가하면 트랜스코딩 비디오 저장소에 벌 수만큼 쌓이고, 작업 큐 대기 시간이 생긴다. 방금 올린 영상에서 고화질이 잠깐 안 보이는 게 그 대기다.

그런데 전송 비용과 인코딩 비용은 **단위가 다르다.**

| 비용 | 단위 | 곱해지는 것 |
| --- | --- | --- |
| 전송 | GB당 0.02달러 | 뷰 수 |
| 인코딩 | 서버 시간당 얼마 | 1회 |

**인코딩은 한 번, 전송은 뷰 수만큼이다.** 이 비대칭이 "인기 없는 비디오는 인코딩을 생략한다"의 근거였다. 뷰가 적으면 선투자를 회수할 횟수가 없다.

### 3. 메타데이터 DB에는 정확히 무엇이 들어가나

읽으면서 "메타데이터 DB"가 뭘 담는지 애매했다. 정리하면 **파일의 내용이 아니라 파일에 대한 사실만** 담는다.

| 들어가는 것 | 안 들어가는 것 |
| --- | --- |
| 제목, 설명, 길이, 업로드 시각 | 비디오 파일 자체 |
| 업로더 ID, 조회 수, 썸네일 URL | 트랜스코딩된 화질별 영상 |

분리하는 이유는 **접근 패턴이 정반대**라서다.

| | 바이트 | 메타데이터 |
| --- | --- | --- |
| 크기 | 수백 MB 이상 | 수백 바이트 |
| 변경 | 거의 없다 | 조회 수가 계속 바뀐다 |
| 접근 | 처음부터 끝까지 순차 전송 | `WHERE`, `ORDER BY`, 조인 |

비디오 바이트를 MySQL에 넣으면 조회 한 번에 디스크를 300MB 긁어야 하고, 반대로 "조회 수 높은 순"을 S3에 물어볼 방법이 없다.

**11장에서 본 결정과 같다.** 뉴스 피드 캐시에 포스팅 전체를 넣지 않고 `<postId, userId>` 쌍만 넣었다. 본문은 따로 두고 가리키는 정보만 모으는 것이다.

## 내 프로젝트에 메타데이터 DB와 BLOB 분리가 이미 있었다

전시 커뮤니티의 사진 업로드가 정확히 이 구조다.

```java
Photo photo = photoRepo.save(photo);   // 메타데이터 DB
s3.putObject(key, bytes);              // BLOB 저장소
```

`Photo` 엔티티에는 S3 키, 업로더, 생성 시각만 있고 이미지 바이트는 없다. **나는 이미 메타데이터 DB를 쓰고 있었고, 책이 거기에 이름을 붙여준 것이었다.**

그리고 4주차에 이 코드에서 다른 문제를 봤다. `s3.putObject`가 3초 걸리는데 트랜잭션 안에 있으면 DB 커넥션을 3초 동안 잡고 있다는 것이었다. 해결은 **ID를 먼저 발급해서 S3에 먼저 올리고, 행 생성을 뒤로 빼는** 쪽이었다.

책의 업로드 흐름이 똑같은 모양이다. **메타데이터 갱신과 바이트 업로드를 병렬로 둔다.** 내가 4주차에 커넥션 점유 문제로 본 것이 14장에서는 아키텍처 그림으로 그려져 있었다. 같은 결론인데 한쪽은 트랜잭션 범위 문제로, 다른 한쪽은 시스템 구성도로 나타난 것이다.

### 내 구조에 없는 것 - 완료 큐

누끼 생성이 외부 API 호출인데, 지금은 요청 안에서 동기로 돌아간다. 책이라면 완료 큐와 완료 핸들러가 들어갈 자리다. 없어서 생기는 구멍이 세 개 있다.

1. 외부 API가 느리면 **요청 스레드가 그대로 묶인다** (3주차 톰캣 스레드 얘기와 같은 자리)
2. 실패했을 때 **재시도 장치가 없다**. 책의 "회복 가능한 오류"에 해당하는 처리가 없다
3. **처리 중 상태가 없다.** 사용자에게 "처리 중입니다"를 보여줄 방법이 없고, 끝날 때까지 기다리게 한다

10장 알림 시스템에서 제3자 서비스 앞에 큐를 두는 걸 봤고, 11장에서 팬아웃 앞에 큐를 두는 걸 봤다. 14장에서 세 번째로 같은 자리에 같은 도구가 나왔다. **내 프로젝트는 세 번 다 그 자리가 비어 있다.**

## 10장, 11장, 12장과 연계해서 생각해보자

| 이전 내용 | 14장에서 쓰이는 자리 |
| --- | --- |
| 1장, 2장 CDN | 여기서는 곁가지가 아니라 설계의 본체 |
| 10장 메시지 큐 | 완료 큐. 업로드와 트랜스코딩을 느슨하게 연결 |
| 10장 재시도 | 회복 가능한 오류와 불가능한 오류 구분 |
| 11장 캐시에 ID만 넣기 | 메타데이터 DB에 바이트를 넣지 않는 것 |
| 12장 무상태 서비스 | API 서버가 무상태라서 스트리밍을 떼어낼 수 있다 |
| 5장 샤딩 | 메타데이터 DB 샤딩과 다중화 |

특히 12장과의 관계가 눈에 띈다. 12장에서는 채팅 서버가 연결을 들고 있어야 해서 상태 유지 서비스가 됐는데, 14장은 **상태를 클라이언트와 CDN으로 밀어내서** API 서버를 무상태로 만들었다. 같은 책에서 반대 방향의 선택이 나왔고, 갈린 이유는 실시간 양방향 통신이 필요한지였다.

## 스스로 확인해본 것 - 코덱 선택의 손익분기

발표 준비하면서 전송 절감과 인코딩 비용이 어디서 뒤집히는지 계산해봤다.

1시간 1080p 영상을 H.264로 1GB라고 하면, AV1은 같은 화질에서 약 0.53GB다. 뷰당 0.47GB가 절약된다.

```
뷰당 절감액 = 0.47GB x 0.02달러 = 약 0.0094달러
손익분기 뷰 수 = (AV1 추가 인코딩 비용) / 0.0094달러

추가 인코딩에 30달러를 쓴다면 -> 약 3,200뷰에서 본전
```

외부에서 관측된 유튜브의 VP9 추가 임계값이 **약 3,500뷰**였다. 가정을 넣은 계산이라 정확한 값은 아니지만 **자릿수가 맞는다.** 코덱 단계가 왜 수천 뷰에서 시작하는지가 이 계산으로 설명이 된다.

## 발표 준비하면서 파본 것

책에 없는 부분인데, 책의 한 줄을 이해하는 데 필요했다.

### 적응형 스트리밍은 클라이언트가 결정한다

책은 MPEG-DASH, Apple HLS 등 프로토콜 네 개를 나열하고 넘어간다. 실제로는 화질별로 여러 벌을 만들어 2~6초 세그먼트로 쪼개고, 매니페스트 파일(`.m3u8` 또는 `.mpd`)에 화질별 URL을 적어둔다. **플레이어가 세그먼트마다 다음 화질을 고른다.**

결정권이 클라이언트에 있다는 게 중요하다. 서버는 **정적 파일 서버**가 되고, 세그먼트는 누가 요청해도 같은 파일이라서 **일반 CDN이 캐시할 수 있다.** 서버가 화질을 정하는 설계였다면 사용자별 상태를 추적해야 하고 같은 URL이 사람마다 다른 응답이 되어 CDN을 쓸 수 없다. **책이 "CDN이 비디오를 스트리밍한다"로 한 줄에 끝낼 수 있었던 근거가 여기였다.**

대가는 지연이다. 세그먼트를 모아서 보내니까 일반 HLS는 18~30초, 저지연 HLS는 2~5초 수준이고, WebRTC는 0.5초 아래지만 CDN을 쓸 수 없다. **지연과 규모를 교환한 것이다.**

### 유튜브는 뷰 수에 따라 코덱을 추가한다

외부 관측에 따르면 뷰가 수천 이하면 H.264만, 약 3,500 이상이면 VP9을 추가하고, 수백만 이상이면 AV1까지 추가한다. AV1은 1080p에서 H.264 대비 약 47%를 절감하지만 **인코딩이 18배 느리다.**

바꾸는 게 아니라 **추가**하는 게 포인트다. H.264를 버리면 구형 기기에서 재생이 안 된다. 그래서 책의 "인코딩을 생략한다"는 실제로는 **"생략이 아니라 단계를 둔다"**였다.

### 유튜브는 18배를 그냥 내지 않았다

구글은 트랜스코딩 전용 칩을 만들었다. **Argos VCU**는 2015년에 개발을 시작해 2018년부터 데이터센터에 배치되고 2021년에 공개됐다. 기존 소프트웨어 방식 대비 20~33배 효율이라고 발표했고(코덱별로 H.264 약 7배, VP9 약 33배), 2세대는 AV1을 지원한다. 구글 자체 수치이고 독립 벤치마크는 아니다.

**"인코딩이 느리다"는 문제를 하드웨어 설계로 푼 것이다.** 14장이 "트랜스코딩 서버"라고 적은 네모 안에 이게 들어 있었다.
