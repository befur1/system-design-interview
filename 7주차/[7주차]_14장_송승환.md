## 비디오 업로드 절차

```
                      사용자 단말
                  (TV · 스마트폰 · 노트북)
             ┌──────────┴──────────┐
             │ 비디오 파일          │ 그 외 모든 요청
             ▼                     ▼
        원본 저장소              로드밸런서
             │                     │
             │                     ▼
             │                  API 서버
             │                  ┌──┴──┐
             │                  ▼     ▼
             │           메타데이터  메타데이터
             │              캐시      DB
             ▼                  ▲     ▲
      트랜스코딩 서버            │     │
             │                  └──┬──┘
             ├─ 트랜스코딩 완료 ─> 완료 큐 ─> 완료 핸들러
             ▼
    트랜스코딩 비디오 저장소
             │
             ▼
            CDN
```

**흐름이 두 갈래로 갈림**

- **왼쪽(비디오 파일)** — 단말이 원본 저장소에 직접 올리고, 트랜스코딩을 거쳐 CDN 까지
- **오른쪽(메타데이터)** — 로드밸런서 → API 서버 → 캐시·DB

그리고 **트랜스코딩 완료 핸들러가 두 갈래를 다시 이어줌.** 변환이 끝났다는 사실을 메타데이터 쪽에 반영해야 하니까 아래에서 위로 화살표가 올라감

#### 컴포넌트

| 컴포넌트 | 역할 |
| --- | --- |
| **사용자 단말** | TV, 스마트폰, 노트북 등 |
| **로드밸런서** | 요청을 API 서버들에 고르게 분산 |
| **API 서버** | **비디오 스트리밍을 제외한 모든 요청**을 처리 |
| **메타데이터 DB** | 비디오 메타데이터 보관. 샤딩·다중화 적용 |
| **메타데이터 캐시** | 성능을 위해 비디오 메타데이터와 사용자 객체를 캐시 |
| **원본 저장소** | 원본 비디오를 보관하는 **BLOB 저장소** |
| **트랜스코딩 서버** | 비디오 포맷(MPEG, HLS 등) 변환. **단말이나 대역폭 요구사항에 맞는 최적의 스트림을 제공**하기 위해 필요 |
| **트랜스코딩 비디오 저장소** | 변환이 끝난 비디오를 저장하는 BLOB 저장소 |
| **트랜스코딩 완료 큐** | 트랜스코딩 완료 이벤트를 보관하는 메시지 큐 |
| **트랜스코딩 완료 핸들러** | 큐에서 이벤트를 꺼내 **메타데이터 캐시와 DB 를 갱신** |
| **CDN** | 변환된 비디오를 캐시. 재생 버튼을 누르면 여기서 스트리밍됨 |

> **BLOB(Binary Large Object) 저장소** — 이미지·비디오 같은 큰 이진 파일을 통째로 저장하는 시스템. 관계형 DB 에 넣기엔 부적합한 덩어리를 다룸
> 

#### 짚어둘 것

**비디오 파일은 API 서버를 안 거침.** 단말에서 원본 저장소로 바로 감. 수십 MB~GB 짜리를 API 서버가 받아 넘기면 서버가 그동안 묶이니까

**API 서버는 스트리밍을 안 함.** 재생은 CDN 이 담당. API 서버는 메타데이터·인증 같은 가벼운 요청만 처리

**큐가 중간에 끼는 이유** — 트랜스코딩은 오래 걸리는 작업이라, 끝날 때까지 붙잡고 있으면 자원이 묶임. 완료 이벤트만 큐에 던지고 핸들러가 따로 처리하면 트랜스코딩 서버는 바로 다음 일을 받을 수 있음

### 메타데이터 DB

|  | 들고 있는 것 |
| --- | --- |
| **CDN** | 영상 파일 덩어리. 누구 건지·재생 가능한지는 모름 |
| **메타데이터 DB** | 제목, 소유자, **상태**, 준비된 화질 목록 |

영상 목록·제목·재생 버튼 상태는 전부 메타데이터 DB 에서 만들어짐. **CDN 은 재생 버튼을 누른 다음에야 등장함**

#### 상태가 바뀌는 지점

```
업로드 직후        { status: PROCESSING, renditions: [] }
                   → 화면: "처리 중입니다"

트랜스코딩 완료
  → 큐 → 핸들러 → { status: READY,
                     renditions: [1080p, 720p, 480p 의 CDN 주소] }
                   → 재생 버튼 활성화
```

**"처리 중"은 큐가 알려주는 게 아님.** 메타데이터에 아직 완료 표시가 없어서 그렇게 보이는 것

#### 왜 CDN 만으로는 안 되나

CDN 은 **주소를 알면 파일을 주는** 역할만 함. "이 유저의 영상 목록"같은 질의를 못 하고, 어떤 화질이 준비됐는지도 모름. 그 주소를 알려주는 게 메타데이터 DB

### 메타데이터 갱신

위와 같은 작업이 뒤에서 일어나는 동안 단말은 (파일 이름, 크기, 포맷 등) 정보를 넣어서 메타데이터 캐시와 DB를 업데이트 함

## 비디오 스트리밍 절차

다운로드 받아서 보는 것이 아닌 지속적으로 비디오 스트림을 전송 받아 영상을 재생하기 위해서는 스트리밍 프로토콜이 존재함. 

수 많은 프로토콜이 있지만, 각 프로토콜마다 지원하는 비디오 인코딩 방식 및 플레이어도 다름

## 비디오 트랜스코딩

비디오는 보통 특정 포맷으로 저장됨. 여러 단말에서 재생되려면 다른 단말과 호환되는 비트레이트(bitrate)와 포맷으로 저장되어야 함

비트레이트(bitrate)가 높은 비디오가 일반적으로 고화질 비디오로, 고화질 영상을 재생하려면 높은 컴퓨팅 파워가 필요함

- 가공되지 않은 원본 비디오는 저장 공간을 많이 차지 함
- 상당수의 단말과 브라우저는 특정 종류의 비디오 포맷만 지원
- 사용자에게 끊김없는 비디오 재생을 보장하려면, 네트워크 대역폭에 따른 화질 조정을 해주는 것이 좋음

인코딩 포멧은 아주 다양한데, 보통 다음 두 부분으로 구성

1. 컨테이너: .avi, .mov, .mp4 같은 확장자로서 비디오 파일, 오디오, 메타데이터를 담는 바구니
2. 코덱: 화질을 보존하면서 파일 크기를 줄일 목적으로 고안된 압축 및 압축 해제 알고리즘

## 유향 비순환 그래프(DAG) 모델

```
                      ┌──> 인스펙션
                      ├──> 비디오 인코딩
          ┌─ video ──┤
          │           ├──> 썸네일
          │           └──> 워터마크
원본 ────┤                                 ──> 합침 ──> 출력
          ├─ audio ──> 오디오 인코딩
          │
          └─ metadata
```

원본을 **영상·음성·메타데이터로 분리**한 뒤, 각 갈래에 필요한 작업을 붙이고 마지막에 합침

### 각 작업

| 작업 | 하는 일 |
| --- | --- |
| **인스펙션** | 비디오 품질·손상 여부 검사 |
| **비디오 인코딩** | 여러 해상도·코덱·비트레이트로 변환 |
| **썸네일** | 사용자가 올린 이미지를 쓰거나 영상에서 자동 추출 |
| **워터마크** | 식별 정보를 영상 위에 겹쳐 넣음 |
| **오디오 인코딩** | 음성 트랙을 변환 |

### 왜 그래프로 모델링하나

**① 영상마다 필요한 작업이 다름** — 워터마크가 필요 없는 영상도 있고, 썸네일을 직접 올린 사용자도 있음. 그래프에서 해당 노드만 빼면 됨

**② 독립적인 작업은 병렬로 돌릴 수 있음** — 썸네일 추출과 오디오 인코딩은 서로 상관이 없으니 동시에 진행. 의존 관계가 그래프에 적혀 있어서 **무엇을 병렬로 돌려도 되는지가 구조에서 드러남**

**③ 작업을 추가하기 쉬움** — 나중에 자막 생성이나 콘텐츠 검수가 필요해지면 **노드 하나를 붙이면 됨**. 기존 코드를 고치지 않아도 됨

## 비디오 트랜스코딩 아키텍처

1. 전처리기
    - 비디오 분할: 비디오 스트림을 GOP라고 불리는 단위로 쪼갬. GOP는 특정 순서로 배열된 프로임 그룹으로, 하나의 GOP는 독립적으로 재생 가능. (GOP 단위의 비디오 분할을 하지 않는 단말의 경우에는 전처리기 비디오 분할을 대신 함)
    - DAG 생성: 클라이언트 프로그래머가 작성한 설정 파일에 따라 DAG를 만들어 냄
    - 데이터 캐시: 전처리기는 분할된 비디오의 캐시로 GOP와 메타데이터를 임시 저장소에 보관
2. DAG 스케줄러: 다음 스텝인 자원 관리자의 작업 큐에 넣어주는 역할로 위에 그림처럼 생김
3. 자원 관리자
    
    ```
    ┌────────────────────── 자원 관리자 ──────────────────────┐
    │                                                         │
    │  ┌─────────────┐                      ┌──────────────┐ │
    │  │   작업 큐    │ ──①──┐        ┌──④─> │ 실행 중인     │ │
    │  │ (우선순위 큐)│       │        │      │   작업 큐     │ │
    │  └─────────────┘       ▼        │      └──────────────┘ │
    │                    ┌────────────┴─┐                     │
    │  ┌─────────────┐   │ 작업 스케줄러  │                     │
    │  │ 작업 서버 큐 │ ─②─>│            │                     │
    │  │ (우선순위 큐)│   └───────┬──────┘                     │
    │  └─────────────┘           │ ③                          │
    └────────────────────────────┼───────────────────────────┘
                                 ▼
                              작업 서버
    ```
    
    |  |  |
    | --- | --- |
    | **작업 큐** | 실행할 작업이 보관되는 우선순위 큐 |
    | **작업 서버 큐** | 작업 서버의 가용 상태가 보관되는 우선순위 큐 |
    | **실행 중인 작업 큐** | 현재 실행 중인 작업과 그 작업 서버 정보 |
    | **작업 스케줄러** | 최적의 작업·서버를 골라 실행을 지시 |
    
    ① 작업 큐에서 **우선순위가 가장 높은 작업**을 꺼냄
    ② 작업 서버 큐에서 **가장 적합한 작업 서버**를 고름
    ③ 그 작업 서버에게 **실행을 지시**
    ④ 할당 정보를 **실행 중인 작업 큐에 기록** (완료되면 제거)
    
4. 작업 서버: 워터마크, 인코딩, 섬네일, 병합과 같은 DAG에 정의된 작업을 수행
5. 임시 저장소
    - 메타 데이터와 같은 크기가 작은 것들은 메모리에 캐시해둠
    - 비디오/오디오 데이터는 BLOB 저장소에 두는 것이 바람직
6. 인코딩된 비디오: 최종 결과물임

## 시스템 최적화

### 속도 최적화

1. 속도를 높이기 위해서 원본 비디오를 올릴 때도 GOP로 분할해서 올림
2. 업로드 센터를 전세계 여러 곳에 두어, 거리로 인한 지연을 최소화 함
3. 비디오를 원본 저장소 → CDN으로 옮길 때, 전 단계의 의존성이 존재하는 걸 메세지 큐를 통해 의존성을 해결하여 병렬적으로 해결 가능

### 안전성 최적화

1. 미리 사인된 URL: 사용자가 POST 요청을 통해 URL을 API 서버로 부터 얻어서, 해당 URL로 안전하게 비디오를 업로드
2. 비디오 보호
    - 디지털 저작권 시스템 도입
    - AES 암호화
    - 워터마크

## CDN의 비용 최적화

1. 인기 비디오는 CDN을 통해서 재생하되, 다른 비디오는 비디오 서버를 통해서 재생
2. 인기 없는 비디오는 인코딩할 필요 없을 수도 있음
3. 어떤 비디오가 특정 지역에서만 인기가 높다면, 다른 지역 CDN으로 굳이 옮길 필요가 없음
4. CDN을 직접 구축하기 보다 대행 서비스를 이용(초기에는 비용이 현저히 적지만, 규모가 커질수록 직접 구축하는게 이득)

## 오류 처리

|  | 예 | 처리 |
| --- | --- | --- |
| **회복 가능** | 특정 비디오 세그먼트 트랜스코딩 실패 | 몇 번 재시도. 계속 실패하면 오류 코드 반환 |
| **회복 불가능** | 비디오 포맷 자체가 잘못됨 | 작업을 **중단**하고 오류 코드 반환 |

### 컴포넌트별 처리

| 어디서 난 오류 | 어떻게 처리하나 |
| --- | --- |
| 업로드 오류 | 몇 회 **재시도** |
| 비디오 분할 오류 | 구버전 클라이언트가 분할을 못 하면 **서버가 대신** 처리 |
| 트랜스코딩 오류 | **재시도** |
| 전처리 오류 | **DAG 를 재생성** |
| DAG 스케줄러 오류 | 작업을 **다시 스케줄링** |
| 자원 관리자 큐 장애 | **사본(replica)** 사용 |
| 작업 서버 장애 | **다른 서버**에서 해당 작업 재시도 |
| API 서버 장애 | **무상태**라서 다른 API 서버로 요청이 전달됨 |
| 메타데이터 캐시 서버 장애 | **다중화**해 뒀으므로 다른 노드에서 가져옴. 장애 서버는 새것으로 교체 |
| 메타데이터 DB 장애 | 주 서버가 죽으면 **부 서버 중 하나를 주 서버로 승격**. 부 서버가 죽으면 다른 부 서버를 쓰거나 새로 추가 |

### 패턴은 세 가지뿐

표가 길어 보이지만 **대응 방식은 셋으로 수렴함**
