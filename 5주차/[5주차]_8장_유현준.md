# [5주차] 8장 - URL 단축기 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

## 책 내용 뼈대

긴 URL을 짧은 URL로 바꾸고, 짧은 URL로 들어온 요청을 원래 주소로 돌려보내는 서비스를 설계한다.

### 규모 추정

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 쓰기 | 초당 약 1,160건 | 1억 건/일 / 86,400초 |
| 읽기 | 초당 약 11,600건 | 읽기:쓰기 = 10:1 |
| 10년간 레코드 | 3,650억 개 | 1억 x 365 x 10 |
| 저장 용량 | 약 36.5TB | 레코드당 평균 100바이트 |

### API 두 개

| | 단축 URL 생성 | 단축 URL 리다이렉션 |
| --- | --- | --- |
| 표기 | POST /api/v1/data/shorten | GET /api/v1/shortUrl |
| 요청 | {longUrl} | 없음 (경로가 식별자) |
| 응답 | {shortUrl} | 301 또는 302 + Location 헤더 |

### 301과 302

| | 301 영구 이동 | 302 임시 이동 |
| --- | --- | --- |
| 브라우저 | 응답을 캐시하고 다음부터 서버를 거치지 않음 | 매번 서버를 거침 |
| 서버 부하 | 적음 | 많음 |
| 트래픽 분석 | 어려움 | 가능 |

### 해시 함수 두 방식

필요한 길이는 62^n이 3,650억을 넘는 최소 n이라서 7글자다. 62^7은 약 3.5조다.

| | 해시 후 충돌 해소 | base-62 변환 |
| --- | --- | --- |
| 길이 | 고정 | 가변, ID가 커지면 길어짐 |
| 유일 ID 생성기 | 필요 없음 | 필요 |
| 충돌 | 가능, 해소 전략 필요 | 불가능 |
| 다음 URL 추측 | 불가능 | ID가 1씩 증가하면 쉽게 알아낼 수 있어 보안상 문제가 될 소지 |

해시 충돌 해소는 미리 정한 문자열을 덧붙여 다시 해시하는 방식인데 DB 조회가 매번 붙는다. 그래서 블룸 필터로 조회를 줄이는 방안이 언급된다.

### 마무리에서 언급되는 것

처리율 제한 장치, 웹 서버 규모 확장, DB 규모 확장, 데이터 분석 솔루션, 가용성과 일관성.

# 개인적인 질문

## 1. GET으로 단축 URL을 보내도 답이 오나

REST API에 익숙해진 상태로 책의 API 표를 보니 이상했다. GET인데 무슨 데이터를 보낸다는 건가 싶었다. 알아보니 표에 나란히 적힌 두 API가 성격이 완전히 다른 것이었다.

| | 단축 URL 생성 | 단축 URL 리다이렉션 |
| --- | --- | --- |
| 누가 호출하나 | 내 코드 (fetch, axios) | 브라우저가 직접 |
| 요청 본문 | {longUrl} JSON | 없음 |
| 응답 | {shortUrl} JSON | JSON이 아니라 리다이렉트 지시 |

첫 번째만 우리가 아는 REST API다. 두 번째는 API라기보다 사용자가 브라우저 주소창에 붙여넣는 주소다.

### 실제 흐름

```
브라우저 -> GET https://tinyurl.com/qtey5

서버     -> HTTP/1.1 301 Moved Permanently
            Location: https://www.youtube.com/watch?v=...
            (본문 없음)

브라우저 -> Location 헤더를 보고 스스로 이동
         -> GET https://www.youtube.com/watch?v=...
```

브라우저가 알아서 두 번 요청한다. 내 코드가 응답을 받아 처리하는 게 아니다. 그래서 답이 오냐는 질문의 답은, 오지만 JSON이 아니라 리다이렉트 지시가 온다는 것이다.

본문이 없는데 무엇을 찾아야 할지 어떻게 아느냐면 경로 자체가 데이터다. 스프링으로 쓰면 PathVariable이라 본문이 필요 없다.

```java
@GetMapping("/{shortId}")
public ResponseEntity<Void> redirect(@PathVariable String shortId) {
    String longUrl = urlService.getLongUrl(shortId);
    return ResponseEntity.status(HttpStatus.MOVED_PERMANENTLY)   // 301
            .location(URI.create(longUrl))
            .build();                                            // 본문 없음
}
```

ResponseEntity<Void>다. 반환할 데이터가 없고 상태코드와 헤더만 보낸다.

### 경로가 /api/v1/ 아래가 아니다

책 표기는 GET /api/v1/shortUrl인데 실제 서비스는 루트 바로 아래다.

```
tinyurl.com/qtey5                  <- 실제
tinyurl.com/api/v1/data/qtey5      <- 이러면 단축이 안 된다
```

짧은 게 상품인데 경로에 /api/v1/을 붙이면 본말전도다. URL 단축 서비스는 REST 관례를 일부러 깬다. 책 표기는 개념적으로 GET 요청이라는 뜻으로 읽어야 한다.

## 2. 브라우저 주소창은 무조건 GET인가, 로그와 메트릭 수집도 부수효과인가

### 주소창은 무조건 GET이다

주소창 입력, 링크 클릭, 북마크, img src, script src 전부 GET이다. GET이 아닌 건 form method가 post인 제출과 JS fetch로 메서드를 지정하는 경우뿐이다. 주소창으로는 GET 외에 보낼 방법이 없다.

그래서 GET으로 상태를 바꾸면 사고가 난다. GET /posts/5/delete 같은 걸 만들면 크롤러가 링크를 긁거나, 브라우저 프리페치, 메신저 링크 미리보기, 안티바이러스 URL 스캐너가 눌러버린다.

2005년 Google Web Accelerator가 페이지 링크를 미리 받아두는 기능을 넣었는데, 당시 웹앱들이 삭제와 수정을 a 태그 링크로 만들어놔서 그걸 전부 눌러 사용자 데이터가 날아간 사고가 있었다. 규칙이 괜히 있는 게 아니었다.

### 보통 GET도 거의 다 기록한다

| 기록되는 것 | 어디서 |
| --- | --- |
| 액세스 로그 | Nginx, 톰캣 필터 |
| http.server.requests 카운터 | Actuator |
| 세션 마지막 접근 시각 | 세션 저장소 |
| 조회수, 추천 알고리즘 학습 데이터 | 애플리케이션 |

GET 요청 한 번에 서버 상태가 여러 군데 바뀐다. 아무것도 안 바뀌는 GET은 현실에 거의 없다.

### 그럼 safe의 기준이 무엇인가

여기가 핵심이었다. HTTP 명세(RFC 9110)가 safe를 정의할 때 서버에 아무 영향이 없다는 뜻이 아니다. 명세는 로깅이나 카운터 증가 같은 건 safe 메서드에서도 일어날 수 있고 그래도 여전히 safe라고 한다.

기준은 클라이언트가 그 변화를 요청했는가다.

| 일어나는 일 | 클라이언트가 요청했나 | safe |
| --- | --- | --- |
| 액세스 로그 기록 | 아니오, 서버가 알아서 | safe |
| 메트릭 카운터 증가 | 아니오 | safe |
| 조회수 증가 | 아니오, 사용자는 보여달라고만 했다 | safe |
| 게시글 삭제 | 예 | unsafe |

사용자는 이 URL로 보내달라고 했을 뿐 카운터를 올려달라고 한 적이 없다. 그래서 책이 말하는 클릭 통계 기록은 safe다.

실무에서 쓰는 판정법은 크롤러가 이 주소를 긁어도 괜찮은가다. 조회수가 올라가면 통계가 좀 더러워지는 정도지만, 글이 삭제되면 재앙이다. 이 테스트가 명세의 기준과 사실상 같다.

## 3. base-62 변환은 단축 URL이 추측 가능해지는 게 아닌가 - 4주차와 이어지는 부분

ID가 순차면 단축 URL도 순차가 된다.

```
tinyurl.com/a1
tinyurl.com/a2      <- 1씩 올려가며 긁으면
tinyurl.com/a3         남이 만든 단축 URL이 전부 나온다
```

4주차에 팠던 문제와 같다. URL에 순차 ID를 노출하면 총량이 유출되고 남의 것을 추측할 수 있다는 것. 그때 내린 결론은 PK는 IDENTITY로 두고 외부 노출용 UUID를 따로 두자는 것이었다.

그런데 여기서는 그 해법이 통하지 않는다. 짧은 게 상품이니까. tinyurl.com/8f3a2c1e-... 는 단축이 아니다.

### 피해갈 수 없는 긴장

| | 짧음 | 추측 불가능성 |
| --- | --- | --- |
| 순차 ID를 base62로 | 매우 짧음 (a1) | 없음 |
| 랜덤 7글자 | 7글자 | 62^7 약 3.5조 중 하나 |

짧게 하려면 키 공간이 작아야 하고, 키 공간이 작으면 전수조사가 가능해진다. 그리고 단축 URL에는 초대 링크, 결제 링크, 비공개 문서가 담기기도 한다.

책도 비교 표에 base-62의 단점으로 다음 단축 URL을 쉽게 알아낼 수 있어 보안상 문제가 될 소지가 있다고 적어뒀다. 다루지 않는 건 그래서 어떻게 해야 하는지다. 해시 방식으로 가면 추측은 막히지만 충돌 해소 비용이 생기고, base-62로 가면 그 반대다. 이슈 질문으로 올렸다.

### 4주차와 다른 점

4주차에서는 Long id와 UUID publicId를 둘 다 가지면 끝나는 문제였다. 비용이 컬럼 하나였으니까. 여기서는 그 선택이 상품 가치를 깎는다. 같은 문제가 제품의 성격에 따라 해결 가능한 문제였다가 트레이드오프가 된다는 게 인상적이었다.

## 4. 단축 URL은 언제 만들어지나, 그리고 301을 쓸 수 있나

책을 읽으면서 생성 시점이 궁금했다. 브라우저에서 주소를 복사하면 단축 URL이 나오는 건 아니니까.

### 브라우저는 단축 기능이 없다

주소창 텍스트를 복사하면 그냥 그 문자열이다. 긴 URL이 나온다. 단축은 누군가 명시적으로 하는 동작이다.

| 어디서 복사하나 | 나오는 것 |
| --- | --- |
| 브라우저 주소창 | youtube.com/watch?v=dQw4w9WgXcQ |
| 앱 공유 버튼 | youtu.be/dQw4w9WgXcQ |

유튜브는 youtu.be라는 자기 단축 도메인을 따로 운영한다.

### 단축 URL이 생기는 경로

| 경로 | 설명 |
| --- | --- |
| 앱의 공유 버튼 | 서비스가 자기 단축 도메인으로 발급 |
| 플랫폼이 치환 | 트위터는 올라온 링크를 전부 t.co로 바꾼다. 사용자가 요청한 게 아니다 |
| 사용자가 직접 서비스 이용 | bit.ly에 긴 URL을 붙여넣는다. 책이 설계하는 게 이것 |
| 마케팅 도구가 자동 생성 | 이메일, SMS 발송 시 수신자마다 다른 단축 URL로 클릭을 추적 |

### 왜 단축하나, 길이가 1순위가 아니다

| 이유 | 설명 |
| --- | --- |
| 길이 | SMS 160자, 인쇄물, QR 코드 |
| 추적 | 누가 언제 어디서 클릭했는지 |
| 목적지 변경 | 링크는 그대로 두고 도착지만 바꿀 수 있다 |

세 번째가 의외로 크다. 전단지에 QR을 박아 10만 장 뿌렸는데 랜딩 페이지 주소가 바뀌면, 긴 URL을 직접 박았으면 10만 장이 쓰레기가 된다. 단축 URL이면 매핑만 고치면 끝이다.

### 그래서 301과 302의 선택이 비즈니스 결정이 된다

책은 301이 부하가 적고 302가 분석이 가능하다고 대등하게 비교한다. 그런데 위의 두 가치를 생각하면 301을 고를 수 있는 경우가 거의 없어 보인다.

| | 301 | 302 |
| --- | --- | --- |
| 클릭 추적 | 불가능, 요청이 서버에 안 온다 | 가능 |
| 목적지 변경 | 먹히지 않는다, 브라우저 캐시 때문 | 즉시 반영 |

301을 쓰면 단축 URL의 가치 두 개가 동시에 망가진다. 추적도 못 하고, 목적지를 바꿔도 이미 한 번 누른 사람에게는 옛 주소로 간다. 그래서 실제 단축 서비스는 서버 부하를 더 받는 걸 감수하고 302를 쓴다. 이것도 이슈 질문으로 올렸다.

## 3주차와 연계해서 생각해보자

마무리에 처리율 제한 장치가 또 나온다. 3주차에 팠던 그것이다.

단축 URL 서비스는 처리율 제한을 걸 자리가 두 군데다.

| 어디에 | 막는 것 |
| --- | --- |
| 생성 API (POST) | 스팸 링크 대량 생성 |
| 리다이렉션 (GET) | 순차 ID를 1씩 올려가며 긁는 전수조사 |

두 번째가 3번 질문과 이어진다. 추측 가능성을 설계로 못 막으면 처리율 제한으로 긁는 속도를 늦추는 수밖에 없다. 키 공간을 못 키울 때 남는 방어선이 처리율 제한이라는 게, 3주차 내용이 8장에서 다른 쓸모로 돌아온 지점이다.
