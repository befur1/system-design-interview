# 10장_ 알림 시스템 설계

## 알림 시스템이란
알림 시스템은 사용자에게 중요한 정보를 비동기적으로 전달하는 시스템임.
- 알림 유형과 전달 경로
    - iOS 푸시: 애플의 APNS를 거쳐 전송하며, 기기 토큰이 필요함.
    - 안드로이드 푸시: 구글의 FCM을 거쳐 전송하며, 기기 토큰이 필요함.
    - SMS: Twilio 같은 외부 문자 발송 서비스를 이용하며, 전화번호가 필요함.
    - 이메일: Sendgrid 같은 외부 메일 발송 서비스를 이용하며, 이메일 주소가 필요함.
- 앱 설치나 회원가입 시 기기 토큰, 전화번호, 이메일 주소를 수집해 DB에 저장함. 한 사용자가 여러 기기를 가질 수 있으므로 기기 정보는 별도로 관리함.

## 설계 범위
- 하루 천만 건의 모바일 푸시, 백만 건의 SMS, 5백만 건의 이메일 전송
- 알림은 가능한 한 빨리 전달하되, 부하가 높을 때는 약간의 지연을 허용함.
- 사용자는 알림 수신을 거부할 수 있어야 함.

## 개략적 설계

초기 설계의 문제점
- 알림 서버 한 대가 모든 알림을 처리하면 단일 장애 지점이 됨.
- 규모 확장이 어렵고, 외부 서비스 응답이 느리면 전체 알림 처리가 지연되는 성능 병목이 발생함.

개선된 설계
- DB와 캐시를 알림 서버와 분리하고, 알림 서버를 여러 대로 늘려 수평 확장함.
- 알림 서버와 전송 작업 사이에 알림 종류별 메시지 큐를 두어 컴포넌트 간 결합을 끊음.
    - 한 외부 서비스에 장애가 생겨도 다른 종류의 알림은 영향을 받지 않음.
    - 알림이 몰리면 큐에 쌓아두고 작업 서버가 차례로 처리함.
- 작업 흐름
    - 각 서비스가 알림 서버의 API를 호출함.
    - 알림 서버는 요청을 검증하고, 캐시나 DB에서 사용자 정보와 기기 토큰, 수신 설정을 조회함.
    - 알림 이벤트를 종류별 메시지 큐에 넣음.
    - 작업 서버가 큐에서 이벤트를 꺼내 외부 서비스로 전송함.
    - 외부 서비스가 사용자 기기로 알림을 전달함.
- 알림 서버의 역할: 알림 전송 API 제공, 요청 검증, 인증된 내부 서비스만 호출 가능하도록 제한, 처리율 제한

## 상세 설계

안정성
- 데이터 손실 방지: 알림 로그를 DB에 보관하고, 전송 실패 시 재시도함.
- 중복 전송 방지: 분산 환경에서 정확히 한 번만 전송하는 것은 보장하기 어려우므로, 이벤트 ID로 이미 보낸 알림인지 확인해 중복을 줄임.

추가 컴포넌트와 고려사항
- 알림 템플릿: 형식이 비슷한 알림은 템플릿을 만들어 재사용해 일관성을 유지하고 오류를 줄임.
- 알림 설정: 사용자가 알림 종류와 채널별로 수신 여부를 설정할 수 있게 하고, 전송 전에 반드시 확인함.
- 처리율 제한: 한 사용자가 받을 수 있는 알림 빈도를 제한해 알림 피로를 막음.
- 재시도 메커니즘: 전송에 실패한 알림은 큐에 다시 넣고, 계속 실패하면 개발자에게 통지함.
- 보안: 인증된 클라이언트만 알림 API를 호출할 수 있도록 appKey, appSecret 등을 사용함.
- 큐 모니터링: 큐에 쌓인 알림 수가 많으면 작업 서버를 증설함.
- 이벤트 추적: 알림 열람률, 클릭률 등을 추적해 사용자 행동을 분석함.

## 크롤링 서비스와 알림 시스템 연계

이전 9장 정리에 썼던 예시 2가지와 10장 내용을 연결해보면 아래와 같은 방식으로 생각해볼 수 있음.

예시 1: 학교 공지사항 통합 서비스 + 새 공지 알림
- 이벤트 발생: 크롤러가 새 공지를 감지하면 알림 서버의 API를 호출해 알림 이벤트를 생성함.
- 알림 설정 활용: 사용자가 구독한 기관(국제교류처, 교양과, 소속 학과 등)과 키워드(장학, 수강신청, 교환학생 등)에 해당하는 공지만 전송함.
- 중복 방지: 같은 공지가 공식 홈페이지와 학과 홈페이지에 동시에 올라오면 크롤러가 두 번 감지할 수 있으므로, 공지 제목과 본문의 해시 값을 이벤트 ID처럼 사용해 한 번만 알림을 보냄. (9장 중복 콘텐츠 확인과 연결)
- 처리율 제한과 묶음 전송: 학기 초처럼 공지가 한꺼번에 많이 올라오면 하나씩 보내지 않고 "새 공지 5건"처럼 묶어서 보내 알림 피로를 줄임.
- 알림 템플릿: "[기관명] 공지 제목" 형식의 템플릿으로 일관된 알림을 보냄.
- 이벤트 추적: 어떤 기관과 키워드의 공지가 많이 열람되는지 분석해 기본 구독 설정이나 추천에 활용함.

예시 2: 공동구매 사이트 모음 서비스 + 가격·마감 알림
- 이벤트 발생: 크롤러가 관심 상품의 가격 하락, 재입고, 마감 임박을 감지하면 알림 이벤트를 생성함.
- 알림 설정 활용: 사용자가 관심 등록한 상품이나 원하는 가격 조건에 해당할 때만 전송함.
- 처리율 제한: 가격이 자주 바뀌는 상품은 변동마다 보내지 않고, 일정 비율 이상 하락했을 때나 하루 한 번 정도로 제한해 스팸처럼 느껴지지 않게 함.
- 중복 방지: "사용자 + 상품 + 이벤트 종류"를 기준으로 이미 보낸 알림인지 확인해 같은 내용을 반복 전송하지 않음.
- 우선순위: 마감 임박 알림은 시간이 지나면 의미가 없으므로 별도 큐로 분리해 먼저 처리함.
- 재시도의 한계: 이미 마감된 상품의 알림은 재시도해도 의미가 없으므로, 알림에 유효 시간을 두고 지난 알림은 버림.

실무 관점에서의 적용 규모
- 책의 설계는 하루 수천만 건 규모를 기준으로 하지만, 학교 공지나 공동구매 모음 같은 소규모 프로젝트는 이를 그대로 구현할 필요가 없음.
- 푸시는 FCM 하나로 안드로이드와 iOS를 함께 처리할 수 있고, 메시지 큐는 간단한 큐 서비스나 DB 테이블과 스케줄러로 대체할 수 있음.
- 다만 알림 설정 확인, 중복 방지, 처리율 제한은 규모와 관계없이 사용자 경험에 직접 영향을 주므로 소규모에서도 반드시 고려해야 함. --> 이게 당장 우리가 고려할 범위
