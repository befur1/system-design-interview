# 9장: 웹 크롤러 설계

## 웹 크롤러란?

웹 크롤러는 웹 페이지를 내려받고, 페이지 안의 링크를 추출한 뒤 그 링크를 따라가며 새로운 콘텐츠를 수집하는 시스템이다.

웹 페이지뿐 아니라 이미지, 동영상, PDF 등도 수집 대상이 될 수 있다.

대표적인 활용 사례는 다음과 같다.

- 검색 엔진 인덱싱: 검색에 사용할 웹 페이지를 수집한다.
- 웹 아카이빙: 웹 콘텐츠를 장기간 보관한다.
- 웹 마이닝: 수집한 데이터에서 유용한 정보를 도출한다.
- 웹 모니터링: 콘텐츠 변경이나 저작물의 무단 사용 등을 감시한다.

기본 알고리즘은 단순하지만, 대규모로 운영하려면 중복 처리, 수집 순서, 대상 서버의 부하, 장애 복구 등을 함께 설계해야 한다.

## 1단계: 문제 이해 및 설계 범위 확정

### 요구사항

책에서는 다음 조건을 가정한다.

- 검색 엔진 인덱싱을 위한 크롤러를 설계한다.
- 매달 10억 개의 웹 페이지를 수집한다.
- 새로 만들어지거나 수정된 페이지도 수집한다.
- 수집한 페이지는 5년간 보관한다.
- 중복 콘텐츠는 별도로 처리하지 않아도 된다.

### 좋은 크롤러가 갖춰야 할 특성

| 특성 | 의미 |
| --- | --- |
| 규모 확장성 | 여러 서버와 작업 스레드로 대량의 페이지를 수집할 수 있어야 한다. |
| 안정성 | 잘못된 HTML, 느린 서버, 장애 등의 상황에서도 전체 작업이 중단되지 않아야 한다. |
| 예의 | 특정 웹사이트에 짧은 시간 동안 요청을 집중시키지 않아야 한다. |
| 확장성 | 이미지 수집 등 새로운 기능을 추가하기 쉬워야 한다. |

여기서 규모 확장성은 처리량을 늘리는 능력이고, 확장성은 새로운 기능이나 콘텐츠 유형을 지원하는 능력이다.

### 개략적 규모 추정

한 달을 30일로 계산하고 웹 페이지의 평균 크기를 500KB로 가정한다.

| 항목 | 계산 | 추정치 |
| --- | --- | --- |
| 월간 수집량 | 주어진 요구사항 | 10억 페이지 |
| 평균 처리량 | 10억 / 30 / 24 / 3,600 | 약 400페이지/초 |
| 최대 처리량 | 평균의 2배로 가정 | 약 800페이지/초 |
| 월간 저장량 | 10억 × 500KB | 약 500TB |
| 5년간 저장량 | 500TB × 12 × 5 | 약 30PB |

최대 처리량의 2배 가정은 이 설계에서 선택한 값이다. 실제 운영에서는 요청량과 처리 시간의 분포를 확인해야 한다.

또한 저장량에는 압축과 중복 제거에 따른 감소, 메타데이터와 복제본에 따른 증가가 반영되지 않았다.

## 2단계: 개략적 설계안 제시 및 동의 구하기

### 주요 컴포넌트

| 컴포넌트 | 역할 |
| --- | --- |
| 시작 URL 집합 | 수집을 시작할 주소를 제공한다. |
| 미수집 URL 저장소 | 앞으로 수집할 URL과 수집 순서를 관리한다. |
| HTML 다운로더 | 대상 서버에 HTTP 요청을 보내 페이지를 내려받는다. |
| 도메인 이름 변환기 | 호스트 이름에 대응하는 IP 주소를 조회한다. |
| 콘텐츠 파서 | 내려받은 문서를 분석하고 형식을 검증한다. |
| 중복 콘텐츠 판별기 | 이미 저장한 콘텐츠인지 확인한다. |
| 콘텐츠 저장소 | 수집한 문서를 보관한다. |
| URL 추출기 | 문서에서 링크를 추출한다. |
| URL 필터 | 수집 범위에 맞지 않는 URL을 제외한다. |
| URL 중복 판별기 | 이미 발견하거나 처리한 URL의 중복 등록을 방지한다. |
| URL 저장소 | URL과 처리 상태를 보관한다. |

### 시작 URL 집합

크롤러가 탐색을 시작하는 출발점이다.

특정 대학의 웹사이트를 수집한다면 해당 대학의 주요 페이지를 시작점으로 사용할 수 있다.

전체 웹을 수집하려면 다양한 페이지로 연결될 수 있는 시작점을 골라야 한다.

- 국가나 지역별 대표 사이트를 선정한다.
- 쇼핑, 스포츠, 건강 등 주제별 사이트를 선정한다.
- 여러 범주의 시작 URL을 함께 사용한다.

정해진 하나의 정답보다 수집 목적에 맞게 시작점을 선택하는 것이 중요하다.

### 미수집 URL 저장소

앞으로 다운로드할 URL을 보관하는 컴포넌트로, URL frontier라고 부른다.

기본적으로는 큐로 생각할 수 있지만, 실제로는 다음 조건을 반영해 수집 순서를 결정해야 한다.

- 어떤 URL이 더 중요한가?
- 같은 호스트에 언제 다시 요청할 수 있는가?
- 어떤 페이지를 다시 수집해야 하는가?

따라서 단순한 대기 목록을 넘어 크롤링 작업의 스케줄러 역할을 한다.

### HTML 다운로더와 도메인 이름 변환기

HTML 다운로더는 미수집 URL 저장소에서 작업을 받아 HTTP 요청을 수행한다.

도메인에 접속하려면 먼저 호스트 이름을 IP 주소로 변환하는 DNS 조회가 필요하다.

여러 페이지를 같은 호스트에서 가져오는 경우가 많으므로 DNS 조회 결과를 캐시하면 반복 조회 비용을 줄일 수 있다.

### 콘텐츠 파서

내려받은 HTML을 분석하고 올바른 형식인지 검증한다.

외부 웹 페이지는 형식이 잘못되었거나 예외적인 내용을 포함할 수 있으므로, 파싱 실패가 전체 수집 작업을 중단시키지 않도록 해야 한다.

다운로드와 파싱을 별도 컴포넌트로 나누면 각 단계의 처리량을 독립적으로 조절하기도 쉽다.

### 중복 콘텐츠 판별과 콘텐츠 저장소

주소가 달라도 같은 콘텐츠를 제공하는 페이지가 있을 수 있다.

모든 문서를 직접 비교하면 비용이 크므로 해시나 체크섬으로 만든 콘텐츠 지문을 활용해 중복 여부를 검사한다.

수집한 문서는 양이 크므로 대부분 디스크에 저장하고, 자주 접근하는 데이터는 메모리에 두어 접근 시간을 줄일 수 있다.

URL 중복과 콘텐츠 중복은 구분해야 한다.

- URL 중복: 같은 주소를 여러 번 발견한 경우
- 콘텐츠 중복: 서로 다른 주소에서 같은 내용을 내려받은 경우

URL 중복 제거는 불필요한 다운로드를 줄이고, 콘텐츠 중복 제거는 중복 저장과 후속 처리를 줄인다.

### URL 추출기

HTML 안의 링크를 찾아 다음 수집 후보를 만든다.

상대 경로는 현재 문서의 기준 URL을 바탕으로 절대 URL로 변환해야 한다.

예를 들어 기준 주소가 `https://example.com/news/`이고 링크가 `today.html`이라면, 수집할 주소는 `https://example.com/news/today.html`이다.

### URL 필터

추출한 URL 중 수집할 필요가 없는 주소를 제외한다.

- 지원하지 않는 파일 형식
- 수집 범위를 벗어난 도메인
- 접근 제외 목록에 등록된 주소
- 유효하지 않은 URL
- 스팸이나 반복 수집을 유발하는 주소

### URL 중복 판별과 URL 저장소

여러 페이지에서 같은 링크를 발견할 수 있으므로 이미 등록한 URL인지 확인해야 한다.

이를 통해 같은 URL이 큐에 계속 추가되거나 링크를 따라 무한히 순환하는 일을 줄일 수 있다.

해시 테이블이나 블룸 필터 등을 활용할 수 있다.

다만 '이미 발견한 URL', '수집 대기 중인 URL', '수집이 완료된 URL'은 서로 다른 상태다. 장애 복구와 재수집까지 고려한다면 이 상태를 구분해서 관리해야 한다.

### 전체 작업 흐름

1. 시작 URL을 미수집 URL 저장소에 등록한다.
2. 다운로더가 수집할 URL을 가져온다.
3. DNS 조회를 통해 대상 호스트의 IP 주소를 확인한다.
4. HTTP 요청으로 페이지를 내려받는다.
5. 콘텐츠를 파싱하고 유효성을 검증한다.
6. 중복 콘텐츠인지 검사하고 필요한 문서를 저장한다.
7. 문서에서 링크를 추출한다.
8. 상대 URL 변환과 URL 필터링을 수행한다.
9. 이미 등록하거나 처리한 URL인지 확인한다.
10. 새로운 URL을 저장하고 미수집 URL 저장소에 추가한다.
11. 같은 과정을 반복한다.

## 3단계: 상세 설계

### DFS와 BFS 중 무엇을 사용할 것인가?

웹은 페이지를 노드, 링크를 간선으로 보는 방향 그래프로 생각할 수 있다.

DFS는 한 경로를 깊게 탐색한다. 하지만 웹에서는 끝없이 깊어지는 경로나 반복되는 링크를 만날 수 있어 탐색 깊이를 통제하기 어렵다.

따라서 일반적으로 BFS를 기본으로 사용한다.

다만 단순한 BFS에도 문제가 있다.

- 한 페이지의 링크가 같은 호스트에 집중되어 있으면 요청도 그 호스트에 몰린다.
- 먼저 발견한 순서만 따르므로 페이지의 중요도를 반영하지 못한다.

이를 보완하기 위해 미수집 URL 저장소에서 예의와 우선순위를 관리한다.

### 미수집 URL 저장소의 상세 설계

#### 예의: 같은 호스트에 요청을 집중시키지 않기

우리 크롤러의 처리량을 높이더라도 상대 웹사이트가 감당할 수 있는 요청량은 제한되어 있다.

따라서 같은 호스트의 URL은 같은 처리 경로로 모으고, 순차적으로 다운로드하거나 요청 사이에 간격을 두어야 한다.

| 구성 요소 | 역할 |
| --- | --- |
| 큐 라우터 | 같은 호스트의 URL을 같은 큐로 전달한다. |
| 매핑 테이블 | 호스트와 담당 큐의 관계를 관리한다. |
| 호스트별 큐 | 해당 호스트의 수집 대상을 보관한다. |
| 큐 선택기 | 요청 가능한 큐에서 작업을 선택한다. |
| 작업 스레드 | URL을 내려받고 요청 간격을 지킨다. |

핵심은 서로 다른 호스트의 요청은 병렬로 처리하면서도, 같은 호스트에 대한 요청량은 통제하는 것이다.

#### 우선순위: 중요한 페이지를 먼저 수집하기

모든 페이지가 같은 중요도를 갖지는 않는다.

다음 정보를 기준으로 우선순위를 정할 수 있다.

- 페이지랭크 등 중요도
- 사용자 트래픽
- 콘텐츠 갱신 빈도
- 수집 목적과의 관련성

순위 결정 장치가 URL의 우선순위를 계산하고, 우선순위별 큐에 배정한다. 큐 선택기는 우선순위가 높은 큐를 더 자주 선택한다.

#### 전면 큐와 후면 큐

책에서는 우선순위와 예의를 담당하는 큐를 나눈다.

- 전면 큐: 어떤 URL을 먼저 처리할지 결정한다.
- 후면 큐: 같은 호스트에 요청이 몰리지 않도록 제어한다.

중요한 URL을 먼저 선택하더라도 해당 호스트에 아직 요청하면 안 되는 시점이라면 기다려야 한다.

#### 신선도: 이미 수집한 페이지 다시 방문하기

웹 페이지는 계속 추가·수정·삭제된다.

따라서 한 번 수집한 URL을 영구적으로 제외해서는 최신 정보를 유지할 수 없다.

재수집 주기를 정할 때는 다음을 고려한다.

- 과거에 얼마나 자주 변경되었는가?
- 얼마나 중요한 페이지인가?
- 마지막으로 언제 수집했는가?

변경이 잦거나 중요한 페이지는 더 자주 방문하고, 거의 변하지 않는 페이지는 방문 간격을 늘릴 수 있다.

#### 미수집 URL 저장소의 지속성

수집할 URL을 모두 메모리에 보관하면 메모리 사용량이 커지고 재시작 시 작업을 잃을 수 있다.

반대로 모든 작업을 디스크에서 직접 읽고 쓰면 I/O가 병목이 될 수 있다.

책에서는 대부분의 URL을 디스크에 보관하면서 메모리 버퍼를 함께 사용하는 절충안을 제시한다.

버퍼의 데이터는 지속성 저장소에 기록하여 장애 이후에도 작업을 복구할 수 있어야 한다.

### HTML 다운로더

#### robots.txt

`robots.txt`는 웹사이트가 크롤러에 수집 규칙을 전달하는 파일이다.

크롤러는 대상 사이트의 규칙을 확인하고 해당 경로를 수집할 수 있는지 판단해야 한다.

- `User-agent`: 규칙을 적용할 크롤러
- `Allow`: 수집을 허용하는 경로
- `Disallow`: 수집을 제한하는 경로

파일을 매번 내려받지 않도록 캐시하되, 변경을 반영할 수 있도록 갱신해야 한다.

다만 `robots.txt`는 크롤러가 따르도록 제공하는 규칙이다. 비공개 데이터를 보호하는 인증·권한 검사 기능을 대신하지 않는다.

#### 분산 크롤링

다운로드 작업을 여러 서버에 나누고, 각 서버에서 여러 작업 스레드를 실행한다.

URL 공간을 나누어 서버별 담당 범위를 정하면 처리량을 늘릴 수 있다.

이때 같은 호스트의 요청 제한이 여러 서버에 걸쳐서도 유지되어야 한다.

#### DNS 조회 결과 캐시

동기 방식의 DNS 조회는 결과가 올 때까지 해당 작업 흐름을 기다리게 한다.

반복되는 DNS 조회를 줄이기 위해 호스트 이름과 IP 주소의 매핑을 캐시한다.

다만 DNS 레코드는 변경될 수 있으므로 캐시를 무기한 유지하지 않고 TTL과 갱신 정책을 고려해야 한다.

#### 지역성 활용

수집 서버가 대상 웹사이트와 지리적으로 가까우면 네트워크 지연을 줄일 수 있다.

지역성은 다운로드 서버뿐 아니라 큐, 캐시, 저장소의 배치에도 고려할 수 있다.

#### 타임아웃

느리거나 응답하지 않는 서버를 무한히 기다리면 작업 스레드가 묶인다.

따라서 대기 시간을 제한하고, 시간이 초과되면 해당 작업을 중단한 뒤 다른 작업을 처리해야 한다.

다시 시도할 작업이라면 즉시 반복 요청하기보다 재시도 횟수와 대기 간격을 정해야 한다.

### 안정성 확보 전략

- 안정 해시를 활용해 다운로드 서버 간 작업을 분산한다.
- URL 처리 상태와 수집 결과를 지속성 저장소에 보관한다.
- 특정 페이지의 다운로드나 파싱 실패가 전체 작업을 중단시키지 않도록 예외를 처리한다.
- 콘텐츠와 URL을 검증해 비정상적인 입력에 대응한다.

안정 해시는 서버 추가·제거 시 담당 범위 변화를 줄이는 데 도움을 준다. 작업 유실 방지나 장애 복구까지 자동으로 해결하는 것은 아니다.

### 새로운 콘텐츠를 지원하기 위한 확장성

다운로드, 파싱, URL 추출 등의 역할을 모듈로 나누면 새로운 기능을 추가하기 쉽다.

예를 들어 다음 모듈을 추가할 수 있다.

- 이미지 다운로드 모듈
- PDF 처리 모듈
- 웹 모니터링 모듈

콘텐츠 유형이 추가될 때 기존 수집 시스템 전체를 다시 만들지 않도록 인터페이스와 처리 단계를 구분하는 것이 중요하다.

### 문제 있는 콘텐츠 감지와 회피

#### 중복 콘텐츠

해시나 체크섬을 활용해 같은 콘텐츠를 반복 저장하지 않도록 한다.

다만 내용 일부만 다른 문서는 단순한 전체 문서 해시만으로 중복이라고 판단하기 어렵다. 어느 범위까지 같은 콘텐츠로 취급할지도 수집 목적에 따라 달라진다.

#### 거미 덫

거미 덫은 크롤러가 끝없이 새로운 링크를 따라가도록 만드는 구조다.

반복되는 경로나 무한히 증가하는 쿼리 파라미터 등이 원인이 될 수 있다.

대응 방법은 다음과 같다.

- URL 최대 길이와 탐색 깊이를 제한한다.
- 같은 호스트에서 수집할 페이지 수를 제한한다.
- 반복적인 URL 패턴을 감지한다.
- 문제가 있는 경로나 사이트를 필터에 등록한다.

모든 형태의 덫을 하나의 규칙으로 완전히 방지하기는 어렵다.

#### 데이터 노이즈

수집 목적에 도움이 되지 않는 광고, 스팸, 불필요한 스크립트 등의 처리를 고려한다.

무엇을 제거할지는 수집 목적에 따라 달라진다. 검색용 텍스트를 만드는 작업과 원본 페이지를 보존하는 아카이빙은 같은 기준을 적용하기 어렵다.

## 4단계: 설계 후 추가로 고려할 사항

### JavaScript로 생성되는 콘텐츠

일부 페이지는 최초 HTML에 본문과 링크가 없고, JavaScript 실행 이후에 콘텐츠가 만들어진다.

이 경우 HTML 다운로드와 파싱만으로는 사용자가 보는 내용을 수집할 수 없다.

필요한 페이지에는 JavaScript 렌더링 단계를 추가하거나, 사이트가 제공하는 서버 렌더링 HTML을 활용하는 방법을 고려할 수 있다.

다만 렌더링은 자원 소모가 크므로 단순 HTML 수집과 구분해서 처리하는 편이 좋다.

### 데이터 계층과 작업 서버의 확장

- 저장소는 복제와 샤딩을 통해 가용성과 처리 용량을 높인다.
- 작업 서버를 추가해 다운로드와 파싱 처리량을 늘린다.
- 복구에 필요한 상태를 특정 서버의 메모리에만 보관하지 않는다.
- 서버를 늘려도 호스트별 요청 제한과 중복 방지가 유지되어야 한다.

### 모니터링과 데이터 분석

시스템을 조정하려면 처리량뿐 아니라 병목과 실패 원인을 파악해야 한다.

- 초당 다운로드 성공 페이지 수
- 다운로드와 파싱의 지연시간
- 대기 중인 URL 수와 대기 시간
- 호스트별 오류율과 요청량
- 타임아웃과 재시도 비율
- 중복 콘텐츠 비율
- 재수집 지연과 데이터 신선도

작업 서버의 CPU 사용률이 낮더라도 네트워크 지연이나 호스트별 요청 간격 때문에 처리량이 낮을 수 있다.

## 생각해본 질문

### React로 만든 페이지는 HTTP 요청으로 HTML만 받아도 화면의 내용을 수집할 수 있을까?

React에서 API를 호출해 화면을 구성했던 경험과 연결된다.

브라우저는 HTML을 받은 뒤 JavaScript를 실행하고 API를 호출해 화면을 만든다. 반면 단순한 HTML 다운로더는 그 최초 응답만 받을 수 있다.

따라서 초기 HTML에 본문이 없다면, 브라우저에서 보이는 내용과 수집한 내용이 달라질 수 있다.

이때는 다음 방법을 비교해볼 수 있다.

- 사용할 수 있는 공식 API에서 데이터를 받는다.
- HTML에 필요한 콘텐츠가 포함되어 있는지 확인한다.
- 필요한 페이지에만 JavaScript 렌더링을 적용한다.

TMDB API로 JSON을 받아 화면에 표시하는 것과, 완성된 웹 화면에서 데이터를 추출하는 것은 어떤 차이가 있을까?

### 작업 서버를 늘리면 같은 사이트의 요청 제한도 그대로 유지될까?

4장에서 배운 처리율 제한과 연결되는 문제다.

각 서버가 특정 호스트에 초당 1회씩 요청한다고 가정하면, 서버가 10대일 때 그 호스트는 초당 최대 10회의 요청을 받을 수 있다.

따라서 각 서버의 요청량만 제한해서는 전체 요청량을 통제할 수 없다.

호스트별 담당 서버를 정하거나, 여러 서버가 공유하는 요청 시각과 카운터를 관리하는 방법을 고려할 수 있다.

우리 크롤러의 전체 처리량을 늘리면서도 같은 호스트에 대한 요청 간격을 유지하려면, 큐와 제한 정보를 어디에 두어야 할까?

### 큐에서 URL을 꺼낸 직후 서버가 종료되면 그 작업은 어떻게 복구할까?

프로젝트에서 작업 상태를 데이터베이스에 기록하거나, 조건을 확인하면서 상태를 변경했던 방식과 연결해볼 수 있다.

큐에서 꺼내자마자 작업을 삭제하면 완료 전에 서버가 종료됐을 때 작업을 잃을 수 있다.

반대로 작업을 다시 전달하면 이미 저장을 마친 페이지를 중복 처리할 수 있다.

따라서 다음을 함께 고려해야 한다.

- 대기 중, 처리 중, 완료 상태를 구분한다.
- 일정 시간 동안 완료되지 않은 작업을 다시 처리할 수 있도록 한다.
- 결과 저장과 후속 작업 등록의 완료 기준을 정한다.
- 재시도해도 중복 저장이나 중복 등록이 발생하지 않도록 한다.

단순히 URL에 UNIQUE 제약조건을 두는 것만으로 충분할까? 다운로드 완료와 링크 추출 완료까지 구분할 필요는 없을까?

### 이미 방문한 URL을 제외하면서 수정된 페이지는 어떻게 다시 수집할까?

중복 URL을 제외하는 기능과 데이터 신선도 유지가 충돌하는 것처럼 보인다.

하지만 같은 수집 작업이 중복 등록되는 것을 막는 것과, 일정 시간이 지난 페이지를 다시 수집하는 것은 구분할 수 있다.

URL마다 마지막 수집 시각, 콘텐츠 지문, 다음 수집 예정 시각 등을 관리하면 정해진 조건에 따라 재수집할 수 있다.

중요하지만 거의 변하지 않는 페이지와, 덜 중요하지만 자주 바뀌는 페이지가 있다면 한정된 수집 자원을 어떻게 배분할까?

또 블룸 필터가 이미 방문했다고 판단한 URL을 전부 버린다면 재수집과 오탐은 어떻게 처리해야 할까?

### 가비아에서 설정했던 DNS TTL은 크롤러의 DNS 캐시와 어떤 관련이 있을까?

도메인 레코드와 TTL을 설정했던 경험과 연결된다.

크롤러가 매번 DNS를 조회하면 비용이 커지지만, 조회 결과를 계속 캐시하면 서버 주소가 바뀐 뒤에도 이전 IP로 요청할 수 있다.

따라서 캐시 적중률만 높이는 것이 아니라 변경 사항을 얼마나 빨리 반영해야 하는지도 고려해야 한다.

DNS 조회 실패와 HTTP 연결 실패를 구분하고, TTL에 맞게 캐시를 갱신하는 설계가 필요하다.

대상 사이트가 서버를 교체한 직후 수집 실패가 증가한다면, 크롤러의 타임아웃 설정과 DNS 캐시 중 무엇부터 확인할까?

### API 연동 때처럼 크롤링 실패도 전부 재시도하면 될까?

외부 API를 호출할 때도 인증 오류, 요청 제한, 서버 장애는 서로 다른 원인이다. 크롤링도 실패 원인에 따라 대응이 달라져야 한다.

- 404: 현재 존재하지 않는 페이지일 수 있으므로 즉시 반복 요청하지 않는다.
- 429: 요청량을 줄이고 서버가 알려주는 재시도 시점 등을 고려한다.
- 5xx나 일시적인 연결 장애: 간격을 두고 제한된 횟수만큼 재시도할 수 있다.
- 파싱 실패: 같은 응답을 다시 받아도 해결되지 않을 수 있으므로 별도로 기록하고 분석한다.

실패할 때마다 즉시 재시도하면 상대 서버의 부하와 우리 큐의 대기량이 함께 증가할 수 있다.

전체 처리량이 떨어졌을 때 작업 서버를 증설하기 전에, 오류 유형과 호스트별 지연을 먼저 확인해야 하는 이유를 설명해볼 수 있다.
