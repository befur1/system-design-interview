# 알림 시스템 설계

## 1. 알림 시스템이란?

알림 시스템의 종류: **모바일 푸시 알림, SMS 메시지, 이메일** 등

### 설계 시 생각해볼 점

- 실시간인가?
- 어떤 알림 시스템을 만들어야 하나?
- 어떤 종류의 단말을 지원하나? (iOS? 안드로이드? 랩톱? 데스크톱?)
- 사용자에게 보낼 알림은 누가 만들 수 있는지?
- 알림 수신 기능을 끌 수 있는지?

### 사용자에게 보낼 알림은 누가 만들 수 있는지? 는 왜 물어볼까

→ 알림을 발생시키는 **주체(트리거)**가 누구냐에 따라 API 설계, 보안, 트래픽 규모가 다 달라지니까

- **클라이언트 앱**이 직접 요청 (예: 친구에게 좋아요 → 알림)
- **서버 측 서비스**가 요청 (예: 결제 서비스, 배송 서비스)
- **스케줄러**가 정해진 시간에 발송 (예: 매일 아침 리마인더)
- **운영자/마케터**가 관리 화면에서 대량 발송 (예: 이벤트 공지)

## 2. 알림 유형별 구조

### iOS 푸시 알림

```
알림 제공자 → APNs → iOS 단말
```

- **APNs** (Apple Push Notification Service): 애플이 제공하는 원격 서비스로, 푸시 알림을 iOS 장치로 보내는 역할

### 안드로이드 푸시 알림

```
알림 제공자 → FCM → 안드로이드 단말
```

- **FCM** (Firebase Cloud Messaging): APNs의 안드로이드 버전

### SMS 메시지 및 이메일

- 중간에 **제3자 서비스** 혹은 회사의 **상용 이메일 서비스**를 이용

### 알림 요청을 만들려면?

- **단말 토큰**: 알림 요청을 보내는 데 필요한 고유 식별자
- **페이로드**: 알림 내용을 담은 JSON 딕셔너리

## 3. 연락처 정보 수집

알림을 보내고 싶으면?

→ 그 사용자의 **모바일 단말 토큰, 전화번호, 이메일 주소** 등의 정보가 필요

→ 계정을 처음 등록할 때 API가 데이터베이스에 해당 사용자의 정보를 저장해야 함

## 4. 알림 전송의 다양한 방식

### 1부터 N까지의 서비스

알림 시스템에 알림 전송을 요청하는 여러 서비스들

- **결제 서비스**: "결제가 완료되었습니다"
- **배송 서비스**: "상품이 발송되었습니다"
- **청구 서비스**: "청구서 납부일이 다가왔습니다"
- **채팅 서비스**: "새 메시지가 도착했습니다"
- **마케팅 서비스**: "이벤트 쿠폰이 발급되었습니다"

알림을 보내야 할 때 알림 API를 호출해서 알림을 전송

→ 이렇게 여러 서비스에서 오는 다양한 알림 → **한 알림 시스템에서 처리하는 것이 좋다**

### 왜 한 알림 시스템에서 처리할까?

각 서비스마다 APNs, FCM 등에 따로 연결한다면

- **중복 코드**: 외부 연동, 재시도, 에러 처리를 서비스마다 각자 구현
- **외부 업체 변경 시 전부 수정**: SMS 업체 하나 바꾸면 연동한 모든 서비스 수정
- **인증 정보 관리의 어려움**: APNs 인증서, FCM 키 등을 여러 서비스가 나눠 가짐 → 유출 위험
- **공통 정책을 지키기 어려워진다**: 수신 거부, 야간 광고 금지 등을 서비스마다 다르게 적용

→ 모으면 연결 수가 **곱하기(서비스 × 채널)에서 더하기(서비스 + 채널)**로 줄어든다

### 제3자 서비스

- 실제로 사용자들에게 알림을 전달하는 역할 → **확장성이 중요하다**
- 외부 업체와 연결하는 것이기에 기존 서비스의 제거 및 새로운 서비스 통합이 편해야 하고
- 특정 국가별로 사용 기준이 다르다 (예: 중국에서는 FCM 사용 불가)

## 5. 단일 서버의 문제점

- **SPOF**: 서버가 한 대라 죽으면 전체 알림 서비스 중단
- **규모 확장성**: 데이터베이스나 캐시 등 중요 컴포넌트가 알림 전송과 분리되어 있지 않아, 개별적인 규모 확장이 불가
- **성능 병목**: HTML 렌더링, 제3자 서비스 응답 대기 같은 무거운 작업을 한 서버가 처리 → 트래픽 몰리면 과부하

### 개선 방법

- **데이터베이스와 캐시**를 알림 시스템의 주 서버와 분리
- **알림 서버 증설** + 자동으로 수평적 규모 확장이 이루어지도록 설계
  - 즉 **로드밸런서와 자동 규모 확장**을 고려하자
- **메시지 큐 도입**: 알림 서버는 큐에 넣기만 하고, 실제 전송은 **작업 서버**가 큐에서 꺼내 처리하자

```
서비스 1~N → 알림 서버(여러 대) → 메시지 큐(채널별) → 작업 서버 → APNs / FCM / SMS / 이메일
                  ↕
              캐시 / DB
```

> 하나로 모은다 ≠ 서버 한 대. **논리적으로 하나의 시스템**이고, 안에서는 여러 대로 나뉘고 복제되어 있다

### 알림 서버의 역할

- 알림 전송 API 제공
- 알림 검증 (이메일 주소, 전화번호 등)
- 데이터베이스 또는 캐시 질의로 알림에 포함시킬 데이터 가져옴
- 알림 전송 (메시지 큐에 넣기)

### 캐시

- 자주 쓰는 데이터를 **더 빠른 곳에 임시로 복사해 두는 저장소**
- 알림 시스템에서는 사용자 정보, 단말 토큰, 알림 설정, 템플릿처럼 **자주 조회되지만 잘 안 바뀌는 데이터**를 둔다

### 메시지 큐

- 메시지를 보내는 쪽과 받는 쪽 **사이에 놓인 대기열**
- **버퍼 역할**: 알림이 한 번에 몰려와도 처리할 수 있는 속도대로 처리 → **트래픽 완충**
- **결합도 낮춤**: 알림 서버와 작업 서버가 서로 직접 알 필요 없음
- **채널별로 큐 분리**: FCM에 장애가 나도 SMS, 이메일 큐는 정상 동작
- 큐에 쌓인 알림 개수가 많으면 → 작업 서버가 이벤트를 빠르게 처리하지 못하는 것이니 **작업 서버 증설**이 필요함

## 6. 상세 설계 시 추가로 고려할 부분

1. **안정성**
2. **데이터 손실 방지**: 알림이 소실되면 안 된다 → **알림 로그 데이터베이스**에 보관하고 재시도
3. **알림 중복 전송 방지**: 이벤트 ID를 확인해서 이미 보낸 알림이면 버린다
4. **알림 템플릿**: 알림을 사전에 지정한 형식에 맞춰 만들어 내는 툴 → 형식 일관성, 오류 감소, 시간 절약
5. **알림 설정**: 사용자가 너무 많이 알림을 받으면 차단한다 → 채널별로 끄고 켜기 고려
6. **전송률 제한**: 사용자에게 너무 많은 알림을 보내면 안 됨 → 사용자가 알림을 아예 꺼버릴 수 있음
7. **재시도**: 알림 전송 실패 시 재시도 큐에 넣고 다시 시도해 봐야 함 → 계속 실패하면 개발자에게 통지
8. **푸시 알림과 보안**: 알림 전송 API는 인증된, 혹은 승인된 클라이언트만 사용하도록 함 (appKey, appSecret 등)
9. **이벤트 추적**: 알림 확인율, 클릭율 등 사용자 반응을 추적 → 데이터 분석 서비스와 연동
