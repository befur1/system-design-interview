## 1단계 - 문제 이해 및 설계 범위 확정
URL 단축키의 기본적인 기능
    - URL 단축
    - URL redirection : 축약된 URL로 HTTP 요청이 오면 원래 URL로 안내
    - 높은 가용성과 규모 확장성, 장애 감내

**개략적 추정의 고려사항과 상황부여**
- 쓰기 연산 수 : 매일 1억 개의 단축 URL 생성을 가정
- 읽기 연산 수 : 쓰기 연산과 10:1로 가정
- 운영 기간 : 10년으로 가정 
    ex) 10년이면 1억 * 365 * 10 개의 레코드를 보관해야함
- 예상 서버 저장 공간 : 축약 전 URL 평균 길이가 100이면 3650억 * 100바이트 = 36.5TB의 공간이 필요
    Q. 근데 단축 url도 저장해야하면 추가 공간이 필요한 거 아닌가?
        - 이런 경우에는 prefix는 제외하면 단축 url의 해시값은 비중이 작으므로 좀 뭉개서 생각할 수 있음
- URL 생성 방식 : 글자제한, 문자제한 등

## 2단계 - 개략적 설계안 제시 및 동의 구하기
API 엔드포인트, URL 리디렉션, URL 단축 플로우에 관하여

### API 엔드포인트
다음 2개의 엔트포인트가 필요
1. URL 단축용 POST 엔드포인트
    인자로 longUrl을 보내면 단축 URL이 반환
2. 리디렉션용 GET 엔드포인트
    /{shortUrl} 형태
    리디렉션 목적지가 될 원본 URL을 헤더도 보내 브라우저를 바로 리디렉션 시킴

클라이언트가 단축 URL 방문 -> 서버가 원래 URL을 반환 -> 원래 URL 방문순으로 이동이 이루어짐.

다음 두 상태코드는 서로 구분됨
- 301 Permanently Moved:
    - 해당 URL 요청의 처리 책임이 영구적으로 헤더에 반환된 URL로 이전되었다는 응답으로 브라우저는 이 응답을 캐시한다. -> 따라서 서버 방문 없이 다음부터 바로 리디렉션함
- 302 Found:
    - 일시적으로 처리한다는 응답으로 이후에도 서버에 방문해야함

장단이 있는데 서버를 방문시켜야 이득인 경우에는 302가 유리함
Ex) 트래픽 분석이 필요한 경우

### URL 단축
단축 Url의 형식이 www.tinyrul.com/{hashValue} 형식이라면 단축은 해시함수 F를 찾는 일이 된다.
F는 다음 두 조건을 만족해야하는데,
1. input이 다르면 output도 다르다 -> collision 발생이 없을 수가 없는데 뭘까??
2. output이 input으로 복원될 수 있어야한다 -> 이게말이되나? 

암호학적 해시 함수와는 다른 종류인 것 같다.
해시함수를 만든다는 느낌 보다는 검증된 해시 함수를 선택하는 조건?에 가까운 행동들인듯.
## 3단계 - 상세 설계
### 데이터 모델
해시 테이블은 접근이 빠르지만 메모리는 유한하고 비싼 자원이므로 rds에 저장한다.

### 해시 함수
#### 해시 값 길이
아까 collision발생에 대해 궁금했었는데 부여된 상황이 약 3650억개의 레코드를 보관해야하므로 hashValue가 [0-9, a-z, A-Z]일 때 62^n > 3650억인 문자열 길이 n을 찾아 단축 url의 suffix를 찾는다.

이 상황의 경우에는 n=7이면 충분하다.

잘 알려진 SHA-1같은 해시 함수를 사용하면 7자리가 넘는다
그럼 어떻게 hashValue를 7자리로 변환할까?
#### 해시 후 충돌 해소
처음 7글자만 사용, collision 발생시 해소될 때까지 사전에 정한 문자열을 해시값에 추가함
-> 단축 URL을 생성할 때 무조건 1번 이상 DB에 질의해야 하므로 오버헤드가 큼
-> 블룸 필터를 사용해서 해결 가능

#### base-62 변환
수의 표현 방식이 다른 두 시스템(DB - 10진수, URL - 62진법) 이 같은 수를 공유하여야 하는 경우에 유용하다.
62진법인 이유는 아까 정한 hashValue에 사용되는 문자가 62개이기 때문.
- 진법은 1대1 매핑이므로 충돌문제에서 자유롭다.
- 축약된 값으로 원본값 조회하는 것을 초고속으로 할 수 있다. (10진수로 변환한 뒤 db조회하면 되기 때문에)

각 문자를 0~61에 대응시키고, 10진수를 62진법 변환 및 대응하는 문자 매칭으로 변환함

**일단 원본 url을 rds에 저장하고 저장된 url의 인덱스(고유 ID)를 가지고 매핑한다는 것 같음**

### 두 접근법 비교

| 해시 후 충돌 해소 전략 | base-62 변환 |
| :--- | :--- |
| 단축 URL의 길이가 고정됨 | 단축 URL의 길이가 가변적. ID 값이 커지면 같이 길어짐 |
| 유일성이 보장되는 ID 생성기가 필요치 않음 | 유일성 보장 ID 생성기가 필요(index 기반 변환이기때문에) |
| 충돌이 가능해서 해소 전략이 필요 | ID의 유일성이 보장된 후에야 적용 가능한 전략이라 충돌은 아예 불가능 |
| ID로부터 단축 URL을 계산하는 방식이 아니라서 다음에 쓸 수 있는 URL을 알아내는 것이 불가능 | ID가 1씩 증가하는 값이라고 가정하면 다음에 쓸 수 있는 단축 URL이 무엇인지 쉽게 알아낼 수 있어서 보안상 문제가 될 소지가 있음 |

### URL 단축기 작동 흐름
1. 입력으로 긴 URL을 받음
2. DB에 해당 URL이 있는지 검사
    2-1. 있다면 반환
3. 없다면 유일 ID 생성 및 진법 변환을 적용해 새로운 단축 URL을 생성하고 DB에 저장
4. 반환

### URL 리디렉션 작동 흐름
1. 사용차가 단축 URL을 클릭
2. 로드밸런서가 요청을 웹서버에 전달
    2-1. 캐시에 있는 경우 바로 전달
    2-2. 없는 경우 DB 들려서 전달

Q. 단축기와 리디렉션은 같은 서버에서 작동하는가?
-> 같은 서버에 둘 수 있지만 리디렉션(읽기)의 트래픽이 단축기(쓰기)에 비해 많다
-> 분리해둘 경우 스케일아웃에 유리함
-> 장애 격리에서도 유리함

Q. 근데 이 단축기, 왜 쓰나요?
1.  SMS 발송 비용 자체를 절감할 수 있다(길이가 돈이기때문에)
2.  마케팅 분석 및 클릭 추적에 활용할 수 있다.
    -> 사용자가 인스타그램에서 링크를 터치하면 다음과 같은 요청이 들어옴

    ```text
    GET /event123 HTTP/1.1
    Host: bit.ly
    User-Agent: Mozilla/5.0 (iPhone; CPU iPhone OS 17_0 like Mac OS X) AppleWebKit/605.1.15 Mobile Safari/604.1
    Referer: https://www.instagram.com/
    Client-IP: 211.234.123.45
    ```

3. 이미 배포된 링크의 목적지 주소를 변경해서 사용할 수 있다.
4.  보안 및 스팸 차단에 활용이 가능하다.
    -> 네이버, 페이스북 등은 외부 링크를 무조건 본인들의 단축 링크로 강제 변환해 리디렉션 하는 중간 서버에서 검사한다.
