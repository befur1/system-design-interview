# 10장: 알림 시스템 설계

## 알림 시스템이란?

알림 시스템은 서비스에서 발생한 중요한 정보를 사용자에게 비동기적으로 전달하는 시스템이다.

대표적인 전달 방식은 다음과 같다.

- 모바일 푸시 알림
- SMS
- 이메일

각 채널은 전송 방식과 비용, 전달 가능한 정보가 다르다. 따라서 공통적인 알림 처리 과정과 채널별 발송 과정을 구분해서 설계해야 한다.

## 1단계: 문제 이해 및 설계 범위 확정

### 요구사항

책에서는 다음 조건을 가정한다.

- 푸시 알림, SMS, 이메일을 지원한다.
- iOS, 안드로이드, 랩톱·데스크톱 사용자를 지원한다.
- 알림은 가능한 한 빨리 전달하되, 부하가 높을 때 약간의 지연을 허용한다.
- 클라이언트의 요청이나 서버의 스케줄링으로 알림을 생성할 수 있다.
- 사용자가 알림 수신을 거부할 수 있어야 한다.

알림을 즉시 전달해야 하는 엄격한 실시간 시스템보다는, 일정 수준의 지연을 허용하는 연성 실시간 시스템을 가정한다.

### 처리 규모

| 채널 | 하루 전송량 |
| --- | --- |
| 모바일 푸시 | 1,000만 건 |
| SMS | 100만 건 |
| 이메일 | 500만 건 |

하루 전송량뿐 아니라 특정 시간대에 집중되는 요청과 알림 한 건의 수신 대상 수도 고려해야 한다.

예를 들어 한 사용자에게 보내는 알림도 여러 단말에 전달한다면 실제 발송 작업은 여러 개가 될 수 있다.

## 2단계: 개략적 설계안 제시 및 동의 구하기

### 알림 유형별 지원 방안

#### iOS 푸시 알림

iOS 푸시 알림은 다음 구성으로 전달된다.

1. 알림 제공자가 알림 요청을 생성한다.
2. APNs에 요청을 보낸다.
3. APNs가 대상 iOS 단말로 전달을 시도한다.

APNs는 Apple Push Notification service의 약자다.

발송 요청에는 다음 정보가 필요하다.

- 단말 토큰: 알림을 전달할 앱·단말을 식별하기 위한 정보
- 페이로드: 제목, 본문, 배지 등의 알림 내용
- 발송 서버를 인증하기 위한 정보

단말 토큰은 수신 대상을 찾기 위한 값이다. 로그인에 사용하는 JWT나 사용자 ID와 같은 역할은 아니다.

#### 안드로이드 푸시 알림

책에서는 FCM을 이용하는 구조를 설명한다.

1. 알림 제공자가 요청을 생성한다.
2. FCM에 요청을 보낸다.
3. FCM이 대상 앱·단말로 전달을 시도한다.

FCM은 Firebase Cloud Messaging의 약자다.

핵심 구조는 발송 서버가 플랫폼의 푸시 서비스를 통해 대상 단말에 알림을 전달한다는 것이다.

#### SMS

SMS는 일반적으로 외부 발송 사업자의 API를 이용한다.

- 수신자의 전화번호가 필요하다.
- 발송 사업자의 인증 정보와 요청 형식에 맞춰 호출한다.
- 전송 비용과 사업자의 요청 제한을 고려해야 한다.

#### 이메일

이메일은 직접 메일 서버를 운영하거나 외부 이메일 발송 서비스를 이용할 수 있다.

외부 서비스는 발송 기능 외에 전달 결과와 클릭 등의 분석 기능을 제공하기도 한다.

| 채널 | 수신 대상 정보 | 주요 연동 대상 |
| --- | --- | --- |
| iOS 푸시 | 단말 토큰 | APNs |
| 안드로이드 푸시 | 앱·단말 등록 정보 | FCM |
| SMS | 전화번호 | SMS 발송 사업자 |
| 이메일 | 이메일 주소 | 이메일 발송 서비스 |

### 연락처 정보 수집

사용자 가입이나 앱 등록 과정에서 알림에 필요한 정보를 수집하고 서버에 저장한다.

한 사용자가 여러 단말을 사용할 수 있으므로 사용자와 단말 정보를 분리한다.

#### 사용자 정보

- 사용자 ID
- 이메일 주소
- 전화번호
- 생성 시각

#### 단말 정보

- 단말 정보의 ID
- 사용자 ID
- 단말 토큰
- 플랫폼
- 최근 갱신 시각

사용자와 단말은 1:N 관계로 볼 수 있다.

책에서는 여러 단말을 사용하는 사용자에게 모든 등록 단말로 알림을 전달하는 상황을 고려한다. 실제 서비스에서는 모든 단말에 보낼지, 일부 단말에만 보낼지 정책을 정해야 한다.

단말 토큰은 변경되거나 무효화될 수 있으므로 갱신과 정리 절차도 필요하다.

전화번호는 계산 대상이 아니고 국가 코드나 앞자리 0 등을 보존해야 하므로, 실제 구현에서는 문자열로 저장하는 것이 적절하다.

### 개략적 설계 초안

초기 구조는 다음과 같다.

1. 여러 서비스가 알림 시스템의 API를 호출한다.
2. 알림 시스템이 사용자 정보와 발송 내용을 확인한다.
3. 채널별 외부 서비스에 요청한다.
4. 외부 서비스가 사용자에게 전달을 시도한다.

이때 알림을 발생시키는 주체는 비즈니스 서비스, 배치 작업, 스케줄러 등이 될 수 있다.

### 초안의 문제점

#### 단일 장애 지점

하나의 알림 서버에 모든 처리가 집중되면 해당 서버의 장애가 전체 알림 기능의 장애로 이어진다.

#### 독립적인 규모 확장의 어려움

요청 접수, 사용자 정보 조회, 템플릿 생성, 외부 서비스 호출을 한곳에서 처리하면 병목이 생긴 부분만 따로 확장하기 어렵다.

#### 성능 병목

외부 발송 서비스의 응답이 느리면 알림 서버의 처리도 지연될 수 있다.

알림을 많이 보내는 시간에는 외부 호출을 기다리는 작업이 쌓여 전체 처리 성능이 저하될 수 있다.

### 개선된 구조

다음 방향으로 개선한다.

- 데이터베이스와 캐시를 알림 서버에서 분리한다.
- 알림 서버를 여러 대로 확장할 수 있게 한다.
- 알림 접수와 실제 발송 사이에 메시지 큐를 둔다.
- 채널별 큐와 작업 서버를 분리한다.

| 구성 요소 | 역할 |
| --- | --- |
| 알림 서버 | 요청 인증·검증, 사용자 정보 조회, 발송 작업 생성 |
| 데이터베이스 | 사용자, 단말, 설정, 알림 이력 저장 |
| 캐시 | 사용자·단말 정보와 템플릿 등의 조회 비용 감소 |
| 메시지 큐 | 발송 작업 보관, 급증한 요청의 버퍼 역할 |
| 작업 서버 | 큐에서 작업을 받아 외부 서비스 호출 |
| 외부 발송 서비스 | 실제 수신 대상에게 알림 전달 시도 |

### 메시지 큐와 작업 서버

책에서는 iOS 푸시, 안드로이드 푸시, SMS, 이메일을 각각 별도 큐로 분리한다.

이렇게 하면 다음 이점이 있다.

- 알림 접수와 실제 발송의 처리 속도를 분리할 수 있다.
- 요청이 급증해도 큐에 쌓아 순차적으로 처리할 수 있다.
- 특정 채널의 작업 서버만 늘릴 수 있다.
- 특정 발송 사업자의 장애가 다른 채널에 미치는 영향을 줄일 수 있다.

다만 큐를 사용한다고 자동으로 데이터 유실이 방지되는 것은 아니다. 큐의 지속성 설정과 처리 확인, 재전달 방식을 함께 설계해야 한다.

### 알림 전송 흐름

1. 서비스가 알림 서버에 발송을 요청한다.
2. 알림 서버가 요청을 인증하고 내용을 검증한다.
3. 사용자 정보, 단말 정보, 수신 설정 등을 조회한다.
4. 채널에 맞는 발송 작업을 생성해 큐에 넣는다.
5. 작업 서버가 큐에서 작업을 가져온다.
6. 템플릿과 발송 데이터를 준비한다.
7. 해당 채널의 외부 서비스에 요청한다.
8. 처리 결과를 기록하고, 재시도가 필요하면 다시 처리하도록 예약한다.

알림 API가 요청을 접수했다는 응답과 사용자가 실제로 알림을 받았다는 것은 구분해야 한다.

## 3단계: 상세 설계

### 안정성: 데이터 손실 방지

알림을 접수한 뒤 작업이 사라지지 않도록 발송 데이터와 처리 상태를 지속성 저장소에 기록해야 한다.

알림 로그에는 다음 정보를 저장할 수 있다.

- 알림 ID와 원인 이벤트 ID
- 수신자와 채널
- 알림 유형과 내용
- 처리 상태
- 발송 시도 횟수
- 마지막 오류
- 생성 시각과 다음 재시도 시각

이 정보가 있으면 장애 이후 미완료 작업을 찾아 복구하거나 재처리할 수 있다.

다만 우리 시스템에서 발송 작업을 보존하는 것과 외부 단말까지 반드시 전달하는 것은 다른 문제다. 단말의 네트워크 상태나 알림 권한 등은 별도로 영향을 준다.

### 알림 중복 전송 방지

분산 환경에서는 같은 이벤트가 재전달되거나 작업이 다시 실행될 수 있다.

기본적인 대응은 이벤트 ID를 확인해 이미 처리한 알림인지 검사하는 것이다.

다만 하나의 이벤트가 여러 사용자나 채널로 전달될 수 있으므로 중복 판단의 범위를 정해야 한다.

예를 들어 다음 조합을 발송 작업의 식별 기준으로 사용할 수 있다.

- 이벤트 ID
- 수신자
- 채널
- 필요하다면 대상 단말

이벤트 ID만으로 중복을 판단하면 같은 이벤트에 필요한 다른 수신자의 알림까지 차단할 수 있다.

여러 작업 서버가 동시에 처리할 수도 있으므로 단순 조회 후 판단만으로는 부족하다. 유일성 제약조건이나 원자적인 상태 변경 등도 함께 고려해야 한다.

또한 외부 서비스 호출에는 결과를 확정하기 어려운 상황이 있다.

- 외부 서비스는 접수했지만 응답이 오기 전에 연결이 끊길 수 있다.
- 발송은 성공했지만 서버가 결과를 기록하기 전에 종료될 수 있다.

따라서 내부 중복 검사만으로 외부 발송까지 정확히 한 번 이루어진다고 보장하기는 어렵다. 사업자가 제공하는 멱등성 기능이나 결과 조회 기능도 확인해야 한다.

### 알림 템플릿

대부분의 알림은 구조가 비슷하고 일부 값만 달라진다.

예를 들어 다음과 같은 템플릿을 사용할 수 있다.

- 제목: `[user_name]님의 결과가 준비되었습니다.`
- 본문: `[result_name]을 확인해보세요.`
- 이동 주소: `[result_url]`

템플릿을 사용하면 문구와 형식을 일관되게 유지하고, 여러 서비스에서 같은 내용을 반복 작성하는 일을 줄일 수 있다.

채널마다 글자 수와 표현 가능한 형식이 다르므로 공통 알림 유형을 채널별 템플릿으로 변환할 수도 있다.

### 알림 수신 설정

사용자가 알림을 받을지 직접 설정할 수 있어야 한다.

책에서는 다음 필드를 예로 든다.

| 필드 | 역할 |
| --- | --- |
| `user_id` | 설정의 주인 |
| `channel` | 푸시, SMS, 이메일 등의 채널 |
| `opt_in` | 해당 채널의 수신 여부 |

실제 서비스에서는 알림 종류별 설정이나 조용한 시간대 등을 추가할 수도 있다.

알림을 보내기 전에 해당 사용자의 설정을 확인해야 하며, 큐에서 오래 대기한 작업이라면 그동안 설정이 변경되었을 가능성도 고려해야 한다.

### 전송률 제한

사용자에게 너무 많은 알림을 보내면 피로감을 주고 전체 알림 기능을 끄게 만들 수 있다.

따라서 사용자별 알림 빈도를 제한하거나 비슷한 알림을 묶어 보내는 정책을 고려한다.

다음 두 제한은 목적이 다르다.

- 사용자별 제한: 알림이 과도하게 전달되는 것을 방지한다.
- 채널·사업자별 제한: 외부 서비스의 처리량 제한을 지킨다.

4장에서 배운 처리율 제한을 알림 발송 과정에도 적용할 수 있다.

### 재시도

일시적인 전송 실패는 재시도할 수 있도록 작업을 다시 예약한다.

다만 모든 오류를 같은 방식으로 재시도해서는 안 된다.

| 상황 | 대응 방향 |
| --- | --- |
| 일시적인 네트워크 오류 | 간격을 두고 재시도 |
| 외부 서비스의 요청량 제한 | 전송 속도 조절과 대기 |
| 잘못된 연락처나 무효한 단말 정보 | 정보 정리와 실패 처리 |
| 잘못된 페이로드 | 원인 수정 후 처리 |
| 반복되는 장애 | 운영자에게 알리고 별도 보관 |

즉시 반복 요청하면 장애 중인 외부 서비스와 우리 시스템의 부하를 함께 키울 수 있다.

재시도 간격, 최대 횟수, 알림 유효기간을 정하고, 더 이상 자동 처리하지 못하는 작업은 따로 확인할 수 있어야 한다.

### 보안

알림 발송 API는 승인된 호출자만 사용할 수 있어야 한다.

인증 외에도 다음을 확인해야 한다.

- 호출자가 해당 수신자에게 알림을 보낼 권한이 있는가?
- 요청한 알림 유형과 내용이 허용되는가?
- 외부 발송 서비스의 인증 정보가 안전하게 관리되는가?

책의 appKey와 appSecret은 인증 수단의 예시다.

특히 서버용 비밀키를 브라우저 코드에 넣으면 사용자가 확인할 수 있으므로, 발송 서비스 호출에 필요한 비밀 정보는 서버에서 관리해야 한다.

### 큐 모니터링

큐에 대기 중인 알림 수는 중요한 지표다.

다만 대기량이 증가했다고 항상 작업 서버를 늘려야 하는 것은 아니다. 외부 사업자의 요청 제한이나 장애가 원인일 수도 있다.

함께 확인할 지표는 다음과 같다.

- 채널별 큐 대기량
- 가장 오래 기다린 작업의 대기 시간
- 알림 접수부터 외부 서비스 요청까지의 지연
- 외부 API 응답 시간
- 성공률과 오류 유형
- 재시도 횟수
- 초당 처리량

### 이벤트 추적

알림의 효과와 시스템 상태를 이해하려면 처리 단계를 구분해서 추적해야 한다.

| 단계 | 의미 |
| --- | --- |
| 요청 접수 | 우리 알림 시스템이 작업을 받아들임 |
| 발송 대기 | 큐에서 처리를 기다림 |
| 외부 서비스 접수 | 발송 사업자가 요청을 받아들임 |
| 전달 | 수신 대상에 전달됨 |
| 확인·클릭 | 사용자가 알림과 상호작용함 |
| 실패·수신 거부 | 전송 실패 또는 설정에 따라 제외됨 |

외부 서비스의 성공 응답이 사용자 확인을 의미하지는 않는다.

또한 모든 채널에서 모든 단계를 관측할 수 있는 것은 아니다. 제공되는 콜백과 단말 이벤트 등을 기준으로 어디까지 확인할 수 있는지 명확하게 해야 한다.

## 4단계: 설계 후 추가로 고려할 사항

### 채널별 독립적인 확장

알림 접수 서버와 채널별 작업 서버를 분리하면 특정 채널의 트래픽이 증가했을 때 해당 부분만 확장할 수 있다.

새 발송 사업자나 채널을 추가할 때도 공통 처리 과정 전체를 수정하지 않도록 연동 부분을 구분한다.

### 장애 중의 동작

외부 서비스가 중단되어도 알림 요청을 보관하고 이후 복구할 수 있어야 한다.

다만 시간이 지나면 의미가 없어지는 알림도 있으므로, 재시도할 때 유효기간과 최신 상태를 확인해야 한다.

### 알림 정책과 시스템 상태의 구분

사용자가 수신을 거부해 발송하지 않은 경우는 전송 장애와 다르다.

정상적인 정책 적용, 일시적인 실패, 영구적인 실패를 구분해야 성공률과 장애 지표를 올바르게 해석할 수 있다.

## 생각해본 질문

### 몽글에서 이미지 생성 결과는 저장됐는데, 알림을 요청하기 전에 서버가 종료되면 어떻게 할까?

이미지 생성 완료 알림을 추가한다고 가정해볼 수 있다.

결과 저장이 성공한 뒤 알림 큐에 넣기 전에 서버가 종료되면, 결과는 존재하지만 알림은 생성되지 않을 수 있다.

반대로 결과 저장이 확정되기 전에 알림을 보내면 사용자가 아직 존재하지 않는 결과로 이동할 수 있다.

커밋 이후에 알림을 요청하면 두 번째 문제를 줄일 수 있지만, 그 사이의 서버 종료로 인한 유실까지 자동으로 해결되는 것은 아니다.

더 강한 복구가 필요하다면 결과와 '발송해야 할 이벤트'를 같은 데이터베이스 트랜잭션에 기록하고, 별도 작업이 그 이벤트를 큐로 전달하는 방법을 고려할 수 있다. 이를 Transactional Outbox 패턴이라고 한다.

우리 서비스에서는 어느 수준의 알림 유실을 허용할 수 있을까? 단순한 비동기 실행과 지속성 있는 발송 작업은 어떤 차이가 있을까?

### 외부 발송 API가 타임아웃됐으면 실패로 보고 다시 보내도 될까?

외부 API를 호출했던 경험과 연결되는 문제다.

타임아웃은 우리가 응답을 받지 못했다는 뜻이다. 상대 서버가 요청을 처리하지 않았다는 뜻은 아니다.

알림이 이미 접수된 상황에서 재시도하면 같은 알림이 두 번 갈 수 있다.

반대로 재시도하지 않으면 실제로 접수되지 않은 알림이 누락될 수 있다.

이때 다음을 확인해야 한다.

- 같은 발송 요청에 동일한 식별자를 사용할 수 있는가?
- 외부 서비스가 멱등성 키를 지원하는가?
- 요청 결과를 조회하거나 콜백으로 확인할 수 있는가?
- 결과가 불명확한 작업을 어떤 상태로 관리할 것인가?

로그인 안내와 일반 이벤트 알림이 같은 수준의 중복·누락 허용 범위를 가져도 될까?

### React 웹 서비스에 알림을 붙일 때도 APNs나 FCM부터 도입해야 할까?

화면 안에 보여주는 알림과 서비스 밖으로 전달하는 푸시 알림을 구분할 필요가 있다.

- 알림 목록: 서버에 저장한 알림을 API로 조회한다.
- 현재 접속 중인 화면의 갱신: 폴링, SSE, WebSocket 등을 검토한다.
- 백그라운드 알림: 브라우저 Web Push 등을 검토한다.

웹 푸시는 브라우저 권한과 서비스 워커 등의 준비가 필요하며, FCM을 이용하는 방식도 있다.

하지만 화면 안의 알림 목록이나 생성 작업의 완료 표시만 필요하다면 처음부터 푸시 시스템 전체가 필요한 것은 아니다.

몽글에서 사용자가 기다리는 화면의 상태 갱신과, 서비스를 떠난 사용자에게 결과를 알려주는 기능은 같은 방식으로 구현해야 할까?

### 로그인 JWT와 단말 토큰은 어떤 차이가 있고, 로그아웃할 때는 무엇을 정리해야 할까?

JWT는 요청한 사용자를 인증하는 데 사용하고, 단말 토큰은 푸시를 전달할 앱·단말을 찾는 데 사용한다.

따라서 JWT가 만료되었다고 단말 토큰도 자동으로 무효화되는 것은 아니다.

같은 기기에서 A가 로그아웃한 뒤 B가 로그인했는데 서버가 기존 사용자와 단말의 연결을 유지하면, 잘못된 대상에게 알림이 갈 수 있다.

다음 정책을 정할 필요가 있다.

- 로그인할 때 사용자와 단말을 어떻게 연결할 것인가?
- 로그아웃할 때 어떤 연결을 해제할 것인가?
- 같은 사용자의 다른 단말에는 계속 알림을 보낼 것인가?
- 토큰이 갱신되거나 무효화되었을 때 어떻게 반영할 것인가?

사용자 인증과 알림 수신 대상 관리를 별개로 설계해야 하는 이유를 설명해볼 수 있다.

### 알림이 큐에서 기다리는 동안 사용자가 수신을 거부하면 어떻게 할까?

알림 요청을 받을 때는 수신을 허용했지만, 실제 발송 시점에는 설정이 바뀌었을 수 있다.

요청 접수 시에만 설정을 확인하면 이미 수신을 거부한 사용자에게 알림이 전달될 수 있다.

이를 줄이려면 실제 외부 발송 직전에도 설정을 확인하는 방법을 고려할 수 있다. 설정을 캐시한다면 변경 반영 지연도 함께 봐야 한다.

다만 외부 발송 서비스에 이미 전달한 요청까지 취소할 수 있는지는 별개의 문제다.

우리 서비스에서는 설정 변경이 어느 시점부터 적용된다고 정의해야 할까? 채널별 설정과 알림 종류별 설정을 모두 지원해야 할까?

### 큐에 알림이 많이 쌓이면 작업 서버만 늘리면 될까?

작업 서버가 부족하면 증설이 도움이 된다. 하지만 외부 서비스가 요청량을 제한하는 상황에서는 더 많은 작업 서버가 오류와 재시도를 늘릴 수 있다.

따라서 먼저 병목의 위치를 확인해야 한다.

- 템플릿 생성이나 DB 조회가 느린가?
- 외부 API 응답이 느린가?
- 요청량 제한에 걸리고 있는가?
- 실패한 작업이 반복해서 큐에 들어오는가?
- 특정 채널이나 사용자에게 작업이 집중되는가?

처리량을 늘리는 것뿐 아니라 알림을 묶어 보내거나, 중요도에 따라 큐를 나누는 방법도 생각해볼 수 있다.

우리 서비스에서 결과 생성 완료 알림과 일반 홍보 알림이 같은 큐에서 같은 우선순위로 처리되어도 괜찮을까?
