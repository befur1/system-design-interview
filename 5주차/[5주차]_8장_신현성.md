# 8장: URL 단축기 설계

## 1단계: 문제 이해 및 설계 범위 확정

URL 단축기는 긴 URL을 짧은 URL로 변환하고, 사용자가 단축 URL에 접속하면 원래 URL로 이동시키는 서비스다.

같은 URL 단축기라도 생성량, 허용 문자, 수정·삭제 가능 여부에 따라 설계가 달라지므로 먼저 요구사항을 확인해야 한다.

### 요구사항

- 매일 1억 개의 단축 URL을 생성할 수 있어야 한다.
- 단축 URL은 가능한 한 짧아야 한다.
- 단축 코드에는 숫자와 영문 대소문자만 사용할 수 있다.
- 단축 URL에 접근하면 원래 URL로 리다이렉션해야 한다.
- 이번 설계에서는 단축 URL의 수정과 삭제를 지원하지 않는다.
- 높은 가용성, 규모 확장성, 장애 감내 능력이 필요하다.

### 개략적 규모 추정

읽기와 쓰기의 비율을 10:1로 가정하고, 서비스를 10년간 운영한다고 가정한다.

| 항목 | 계산 | 추정치 |
| --- | --- | --- |
| 일일 단축 URL 생성량 | 주어진 요구사항 | 1억 개 |
| 평균 쓰기 QPS | 1억 / 86,400 | 약 1,160 |
| 평균 읽기 QPS | 쓰기 QPS × 10 | 약 11,600 |
| 10년간 생성하는 URL 수 | 1억 × 365 × 10 | 3,650억 개 |
| 원래 URL의 평균 크기 | 가정 | 100바이트 |
| 원래 URL 저장 용량 | 3,650억 × 100바이트 | 약 36.5TB |

36.5TB는 원래 URL 문자열만 계산한 값이다. 실제 저장 용량에는 ID, 단축 코드, 인덱스, 복제본 등의 공간이 추가로 필요하다.

또한 위 QPS는 평균값이므로 실제 서버 용량을 정할 때는 피크 트래픽도 고려해야 한다.

## 2단계: 개략적 설계안 제시 및 동의 구하기

### API 엔드포인트

URL 단축기는 기본적으로 URL 생성과 리다이렉션을 위한 API가 필요하다.

#### URL 단축

- 요청: `POST /api/v1/data/shorten`
- 입력: `{"longUrl": "https://example.com/long-path"}`
- 반환: 생성한 단축 URL

서버에 새로운 URL 매핑 정보를 생성하므로 POST 요청을 사용한다.

#### URL 리다이렉션

- 요청 예시: `GET /api/v1/{shortCode}`
- 처리: 단축 코드에 대응하는 원래 URL 조회
- 반환: 리다이렉션 상태 코드와 `Location` 헤더

실제 공개 주소는 `https://short.example.com/abc1234`처럼 구성할 수 있다.

리다이렉션 API는 원래 URL을 JSON으로 알려주는 것과 차이가 있다. 서버가 `Location` 헤더에 목적지를 넣어 응답하면 브라우저가 그 주소로 새로운 요청을 보낸다.

### URL 리다이렉션

동작 과정은 다음과 같다.

1. 사용자가 단축 URL에 접근한다.
2. 단축 URL 서버가 원래 URL을 조회한다.
3. 원래 URL을 `Location` 헤더에 넣어 리다이렉션 응답을 보낸다.
4. 브라우저가 원래 URL의 서버로 요청을 보낸다.

단축 URL 서버가 원래 사이트의 페이지를 대신 받아서 전달하는 구조는 아니다.

### 301과 302의 차이

| 구분 | 301 Moved Permanently | 302 Found |
| --- | --- | --- |
| 의미 | 목적지가 영구적으로 변경됨 | 현재 요청을 임시 목적지로 안내함 |
| 캐시 | 캐시되어 이후 단축 서버를 거치지 않을 수 있음 | 매번 서버를 거치도록 운영하기에 더 적합함 |
| 장점 | 단축 서버의 요청량 감소 가능 | 클릭 기록 수집과 목적지 제어에 유리 |
| 고려할 점 | 목적지 변경 반영이나 클릭 집계가 어려워질 수 있음 | 단축 서버가 처리하는 요청량 증가 |

책에서는 서버 부하 감소가 중요하면 301, 트래픽 분석이 중요하면 302를 고려한다.

다만 실제 캐시 여부는 상태 코드뿐 아니라 `Cache-Control` 등의 설정에도 영향을 받는다. 302를 사용한다고 무조건 캐시되지 않는 것은 아니므로, 클릭마다 서버에 요청이 도달해야 한다면 캐시 정책도 함께 설정해야 한다.

### URL 매핑 정보 저장

단축 URL을 원래 URL로 연결하려면 두 값의 매핑 정보를 보관해야 한다.

초기에는 메모리의 해시 테이블에 저장하는 방법을 생각할 수 있다. 하지만 서버가 재시작되면 데이터가 사라질 수 있고, 저장량이 증가하면 메모리 비용도 커진다.

따라서 원본 매핑 정보는 데이터베이스에 영속적으로 저장하고, 자주 조회되는 매핑은 캐시에 보관한다.

## 3단계: 상세 설계

### 데이터 모델

책에서는 관계형 데이터베이스에 다음 정보를 저장한다.

| 필드 | 역할 |
| --- | --- |
| `id` | URL 매핑을 식별하는 기본키 |
| `shortURL` | 원래 URL을 찾는 데 사용하는 단축 코드 |
| `longURL` | 사용자가 입력한 원래 URL |

실제 구현에서는 `shortURL`에 전체 도메인을 포함한 주소 대신 단축 코드만 저장하고, 응답할 때 서비스 도메인과 합칠 수 있다.

단축 코드는 서로 다른 원래 URL에 중복 배정되면 안 되므로 유일성을 보장해야 한다.

### 단축 코드의 길이

사용 가능한 문자는 다음과 같다.

- 숫자: 10개
- 영문 소문자: 26개
- 영문 대문자: 26개

총 62개이므로 길이가 n인 코드로 만들 수 있는 조합은 `62^n`개다.

| 코드 길이 | 가능한 조합 수 |
| --- | --- |
| 5글자 | 916,132,832개 |
| 6글자 | 56,800,235,584개 |
| 7글자 | 3,521,614,606,208개 |

10년간 필요한 코드는 3,650억 개다.

6글자로는 부족하지만 7글자라면 약 3.5조 개를 표현할 수 있으므로, 책에서는 7글자를 선택한다.

이는 필요한 코드 공간의 크기를 계산한 것이다. 실제로 충돌 없이 코드를 배정하는 방법은 별도로 설계해야 한다.

### 단축 코드 생성 방법 1: 해시 후 충돌 해소

원래 URL을 해시한 뒤 짧은 코드로 만드는 방법이다.

책에서는 CRC32, MD5, SHA-1 등을 예로 든다. 다만 계산 결과를 짧게 줄이면 서로 다른 URL에 같은 코드가 배정되는 충돌이 발생할 수 있다.

처리 과정은 다음과 같다.

1. 입력 URL로 단축 코드 후보를 생성한다.
2. 해당 코드가 데이터베이스에 존재하는지 확인한다.
3. 다른 URL이 이미 사용 중이면 입력에 추가 문자열을 붙이는 등의 방법으로 다시 계산한다.
4. 사용 가능한 코드를 찾으면 원래 URL과 함께 저장한다.

충돌을 해소할 수 있지만, 후보를 만들 때마다 존재 여부를 확인하면 데이터베이스 조회 비용이 커진다.

또한 해시 결과 자체에서 원래 URL을 복원하는 것은 아니다. 원래 URL은 저장해둔 매핑 정보에서 찾아야 한다.

#### 블룸 필터 활용

블룸 필터는 어떤 값이 집합에 포함되어 있는지 적은 메모리로 검사하는 자료구조다.

정상적으로 관리되는 필터를 기준으로 다음과 같이 해석한다.

- 없다고 판단한 값: 집합에 없다.
- 있다고 판단한 값: 실제로는 없을 수도 있으므로 추가 확인이 필요하다.

이를 활용하면 존재하지 않는 코드에 대한 일부 데이터베이스 조회를 줄일 수 있다.

다만 블룸 필터만으로 코드의 유일성을 확정하거나 동시 요청의 충돌을 방지할 수는 없다. 최종 저장 시의 유일성 보장은 여전히 필요하다.

### 단축 코드 생성 방법 2: Base62 변환

Base62는 정수를 62개의 문자로 표현하는 진법 변환이다.

책에서는 다음 순서로 문자를 대응시킨다.

- `0~9`: 0~9
- `a~z`: 10~35
- `A~Z`: 36~61

예를 들어 10진수 11157은 다음과 같이 나타낼 수 있다.

`11157 = 2 × 62² + 55 × 62 + 59`

각 자릿값을 문자로 바꾸면 `2TX`가 된다.

URL 단축기에 적용하는 과정은 다음과 같다.

1. 전역적으로 유일한 정수 ID를 발급한다.
2. ID를 Base62로 변환한다.
3. 변환 결과를 단축 코드로 사용한다.
4. 코드와 원래 URL의 매핑을 저장한다.

서로 다른 정수를 같은 문자 대응 규칙으로 변환하면 서로 다른 코드가 나온다. 따라서 이 방식에서는 입력 ID의 유일성이 중요하다.

Base62는 해시나 암호화가 아니다. 표현 방식을 바꾸는 것이므로 코드를 다시 정수로 변환할 수도 있다.

### 두 접근법 비교

| 항목 | 해시 후 충돌 해소 | 유일 ID의 Base62 변환 |
| --- | --- | --- |
| 코드 생성 기준 | 원래 URL의 해시 | 발급한 정수 ID |
| 길이 | 고정 길이로 설계 가능 | ID 크기에 따라 증가 |
| 충돌 | 발생 가능하므로 해소 필요 | ID가 유일하면 코드도 유일 |
| 별도 ID 생성 | 필수는 아님 | 유일한 ID 발급 방법 필요 |
| 주요 고려사항 | 충돌 검사와 재시도 비용 | ID 발급, 코드 길이, 예측 가능성 |

순차 증가 ID를 그대로 Base62로 바꾸면 인접한 코드를 추측하기 쉽다.

또한 Base62를 사용한다고 항상 7글자가 되는 것은 아니다. 7글자 이내로 표현하려면 발급하는 ID가 그 범위에 들어가야 한다.

### URL 단축 상세 설계

책에서는 Base62 방식을 선택한다.

1. 클라이언트로부터 긴 URL을 받는다.
2. 같은 URL에 대한 기존 매핑이 있는지 조회한다.
3. 이미 존재하면 기존 단축 URL을 반환한다.
4. 없다면 새로운 유일 ID를 생성한다.
5. ID를 Base62로 변환한다.
6. ID, 단축 코드, 원래 URL을 데이터베이스에 저장한다.
7. 저장이 완료되면 단축 URL을 반환한다.

7장에서 공부한 유일 ID 생성기가 이 과정에 연결된다.

다만 모든 서비스에 별도 분산 ID 생성기가 필요한 것은 아니다. 초기에는 MySQL의 `AUTO_INCREMENT`를 이용할 수도 있고, 여러 저장소가 독립적으로 ID를 발급해야 할 만큼 확장되면 다른 방법을 검토할 수 있다.

같은 원래 URL에 항상 같은 단축 URL을 반환할지도 서비스 정책에 따라 달라질 수 있다. 사용자나 캠페인별 통계가 필요하다면 같은 목적지에 여러 단축 URL을 만들 수도 있다.

### URL 리다이렉션 상세 설계

URL 단축기는 생성보다 조회가 많은 시스템이므로, 자주 사용하는 매핑 정보를 캐시에 저장한다.

1. 사용자가 단축 URL에 접근한다.
2. 로드밸런서가 요청을 웹 서버로 전달한다.
3. 웹 서버가 캐시에서 단축 코드에 대응하는 원래 URL을 조회한다.
4. 캐시에 있으면 해당 URL로 리다이렉션한다.
5. 캐시에 없으면 데이터베이스를 조회한다.
6. 데이터베이스에서 찾은 매핑을 캐시에 저장하고 리다이렉션한다.
7. 데이터베이스에도 없다면 잘못된 단축 코드에 대한 오류 응답을 반환한다.

캐시와 데이터베이스를 조회하는 것은 웹 서버의 역할이다. 로드밸런서는 요청을 처리할 웹 서버를 선택한다.

이 구조는 1장에서 배운 캐시와 무상태 웹 계층을 실제 서비스에 적용한 예시다.

## 4단계: 설계 후 추가로 고려할 사항

### 처리율 제한

과도한 단축 URL 생성 요청은 데이터베이스 저장 공간과 ID 발급 자원을 소모시킬 수 있다.

4장에서 배운 처리율 제한을 적용해 IP, 사용자, API 키 등을 기준으로 생성 요청을 제한할 수 있다.

### 웹 서버와 데이터베이스의 규모 확장

- 웹 서버는 상태를 공유 저장소에 두어 수평적으로 확장한다.
- 읽기 요청이 많으면 캐시와 읽기 복제본을 활용한다.
- 저장량과 쓰기 부하가 커지면 샤딩을 검토한다.
- 서버를 늘릴 때도 ID와 단축 코드의 유일성이 유지되어야 한다.

### 데이터 분석

단축 URL 서비스에서는 다음 정보가 유용할 수 있다.

- 어떤 링크가 많이 클릭되는가?
- 주로 언제 클릭되는가?
- 어떤 경로나 지역에서 유입되는가?

클릭 통계를 수집하려면 리다이렉션 방식과 캐시 정책을 함께 검토해야 한다.

### 가용성과 데이터 안정성

단축 URL의 매핑 정보가 사라지면 기존 링크를 사용할 수 없게 된다.

따라서 캐시만으로 운영하지 않고 데이터베이스 복제와 백업, 장애 대응을 고려해야 한다.

## 생각해본 질문

### MySQL의 AUTO_INCREMENT를 Base62로 바꾸면 충분할까? 7장에서 배운 분산 ID를 그대로 사용해도 7글자가 될까?

프로젝트에서 데이터베이스가 기본키를 발급해주던 방식과 연결되는 질문이다.

하나의 MySQL이 ID를 발급한다면 `AUTO_INCREMENT`를 사용하는 방법도 가능하다. 다만 여러 데이터베이스가 독립적으로 ID를 발급한다면 전체 시스템에서 중복되지 않도록 해야 한다.

반대로 7장의 스노플레이크 ID를 그대로 Base62로 바꾸면 유일성은 확보할 수 있지만, ID의 크기에 따라 7글자를 넘을 수 있다. 양의 63비트 정수 범위 전체를 표현하려면 최대 11글자가 필요하다.

따라서 다음 조건을 함께 검토해야 한다.

- 우리 서비스는 하루에 몇 개의 ID를 발급하는가?
- 여러 서버나 데이터베이스에서 독립적으로 발급해야 하는가?
- 단축 코드는 반드시 7글자 이내여야 하는가?
- 7글자를 지키기 위해 별도의 ID 범위를 관리할 필요가 있는가?

### JPA에서 먼저 존재 여부를 확인하면 단축 코드 중복을 막을 수 있을까?

해시 충돌을 검사할 때 `existsByShortCode()`로 먼저 조회한 뒤 `save()`하면 안전할 것처럼 보인다.

하지만 두 요청이 동시에 같은 코드의 존재 여부를 확인하면, 둘 다 없다고 판단한 후 저장을 시도할 수 있다.

따라서 조회 결과만 믿기보다 데이터베이스에 `UNIQUE` 제약조건을 두고, 중복 저장이 거절되었을 때의 처리를 설계해야 한다.

여기서 구분할 점도 있다.

- 서로 다른 원래 URL이 같은 코드 후보를 만든 경우: 새 코드를 만들어 재시도한다.
- 같은 원래 URL에 대한 요청이 동시에 들어온 경우: 기존 코드를 재사용할지 별도 코드를 발급할지 정책을 정한다.

애플리케이션의 사전 검사와 데이터베이스의 유일성 보장이 각각 어떤 역할을 하는지 토론해볼 수 있다.

### Base62 코드를 MySQL에 저장할 때 대소문자 구분도 확인해야 하지 않을까?

Base62에서는 `abc1234`와 `Abc1234`가 서로 다른 코드다.

그런데 데이터베이스의 문자열 비교 설정이 대소문자를 구분하지 않는다면, 두 코드가 같은 값으로 취급될 수 있다.

그러면 애플리케이션에서 생각한 62개의 문자 조합과 데이터베이스에서 구분하는 값의 범위가 달라진다.

MySQL에 코드를 저장할 때는 대소문자를 구분하는 collation이나 바이너리 타입을 검토해야 한다.

알고리즘에서 유일한 코드를 만들었더라도 실제 저장소의 비교 규칙까지 일치해야 한다는 점을 생각해볼 수 있다.

### Nginx로 리다이렉션해본 경험을 기준으로, 단축 URL에는 301과 302 중 무엇을 선택해야 할까?

배포하면서 도메인과 HTTPS 연결을 설정했던 경험과 연결해볼 수 있다.

단축 URL 서버의 부하만 줄이고 싶다면 301의 캐시가 유리할 수 있다. 하지만 클릭 통계를 수집하거나 목적지를 변경해야 한다면, 브라우저가 단축 서버를 거치지 않는 상황이 문제가 된다.

반면 웹 서버가 Redis에서 매핑을 읽더라도 요청은 서버에 도착하므로 클릭 기록을 남길 기회가 있다.

즉 다음 두 캐시는 구분해서 생각해야 한다.

- 브라우저가 리다이렉션 응답을 캐시하는 경우
- 웹 서버가 URL 매핑 정보를 Redis에 캐시하는 경우

우리 서비스에서 클릭 분석과 서버 부하 감소 중 무엇을 우선할지, 그리고 `Cache-Control`을 어떻게 설정할지 토론해볼 수 있다.

### 단축 URL을 방금 만들었는데 첫 클릭에서 404가 발생한다면 무엇을 확인해야 할까?

웹 서버와 데이터베이스를 분리해 운영했던 구조를 더 확장한다고 가정해볼 수 있다.

단축 URL을 주 데이터베이스에 저장한 직후, 읽기 복제본에서 매핑을 조회하면 복제 지연 때문에 아직 데이터를 찾지 못할 수 있다.

또한 새 링크를 캐시에 미리 넣지 않았다면 첫 요청은 캐시에도 데이터가 없어 데이터베이스까지 조회해야 한다.

이때 확인할 것은 다음과 같다.

- 생성 API가 데이터베이스 저장 완료 후 응답했는가?
- 조회 요청이 주 데이터베이스와 읽기 복제본 중 어디로 갔는가?
- 복제 지연이 얼마나 발생했는가?
- 존재하지 않는다는 조회 결과까지 캐시하고 있지는 않은가?

새 링크의 즉시 사용을 보장하려면 주 데이터베이스 재조회나 저장 완료 후 캐시 등록 등의 방법을 검토할 수 있다. 각 방법의 정확성과 부하 사이에서 어떤 선택이 적절할지 생각해볼 수 있다.

### 몽글에 꿈 결과 공유 링크를 만든다면 짧은 코드만으로 접근 권한까지 해결해도 될까?

공유 기능을 추가한다고 가정하면, 짧은 코드를 가진 링크는 전달하기 편리하다. 하지만 코드가 짧거나 순차적으로 생성된다면 다른 링크를 추측할 가능성도 있다.

Base62는 암호화가 아니므로 코드가 짧아졌다는 사실만으로 비공개 데이터가 보호되지는 않는다.

먼저 공유 정책을 구분해야 한다.

- 누구나 볼 수 있는 공개 공유인가?
- 로그인한 특정 사용자만 볼 수 있는가?
- 링크를 아는 사람에게만 공개하는가?
- 만료나 공유 취소가 필요한가?

정책에 따라 인증과 권한 검사, 추측하기 어려운 토큰, 만료 처리가 필요할 수 있다.

특히 공유 취소를 지원한다면 책의 '수정·삭제가 없는 URL 매핑'과 달라진다. 데이터베이스에서 링크를 비활성화했을 때 캐시나 브라우저에 남은 정보까지 어떻게 처리할지도 함께 설계해야 한다.
