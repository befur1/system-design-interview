# [5주차] 8장 정리 - 원지현
# 8장_ URL 단축기 설계

## 문제 이해 및 설계 범위 확정
URL 단축기란 긴 URL을 짧은 URL로 바꿔주고, 단축 URL로 접속하면 원래 URL로 리디렉션해주는 서비스임.
- 핵심 기능: URL 단축, 단축 URL 접속 시 원래 URL로 리디렉션
- 트래픽 규모: 매일 1억 개의 단축 URL 생성
- 사용 가능한 문자: 0-9, a-z, A-Z (총 62개)
- 단축 URL의 삭제나 갱신은 불가능하다고 가정함.

## 개략적 규모 추정
- 쓰기 연산: 초당 약 1,160회 / 읽기 연산(읽기:쓰기 = 10:1): 초당 약 11,600회
- 10년간 저장할 레코드 수: 1억 × 365 × 10 = 3,650억 개
- 평균 URL 길이를 100바이트로 가정하면 10년간 약 36.5TB 필요

## 개략적 설계

URL 리디렉션: 301 vs 302
- 301 Permanent Redirect: 브라우저가 응답을 캐시하므로 이후 요청은 단축기 서버를 거치지 않음. → 서버 부하 감소에 유리함.
- 302 Found: 매번 단축기 서버를 거쳐 리디렉션됨. → 클릭 수, 유입 경로 같은 트래픽 분석에 유리함.

해시 값 길이
- 62^n ≥ 3,650억을 만족하는 최소 n을 구함.
- n=6이면 약 568억으로 부족, n=7이면 약 3.5조로 충분함. → 단축 URL 길이는 7자로 결정

## 상세 설계

방안 1: 해시 후 충돌 해소
- 긴 URL을 CRC32, MD5 등으로 해시한 뒤 앞 7자만 사용함.
- 충돌 시 긴 URL에 미리 정한 문자열을 덧붙여 다시 해시함. (충돌이 사라질 때까지 반복)
- 매번 DB 조회가 필요해 비용이 크므로, 블룸 필터로 성능을 개선할 수 있음.

방안 2: base-62 변환
- 유일 ID 생성기로 겹치지 않는 ID를 발급하고, 이를 62진수로 변환해 단축 URL을 만듦.
- 해시가 아닌 진법 변환이므로 되돌릴 수 있고, ID가 유일하면 충돌이 원천적으로 발생하지 않음.

두 방안 비교
- 해시 후 충돌 해소: 길이 고정 / ID 생성기 불필요 / 충돌 해소 필요 / 다음 URL 추측이 어려움
- base-62 변환: 길이 가변 / 유일 ID 생성기 필요 / 충돌 없음 / ID가 순차 증가하면 다음 URL 추측이 쉬워 보안 문제가 생길 수 있음

URL 단축 흐름 (base-62 방식)
- 긴 URL을 입력받음.
- DB에 이미 있는 URL이면 기존 단축 URL을 반환함.
- 없으면 유일 ID를 생성함. (예: 2009215674938)
- ID를 62진수로 변환함. (예: zn9edcu)
- <id, shortURL, longURL>을 DB에 저장하고 단축 URL을 반환함.

URL 리디렉션 흐름
- 읽기가 쓰기보다 훨씬 많으므로 <단축 URL, 원래 URL> 쌍을 캐시에 저장함.
- 단축 URL 요청이 오면 캐시를 먼저 조회하고, 없으면 DB에서 조회한 뒤 캐시에 저장하고 반환함.

## 마무리
- 처리율 제한 장치로 악의적인 대량 단축 요청을 차단함.
- 웹 계층은 무상태이므로 서버를 쉽게 추가·삭제할 수 있고, DB는 다중화와 샤딩으로 확장함.

## 실제 사례 찾아보기: 실제 서비스의 단축 URL 방식 차이
- 유튜브 (youtu.be)
    - 공유되는 URL 대부분이 동영상이고, 동영상마다 이미 짧고 유일한 ID(11자)가 있음.
    - 단축 URL에서도 이 ID를 그대로 사용하고 앞부분만 바꾸므로, 별도 DB 조회 없이 규칙만으로 리디렉션 가능함.
    - 예: youtube.com/watch?v=dQw4w9WgXcQ → youtu.be/dQw4w9WgXcQ
- 네이버 (naver.me)
    - 지도, 검색, 블로그 등 여러 서비스의 URL 구조가 서로 다르고, URL 안에 많은 정보가 담겨 있어 공통 규칙으로 줄일 수 없음.
    - 따라서 책의 방식처럼 새 ID를 발급하고 <단축 URL, 긴 URL> 매핑을 DB에 저장하는 방식이 필요함.
- 정리: 단축하려는 URL의 구조를 직접 알고 통제할 수 있으면 규칙 기반으로, 그렇지 않으면 ID 발급 + DB 매핑 방식으로 단축함.

## 내 경험에 녹여보기: 데모데이 프로젝트에 적용해보기
- 현재 진행 중인 데모데이 프로젝트는 서비스 규모가 작고 URL 구조가 단순해 애초에 URL이 짧으므로, 별도의 URL 단축기가 필요하지 않음.
- 다만 홍보용 마케팅 링크가 필요하다면, 의미 없는 문자열을 자동 생성하는 방식 대신 커스텀 별칭을 사용해 단축 URL을 만들 수 있음.
    - 예: 홍보 채널별로 별칭을 다르게 만들어 어떤 채널에서 유입이 많은지 확인할 수 있음.
- 커스텀 별칭은 사용자가 직접 정하므로 중복될 수 있어, 생성 시 이미 사용 중인 별칭인지 확인하는 과정이 필요함.
- 자체 단축기를 구축하기보다 외부 단축 서비스를 활용하는 것이 규모에 맞는 선택임.
