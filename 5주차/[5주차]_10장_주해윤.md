## 10장 알림 시스템 설계

---

> 알림 시스템은 최신 뉴스, 제품 업데이트, 이벤트, 선물 등 고객에게 중요할 만한 정보를 비동기적으로 제공하는 기능이다.
> 
- 알림의 종류
    1. 모바일 푸시 알림
    2. SMS 메시지
    3. 이메일

### 문제 이해 및 설계 범위 확정

- 지원할 알림: 푸시 알림, SMS 메시지, 이메일
- 연성 실시간 시스템
    - 알림은 가능한 한 빨리 전달되어야 함
    - 시스템에 높은 부하가 걸렸을 때 약간의 지연은 허용
- 지원 단말
    - iOS 단말
    - 안드로이드 단말
    - 랩톱/데스크톱
- 알림 생성 주체
    - 클라이언트 애플리케이션
    - 서버 측 스케줄링
- 사용자가 알림을 받지 않도록 설정할 수 있어야 함
- 하루에 전송해야 하는 알림
    - 모바일 푸시 알림: 천만 건
    - SMS 메시지: 백만 건
    - 이메일: 5백만 건

### 개략적 설계안 제시 및 동의 구하기

**알림 유형별 지원 방안**

- iOS 푸시 알림
    - 알림 제공자가 알림 요청을 만들어 APNS에 전달
    - APNS가 iOS 단말에 푸시 알림을 전송
    - 알림 요청에 필요한 데이터
        - 단말 토큰: 알림 전송에 필요한 고유 식별자
        - 페이로드: 알림 내용을 담은 JSON 딕셔너리
- 안드로이드 푸시 알림
    - iOS 푸시 알림과 비슷한 절차
    - APNS 대신 FCM을 사용
- SMS 메시지
    - 트윌리오, 넥스모 같은 제3자 서비스를 사용
    - 대부분 상용 서비스이므로 이용 요금이 발생
- 이메일
    - 자체 이메일 서버 또는 센드그리드, 메일침프 같은 상용 이메일 서비스 사용
    - 상용 서비스는 높은 전송 성공률과 데이터 분석 서비스를 제공

**연락처 정보 수집 절차**

- 사용자가 앱을 설치하거나 계정을 등록하면 API 서버가 연락처 정보를 수집하여 데이터베이스에 저장
- 이메일 주소와 전화번호는 `user` 테이블에 저장
- 단말 토큰은 `device` 테이블에 저장
- 한 사용자가 여러 단말을 가질 수 있으며, 알림은 모든 단말에 전송될 수 있음

**개략적 설계안 초안**

- 서비스 1~N
    - 알림 시스템 API를 호출하는 마이크로서비스, 크론잡 또는 분산 시스템 컴포넌트
- 알림 시스템
    - 알림 전송과 수신 처리의 핵심
    - 서비스에 알림 전송 API 제공
    - 사용자 정보, 단말 토큰, 알림 설정 등을 데이터베이스나 캐시에서 조회
    - 알림에 맞는 이벤트를 생성하여 해당 메시지 큐에 저장
- 제3자 서비스
    - APNS, FCM, SMS 서비스, 이메일 서비스
    - 사용자에게 알림을 실제로 전달
    - 일부 서비스는 특정 시장에서 사용할 수 없으므로 확장성을 고려해야 함
- iOS·안드로이드·SMS·이메일 단말
    - 사용자가 알림을 수신하는 단말

**초안의 문제점**

- SPOF: 알림 서비스 서버가 한 대뿐이면 장애가 전체 서비스 장애로 이어짐
- 규모 확장성: 한 대의 서버가 푸시 알림과 관련된 모든 작업을 처리하므로 컴포넌트를 개별적으로 확장할 수 없음
- 성능 병목: 알림 처리와 제3자 서비스의 응답을 기다리는 작업에는 시간이 걸릴 수 있어 트래픽이 몰리면 시스템이 과부하 상태에 빠질 수 있음

**개선된 설계안**

- 데이터베이스와 캐시를 알림 시스템의 주 서버에서 분리
- 알림 서버를 증설하여 수평적 규모 확장이 가능하도록 함
- 메시지 큐를 사용해 시스템 컴포넌트 사이의 강한 결합을 끊음
- 알림 종류별로 별도의 메시지 큐를 사용
    - 특정 제3자 서비스에 장애가 발생해도 다른 종류의 알림은 정상적으로 동작
- 작업 서버가 메시지 큐에서 알림을 꺼내 제3자 서비스에 전달

**알림 전송 절차**

1. 서비스가 API를 호출하여 알림 서버에 알림을 보냄
2. 알림 서버가 사용자 정보, 단말 토큰, 알림 설정 등의 메타데이터를 캐시나 데이터베이스에서 가져옴
3. 알림 서버가 알림에 맞는 이벤트를 만들어 해당 메시지 큐에 저장
4. 작업 서버가 메시지 큐에서 알림 이벤트를 꺼냄
5. 작업 서버가 알림을 제3자 서비스에 전달
6. 제3자 서비스가 사용자 단말로 알림을 전송

### 상세 설계

**안정성**

- 데이터 손실 방지
    - 알림이 지연되거나 순서가 바뀔 수는 있지만 소실되어서는 안 됨
    - 알림 데이터를 데이터베이스에 보관하고 재시도 메커니즘을 구현
    - 알림 로그 데이터베이스를 유지
- 알림 중복 전송 방지
    - 분산 시스템의 특성상 같은 알림이 중복 전송될 수 있음
    - 알림이 도착하면 이벤트 ID를 검사하여 이전에 처리한 이벤트인지 확인
    - 중복 이벤트라면 버리고, 그렇지 않으면 알림을 발송
    - 중복 전송을 100% 방지하는 것은 불가능

**추가로 필요한 컴포넌트 및 고려사항**

- 알림 템플릿
    - 비슷한 형식의 알림을 매번 처음부터 만들지 않도록 함
    - 인자, 스타일, 추적 링크 등을 조정하여 정해진 형식의 알림 생성
    - 알림 형식의 일관성을 유지하고 오류 가능성과 작성 시간을 줄임
- 알림 설정
    - 사용자가 알림을 받을 채널과 수신 여부를 설정할 수 있도록 함
    - 사용자 ID, 채널, 수신 여부 등의 정보를 저장
    - 알림을 보내기 전에 사용자가 해당 알림을 켜 두었는지 확인
- 전송률 제한
    - 한 사용자가 받을 수 있는 알림의 빈도를 제한
    - 너무 많은 알림으로 인해 사용자가 알림 기능을 꺼 버리는 일을 방지
- 재시도 방법
    - 제3자 서비스가 알림 전송에 실패하면 해당 알림을 재시도 전용 큐에 저장
    - 같은 문제가 계속 발생하면 개발자에게 통지
- 푸시 알림과 보안
    - iOS와 안드로이드 알림 전송 API는 `appKey`와 `appSecret`을 사용
    - 인증되거나 승인된 클라이언트만 API를 사용하여 알림을 보낼 수 있음
- 큐 모니터링
    - 큐에 쌓인 알림 개수는 중요한 지표
    - 큐의 크기가 너무 크면 작업 서버가 이벤트를 빠르게 처리하지 못하고 있다는 의미
    - 필요한 경우 작업 서버를 증설
- 이벤트 추적
    - 알림 확인율, 클릭률, 실제 앱 사용으로 이어지는 비율 등을 추적
    - 데이터 분석 서비스를 알림 시스템과 통합

**수정된 설계안에 추가된 내용**

- 알림 서버에 인증과 전송률 제한 기능 추가
- 전송 실패에 대응하기 위한 재시도 기능 추가
- 전송 템플릿을 사용하여 알림 생성 과정과 내용의 일관성 유지
- 모니터링과 추적 시스템으로 시스템 상태와 알림 이벤트 확인
- 사용자의 알림 수신 설정을 확인한 뒤 알림 전송
