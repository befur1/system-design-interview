# [5주차] 10장 - 알림 시스템 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

## 책 내용 뼈대

푸시, SMS, 이메일 세 종류의 알림을 하루 수천만 건 보내는 시스템을 설계한다.

### 알림 유형과 제3자 서비스

| 유형 | 경로 | 필요한 것 |
| --- | --- | --- |
| iOS 푸시 | APNS | 디바이스 토큰, 페이로드 |
| 안드로이드 푸시 | FCM | 디바이스 토큰 |
| SMS | 트윌리오, 넥스모 | 전화번호 |
| 이메일 | 센드그리드, 메일침프 | 이메일 주소 |

공통점은 전부 우리가 통제하지 않는 외부 서비스라는 것이다. 설계의 많은 부분이 이 사실에서 나온다.

### 규모 추정

| 유형 | 하루 발송량 |
| --- | --- |
| 푸시 | 1,000만 |
| SMS | 100만 |
| 이메일 | 500만 |

### 연락처 정보 수집

앱을 설치하거나 처음 로그인할 때 디바이스 토큰과 연락처가 서버로 와서 저장된다. 사용자 한 명이 여러 단말을 가질 수 있으므로 user와 device는 1:N이다.

### 초기 설계의 문제 세 가지

알림 서버 하나가 전부 처리하는 설계에서 출발한다.

| 문제 | 내용 |
| --- | --- |
| SPOF | 알림 서버가 하나라 죽으면 전부 멈춘다 |
| 규모 확장성 | 한 서버가 DB, 캐시, 제3자 전송을 다 한다 |
| 성능 병목 | 제3자 서비스 응답을 기다리는 동안 자원이 묶인다 |

### 개선안

알림 서버를 여러 대로 늘리고, 그 뒤에 메시지 큐를 유형별로 따로 둔다. 큐 뒤에 워커가 붙어 제3자 서비스를 호출한다.

큐를 유형마다 나누는 이유가 핵심이다. 한 제3자 서비스에 장애가 생겨 큐가 막혀도 다른 유형의 알림은 계속 나간다. 장애 전파를 막는 격리다.

### 신뢰성

| 주제 | 내용 |
| --- | --- |
| 데이터 손실 방지 | 알림 로그 DB에 기록하고 재시도 |
| 중복 전송 방지 | 정확히 한 번은 보장할 수 없다. 이벤트 ID로 본 적 있으면 버린다 |

### 추가 고려사항

알림 템플릿, 알림 설정(사용자가 끌 수 있게, 보내기 전에 확인), 처리율 제한, 재시도, 푸시 알림 보안(appKey와 appSecret), 큐 모니터링(쌓인 알림 수가 핵심 메트릭), 이벤트 추적(오픈율, 클릭율).

# 개인적인 질문

## 1. 정확히 한 번만 보낸다는 게 왜 불가능한가 - 4주차와 이어지는 부분

책이 신뢰성 절에서 중복 방지가 가능한가라고 묻고 아니오라고 답한다. 처음에는 이게 무슨 말인지 몰랐다. 잘 만들면 되는 거 아닌가 싶었다.

응답이 유실되는 상황을 그려보니 바로 보였다.

```
알림 서버 -> FCM      : 이 푸시 보내줘
FCM       -> 사용자   : 푸시 도착함
FCM       -> 알림 서버: 보냈어          <- 이 응답이 네트워크에서 유실
알림 서버 : 응답이 없다. 실패했나? 재시도해야지.
알림 서버 -> FCM      : 이 푸시 보내줘
                        -> 사용자는 같은 알림을 두 번 받는다
```

핵심은 서버가 이 둘을 구분할 수 없다는 것이다.

| 실제로 일어난 일 | 서버가 보는 것 |
| --- | --- |
| 전송에 실패했다 | 응답 없음 |
| 전송은 됐는데 응답만 유실됐다 | 응답 없음 |

똑같이 보인다. 그러면 선택지가 두 개뿐이다.

| 재시도한다 | 재시도 안 한다 |
| --- | --- |
| 최소 한 번 (at-least-once) | 최대 한 번 (at-most-once) |
| 중복은 생길 수 있다 | 유실은 생길 수 있다 |

정확히 한 번은 애초에 선택지에 없다. 구현을 잘 못해서가 아니고 네트워크가 메시지를 잃을 수 있는 한 피할 수 없는 제약이다.

### 그래서 실무가 하는 것

최소 한 번 보내고 받는 쪽에서 중복을 제거해 사실상 한 번을 만든다. 책의 로직이 이것이다. 알림을 보내기 전에 이벤트 ID를 검사해서 본 적 있는 ID면 버리고, 처음 보는 ID면 발송하고 기록한다.

이것도 100%는 아니다. 기록과 전송 사이에 서버가 죽으면 틈이 생긴다.

| 순서 | 서버가 중간에 죽으면 |
| --- | --- |
| 기록하고 전송 | 기록은 남았는데 안 보냄. 유실 |
| 전송하고 기록 | 보냈는데 기록이 없음. 중복 |

어느 쪽을 택해도 틈이 남는다. 그래서 책이 대부분의 경우 한 번만 가지만 가끔 중복된다고 쓴다. 빈도를 줄이는 것이 목표고 0으로 만드는 건 목표가 아니다.

### 4주차에 팠던 멱등성 키와 구조가 같다

| | 4주차 멱등성 키 | 10장 중복 알림 방지 |
| --- | --- | --- |
| 문제 | 결제 요청이 두 번 들어옴 | 알림을 두 번 보냄 |
| 원인 | 클라이언트가 응답을 못 받아 재시도 | 서버가 응답을 못 받아 재시도 |
| 방향 | 들어오는 것을 막음 | 나가는 것을 막음 |
| 해법 | 키를 기록하고 본 적 있으면 거부 | 이벤트 ID를 기록하고 본 적 있으면 버림 |
| 진짜 방어선 | DB unique 제약 | 같음 |
| 완벽한가 | 아니오 | 아니오 |

방향만 반대고 구조가 같다. 4주차에 Idempotency-Key 헤더와 unique 제약 위반을 잡아 기존 결과를 돌려주는 패턴까지 봤는데, 그게 10장에서 나가는 방향으로 다시 나온 셈이다.

### 그런데 왜 알림은 결제처럼 막지 않나

중복의 비용이 다르기 때문이다.

| | 중복되면 | 그래서 |
| --- | --- | --- |
| 결제 | 돈이 두 번 빠진다 | unique 제약으로 강하게 막는다 |
| 알림 | 사용자가 짜증난다 | 이벤트 ID 체크로 느슨하게 막는다 |

중복의 비용이 방어의 강도를 결정한다. 알림에 결제급 방어를 걸면 비용만 들고, 결제에 알림급 방어를 걸면 사고가 난다. 같은 문제에 다른 강도를 쓰는 판단이 들어가는 것이다. 책이 알림에서는 빈도를 줄이는 것으로 만족하는 이유가 여기 있었다.

# 내 프로젝트에 이미 같은 구조가 있었다

전시 공간 서비스 프로젝트에서 사용자가 사진을 올리면 외부 API로 배경을 제거하고 후처리해서 저장하는 기능을 만들었다. 알림이 아닌데 10장의 구조와 거의 같았다.

| 10장 알림 시스템 | 내 이미지 처리 |
| --- | --- |
| 알림 서버가 접수하고 큐에 넣는다 | 트랜잭션 커밋 후 이벤트로 접수하고 실행기에 넣는다 |
| 제3자 서비스 호출이 느려서 비동기로 | 외부 API 왕복만 1~3초, 전체 수 초 |
| 유형별 큐 분리 | 이미지 처리용 실행기를 따로 분리 |
| 알림 로그로 상태 추적 | PENDING, READY, FAILED 상태 기록 |
| 재시도 | 실패한 건 재처리 |
| 큐 모니터링 | 큐가 가득 차면 거절을 받아 FAILED로 정리 |

## 1. 책이 왜 비동기로 가는지를 이미 겪었다

요청 스레드에서 외부 API를 기다리면 업로드 버튼을 누른 화면이 수 초간 멈춘다. 그래서 접수만 하고 백그라운드로 넘겼다. 책이 성능 병목으로 지적한 제3자 서비스 대기가 정확히 그 문제였다.

## 2. 트랜잭션 안에 외부 호출을 넣지 않은 이유 - 3주차와 이어진다

외부 API 왕복을 트랜잭션이 물고 있으면 그동안 DB 커넥션을 붙잡는다. 그래서 처리 전체에는 트랜잭션을 걸지 않고, 결과를 쓸 때만 짧은 트랜잭션을 연다.

3주차에 상준이형이 어떻게 해야 톰캣 스레드와 DB 커넥션을 0.001초라도 빨리 풀어줄까라고 했던 그 얘기다. 비싼 자원은 꼭 필요한 순간에만 가장 짧게 잡는다는 원칙이 1장부터 10장까지 계속 같은 모양으로 나온다.

| 주차 | 짧게 잡아야 하는 자원 |
| --- | --- |
| 3주차 | 톰캣 스레드, DB 커넥션 |
| 4주차 | DB 락 (ID를 미리 발급해 락 보유 시간을 줄인다) |
| 5주차 | 제3자 서비스를 기다리는 워커 |

## 3. 그런데 내 구조에는 구멍이 있다 - 책을 읽고 알았다

내 코드는 스프링의 실행기, 즉 프로세스 안의 스레드풀을 큐로 쓴다. 책은 메시지 큐를 쓰라고 한다. 차이가 뭔지 생각해보니 하나였다.

| | 인메모리 실행기 (내 코드) | 메시지 큐 (책) |
| --- | --- | --- |
| 큐가 어디 있나 | 프로세스 메모리 | 외부 저장소 |
| 서버가 죽으면 | 큐에 있던 작업이 사라진다 | 메시지가 남아있다 |
| 재시작 후 | PENDING인 채로 영원히 방치 | 워커가 다시 꺼내 처리 |
| 워커 수평 확장 | 그 서버 안에서만 | 서버를 늘리면 늘어난다 |

내 코드에는 큐가 가득 차 거절되는 경우를 처리하는 로직이 있다. 거절을 그 자리에서 잡아 FAILED로 정리하도록 일부러 그렇게 짰다. 그런데 서버가 죽는 경우는 처리하지 못한다. 배포 중에 작업이 진행되고 있었으면 그 사진은 PENDING인 채로 남고 아무도 다시 처리해주지 않는다.

책이 말하는 알림 데이터 손실 방지가 이 문제였다. 큐를 프로세스 밖에 두는 이유는 확장 때문만이 아니라 프로세스의 생사와 작업의 생사를 분리하기 위한 것이다. 비동기로 바꿀 때 큐를 메모리에 두느냐 밖에 두느냐가 단순한 구현 선택이 아니라 신뢰성 수준을 결정하는 선택이었다.

당장 메시지 큐를 도입할 규모는 아니지만, PENDING 상태로 오래 남은 건을 주기적으로 찾아 재처리하는 쪽은 지금 구조에서도 붙일 수 있을 것 같다.

## 4. 데모데이에 이메일 발송을 붙이려고 하는데 10장이 그대로 쓰인다

이번 데모데이에 이메일 발송 기능을 붙일 계획인데, 10장을 읽고 나니 그냥 보내면 안 되는 것들이 보였다.

| 10장에서 가져올 것 | 왜 |
| --- | --- |
| 큐를 거쳐 보내기 | 센드그리드 응답을 요청 스레드가 기다리면 안 된다 |
| 발송 로그 기록 | 안 갔을 때 확인할 방법이 있어야 한다 |
| 이벤트 ID로 중복 체크 | 재시도가 중복 발송이 되지 않게 |
| 발송 전에 수신 설정 확인 | 끈 사용자에게 보내면 안 된다 |
| 처리율 제한 | 제3자 서비스의 쿼터와 비용을 넘지 않게 |
| 재시도 | 일시적 실패는 다시, 영구 실패는 포기 |

특히 중복 체크와 재시도를 처음부터 같이 설계해야 한다는 걸 알았다. 재시도를 넣는 순간 중복이 생길 수 있고, 중복 방지가 없는 재시도는 사용자에게 같은 메일을 여러 통 보내는 기능이 된다. 둘은 한 쌍이었다.

## 3주차, 4주차와 연계해서 생각해보자

10장은 앞에서 본 것들이 한곳에 모이는 장이었다.

| 앞에서 배운 것 | 10장에서 쓰이는 곳 |
| --- | --- |
| 처리율 제한 (3주차) | 제3자 서비스 쿼터와 사용자 피로도 관리 |
| 큐와 워커 (3주차) | 동시 호출 수를 워커 수로 제한 |
| 멱등성 키 (4주차) | 이벤트 ID로 중복 발송 차단 |
| 로그와 메트릭 (4주차) | 알림 로그, 큐에 쌓인 알림 수 모니터링 |

3주차에 처리율 제한을 보면서 무거운 작업은 비율이 아니라 동시성을 제한해야 하고 큐에 워커를 붙이면 그게 동시성 제한이 된다는 이야기를 했다. 10장의 큐와 워커 구조가 정확히 그 모양이다. 알림 발송은 제3자 서비스 왕복이라 무거운 작업이고, 그래서 초당 몇 건이 아니라 동시에 몇 건으로 제한하는 게 맞는 작업이다.

## 스스로 확인해본 것 - 큐를 하나로 합치면 무엇이 깨지나

유형별로 큐를 나누는 이유를 생각해봤다. 하나로 합치면 FCM에 장애가 생겨 푸시 워커가 전부 막혔을 때 큐 앞쪽이 푸시 메시지로 막히고, 뒤에 있는 이메일과 SMS가 나가지 못한다. 한 제3자 서비스의 장애가 전체 알림의 장애가 된다.

나눠두면 푸시 큐만 쌓이고 나머지는 그대로 나간다. 장애의 영향 범위를 큐 경계로 자르는 것이다. 이미지 처리 실행기를 따로 분리해둔 것도 같은 이유였다는 걸 이제 알았다. 공용 스레드풀을 썼으면 외부 API가 느려질 때 다른 비동기 작업까지 같이 멈췄을 것이다.
