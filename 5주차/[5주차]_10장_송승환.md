### 알림 유형별 지원 방안

1. IOS 푸시 알림
    
    세 가지 컴포넌트가 필요한데
    
    1. **알림 제공자:** 알림 요청을 만들어 애플 푸시 알림 서비스로 보내는 주체
    2. **APNS**: 애플이 제공하는 서비스로 푸시 알림을 IOS 장치로 보내는 역할을 담당함
    3. **IOS 단말:** 사용자 단말
2. 안드로이드 푸시 알림
    
    IOS 푸시 알림 컴포넌트에서 APNS 대신 FCN을 사용
    
3. SMS 메세지
    
    트윌리오, 넥스모 같은 제3 사업자의 서비스를 APNS 대신 이용
    
4. 이메일
    
    센드그리드, 메일침프 같은 서비스로 이용
    

### 연락처 정보 수집 절차

### 알림 전송 및 수신 절차

- 1개의 서버만 사용하는 시스템일 때
    
     알림 전송 관련 제3자 제공 서비스들이 OS 마냥 확장성이 있어야 함. 즉, 새로운 서비스를 쉽게 통합하거나 기존의 서비스를 쉽게 제거할 수 있어야 한다는 의미임
    
- 개선된 시스템
    
    DB와 캐시를 주 서버에서 분리하고, 알림 서버와 작업 서버를 나누어 처리 함
    
    1. 처음에 여러 서비스에서 요청하는 알림 관련 처리를 알림 서버가 담당
        - 알림 전송 API: 스팸 방지를 위해 인증된 클라이언트만 처리
        - 알림 검증: 이메일 주소, 전화 번호와 같은 기본적 검증을 수행
        - DB 또는 캐시 질의: 알림에 포함시킬 데이터를 가져오는 기능
        - 알림 전송: 알림 데이터를 큐에 넣음
    2. 알림 서버가 캐시를 찾아서 알림 검증이나 알림 템플릿 등을 가져옴
    3. 캐시에 없으면 DB에서 찾아서 캐시에 넣고 가져옴
    4. 알림의 종류마다 큐가 따로 있어서 제3자 서비스 중 하나가 문제가 있어도 다른 것들은 정삭 작동함
    5. 큐에서 전송할 알림을 꺼내서 제3자 서비스로 전달하는 작업 서버로 전달
    6. 제3자 서비스가 데이터를 받아서 처리해 줌
    
    ### 상세 설계에서 고려해야 할 것
    
    #### 안정성
    
    - 데이터 손실 방지: 알림이 지연되거나 순서가 틀리는건 상관 X. But, 알림이 소실되면 안 된다는 것
    - 알림 중복 전송 방지: 같은 알림을 여러 번 반복되는 것을 완전히 막을 수는 없지만 최대한 막으려고 함.
        
        → 알림 서버는 제 3자 서비스로 전달한 것만 알고, 제 3자 서비스의 응답 ACK이 유실된건지, 자신이 보낸 요청이 안 간건지 알 수 없으니 다시 보낼 수 밖에 없음
        
    
    #### 추가로 필요한 컴포넌트 및 고려사항
    
    - 알림 템플릿: 수 백만 건 이상의 알림이 대부분 비슷한 형식이다 보니 이를 템플릿으로 만들어 인자만 바꿔서 전송하면 일관성 있게 형식을 유지할 수 있고, 오류 가능성 및 알림 작성 시간 감소로 이어짐
    - 알림 설정: 사용자가 알림을 받을 것인지를 확인하는 필드로 알림을 보내기 전에 확인해야 함
    - 전송률 제한: 사용자에게 너무 많은 알림을 받지 않게 하는 것
    - 재시도 방법: 제3자 서비스가 알림 전송에 실패하면, 해당 알림을 재시도 전용 큐에 넣음
    - 푸시 알림과 보안: 애플은 인증/승인된 클라이언트만 해당 API를 사용하여 알림을 보낼 수 있음
    - 큐 모니터링: 메세지 큐엥 너무 많이 쌓여 있으면 작업 서버들이 이벤트를 빠르게 못 처리하고 있다는 의미
    - 이벤트 추적: 알림 확인율, 클릭율, 실제 앱 사용으로 이어지는 비율 같은 메트릭은 사용자를 이해하는데 중요
    
    ### 내 프로젝트에 이미 같은 자리가 있었음 — HAMA 비밀번호 재설정
    
    데모데이 프로젝트(HAMA)에서 비밀번호 찾기에 Resend(메일 API)를 붙였는데, 책이 말한 **제3자 서비스**가 정확히 그 자리였음. 센드그리드·메일침프가 들어가는 칸에 Resend가 들어간 것
    
    | 책 10장 | HAMA |
    | --- | --- |
    | 알림 제공자 | HAMA 백엔드 |
    | 제3자 서비스 | Resend |
    | 단말 | 사용자 메일함 |
    | 전송률 제한 | IP·이메일 각각 15분에 5회 |
    | 재시도 방법 | **없음** → 아래 질문 |
    
    #### 1. 책이 말한 '재시도 전용 큐'가 내 코드엔 없음
    
    지금 흐름
    
    - `requestPasswordReset()`은 한도 검사만 하고 `@Async`로 넘김 → 사용자는 바로 200을 받음
    - 메일 발송 실패는 `catch`해서 로그만 남기고 끝남
    
    그래서 Resend가 5xx를 주거나 타임아웃이 나면 메일이 영영 안 감. **사용자는 이미 200을 받아서 실패한 줄 모르고**, 안 와서 다시 요청하면 15분 5회 한도만 깎임
    
    책은 "제3자 서비스가 알림 전송에 실패하면 해당 알림을 재시도 전용 큐에 넣는다"고 함. 그 큐가 없는 상태임
    
    <aside>
    ⚠️
    
    그런데 큐를 그냥 넣으면 오히려 더 나빠짐
    
    - 재설정 토큰은 `upsert`라서 다시 요청하면 같은 행의 해시를 덮어씀(옛 링크 무효화)
    - 재시도 큐에 들어간 메일은 **실패 당시의 옛 토큰**을 들고 있음
    - 재시도를 기다리는 사이 사용자가 다시 요청 → 해시가 바뀜 → 뒤늦게 나간 재시도 메일의 링크는 이미 죽어 있음
    - **실패를 복구하려고 넣은 장치가 죽은 링크를 보내게 됨**
    </aside>
    
    #### 2. 메일 서버를 헬스 체크에서 뺀 이유
    
    ```yaml
    management:
      health:
        mail:
          enabled: false
    ```
    
    안 빼면 이렇게 됨
    
    Resend 잠깐 장애 → `/actuator/health`가 DOWN → ALB가 인스턴스를 비정상으로 판정 → ASG가 **멀쩡한 서버를 갈아치움**
    
    부가 기능인 메일의 장애가 서비스 전체 장애로 번지는 경로가 애플리케이션이 아니라 **인프라 쪽에** 있었음
    
    책 10장은 "제3자 서비스 중 하나에 문제가 생겨도 다른 것들은 정상 작동하게" 알림 종류마다 큐를 따로 두라고 함. 나는 큐 없이 **헬스 체크 범위를 줄이는 방식**으로 같은 격리를 얻은 셈
    
    판단 기준은 **"이 의존성이 죽으면 이 서버를 죽여야 하는가"**였음
    
    - DB → 그렇다. 넣는다
    - 메일 → 아니다. 뺀다
