# [5주차] 9장 - 웹 크롤러 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

## 책 내용 뼈대

시작 URL에서 출발해 링크를 따라가며 페이지를 수집하는 시스템을 설계한다.

### 규모 추정

| 항목 | 값 |
| --- | --- |
| 수집량 | 매월 10억 페이지 |
| QPS | 평균 약 400, 최대 약 800 |
| 페이지 평균 크기 | 500KB |
| 월 저장량 | 약 500TB |
| 5년 보관 | 약 30PB |

### 기본 알고리즘

```
URL 집합에서 하나 꺼내 다운로드
 -> HTML에서 링크를 추출
 -> 아직 방문하지 않은 링크를 URL 집합에 추가
 -> 반복
```

### 주요 컴포넌트

| 컴포넌트 | 역할 |
| --- | --- |
| 시작 URL 집합 | 출발점. 지역별, 주제별로 나눠 잡는다 |
| URL 프런티어 | 다운로드할 URL을 보관하는 큐 |
| HTML 다운로더 | 실제로 받아온다 |
| 도메인 이름 변환기 | URL을 IP로. DNS가 병목이 된다 |
| 콘텐츠 파서 | 받은 HTML을 검증, 파싱 |
| 중복 콘텐츠인가 | 같은 내용을 또 저장하지 않도록 판정 |
| URL 추출기 | 링크를 뽑아낸다 |
| URL 필터 | 확장자, 블랙리스트 제외 |
| 이미 방문한 URL인가 | 블룸 필터나 해시 테이블이 널리 쓰인다 |
| URL 저장소 | 방문한 URL 보관 |

### URL 프런티어가 풀어야 하는 세 가지

| | 문제 | 해법 |
| --- | --- | --- |
| 예의 | 같은 호스트에 요청이 몰리면 DoS처럼 된다 | 호스트별 큐 + 큐마다 워커 하나 |
| 우선순위 | 중요한 페이지를 먼저 받아야 한다 | 순위결정장치 + 우선순위별 큐 + 큐 선택기 |
| 신선성 | 페이지는 계속 바뀐다 | 재수집. 변경 이력과 중요도로 빈도 결정 |

프런티어는 전면 큐(우선순위)와 후면 큐(예의)의 두 단으로 구성된다.

### 성능과 안정성

| 분류 | 내용 |
| --- | --- |
| 성능 | 분산 크롤링, DNS 캐시, 지역성(서버를 대상 가까이), 짧은 타임아웃 |
| 안정성 | 안정 해시로 다운로더 서버 부하 분산, 크롤 상태 저장, 예외 처리, 데이터 검증 |
| 예의 | robots.txt 준수 |

### 문제 있는 콘텐츠 감지

| | 내용 |
| --- | --- |
| 중복 콘텐츠 | 웹의 30% 가까이가 중복. 해시나 체크섬으로 탐지 |
| 거미 덫(크롤러 함정) | 무한히 깊은 URL. 최대 길이 제한, 수동 제외 목록 |
| 데이터 노이즈 | 광고, 스크립트, 스팸은 제외 |

# 개인적인 질문

## 1. 중복 콘텐츠를 HTML 비교로 잡는다는데, 페이지에 시계가 있으면

책은 중복 콘텐츠 판단을 해시나 체크섬으로 한다고 쓴다. 그런데 페이지에 시계가 있으면 1초마다 해시값이 전부 달라진다. 그러면 못 잡는 게 아닌가 싶었다.

못 잡는다. 그리고 시계만의 문제가 아니었다.

| 같은 페이지인데 바뀌는 것 | 예 |
| --- | --- |
| 시간 표시 | 2026-11-02 14:33:07 |
| 조회수, 좋아요 | 조회 1,234회가 1,235회로 |
| 광고 | 로테이션으로 매번 다른 배너 |
| CSRF 토큰 | hidden input 값 |
| A/B 테스트 | 버튼 색과 문구가 사용자별로 다름 |
| 추천 목록 | 이 글을 본 사람들이 본 글 |
| 캐시 버스팅 | style.css?v=8f3a2c |

MD5는 한 글자만 바뀌어도 결과가 완전히 달라진다. 그게 암호학적 해시의 설계 목표(눈사태 효과)인데, 중복 판정에는 바로 그 성질이 독이 된다.

### 그래도 정확 해시는 1차 필터로 쓴다

바이트 단위로 똑같은 경우가 실제로 꽤 있다. 정적 문서, CDN 미러, URL 변형(트레일링 슬래시 유무, www 유무, http와 https). 제일 싼 필터라 먼저 돌린다. 문제는 여기서 못 걸러진 게 대부분이라는 것이다.

### 실제로는 3층으로 간다

1층은 URL 정규화다. 받기 전에 걸러낸다. 소문자화, 기본 포트 제거, 트레일링 슬래시 통일, 프래그먼트 제거, 쿼리 파라미터 정렬, utm_source 같은 추적 파라미터 제거. 그리고 사이트가 link rel=canonical로 정본을 직접 선언하면 그걸 믿고 접는다.

2층은 본문 추출이다. HTML 전체가 아니라 헤더, 푸터, 사이드바, 광고, 댓글을 떼고 본문 텍스트만 남긴다. 2만 글자 HTML이 본문 1,800자가 된다. 시계는 본문이 아니니까 여기서 대부분 사라진다.

3층이 유사도 해시다. 본문만 남겨도 오타 수정이나 문장 추가로 완전히 같지는 않다. 그래서 조금 다름을 같음으로 판정하는 해시가 필요한데, 요구사항이 암호학적 해시와 정반대다.

| | MD5, SHA | SimHash, MinHash |
| --- | --- | --- |
| 1비트 바뀌면 | 결과가 전부 바뀜 (의도된 설계) | 결과도 1~2비트만 바뀜 |
| 목적 | 완전 동일 판정, 위조 방지 | 유사 판정 |
| 비교 방법 | 같냐 다르냐 | 해밍 거리 |

SimHash는 문서를 특징(단어, 연속 단어 묶음)으로 쪼개 각각 해시하고, 가중치를 붙여 합산해 64비트 지문 하나로 압축한다. 두 지문의 해밍 거리가 3 이하면 중복으로 본다. 시계 한 줄이 바뀌면 특징 수천 개 중 하나만 바뀌니 지문은 거의 그대로다. 정확 해시로는 못 잡지만 유사도 해시는 잡는다.

이슈 질문으로 올렸다.

## 2. HTML에서 어떤 게 본문인지 어떻게 아나

2층에서 본문만 남긴다고 했는데, AI 없이 그걸 어떻게 아는지가 궁금했다. 알아보니 휴리스틱과 통계로 한다. 수단 네 개를 겹쳐 쓴다.

### 태그가 직접 알려주는 경우

HTML5 의미 태그가 있으면 끝난다. header, nav, aside, footer는 본문이 아니고 main, article은 본문이다. 문제는 많은 사이트가 전부 div로 짠다는 것이다.

### 링크 밀도

링크 밀도는 링크 안에 있는 글자수를 전체 글자수로 나눈 값이다.

| 블록 | 링크 밀도 |
| --- | --- |
| 네비게이션, 사이드바, 푸터 | 0.8 ~ 1.0 |
| 관련 글 목록 | 0.9 |
| 본문 문단 | 0.0 ~ 0.2 |

메뉴와 사이드바는 본질적으로 링크 덩어리고 본문은 아니다. 이 지표 하나로 보일러플레이트 대부분이 날아간다. div만 쓴 사이트에서도 작동한다. 비슷하게 텍스트와 태그의 비율도 쓴다. 본문 문단은 태그 하나에 글자가 많고 네비는 태그마다 글자가 몇 개뿐이다.

### 클래스와 아이디 이름으로 점수 매기기

조잡해 보이지만 실제로 많이 쓰인다. 개발자들이 이름을 정직하게 짓기 때문이다.

| | 단어 |
| --- | --- |
| 긍정 (점수 올림) | article, body, content, entry, main, post, text, story |
| 부정 (점수 내림) | comment, sidebar, footer, nav, related, promo, sponsor, widget, share |

파이어폭스 읽기 모드와 사파리 리더뷰가 쓰는 Readability 알고리즘이 이 방식이다. 콤마 개수와 텍스트 길이로 점수를 주고, 클래스 이름으로 가감하고, 마지막에 (1 - 링크밀도)를 곱한다. 사람이 짠 HTML에는 의도가 이름으로 남아있어서 통계적으로 잘 맞는다.

### 여러 페이지를 비교한다

이게 제일 정확하고, 크롤러만 쓸 수 있는 방법이다. 한 페이지만 보면 뭐가 템플릿인지 알 수 없지만, 같은 사이트의 여러 페이지를 받아놓고 겹치는 구조를 지우면 남는 게 본문이다.

```
페이지 A:  [헤더][메뉴][시계][ 본문 A ][사이드바][푸터]
페이지 B:  [헤더][메뉴][시계][ 본문 B ][사이드바][푸터]
                  모든 페이지에 공통인 DOM 위치를 제거
           [ 본문 A ] / [ 본문 B ]
```

시계도 여기서 같이 날아간다. 값은 매번 다르지만 DOM 트리에서 같은 자리에 있으니 템플릿으로 잡힌다. 값을 비교하는 게 아니라 구조상 위치를 비교하는 것이다. 크롤러는 어차피 같은 사이트를 수천 페이지 받으니 이 정보가 공짜로 생긴다.

AI가 하는 일을 통계가 대신하는 셈이다. 본문은 글자가 길고 링크가 적고 이름에 content가 들어간다는 건 의미를 이해한 게 아니라 형태적 특징이라서, AI 이전에도 됐다.

완벽하지는 않다. JS로 본문을 그리는 SPA, 무한 스크롤, 표가 본문인 페이지에서 깨진다. 그래서 중복 감지가 3층 구조인 거고, 2층이 틀려도 3층 유사도 해시가 어느 정도 흡수한다.

# 내 프로젝트에서 같은 자리를 만들었던 경험

항공권 특가를 모으는 개인 프로젝트에서 항공사 프로모션 메일을 파싱해 특가 정보를 뽑는 로직을 만든 적이 있다. 9장의 콘텐츠 파서와 같은 자리다. 책을 읽고 내 코드를 다시 보니 9장 컴포넌트가 거의 그대로 들어있었다.

| 9장 컴포넌트 | 내 코드 |
| --- | --- |
| 콘텐츠 파서 | HTML을 텍스트로 바꾸는 함수 |
| URL 추출기 | 태그를 지울 때 링크만 일부러 보존 |
| URL 필터 | 수신자 추적 파라미터가 붙은 링크는 제외 |
| 이미 방문한 URL인가 | 처리 완료 플래그 |
| 중복 콘텐츠인가 | DB unique 제약으로 같은 특가를 두 번 저장하지 않음 |
| 예의, 처리율 제한 | 한 번 실행에 받아들이는 메일 수 상한 |
| 문제 있는 콘텐츠 | 발신 도메인 허용 목록 + 발신자 인증 확인 |

## 1. 본문 추출을 조잡하게 하고 있었다

정규식 네 줄로 2층을 하고 있었다. style과 script 태그 제거, 링크를 [텍스트](URL) 형태로 보존, 남은 태그 전부 제거, 공백 정규화, 그리고 글자 수 절단이다.

링크를 살린 게 의도적이었다. 태그를 다 지우면 href가 날아가는데 프로모션 페이지 URL을 뽑아야 했기 때문이다. 9장 크롤러가 콘텐츠 파싱과 링크 추출을 동시에 하는 것과 같은 구조다.

단 링크 밀도나 클래스 이름 점수는 안 쓴다. 조잡한 버전이다. 그래도 됐던 이유가 아래 3번이다.

## 2. 싼 필터 먼저, 비싼 판정 나중 - 블룸 필터와 같은 구조였다

내 코드에는 제목에 광고나 특가 같은 신호가 없으면 LLM 호출을 아예 생략하는 사전 필터가 있다. 정규식은 공짜고 LLM 호출은 돈이기 때문이다.

이게 9장과 8장에 나오는 구조와 같다는 걸 책을 읽고 알았다.

| | 싼 1차 필터 | 비싼 2차 판정 |
| --- | --- | --- |
| 9장 이미 방문한 URL인가 | 블룸 필터 | 저장소 조회 |
| 9장 중복 콘텐츠인가 | 정확 해시 | 유사도 해시 |
| 8장 해시 충돌 확인 | 블룸 필터 | DB 조회 |
| 내 메일 파싱 | 제목 정규식 | LLM 호출 |

블룸 필터의 핵심은 확실히 없음 또는 있을지도로만 답한다는 것이다. 없다고 하면 바로 진행하고, 있을지도라고 할 때만 비싼 확인을 한다. 내가 비용 때문에 짜놨던 구조가 책에서 이름을 가진 기법이라는 걸 알게 됐다.

## 3. 왜 책의 휴리스틱 대신 LLM을 썼나 - 규모가 도구를 결정한다

9장이 말하는 HTML 구조 휴리스틱을 안 쓰고 메일 본문을 그대로 LLM에 던졌다. 당시엔 그냥 그게 빨라서 그렇게 했는데, 책을 읽고 왜 그 선택이 가능했는지가 설명됐다.

| | 내 프로젝트 | 책의 크롤러 |
| --- | --- | --- |
| 처리량 | 주 3~4통 (실측) | 매월 10억 페이지 |
| 1건 비용 | 몇 원 | |
| 전체 비용 | 월 몇백 원 | 같은 방식이면 천문학적 |
| 쓸 수 있는 것 | LLM. 개발 시간이 0에 가깝다 | 휴리스틱밖에 없다 |

템플릿마다 정규식을 짜는 개발 비용이 API 비용보다 비쌌기 때문에 LLM이 합리적이었다. 구글 규모면 그 선택지가 아예 없다.

같은 문제인데 규모가 도구를 뒤집는다. 1장의 개략적 규모 추정이 그래서 뭘 쓸지로 돌아오는 지점이었다. 규모 추정을 왜 면접 초반에 하는지가 여기서 납득됐다.

## 5장, 6장과 연계해서 생각해보자

9장은 앞 장에서 배운 도구들이 쓸 자리를 찾는 장이었다.

| 도구 | 어디서 배웠나 | 9장에서 쓰는 곳 |
| --- | --- | --- |
| 안정 해시 | 5장 | 다운로더 서버에 부하 분산 (책의 안정성 절) |
| 블룸 필터 | 6장 | 이미 방문한 URL 판정 |
| 처리율 제한 | 3주차 4장 | 예의. 호스트별 요청 간 지연 |

### 안정 해시가 왜 필요한지가 9장에서 보인다

호스트별 큐 구조에서 어느 큐로 갈지는 호스트 이름의 해시로 정해진다.

```
queueIndex = hash(hostname) % 큐개수
```

같은 호스트는 항상 같은 해시값이라 항상 같은 큐, 항상 같은 워커로 간다. 그래서 두 워커가 같은 호스트를 동시에 때릴 수 없고, 워커가 요청 사이에 지연을 두면 그 호스트에 대한 예의가 저절로 지켜진다. 하나의 구조가 중복 배정과 예의를 동시에 푼다.

문제는 워커를 10대에서 15대로 늘릴 때다. % 10이 % 15가 되면서 매핑이 전부 어긋나고, 진행 중이던 호스트가 다른 워커로 넘어가 예의 보장이 깨진다. 5장에서 서버 추가 시 키 재배치 최소화라는 추상적인 말로 배웠던 게 여기서 구체적인 쓸모를 얻는다. 책은 안정 해시를 다운로더 서버 부하 분산으로 한 줄 적어두는데, 호스트별 큐 구조와 합쳐 생각하면 이 문제로 읽힌다.

### 블룸 필터도 같다

10억 개 URL을 상대로 이미 방문했는지 매번 저장소에 물으면 디스크를 계속 때린다. 블룸 필터는 확실히 없음과 있을지도로만 답하지만 그게 충분하다. 없다고 하면 바로 크롤하고, 있을지도라고 할 때만 저장소를 확인하니 디스크 조회가 극적으로 줄어든다. 거짓 양성이 생기면 크롤할 수 있는 페이지를 건너뛰는 것이고, 10억 페이지 중 일부를 놓치는 건 감수할 수 있는 손실이다. 6장에서 머클 트리 옆에 있던 도구가 왜 있었는지가 여기서 설명된다.

## 스스로 확인해본 것

평범한 FIFO 큐로 BFS를 하면 왜 안 되는지를 생각해봤다. 예의 없는 크롤러가 되고 우선순위가 없다는 두 가지인데, 예의가 깨지는 기계적인 이유가 처음엔 안 보였다.

한 페이지에서 뽑은 링크는 대부분 같은 호스트다. 위키백과 문서를 긁으면 나오는 링크가 거의 다 위키백과 내부다. 그걸 FIFO 큐에 넣고 순서대로 꺼내면 연속으로 같은 서버를 때린다. 의도가 없어도 DoS처럼 된다. 링크의 지역성이 그대로 요청의 집중으로 번역되는 것이다.

그리고 책이 크롤러 함정에 대해서는 자동 감지가 어렵다고 인정한다. 비정상적으로 많은 페이지를 가진 사이트를 기계적으로 가려내기 힘들어서, URL 최대 길이 제한이라는 싼 방법과 수동 제외 목록이라는 사람 손으로 간다. 책에서 드물게 답이 없다고 말하는 지점이었다.
