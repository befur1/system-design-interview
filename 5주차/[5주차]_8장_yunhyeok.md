# URL 단축기 설계 (URL Shortener)


## 1. 개요
- **목표**: 긴 URL을 짧은 단축 URL로 바꾸고, 단축 URL로 요청이 오면 원래 URL로 **리다이렉트**한다.
- **요구사항**: 많은 사람이 단축 URL을 사용하므로
    - 높은 가용성
    - 규모 확장성
    - 장애 감내

## 2. API 엔드포인트
| 엔드포인트 | 역할 |
|---|---|
| **URL 단축** (`POST`) | 클라이언트가 단축할 URL을 인자로 실어 요청하면 단축 URL을 생성해 반환 |
| **URL 리다이렉트** (`GET`) | 단축 URL로 HTTP 요청이 오면 원래 URL로 보내줌 |

## 3. 리다이렉트 방식: 301 vs 302
| | 301 Moved Permanently | 302 Found |
|---|---|---|
| 의미 | 영구 이동 | 임시 이동 |
| 동작 | 첫 요청 후 브라우저가 결과를 **캐싱** → 이후엔 단축 서버를 거치지 않고 바로 원본 URL로 이동 | 매 요청마다 **단축 서버를 거쳐** 원본 URL로 리다이렉트 |
| 장점 | 서버 부하가 적다 | 클릭 수, 유입 경로, 지역, 기기 등 **분석 데이터를 정확히 수집** 가능 |
| 단점 | 클릭 통계가 부정확해진다 | 서버 부하가 크다 |
| 언제? | 부하 감소가 우선일 때 | 트래픽 분석이 중요할 때 |

> 💡 301도 **첫 요청은** 단축 서버를 거칩니다. "서버를 안 거친다"는 건 캐싱 이후의 이야기

## 4. 단축 URL 생성 방법

### ① 해시 후 충돌 해소
- URL을 해시 함수(CRC32, MD5, SHA-1 등)로 해싱한 뒤 **앞 7글자만** 사용
- 앞 7글자만 자르므로 **서로 다른 URL이 겹칠 수 있음(충돌)**
- 해결: 충돌 시 **사전에 정한 문자열을 덧붙여** 다시 해싱 → 충돌이 없을 때까지 반복
- 단점: 충돌 여부를 확인하려고 **DB에 한 번 이상 질의**해야 해서 부담이 큼
    - (보완책: 블룸 필터로 존재 여부를 빠르게 확인)

### ② Base-62 변환
- 62개 문자(`0-9`, `a-z`, `A-Z`)로 수를 표현하는 **진법 변환** (해시 함수가 아님)
- DB에 저장할 때 받은 **고유 ID(정수)**를 Base62 문자열로 바꿔 단축 코드로 사용
    - 예: ID `11157` → `2TX`
- 장점: ID가 고유하므로 **유일성 보장, 충돌 없음**
- 단점: ID가 1씩 증가하면 다음 단축 URL을 **쉽게 예측**할 수 있어 보안상 취약
- 7자리면 62⁷ ≈ 3.5조 개 표현 가능

### 비교
| | 해시 + 충돌 해소 | Base-62 변환 |
|---|---|---|
| URL 길이 | 고정 (7자) | ID 크기에 따라 가변 |
| 고유 ID 생성기 | 불필요 | 필요 |
| 충돌 | 발생 가능 → 해소 필요 | 없음 |
| 다음 URL 예측 | 불가능 | 가능 (ID가 순차적일 때) |

## 5. 상세 설계: 데이터 모델
- 해시 테이블(메모리)에 저장하는 방법 → 메모리는 **유한하고 비싸서** 실제 서비스엔 부적합
- **관계형 DB에 저장**: `<단축 URL, 원래 URL>` 순서쌍을 저장
    - 테이블 예: `id`, `shortURL`, `longURL`
