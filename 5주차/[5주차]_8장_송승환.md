## 8장 요약

### 1. 문제 이해 및 설계 범위 확정

성공적으로 시스템을 설계해 내려면 질문을 통해 모호함을 줄이고 요구사항을 알아내야 함

### 2. 개략적 설계안 제시 및 동의 구하기

8장에서는 API Endpoint, URL redirection, URL 단축 flow를 보려고 함

#### API 엔드포인트

URL 단축키는 기본적으로 두 개의 Endpoint를 필요로 함

- URL 단축용 엔드포인트: 새 단축 URL을 생성하고자 하는 클라이언트는 이 엔드포인트에 단축할 URL을 인자로 실어서 POST 요청을 보내야 함
    
    ```sql
    POST/api/v1/data/shorten
    - 인자: {longUrl: longURLstring}
    - 반환: 단축 URL
    ```
    
- URL 리디렉션용 엔드포인트: 단축 URL에 대해서 HTTP 요청이 오면 원래 URL로 보내주기 위한 용도의 엔드포인트
    
    ```sql
    GET/api/vi/shortUrl
    - 반환: HTTP 리디렉션 목적지가 될 원래 URL
    ```
    

#### URL 리디렉션

브라우저에 단축 URL을 입력 → 단축 URL을 받은 서버는 그 URL을 원래 URL로 바꾸어서 301 or 302 Location 헤더에 넣어 반환함

- 301 (Permanetly Moved): 이 응답은 해당 URL에 대한 HTTP 요청의 처리 책임이 ‘영구적으로’ Location 헤더에 반환된 URL로 이전되었다는 응답
    
    → 영구적으로 이전되었으니, 브라우저는 이 응답을 캐시함
    
    장점: 서버 부하를 줄이는 방식으로 유용함
    
- 302 (Found): 이 응답은 주어진 URL로의 요청이 ‘일시적으로’ Location 헤더가 지정하는 URL에 의해 처리되어야 한다는 응답
    
    장점: 트래픽 분석이 중요할 때는 이 방식이 클릭 발생률이나 발생 위치를 추적하는데 좀 더 유리함
    

#### URL 단축

긴 URL → 해시함수 → www.tinyurl/{hashValue}

- 입력으로 주어지는 긴 URL이 다른 값이면 해시 값도 달라져야 함
- 계산된 해시 값은 원래 입력으로 주어졌던 긴 URL로 복원될 수 있어야 함

### 3. 상세 설계

#### 데이터 모델

KV 저장소에 <단축 URL, 원래 URL>의 순서쌍을  저장하기에는 메모리가 유한한 데다 비싸기 때문임.

더 나은 방법은 <단축 URL, 원래 URL>의 순서쌍을 관계형 데이터베이스에 저장하는 것임

#### 해시 함수

www.tinyurl/{hashValue}에서 hashValue를 계산하기 위해서 **해시 함수**를 사용

hashValue는 [0-9, a-z, A-Z]의 문자들로 구성되고, 이 길이를 정하기 위해서는 62^n ≥ 365billion인 n의 최소값을 찾으면 됨

- 해시 변환: 해시 후 충돌이 일어날 수 있는데 이는 데이터베이스 질의(오버헤드가 큼) 대신에 블룸필터(확률적 자료구조라는데 설명을 봐도 어려움)를 사용하면 성능을 높일 수 있음
    - 해시값 길이가 고정
    - 유일성 보장되는 ID 생성기 필요X
- base-62 변환: 62진법으로 hashValue에서 사용할 수 있는 문자 개수가 62개이다 보니 변환을 통해 다음에 쓰는 단축 URL이 무엇인지 쉽게 알아낼 수 있다는 단점이 존재.
    - ID 값이 커지면 값이 길어짐
    - 유일성 보장 ID 생성기가 필요

#### URL 단축기 상세 설계

1. 입력으로 긴 URL을 받음
2. DB에 해당 URL 있는지 확인
3. URL이 있으면 단축 URL을 유저에게 반환. 없으면 해당 URL에 해당하는 유일한 ID를 생성. 이 ID는 데이터베이스의 기본 키로 사용
4. 62진법 변환을 적용. ID를 단축 URL로 만듬
5. ID, 단축 URL, 원래 URL로 DB 레코드를 만든 후 단축 URL을 유저에게 반환

#### URL 리디렉션 상세 설계

쓰기보다 읽기를 더 자주하는 시스템이라, <단축 URL, 원래 URL>의 쌍을 캐시에 저장하여 성능을 높임

1. 사용자가 단축 URL을 클릭
2. LB가 클릭으로 요청을 웹 서버에 전달
3. 단축 URL이 캐시에 있으면 원래 URL을 바로 꺼내서 사용자에게 전달
4. 캐시에 없으면 DB에서 꺼냄
5. DB에서 꺼낸 URL을 캐시에 넣은 후 사용자에게 반환

### 해시가 꼭 짧게 만드는 건 아니었음

8장에서 해시는 **긴 URL 을 7글자로 줄이는 도구**로 나옴. 그런데 데모데이 프로젝트(HAMA)에서 내가 맡은 인증·결제 코드에도 해시가 있는데, **짧게 만드는 게 목적인 건 하나도 없었음**

| 자리 | 입력 → 출력 | 목적 | 충돌이 나면 |
| --- | --- | --- | --- |
| 8장 단축 URL | 긴 URL → 7글자 | **압축** | 남의 링크로 감 → **해소 전략 필요** |
| `TokenHasher` (비번 재설정) | 토큰 → SHA-256 전체 | **단방향 보관** | 2²⁵⁶이라 고려 안 함 |
| `PaddleSignatureVerifier` | 본문 → HMAC-SHA256 | **위조 방지** | 위조 가능 → 치명적 |

차이는 **출력을 잘라 쓰느냐**임. 8장만 7글자로 자르고 나머지는 256비트를 통째로 써서, **8장만 충돌 해소가 필요**함

그리고 8장이 7글자를 정한 근거가 `62ⁿ ≥ 3,650억`인데, 이건 **용량 계산이지 보안 계산이 아님**

#### 길이를 반대로 고른 사례

|  | tinyurl 단축 URL | HAMA 재설정 링크 |
| --- | --- | --- |
| 길이 | 7글자 | **43글자** |
| 키 공간 | 62⁷ ≈ 3.5조 | 2²⁵⁶ |
| 전수조사 | 이론상 가능 | 불가능 |
| 고른 기준 | 짧은 게 **상품** | **추측 불가능성** |

"짧게 하려면 키 공간이 작아야 하고, 키 공간이 작으면 전수조사가 가능해진다"는 같은 저울에서 **나는 반대쪽을 고른 셈**. 재설정 링크는 한 번 누르고 버리는 거라 길어도 상관없으니까

정리하면 **8장의 7글자는 기술적 최적해가 아니라 제품 제약임**. URL 자체가 상품인 서비스라 길이를 먼저 정해놓고, 거기에 맞춰 충돌을 감수한 것
