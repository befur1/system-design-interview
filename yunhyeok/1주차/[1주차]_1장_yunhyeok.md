## 수백만 사용자를 지원하는 시스템 설계

시스템이 성장하는 흐름을 따라가며, 각 단계에서 왜 그 컴포넌트가 필요해지는지 정리한다.

## 1.단일 서버 (Single Server)

모든 컴포넌트(독립적인 기능을 수행하며 재사용 가능한 단위)가 단 한 대의 서버에서 실행되는 가장 단순한 구조. 웹, 앱, 데이터베이스, 캐시가 전부 서버 한 대 안에서 돌아간다.

사용자 요청 처리 과정
사용자가 도메인 이름으로 웹사이트에 접속한다.
도메인 이름이 IP 주소(컴퓨터가 이해하는 주소)로 변환된다.
DNS 조회 결과로 IP 주소가 반환되고, 해당 IP로 HTTP 요청이 전달된다.
요청을 받은 웹 서버가 HTML 페이지 또는 JSON 형태의 응답을 반환한다.


## 2. 데이터베이스 분리

사용자가 늘어나면 서버 한 대로는 부족해져 역할을 나눈다.

웹 계층: 웹/모바일 트래픽을 처리하는 서버
데이터 계층: 데이터베이스 전용 서버
어떤 데이터베이스를 쓸 것인가
구분	특징
RDBMS (관계형)	SQL을 통한 JOIN 가능
NoSQL (비관계형)	JOIN 불가능. 다음 상황에 적합: 매우 낮은 응답 지연시간이 필요할 때 / 데이터가 비정형이라 관계형으로 다루기 어려울 때 / 직렬화·역직렬화만 하면 되는 데이터일 때 / 아주 많은 양의 데이터를 저장해야 할 때
수직적 확장 vs 수평적 확장

수직적 확장 (Scale Up) — CPU, RAM 추가

단점 ① 무제한으로 늘릴 수 없다
단점 ② 장애 자동복구·다중화 방안이 없어, 문제가 생기면 웹사이트 전체가 멈춘다

수평적 확장 (Scale Out) — 서버 자체를 추가, 대규모 애플리케이션에 적합

다만 서버를 늘려도 특정 서버가 다운되거나 트래픽이 몰려 느려지는 문제는 남는다. 이를 해결하는 것이 로드 밸런서다.

## 3. 로드 밸런서

트래픽을 여러 서버에 나누어주는 장치.

사용자는 로드밸런서의 공개 IP로 접속하고, 실제 서버들은 사설 IP로 숨겨져 보안성이 높아진다.
부하를 분산해 장애 자동복구 문제를 해소하고 웹 계층의 가용성을 높인다.
## 4. 데이터베이스 다중화 (Replication)

다중화 시 데이터베이스는 **주(Master)**와 **부(Slave)**로 나뉜다.

주 데이터베이스: 쓰기 연산 담당
부 데이터베이스: 주의 복사본을 전달받아 읽기 연산만 담당 (읽기 비중이 훨씬 크므로 부의 개수가 더 많다)
장점
성능: 쓰기/읽기를 분산해 병렬 처리 → 처리 가능한 쿼리 수 증가
안전성: 서버 일부가 훼손되어도 데이터 보존
가용성: 데이터를 여러 지역에 복제해두어 일부 장애에도 서비스 지속
장애 시나리오
부 서버 다운 (부가 1대뿐일 때) → 읽기 연산이 한시적으로 모두 주 데이터베이스로 이동
주 서버 다운 → 부 서버(1대)가 새로운 주로 승격되어 대체
지금까지의 설계 정리
사용자는 DNS로부터 로드밸런서의 공개 IP를 받는다.
그 IP로 로드밸런서에 접속한다.
HTTP 요청이 여러 서버 중 하나로 전달된다.
웹 서버는 부 데이터베이스에서 데이터를 읽는다.
웹 서버는 데이터 변경 연산(추가·삭제·갱신)을 주 데이터베이스에서 수행한다.

## 5. 캐시와 CDN — 응답 속도 개선

웹 계층(서버 분산)과 데이터 계층(다중화)의 분산을 마쳤다면, 이제는 응답 시간 자체를 개선할 차례다. 캐시를 붙이고 정적 콘텐츠를 CDN으로 옮기면 된다.

용어	의미
캐시	자주 쓰는 데이터를 빠른 임시 저장소에 미리 저장해 요청 시간을 줄이는 것
정적 콘텐츠	서버에 미리 저장된 파일을 그대로 전달하는 것
CDN	분산된 서버 네트워크를 통해 콘텐츠를 빠르고 안전하게 전달하는 것
캐시 계층

페이지를 새로고침할 때마다 데이터베이스를 호출하면 성능이 저하된다. 캐시 계층은 데이터베이스보다 훨씬 빠른 임시 보관소이며, 독립적으로 규모를 확장할 수도 있다.

## 캐시 우선 읽기 전략

캐시에 데이터가 있으면 → 캐시에서 바로 클라이언트에 반환
없으면 → 데이터베이스에서 조회해 반환

캐시 사용 시 유의점

갱신은 드물지만 참조가 빈번한 데이터에 적합한지 고려한다.
어떤 데이터를 캐시할지 고민한다 — 캐시는 휘발성(서버 재시작 시 초기화)이므로 중요 데이터는 지속적 저장소에도 보관한다.
만료 기한을 어떻게 설정할지 정한다.
원본 데이터와 캐시 간 일관성을 어떻게 유지할지 정한다.
장애 대응 — 캐시 서버가 한 대뿐이면 **단일 장애 지점(SPOF)**이 될 수 있다.
캐시 메모리 크기를 얼마로 할지 정한다.
데이터 방출(eviction) 정책 — 캐시가 꽉 찼을 때 무엇을 내보낼지 정한다.
LRU: 가장 오래전에 사용된 데이터부터 방출
LFU: 사용 빈도가 가장 낮은 데이터부터 방출
FIFO: 가장 먼저 들어온 데이터부터 방출
CDN (콘텐츠 전송 네트워크)

이미지, 비디오, CSS, JavaScript 등을 캐시하며, 사용자와 가장 가까운 CDN 서버가 정적 콘텐츠를 제공한다 (멀수록 로딩이 느려진다).

동작 과정

사용자가 이미지 URL로 image.png에 접근한다.
CDN 서버 캐시에 없으면 → 원본 서버(웹 서버 또는 S3 같은 온라인 저장소)에 요청해 파일을 가져온다.
원본 서버가 파일을 반환하며, HTTP 헤더에 TTL(캐시 유지 기간)을 함께 반환한다.
CDN 서버가 파일을 캐시하고 사용자에게 반환한다.
이후 다른 사용자의 동일 이미지 요청은, 만료 전이라면 캐시로 바로 처리한다.

고려 사항

비용
적절한 만료 기한
CDN 장애 대응 방안
콘텐츠 무효화: 만료되지 않은 콘텐츠도 CDN에서 제거 가능 — 파일의 다른 버전을 서비스하려면 오브젝트 버저닝(클라우드 스토리지의 모든 파일 버전을 안전하게 보관·관리하는 기능)을 활용한다.


## 6.무상태 웹 계층 (Stateless)

웹 서버가 사용자의 로그인·세션 정보를 직접 갖지 않고, 외부 공유 저장소에 맡기는 아키텍처.

서버가 상태를 가지고 있다면?

서버 1에는 사용자 A 정보, 서버 2에는 사용자 B 정보가 저장되어 있다고 하면, A는 반드시 서버 1로만 요청해야 한다.
로드밸런서의 "고정 세션(sticky session)" 기능으로 해결할 수는 있지만, 로드밸런서에 큰 부하를 준다.

→ 무상태 웹 계층을 설계하면 어떤 사용자든 어느 서버로 요청해도 정상적으로 처리된다.

## 7. 데이터 센터 (다중 리전)

사용자는 가장 가까운 데이터 센터로 안내되는데, 이를 지리적 라우팅이라 한다. 데이터 센터를 하나만 두면 심각한 장애 시 전체 서비스가 멈추므로, 여러 곳에 두어 장애 발생 시 트래픽을 정상 데이터 센터로 우회시켜야 한다.

다중 데이터 센터 설계의 기술적 난제
트래픽 우회: 올바른 데이터 센터로 트래픽을 보내야 한다 (GeoDNS로 사용자와 가장 가까운 데이터 센터로 라우팅).
데이터 동기화: 데이터 센터마다 별도 데이터베이스를 쓰면, 우회해도 필요한 데이터가 없을 수 있다.
테스트와 배포: 자동화된 배포 도구가 모든 데이터 센터에 동일한 서비스를 설치하도록 보장해야 한다.


## 8. 메시지 큐

데이터를 비동기식으로 교환하는 임시 저장소. 큐에 보관된 메시지는 소비자가 꺼낼 때까지 안전하게 보관되어 메시지 무손실을 보장한다.

비동기식 통신: 어떤 작업이 끝날 때까지 기다리지 않고 다음 작업을 수행하는 방식. 예를 들어 오래 걸리는 이미지 보정 작업은 메시지 큐에 넣어 비동기로 처리한다.


## 9. 로그, 메트릭, 자동화
   항목	내용
   로그	에러 로그 모니터링이 중요하다
   메트릭	시스템 현재 상태를 파악하는 지표 — 호스트 단위(CPU, 메모리) / 종합(DB·캐시 계층 성능) / 핵심 비즈니스(사용자, 수익, 재방문)
   자동화(CI)	개발자가 코드 변경 사항을 공유 리포지터리에 자주 병합하고, 자동으로 빌드·테스트를 진행하는 개발 환경


## 10. 데이터베이스의 수평적 확장 — 샤딩 (Sharding)

데이터베이스의 수평적 확장을 샤딩이라 한다. 핵심은 샤딩 키(샤딩 파티션 키)를 정하는 것 — 데이터가 어떻게 분산될지 결정하는 하나 이상의 컬럼(예: user_id).

샤딩 도입 시 생기는 문제
데이터 재샤딩이 필요해지는 경우
데이터가 너무 많아져 하나의 샤드로 감당이 안 될 때
샤드 간 데이터 분포가 불균등해 특정 샤드의 공간이 먼저 소진될 때 (샤드 소진) → 안정 해시(Consistent Hashing) 기법으로 해결
유명인사 문제(Celebrity Problem): 특정 샤드에 질의가 몰려 서버에 과부하가 걸리는 문제
조인과 비정규화: 여러 샤드에 걸친 데이터는 조인하기 어렵다 → 데이터베이스를 비정규화하여 하나의 테이블에서 질의가 끝나도록 설계한다.
