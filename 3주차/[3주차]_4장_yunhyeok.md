# 처리율 제한 장치 (Rate Limiter)


### 생각해보자

- 처리율 제한 규칙을 디스크에 보관하는 이유는 알겠음. 중요한 정보이고 이게 REDIS 같은 인메모리 저장하는 것이고, 휘발성이니까
- 근데 작업 프로세스에서 수시로 규칙을 디스크에서 읽어 캐시에 저장한다?
- 비효율적이지 않을까? 그럼 메모리 낭비일텐데 읽는 방식을 정해야하지 않을까? 기준을 어떻게 설정할까?

### 분산 환경 고도화 시 추가 전략(생각해보기)

- Redis 자원 고갈 대책 (TTL 설정)
    - 정렬집합에 데이터가 계속 쌓이면 Redis 메모리가 버티지 못함

- 로컬 캐시 혼합 (Redis 부하 완화)
    - 모든 요청마다 Redis에 접근하면 Redis 자체가 병목이 될 수 있음


## 1. 처리율 제한 장치란?

- 클라이언트 또는 서비스가 보내는 트래픽의 처리율을 제어하기 위한 장치
- 예) HTTP에서는 특정 기간 내에 전송되는 클라이언트의 요청 횟수를 제한
- 예) API 요청 횟수가 임계치를 넘으면 추가로 도달하는 호출은 처리 중단 (HTTP `429 Too Many Requests`)

### API에 두면 좋은 점

1. DoS 공격에 의한 자원 고갈 방지
2. 비용 절감
3. 서버 과부하 방지

---

## 2. 처리율 제한 장치는 어디에 둘까?

| 위치 | 특징 |
| --- | --- |
| 클라이언트 측 | 요청 위변조가 쉽고, 모든 클라이언트 구현을 통제하기 어려워 부적합 |
| API 서버 측 | 서비스 코드 안에 직접 구현 |
| 미들웨어 (게이트웨이) | 서버 앞단에서 요청을 걸러냄 → MSA에서 가장 널리 채택 |

### 왜 API 게이트웨이에 두는 것이 좋은가?

> 마이크로 서비스에 기반하고 인증, IP 허용목록 관리 등을 처리하는 API 게이트웨이가 있다면 처리율 제한도 게이트웨이에 포함하는 것이 좋다.
> 
> 마이크로서비스: 거대한 하나의 프로그램이 각 기능별로 쪼개진 설계 방식.
> 이미 API 게이트웨이가 있다 == 이미 JWT 토큰 인증으로 검사 하고있다는 뜻이자, 어디서 온건지 알수있다.
> 처리율 제한 규칙만 넣으면 날로 먹을 수 있다는 얘기임.(사용자 식별 단계를 건너뛰니까)
> 숟가락 얹기.

1. 자원 절약과 서버 보호 (가장 결정적)
    - 디도스나 트래픽 폭주 시 게이트웨이 단계에서 즉시 `429`로 차단
    - 내부 서비스에 두면 쓰레기 트래픽도 내부 네트워크를 타고 서버까지 도달해야 함 → CPU/메모리가 요청을 읽고 거절해야 하므로 비효율적이고 안전하지 못함

2. 이미 검증된 데이터 활용 (중복 연산 제거)
    - 게이트웨이는 인증(User ID), IP 허용목록 검사(IP)로 이미 "누가 보냈는지"를 파악한 상태
    - 처리율 제한은 '누가(IP 또는 User ID)' 보냈는지가 기준 → 식별 정보를 그대로 재활용

3. 단일 진입점(Single Point of Entry) 활용
    - 모든 요청이 게이트웨이를 거쳐 회원/주문/결제 등으로 라우팅됨
    - 한 번의 구현으로 모든 서비스 트래픽을 중앙 집중식으로 관리, 각 팀이 개별 구현·배포할 필요 없음

4. 아키텍처 단순화 (관심사 분리)
    - 마이크로서비스는 순수 비즈니스 로직에만 집중( 훨씬 가벼워짐 )
    - 인증, IP 필터링, 처리율 제한은 인프라/보안 공통 관심사 → 게이트웨이가 담당


### 애플리케이션 내부에 둘 때의 설계(찾아봄)

```
[사용자 요청] ──> [인터셉터 / 미들웨어] ──(허용)──> [비즈니스 로직 (Controller)]
                        │
                  (토큰 확인 및 차단)
                        ▼
               [메모리 / Redis]
```

- 인터셉터/미들웨어: 헤더에서 `IP 주소`나 `API 키(JWT)`를 추출해 식별자로 사용
- 저장소: 식별자별로 남은 토큰 수와 마지막 업데이트 시간을 저장
    - 단일 서버: `ConcurrentHashMap`, 라이브러리(Java `Bucket4j`, Node.js `rate-limiter-flexible`) 등 인메모리
    - 여러 대 서버: 앱 코드가 Redis에 접근해 토큰 수를 확인/갱신

## 3. 처리율 제한 알고리즘

### ① 토큰 버킷 (Token Bucket)

- 가장 널리 쓰이는 알고리즘
- 파라미터 2개: 버킷 크기, 토큰 공급률(초당 몇 개 재생성?)
- 요청이 오면 토큰 1개를 소모, 토큰이 없으면 요청 거부
- 장점: 구현이 쉽고 메모리 효율적, 짧은 시간에 집중되는 트래픽(burst)도 처리 가능
- 단점: 두 파라미터를 적절히 조절하기 어렵다

### ② 누출 버킷 (Leaky Bucket)

- FIFO 큐로 구현, 큐가 가득 차면 새 요청은 버림, 일정 속도로 큐에서 꺼내 처리
- 장점: 메모리 효율적, 처리율이 안정적
- 단점: 단시간에 트래픽이 몰리면 큐에 오래된 요청이 쌓이고, 최신 요청이 버려질 수 있음. 파라미터 튜닝도 어렵다

### ③ 고정 윈도 카운터 (Fixed Window Counter) : 집중 정리

동작 방식

1. 타임라인을 고정된 간격의 윈도로 나누고, 각 윈도에 카운터를 붙인다
2. 요청이 접수될 때마다 카운터를 1씩 증가
3. 카운터가 임계치에 도달하면 새 요청은 버려진다 (다음 윈도가 시작되면 카운터 초기화)

문제점: 윈도 경계 부근의 트래픽 집중

- 예) 윈도 1분, 임계치 10이라고 가정 (윈도: `0:00~1:00`, `1:00~2:00`)
- `0:50`에 7개, `1:10`에 6개 요청 → 각 윈도에서는 임계치(10) 이하라 모두 통과
- 하지만 실제로는 20초 사이에 13개가 처리됨 → 의도한 한도(1분 10개)를 초과

장단점

- 장점: 메모리 효율적, 이해하기 쉽고 구현이 간단
- 단점: 윈도 경계에서 일시적으로 한도를 초과하는 요청이 통과될 수 있음

### ④ 이동 윈도 로그 (Sliding Window Log)

- 금융결제, 티켓팅처럼 정확성이 중요한 곳에서 사용 
- 요청의 타임스탬프를 추적하여 Redis 정렬집합(Sorted Set) 같은 캐시에 보관

> Redis 정렬집합: key 1개에 여러 MEMBER, 각 MEMBER마다 SCORE를 저장.
    1. SCORE 기준 오름차순 자동 정렬
    2. SET처럼 중복 불가

동작 방식

1. 새 요청이 오면 타임스탬프를 로그에 기록
2. 만료된 타임스탬프(윈도 범위를 벗어난 것)는 제거
3. 로그의 크기가 허용치보다 같거나 작으면 요청을 시스템에 전달
4. 크면 처리 거부 (단, 거부된 요청의 타임스탬프도 로그에는 보관)

장단점

- 장점: 완벽한 정확성(오차 0%), 60초간 로그를 전수조사하므로 1초 단위 검사도 가능
  - 은행 입장에서 공격이 들어오거나 비정상적인 결제건에 대해서 수사가 가능해짐.
- 단점: 메모리 부하 (거부된 요청의 타임스탬프도 보관), 연산 비용 큼
  - 그래서 은행은 메모리 사용량을 기부하는 대신, 정확성을 채택한 것

### ⑤ 이동 윈도 카운터 (Sliding Window Counter)

- 고정 윈도 카운터 + 이동 윈도 로그의 하이브리드, 추정치를 사용

```
현재 윈도 요청 수 + (직전 윈도 요청 수 × 이동 윈도와 직전 윈도가 겹치는 비율)
```

- 장점: 트래픽이 몰려도 사용 가능, 메모리 효율 좋음 (로그는 타임스탬프가 들어가지만 여기는 숫자만 저장)
- 단점: 추정치이므로 약간의 오차가 있는 트레이드오프
  - 단점과 관련해서 오차는 1.47% 정도의 오차가 있고, 실제로 가장 최악의 상황을 가정하면 25%까지도 나온다고 하지만, 현실성이 없기에 1% 내외
  라고 한다.

저장되는 데이터 (Key-Value)

```
user:123:current_minute ──> 45   (현재 1분간 요청 수)
user:123:last_minute    ──> 80   (직전 1분간 요청 수)

```

### 알고리즘 비교

| 알고리즘 | 정확도 | 메모리 | Burst 허용 | 핵심 특징 |
| --- | --- | --- | --- | --- |
| 토큰 버킷 | 중 | 좋음 | O | 버킷 크기·공급률 튜닝이 어려움 |
| 누출 버킷 | 중 | 좋음 | X (큐에 쌓임) | FIFO 큐, 안정적 처리율 |
| 고정 윈도 카운터 | 낮음 | 좋음 | 경계에서 초과 가능 | 단순하지만 경계 문제 |
| 이동 윈도 로그 | 매우 높음 | 나쁨 | X | 금융결제/티켓팅, 연산·메모리 부담 |
| 이동 윈도 카운터 | 높음 (추정) | 좋음 | 제한적 | 숫자 2개만 저장 |

## 4. 분산 환경에서의 처리율 제한 장치

### 문제 상황: 서버가 각자 기억할 때 (동기화 문제)

한도가 1분에 최대 10개인 사용자가 1초 만에 요청 15개를 보낸 경우

1. 로드밸런서가 서버 1, 2, 3에 각각 5개씩 분산
2. 각 서버는 "나한테는 5개뿐이네? 통과!"라고 판단
3. 결과: 사용자는 한도(10개)를 넘겨 15개를 사용 → 서버끼리 정보를 몰라 차단하지 못하는 구멍 발생

### 해결책: 중앙 집중형 저장소 (Redis)

```
[사용자 요청 15개] ──> [로드밸런서] ── 분산 ──> [서버 1, 2, 3]
                                                      │
                                           (다 같이 Redis 하나만 바라봄)
                                                      ▼
                                              [중앙 저장소: Redis]
                                        "이 사용자 지금 총 몇 번 요청했지?"
```

- 어느 서버가 요청을 받든 Redis의 카운터를 `INCR` → 전체 요청 수가 정확하게 합산됨

### 2대 난제

1. 경쟁 조건 (Race Condition)
- 두 서버가 동시에 카운터를 읽고(`GET`) 1을 더해 저장(`SET`)하면, 원래 +2가 되어야 하는데 +1만 반영되어 제한이 뚫림
1. 동기화 지연 (Synchronization)
- 서버들이 로컬 메모리에만 카운트를 기록하면 서로의 상태를 몰라 전체 한도를 정확히 제어할 수 없음

### 표준 해결책: Redis + Lua 스크립트

- Redis는 기본적으로 싱글 스레드로 명령을 처리 → 줄 세워서 하나씩 처리하므로 원자성 확보
- Lua 스크립트로 여러 명령(읽기, 지우기, 쓰기)을 하나로 묶어 한 번에 원자적으로 실행 (All-or-Nothing 처럼 동작)
