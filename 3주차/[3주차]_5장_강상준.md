수평적 규모 확장성 달성을 위해서는 요청/데이터를 서버에 균등하게 나누는 것이 중요.
안정 해시는 이 목표를 위해 보편적으로 사용하는 기술.

# 해시 키 재배치(rehash) 문제
N개의 캐시 서버가 있을 때 부하를 균등하게 나누는 보편적 방법은 아래의 해시 함수를 사용하는 것이다.
serverIndex = hash(key) % N

서버 풀의 크기가 고정되어 있을 때, 데이터 분포가 균등할 때는 잘 동작한다.
서버가 증설되거나 감설될 때 대부분의 키가 재분배되므로 대규모 캐시 미스가 발생하게 된다.

## 안정 해시
안정 해시를 사용하면 평균적으로 k(키의 개수)/n(서버의 개수)개의 키만 재배치 할 수 있다. -> 서버 한 대 몫의 키
재분배되는 키의 수를 최소화하는 것이 안정 해시의 주된 목표.

1. 해시 함수에 따라 해시 공간의 크기가 정해짐
2. 해시 공간을 시계처럼 링 형태로 만들면 안정 해시 링이 만들어짐
3. 각 서버를 해시 링 위에 대응함(해시 함수 사용) - 해시 서버
4. 데이터의 키를 해시 함수로 해시한 뒤 해시 링 위에서 오른쪽으로 이동하여 처음 만나는 서버에 할당

## 기본 구현법의 두 가지 문제
안정 해시 알고리즘의 기본 절차는 다음과 같다
- 서버와 키를 균등 분포 해시 함수를 사용해 해시 링에 배치한다
- 키의 위치에서 링을 시계 방향으로 탐색하다 만나는 최초의 서버가 키가 저장될 서버이다.

다음 **두 가지 문제**를 가진다
1. 파티션의 크기를 균등하게 유지하는 게 불가능하다.
2. 키의 균등 분포를 달성하기가 어렵다.
    - 좋은 키 해시 함수를 사용해도 각 서버의 크기를 균등하게 유지하는 게 불가능하므로 키가 각 서버에 균등하게 분포되게 하기가 어렵다.
    - 1번에 따른 필연적인 문제

위 두 가지 문제를 해결하기 위해 제안된 기법이 가상노드이다.

## 가상 노드
가상노드는 실제 노드 또는 서버를 가르키는 노드다.
링 위에 하나의 서버를 가리키는 여러 개의 가상 노드를 배치해서 파티션을 촘촘히 나눠서 편차를 해결하는 느낌인듯?
근데 가상 노드를 배치하면 데이터가 저장될 해시 공간을 잡아먹는 거라 tradeOff를 잘 생각해야한다.

## 재배치할 키 결정
서버가 증/감설되면 어느 범위의 키들이 재배치 되어야 할까?

추가되거나 감설된 서버의 반시계 방향에 있는 서버 사이에 있는 키들이 재배치 되어야한다.


---

안정 해시를 사용하면
- 서버가 추가되거나 삭제될 때 재배치되는 키의 수가 최소화된다.
- 데이터가 균등하게 분포되므로 수평적 규모 확장을 달성하기 쉽다.
- 핫스팟 키 문제를 줄인다.

Q. 이 안정해시가 좋은 건 알겠는데 어디서 계산하고 적용되는 걸까요?
- 클라이언트 라이브러리(SDK) 내부 (가장 흔함)
    - Spring Boot 애플리케이션 코드 안에 깔린 캐시 드라이버 라이브러리가 알아서 안정 해시를 돌려줌
- 중간 프록시/로드밸런서
    - 앱과 캐시 사이에 전용 프록시 서버를 두는 경우, 해당 프록시가 안정 해시를 담당함
- 분산 DB 노드 내부(클러스터 자체)
    - 클러스터 내의 아무 서버에나 요청을 던지면 자체적으로 가지고있는 해시 링 정보(라우팅 테이블)를 보고 적절한 노드로 전달해줌

Q. 우리가 코드 레벨에서 안정 해시를 직접 설계할 일이 있을까요?
- 거의 없지만 실시간 웹소켓/채팅 서버 분산 라우팅의 경우가 가장 흔하게 실제 구현을 해야하는 경우임
    - 채팅 서버는 단순 DB가 아니라 비즈니스 서버이기 때문에 자체 개발한 게이트웨이를 사용해 세밀한 튜닝이 필요한 경우가 있음.
    - 이 경우도 오픈소스 라이브러리를 통으로 사용하느냐 튜닝하느냐 차이지 직접 처음부터 개발할 필요는 없음.
- 근데 그럼 왜 알아야되나요?
    - 원리를 알아야 특정 서버 1대가 메모리가 꽉차는 경우/CPU가 튀는 경우 대응 할 수 있음.
    - 서버 증설/장애 시 시스템 동작을 예측할 수 있음
