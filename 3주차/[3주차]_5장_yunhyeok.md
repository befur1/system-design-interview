# 안정 해시 (Consistent Hashing)

## 1. 왜 필요한가

수평적 규모 확장(서버 수를 늘리는 것)을 달성하려면 아래 두 가지를 서버에 균등하게 나눠야 한다.

- 요청
- 데이터

안정 해시는 이 목표, 즉 서버에 요청과 데이터를 균등하게 나누기 위해 사용하는 기술이다.

## 2. 기본 개념

### 해시 키
- 자료구조나 데이터베이스에서 데이터를 저장하고 찾을 때 부여하는 고유 식별자
- 예: 사용자 ID, 이메일 주소
- 해시 테이블이나 NoSQL 데이터베이스에서 말하는 그 해시 키이다.

### 해시 테이블은 데이터베이스인가?

> 해시 테이블은 "Key를 넣으면 Value를 초고속으로 찾아준다"는 수학적 알고리즘(자료구조)이다.
> 즉 데이터베이스 그 자체가 아니라, 데이터를 저장하고 관리하는 원리이자 자료구조이다.

- 캐시 서버 (Redis, Memcached 등): 메모리(RAM) 위에 해시 테이블 원리로 데이터를 올려둔 시스템. 속도가 극도로 빠르다.
- NoSQL 데이터베이스 (DynamoDB, Cassandra 등): 디스크(HDD/SSD)나 메모리에 해시 테이블 원리로 데이터를 영구 저장하는 시스템

## 3. 해시 키 재배치 문제

### 문제 상황
- 대규모 분산 시스템(여러 개의 캐시 서버, 데이터베이스)에 데이터를 분산 저장할 때, 서버가 추가되거나 삭제되면 기존 데이터의 위치가 바뀌어 대규모 캐시 미스가 발생한다.

### 대규모 캐시 미스
- 사용자가 데이터를 요청했을 때 서버가 데이터를 찾지 못해, 모든 요청이 원본 데이터베이스로 몰리는 현상
- 캐시(메모리)로 빠르게 가져오려 했지만 결국 DB(디스크)에 접근하게 된다.
- 결과: 시스템 마비, 데이터 대이동 부하
- 바뀐 서버 위치에 맞춰 엄청난 양의 데이터를 다른 서버로 옮겨야 하므로 네트워크와 서버에 부하가 걸린다.

### 서버에 부하를 균등하게 나누는 보편적인 방법 (모듈러 해싱)

서버 인덱스 = 해시 키 % N

- 서버 인덱스: 여러 대의 서버를 구분하기 위해 매기는 방 번호(일련번호)
- N: 서버 풀의 크기 (서버 개수)
- 서버 인덱스에 따라 요청을 보낼 서버가 결정된다.
- 예: 서버가 4대면 인덱스는 0, 1, 2, 3 → 인덱스가 0이면 클라이언트는 캐시에 보관된 데이터를 가져오기 위해 서버 1에 접근한다.

### 이 방식의 한계
- 서버가 5대로 늘거나 3대로 줄면 N이 바뀌어 계산 결과가 달라진다.
- 엉뚱한 서버로 접근해 데이터를 가져오지 못하고, 디스크 접근으로 원본 DB까지 가게 된다.

## 4. 안정 해시 설계

### 구조
- 서버와 데이터를 원형의 링 위에 배치하는 방식
- 해시 서버를 링 위에 배치하고, 해시 키도 링 위에 배치한다.
- 시계 방향으로 가장 먼저 만나는 서버에 데이터를 저장한다.
- 데이터 키 해싱: user_12 같은 원래의 고유값(키)을 해시 함수에 넣어 숫자나 문자열로 바꾸는 과정

### 장점
- 서버가 추가·삭제되어도 전체 데이터가 이동하지 않는다.
- 추가·삭제된 서버 주변의 일부 데이터(k/n)만 재배치된다. (k: 키의 개수, n: 서버의 개수)
- 대규모 캐시 미스를 막고, 시스템을 안정적으로 수평 확장(Scale-out)할 수 있다.

## 5. 안정 해시의 문제점: 파티션 크기 불균등

### 용어 정리
- 분산 시스템에서의 파티션 크기: 하나의 서버(분산 단위)가 감당하는 데이터의 용량 또는 범위
- 안정 해시에서의 파티션 크기: 특정 서버가 책임지기로 한 데이터의 범위

### 예시
- A: 0~999 / B: 1000~1999 / C: 2000~2999 / D: 3000~3999
- 서버 B가 사라지면, 시계 방향으로 다음 서버인 C가 1000~2999를 책임지게 된다.
- 결과: C의 파티션 크기가 다른 서버에 비해 두 배로 커진다.
- 즉 파티션의 크기를 균등하게 유지하기 어렵다.

## 6. 해결책: 가상 노드 (Virtual Node)

### 개념
- 실제 서버를 가리키는 노드로, 하나의 서버가 링 위에 여러 개의 가상 노드를 가질 수 있다.
- 예: 서버 A를 A_1, A_2, A_3 처럼 여러 개로 나누어 배치한다.
- A_3에 데이터가 저장되면 실제로는 서버 A에 저장되는 구조이다.
- 가상 노드의 개수를 늘리면 키의 분포가 균등해진다.

### 가상 노드 개수와 표준 편차
- 가상 노드를 100~200개 사용하면 표준 편차가 평균 대비 약 5%~10% 수준이다.
- 개수를 늘릴수록 데이터가 특정 서버로 쏠리는 현상이 줄어 파티션 크기가 매우 균등해진다.

## 7. 가상 노드의 단점 (Trade-off)

가상 노드가 많아지면 데이터를 저장할 공간이 더 많이 필요해진다.

1. 메모리 낭비
    - 각 서버와 클라이언트가 기억해야 하는 해시 링의 크기가 너무 커진다.
    - 이 정보를 메모리에 들고 있어야 하므로 부담이 크다.
2. 서버를 찾는 속도 저하
    - 가상 노드가 너무 많으면 탐색 기법(이진 탐색 등)을 써야 한다.
    - 탐색 비용이 늘어 API 응답 시간이 증가할 수 있다.
3. 데이터 동기화 부하
    - 서버가 꺼졌다가 새로 켜질 때, 변경된 수십만 개의 가상 노드 위치 정보를 모든 클라이언트 서버에 전송하고 업데이트(동기화)해야 한다.

## 한 줄 요약

> 해시키 재배치 문제에서 서버 수가 바뀌면 대부분의 키가 이동한다. 
> 안정 해시는 링 구조로 일부(k/n)만 이동시키고, 가상 노드로 쏠림을 줄인다. 
> 단, 가상 노드가 많을수록 메모리·탐색·동기화 비용이 늘어난다.
