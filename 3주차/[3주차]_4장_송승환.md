## 4장 요약

`처리율 제한 장치(rate limiter)`는 클라이언트 또는 서비스가 보내는 트래픽의 처리율을 제어하기 위한 장치

Rate Limiter 사용이유

- DoS(Denial of Service) 공격에 의한 자원 고간을 방지

→ 대형 기업들의 API는 어떤 형태로든 처리율 제한 장치를 가지고 있음

- 비용 절감에 도움이 됨

→ 추가 요청에 대해 제한하면 서버를 많이 두지 않아도 되고, 우선 순위가 높은 API에 더 많은 자원을 할당할 수 있

- 서버 과부하를 막음

→ Bot에서나 잘못된 이용 패턴으로 오는 트래픽을 걸러내는데 활용

### 1단계 문제 이해 및 설계 범위 확정

처리율 제한 장치 구현은 여러 알고리즘을 사용할 수 있는데, 이 선택은 면접관과 소통하면서 어떤 제한 장치를 구현해야 하는지 분명히 할 수 있다

### 2단계 개략적 설계안 제시 및 동의 구하기

1. 처리율 제한 장치 위치 설정
- 클라이언트 측: 클라이언트 요청이 쉽게 위변조가 가능한 점은 처리율 제한을 안정적으로 걸 수 있는 장소가 못 됨
- 서버 측: API 서버쪽에 처리율 제한 장치를 같이 묶어 놓는 법
- 미들웨어(API Gateway): 서버와 클라이언트 사이에 제한 장치를 두어서 보통 처리율 제한, SSL 종단, 사용자 인증, IP 허용 목록 관리 등을 지원하는 완전 위탁관리형 서비스로 둠

→ 위의 방식 중에서 현재 기술 스택이나 인력, 우선 순위, 목표에 따라 위치가 달리질 수 있음

- 프로그래밍 언어가 서버 측 구현을 지원할 수 있는가
- 서버 측에서 구현 시 알고리즘 선택 가능, 제 3자가 제공하는 게이트웨이 방식을 쓰면 선택지는 제한됨
- 처리율 제한 장치를 구현하기 어렵다면 상용 API 게이트웨이를 쓰는 게 바람직 함

### 처리율 제한 알고리즘

#### 1. 토큰 버킷 알고리즘

처리율 제한에 폭 넓게 이용되며, 간단하고 보편적으로 사용. → 아마존, 스트라이프 등이 사용함

- 토큰 버킷은 지정된 용량을 갖는 컨테이너 ← 사전 설정된 양의 토큰이 주기적으로 채워짐
- 토큰이 꽉 찬 버킷에는 토큰이 추가가 되지 X
- 버킷 크기: 버킷이 담을 수 있는 토큰의 최대 개수
- 토큰 공급률: 초당 몇 개의 토큰이 버킷에 공급되는지
- API 엔트포인트 기준이냐 IP 주소별이냐 시스템 처리율을 초당으로 제한하냐에 따라 다름

장점

- 구현이 쉬움
- 메모리 사용 측면에서도 효율적
- 짧은 시간에 집중되는 트래픽도 처리 가능

단점

- 버킷 크기와 토큰 공급률을 적절하게 튜닝하는 것이 까다로움

#### 2. 누출 버킷 알고리즘

토큰 버킷 알고리즘과 비슷하지만 요청 처리율이 고정되어 있음, FIFO 큐로 구현

- 버킷 크기: 큐 사이즈와 같은 값. 큐에는 처리될 항목들이 보관
- 처리율: 지정된 시간당 몇 개의 항목을 처리할지 지정하는 값

장점

- 큐의 크기가 제한되어 있어 메모리 사용량 측면에서 효율적
- 고정된 처리율로 인해서 안정적 출력이 가능해짐

단점

- 단시간에 트래픽이 몰리는 경우, 큐가 가득차면 새로운 요청들이 버려지게 됨
- 버킷 크기와 처리율을 튜닝하기가 까다로움

#### 3. 고정 윈도 카운터 알고리즘

타임라인을 고정된 간격의 윈도로 나누고, 각 윈도마다 카운터(요청이 접수될 때마다 카운터 값이 증가)를 붙임 → 카운터의 값이 임계치에 도달하면 새로운 요청은 새 윈도가 열릴따까지 버려지게 됨

장점

- 메모리 효율이 좋음
- 이해하기 쉬움
- 윈도가 닫히는 시점에 카운터를 초기화하는 방식은 특정한 트래필 패턴을 처리하기에 적합

단점

- 윈도 경계 부근에서 일시적으로 많은 트래픽이 몰려드는 경우, 기대했던 시스템의 처리 한도보다 많은 양의 요청을 처리함

#### 4. 이동 윈도 로깅 알고리즘

고정 윈도 카운터의 단점을 해결하기 위해 이 알고리즘이 등장함

- 요청의 타임스탬프를 추적 → 타임스탬프 데이터는 레디스 같은 캐시에 보관
- 새 요청이 오면 만료된 타임스탬프는 제거
- 새 요청의 타임스탬프를 로그에 추가
- 로그의 크기가 허용치보다 같거나 작으면 요청을 시스템에 전달
- 그렇지 않으면 처리를 거부

장점

- 어느 순간의 윈도를 보더라도, 허용되는 요청의 개수는 시스템의 처리율 한도를 넘지 않음

단점

- 알고리즘이 다량의 메모리를 사용 ← 이유: 거부된 요청의 타임스탬프도 보관해야하니

#### 5. 이동 윈도 카운터 알고리즘

이전 1분 동안의 요청 수 * 이동 윈도와 직전 1분이 겹치는 비율 + 현재 1분간의 요청 수의 계산을 통해 고정 윈도 카운터 알고리즘의 문제점을 해결

장점

- 이전 시간대의 평균 처리율에 따라 현재 윈도의 상태를 계산해서 짧은 시간에 몰리는 트래픽에도 잘 대응
- 메모리 효율이 좋음

단점

- 직전 시간에 도착한 요청이 균등하게 분포되어 있다고 가정 ← 직전 윈도 겹치는 비율이 10%인데, 분당 한도만큼 요청이 들어오면 또 문제가 됨.

### 3단계 상세 설계

#### 처리율 제한 규칙

리프트는 처리율 제한에 오픈 소스를 사용하고 있음

```sql
domain: messaging
descriptors:
	- key: message_type
		value: marketing
		rate_limit:
				unit: day
				requests_per_unit: 5
```

```sql
domain: auth
descriptors:
	- key: auth_type
		value: login
		rate_limit:
				unit: minute
				requests_per_unit: 5
```

#### 처리율 한도 초과 트래픽의 처리

사용자가 처리율 제한에 걸리기까지 얼마나 많은 요청을 알려면, HTTP 응답 헤더에 정보를 담아 클라이언트에게 전달함

- X-Ratelimit-Remaining: 윈도 내에 남은 처리 가능 요청의 수
- X-Ratelimit-Limit: 매 윈도마다 클라이언트가 전송할 수 있는 요청의 수
- X-Ratelimit-Retry-After: 한도 제한에 걸리지 않으려면 몇 초 뒤에 요청을 다시 보내야 하는지 알림.

→ 사용자가 너무 많은 요청을 보내면 429 too many requests 오류를 X-Ratelimit-Retry-After 헤더와 함께 반환

#### 분산 환경에서의 처리율 제한 장치의 구현

분산 환경에서 처리율 제한 장치 구현에서 풀어내야 할 숙제는 1) 경쟁 조건, 2) 동기화

1. 경쟁 조건

경쟁 조건 문제를 해결하는 가장 널리 알려진 해결책은 락임 ← 시스템 성능을 상당히 떨어뜨림

그래서 해결책으로는 **`루아 스크립트`**와 **`정렬 집합이라고 불리는 레디스 자료구조`**를 사용(보통 같이 사용함)

- 루아는 아주 가볍고 빠른 스크립트 언어로 레디스 서버 내부에서 루아 스크립트를 직접 실행할 수 있음
- 레디스는 명령어를 싱글 쓰레드로 처리
- 한 스크립트의 실행이 끝날 때까지 다른 클라이언트의 명령을 일절 처리하지 않음

---

- 정렬 집합은 일반적인 집합 구조에 점수라는 개념을 추가해서, 점수를 기준으로 데이터를 항상 정렬된 상태로 유지해 주는 레디스만의 자료 구조
- 데이터를 넣을 때 아래와 같은 쌍으로 값을 넣음

```sql
(데이터: "User_Request_1", 점수:1700000000)
```

- 점수를 요청이 들어온 타임스탬프로 설정
- 레디스의 원자적으로 동작하는 싱글 쓰레드 덕분에 락이 필요 없이 들어온대로 처리 가능
1. 동기화 이슈

웹 계층은 무상태이므로 처리율 제한 장치가 여러 개일 때,  클라이언트가 요청을 할 때마다 다른 처리율 제한 장치로 갈 수 있음

→ 위와 같은 상황을 고정 세션으로 해결할 수 있지만, 규모 확장이 가능 X & 유연하지도 X

그래서 더 나은 해결책은 레디스와 같은 중앙 집중형 데이터 저장소를 쓰는 것

1. 성능 최적화

여러 데이터 센터를 지원하는 문제는 처리율 제한 장치에 매우 중요한 문제 ← 데이터 센터에서 멀리 떨어진 사용자를 지원핟려다 보면 지연시간이 증가하는 문제가 발생

그래서 에지 서버를 세계 곳곳에 심어 놓고 있어서, 지연 시간을 줄이고자 함

+제한 장치 간에 데이터를 동기화할 때 최종 일관성 모델을 사용하는 것

1. 모니터링

처리율 제한 장치가 효과적으로 동작하고 있는 지 보려면

1. 채택된 처리율 제한 알고리즘이 효과적인지
2. 정의한 처리율 제한 규칙이 효과적인지

를 확인해야한다

### 4단계 마무리

경성 처리율 제한: 요청의 애수는 임계치를 절대 넘어설 수 없다

연성 처리율 제한: 요청 개수는 잠시 동안은 임계치를 넘어설 수 있다

애플리케이션 계층이외에도 네트워크 계층에서 IP주소에 처리율을 제한하는 것도 가능함

- 처리율 제한을 회피하는 방법
1. 클라이언트 측 캐시를 사용하여 API 호출 횟수를 줄인다
2. 처리율 제한의 임계치를 이해하고, 짦은 시간 동안 너무 많은 메세지를 보내지 않게 함
3. 예외나 에러를 처리하는 코드를 도입하여 사용자가 그런 상황에서 graceful하게 복구될 수 있도록 함
4. 재시도 로직을 구현할 때는 충분한 백오프 시간이 필요

### 질문 관련 답변

#### Q1. 외부 API 호출 시 어느 Rate Limiting 알고리즘이 적합한가?

→ 토큰 버킷 알고리즘

- remove.bg 무료 플랜은 월 50회라는 총량 제한이 있음
- 토큰 버킷은 버킷 크기(총량)와 토큰 공급률(시간당 개수)로 제어 가능
- 순간적으로 요청이 몰려도 버킷에 토큰이 남아있으면 처리, 소진되면 차단하는 방식이라 유연함
- 누출 버킷은 처리율이 고정이라 이런 총량 기반 제어엔 유연성이 떨어짐

#### Q2. DB로 Rate Limiting을 구현하면 얼마나 느려지나?

→ 요청량이 많을수록 병목이 심각해짐

- Redis: 0.1~1ms (인메모리) / MySQL·Aurora: 1~10ms (디스크 기반)
- Rate Limiting은 요청마다 카운터 SELECT + UPDATE로 2번 DB 접근 발생
- QPS 1,000이면 Rate Limiting 용으로만 초당 2,000번 쿼리 추가됨
- 동시성 제어를 위한 락까지 걸리면 더 느려짐
- But, 로그인 제한처럼 호출 빈도가 낮은 곳은 DB로도 충분함

#### Q3. 여러 데이터센터 환경에서 Rate Limiter를 어떻게 동기화하는가?

→ 중앙 집중형 Redis 공유 + 최종 일관성

- 데이터센터마다 Rate Limiter가 따로 있으면 카운터가 분산되어 실제 호출 횟수보다 적게 집계되는 문제 발생 (ex. 서울 3회 + 미국 3회 = 6회지만 각자 3회로만 인식)
- 해결책: 중앙 집중형 Redis에 카운터를 공유
- But, 글로벌 Redis가 멀면 지연시간이 발생하므로 최종 일관성 모델을 써서 약간의 오차를 허용하는 방식으로 타협함
