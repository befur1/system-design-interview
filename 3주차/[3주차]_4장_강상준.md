처리율 제한 장치는 클라이언트 또는 서비스가 보내는 트래픽의 처리율(rate)를 제어하기 위한 장치다

### 다음의 이점을 얻을 수 있다
- DoS 공격에 의한 자원 고갈 방지
- 비용 절감
- 서버 과부하 방지

# 문제 이해 및 설계 범위 확정
### 다음의 설계 범위를 생각해볼 수 있다
- 제한 장치의 위치 (클라이언트 vs 서버)
    - 클라이언트: 앱/웹단에서 제한 -> 제어 불가능, 우회 가능
    - 버튼 중복 클릭 방지, 클라이언트 SDK 내부의 요청 스케줄러 도입 등의 방식이 있음
- 제한 장치가 참고할 기준(IP, 사용자 ID, Device ID, etc)
- 시스템 규모
- 단일 서버인지 분산된 환경인지?
- 독립된 장치인지 코드레벨에서 구현해야 하는지?
- 요청 거부시 사용자에게 그 사실을 알려야하는지?

클라이언트 측 제한은 우회가 가능해 신뢰할 수 없으므로 서버단에서 제한을 거는 것이 필수적이고 보조적인 수단으로 클라이언트 측 제한을 거는게 좋을 것 같다.

Q. 미들웨어가 어떻게 동작하고 위치는 어디에 있는 건가??
- 물리적/논리적으로 클라이언트 - API서버 사이에 위치
- 외부 서비스 업체를 이용하는 방식
    - Cloudflare나 Akamai 같은 CDN에 도메인을 연결해두면 트래픽을 가장 먼저 받고 걸러서 전달해줌
- 사내 인프라 맨 앞단에 직접 띄우는 방식
    - Nginx, Spring Cloud Gateway 등을 활용
- 백엔드 코드레벨에서 구현하게 되면 톰캣 스레드를 하나 잡은 상태에서 검사하게 되어 요청이 몰렸을 때 서버가 터질 가능성이 높음
    - 백엔드 서버가 다중화되어있을 때 앞단의 미들웨어 1곳에서 공통으로 처리할 수 있음.
- EC2 단일 서버 내에서 nginx로 처리하는 경우도 소프트웨어적으로는 독립된 미들웨어 서버를 띄워두는 것과 같다.
    - 별도 서버 인스턴스를 두는 것이 자원을 공유하지 않기 때문에 안정성 면에서 더 좋음

# 개략적인 설계안 제시 및 동의 구하기

## 처리율 제한 알고리즘

### 토큰 버킷
1. 토큰 버킷은 지정된 용량을 가진 버킷에 토큰을 일정한 속도로 채우는 방식으로 동작한다.
2. 각 요청은 처리될 때마다 하나의 토큰을 사용하고 토큰이 없으면 요청은 거부된다.
- 토큰 버킷을 구현하거나 설정할 떄 버킷 크기, 토큰 공급률 2개의 인자를 넣어줘야한다.

장:
- 구현이 쉽다
- 메모리 사용이 효울적이다
- 집중 트래픽도 처리 가능하다
단:
- 2개 파라미터를 튜닝하는 게 까다롭다.

### 누출 버킷 알고리즘
- 토큰 버킷 알고리즘과 유사하지만 **요청 처리율**이 고정되어있음
- 보통 FIFO 큐로 구현
1. 요청이 도착하면 큐를 확인
2. 빈자리가 있으면 추가하고 없으면 버린다
3. 지정된 시간마다 큐에서 요청을 꺼내어 처리한다.
- 버킷크기, 처리율 두 인자를 사용

장:
- 큐의 크기가 제한되어 있어 메모리 사용량 측면에서 효율적
- 고정된 처리율 -> 안정적 출력
단:
- 버스트 트래픽(순간적인 트래픽 증가)을 처리하지 못한다.
- 두 개 인자 튜닝이 까다롭다.

### 고정 윈도 카운터 알고리즘
1. 타임라인을 고정된 간격의 윈도(window)로 나누고, 각 윈도마다 카운터를 붙임
2. 요청이 오면 해당 윈도의 카운터를 +1
3. 카운터가 한도에 도달하면 새 윈도가 열릴 때까지 버려짐

- 윈도의 경계 부분에서 트래픽이 몰릴 경우 윈도 하나에 요청이 몰려버릴 수 있는 단점이 있다. (1초에 100개 제한인데 정확히 0.5초~1.5초사이에 150개의 요청이 오면?)

장:
- 메모리 효율이 좋다
- 이해하기 쉽다
- 윈도가 닫히는 시점에 카운터를 초기화 하는 방식이 특정한 트래픽 패턴을 처리하기 적합하다.
    - 시계 기준으로 정각마다 리셋되는 API 사용량 정책이나 정기적으로 특정 시점에 몰려오는 배치 트래픽.

단:
- 경계 부근에서 트래픽이 몰리면 기대한 양보다 많은 양의 요청을 처리하게 됨.

### 이동 윈도 로깅 알고리즘
고정 윈도 카운터 알고리즘의 단점을 해결

1. 요청의 타임스탬프를 추적. 타임스탬프 데이터는 보통 레디스의 정렬 집합과 같은 캐시에 보관
2. 새 요청이 오면 만료된 타임스탬프는 제거한다(실행 여부와 관계없음)
3. 새 요청의 타임 스탬프를 로그에 추가한다
4. 로그의 크기가 허용치보다 같거나 작으면 요청을 전달하고 아니면 거부한다

장:
어느 순간에 윈도를 봐도 시스템 처리율 한도를 넘지 않는다.

단:
메모리를 너무 많이 사용함(모든 요청의 타임스탬프 저장)

Q.요청이 들어올 때마다 시간 범위에 있는 로그를 확인하고 , 크기를 계산하고, 만료된 로그는 지워야하는데 매 요청마다 삭제,추가,조회 쿼리가 계속 발생하는 것 아닌지? 부하가 너무 심하지 않은지?
- 요청 1개당 redis에는 최소 3개의 연산이 일어남(옛날 데이터 탐색 후 삭제, 이번 요청 타임 스탬프 추가, 남은 개수 조회)
- 실제로 레디스 자체가 병목구간이 될 수도 있음
- 3번의 통신을 루아 스크립트를 써서 묶어 전달하고 내부에서 원자적으로 실행되게 줄이는 꼼수를 사용하기는 한다.
- 이 문제는 이동 윈도 카운터 알고리즘에서 해결함

### 이동 윈도 카운터 알고리즘
고정 윈도 카운터 알고리즘 + 이동 윈도 로깅 알고리즘
- 카운터 + 이동 윈도 사용
- 현재 1분간의 요청 수 + 직전 1분간의 요청 수 * 이동 윈도와 직전 1분이 겹치는 비율을 확인해서 계산

장:
- 이전 시간대의 평균 처리율(균등하다고 가정)에 따라 현재 윈도의 상태를 계산하므로 짧은 시간에 몰리는 트래픽에도 잘 대응
- 메모리 효율이 좋음
단:
- 직전 시간대에 도착한 요청이 균등하게 분포되었다고 가정하기에 다소 조건이 느슨할 수 있지만 설계와 다르게 허용되거나 버려진 요청은 0.003% 수준이라는 실험이 있음.

### 개량적 아키텍처
언급되었던 카운터는 어디에 저장될 것인가?
데이터베이스는 느리니까 레디스 캐시 같은 걸 따로 둬서 가져오도록 설계한다.

# 상세 설계
## 처리율 제한 규칙은 어떻게 만들어지고 어디에 저장되는가?
보통 설정 파일로 디스크에 저장된다.
## 처리가 제한된 요청들은 어떻게 처릭되는가?
요청이 한도 제한에 걸리면 API는 HTTP 429 응답을 클라이언트에게 전송함.
한도 제한에 걸린 메시지를 나중에 처리하기 위해 큐에 보관할 수도 있음
### 처리율 제한 장치가 사용하는 HTTP 헤더
- X-Ratelimit-Remaining: 윈도 내에 남은 처리 가능 요청의 수
- X-Ratelimit-Limit: 매 윈도마다 클라이언트가 전송할 수 있는 요청의 수
- X-Ratelimit-Retry-After: 한도 제한에 걸리지 않으려면 요청을 몇 초 후에 다시 전송해야 하는지 알려줌.

Q. 윈도 내에 남은 처리 가능 요청의 수나 매 윈도마다 클라이언트가 전송할 수 있는 요청의 수는 서버 내부 정보인데 헤더에 담아서 보내주면 안 되는 거 아닌지?
- 우리 내부 인프라 스펙을 요청하는 게 아니라 클라이언트 개인의 잔여량이기 때문에 괜찮다.
- 언제 끝날지 모르니 일단 쏘다가 에러 터지면 멈추는 것 보다 잔여 요청 수를 보내서 스스로 조절하게 하는 게 더 좋은 경험을 제공함.

## 분산 환경에서의 처리율 제한
### race condition
가장 널리 알려진 해결책은 락을 거는 건데 시스템 성능을 떨어뜨린다는 문제가 있음
경쟁조건이 발생하는 근본적인 이유는 카운터를 읽고->비교하고->올리는 과정이 쪼개져있기 때문임
- 루아 스크립트
    - 여러 단계의 로직을 하나의 스크립트로 묶어서 던질 수 있음
    - 레디스는 싱글 스레드 엔진이므로 원자적 실행을 보장함
    - 단, 루아 스크립트가 길어지면 성능 저하의 원인이 될 수 있음
- 정렬 집합
    - 숫자를 읽고 더하는 게 아니라 그냥 타임스탬프를 집합에 넣었다가 빼는 거라 카운터 연산이 필요없음.(이동 윈도 로깅)

### 동기화
- 고정 세션을 활용해 같은 클라이언트로부터 요청은 항상 같은 미들웨어에서 처리
- 레디스와 같은 중앙 집중형 데이터 저장소를 사용(추천)
