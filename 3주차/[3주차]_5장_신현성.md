## 안정 해시가 필요한 이유

수평적 규모 확장을 하려면 요청이나 데이터를 여러 서버에 균등하게 분배해야 한다.

캐시 서버가 여러 대라면 특정 데이터가 어느 서버에 저장되어 있는지 결정하는 규칙이 필요하다. 가장 단순한 방법은 키를 해시한 값을 서버 수로 나누는 것이다.

`serverIndex = hash(key) % N`

여기서 `N`은 서버의 개수다.

예를 들어 서버가 4대라면 키의 해시값을 4로 나눈 나머지에 따라 서버를 선택한다.

- `hash(key0) % 4 = 1` → 서버 1
- `hash(key1) % 4 = 0` → 서버 0
- `hash(key2) % 4 = 2` → 서버 2

이 방식은 서버 수가 고정되어 있고 데이터가 균등하게 분포할 때는 잘 동작한다. 문제는 서버가 추가되거나 제거될 때 발생한다.

---

## 해시 키 재배치 문제

서버 한 대에 장애가 발생해 서버 수가 4대에서 3대로 줄어들었다고 가정한다.

기존에는 `hash(key) % 4`를 사용했지만 서버가 제거된 뒤에는 `hash(key) % 3`을 사용해야 한다.

나누는 값이 바뀌었기 때문에 장애가 발생한 서버에 저장되어 있던 키뿐만 아니라 대부분 키의 서버 위치가 달라진다.

클라이언트가 새로운 계산 결과를 따라 서버에 접근하면 실제 데이터가 없는 서버에 요청을 보내게 된다. 캐시 시스템에서는 대규모 캐시 미스가 발생하고, 모든 요청이 원본 데이터베이스로 몰릴 수 있다.

서버를 추가하는 경우에도 나누는 값이 바뀌므로 비슷한 문제가 생긴다.

따라서 서버가 추가되거나 제거될 때 데이터 전체가 아니라 일부만 재배치하는 방법이 필요하다.

---

## 안정 해시

안정 해시(Consistent Hashing)는 해시 테이블의 크기가 조정될 때 전체 키 중 일부만 재배치되도록 하는 해시 기술이다.

전체 키의 수를 `K`, 서버 또는 슬롯의 수를 `N`이라고 하면 서버 변경 시 평균적으로 약 `K/N`개의 키만 재배치된다.

일반적인 나머지 연산 방식은 서버 수가 바뀌면 대부분의 키가 영향을 받지만, 안정 해시는 영향을 받는 키의 범위를 최소화한다.

---

## 해시 공간과 해시 링

해시 함수의 결과값이 가질 수 있는 전체 범위를 해시 공간이라고 한다.

해시 함수의 출력 범위를 `x0, x1, x2, ..., xn`이라고 가정할 수 있다. 해시 공간의 처음과 끝을 연결하면 원 모양의 해시 링(Hash Ring)을 만들 수 있다.

이제 서버와 데이터의 키를 같은 해시 함수를 이용해 해시 링 위에 배치한다.

---

## 해시 서버

각 서버의 IP 주소나 이름을 해시 함수에 입력해 해시 링 위의 특정 위치에 배치한다.

서버가 네 대라면 다음과 같은 서버들이 서로 다른 지점에 배치될 수 있다.

- `s0` → 서버 0
- `s1` → 서버 1
- `s2` → 서버 2
- `s3` → 서버 3

서버의 실제 번호가 해시 링의 순서를 의미하는 것은 아니다. 서버의 위치는 서버 식별자를 해시한 결과로 결정된다.

---

## 해시 키

캐시할 데이터의 키도 서버와 동일한 해시 함수로 계산해 해시 링 위에 배치한다.

- `k0` → key0
- `k1` → key1
- `k2` → key2
- `k3` → key3

기존의 나머지 연산 방식과 달리 서버의 개수를 해시 계산에 직접 사용하지 않는다.

따라서 서버의 수가 변경되더라도 모든 키의 해시값을 다시 계산할 필요가 없다.

---

## 서버 조회

어떤 키가 저장될 서버를 찾으려면 다음 규칙을 사용한다.

> 키의 위치에서 해시 링을 시계 방향으로 탐색했을 때 처음 만나는 서버에 키를 저장한다.

예를 들어 `k0`에서 시계 방향으로 이동했을 때 처음 만나는 서버가 `s0`이라면 `key0`은 서버 0에 저장된다.

- `k0` → `s0`
- `k1` → `s1`
- `k2` → `s2`
- `k3` → `s3`

키와 서버가 링 위에 배치되는 위치에 따라 여러 키가 하나의 서버에 저장될 수도 있다.

---

## 서버 추가

새로운 서버가 추가되더라도 모든 키를 재배치할 필요는 없다.

새 서버 `s4`가 `s3`과 `s0` 사이에 추가됐다고 가정한다. 기존에는 해당 범위의 키가 시계 방향으로 처음 만나는 `s0`에 저장되었다.

서버 `s4`가 추가된 뒤에는 해당 범위의 키가 `s4`를 먼저 만나므로 그 키들만 `s4`로 이동한다. 나머지 키들은 기존 서버에 그대로 남는다.

서버 추가 시에는 새 서버의 반시계 방향에 있는 이전 서버와 새 서버 사이의 키만 새 서버로 재배치된다.

안정 해시는 서버 추가 시 데이터 전체가 아니라 새 서버가 담당하게 된 범위만 재배치한다.

---

## 서버 제거

서버가 제거될 때도 일부 키만 재배치된다.

서버 `s1`이 제거되면 기존에 `s1`이 담당하던 범위의 키는 시계 방향으로 다음에 위치한 서버로 이동한다. 나머지 서버에 저장된 키는 영향을 받지 않는다.

즉, 제거된 서버가 담당하던 키만 시계 방향의 다음 서버로 재배치된다.

이를 통해 서버 장애나 제거로 인해 발생하는 대규모 데이터 이동을 줄일 수 있다.

---

## 기본 구현법

안정 해시의 기본 구현은 다음 두 단계로 정리할 수 있다.

1. 서버와 키를 균등 분포 해시 함수를 사용해 해시 링에 배치한다.
2. 키의 위치에서 링을 시계 방향으로 탐색했을 때 처음 만나는 서버에 키를 저장한다.

이 방법을 사용하면 서버가 추가되거나 제거될 때 재배치되는 키의 수를 줄일 수 있다.

하지만 실제 환경에서는 기본 구현만으로 해결되지 않는 문제가 있다.

---

## 기본 구현법의 두 가지 문제

### 파티션 크기가 균등하지 않을 수 있다

해시 링에서 인접한 서버 사이의 공간을 파티션이라고 볼 수 있다.

서버가 링 위에 완벽하게 균등하게 배치된다는 보장은 없다. 어떤 서버는 작은 범위만 담당하고, 다른 서버는 매우 큰 범위를 담당할 수 있다.

특히 서버가 추가되거나 제거되면 파티션 크기의 불균형이 더 커질 수 있다.

특정 서버가 다른 서버보다 훨씬 큰 범위의 키를 담당하면 저장 공간과 요청량이 한쪽으로 몰릴 수 있다.

### 키가 균등하게 분포하지 않을 수 있다

서버의 위치가 어느 정도 균등하더라도 키가 특정 구간에 집중될 수 있다.

이 경우 어떤 서버에는 많은 키가 저장되고 다른 서버에는 거의 데이터가 저장되지 않는 상황이 발생한다.

따라서 기본적인 해시 링만으로는 다음 두 가지를 모두 보장하기 어렵다.

- 서버가 담당하는 파티션의 크기
- 서버에 저장되는 키의 균등한 분포

이 문제를 해결하기 위해 가상 노드를 사용한다.

---

## 가상 노드

가상 노드(Virtual Node)는 실제 서버를 가리키는 논리적인 노드다.

하나의 물리 서버를 해시 링의 한 지점에만 배치하지 않고 여러 개의 가상 노드로 나누어 링의 여러 지점에 배치한다.

예를 들어 서버 0과 서버 1이 각각 세 개의 가상 노드를 가진다면 다음과 같이 표현할 수 있다.

- 서버 0 → `s0_0`, `s0_1`, `s0_2`
- 서버 1 → `s1_0`, `s1_1`, `s1_2`

각 가상 노드는 특정한 파티션을 담당하며, 해당 파티션의 실제 데이터는 가상 노드가 가리키는 물리 서버에 저장된다.

키가 저장될 서버를 찾는 규칙은 기존과 같다.

1. 키의 위치에서 시계 방향으로 링을 탐색한다.
2. 처음 만나는 가상 노드를 찾는다.
3. 그 가상 노드가 가리키는 실제 서버에 데이터를 저장한다.

가상 노드를 사용하면 하나의 서버가 링의 여러 구간을 나누어 담당한다. 따라서 특정 물리 서버에 연속된 큰 파티션이 할당될 가능성이 줄어든다.

---

## 가상 노드 개수의 트레이드오프

가상 노드의 개수를 늘릴수록 키가 더 균등하게 분포한다.

가상 노드가 많아지면 각 서버가 작은 파티션을 여러 개 담당하므로 데이터 분포의 표준 편차가 작아진다.

그러나 가상 노드의 개수가 많아질수록 다음 비용도 증가한다.

- 해시 링 정보를 저장하기 위한 메모리
- 노드 정보를 관리하는 비용
- 서버 추가·제거 시 변경해야 하는 메타데이터
- 장애 복구와 데이터 이동을 추적하는 복잡도

따라서 가상 노드의 수는 많을수록 무조건 좋은 것이 아니다. 데이터 분포의 균일성과 관리 비용 사이에서 적절한 값을 선택해야 한다.

서버마다 처리 능력이 다르다면 성능이 좋은 서버에 더 많은 가상 노드를 배정하고, 성능이 낮은 서버에는 적은 가상 노드를 배정하는 방식도 생각할 수 있다.

---

## 재배치할 키 결정

### 서버 추가 시

새 서버가 추가되면 새 서버의 위치에서 반시계 방향에 있는 이전 서버까지의 범위가 영향을 받는다.

기존에는 그 범위의 키가 시계 방향에 있던 기존 서버에 저장되었지만, 새 서버가 추가된 뒤에는 새 서버를 먼저 만나게 된다.

따라서 이전 서버와 새 서버 사이에 있는 키만 새 서버로 이동한다.

### 서버 제거 시

서버가 제거되면 제거된 서버가 담당하던 범위의 키가 시계 방향의 다음 서버로 이동한다.

다른 서버가 담당하던 키는 이동하지 않는다.

---

## 안정 해시의 장점

### 키 재배치 최소화

서버가 추가되거나 제거될 때 전체 키가 아니라 영향을 받는 범위의 키만 이동한다.

캐시 서버가 변경되었을 때 대규모 캐시 미스가 발생하는 것을 완화할 수 있다.

### 수평적 규모 확장에 유리

서버를 추가해도 전체 데이터를 다시 분배할 필요가 없으므로 서버 증설이 쉬워진다.

트래픽 증가에 따라 캐시 서버나 데이터 저장 서버를 점진적으로 추가할 수 있다.

### 균등한 데이터 분포

가상 노드를 충분히 사용하면 물리 서버가 담당하는 데이터와 요청량을 비교적 균등하게 분산할 수 있다.

### 핫스팟 문제 완화

해시 분포가 고르지 않아 특정 서버에 데이터가 집중되는 문제를 줄일 수 있다.

다만 특정 키 하나가 지나치게 자주 조회되는 핫키 문제까지 안정 해시만으로 해결되는 것은 아니다.

---

## 안정 해시의 활용 사례

안정 해시는 다음과 같은 분산 시스템에서 활용된다.

- 분산 캐시 서버
- 데이터베이스 샤딩
- Amazon DynamoDB의 파티셔닝
- Apache Cassandra 클러스터의 데이터 파티셔닝
- Discord의 대규모 시스템
- CDN 서버 선택
- 네트워크 부하 분산

안정 해시는 캐시에만 사용되는 기술이 아니라 특정 데이터나 요청을 여러 노드에 안정적으로 분배해야 하는 시스템 전반에 활용할 수 있다.

---

## 기존 내용과 연결해서 생각해본 부분

### 1장의 샤딩 문제와 연결

1장에서는 데이터베이스를 여러 샤드로 분리할 때 데이터 재샤딩 문제가 발생한다고 배웠다.

다음과 같은 단순한 방식을 사용한다고 가정할 수 있다.

`shardIndex = userId % shardCount`

샤드가 4개에서 5개로 늘어나면 나누는 값이 바뀌기 때문에 대부분 사용자의 샤드 위치가 달라진다.

안정 해시를 적용하면 새 샤드가 담당하는 범위의 데이터만 이동하도록 설계할 수 있으므로 재샤딩에 필요한 데이터 이동량을 줄일 수 있다.

다만 캐시는 데이터가 사라지면 원본 저장소에서 다시 가져올 수 있지만, 데이터베이스 샤딩에서는 실제 원본 데이터를 안전하게 이동해야 한다. 따라서 데이터 복제, 검증, 라우팅 전환과 같은 추가 과정이 필요하다.

### 로드밸런서와 안정 해시의 차이

로드밸런서와 안정 해시는 모두 여러 서버에 부하를 분산하지만 목적이 다르다.

- 로드밸런서는 들어오는 요청을 현재 사용 가능한 서버에 분배한다.
- 안정 해시는 같은 키가 가능한 한 같은 서버를 찾아가도록 매핑 관계를 유지한다.

일반적인 API 요청은 어느 무상태 서버가 처리해도 되므로 라운드 로빈을 사용할 수 있다. 반면 특정 데이터가 저장된 캐시 서버를 찾아야 한다면 키와 서버 사이의 안정적인 매핑이 필요하다.

### 단일 서버 프로젝트에서는 필요성이 잘 드러나지 않았던 이유

기존 프로젝트에서는 애플리케이션 서버나 데이터 저장소를 한 대씩 사용한 경우가 많아 어떤 서버에 데이터를 저장할지 결정할 필요가 없었다.

하지만 캐시 서버나 데이터베이스 샤드가 여러 대로 늘어나면 다음 문제가 새롭게 생긴다.

- 특정 키를 어느 서버에 저장할 것인가?
- 서버가 추가되면 기존 키를 얼마나 이동할 것인가?
- 서버가 죽으면 그 서버의 키를 어디로 보낼 것인가?
- 서버별 저장량과 요청량을 어떻게 균등하게 만들 것인가?

안정 해시는 서버를 여러 대로 늘리는 것만으로 확장이 끝나는 것이 아니라 데이터의 위치를 관리하는 규칙도 필요하다는 점을 보여준다.

## 추가적으로 생각해볼 질문

### 안정 해시는 고가용성을 보장하는가?

안정 해시는 서버 장애 시 키가 이동할 새로운 서버를 결정해준다. 하지만 장애가 발생한 서버에만 데이터가 저장되어 있었다면 새 서버에는 해당 데이터가 없을 수 있다.

캐시라면 원본 데이터베이스에서 다시 읽을 수 있지만 데이터베이스나 영속 저장소라면 데이터 유실로 이어질 수 있다.

따라서 안정 해시는 데이터의 위치를 결정하는 기술이지 데이터 복제와 백업까지 자동으로 해결하는 기술은 아니다. 실제 시스템에서는 복제본, 장애 감지, 데이터 복구 전략을 함께 설계해야 한다.

### 안정 해시를 사용하면 핫키 문제도 해결될까?

가상 노드를 사용하면 많은 키가 특정 서버에 몰리는 불균등 분포는 줄일 수 있다.

하지만 유명인의 게시물이나 인기 콘텐츠처럼 하나의 키 자체에 요청이 집중된다면 그 키는 여전히 하나의 서버로 향한다.

이런 핫키 문제에는 다음과 같은 추가 전략이 필요할 수 있다.

- 인기 데이터를 여러 서버에 복제한다.
- 키를 더 작은 단위로 분할한다.
- 애플리케이션 서버에 로컬 캐시를 둔다.
- 읽기 전용 복제본을 추가한다.
- 요청을 제한하거나 일정 시간 결과를 캐시한다.

### 가상 노드는 몇 개가 적절할까?

가상 노드가 많을수록 데이터는 균등하게 분산되지만 메타데이터와 운영 복잡도도 증가한다.

또한 모든 서버의 성능이 같지 않다면 가상 노드를 같은 수로 배정하는 것이 오히려 불균형을 만들 수 있다.

서버의 CPU, 메모리, 저장 공간과 실제 요청량을 바탕으로 가상 노드 개수를 조절하는 방법을 생각해볼 수 있다.

### 모든 클라이언트가 같은 해시 링을 알고 있어야 할까?

각 클라이언트나 서버가 서로 다른 노드 목록을 가지고 있다면 동일한 키에 대해 서로 다른 서버를 선택할 수 있다.

따라서 서버 추가·제거 정보를 어떻게 전달하고, 모든 요청 처리 노드가 같은 해시 링 버전을 사용하도록 할지도 중요하다.

중앙 라우팅 계층을 두거나 클러스터 멤버십 정보를 배포하는 방법을 고려할 수 있다.
