# 5장_ 안정 해시

## 해시 키 재배치 문제
전통적으로 데이터 파티셔닝 시 특정 키가 저장될 서버는 hash(key) mod n 연산으로 결정함.
- 서버 풀의 크기가 고정되어 있고 데이터 분포가 균등하면 잘 동작함.
- 서버가 추가되거나 삭제되면 n이 바뀌면서 나머지 연산 결과가 대부분 바뀌어, 캐시 키와 서버 사이의 매핑 관계가 거의 다 무효화됨.
- 그 결과 대량의 키 재배치가 발생하고, 일시적으로 데이터베이스 서버 부하가 폭증함.
- 안정 해시는 이 문제를 해결하기 위해 고안된 기술임.

## 해시 공간과 해시 링
- 안정 해시: 해시 테이블 크기가 조정될 때 평균적으로 k/n개의 키만 재배치하는 해시 기술임 (k=키 개수, n=슬롯 개수).
- 대부분의 전통적인 해시 테이블은 슬롯 개수가 바뀌면 거의 모든 키를 재배치해야 함.
- SHA-1 같은 해시 함수 사용 시 출력값의 범위는 0부터 2^160-1까지임.
- 이 값의 범위 양쪽 끝이 서로 맞닿도록 구부리면 하나의 해시 공간이 만들어지며, 이를 해시 링이라 부름.

## 서버와 키의 매핑
- 해시 함수로 서버의 IP 주소나 이름을 해시하면, 각 서버는 해시 링 위의 한 지점에 대응됨.
- 데이터를 나타내는 키도 같은 해시 함수로 링 위의 한 점에 매핑함.
- 키를 저장할 서버를 찾을 때는 그 키의 위치부터 시계 방향으로 링을 탐색하여, 처음 만나는 서버에 저장함.

## 서버 추가 시의 동작
- 새 서버는 해시 링 위의 임의의 지점에 위치함.
- 그 지점으로부터 시계 반대 방향으로 가장 가까운 기존 서버와 새 서버 사이에 있던 키들만 새 서버로 재배치됨.
- 나머지 키들의 위치는 전혀 영향을 받지 않음. → hash mod n 방식과 달리 재배치 범위가 국소적으로 한정됨.

## 서버 제거 시의 동작
- 서버가 삭제되면, 그 서버가 담당하던 키의 범위는 시계 방향으로 인접한 다음 서버가 그대로 넘겨받음.
- 삭제된 서버가 갖고 있던 키들만 이동하며, 다른 서버가 담당하던 키에는 영향이 없음.

## 기본 접근법의 문제점
서버를 무작위 해시 함수 값에 따라 배치하는 기본 접근법은 두 가지 문제를 일으킬 수 있음.
- 파티션(서버가 담당하는 해시 공간의 범위) 크기를 균등하게 유지하는 것이 사실상 불가능함.
- 키의 분포가 균등하지 않을 수 있음.
- 서버 위치가 몇 개 되지 않을 때는 서버 간 물리적 거리가 불균등해져, 어떤 서버는 매우 좁은 구간을, 어떤 서버는 매우 넓은 구간을 담당하는 불균형이 발생함.

## 가상 노드
- 위 문제를 해결하기 위한 기법이 가상 노드, 또는 복제임.
- 가상 노드는 실제 서버를 가리키는 노드로, 하나의 서버가 링 위에 여러 개의 가상 노드로 표현됨.
- 가상 노드 개수를 늘릴수록 표준 편차가 작아져 데이터가 고르게 분산됨.
- 물리 서버를 늘리지 않고도 링 위에 배치되는 점의 개수를 늘림으로써, 대수의 법칙에 따라 각 서버가 담당하는 부하 비율이 통계적으로 1/n에 수렴하게 만드는 방식임.

## 재배치되는 키의 계산
가상 노드가 도입된 해시 링에서 서버가 추가/삭제될 때 재배치할 키를 찾는 절차는 다음과 같음.
- 시계 방향으로 링을 순회하며 만나는 모든 가상 노드를 찾음.
- 그 가상 노드들에 대응하는 키의 범위를 계산함.
- 계산된 범위에 속한 키들만 재배치하며, 나머지 서버가 담당하는 키의 범위는 변경되지 않음.

## 안정 해시의 이점
- 서버가 추가/삭제될 때 재배치되는 키의 수가 평균적으로 k/n개로 최소화됨.
- 데이터가 더 균등하게 분산되므로, 특정 샤드에 접근이 지나치게 몰려 서버가 과부하되는 상황(핫스팟 키 문제)의 발생 가능성이 줄어듦.
- 단, 이는 구조적인 분산 문제를 개선하는 것일 뿐, 특정 키 하나에 접근이 집중되는 근본적인 핫스팟 문제까지 해결하는 것은 아님.

## 안정 해시의 활용 사례
- 아마존 다이나모디비(DynamoDB): 파티셔닝 관리에 활용
- 아파치 카산드라(Cassandra): 데이터 분산에 활용
- 구글 매글레브(Maglev): 부하 분산기가 백엔드 서버를 고를 때 활용
- 콘텐츠 전송 네트워크(CDN): 요청을 캐시 서버에 매핑하는 데 활용

## 적용 가능 사례 0 — 아직 실적용 어려움
- 안정 해시는 서버가 여러 대로 늘어나거나 줄어들 때 재배치되는 키의 수를 최소화하기 위한 기술인데, 지금 프로젝트는 MySQL 단일 서버와 앱 서버 1대로 구성돼 있어 애초에 여러 대로 쪼개는 상황 자체가 없다. CLOVA 파일 저장도 NCP Object Storage 내부에서 샤딩을 알아서 처리해주기 때문에, 현재 규모에서는 직접 적용할 지점이 없다.
