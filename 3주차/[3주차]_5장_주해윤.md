## 5장 안정 해시 설계

---

### 1) 해시 키 재배치 문제

`serverIndex = hash(key) % N`  (N은 서버의 개수)

- 서버들에 부하를 균등하게 나누는 보편적인 방법이다.
    - 서버 풀의 크기가 고정되어 있을 때, 데이터 분포 균등할 때 잘 동작
    - 서버 추가 되거나 기존 서버 삭제되면 문제 발생 → 키 재분배로 인해 대규모 캐시 미스 발생

### 2) 안정 해시

> 안정 해시란, 해시 테이블 크기가 조정될 때 평균적으로 오직 k/n개의 키만 재배치하는 해시 기술이다. (k - key 개수, n - 슬롯 개수)
> 

해시 함수 f(SHA-1 사용, 해시 공간 범위 $2^{160}-1$)의 출력 범위 x0~xn

→ 이 해시 공간의 양쪽을 구부려 접어 해시 링 만듦

→ 서버를 이 해시 링 위에 배치, 키 또한 링 위에 배치

→ 어떤 키가 저장되는 서버는 해당 키의 위치로부터 시계 방향으로 링을 탐색해 나가면서 만나는 첫번째 서버

→ 서버 추가/제거를 하더라도 키 가운데 일부만 재배치하면 된다는 사실을 알 수 있음

**문제점**

- 서버가 추가/삭제되는 상황을 감안하면 파티션의 크기를 균등하게 유지하는 게 불가능
- 키의 균등 분포를 달성하기 어려움

→ **해결책**

- 가상 노드: 실제 노드 또는 서버를 가리키는 노드, 하나의 서버는 링 위에 여러 개의 가상 노드 가질 수 있음
    - 각 서버는 하나가 아닌 여러 개 파티션을 관리
    - 개수를 늘릴수록 키의 분포 점점 더 균등

### +) 논의할 사항 및 경험과 연결

- 안정 해시는 서버 수가 바뀔 때 이동하는 데이터량을 줄이는 방법임 → 어떤 키를 가지고 데이터를 나눌지를 생각해봐야 함
    - 예를 들어 CoTempo가 대규모 서비스가 된다면 사용자 ID, 팀 ID 중 어떤 걸 분산 키로 선택할지 등을 생각해볼 수 있을 듯
- 단순히 사용자가 늘어날 것 같다는 생각만으로 안정 해시를 도입하기엔 데이터 위치 추적과 노드 장애 처리에 복잡성이 생김
    - 작은 규모에서는 단일 서버에서의 병목 해결에 힘을 쓰고 캐시나 저장소를 여러 대로 나누어야 하는 상황이 왔을 때 고려하는 것이 합리적임
