# 4장_ 처리율 제한 장치

## 처리율 제한 장치의 정의
처리율 제한 장치란 클라이언트 또는 서비스가 보내는 트래픽의 처리율을 정의된 임계치 아래로 제어하는 장치임.
- ex) 사용자는 초당 2회 이상 새 글을 올릴 수 없음.
- ex) 같은 IP 주소로는 하루에 10개 이상의 계정을 생성할 수 없음.
- 임계치를 넘는 요청은 전부 또는 일부가 처리되지 않고 차단됨.

## 처리율 제한 장치의 이점
- DoS 공격에 의한 자원 고갈 방지: 악의적으로 유발된 요청 폭주로부터 시스템 자원을 보호함.
- 비용 절감: 사용료를 지불해야 하는 서드파티 API 사용 시 호출 횟수를 제한해 비용을 절감함.
- 서버 과부하 방지: 봇 트래픽이나 잘못된 이용 패턴으로 유발된 트래픽을 걸러냄.
- 등급별 트래픽 관리: API 요청 횟수 제한에 따라 사용자를 등급별로 나눠 서비스를 지원함.

## 처리율 제한 알고리즘
처리율 제한 장치를 구현하는 데는 여러 알고리즘이 존재하며, 각기 다른 장단점을 가짐.

토큰 버킷
지정된 용량을 갖는 컨테이너인 버킷에 사전 설정된 양의 토큰이 주기적으로 채워짐.
- 버킷이 가득 차면 추가로 공급되는 토큰은 버려짐.
- 요청이 처리될 때마다 버킷에서 토큰을 하나씩 꺼내며, 남은 토큰이 없으면 요청은 거부됨.
- 파라미터: 버킷 크기, 토큰 공급률
- 필요한 버킷 개수는 제한 기준에 따라 달라짐 (API 엔드포인트별 제한 → 엔드포인트마다 버킷 / IP 주소별 제한 → IP마다 버킷)
- 장점: 구현이 쉽고 메모리 효율적이며, 짧은 시간에 집중되는 트래픽(버스트)도 처리 가능함.
- 단점: 버킷 크기와 토큰 공급률, 두 파라미터를 적절히 튜닝하기가 까다로움.

누출 버킷
토큰 버킷과 유사하지만 요청 처리율이 고정되어 있으며, 보통 FIFO 큐로 구현함.
- 요청 도착 시 큐가 가득 차 있지 않으면 삽입하고, 가득 차 있으면 새 요청은 버림.
- 큐에 담긴 요청은 정해진 속도로만 꺼내어져 처리됨 (선입선출)
- 파라미터: 버킷 크기, 처리율
- 장점: 큐 크기가 고정되어 메모리 효율적이며, 고정된 처리율로 안정적인 출력이 가능함.
- 단점: 단시간에 트래픽이 몰릴 경우 큐에 오래된 요청이 쌓여, 최신 요청이 버려질 수 있음.

고정 윈도우 카운터
타임라인을 고정된 간격의 윈도우로 나누고, 각 윈도우마다 카운터를 붙이는 방식으로 동작함.
- 요청이 접수될 때마다 카운터 값이 1씩 증가함.
- 카운터 값이 임계치에 도달하면 새 윈도우가 열릴 때까지 새로운 요청은 모두 버려짐.
- 장점: 메모리 효율이 우수하고 구현이 매우 쉬움.
- 단점: 윈도우 경계 부근에 트래픽이 몰리면, 실제 허용량의 최대 두 배까지 요청이 통과될 수 있음.

이동 윈도우 로깅
고정 윈도우 카운터의 경계 문제를 해결하기 위해 요청의 타임스탬프를 로그(ex. 레디스 정렬 집합)에 기록하는 방식임.
- 새 요청 도착 시, 현재 윈도우 시작 시점보다 오래된(만료된) 타임스탬프를 제거함.
- 새 요청의 타임스탬프를 로그에 추가함.
- 로그 크기가 허용치 이하면 요청을 허용하고, 초과하면 거부함.
- 장점: 정교하게 계산되어 정확도가 매우 높음.
- 단점: 거부된 요청의 타임스탬프도 로그에 남을 수 있어, 트래픽이 몰릴 때 메모리 사용량이 급격히 늘어날 수 있음.

이동 윈도우 카운터
고정 윈도우 카운터와 이동 윈도우 로깅을 결합한 절충 방식임.
- 계산식: 직전 윈도우 요청 수 × (현재 윈도우에 포함되지 않은 비율) + 현재 윈도우 요청 수
- 이전 시간대의 평균 처리율을 반영해 현재 윈도우 상태를 근사치로 계산함.
- 장점: 순간적인 트래픽 폭증 문제를 완화할 수 있고, 메모리 효율도 좋음.
- 단점: 직전 윈도우에 요청이 균등하게 분포되어 있다고 가정하는 근사치라, 정확도는 다소 느슨함.

## 처리율 제한 장치의 구현 위치
- 클라이언트: 요청이 위조되기 쉬워 신뢰할 수 없는 위치이므로 부적합함.
- 서버: 분산 환경에서 여러 서버가 동시에 상태를 다뤄야 하는 동기화 문제가 발생할 수 있음.
- 미들웨어: API 서버로 가는 요청을 가로채는 별도 계층으로, 처리율 제한을 구현하는 표준적인 방식임.
- 대표 형태는 API 게이트웨이이며, 처리율 제한 외에도 SSL 종단 처리, 사용자 인증, IP 허용 목록 관리 등을 함께 지원함.

## 분산 환경에서의 처리율 제한 이슈
- 경쟁 조건: 여러 요청이 동시에 카운터 값을 읽고 갱신하면서 값이 부정확하게 처리될 수 있음.
    - 해결책: 락은 성능을 크게 떨어뜨리므로, 루아 스크립트나 정렬 집합 같은 자료구조로 원자적 연산을 구현함.
- 동기화 이슈: 여러 대의 처리율 제한 서버가 상태를 공유하지 않으면 정확한 제한이 불가능함.
    - 고정 세션 방식은 확장성이 떨어지고 부하 분산도 어렵게 만듦.
    - 레디스와 같은 중앙 집중형 데이터 저장소를 사용하는 것이 더 나은 해결책임.

## 초과 요청에 대한 처리
- 한도를 넘은 요청에는 HTTP 429(Too Many Requests) 응답을 반환함.
- 상황에 따라 초과 요청을 큐에 담아 나중에 처리하기도 함.
- 응답 헤더에 포함하면 좋은 정보
    - X-Ratelimit-Limit: 윈도우당 허용되는 최대 요청 수
    - X-Ratelimit-Remaining: 윈도우 내에 남아있는 처리 가능 요청 수
    - X-Ratelimit-Retry-After: 한도 제한에 걸리지 않으려면 몇 초 뒤에 재요청해야 하는지 알려주는 값

## 적용 가능 사례 1. CLOVA Speech 호출량 보호
- 최근에 실제로 Free 도메인의 월 무료 인식 시간을 반복 테스트로 전부 소진하는 문제를 겪었다. 책에서 말하는 "사용료를 지불하는 서드파티 API 호출 횟수를 제한해 비용을 절감한다"는 이점이 정확히 이 상황에 해당한다는 것을 알 수 있었다. 유저별로 하루 업로드 횟수를 제한하거나 짧은 시간 내 반복 업로드를 막는 로직을 토큰 버킷 방식으로 구현하면 순간적으로 몰리는 업로드 버스트도 처리하면서 CLOVA 호출량을 통제할 수 있다는 것을 배웠다. 아직 별도의 API 게이트웨이가 없으므로 Spring Interceptor나 Bucket4j 라이브러리를 컨트롤러 앞단에 두고, 한도를 초과하면 기존 공통 응답 형식에 429 상태코드를 추가해 반환하도록 구현하면 될 것 같다.

## 사례 2. 로그인 API 무차별 대입 공격 방지
- POST /api/v1/auth/login은 인증 절차 없이 누구나 호출할 수 있는 API이기 때문에 비밀번호 대입 공격의 대상이 되기 쉽다. 같은 이메일이나 같은 IP를 기준으로 일정 시간 내 로그인 시도 횟수를 제한하면 이런 공격을 효과적으로 막을 수 있다. 이 처리율 제한은 인증 도메인에 속하는 작업이라 타 팀원의 담당 영역이기 때문에 팀 회의에서 로그인 API에 처리율 제한이 필요하다는 점을 요구사항으로 전달해보면 좋을 것 같다.

## 사례 3. 무료 체험 어뷰징 방지와의 연결점
- 예전에 팀원들과 논의했던 주제인데, 회원가입을 반복해서 첫 이용 무료 혜택만 계속 받아가는 문제도 관점을 바꾸면 가입 처리율 제한 문제와 비슷한 것 같다. 책에 나온 "같은 IP 주소로는 하루에 10개 이상의 계정을 생성할 수 없다"는 예시가 이 상황과 정확히 일치한다. 다만 이 문제는 단순히 요청을 차단하는 것이 아니라 무료 혜택 지급 여부를 판단하는 문제이므로, 순수한 처리율 제한 로직만으로는 부족하고 이전에 정리했던 디바이스 해시 기반 판별 로직과 결합해서 해결해보면 좋을 것 같다.
