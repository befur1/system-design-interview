## 처리율 제한 장치란

처리율 제한 장치(Rate Limiter)는 클라이언트 또는 서비스가 보내는 요청의 처리율을 일정 기준 이하로 제한하는 장치다.

다음과 같이 다양한 기준으로 요청을 제한할 수 있다.

- 사용자는 초당 일정 개수 이상의 게시물을 작성할 수 없다.
- 동일한 IP 주소에서는 하루에 생성할 수 있는 계정 수가 제한된다.
- 같은 디바이스에서는 일정 기간 받을 수 있는 보상의 수가 제한된다.

처리율 제한 장치를 사용하면 다음과 같은 이점이 있다.

- **서비스 거부 공격 방지**: 특정 사용자가 지나치게 많은 요청을 보내 서버 자원을 고갈시키는 것을 막는다.
- **비용 절감**: 서버를 과도하게 증설하지 않아도 되며, 호출 횟수에 따라 비용이 발생하는 외부 API의 사용량도 통제할 수 있다.
- **서버 과부하 방지**: 봇이나 잘못 구현된 클라이언트가 보내는 비정상적인 요청을 걸러낸다.
- **공정한 자원 사용**: 일부 사용자가 시스템 자원을 독점하지 못하도록 한다.

## 1단계: 문제 이해 및 설계 범위 확정

처리율 제한 장치를 설계하기 전에 제한 대상과 시스템의 범위를 먼저 확인해야 한다.

다음과 같은 질문을 통해 요구사항을 구체화할 수 있다.

- 클라이언트 측 제한 장치인가, 서버 측 API 처리율 제한 장치인가?
- 요청을 제한하는 기준은 IP 주소, 사용자 ID, 디바이스 ID 중 무엇인가?
- 하나의 기준만 사용하는가, 여러 제한 규칙을 함께 적용하는가?
- 시스템의 요청 규모는 어느 정도인가?
- 처리율 제한 장치는 분산 환경에서 동작해야 하는가?
- 제한된 요청을 단순히 버릴 것인가, 나중에 처리할 수 있도록 큐에 보관할 것인가?
- 클라이언트에 요청 거절 사실과 재시도 시점을 알려야 하는가?

이 장에서 설계하는 처리율 제한 장치의 요구사항은 다음과 같다.

- 설정된 처리율을 정확하게 제한해야 한다.
- 응답 시간이 크게 늘어나서는 안 된다.
- 가능한 한 적은 메모리를 사용해야 한다.
- 여러 서버와 프로세스가 처리율 제한 상태를 공유할 수 있어야 한다.
- 제한된 요청에 대해 명확한 응답을 제공해야 한다.
- 처리율 제한 장치에 장애가 발생하더라도 전체 시스템에 미치는 영향을 최소화해야 한다.

## 2단계: 개략적 설계안 제시

### 처리율 제한 장치는 어디에 둘 것인가

처리율 제한 장치는 다음 위치에 둘 수 있다.

#### 클라이언트 측

클라이언트가 스스로 요청 수를 제한하도록 구현할 수 있다. 하지만 클라이언트 코드는 쉽게 위조되거나 변경될 수 있고, 모든 클라이언트를 통제하기도 어렵다.

따라서 보안이나 서비스 보호를 위한 제한을 클라이언트에만 맡길 수는 없다.

#### 서버 측

웹 서버 또는 애플리케이션 내부에서 요청 수를 검사하고 제한을 초과한 요청을 거절할 수 있다.

Spring 기반 서비스라면 필터, 인터셉터 또는 AOP 등을 이용해 구현할 수 있다. 다만 서버가 여러 대라면 각 서버의 메모리에 저장된 요청 횟수가 서로 다르기 때문에 공통 저장소가 필요하다.

#### 미들웨어 또는 API Gateway

클라이언트와 서버 사이에 처리율 제한 미들웨어를 둘 수도 있다.

클라우드 환경에서는 API Gateway가 처리율 제한뿐 아니라 인증, SSL 종료, IP 허용 목록 등의 기능을 함께 제공하기도 한다.

어디에 배치할지는 다음 조건을 고려해 결정한다.

- 현재 사용하는 기술 스택에서 지원하는 기능
- 처리율 제한 규칙의 복잡도
- 제한 규칙을 변경해야 하는 빈도
- 시스템 규모와 서버 수
- 개발 및 운영에 투입할 수 있는 인력
- API Gateway와 같은 기존 인프라의 유무

처리율을 초과한 요청에는 일반적으로 `HTTP 429 Too Many Requests`를 반환한다.

## 처리율 제한 알고리즘

### 토큰 버킷

토큰 버킷에는 정해진 용량만큼 토큰을 보관할 수 있다. 일정한 속도로 토큰이 추가되며, 버킷이 가득 찬 상태에서 추가되는 토큰은 버려진다.

요청이 도착하면 다음과 같이 처리한다.

1. 버킷에 토큰이 있으면 토큰 하나를 사용하고 요청을 처리한다.
2. 토큰이 없으면 요청을 거절한다.
3. 시간이 지나면 설정된 속도에 따라 토큰이 다시 채워진다.

설정해야 하는 값은 다음 두 가지다.

- 버킷의 최대 크기
- 토큰이 채워지는 속도

장점은 구현이 단순하고 메모리 사용량이 적으며, 버킷에 토큰이 남아 있다면 순간적인 트래픽 증가도 허용할 수 있다는 것이다.

반면 버킷 크기와 토큰 공급률을 적절하게 결정하기 어렵다는 단점이 있다. API별, 사용자별 또는 IP 주소별로 별도의 버킷을 둘 수 있다.

### 누출 버킷

누출 버킷은 요청을 FIFO 큐에 보관하고 일정한 속도로 꺼내 처리한다.

요청이 들어왔을 때 큐에 빈 공간이 있으면 요청을 추가하고, 큐가 가득 차 있으면 새로운 요청을 버린다.

설정해야 하는 값은 다음 두 가지다.

- 큐의 크기
- 요청을 처리하는 속도

출력 속도가 일정하기 때문에 안정된 처리율이 필요한 시스템에 적합하다.

다만 짧은 시간에 많은 요청이 들어오면 오래된 요청이 큐를 차지해 새로운 요청이 거절될 수 있으며, 큐 크기와 처리율을 조정하기 어렵다.

### 고정 윈도 카운터

시간을 일정한 크기의 구간으로 나누고 각 구간마다 요청 수를 기록한다. 현재 구간의 요청 수가 제한값에 도달하면 다음 구간이 시작될 때까지 새로운 요청을 거절한다.

구현이 단순하고 메모리 사용량이 적지만, 구간의 경계에서 제한보다 많은 요청이 통과할 수 있다는 문제가 있다.

예를 들어 분당 100개의 요청을 허용한다면 12시 00분 59초에 100개, 12시 01분 00초에 다시 100개의 요청이 처리될 수 있다. 실제로는 매우 짧은 시간 동안 200개의 요청이 처리되는 셈이다.

### 이동 윈도 로그

각 요청의 타임스탬프를 저장하고 현재 윈도 범위에서 벗어난 타임스탬프를 제거한다. 현재 윈도 안의 요청 수가 제한값보다 작을 때만 요청을 허용한다.

Redis의 정렬 집합과 같은 자료구조를 이용할 수 있다.

정확하게 요청 수를 제한할 수 있다는 장점이 있지만, 거절된 요청의 타임스탬프까지 저장하면 메모리 사용량이 많아질 수 있다.

### 이동 윈도 카운터

고정 윈도 카운터와 이동 윈도 로그의 장점을 결합한 방식이다. 현재 구간의 요청 수와 이전 구간의 요청 수에 가중치를 적용해 현재 윈도의 요청 수를 추정한다.

계산 방식은 다음과 같다.

`현재 구간의 요청 수 + 이전 구간의 요청 수 × 이전 구간이 현재 범위와 겹치는 비율`

예를 들어 현재 구간의 30%가 지났고, 이전 구간에 5개, 현재 구간에 3개의 요청이 있었다면 `3 + 5 × 70% = 6.5`로 계산한다.

근삿값을 사용하므로 아주 작은 오차가 생길 수 있지만, 메모리 사용량이 적고 경계 부근의 트래픽 폭증 문제를 완화할 수 있다.

### 알고리즘 비교

| 알고리즘 | 장점 | 단점 | 적합한 상황 |
| :--- | :--- | :--- | :--- |
| 토큰 버킷 | 단순하고 순간적인 트래픽을 허용할 수 있음 | 버킷 크기와 공급률 조정이 어려움 | 일정 수준의 버스트를 허용하는 API |
| 누출 버킷 | 출력 처리율을 일정하게 유지함 | 트래픽 폭증 시 오래된 요청이 큐를 차지함 | 일정한 처리 속도가 중요한 작업 |
| 고정 윈도 카운터 | 구현이 단순하고 메모리 사용량이 적음 | 윈도 경계에서 제한을 초과할 수 있음 | 엄격한 정확도가 필요하지 않은 단순 제한 |
| 이동 윈도 로그 | 처리율 제한이 정확함 | 요청 타임스탬프 저장으로 메모리 사용량이 큼 | 정확한 제한이 중요한 API |
| 이동 윈도 카운터 | 메모리 효율과 정확도의 균형이 좋음 | 근삿값으로 인한 작은 오차가 존재함 | 대규모 트래픽의 일반적인 처리율 제한 |

## 처리율 제한 장치의 개략적 구조

처리율 제한 장치는 사용자 ID, IP 주소 또는 API 엔드포인트별 요청 횟수를 저장해야 한다.

디스크 기반 데이터베이스는 요청마다 읽기와 쓰기가 발생해 느릴 수 있으므로 빠른 접근과 만료 기능을 제공하는 Redis와 같은 인메모리 저장소가 적합하다.

Redis에서는 다음 명령을 활용할 수 있다.

- `INCR`: 카운터 값을 증가시킨다.
- `EXPIRE`: 카운터의 만료 시간을 설정한다.

기본 처리 흐름은 다음과 같다.

1. 클라이언트가 요청을 보낸다.
2. 처리율 제한 미들웨어가 제한 규칙을 조회한다.
3. Redis에서 해당 사용자 또는 IP의 현재 요청 횟수를 확인한다.
4. 제한을 초과하지 않았다면 카운터를 증가시키고 API 서버로 요청을 전달한다.
5. 제한을 초과했다면 요청을 거절하고 `HTTP 429`를 반환한다.

## 3단계: 상세 설계

### 처리율 제한 규칙

처리율 제한 규칙은 코드에 직접 작성하기보다 별도의 설정 파일이나 규칙 저장소에서 관리할 수 있다.

예를 들어 다음과 같은 규칙을 둘 수 있다.

- 특정 메시지는 사용자당 하루에 최대 5회 전송할 수 있다.
- 로그인 시도는 사용자 또는 IP 주소당 1분에 최대 5회 허용한다.
- 외부 API 호출은 서비스 계약에서 허용한 호출량 이하로 제한한다.

작업 프로세스가 규칙을 주기적으로 읽어 캐시에 저장하면 처리율 제한 장치는 요청마다 원본 저장소를 조회하지 않고 캐시된 규칙을 사용할 수 있다.

### 제한된 요청의 처리

단순 조회 요청처럼 나중에 처리할 필요가 없는 요청은 즉시 거절할 수 있다.

반면 주문 처리나 중요한 비동기 작업처럼 요청을 잃어서는 안 되는 경우에는 메시지 큐에 저장한 뒤 나중에 처리하는 방법을 고려할 수 있다.

처리율 제한 장치가 모든 요청을 무조건 버려야 하는 것은 아니다.

클라이언트가 현재 제한 상태를 알 수 있도록 응답 헤더에 다음 정보를 포함할 수 있다.

- 남아 있는 요청 횟수
- 적용된 요청 제한값
- 다시 요청할 수 있는 시점 또는 대기 시간

책에서는 다음과 같은 헤더를 소개한다.

- `X-Ratelimit-Remaining`
- `X-Ratelimit-Limit`
- `X-Ratelimit-Retry-After`

실제 구현에서는 사용하는 API 규약에 맞춰 `Retry-After` 또는 `RateLimit-*` 헤더 사용 여부도 확인해야 한다.

### 경쟁 조건

여러 요청이 동시에 들어오면 다음과 같은 경쟁 조건이 발생할 수 있다.

1. 두 요청이 동일한 카운터 값을 읽는다.
2. 두 요청 모두 아직 제한에 도달하지 않았다고 판단한다.
3. 각 요청이 카운터를 증가시킨다.
4. 실제보다 적은 값이 저장되거나 제한보다 많은 요청이 허용된다.

단순히 락을 사용하면 경쟁 조건은 해결할 수 있지만 처리 성능이 낮아질 수 있다.

Redis Lua 스크립트를 사용해 조회·검사·증가 연산을 원자적으로 처리하거나 Redis 정렬 집합을 사용하는 방법을 고려할 수 있다.

### 동기화 문제

처리율 제한 서버가 여러 대라면 각 서버가 서로 다른 카운터를 가지고 있어서는 안 된다.

특정 사용자의 요청을 항상 같은 서버로 보내는 고정 세션을 사용할 수도 있지만, 서버의 추가·제거가 어려워지고 확장성이 떨어진다.

따라서 여러 처리율 제한 서버가 Redis와 같은 중앙 집중형 저장소를 공유하는 방식이 일반적이다.

여러 데이터센터에서 하나의 처리율 제한 정책을 적용하면 지역 간 네트워크 지연과 데이터 동기화 문제가 발생한다.

모든 지역의 요청 수를 매번 강한 일관성으로 동기화하면 정확도는 높아지지만 응답 시간이 증가한다. 따라서 서비스의 성격에 따라 지역별 제한을 두거나 약간의 오차를 허용하는 최종적 일관성을 사용할 수 있다.

### 성능 최적화

사용자와 처리율 제한 장치 사이의 물리적 거리가 멀면 매 요청마다 네트워크 지연이 발생한다. 가능한 경우 사용자와 가까운 에지 서버 또는 데이터센터에서 요청을 제한하는 것이 좋다.

다만 여러 지역에서 동일한 제한값을 공유해야 한다면 다음 요소 사이에서 균형을 잡아야 한다.

- 전역적으로 정확한 처리율 제한
- 낮은 응답 지연
- 데이터 동기화 비용
- 장애 발생 시 가용성

### 모니터링

처리율 제한 장치를 도입한 뒤에는 알고리즘과 제한 규칙이 실제 트래픽에 적합한지 확인해야 한다.

다음과 같은 지표를 관찰할 수 있다.

- API별 전체 요청 수
- 허용된 요청과 거절된 요청의 수
- `HTTP 429` 응답 비율
- 사용자 또는 IP별 제한 규칙 적중 횟수
- Redis 응답 시간과 오류율
- 특정 키에 요청이 집중되는 핫키 현상
- 정상 사용자가 지나치게 자주 제한되는지 여부
- 재시도로 인해 요청량이 더 증가하는지 여부

정상적인 사용자가 자주 차단된다면 제한값이 너무 엄격할 수 있다. 반대로 트래픽 폭증을 막지 못한다면 알고리즘이나 제한값을 다시 검토해야 한다.

## 4단계: 마무리

### 경성 제한과 연성 제한

- **경성 처리율 제한**: 요청 수가 제한값을 절대로 넘을 수 없다.
- **연성 처리율 제한**: 짧은 시간 동안 제한값을 일부 초과하는 것을 허용한다.

결제, 보상 지급 또는 외부 API 비용 통제처럼 초과를 허용하기 어려운 기능에는 경성 제한이 적합하다.

일반적인 콘텐츠 조회처럼 순간적인 요청 증가를 허용해도 되는 기능에는 연성 제한을 고려할 수 있다.

### 여러 계층에서의 처리율 제한

이 장에서는 HTTP 요청을 다루는 애플리케이션 계층의 처리율 제한을 중심으로 살펴봤다.

하지만 네트워크 계층에서도 IP 주소를 기준으로 요청을 제한할 수 있다. 실제 시스템에서는 네트워크 방화벽, 로드밸런서, API Gateway, 애플리케이션 등 여러 계층의 제한을 조합할 수 있다.

### 클라이언트의 대응

클라이언트도 처리율 제한을 고려해 설계해야 한다.

- 불필요한 API 호출을 줄이고 캐시를 활용한다.
- 서버가 제공하는 제한값과 재시도 시점을 확인한다.
- `HTTP 429`를 정상적인 예외 상황으로 처리한다.
- 재시도할 때 충분한 백오프 시간을 둔다.
- 여러 클라이언트가 동시에 재시도하지 않도록 지터를 추가할 수 있다.

## 마무리

### 사용자별 일일 사용 횟수 제한은 처리율 제한과 무엇이 다를까?

기존 프로젝트에서 특정 기능을 사용자별로 하루 3회까지만 사용할 수 있도록 구현한 경험이 있다. 이 기능도 요청 횟수를 제한한다는 점에서는 처리율 제한과 비슷하지만 목적에는 차이가 있다.

- 일일 사용 횟수 제한은 상품 정책이나 비용 통제를 위한 **사용량 제한(Quota)**에 가깝다.
- 초당 요청 수 제한은 서버 보호를 위한 **처리율 제한(Rate Limiting)**에 가깝다.

사용자와 트래픽이 적을 때는 데이터베이스에 사용 횟수를 기록하는 방식도 가능하다. 하지만 모든 요청을 검사해야 하고 서버가 여러 대로 확장된다면, Redis와 같은 공통 인메모리 저장소에서 카운터를 관리하는 편이 적합하다.

다만 결제 금액이나 유료 사용권처럼 반드시 보존해야 하는 사용량은 Redis에만 저장하기보다 데이터베이스에도 기록해야 한다.

### 처리율 제한 장치를 서버 내부에 둘지 미들웨어에 둘지는 프로그래밍 언어의 성능으로 결정될까?

프로그래밍 언어의 성능은 여러 판단 기준 중 하나일 뿐이다. Java, JavaScript, Python과 같은 일반적인 서버 언어로도 처리율 제한 장치를 충분히 구현할 수 있다.

실제로는 언어보다 다음 사항이 더 중요하다.

- 여러 서버가 카운터를 공유할 수 있는가?
- 카운터를 원자적으로 변경할 수 있는가?
- 모든 서비스에 같은 정책을 적용해야 하는가?
- 처리율 제한으로 인해 요청 지연이 얼마나 증가하는가?
- 정책을 얼마나 자주 변경해야 하는가?

미들웨어나 API Gateway를 사용하는 주된 이유는 언어의 성능이 부족해서가 아니라, 여러 서비스에 적용되는 인증과 처리율 제한 등의 공통 정책을 한곳에서 관리하기 위해서다.

### 서버 외부의 처리율 제한 장치는 반드시 제3자 서비스를 사용해야 할까?

서버 외부의 처리율 제한 장치도 직접 구축할 수 있다.

- 애플리케이션 내부: Spring Filter, Interceptor, AOP
- 자체 미들웨어: 별도의 처리율 제한 서비스
- 자체 운영 Gateway: Spring Cloud Gateway, Kong
- 프록시 계층: Nginx, Envoy
- 관리형 서비스: AWS API Gateway, Cloudflare

애플리케이션 내부에서는 사용자 등급이나 기능별 제한처럼 비즈니스 규칙을 세밀하게 적용하기 쉽다. Gateway에서는 IP, API 경로, HTTP 메서드와 같은 공통 기준을 여러 서비스에 일괄 적용하기 좋다.

실제 시스템에서는 Gateway에서 기본적인 제한을 적용하고, 애플리케이션에서 추가적인 비즈니스 제한을 적용하는 방식도 사용할 수 있다.

### 처리율 제한 알고리즘은 간단해 보이는데 직접 서비스를 만드는 데 왜 시간이 많이 들까?

카운터를 증가시키거나 토큰을 차감하는 알고리즘 자체는 비교적 간단하다. 어려운 부분은 이를 분산 환경에서 안정적으로 운영하는 것이다.

직접 구축하려면 다음 문제를 해결해야 한다.

- 사용자, IP, API별 제한 규칙 관리
- 여러 서버가 공유하는 카운터 저장소
- 동시 요청에 대한 원자성 보장
- Redis와 네트워크 장애 대응
- 여러 데이터센터의 카운터 동기화
- 제한 규칙 변경과 배포
- `429 Too Many Requests` 응답 처리
- 정상 사용자가 잘못 차단되는지 모니터링
- 특정 카운터에 요청이 집중되는 핫키 대응

따라서 알고리즘 구현보다 장애 대응, 모니터링, 설정 관리와 같은 운영 기능을 만드는 데 더 많은 시간이 든다.

### 토큰 버킷의 버킷 크기와 토큰 공급률은 왜 조정하기 어려울까?

토큰 공급률은 장시간 유지할 수 있는 평균 요청 처리율이고, 버킷 크기는 짧은 시간 동안 허용할 순간 최대 요청량이다.

예를 들어 초당 100개의 토큰을 공급하고 버킷 크기를 200으로 설정하면, 토큰이 충분히 쌓여 있을 때는 순간적으로 200개의 요청이 통과할 수 있다. 이후에는 평균적으로 초당 100개 수준으로 제한된다.

버킷이 너무 크면 순간적으로 많은 요청이 통과해 하위 서버나 데이터베이스가 과부하될 수 있다. 반대로 너무 작으면 앱 실행 직후 여러 API를 호출하는 것과 같은 정상적인 요청까지 거절될 수 있다.

따라서 하위 시스템의 처리 용량, 실제 트래픽의 순간 최대치, 정상 사용자의 요청 패턴과 허용 가능한 버스트를 바탕으로 두 값을 조정해야 한다.

### 누출 버킷의 일정한 출력 속도는 어떤 시스템에 유용할까?

누출 버킷은 요청이 불규칙하게 들어와도 하위 시스템에는 일정한 속도로 전달한다.

다음과 같은 작업에 적합하다.

- 이메일이나 SMS 전송
- 이미지 및 동영상 변환
- 외부 결제 API 호출
- 로그 수집 및 저장
- 데이터베이스 쓰기 요청 보호
- 처리 능력이 일정한 작업 서버

예를 들어 이미지 처리 서버가 초당 10개의 작업만 안정적으로 처리할 수 있다면, 요청이 순간적으로 100개 들어와도 큐에 보관한 뒤 초당 10개씩 전달할 수 있다.

다만 큐가 가득 찼을 때 요청을 버릴 것인지, 대기를 안내할 것인지, 영속적인 메시지 큐로 넘길 것인지도 함께 결정해야 한다.

### 처리율 제한 카운터에는 왜 데이터베이스보다 Redis가 적합할까?

처리율 제한은 거의 모든 요청의 앞단에서 실행되기 때문에 카운터 저장소가 느리면 전체 API의 응답도 느려진다.

Redis가 적합한 이유는 다음과 같다.

- 데이터를 메모리에서 빠르게 읽고 쓸 수 있다.
- `INCR`과 같은 원자적 카운터 연산을 제공한다.
- TTL과 `EXPIRE`를 이용해 일정 시간이 지난 카운터를 자동으로 제거할 수 있다.
- 몇 초 또는 몇 분만 필요한 임시 데이터를 저장하기에 적합하다.

데이터베이스가 반드시 디스크를 매번 직접 읽는 것은 아니다. 데이터베이스도 버퍼 풀을 사용하지만, 트랜잭션과 영속성 보장, 로그 기록, 인덱스 관리, 행 잠금 등의 추가 비용이 있다.

따라서 초당 요청 수처럼 고빈도로 변경되는 임시 카운터에는 Redis가 적합하다. 반면 결제나 유료 사용권처럼 반드시 보존해야 하는 사용량은 데이터베이스에 별도로 기록하는 것이 안전하다.

### Redis의 `INCR`이 원자적이어도 경쟁 조건이 발생할 수 있을까?

`INCR` 명령 하나는 원자적으로 실행된다. 여러 요청이 동시에 같은 키를 증가시켜도 증가 연산 자체가 중간에 섞이지 않는다.

하지만 실제 처리율 제한은 다음과 같이 여러 단계로 이루어질 수 있다.

1. 현재 요청 수를 조회한다.
2. 제한값을 넘었는지 검사한다.
3. 카운터를 증가시킨다.
4. 만료 시간을 설정한다.

각 단계를 별도의 명령으로 실행하면 명령 사이에 다른 요청이 끼어들어 경쟁 조건이 생길 수 있다.

따라서 여러 명령을 Redis Lua 스크립트로 묶어 하나의 원자적인 작업으로 실행해야 한다. 스크립트가 실행되는 동안 다른 명령은 중간에 끼어들 수 없다.

다만 긴 Lua 스크립트는 Redis의 다른 작업까지 지연시킬 수 있으므로 짧고 단순하게 작성해야 한다.

### 락은 왜 처리율 제한 장치의 성능을 떨어뜨릴까?

락을 사용하면 같은 카운터를 변경하려는 요청 중 하나만 작업할 수 있고 나머지 요청은 락이 해제될 때까지 기다려야 한다.

분산 락을 사용하면 락 획득, 카운터 조회와 변경, 락 해제 과정에서 여러 번의 네트워크 통신이 필요하다. 트래픽이 많을수록 락을 기다리는 요청도 늘어나 병목이 커진다.

또한 락을 획득한 서버가 장애를 일으키는 상황에 대비해 락 만료 시간과 재시도 정책도 관리해야 한다.

처리율 제한처럼 모든 요청이 통과하는 경로에서는 분산 락보다 Redis의 원자적 명령이나 Lua 스크립트를 사용하는 편이 일반적으로 효율적이다.

### 정렬 집합은 이동 윈도 처리율 제한에 어떻게 사용될까?

Redis의 정렬 집합은 요청이 발생한 시각을 점수로 저장할 수 있다.

이동 윈도 로그는 다음과 같이 구현할 수 있다.

1. 현재 윈도보다 오래된 요청 기록을 제거한다.
2. 현재 윈도 안에 남아 있는 요청 수를 확인한다.
3. 제한을 넘지 않았다면 현재 요청 시각을 추가한다.

이 방식은 최근 1분처럼 현재 시점을 기준으로 정확한 요청 수를 계산할 수 있다.

다만 정렬 집합을 사용한다고 경쟁 조건이 자동으로 해결되는 것은 아니다. 오래된 기록 제거, 요청 수 확인, 현재 요청 추가를 각각 실행하면 사이에 다른 요청이 들어올 수 있으므로 이 연산들도 Lua 스크립트 등으로 묶어야 한다.

### 중앙 Redis는 여러 서버의 카운터 동기화 문제를 어떻게 해결할까?

각 서버가 자신의 메모리에 카운터를 저장하면 요청 횟수가 서버별로 나뉜다.

예를 들어 1분당 5회 제한인데 요청이 서버 A, B, C에 각각 3회씩 전달되면 각 서버는 제한을 넘지 않았다고 판단한다. 결과적으로 총 9개의 요청이 통과할 수 있다.

중앙 Redis를 사용하면 어느 웹 서버가 요청을 받더라도 동일한 `user:123:counter` 키를 확인한다. 웹 서버는 카운터 상태를 보관하지 않는 무상태 서버가 되고, Redis가 모든 서버가 공유하는 논리적인 단일 진실 공급원이 된다.

여기서 중앙 집중형이라는 말이 반드시 Redis 한 대만 사용한다는 뜻은 아니다. Redis Sentinel, 복제본 또는 Redis Cluster를 사용해 장애 복구와 확장을 지원할 수 있다.

### 여러 데이터센터의 처리율 제한 장치가 최종적 일관성을 사용한다는 것은 무슨 뜻일까?

여러 데이터센터가 각자 카운터를 관리하고 변경 사항을 비동기적으로 전달하면, 한 지역에서 증가한 카운터가 다른 지역에 즉시 반영되지 않을 수 있다.

예를 들어 전역 제한이 100회인데 서울에서 60회, 미국에서 60회를 허용하면 동기화 전에는 총 120회의 요청이 통과할 수 있다. 시간이 지나면 카운터 상태는 같아지지만 일시적으로 제한값을 초과하는 것이다.

최종적 일관성을 사용하면 지역 간 통신을 기다리지 않아도 되므로 응답이 빠르고 한 지역의 장애가 다른 지역으로 전파될 가능성이 줄어든다. 반면 완벽하게 정확한 전역 제한은 보장하기 어렵다.

일반 조회 API는 약간의 초과를 허용할 수 있지만, 결제·보상·유료 사용권은 중앙 조정이나 강한 일관성이 필요할 수 있다.

### 깜짝 세일과 같은 순간적인 트래픽에는 왜 토큰 버킷이 적합할까?

토큰 버킷은 요청이 적은 동안 토큰을 미리 저장해 두기 때문에 짧은 시간 동안 발생한 정상적인 트래픽 증가를 일정 범위까지 허용할 수 있다. 동시에 토큰 공급률을 통해 장기적인 평균 요청량은 제한한다.

다른 알고리즘과 비교하면 다음과 같다.

- 고정 윈도 카운터는 윈도 경계에서 요청이 과도하게 통과할 수 있다.
- 이동 윈도 로그는 정확하지만 요청 기록을 많이 저장한다.
- 누출 버킷은 출력이 안정적이지만 순간 요청이 큐에서 오래 대기하거나 버려질 수 있다.
- 토큰 버킷은 제한된 범위의 버스트를 허용하면서 장기 평균 처리율을 통제한다.

다만 깜짝 세일이라고 무조건 토큰 버킷이 정답은 아니다. 하위 결제 서버나 데이터베이스에 일정한 속도로만 요청을 전달해야 한다면 누출 버킷이나 메시지 큐가 더 적합할 수 있다.

또한 처리율 제한만으로 재고 정합성은 보장되지 않으므로 원자적 재고 차감과 멱등성도 함께 고려해야 한다.

### 경성 처리율 제한과 연성 처리율 제한의 차이는 무엇일까?

경성 처리율 제한은 요청 수가 제한값을 절대로 넘지 못하게 한다.

외부 API의 계약상 호출 한도, 유료 사용권, 보상 지급, 결제 시도와 같이 제한 초과가 비용이나 데이터 오류로 이어지는 기능에 적합하다.

연성 처리율 제한은 짧은 시간 동안 제한값을 약간 초과하는 것을 허용한다.

일반 게시물 조회, 검색, 피드 요청과 같이 일시적인 초과보다 사용자 경험과 가용성이 중요한 기능에 적합하다.

경성 제한은 정확도가 높지만 여러 서버와 데이터센터의 카운터를 강하게 동기화해야 하므로 지연과 운영 비용이 커질 수 있다.

### 처리율 제한을 이해하려면 OSI 7계층과 5계층 중 무엇을 알아야 할까?

실제 인터넷 구현과 네트워크 수업에서는 TCP/IP 기반 5계층 구조를 많이 사용한다. OSI 7계층은 네트워크 기능을 더 세부적으로 나눈 개념적 모델로 활용된다.

처리율 제한에서는 모든 계층을 외우기보다 제한이 어디에서 적용되는지 구분하는 것이 중요하다.

- 응용 계층: 사용자 ID, API 경로, HTTP 메서드별 제한
- 전송 계층: TCP 연결이나 포트 기준 제한
- 네트워크 계층: IP 주소 기준 제한

시스템 설계에서는 특히 L4 로드밸런서와 L7 로드밸런서의 차이를 설명할 수 있는 정도로 이해하는 것이 좋다.

### 클라이언트 캐시로 API 호출 횟수를 줄인다는 것은 무슨 뜻일까?

클라이언트가 이미 받은 데이터를 일정 시간 보관하고, 같은 데이터가 다시 필요할 때 서버에 요청하지 않고 저장된 값을 사용하는 것이다.

예를 들어 프로필 정보를 한 번 조회한 뒤 3분 동안 앱 메모리에 저장하면 화면을 다시 열 때마다 `GET /users/me`를 호출하지 않아도 된다. 불필요한 네트워크 요청이 줄어들기 때문에 처리율 제한에 도달할 가능성도 낮아진다.

브라우저 HTTP 캐시, LocalStorage, IndexedDB, 모바일 앱 내부 저장소 등을 사용할 수 있다. 다만 잔액이나 재고처럼 최신성이 중요한 데이터는 오래 캐시하면 안 된다.

또한 처리율 제한 카운터 자체를 클라이언트에 저장해서는 안 된다. 클라이언트의 값은 사용자가 조작할 수 있기 때문이다.

### 캐시는 시스템의 어느 위치에나 둘 수 있을까?

캐시는 클라이언트, CDN, 프록시, 애플리케이션 서버, Redis, 데이터베이스 내부 등 다양한 위치에 둘 수 있다. 그러나 아무 위치에나 두는 것은 아니다.

- 클라이언트 캐시는 가장 빠르지만 서버가 즉시 무효화하기 어렵다.
- CDN은 정적 콘텐츠를 사용자 가까이에서 제공하기 좋다.
- 서버 내부 캐시는 매우 빠르지만 서버별 값이 달라질 수 있다.
- Redis는 여러 서버가 같은 데이터를 공유하기 좋다.
- 데이터베이스의 버퍼 풀은 자주 사용하는 데이터 페이지를 메모리에 보관한다.

캐시 위치는 데이터 변경 빈도, 공유 범위, 일관성 요구사항, 사용자와의 거리, 장애 시 원본 복구 가능성을 바탕으로 결정해야 한다.

### 개발자가 직접 구현할 수 있는 것은 클라이언트 예외 처리뿐일까?

처리율 제한 장치와 Redis 연동도 백엔드 개발자가 직접 구현할 수 있다.

Spring 기반 프로젝트에서는 다음과 같이 구현해볼 수 있다.

1. Filter 또는 Interceptor에서 사용자 ID나 IP 주소를 추출한다.
2. 요청마다 Redis의 제한 키를 확인한다.
3. 제한을 초과하면 `HTTP 429`를 반환한다.
4. 여러 Redis 명령이 필요하면 Lua 스크립트로 묶는다.
5. 응답에 남은 요청 수와 재시도 시점을 포함한다.
6. 허용·거절 횟수와 Redis 오류를 모니터링한다.

직접 알고리즘을 작성하지 않고 Bucket4j, Spring Cloud Gateway의 Redis RateLimiter, Nginx, Envoy 또는 AWS API Gateway를 사용할 수도 있다.

외부 API를 호출하는 클라이언트 입장에서는 상대방의 처리율 제한 정책을 변경할 수 없으므로 `429` 응답 처리, `Retry-After` 준수, 지수 백오프와 지터, 최대 재시도 횟수 제한 등을 구현해야 한다.

즉, 클라이언트의 예외 처리는 외부 제한에 대응하는 코드이고 서버 측 처리율 제한 장치는 자신의 서버를 보호하기 위한 코드다. 둘 다 개발자가 구현할 수 있는 범위다.
