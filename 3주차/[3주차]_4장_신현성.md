## 처리율 제한 장치란

처리율 제한 장치(Rate Limiter)는 클라이언트 또는 서비스가 보내는 요청의 처리율을 일정 기준 이하로 제한하는 장치다.

다음과 같이 다양한 기준으로 요청을 제한할 수 있다.

- 사용자는 초당 일정 개수 이상의 게시물을 작성할 수 없다.
- 동일한 IP 주소에서는 하루에 생성할 수 있는 계정 수가 제한된다.
- 같은 디바이스에서는 일정 기간 받을 수 있는 보상의 수가 제한된다.

처리율 제한 장치를 사용하면 다음과 같은 이점이 있다.

- **서비스 거부 공격 방지**: 특정 사용자가 지나치게 많은 요청을 보내 서버 자원을 고갈시키는 것을 막는다.
- **비용 절감**: 서버를 과도하게 증설하지 않아도 되며, 호출 횟수에 따라 비용이 발생하는 외부 API의 사용량도 통제할 수 있다.
- **서버 과부하 방지**: 봇이나 잘못 구현된 클라이언트가 보내는 비정상적인 요청을 걸러낸다.
- **공정한 자원 사용**: 일부 사용자가 시스템 자원을 독점하지 못하도록 한다.

## 1단계: 문제 이해 및 설계 범위 확정

처리율 제한 장치를 설계하기 전에 제한 대상과 시스템의 범위를 먼저 확인해야 한다.

다음과 같은 질문을 통해 요구사항을 구체화할 수 있다.

- 클라이언트 측 제한 장치인가, 서버 측 API 처리율 제한 장치인가?
- 요청을 제한하는 기준은 IP 주소, 사용자 ID, 디바이스 ID 중 무엇인가?
- 하나의 기준만 사용하는가, 여러 제한 규칙을 함께 적용하는가?
- 시스템의 요청 규모는 어느 정도인가?
- 처리율 제한 장치는 분산 환경에서 동작해야 하는가?
- 제한된 요청을 단순히 버릴 것인가, 나중에 처리할 수 있도록 큐에 보관할 것인가?
- 클라이언트에 요청 거절 사실과 재시도 시점을 알려야 하는가?

이 장에서 설계하는 처리율 제한 장치의 요구사항은 다음과 같다.

- 설정된 처리율을 정확하게 제한해야 한다.
- 응답 시간이 크게 늘어나서는 안 된다.
- 가능한 한 적은 메모리를 사용해야 한다.
- 여러 서버와 프로세스가 처리율 제한 상태를 공유할 수 있어야 한다.
- 제한된 요청에 대해 명확한 응답을 제공해야 한다.
- 처리율 제한 장치에 장애가 발생하더라도 전체 시스템에 미치는 영향을 최소화해야 한다.

## 2단계: 개략적 설계안 제시

### 처리율 제한 장치는 어디에 둘 것인가

처리율 제한 장치는 다음 위치에 둘 수 있다.

#### 클라이언트 측

클라이언트가 스스로 요청 수를 제한하도록 구현할 수 있다. 하지만 클라이언트 코드는 쉽게 위조되거나 변경될 수 있고, 모든 클라이언트를 통제하기도 어렵다.

따라서 보안이나 서비스 보호를 위한 제한을 클라이언트에만 맡길 수는 없다.

#### 서버 측

웹 서버 또는 애플리케이션 내부에서 요청 수를 검사하고 제한을 초과한 요청을 거절할 수 있다.

Spring 기반 서비스라면 필터, 인터셉터 또는 AOP 등을 이용해 구현할 수 있다. 다만 서버가 여러 대라면 각 서버의 메모리에 저장된 요청 횟수가 서로 다르기 때문에 공통 저장소가 필요하다.

#### 미들웨어 또는 API Gateway

클라이언트와 서버 사이에 처리율 제한 미들웨어를 둘 수도 있다.

클라우드 환경에서는 API Gateway가 처리율 제한뿐 아니라 인증, SSL 종료, IP 허용 목록 등의 기능을 함께 제공하기도 한다.

어디에 배치할지는 다음 조건을 고려해 결정한다.

- 현재 사용하는 기술 스택에서 지원하는 기능
- 처리율 제한 규칙의 복잡도
- 제한 규칙을 변경해야 하는 빈도
- 시스템 규모와 서버 수
- 개발 및 운영에 투입할 수 있는 인력
- API Gateway와 같은 기존 인프라의 유무

처리율을 초과한 요청에는 일반적으로 `HTTP 429 Too Many Requests`를 반환한다.

## 처리율 제한 알고리즘

### 토큰 버킷

토큰 버킷에는 정해진 용량만큼 토큰을 보관할 수 있다. 일정한 속도로 토큰이 추가되며, 버킷이 가득 찬 상태에서 추가되는 토큰은 버려진다.

요청이 도착하면 다음과 같이 처리한다.

1. 버킷에 토큰이 있으면 토큰 하나를 사용하고 요청을 처리한다.
2. 토큰이 없으면 요청을 거절한다.
3. 시간이 지나면 설정된 속도에 따라 토큰이 다시 채워진다.

설정해야 하는 값은 다음 두 가지다.

- 버킷의 최대 크기
- 토큰이 채워지는 속도

장점은 구현이 단순하고 메모리 사용량이 적으며, 버킷에 토큰이 남아 있다면 순간적인 트래픽 증가도 허용할 수 있다는 것이다.

반면 버킷 크기와 토큰 공급률을 적절하게 결정하기 어렵다는 단점이 있다. API별, 사용자별 또는 IP 주소별로 별도의 버킷을 둘 수 있다.

### 누출 버킷

누출 버킷은 요청을 FIFO 큐에 보관하고 일정한 속도로 꺼내 처리한다.

요청이 들어왔을 때 큐에 빈 공간이 있으면 요청을 추가하고, 큐가 가득 차 있으면 새로운 요청을 버린다.

설정해야 하는 값은 다음 두 가지다.

- 큐의 크기
- 요청을 처리하는 속도

출력 속도가 일정하기 때문에 안정된 처리율이 필요한 시스템에 적합하다.

다만 짧은 시간에 많은 요청이 들어오면 오래된 요청이 큐를 차지해 새로운 요청이 거절될 수 있으며, 큐 크기와 처리율을 조정하기 어렵다.

### 고정 윈도 카운터

시간을 일정한 크기의 구간으로 나누고 각 구간마다 요청 수를 기록한다. 현재 구간의 요청 수가 제한값에 도달하면 다음 구간이 시작될 때까지 새로운 요청을 거절한다.

구현이 단순하고 메모리 사용량이 적지만, 구간의 경계에서 제한보다 많은 요청이 통과할 수 있다는 문제가 있다.

예를 들어 분당 100개의 요청을 허용한다면 12시 00분 59초에 100개, 12시 01분 00초에 다시 100개의 요청이 처리될 수 있다. 실제로는 매우 짧은 시간 동안 200개의 요청이 처리되는 셈이다.

### 이동 윈도 로그

각 요청의 타임스탬프를 저장하고 현재 윈도 범위에서 벗어난 타임스탬프를 제거한다. 현재 윈도 안의 요청 수가 제한값보다 작을 때만 요청을 허용한다.

Redis의 정렬 집합과 같은 자료구조를 이용할 수 있다.

정확하게 요청 수를 제한할 수 있다는 장점이 있지만, 거절된 요청의 타임스탬프까지 저장하면 메모리 사용량이 많아질 수 있다.

### 이동 윈도 카운터

고정 윈도 카운터와 이동 윈도 로그의 장점을 결합한 방식이다. 현재 구간의 요청 수와 이전 구간의 요청 수에 가중치를 적용해 현재 윈도의 요청 수를 추정한다.

계산 방식은 다음과 같다.

`현재 구간의 요청 수 + 이전 구간의 요청 수 × 이전 구간이 현재 범위와 겹치는 비율`

예를 들어 현재 구간의 30%가 지났고, 이전 구간에 5개, 현재 구간에 3개의 요청이 있었다면 `3 + 5 × 70% = 6.5`로 계산한다.

근삿값을 사용하므로 아주 작은 오차가 생길 수 있지만, 메모리 사용량이 적고 경계 부근의 트래픽 폭증 문제를 완화할 수 있다.

### 알고리즘 비교

| 알고리즘 | 장점 | 단점 | 적합한 상황 |
| :--- | :--- | :--- | :--- |
| 토큰 버킷 | 단순하고 순간적인 트래픽을 허용할 수 있음 | 버킷 크기와 공급률 조정이 어려움 | 일정 수준의 버스트를 허용하는 API |
| 누출 버킷 | 출력 처리율을 일정하게 유지함 | 트래픽 폭증 시 오래된 요청이 큐를 차지함 | 일정한 처리 속도가 중요한 작업 |
| 고정 윈도 카운터 | 구현이 단순하고 메모리 사용량이 적음 | 윈도 경계에서 제한을 초과할 수 있음 | 엄격한 정확도가 필요하지 않은 단순 제한 |
| 이동 윈도 로그 | 처리율 제한이 정확함 | 요청 타임스탬프 저장으로 메모리 사용량이 큼 | 정확한 제한이 중요한 API |
| 이동 윈도 카운터 | 메모리 효율과 정확도의 균형이 좋음 | 근삿값으로 인한 작은 오차가 존재함 | 대규모 트래픽의 일반적인 처리율 제한 |

## 처리율 제한 장치의 개략적 구조

처리율 제한 장치는 사용자 ID, IP 주소 또는 API 엔드포인트별 요청 횟수를 저장해야 한다.

디스크 기반 데이터베이스는 요청마다 읽기와 쓰기가 발생해 느릴 수 있으므로 빠른 접근과 만료 기능을 제공하는 Redis와 같은 인메모리 저장소가 적합하다.

Redis에서는 다음 명령을 활용할 수 있다.

- `INCR`: 카운터 값을 증가시킨다.
- `EXPIRE`: 카운터의 만료 시간을 설정한다.

기본 처리 흐름은 다음과 같다.

1. 클라이언트가 요청을 보낸다.
2. 처리율 제한 미들웨어가 제한 규칙을 조회한다.
3. Redis에서 해당 사용자 또는 IP의 현재 요청 횟수를 확인한다.
4. 제한을 초과하지 않았다면 카운터를 증가시키고 API 서버로 요청을 전달한다.
5. 제한을 초과했다면 요청을 거절하고 `HTTP 429`를 반환한다.

## 3단계: 상세 설계

### 처리율 제한 규칙

처리율 제한 규칙은 코드에 직접 작성하기보다 별도의 설정 파일이나 규칙 저장소에서 관리할 수 있다.

예를 들어 다음과 같은 규칙을 둘 수 있다.

- 특정 메시지는 사용자당 하루에 최대 5회 전송할 수 있다.
- 로그인 시도는 사용자 또는 IP 주소당 1분에 최대 5회 허용한다.
- 외부 API 호출은 서비스 계약에서 허용한 호출량 이하로 제한한다.

작업 프로세스가 규칙을 주기적으로 읽어 캐시에 저장하면 처리율 제한 장치는 요청마다 원본 저장소를 조회하지 않고 캐시된 규칙을 사용할 수 있다.

### 제한된 요청의 처리

단순 조회 요청처럼 나중에 처리할 필요가 없는 요청은 즉시 거절할 수 있다.

반면 주문 처리나 중요한 비동기 작업처럼 요청을 잃어서는 안 되는 경우에는 메시지 큐에 저장한 뒤 나중에 처리하는 방법을 고려할 수 있다.

처리율 제한 장치가 모든 요청을 무조건 버려야 하는 것은 아니다.

클라이언트가 현재 제한 상태를 알 수 있도록 응답 헤더에 다음 정보를 포함할 수 있다.

- 남아 있는 요청 횟수
- 적용된 요청 제한값
- 다시 요청할 수 있는 시점 또는 대기 시간

책에서는 다음과 같은 헤더를 소개한다.

- `X-Ratelimit-Remaining`
- `X-Ratelimit-Limit`
- `X-Ratelimit-Retry-After`

실제 구현에서는 사용하는 API 규약에 맞춰 `Retry-After` 또는 `RateLimit-*` 헤더 사용 여부도 확인해야 한다.

### 경쟁 조건

여러 요청이 동시에 들어오면 다음과 같은 경쟁 조건이 발생할 수 있다.

1. 두 요청이 동일한 카운터 값을 읽는다.
2. 두 요청 모두 아직 제한에 도달하지 않았다고 판단한다.
3. 각 요청이 카운터를 증가시킨다.
4. 실제보다 적은 값이 저장되거나 제한보다 많은 요청이 허용된다.

단순히 락을 사용하면 경쟁 조건은 해결할 수 있지만 처리 성능이 낮아질 수 있다.

Redis Lua 스크립트를 사용해 조회·검사·증가 연산을 원자적으로 처리하거나 Redis 정렬 집합을 사용하는 방법을 고려할 수 있다.

### 동기화 문제

처리율 제한 서버가 여러 대라면 각 서버가 서로 다른 카운터를 가지고 있어서는 안 된다.

특정 사용자의 요청을 항상 같은 서버로 보내는 고정 세션을 사용할 수도 있지만, 서버의 추가·제거가 어려워지고 확장성이 떨어진다.

따라서 여러 처리율 제한 서버가 Redis와 같은 중앙 집중형 저장소를 공유하는 방식이 일반적이다.

여러 데이터센터에서 하나의 처리율 제한 정책을 적용하면 지역 간 네트워크 지연과 데이터 동기화 문제가 발생한다.

모든 지역의 요청 수를 매번 강한 일관성으로 동기화하면 정확도는 높아지지만 응답 시간이 증가한다. 따라서 서비스의 성격에 따라 지역별 제한을 두거나 약간의 오차를 허용하는 최종적 일관성을 사용할 수 있다.

### 성능 최적화

사용자와 처리율 제한 장치 사이의 물리적 거리가 멀면 매 요청마다 네트워크 지연이 발생한다. 가능한 경우 사용자와 가까운 에지 서버 또는 데이터센터에서 요청을 제한하는 것이 좋다.

다만 여러 지역에서 동일한 제한값을 공유해야 한다면 다음 요소 사이에서 균형을 잡아야 한다.

- 전역적으로 정확한 처리율 제한
- 낮은 응답 지연
- 데이터 동기화 비용
- 장애 발생 시 가용성

### 모니터링

처리율 제한 장치를 도입한 뒤에는 알고리즘과 제한 규칙이 실제 트래픽에 적합한지 확인해야 한다.

다음과 같은 지표를 관찰할 수 있다.

- API별 전체 요청 수
- 허용된 요청과 거절된 요청의 수
- `HTTP 429` 응답 비율
- 사용자 또는 IP별 제한 규칙 적중 횟수
- Redis 응답 시간과 오류율
- 특정 키에 요청이 집중되는 핫키 현상
- 정상 사용자가 지나치게 자주 제한되는지 여부
- 재시도로 인해 요청량이 더 증가하는지 여부

정상적인 사용자가 자주 차단된다면 제한값이 너무 엄격할 수 있다. 반대로 트래픽 폭증을 막지 못한다면 알고리즘이나 제한값을 다시 검토해야 한다.

## 4단계: 마무리

### 경성 제한과 연성 제한

- **경성 처리율 제한**: 요청 수가 제한값을 절대로 넘을 수 없다.
- **연성 처리율 제한**: 짧은 시간 동안 제한값을 일부 초과하는 것을 허용한다.

결제, 보상 지급 또는 외부 API 비용 통제처럼 초과를 허용하기 어려운 기능에는 경성 제한이 적합하다.

일반적인 콘텐츠 조회처럼 순간적인 요청 증가를 허용해도 되는 기능에는 연성 제한을 고려할 수 있다.

### 여러 계층에서의 처리율 제한

이 장에서는 HTTP 요청을 다루는 애플리케이션 계층의 처리율 제한을 중심으로 살펴봤다.

하지만 네트워크 계층에서도 IP 주소를 기준으로 요청을 제한할 수 있다. 실제 시스템에서는 네트워크 방화벽, 로드밸런서, API Gateway, 애플리케이션 등 여러 계층의 제한을 조합할 수 있다.

### 클라이언트의 대응

클라이언트도 처리율 제한을 고려해 설계해야 한다.

- 불필요한 API 호출을 줄이고 캐시를 활용한다.
- 서버가 제공하는 제한값과 재시도 시점을 확인한다.
- `HTTP 429`를 정상적인 예외 상황으로 처리한다.
- 재시도할 때 충분한 백오프 시간을 둔다.
- 여러 클라이언트가 동시에 재시도하지 않도록 지터를 추가할 수 있다.

## 개인 경험과 연결해서 생각해본 내용

### 사용자별 일일 사용 횟수 제한

기존 프로젝트에서 특정 기능을 사용자별로 하루 3회까지만 사용할 수 있도록 구현한 경험이 있다. 이 기능도 넓게 보면 처리율 제한과 비슷한 구조를 갖는다.

다만 목적에는 차이가 있다.

- 일일 사용 횟수 제한은 상품 정책이나 비용 통제를 위한 **사용량 제한(Quota)**에 가깝다.
- 초당 요청 수 제한은 서버 보호를 위한 **처리율 제한(Rate Limiting)**에 가깝다.

사용자 수와 트래픽이 적을 때는 데이터베이스에 사용 횟수를 기록하는 방식도 가능하다.

하지만 모든 요청이 처리율 제한 검사를 받아야 하고 서버가 여러 대로 확장된다면, 매번 데이터베이스를 조회하는 것보다 Redis와 같은 공통 인메모리 저장소를 사용하는 편이 적합하다.

### 서버 메모리에만 카운터를 저장하면 생기는 문제

단일 서버에서는 애플리케이션 메모리에 요청 횟수를 기록할 수도 있다. 하지만 서버를 두 대 이상으로 확장하면 각 서버의 카운터가 서로 달라진다.

예를 들어 서버당 10회를 허용하면 사용자가 두 서버를 번갈아 호출해 총 20회의 요청을 통과시킬 수도 있다. 서버가 재시작되면 메모리의 카운터가 사라지는 문제도 있다.

따라서 분산 환경에서는 여러 서버가 공유하는 저장소가 필요하다는 점이 1장의 무상태 웹 계층과 연결된다.

### 모든 API에 같은 제한 정책을 적용할 수는 없다

로그인, 결제, 게시물 조회, 파일 업로드는 요청의 중요도와 비용이 서로 다르다.

- 로그인 API는 무차별 대입 공격을 막기 위해 사용자와 IP를 함께 고려해야 한다.
- 결제 API는 중복 처리를 막는 멱등성도 함께 고려해야 한다.
- 게시물 조회 API는 순간적인 트래픽을 어느 정도 허용할 수 있다.
- 파일 업로드와 AI API 호출은 요청 한 건의 비용이 크므로 더 엄격한 제한이 필요할 수 있다.

따라서 하나의 처리율 제한 알고리즘을 모든 API에 동일하게 적용하기보다 API 특성에 맞게 제한 키와 알고리즘을 선택해야 한다.

## 추가적으로 생각해볼 질문

### 처리율 제한 저장소에 장애가 발생하면 어떻게 해야 할까?

처리율 제한에 Redis를 사용한다고 해도 Redis가 항상 정상이라는 보장은 없다.

Redis에 접근할 수 없을 때 요청을 그대로 허용하는 `Fail-open` 방식은 가용성이 높지만 서버 과부하나 비용 증가로 이어질 수 있다.

요청을 차단하는 `Fail-closed` 방식은 시스템을 보호하지만 정상 사용자까지 서비스를 이용하지 못하게 만든다.

일반 조회 API, 로그인 API, 결제 API가 각각 어떤 방식을 선택해야 하는지 생각해볼 필요가 있다.

### 처리율 제한 키는 무엇으로 정해야 할까?

IP 주소만 사용하면 학교, 회사 또는 통신사 NAT 환경에서 여러 사용자가 하나의 제한을 공유할 수 있다.

반대로 사용자 ID만 사용하면 로그인 전 요청이나 여러 계정을 이용하는 공격을 막기 어렵다.

사용자 ID, IP 주소, 디바이스 ID, API 키를 어떤 방식으로 조합해야 정상 사용자를 과도하게 차단하지 않으면서 공격을 막을 수 있을지 고민이 필요하다.

### 정확성과 가용성 중 무엇을 우선해야 할까?

여러 데이터센터의 요청 수를 완벽하게 동기화하려면 지역 간 통신이 필요하고 응답 지연과 장애 가능성이 커진다.

반대로 지역별 카운터를 사용하면 빠르고 가용성이 높지만 전역 제한값을 잠시 초과할 수 있다.

결제나 보상 지급과 같은 API와 일반 콘텐츠 조회 API가 같은 수준의 정확성을 요구하는지 구분해야 한다.

### 어떤 알고리즘을 선택해야 할까?

토큰 버킷은 순간적인 요청 증가를 허용할 수 있고, 누출 버킷은 일정한 처리 속도를 유지할 수 있다.

이동 윈도 로그는 정확하지만 메모리를 많이 사용하며, 이동 윈도 카운터는 효율적이지만 작은 오차가 존재한다.

따라서 알고리즘의 우열을 정하기보다 허용 가능한 버스트와 오차, 메모리 사용량을 기준으로 선택해야 한다.
