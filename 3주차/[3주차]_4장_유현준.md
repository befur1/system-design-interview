# [3주차] 4장 - 처리율 제한 장치의 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

이번 장은 내용 정리보다 읽으면서 막힌 것들을 하나씩 따라간 기록이 길어졌다. 책 내용은 뼈대만 두고, 파고든 내용을 아래 "개인적인 질문"에 정리했다.

## 처리율 제한 장치란

클라이언트나 서비스가 보내는 트래픽의 처리율을 제어하기 위한 장치. 임계치를 넘으면 추가 요청은 차단된다.

두는 이유는 세 가지다. DoS 공격 방지, 비용 절감(특히 외부 API를 유료로 쓸 때), 서버 과부하 방지.

## 어디에 둘 것인가

클라이언트 측, 서버 측, 미들웨어(API 게이트웨이) 세 가지 선택지가 있다. 클라이언트는 위변조가 쉬워서 안정적이지 않으므로 서버 측이 기본이다. 이 선택이 생각보다 단순하지 않아서 따로 파봤다(개인적인 질문 1).

## 알고리즘

| 알고리즘 | 방식 | 대가 |
| --- | --- | --- |
| 토큰 버킷 | 토큰을 미리 채워두고 요청마다 하나씩 꺼낸다 | 근사치. 버스트 허용 |
| 누출 버킷 | 고정된 속도로 큐에서 빠져나간다 | 버스트를 못 받음 |
| 고정 윈도 카운터 | 시간을 창으로 잘라 창마다 센다 | 창 경계에서 2배 통과 |
| 이동 윈도 로그 | 요청 타임스탬프를 전부 기록 | 정확하지만 메모리를 많이 씀 |
| 이동 윈도 카운터 | 앞의 둘을 절충 | 근사치 |

이 중 토큰 버킷(Stripe)과 이동 윈도 로그(ClassDojo)는 주석에 걸린 글에서 실제 구현을 먼저 봤다(개인적인 질문 4). 실물을 보고 나서 책 설명을 읽으니 훨씬 잘 붙었다.

## 분산 환경에서의 문제

서버가 여러 대가 되면 경쟁 조건과 동기화 문제가 생긴다. 카운터를 읽고 판단하고 쓰는 사이에 다른 서버가 끼어들 수 있다. 해결책으로 루아 스크립트와 정렬 집합이 나온다.

## 1장과 연계해서 생각해보자

카운터를 서버 메모리에 두면 서버 한 대일 때만 동작한다. 3대로 늘리면 각자 세기 때문에 제한이 100회여도 실질 300회가 된다.

이게 1장의 무상태 웹 계층과 정확히 같은 얘기였다. 상태를 서버가 들고 있으면 규모 확장이 안 된다는 것. 그래서 카운터를 Redis 같은 공유 저장소로 빼야 하고, 그러면 여러 서버가 같은 값을 건드리는 경쟁 조건이 생기고, 그걸 푸는 게 이 장 뒷부분이다.

1장 → 4장이 한 줄로 이어진다.

- 1장: 상태를 서버 밖으로 빼라
- 4장: 뺐더니 이번엔 여럿이 동시에 건드린다
- 4장 해법: 루아 스크립트로 읽기-판단-쓰기를 원자적으로 묶는다

# 개인적인 질문

## 1. 처리율 제한 장치를 정확히 어디에 둬야 하나

### 클라이언트 측과 서버 측의 차이

모의면접에서 "클라이언트 측입니까 서버 측입니까"라고 묻는데 차이를 몰라서 찾아봤다. 핵심은 누가 강제하느냐, 즉 믿을 수 있느냐였다.

클라이언트 측은 클라이언트가 스스로 자기 요청을 줄이는 것이다. 검색창 디바운스, 버튼 연타 방지 같은 것. 문제는 코드가 사용자 기기에서 돌기 때문에 개발자도구로 고치거나 앱을 디컴파일하거나 아예 curl로 직접 호출하면 그만이라는 점이다. 악의적 사용자에게는 효력이 없다.

서버 측은 모든 요청이 서버를 거치므로 강제력이 있다.

| | 클라이언트 측 | 서버 측 |
| --- | --- | --- |
| 목적 | 예의, 비용 절감, UX | 보호, 강제 |
| 막는 대상 | 협조적인 사용자의 실수 | 악의적 사용자, 폭주 |
| 우회 가능 여부 | 쉽게 뚫림 | 못 뚫음 |

내 경우로 바꿔 생각해보면, 내 서버가 외부 API를 부를 때는 내 서버가 곧 클라이언트다. 상대방은 서버 측 제한을 걸어두었을 것이고 내가 넘기면 429를 맞는다. 그래서 내 쪽에서 미리 호출 간격을 조절하는 게 클라이언트 측 제한이다. 실무에서 클라이언트 측 제한을 직접 구현하게 되는 건 대부분 이 경우인 듯하다. 결국 둘은 택일이 아니라 양쪽에 다 있는 게 정상이다.

### 미들웨어 주석에 달린 마이크로서비스

"클라우드 마이크로서비스의 경우 처리율 제한은 보통 API 게이트웨이에 구현된다"에 주석이 달려 있어서 읽어봤다. 왜 하필 게이트웨이인지가 마이크로서비스를 알아야 납득이 됐다.

마이크로서비스는 하나의 큰 애플리케이션을 독립적으로 배포 가능한 작은 서비스들로 쪼갠 구조다. 서비스마다 자기 기술 스택과 자기 DB를 갖는다. 내가 스프링부트로 만든 프로젝트는 모놀리식이다.

서비스가 20개로 쪼개지면 클라이언트가 주소 20개를 알 수 없고 인증을 20군데 구현할 수도 없으니 입구를 하나로 만드는데, 그게 API 게이트웨이다. 처리율 제한이 여기 사는 이유도 같다. 서비스마다 제한 로직을 20번 짤 수 없으니 모든 요청이 지나가는 입구에서 한 번 거른다.

뒤집어 말하면 모놀리식은 입구가 어차피 하나라서 굳이 게이트웨이를 둘 필요가 없다. 책이 "서버 측 구현"과 "미들웨어"를 선택지로 나눈 게 이 차이라고 이해했다.

IBM 글의 경고가 인상적이었다. "모놀리식의 복잡성을 아직 느끼지 못했다면 마이크로서비스로 시작하지 마라."

### 그럼 스프링부트에서는 실무적으로 어디에 두나

둘 중 하나가 아니라 계층별로 나눠서 한다는 걸 알게 됐다.

인프라 계층은 Nginx limit_req, AWS WAF, Cloudflare 같은 것들이다. 장점이 결정적인데, 막힌 요청이 애플리케이션에 아예 닿지 않는다. 톰캣 스레드도 안 쓰고 DB 커넥션도 안 잡는다.

애플리케이션 계층은 Bucket4j, Resilience4j, 또는 인터셉터에 Redis 카운터를 직접 구현하는 것이다.

앞단만으로 안 되는 이유는 Nginx가 이 요청이 유료 플랜 사용자인지 모르기 때문이다. IP나 경로 정도만 본다. 그런데 실제 요구사항은 "무료 100회, 유료 10,000회", "업로드는 10회, 조회는 1,000회" 같은 것들이고, 이건 누가 어떤 플랜인지 아는 앱 안에서만 할 수 있다.

정리하면 인프라는 거친 방어(IP 단위 폭주, DDoS), 앱은 세밀한 정책(사용자별, 플랜별, 엔드포인트별)을 맡는다.

## 2. 톰캣 스레드와 DB 커넥션을 빨리 풀어준다는 게 무슨 말인가

2주차에 강상준 님이 3장 문서에 "어떻게 해야 톰캣 스레드와 DB 커넥션을 0.001초라도 빨리 풀어줄 수 있는가"라고 쓴 게 무슨 뜻인지 몰라서 물어봤는데, 결국 4장과 같은 문제였다.

### 제한된 풀이 두 개 있다

톰캣 스레드 풀은 기본 200개로, 요청 하나가 스레드 하나를 배정받아 응답을 다 내보낼 때까지 점유한다. DB 커넥션 풀(HikariCP)은 기본 10개다. 둘 다 다 쓰면 다음 요청은 줄을 선다.

### 문제가 생기는 코드

```java
@Transactional
public void order(Long userId) {
    Order o = orderRepo.save(...);    // DB 10ms
    paymentClient.pay(o);              // 결제 API 3초
    mailClient.send(...);              // 메일 발송 1초
}
```

@Transactional은 메서드 시작할 때 커넥션을 빌려 끝날 때까지 놓지 않는다. 이 메서드는 4초간 커넥션을 쥐는데 실제 DB를 쓰는 건 맨 앞 10ms뿐이고, 나머지 3.99초는 커넥션을 붙잡고 결제 서버 응답만 기다린다.

커넥션이 10개니 동시 주문 10건이면 풀이 바닥나고 11번째부터 타임아웃. CPU도 놀고 DB도 한가한데 장애가 난다.

| 커넥션 점유 시간 | 초당 처리 가능 요청 (커넥션 10개) |
| --- | --- |
| 1초 | 10건 |
| 0.1초 | 100건 |
| 0.01초 | 1,000건 |

같은 서버, 같은 DB인데 점유 시간만 줄여서 100배가 된다. 풀을 늘리면 되지 않나 싶었는데, DB 쪽에서 커넥션마다 자원을 쓰기 때문에 늘리면 DB가 먼저 죽는다고 한다. 그래서 늘리는 게 아니라 빨리 반납하는 쪽으로 간다.

개선은 트랜잭션 범위를 DB 쓰는 부분으로 좁히고 결제와 메일은 이벤트로 빼는 것이다. 커넥션 점유가 4초에서 10ms로 400배 차이가 난다.

### 톰캣의 역할

계속 "톰캣 스레드"를 전제로 얘기했는데 정작 톰캣이 뭘 하는지 몰라서 확인했다. 한 줄로는 HTTP와 자바 코드 사이의 번역기다.

내가 쓴 컨트롤러는 그냥 자바 클래스일 뿐이고, 자바는 그게 HTTP 요청에 응답하는 코드라는 걸 모른다. 톰캣이 포트를 열고 연결을 받고 바이트를 HTTP로 해석해 HttpServletRequest 객체로 만들어 넘겨준다.

그리고 스프링은 톰캣 입장에서 서블릿 딱 하나다. 톰캣은 모든 요청을 DispatcherServlet에 넘기고 손을 뗀다. 어느 컨트롤러로 보낼지 정하는 건 스프링이고, 톰캣은 컨트롤러가 몇 개인지 모른다.

스레드를 잡는 이유는 서블릿 명세가 요청 하나당 스레드 하나 모델이기 때문이다. 서블릿 코드는 동기 블로킹이라 DB 응답을 기다리는 동안에도 스레드가 점유된 상태다.

## 3. 그러면 처리율 제한도 트랜잭션 밖으로 빼면 되는 것 아닌가

결제 API를 트랜잭션 밖으로 뺀 것처럼 하면 되지 않나 생각했는데, 이미 그렇게 되어 있었다.

```
1. 톰캣이 요청 받음 → 스레드 배정        ← 스레드 소모 시작
2. 서블릿 필터 체인                      ← 처리율 제한 보통 여기
3. DispatcherServlet
4. 인터셉터 preHandle                    ← 또는 여기
5. 컨트롤러
6. 서비스 @Transactional                 ← 여기서 비로소 커넥션 빌림
```

처리율 제한은 2번이나 4번에 달기 때문에 6번까지 가지 않는다. 막히면 429를 뱉고 끝이라 트랜잭션은 시작조차 안 한다. 프레임워크가 구조적으로 이미 그렇게 해두고 있었다.

| 어디서 막나 | 톰캣 스레드 | DB 커넥션 |
| --- | --- | --- |
| Nginx 앞단 | 안 씀 | 안 씀 |
| 앱 필터 | 씀 (Redis 왕복 약 1ms) | 안 씀 |
| 컨트롤러 안 | 씀 | 안 씀 |

앱 레벨 제한도 생각보다 가볍다. 차이가 벌어지는 건 초당 수만 건 규모부터다.

### 진짜로 문제가 되는 구현

카운터를 Redis가 아니라 DB 테이블에 두면 얘기가 달라진다. 처리율 제한을 하려고 모든 요청마다 DB 커넥션을 빌리게 되고, 막으려는 요청 때문에 보호하려던 자원을 쓰는 셈이 된다. 동시 요청이 몰리면 같은 행에 락 경합까지 난다.

책이 Redis를 쓰라고 하는 게 단순히 빨라서가 아니라, 보호 대상인 DB를 건드리지 않으려는 이유도 있다고 이해했다.

### 왜 앞단이 더 싼가

서버에 닿기만 하면 톰캣 스레드가 잡히니까 그걸 막으려고 앞단에 두는 것인지 물었는데, 이유가 두 개였다.

톰캣은 요청 하나당 스레드 하나를 쓰지만, Nginx는 이벤트 기반 비동기 I/O라서 워커 프로세스 몇 개가 수만 개 연결을 동시에 처리한다. 앞단이 싼 이유는 단순히 더 일찍 막아서가 아니라 애초에 요청당 비용 구조가 다르기 때문이다. 같은 1만 건을 거절할 때 톰캣은 스레드 풀이 말라붙고 Nginx는 별 타격이 없다.

```
Cloudflare/CDN   ← 내 네트워크에 도달조차 안 함
    ↓
Nginx / ALB      ← 스레드 안 잡힘 (이벤트 기반)
    ↓
톰캣 스레드      ← 여기부터 스레드 1개 점유
    ↓
필터 (처리율 제한) ← Redis 1ms, 커넥션은 안 씀
    ↓
@Transactional   ← 커넥션 점유
```

바깥에서 막을수록 싸고 안쪽으로 들어올수록 비싸다. 대신 바깥은 아는 게 없다. Cloudflare는 이 요청이 유료 플랜 사용자인지 모른다.

### 반복되는 원칙

이 장을 읽으면서 같은 원칙이 계속 나왔다. 비싼 자원은 꼭 필요한 순간에만, 가장 짧게 잡는다.

- @Transactional 범위 최소화 → 커넥션
- 결제 API를 트랜잭션 밖으로 → 커넥션
- 처리율 제한을 필터에 → 커넥션 자체를 안 씀
- Nginx 앞단 제한 → 스레드까지 안 씀

강상준 님이 2주차에 쓴 5가지도 전부 이 얘기였다고 생각한다.

## 4. 루아 스크립트와 정렬 집합 주석은 무슨 내용인가

둘 다 경쟁 조건 해결책이었다.

```
서버 A: GET counter → 9
서버 B: GET counter → 9        ← A가 아직 못 올림
서버 A: 9 < 10 통과, SET 10
서버 B: 9 < 10 통과, SET 10    ← 11이 돼야 하는데 10
```

읽기와 쓰기 사이에 틈이 있어서 둘 다 통과시켰고 카운터도 틀렸다. 락을 걸면 해결되지만 느리다.

### 루아 스크립트 (Stripe)

Redis가 루아 스크립트를 원자적으로 실행한다. 읽고 판단하고 쓰는 걸 통째로 보내면 도는 동안 다른 명령이 끼어들지 못한다. 틈이 사라지고 왕복도 한 번으로 준다.

Stripe는 리미터를 네 종류 돌린다.

| 리미터 | 막는 것 |
| --- | --- |
| Request rate limiter | 사용자당 초당 N개. 토큰 버킷 |
| Concurrent requests limiter | 동시에 진행 중인 요청 20개. 무거운 엔드포인트용 |
| Fleet usage load shedder | 인프라 20%를 중요 요청용으로 예약 |
| Worker utilization load shedder | 최후 방어선. 테스트모드 → GET → POST 순으로 버림 |

두 번째가 흥미로웠다. "초당 몇 개"가 아니라 "동시에 몇 개"다. 무거운 API는 사용자가 기다리다 재시도하며 상황이 악화되는데 횟수 제한으로는 못 막는다.

실무 조언도 인상적이었다. Redis가 죽어도 요청은 통과시켜라(리미터 때문에 서비스가 죽으면 본말전도), 429와 503을 구분해라, 킬 스위치를 만들어둬라, 그리고 먼저 로깅만 하고 켜지 마라(dark launch). 마지막이 제일 실전적으로 느껴졌다. 임계값을 감으로 정하면 멀쩡한 사용자가 막힌다.

### 정렬 집합 (ClassDojo)

책의 이동 윈도 로그 알고리즘의 실제 구현이었다.

고정 윈도는 0:59에 10개, 1:01에 10개를 보내면 2초 만에 20개가 통과한다. 해결은 항상 "지금부터 1분 전까지"를 보는 것이다. 사용자마다 정렬 집합을 두고 멤버와 스코어에 둘 다 요청 시각을 넣는다. 스코어가 시각이라 시간순 정렬이 저절로 유지된다.

```
ZREMRANGEBYSCORE   윈도우 밖 항목 제거
ZRANGE / ZCARD     남은 개수 세기
ZADD               현재 시각 추가
EXPIRE             TTL로 메모리 정리
```

원자성은 MULTI로 확보한다. 대가는 요청 하나하나의 타임스탬프를 전부 저장한다는 것이다. 초당 1000건이면 1분 윈도에 6만 개가 쌓인다. 책이 이동 윈도 로그의 단점으로 메모리를 많이 쓴다고 한 게 이거였다.

| | 루아 (Stripe) | 정렬 집합 (ClassDojo) |
| --- | --- | --- |
| 알고리즘 | 토큰 버킷 | 이동 윈도 로그 |
| 저장 | 토큰 개수 + 마지막 갱신 시각 | 모든 요청 타임스탬프 |
| 메모리 | 사용자당 상수 | 요청 수에 비례 |
| 정확도 | 근사 | 정확 |

정확도와 메모리의 맞바꿈이다. Stripe처럼 규모가 크면 메모리가 안 되니 토큰 버킷으로 가고, 정확히 세야 하면 정렬 집합으로 간다.
