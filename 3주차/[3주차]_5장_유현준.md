# [3주차] 5장 - 안정 해시 설계

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

4장과 달리 5장은 막히는 데가 거의 없었다. 읽으면서 "그럴만하네" 하고 넘어간 장이라 정리도 짧게 둔다. 대신 이해한 게 맞는지 스스로 확인한 기록을 아래에 남긴다.

## 해시 키 재배치 문제

서버 N대에 hash(key) % N으로 분배하면, 서버가 추가되거나 빠져서 N이 바뀌는 순간 나머지 값이 전부 달라진다. 사실상 전면 재배치가 일어나고 캐시 미스가 폭발한다.

## 안정 해시

해시 공간을 링으로 만들고 서버와 키를 모두 링 위에 올린 뒤, 키에서 시계 방향으로 처음 만나는 서버에 할당한다. 서버가 추가되거나 제거되어도 영향받는 건 인접 구간뿐이다.

| 방식 | 서버 4→5대일 때 옮겨지는 키 |
| --- | --- |
| hash(key) % N | 거의 전부 (약 80%) |
| 안정 해시 | 약 1/5 |

## 가상 노드

서버 수가 적으면 링 위 위치가 무작위라 구간 크기가 제각각이 된다. 어떤 서버는 많이, 어떤 서버는 적게 받는다.

서버 하나를 링 위 여러 지점에 올려 가상 노드로 만들면 분포가 고르게 잡힌다. 가상 노드 수가 늘수록 표준편차가 작아진다.

대신 가상 노드 하나하나가 링에 들어가는 항목이므로 저장 공간이 더 든다. 서버당 200개씩 1000대면 20만 개를 들고 있어야 한다. 그래서 타협의 축은 정확한 분산과 메모리 사이에 있다.

## 1장과 연계해서 생각해보자

1주차에 1장을 정리하면서 샤딩의 문제로 재샤딩을 적었다. 샤드가 꽉 차거나 데이터 분포가 한쪽으로 쏠리면 샤드 수를 바꾸고 데이터를 재배치해야 한다고.

그때 재배치가 왜 그렇게 큰 문제인지는 사실 잘 몰랐는데, 그게 정확히 hash % N의 문제였다. 5장이 1장에서 남겨둔 숙제의 답이다.

그리고 4장과도 맞닿는다. 4장에서 이동 윈도 로그와 토큰 버킷이 정확도와 메모리를 맞바꾸는 걸 봤는데, 5장의 가상 노드 수도 같은 모양의 맞바꿈이다. 한 주 안에 같은 구조의 트레이드오프를 두 번 봤다.

# 개인적인 질문

5장은 질문이 안 나왔다. 대신 이해한 게 맞는지 세 가지를 스스로 답해보고 확인했는데, 두 개가 어긋나 있었다.

## 내가 답한 것

1. 가상 노드를 왜 두나 → 표준편차가 줄어 배치가 고르게 된다
2. 서버 추가 시 어떤 키가 옮겨지나 → 반시계 방향으로 다른 서버를 만날 때까지. 서버 4개 기준 1/4 정도
3. 가상 노드를 왜 무한정 안 늘리나 → 연산이 무거워져서?

## 어긋난 것

### 2번 - 방향은 맞았지만 비교 대상이 빠져 있었다

"반시계 방향으로 이전 서버를 만날 때까지"는 맞다. 서버 4대에 한 대를 추가하면 새 서버가 가져가는 건 평균 1/5이다(추가 후 총 5대이므로).

그런데 숫자보다 중요한 건 비교 대상이었다. 1/5가 의미 있는 건 hash % N이 거의 전부를 옮기기 때문이다. 나는 "1/N만 옮겨진다"는 사실만 알고 있었지, 그게 무엇과 비교해서 좋은 건지를 놓치고 있었다.

또 가상 노드가 있으면 옮겨지는 키가 한 이웃에게 몰리지 않고 링 곳곳의 작은 구간으로 흩어진다. 이전 부하까지 고루 퍼진다는 점은 생각 못 했다.

### 3번 - 연산이 아니라 저장 공간이었다

조회 비용은 거의 안 늘어난다. 링이 정렬된 구조라 이진 탐색이고, 가상 노드가 10배가 돼도 log n이라 사실상 그대로다.

진짜 대가는 메모리다. 책도 "가상 노드 수를 늘리면 표준편차는 작아지지만 가상 노드 데이터를 저장할 공간은 더 많이 필요해진다"고 쓴다. 막연히 "많아지면 느려지겠지"라고 생각한 게 틀렸다.

## 이번 장에서 배운 것

읽고 다 이해했다고 느꼈는데 막상 답해보니 두 개가 어긋나 있었다. 특히 3번은 확인 안 했으면 그대로 넘어갔을 것 같다. 이해했다는 느낌과 실제로 설명할 수 있는 건 다르다는 걸 확인했다.
