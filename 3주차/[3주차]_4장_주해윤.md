## 4장 처리율 제한 장치의 설계

---

> 네트워크 시스템에서 처리율 제한 장치는 클라이언트 또는 서비스가 보내는 트래픽의 처리율을 제어하기 위한 장치다.
> 

예시) HTTP: 특정 기간 내에 전송되는 클라이언트의 요청 횟수 제한

**API에 처리율 제한 장치를 두면 좋은 점**

- DoS 공격에 의한 자원 고갈을 방지
- 비용 절감
- 서버 과부하 막음

### 1) 문제 이해 및 설계 범위 확정

- 클라이언트 쪽 제한 장치인지/서버 쪽 제한 장치인지
- API 호출을 제어하는 기준
- 시스템 규모
- 분산 환경에서의 작동 여부
- 독립된 서비스인지/애플리케이션 코드에 포함될 수 있는지

→ 질문을 통해 각각의 장단점을 가진 제한 장치들 중 어떤 것을 구현해야 하는지 분명히 할 것

### 2) 개략적 설계안 제시 및 동의 구하기

- 처리율 제한 장치는 어디에 둘 것인가?
    - 클라이언트 측: 쉽게 위변조 가능
    - 서버 측: 클라이언트가 HTTP 요청을 보내고 처리율 제한 장치는 API 서버에 둠
    - 미들웨어 만들기: 처리율 제한 미들웨어를 만들어 해당 미들웨어로 하여금 API 서버로 가는 요청을 통제하도록 함
        
        예시) 클라우드 마이크로서비스: API 게이트웨이
        

**처리율 제한 알고리즘**

- 토큰 버킷 알고리즘
    - 토큰 버킷: 지정된 용량을 갖는 컨테이너, 사전 설정된 양의 토큰이 주기적으로 채워짐
    - 이 알고리즘은 버킷 크기, 토큰 공급률이라는 두개의 파라미터를 받음
    
    예제) 용량이 4인 버킷
    
    1. 토큰 공급기는 이 버킷에 매초 2개의 토큰을 추가, 버킷이 가득 차면 추가로 공급된 토큰은 버려짐(overflow)
    2. 각 요청은 처리될 때마다 하나의 토큰을 사용하고 요청이 도착하면 버킷에 충분한 토큰이 있는지 검사
        1. 충분하면 버킷에서 토큰 하나 꺼내 요청을 시스템에 전달
        2. 없으면 해당 요청 버려짐
    
    - 장점: 구현이 쉽고 메모리 사용 측면에서 효율적, 트래픽 처리 가능
    - 단점: 두개의 파라미터를 적절하게 튜닝하는 것이 까다로움

- 누출 버킷 알고리즘
    - 보통 FIFO로 구현
    1. 요청이 도착하면 큐가 가득 차 있는지 보고, 빈자리가 있는 경우 큐에 요청 추가
    2. 큐가 가득 차 있는 경우 새 요청은 버림
    3. 지정된 시간마다 큐에서 요청 꺼내 처리
    - 버킷 크기, 처리율(고정) 두개의 파라미터 사용
    - 장점: 큐의 크기가 제한되어 있어 메모리 사용량 측면에서 효율적
    - 단점: 단시간에 많은 트래픽이 몰리면 큐에 오래된 요청 쌓이고 이를 처리 못할시 최신 요청 버려짐, 두개의 인자 올바르게 튜닝하기 까다로움

- 고정 윈도 카운터 알고리즘
    1. 타임라인을 고정된 간격의 윈도로 나누고, 각 윈도마다 카운터 붙임
    2. 요청이 접수될 때마다 이 카운터의 값은 1씩 증가
    3. 이 카운터의 값이 사전에 설정된 임계치에 도달하면 새로운 요청은 새 윈도가 열릴 때까지 버려짐
    - 장점: 메모리 효율 좋고 이해하기 쉬움, 특정한 트래픽 패턴을 처리하기에 적합
    - 단점: 윈도 경계 부근에서 일시적으로 많은 트래픽이 몰려드는 경우, 기대했던 시스템의 처리 한도보다 많은 요청을 처리하게 됨

- 이동 윈도 로깅 알고리즘
    - 요청의 타임스탬프를 추적, 타임스탬프 데이터는 보통 레디스의 정렬 집합 같은 캐시에 보관
    1. 새 요청이 오면 만료된 타임스탬프는 제거
    2. 새 요청의 타임스탬프를 로그에 추가
    3. 로그의 크기가 허용치보다 같거나 작으면 요청을 시스템에 전달, 그렇지 않은 경우 처리를 거부
    - 장점: 아주 정교함
    - 단점: 다량의 메모리를 사용

- 이동 윈도 카운터 알고리즘
    - 고정 윈도 카운터 알고리즘 + 이동 윈도 로깅 알고리즘
    
    예제) 처리율 제한 장치의 한도-분당 7개 요청, 이전 1분 동안 5개의 요청, 현재 1분 동안 3개의 요청, 현재 1분의 30% 시점에 도착한 새 요청의 경우 현재 윈도에 몇 개의 요청이 온 것으로 보고 처리해야 할까?
    
    1. 현재 1분간의 요청 수 + 직전 1분간의 요청 수 * 이동 윈도와 직전 1분이 겹치는 비율
    2. 3+5*70% = 6.5 → 내림하여 쓰면 6
    3. 한도가 분당 7개 요청이라고 했으므로 시스템으로 전달될 것
    
    - 장점: 짧은 시간에 몰리는 트래픽에도 잘 대응, 메모리 효율 좋음
    - 단점: 다소 느슨함

**개략적인 아키텍처**

- 클라이언트가 처리율 제한 미들웨어에게 요청을 보냄
- 처리율 제한 미들웨어는 레디스의 지정 버킷에서 카운터를 가져와 한도에 도달했는지 아닌지를 검사
    - 도달했다면 요청 거부
    - 도달하지 않았다면 요청은 API 서버로 전달, 미들웨어는 카운터의 값 증가시킨 후 다시 레디스에 저장

### 3) 상세 설계

**처리율 제한 규칙**

- 보통 설정 파일 형태로 디스크에 저장

**처리율 한도 초과 트래픽의 처리**

- HTTP 응답 헤더를 통해 처리율 제한에 걸리고 있는지를 감지
    - X-Ratelimit-Remaining
    - X-Ratelimit-Limit
    - X-Ratelimit-Retry-After

**상세 설계**

- 클라이언트가 요청을 서버에 보내면 요청은 먼저 처리율 제한 미들웨어에 도달
- 처리율 제한 미들웨어는 제한 규칙을 캐시에서 가져옴, 아울러 카운터 및 마지막 요청의 타임스탬프를 레디스 캐시에서 가져옴
    - 해당 요청이 처리율 제한에 걸리지 않은 경우 API 서버로 보냄
    - 해당 요청이 처리율 제한에 걸렸다면 `429 too many request` 에러를 클라이언트에 보냄
- 분산 환경에서의 처리율 제한 장치의 구현
    - 경쟁 조건 해결책
        - lock
        - 루아 스크립트
        - 정렬 집합
    - 동기화 이슈 해결책
        - 고정 세션 활용
        - 중앙 집중형 데이터 저장소 사용
    - 성능 최적화
        - 데이터 센터 지원
        - 데이터 동기화 시 최종 일관성 모델 사용

### +) 논의해 볼 사항 및 경험과 연결

- 정성 또는 연성 처리율 제한
    - 어떤 알고리즘을 쓸까??
        - 호출할 때마다 비용 발생 → 강성 제한이 유리
        - 순간적인 급증을 허용해야 한다면? → 토큰 버킷 방식이 유리할 듯
- 다양한 계층에서의 처리율 제한(컴네 시간에 배운거!!)
    - 네트워크 계층(3계층): 출발지 IP를 기준으로 제한 → 대량의 비정상 트래픽을 초기에 막는데에 유용, 학교나 카페 같이 IP 공유하는 사용자도 함께 영향 받을 수도 있다~
    - 전송 계층(4계층): TCP 연결 수나 새 연결 생성 속도를 제한
    - 응용 계층(7계층): HTTP 요청의 경로, 로그인 계정, API 키 등을 기준으로 제한
        - 예를 들자면 AI 호출 API는 엄격하게 일반 조회 API는 넉넉하게 설정할 수 있겠네요
- 처리율 제한을 회피하는 방법, 클라이언트를 어떻게 설계하는 것이 최선인가?
    - 예외 처리나 에러 처리를 도입하거나
    - 재시도 로직을 구현한다면?
        - 실패했다고 바로 다시 보내지 않도록 기다리는 시간을 설정할 것
- 계속 생각나는건 AI 요청을 사용하는 API와 일반 조회 API 간의 차이인데
    - 예를 들어 중커톤 CoTempo에서는 AI 추천을 ‘팀 전체 일정’을 기준으로 하는데 그럼 처리율 제한을 사용자별 제한으로 두는 게 좋을지 팀별 제한으로 두는 게 좋을지 같은 걸 생각해볼 수 있을 듯
    - 그리고 AI 호출 같은 경우에는 호출 시마다 비용이 발생하니 일반 조회보다 제한을 더 엄격하게 두어야겠죠… 같은 입력값을 가지고 추천 받게 된다면 이건 결과 재사용이나 중복 요청을 방지해야 할 듯
        - 실제로 Peerfolio 프로젝트 진행 시에 금융 정보 수정이 안된 상태에서는 재분석이 불가능하도록 구현했었음!!
