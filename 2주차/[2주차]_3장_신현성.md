# 3장: 시스템 설계 면접 공략법

## 시스템 설계 면접

시스템 설계 면접에서는 실제 서비스의 모든 기능을 완벽하게 구현하는 능력만을 평가하지 않는다.

모호하고 범위가 넓은 문제를 질문을 통해 구체화하고, 면접관과 협력하여 해결책을 찾아가는 과정을 종합적으로 평가한다.

면접관이 확인하려는 능력은 다음과 같다.

- 모호한 문제를 구체적인 요구사항으로 바꾸는 능력
- 문제를 구조적으로 분석하는 능력
- 여러 해결 방법의 장단점을 비교하는 능력
- 설계 과정과 판단 근거를 명확하게 설명하는 능력
- 면접관의 질문과 피드백을 받아들이는 태도
- 장애, 운영, 확장성까지 고려하는 능력
- 제한된 시간 안에 중요한 문제를 선택하는 능력

시스템 설계 문제에는 하나의 정답이나 모든 상황에서 사용할 수 있는 최선의 설계가 없다. 요구사항과 제약사항에 따라 적절한 설계가 달라지므로, 선택한 설계의 근거와 트레이드오프를 설명해야 한다.

## 효과적인 면접을 위한 4단계 접근법

시스템 설계 면접은 다음 네 단계로 나누어 접근할 수 있다.

1. 문제 이해 및 설계 범위 확정
2. 개략적인 설계안 제시 및 동의 구하기
3. 상세 설계
4. 마무리

## 1단계: 문제 이해 및 설계 범위 확정

문제를 받자마자 바로 설계를 시작해서는 안 된다. 같은 서비스라도 어떤 기능과 규모를 요구하는지에 따라 설계가 크게 달라지기 때문이다.

먼저 질문을 통해 요구사항과 제약사항을 명확하게 만들어야 한다.

확인할 수 있는 질문의 예시는 다음과 같다.

- 시스템이 제공해야 하는 핵심 기능은 무엇인가?
- 이번 설계에서 제외해도 되는 기능은 무엇인가?
- 예상 사용자 수와 일간 능동 사용자 수는 얼마인가?
- 읽기와 쓰기 요청의 비율은 어느 정도인가?
- 평균 QPS와 최대 QPS는 얼마인가?
- 데이터는 얼마나 오래 보관해야 하는가?
- 강한 일관성이 필요한가, 최종적 일관성을 허용할 수 있는가?
- 응답지연과 가용성에 대한 요구사항은 무엇인가?
- 모바일 앱과 웹 애플리케이션을 모두 지원해야 하는가?
- 회사에서 이미 사용하고 있는 기술이나 인프라가 있는가?

면접관이 구체적인 수치를 주지 않는다면 합리적인 값을 가정하고 그 가정을 명확하게 말해야 한다.

예를 들면 다음과 같이 말할 수 있다.

> 구체적인 사용자 수가 정해져 있지 않으므로 일간 능동 사용자 1,000만 명과 최대 트래픽이 평균의 두 배인 상황을 가정하고 진행하겠습니다. 다른 규모를 원하시면 해당 수치에 맞춰 조정하겠습니다.

이 단계의 목적은 문제를 임의로 해석하는 것이 아니라, 면접관과 설계 범위에 대한 공통된 이해를 만드는 것이다.

## 2단계: 개략적인 설계안 제시 및 동의 구하기

요구사항과 범위를 정했다면 시스템을 구성하는 핵심 컴포넌트를 중심으로 개략적인 설계안을 제시한다.

일반적으로 다음 항목을 포함한다.

- 클라이언트
- DNS
- 로드밸런서
- 웹 서버 또는 API 서버
- 주요 애플리케이션 서비스
- 캐시
- 데이터베이스
- 메시지 큐와 작업 서버
- CDN 또는 객체 저장소

이 단계에서는 각 컴포넌트의 내부 구현을 먼저 설명하기보다, 요청과 데이터가 시스템을 통과하는 전체 흐름을 보여주는 것이 중요하다.

설계안을 제시하면서 다음 내용을 함께 확인한다.

- 핵심 API
- 데이터 모델
- 읽기 및 쓰기 흐름
- 컴포넌트 사이의 관계
- 시스템 규모에 대한 개략적인 계산
- 요구사항을 만족하는지 여부

최초 설계안을 설명한 뒤에는 면접관에게 의견을 구해야 한다.

> 우선 이 구조를 기준으로 진행해도 괜찮을까요? 동의하시면 쓰기 경로와 뉴스 피드 생성 과정을 더 자세히 설명하겠습니다.

이와 같이 면접관의 동의를 구하면 잘못된 방향으로 상세 설계를 진행하는 일을 줄일 수 있다.

## 뉴스 피드 시스템의 개략적 설계 예시

책에서는 뉴스 피드 시스템을 예로 들어 개략적인 설계와 상세 설계의 차이를 설명한다.

뉴스 피드 시스템은 크게 피드 발행과 피드 조회 흐름으로 나눌 수 있다.

### 피드 발행

사용자가 게시물을 작성하면 요청은 로드밸런서와 웹 서버를 거쳐 게시물 작성 서비스로 전달된다.

게시물 작성 서비스는 다음 작업을 수행할 수 있다.

1. 사용자 인증 및 권한을 확인한다.
2. 게시물 데이터를 데이터베이스에 저장한다.
3. 사용자 정보가 필요하면 사용자 캐시 또는 사용자 데이터베이스를 조회한다.
4. 피드 갱신 작업을 메시지 큐에 전달한다.
5. 피드 작업 서버가 메시지를 소비하여 팔로워들의 뉴스 피드를 갱신한다.
6. 갱신된 피드 정보를 뉴스 피드 캐시에 저장한다.
7. 필요한 경우 알림 서비스에 이벤트를 전달한다.

메시지 큐를 사용하면 게시물 저장 요청과 피드 생성 작업을 분리할 수 있다. 사용자는 게시물이 모든 팔로워의 피드에 반영될 때까지 기다리지 않고 빠르게 응답을 받을 수 있다.

### 피드 조회

사용자가 뉴스 피드를 요청하면 다음과 같은 흐름으로 처리할 수 있다.

1. 요청이 로드밸런서를 거쳐 웹 서버에 전달된다.
2. 웹 서버가 뉴스 피드 서비스에 조회를 요청한다.
3. 뉴스 피드 서비스가 뉴스 피드 캐시에서 게시물 ID 목록을 가져온다.
4. 게시물과 사용자 정보를 각각의 캐시 또는 데이터베이스에서 조회한다.
5. 조회한 결과를 조합하여 클라이언트에 반환한다.
6. 이미지와 동영상 같은 정적 콘텐츠는 CDN을 통해 제공한다.

개략적인 설계 단계에서는 위와 같은 주요 흐름과 컴포넌트를 확인하고, 상세 설계 단계에서 데이터 저장 방식, 피드 생성 방식, 캐시 정책 등을 깊게 다룬다.

## 3단계: 상세 설계

개략적인 설계에 대해 면접관과 합의했다면 중요한 컴포넌트를 선택하여 상세하게 설명한다.

모든 컴포넌트를 같은 깊이로 설명하기에는 면접 시간이 부족하므로 우선순위를 정해야 한다.

상세 설계 대상을 선택할 때는 다음 기준을 사용할 수 있다.

- 핵심 요구사항을 직접 처리하는 컴포넌트
- 가장 높은 트래픽을 받는 컴포넌트
- 단일 장애 지점이 될 가능성이 큰 컴포넌트
- 데이터 일관성 문제가 발생할 수 있는 컴포넌트
- 설계안의 핵심 트레이드오프가 드러나는 컴포넌트
- 면접관이 관심을 보이거나 추가 설명을 요청한 컴포넌트

뉴스 피드 시스템이라면 다음과 같은 주제를 상세하게 다룰 수 있다.

- 게시물 데이터 모델
- 피드 캐시의 자료 구조
- 메시지 큐와 작업 서버 구성
- 팔로워에게 피드를 전달하는 방식
- 유명 사용자로 인한 핫키 문제
- 캐시 장애 및 데이터베이스 장애 대응
- 중복 메시지 처리
- 읽기와 쓰기 경로의 확장 방법

상세 설계 중에도 면접관과 계속 소통해야 한다. 하나의 방법만 단정적으로 제시하기보다 가능한 선택지를 비교하고, 현재 요구사항에 적합한 방법을 선택해야 한다.

## 4단계: 마무리

상세 설계를 마쳤다면 전체 설계를 짧게 정리하고, 장애와 운영 및 향후 확장에 대해 논의한다.

마무리 단계에서는 다음 내용을 확인할 수 있다.

- 설계한 시스템의 전체 요청 흐름
- 현재 설계에서 병목이 발생할 수 있는 지점
- 서버나 데이터베이스에 장애가 발생했을 때의 동작
- 데이터 복제와 백업 방법
- 로그, 메트릭, 모니터링 방법
- 보안과 권한 관리
- 트래픽이 증가했을 때의 확장 방법
- 비용을 줄일 수 있는 부분
- 시간이 부족해 다루지 못한 개선 사항

면접관이 개선할 부분을 묻는다면 개선할 부분이 없다고 답하기보다, 현재 설계의 한계와 개선 방향을 설명해야 한다.

설계를 다시 한번 간략하게 요약하면 면접관이 전체 구조와 판단 과정을 확인하는 데 도움이 된다.

## 해야 할 것

- 질문을 통해 요구사항과 제약사항을 확인한다.
- 사용한 가정을 분명하게 밝힌다.
- 면접관이 사고 흐름을 이해할 수 있도록 계속 설명한다.
- 가능한 해결책이 여러 개라면 각각의 장단점을 비교한다.
- 개략적인 설계부터 제시하고 동의를 구한다.
- 핵심 컴포넌트부터 상세하게 설명한다.
- 설계 선택에 따른 트레이드오프를 설명한다.
- 막혔을 때는 지금까지 판단한 내용과 어려운 지점을 설명한 뒤 힌트를 요청한다.
- 피드백을 받으면 설계에 반영한다.
- 장애와 운영 및 확장 가능성을 함께 고려한다.

## 하지 말아야 할 것

- 요구사항을 확인하지 않고 바로 설계를 시작하지 않는다.
- 처음부터 특정 컴포넌트의 구현 세부사항에 지나치게 깊게 들어가지 않는다.
- 특정 기술을 사용하고 싶다는 이유만으로 설계에 포함하지 않는다.
- 하나의 설계가 유일한 정답인 것처럼 설명하지 않는다.
- 계산에 사용한 가정과 단위를 생략하지 않는다.
- 면접관과 소통하지 않은 채 혼자 설계를 진행하지 않는다.
- 면접관의 피드백을 방어적으로 받아들이지 않는다.
- 최초 설계안을 제시하는 것으로 면접이 끝났다고 생각하지 않는다.

## 시간 배분

45분 동안 시스템 설계 면접을 진행한다고 가정하면 다음과 같이 시간을 배분할 수 있다.

| 단계 | 권장 시간 |
| --- | ---: |
| 문제 이해 및 설계 범위 확정 | 3분~10분 |
| 개략적인 설계안 제시 및 동의 구하기 | 10분~15분 |
| 상세 설계 | 10분~25분 |
| 마무리 | 3분~5분 |

시간은 문제와 면접관의 요구에 따라 달라질 수 있다. 중요한 것은 모든 내용을 같은 깊이로 설명하는 것이 아니라, 면접관과 합의한 핵심 부분에 시간을 사용하는 것이다.

## 시스템 설계 면접에서의 핵심 태도

시스템 설계 면접은 완성된 정답을 발표하는 자리가 아니다.

요구사항을 확인하고, 가정을 세우고, 규모를 추정하고, 가능한 설계안을 비교하고, 면접관의 의견을 받아 설계를 개선하는 협력 과정이다.

따라서 최종 설계의 복잡성뿐 아니라 설계에 도달한 과정과 판단 근거를 명확하게 전달하는 것이 중요하다.
