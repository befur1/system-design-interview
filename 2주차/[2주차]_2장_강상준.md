### 1장과 연계해서 생각해보자
L1 캐시 기준으로 하위 레벨로 내려갈 때 L2캐시 참조는 14배, 메모리는 200배, 디스크 탐색은 20,000배 차이가 난다.  Latency를 낮추기 위해서 DB접근을 최소화해야 하는 이유가 명확해진다.

같은 데이터 센터 내에서의 메시지 왕복 지연시간이 발생한다(내부 통신도 공짜가 아님)
ex) 웹서버와 DB 서버 간의 통신, Master DB 와 Slave DB 간의 통신, Cache 서버와 DB 서버 간의 통신 등

캐시를 사용하는 게 생각보다 더 지연시간 이점이 많이 생긴다. DB는 Seek 지연 + 읽기 시간 + 네트워크 왕복 지연 시간이 추가로 발생하기 때문에. 어느 데이터를 캐시에 저장할지를 잘 고민해야할 것 같다.

메시지를 보낼 때면 데이터가 손상되지 않는 선에서 최대한 압축해서 보내는 게 좋을 것 같기도 하다.

개발자는 DB를 조회할 때 항상 N+1쿼리 문제를 생각해야 할 것 같다. JOIN을 걸어서 한 번에 쿼리로 가져오는 경우 쿼리당 10ms + 네트워크 왕복 지연 시간 + DB processing time이 발생하지만, N+1 쿼리로 가져오는 경우 쿼리당 10ms + 네트워크 왕복 지연 시간이 N번 발생 + DB processing time가 N번 발생하기 때문이다.
(기하급수적으로 늘어남..)

디스크 seek vs Read?
- Seek는 데이터를 읽기 위해 디스크의 물리적인 위치를 찾아가는 시간이고, Read는 그 위치에서 실제 데이터를 긁어오는 시간
- SSD는 물리적 헤드가 없어서 Seek 지연이 0.1ms 수준이지만 HDD랑 동일하게 순차읽기가 랜덤 읽기보다 빠르다.
