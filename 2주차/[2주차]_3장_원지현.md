# 3장_ 시스템 설계 면접 공략법



## 시스템 설계 면접의 본질
정해진 정답 하나를 도출하는 시험이 아니며, 두 엔지니어가 모호한 문제를 해결해 나가는 협업 과정임.
- 지원자의 기술적 능력뿐만 아니라 설계 프로세스, 커뮤니케이션 능력, 트레이드오프 분석 능력을 종합적으로 평가함.
- 경계해야 할 태도: 성급하게 다이어그램부터 그리기, 침묵 속에 혼자 생각하기, 피드백을 수용하지 않고 고집부리기.



## 4단계 문제 해결 프레임워크

1단계: 문제 이해 및 설계 범위 확정 (3~8분)
요구사항이 의도적으로 모호하게 주어지므로, 질문을 던져 시스템의 경계와 요구사항을 명확히 좁혀야 함.
- 구체적으로 어떤 기능들을 만들어야 하는가? (핵심 기능 정의)
- 시스템의 사용자 규모는 어느 정도인가? (DAU, MAU)
- 회사의 성장세와 예상 규모 확장 속도는 어떠한가?
- 주 사용 기술 스택이나 활용 가능한 기존 서비스가 있는가?
- 모바일 앱, 웹 등 어떤 클라이언트를 지원해야 하는가?

2단계: 개략적인 설계안 제시 및 동의 구하기 (10~15분)
면접관과 함께 기본 뼈대를 구성하고 큰 그림에 대해 사전 동의를 얻는 단계임.
- 시스템의 주요 컴포넌트(클라이언트, 로드밸런서, 웹 서버, 데이터베이스, 캐시, CDN 등)가 포함된 핵심 아키텍처 블록 다이어그램을 그림.
- 핵심 기능에 필요한 RESTful API 엔드포인트(엔드포인트 명칭, 파라미터, 반환 형식)를 정의함.
- 데이터 저장을 위한 핵심 DB 스키마를 개략적으로 정의함.
- 2단계 설계안이 2장에서 배운 규모 추정치(QPS, 용량)를 감당할 수 있는지 가볍게 검증하고 면접관의 피드백을 청취함.

3단계: 상세 설계 (10~25분)
개략적 설계안을 바탕으로 시스템에서 가장 중요하거나 병목이 될 만한 컴포넌트를 깊게 파고드는 단계임.
- 면접관과 상의하여 어느 영역에 우선순위를 두고 깊게 들어갈지 결정함.
- 단일 장애 지점(SPOF)을 식별하고 이를 완화할 다중화 방안 제시.
- 캐시 계층의 상세 정책(TTL, 캐시 무효화 시점, 일관성 유지 전략) 점검.
- 데이터베이스 확장 방안(샤딩 키 선정 기준, 복제 지연 문제 해결) 논의.
- 특정 유명인사(Celebrity) 트래픽 집중 등 핫스팟 문제 처리 기법 구체화.

4단계: 마무리 (3~5분)
설계를 되돌아보며 부족했던 점을 스스로 짚어보고 후속 개선점을 제시하는 단계임.
- 스스로 시스템의 병목 구간과 한계점을 솔직하게 짚고 개선 방향 제안.
- 서버 다운 등 에러 발생 시의 자동 장애 복구(Failover) 시나리오 언급.
- 시스템 모니터링, 로그 수집, 메트릭 추적 및 배포 자동화 파이프라인 언급.
- 트래픽이 현재보다 10배~100배 더 증가했을 때의 미래 대응책 간략히 제시.



## 면접 시 해야 할 것과 하지 말아야 할 것

해야 할 것:
- 질문을 통해 모호한 요구사항을 스스로 명확히 할 것.
- 면접관에게 끊임없이 자신의 사고 과정을 설명하며 소통할 것.
- 여러 대안을 제시하고 각 대안의 장단점(Trade-off)을 비교 분석할 것.
- 가장 중요한 컴포넌트부터 풀고 점진적으로 디테일하게 들어갈 것.

하지 말아야 할 것:
- 요구사항을 마음대로 넘겨짚고 혼자 설계를 끝까지 진행하지 말 것.
- 면접관의 힌트나 피드백을 무시하고 본인의 첫 설계안만 고집하지 말 것.
- 아무 말 없이 혼자 침묵 속에서 고민하지 말 것.
- 전체적인 큰 그림이 합의되기 전에 특정 세부 기술에만 과도하게 매몰되지 말 것.
