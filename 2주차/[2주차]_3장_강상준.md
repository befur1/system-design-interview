시스템 설계 면접은 동료와 모호한 문제를 풀기 위해 협력하여 해결책을 찾아내는 과정에 대한 시뮬레이션이다 - 정답도 없고 정형화된 과정도 없다.
A라는 시스템을 설계하려고 결정하기 까지의 과정과 의도가 제일 중요하다

## 효과적 면접을 위한 4단계 접근법
시스템 설계를 위한 접근법이라고 생각해도 무방하지 않을까?
### 1단계 - 문제 이해 및 설계 범위 확정
- 구체적으로 어떤 기능들을 만들어야 하는가?
- 제품의 사용자수(트래픽)은 얼마나 되는가?
- 회사의 규모 성장은 어느정도의 속도로 이루어지는가(확장 가능성)
- 기술 스택 및 레거시는 어떤 게 있는가?

우리가 다 이미 해왔던 과정이라고 생각함. PM과 질의를 통해 기능명세와 정책을 확정지었던 경험과 같아보인다.

개인적인 질문
- 우리는 개발자인데 다중화를 하고 캐시를 두는 것 이외에 코드 레벨에서 성능 개선을 위해 어떤 노력을 해야하는걸까? 트래픽이 많아지면 고려해야될 사항이 있을까?

트래픽이 작을 때는 **"기능이 에러 없이 잘 돌아가는가?"**에 집중하여 코드를 짜지만,
트래픽이 커질수록 코드는 "어떻게 해야 톰캣 스레드와 DB 커넥션을 0.001초라도 빨리 풀어줄 수 있는가?", **"서버가 10대로 늘어났을 때도 데이터가 꼬이지 않는가?"**를 해결하는 코드가 된다.

1. 동기(Sync) 코드 ➡️ 비동기 / 이벤트 기반 코드로 전환
- 하나의 메서드에 Transactional 걸고 여러 동작들을 다 동기적으로 쓰면 쓰레드 + DB 커넥션이 계속 묶여있어서 터질 수 있음
- 핵심 로직만 동기적으로 처리하고 이벤트 발행해서 비동기적으로 처리하게 바꿈(쓰레드를 빠르게 풀어줌)

2. Transactional의 범위 최소화
- 메서드 통으로 걸어두면 DB쿼리 나가는 부분 이외의 작업이 끝나도 계속 DB 커넥션이 묶여있게됨
- 쿼리 나가는 부분만 걸어두고 복잡한 로직은 트랜잭션 밖에서 처리
- 우리가 Read는 트랜잭셔널 안 걸고 쓰기 로직에만 걸어둔 것도 같은 맥락인듯?

3. 동시성 제어 방식의 변화 (단일 JVM 락 ➡️ 분산 락)
- 트래픽이 적을 때는 synchronized 키워드 같은 자바의 내장 락만으로도 충분
- 각자 서버의 문을 잠그지 말고, **모든 서버(1, 2, 3번)가 함께 바라보는 제3의 중재자(Redis)**를 둔다. 열쇠를 Redis에 딱 1개만 넣어두고 쓰기가 필요하면 열쇠를 가져가는 방식임.

4. 쿼리 방식의 변화: 배치(Bulk) 처리 & No-Offset 페이징
- 소규모에는 단건 저장을 반복해도 문제가 없지만 규모가 커지면 네트워크 왕복 지연 + DB 락 경합으로 서버가 터질 수 도 있음
- 벌크로 묶어서 쿼리를 날림
- 일반 페이징 말고 커서 기반 페이징으로 구현(ID가 1000인 다음 데이터 20개 보여줘와 같은 방식..)

4번은 노디에서 했었으니까 관련코드 찾아보면 좋을듯
