# 1장: 사용자 수에 따른 규모 확장성

## 단일 서버

단일 서버는 웹 애플리케이션, 데이터베이스, 캐시 등 모든 컴포넌트가 한 대의 서버에서 실행되는 가장 단순한 구조이다.

사용자의 요청은 다음과 같은 순서로 처리된다.

1. 사용자가 도메인 이름을 이용해 웹사이트에 접속한다.
2. DNS가 도메인 이름을 IP 주소로 변환해 반환한다.
3. 클라이언트가 해당 IP 주소로 HTTP 요청을 보낸다.
4. 웹 서버가 HTML 페이지나 JSON 형태의 응답을 반환한다.

초기에는 구조가 단순해 개발과 운영이 쉽지만, 서버 한 대에 장애가 발생하면 서비스 전체가 중단된다. 또한 트래픽과 데이터가 증가하면 한 서버의 자원만으로 처리하기 어려워진다.

## 데이터베이스

사용자가 늘어나면 웹·모바일 트래픽을 처리하는 웹 계층과 데이터를 보관하는 데이터 계층을 서로 다른 서버로 분리한다. 이렇게 하면 웹 서버와 데이터베이스를 각자의 부하에 맞춰 독립적으로 확장할 수 있다.

### 어떤 데이터베이스를 사용할 것인가?

데이터베이스는 크게 관계형 데이터베이스와 비관계형 데이터베이스로 나눌 수 있다.

| 구분 | 관계형 데이터베이스(RDBMS) | 비관계형 데이터베이스(NoSQL) |
|---|---|---|
| 데이터 표현 | 테이블, 행, 열 | 키-값, 문서, 그래프, 칼럼 등 |
| 특징 | SQL과 JOIN을 이용해 데이터 관계를 표현 | 접근 패턴에 맞춰 데이터를 유연하게 저장 |
| 예시 | MySQL, PostgreSQL, Oracle | Redis, CouchDB, Neo4j, Cassandra 등 |

대부분의 일반적인 서비스에서는 관계형 데이터베이스가 좋은 기본 선택이다. 다음과 같은 경우에는 NoSQL을 고려할 수 있다.

- 아주 낮은 응답 지연 시간이 필요할 때
- 다루는 데이터가 비정형일 때
- 데이터를 직렬화·역직렬화하는 방식만으로 처리할 수 있을 때
- 아주 많은 양의 데이터를 분산 저장해야 할 때

데이터베이스는 유행이나 익숙함만으로 선택하는 것이 아니라 데이터 구조, 조회 방식, 트랜잭션과 일관성 요구를 기준으로 선택해야 한다.

## 수직적 규모 확장 vs 수평적 규모 확장

수직적 규모 확장(Scale Up)은 기존 서버에 더 좋은 CPU나 더 많은 메모리를 추가하는 방식이다. 구조가 단순하고 트래픽이 많지 않을 때 적용하기 쉽지만, 한 서버에 자원을 무한히 추가할 수 없고 서버 장애에 취약하다.

수평적 규모 확장(Scale Out)은 서버를 여러 대로 늘려 요청을 분산하는 방식이다. 구조와 운영은 복잡해지지만 대규모 트래픽에 대응하기 쉽고, 특정 서버의 장애가 서비스 전체 장애로 이어질 가능성을 낮출 수 있다.

| 구분 | 수직적 확장 | 수평적 확장 |
|---|---|---|
| 확장 방법 | 한 서버의 성능 향상 | 서버 대수 증가 |
| 장점 | 단순하고 적용이 쉬움 | 확장성과 가용성이 높음 |
| 한계 | 하드웨어 한계, 높은 비용, 단일 장애 지점 | 부하 분산과 상태 관리가 필요 |

### 로드밸런서

로드밸런서는 여러 웹 서버에 트래픽을 고르게 분산한다.

- 사용자는 웹 서버가 아니라 로드밸런서의 공개 IP 주소로 접속한다.
- 로드밸런서와 웹 서버는 사설 IP 주소로 통신할 수 있다.
- 특정 웹 서버가 중단되면 요청을 정상 서버로 전달한다.
- 트래픽이 증가하면 웹 서버를 추가해 처리량을 늘릴 수 있다.

로드밸런서를 도입하면 웹 계층의 가용성과 확장성이 높아진다. 다만 정상 서버를 판별하기 위한 헬스 체크와 로드밸런서 자체의 다중화도 함께 고려해야 한다.

### 데이터베이스 다중화

데이터베이스 서버 사이에 주(Primary)와 부(Replica) 관계를 설정하고 데이터의 사본을 여러 서버에 보관하는 방식이다.

- Primary 데이터베이스는 데이터 추가, 수정, 삭제와 같은 쓰기 연산을 처리한다.
- Replica 데이터베이스는 Primary의 데이터를 복제하고 주로 읽기 연산을 처리한다.
- 일반적으로 읽기 연산이 쓰기 연산보다 많기 때문에 Replica를 여러 대 둘 수 있다.

데이터베이스 다중화의 장점은 다음과 같다.

- **성능**: 읽기 요청을 여러 Replica에 분산할 수 있다.
- **안정성**: 데이터 사본을 여러 위치에 보관할 수 있다.
- **가용성**: 일부 서버에 장애가 발생해도 다른 서버가 요청을 처리할 수 있다.

Replica에 장애가 발생하면 다른 Replica나 Primary가 읽기 요청을 처리한다. Primary에 장애가 발생하면 Replica 중 하나를 새로운 Primary로 승격할 수 있다. 이때 최신 변경 사항이 Replica에 아직 전달되지 않은 복제 지연 문제도 고려해야 한다.

## 캐시

캐시는 값비싼 연산 결과나 자주 조회되는 데이터를 빠른 메모리에 저장하여 이후 요청을 더 빠르게 처리하도록 돕는 저장소이다. 캐시를 사용하면 응답 시간이 줄어들고 데이터베이스의 부하도 감소한다.

### 캐시 계층

캐시 계층은 웹 서버와 데이터베이스 사이에 두며 다음과 같이 동작한다.

1. 웹 서버가 캐시에 필요한 데이터가 있는지 확인한다.
2. 데이터가 있으면 캐시에서 바로 반환한다(Cache Hit).
3. 데이터가 없으면 데이터베이스에서 조회한다(Cache Miss).
4. 조회한 데이터를 캐시에 저장한 뒤 사용자에게 반환한다.

애플리케이션이 캐시와 데이터베이스를 직접 확인하는 이러한 방식은 일반적으로 Cache-Aside 전략이라고 한다. 캐시 계층은 데이터베이스와 별도로 확장할 수 있다는 장점도 있다.

### 캐시 사용 시 유의할 점

- **사용 시점**: 데이터 갱신은 드물지만 조회가 빈번할 때 효과적이다.
- **데이터 종류**: 영구 보관해야 하는 원본 데이터는 반드시 지속성 저장소에도 저장해야 한다.
- **만료 정책**: 만료 시간이 너무 짧으면 DB 조회가 증가하고, 너무 길면 오래된 데이터가 반환될 수 있다.
- **일관성**: 원본 데이터가 변경될 때 캐시를 갱신하거나 무효화하는 방법이 필요하다.
- **장애 대응**: 캐시 서버 한 대가 새로운 단일 장애 지점이 되지 않도록 다중화를 고려해야 한다.
- **메모리 크기**: 캐시가 너무 작으면 데이터가 자주 방출되어 효과가 떨어진다.
- **데이터 방출 정책**: LRU, LFU, FIFO 등의 정책을 서비스 특성에 맞게 선택해야 한다.

캐시는 단순히 데이터를 저장하는 것보다 만료와 원본 데이터의 일관성을 관리하는 일이 중요하다.

## 콘텐츠 전송 네트워크(CDN)

CDN은 이미지, 동영상, CSS, JavaScript 같은 정적 콘텐츠를 전송하기 위해 지리적으로 분산된 서버 네트워크이다. 사용자는 원본 서버가 아니라 자신과 가까운 CDN 서버에서 콘텐츠를 받아 지연 시간을 줄일 수 있다.

CDN은 다음과 같이 동작한다.

1. 사용자가 CDN URL을 통해 콘텐츠를 요청한다.
2. CDN 서버에 콘텐츠가 없으면 원본 서버에서 가져온다.
3. 원본 서버가 콘텐츠와 TTL을 CDN에 전달한다.
4. CDN이 콘텐츠를 캐시하고 사용자에게 반환한다.
5. 콘텐츠가 만료되기 전의 동일한 요청은 CDN 캐시에서 처리한다.

### CDN 사용 시 고려해야 할 사항

- **비용**: 데이터 전송량에 따라 비용이 발생하므로 자주 사용되지 않는 콘텐츠는 제외할 수 있다.
- **만료 시한**: 너무 길면 최신성이 떨어지고, 너무 짧으면 원본 서버 요청이 증가한다.
- **장애 대응**: CDN 장애 시 원본 서버에서 직접 콘텐츠를 가져올 수 있는 방법을 고려해야 한다.
- **콘텐츠 무효화**: CDN API나 `image.png?v=2`와 같은 오브젝트 버저닝을 이용해 기존 캐시를 무효화할 수 있다.

## 무상태(stateless) 웹 계층

웹 서버를 수평적으로 확장하려면 사용자의 요청이 특정 서버에 의존하지 않도록 만들어야 한다.

### 상태 정보 의존적인 아키텍처

상태 유지(Stateful) 아키텍처는 사용자 세션과 같은 상태 정보를 특정 웹 서버의 메모리에 저장한다. 사용자 A의 세션이 서버 1에 있다면 이후 요청도 서버 1로 전달되어야 한다.

이를 위해 고정 세션(Sticky Session)을 사용할 수 있지만 다음과 같은 문제가 생긴다.

- 서버 추가와 제거가 어려워진다.
- 특정 서버에 트래픽이 집중될 수 있다.
- 서버 장애 시 해당 서버가 가진 상태 정보가 사라질 수 있다.
- 로드밸런서의 구성이 복잡해진다.

### 무상태 아키텍처

무상태(Stateless) 아키텍처는 세션과 같은 상태 정보를 웹 서버 외부의 공유 저장소에 보관한다. 웹 서버는 필요할 때 RDBMS, NoSQL, Redis 등의 저장소에서 상태 정보를 가져온다.

따라서 사용자의 요청을 어떤 웹 서버로 보내도 처리할 수 있고, 서버를 자유롭게 추가하거나 제거할 수 있다. 무상태란 시스템 전체에 상태가 없다는 의미가 아니라 특정 웹 서버의 로컬 상태에 요청 처리가 의존하지 않는다는 뜻이다.

## 데이터 센터

서비스 규모가 매우 커지면 여러 데이터 센터를 사용할 수 있다. 지리적 라우팅(GeoDNS)을 이용하면 사용자를 가까운 데이터 센터로 안내하고, 한 데이터 센터에 장애가 발생하면 다른 데이터 센터로 트래픽을 우회할 수 있다.

다중 데이터 센터를 구성할 때는 다음 문제를 해결해야 한다.

- **트래픽 우회**: 사용자를 올바른 데이터 센터로 보내야 한다.
- **데이터 동기화**: 데이터 센터마다 데이터가 달라지지 않도록 복제해야 한다.
- **테스트와 배포**: 모든 데이터 센터에 동일한 버전과 설정을 배포해야 한다.
- **장애 대응**: 한 데이터 센터가 중단됐을 때 다른 센터가 증가한 트래픽을 감당해야 한다.

여러 데이터 센터는 지연 시간과 가용성을 개선하지만 데이터 일관성과 운영 복잡도라는 새로운 문제를 만든다.

## 메시지 큐

메시지 큐는 메시지를 임시로 보관하고 비동기 통신을 지원하는 컴포넌트이다.

- **생산자(Producer/Publisher)**는 처리할 작업을 메시지로 만들어 큐에 넣는다.
- **소비자(Consumer/Subscriber)**는 큐에서 메시지를 꺼내 작업을 처리한다.

생산자와 소비자가 서로의 상태에 직접 의존하지 않으므로 결합도가 낮아진다. 소비자가 일시적으로 작업을 처리하지 못해도 메시지를 큐에 보관할 수 있고, 작업량이 늘면 소비자만 추가해 처리량을 높일 수 있다.

이미지 보정이나 이메일 전송처럼 시간이 오래 걸리는 작업을 웹 서버가 직접 처리하지 않고 메시지 큐와 작업 서버로 넘기면 사용자 요청에 빠르게 응답할 수 있다. 메시지를 안전하게 처리하려면 영속성, 처리 확인, 실패 재시도와 같은 설정도 필요하다.

## 로그, 메트릭 그리고 자동화

서비스와 서버의 수가 많아지면 시스템을 안정적으로 운영하기 위해 로그, 메트릭, 자동화 도구가 필요하다.

- **로그**: 오류와 요청 처리 기록을 남긴다. 여러 서버의 로그를 중앙 서비스에 모으면 검색과 분석이 쉬워진다.
- **호스트 단위 메트릭**: CPU, 메모리, 디스크 I/O 등 서버의 상태를 나타낸다.
- **종합 메트릭**: 응답 시간, 오류율, DB 성능, 캐시 적중률 등 시스템 계층의 상태를 나타낸다.
- **비즈니스 메트릭**: 일별 활성 사용자, 수익, 재방문율 등 서비스의 상태를 나타낸다.
- **자동화**: 빌드, 테스트, 배포 절차를 자동화하여 개발 생산성과 배포 안정성을 높인다.

### 메시지 큐, 로그, 메트릭, 자동화 등을 반영하여 수정한 설계안

규모가 커진 시스템에서는 정적 콘텐츠를 CDN에서 제공하고, 동적 요청은 로드밸런서가 여러 무상태 웹 서버에 분산한다. 웹 서버는 캐시를 먼저 확인하고 필요한 경우 데이터베이스를 조회한다.

오래 걸리는 작업은 메시지 큐에 넣고 작업 서버가 비동기로 처리한다. 각 계층에서 발생하는 로그와 메트릭은 중앙 모니터링 시스템으로 모으며, 빌드·테스트·배포는 자동화한다. 이렇게 각 계층을 분리하면 병목이 생긴 부분만 독립적으로 확장할 수 있다.

## 데이터베이스의 규모 확장

데이터베이스도 트래픽과 데이터 증가에 맞춰 수직적 또는 수평적으로 확장할 수 있다.

### 수직적 확장

기존 데이터베이스 서버에 더 좋은 CPU, 더 많은 메모리와 디스크를 추가하는 방식이다. 적용이 비교적 단순하지만 하드웨어 확장에 한계가 있고 비용이 많이 들며, 서버 한 대가 단일 장애 지점이 될 수 있다.

### 수평적 확장

데이터베이스의 수평적 확장을 샤딩(Sharding)이라고 한다. 대규모 데이터베이스를 샤드라고 부르는 작은 단위로 분할하고 여러 서버에 저장한다. 모든 샤드는 같은 스키마를 사용할 수 있지만 서로 다른 데이터를 보관한다.

어떤 데이터를 어느 샤드에 저장할지는 샤딩 키가 결정한다. 예를 들어 샤드가 네 개일 때 `user_id % 4`의 결과로 저장할 샤드를 선택할 수 있다. 샤딩 키는 데이터와 요청이 특정 샤드에 집중되지 않도록 신중하게 선택해야 한다.

샤딩을 도입하면 다음과 같은 문제가 생긴다.

- **데이터 재샤딩**: 데이터 증가나 불균형으로 샤드 수와 분배 규칙을 변경해야 할 수 있다.
- **유명인사 문제(Hotspot Key)**: 특정 데이터에 요청이 집중되어 한 샤드에 과부하가 발생할 수 있다.
- **조인과 비정규화**: 여러 샤드에 걸친 JOIN이 어려워 데이터 중복을 허용하거나 애플리케이션에서 결과를 합쳐야 할 수 있다.

샤딩은 확장성이 높지만 구조와 운영이 복잡하다. 따라서 더 단순한 방법으로 해결할 수 없는 규모인지 확인한 후 도입해야 한다.

## 백만 사용자, 그리고 그 이상

시스템의 규모를 확장하는 것은 지속적이고 반복적인 과정이다. 사용자 증가에 따라 생기는 병목을 관찰하고 다음 방법을 상황에 맞게 적용해야 한다.

- 웹 계층을 무상태로 설계한다.
- 각 계층에 다중화를 도입한다.
- 자주 조회되는 데이터를 캐시한다.
- 정적 콘텐츠는 CDN을 통해 제공한다.
- 여러 데이터 센터를 지원한다.
- 오래 걸리는 작업은 메시지 큐로 분리한다.
- 데이터 계층은 필요할 때 샤딩으로 확장한다.
- 각 계층을 독립적인 서비스로 분리한다.
- 로그와 메트릭으로 시스템을 모니터링한다.
- 빌드, 테스트, 배포 과정을 자동화한다.

중요한 것은 처음부터 모든 기술을 적용하는 것이 아니라 현재 시스템에서 발생한 문제를 확인하고 그 문제를 해결하는 기술을 단계적으로 도입하는 것이다.
