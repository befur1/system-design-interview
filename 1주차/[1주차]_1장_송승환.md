# 가면사배대시설기

## 1장 요약

### 1-1. 단일 서버

→ 모든 컨포넌트가 한 대의 서버에서 실행되는 간단한 시스템

### 1-2. 데이터베이스

→ 하나의 서버는 트래픽 처리 용도(웹 계층), 다른 하나는 데이터베이스용(데이터 계층)

관계형 데이터베이스(RDMS) VS 비관계형 데이터베이스(NoSQL)

1. RDMS
- MySQLL, Oracle DB, PostgreSQL
- 자료를 테이블과 열, 컬럼으로 표현

ii. NoSQL

- 키-값 저장소
- 그래프 저장소
- 컬럼 저장소
- 문서 저장소

### 2. 규모 확장

수직적 규모 확장(scale up):  서버에 고사양 자원(더 좋은 CPU, 더 많은 RAM)을 추가하는 행위

단점:

- 확장의 한계 - CPU 무한대로 증설할 방법이 없음
- 자동복구 방안이나 다중화 방안을 제시X - 서버가 하나이기 때문에 장애시 서비스 중단

→ 수평적 규모 확장(scale out): 더 많은 서버를 추가하는 방식을 추천

`로드 밸런서`는 부하 분산 집합에 속한 웹 서버들에게 트래픽 부하를 고르게 분산하는 역할

1. 사용자가 public IP 주소로 접속
2. 그러면 로드밸런서가 트래픽이 덜 한 웹 서버로 보냄

`데이터베이스 다중화`는 주(master)-부(slave) 관계 설정하고 데이터 원본은 주 서버에, 사본은 부 서버에 저장

- master에서 쓰기 연산을 지원
- slave에서는 읽기 연산 및 사본 전달만 받음

### 3. 캐시

애플리케이션의 성능은 DB의 호출 횟수에 따라 크게 좌우 되는데, 캐시가 자주 참조되는 데이터를 메모리 안에 두고 요청을 더 빨리 처리할 수 있게 해 줌

### 4. 콘텐츠 전송 네트워크(CDN)

CDN은 ‘자주 변하지 않는 모든 리소스’를 다루는데 스트리밍 동영상 파일, 웹 화면을 꾸미는 파일, 웹 폰트, 다운로드용 설치 파일과 같은 걸 여러 CDN 서버에 저장하여 물리적 거리에 따른 latency를 줄여줌

### 5. 웹 계층

`stateful architecture`는 특정 사용자의 정보를 저장한 그 특정 서버로 인증이나 요청이 항상 거기로 향해야해서 로드밸런서에 부담을 줌

`stateless architecture`는 상태 정보가 필요할 경우 공유 저장소로부터 데이터를 가져와서, 구조가 단순하고 안정적임

### 6. 데이터 센터

큰 서비스일 수록 여러 데이터 센터를 사용하게 됨. 이때, 사용자는 보통 `geoDNS-routing`을 통해 도메인이름을 어떤 IP주소로 변환할 지 결정

생각해야하는 점:

- 트래픽 우회 - 트래픽을 효과적으로 보내는 방법을 찾아야 함
- 데이터 동기화 - 데이터 센터마다 별도의 DB를 사용한다면, 둘의 동기화를 하는 효율적 방법이 필요

### 7. 메세지 큐

메세지 큐는 메세지의 버퍼 역할을 하며, 비동기적으로 전송함

`비동기적`이라고 하는 것은 작업을 요청해 두고, 그 결과가 당장 나오지 않더라도 일단 다음 작업으로 넘어가는 방식

### 8. 로그, 메트릭 그리고 자동화

- 로그: 에러 로그는 서버 단위로 모니터링할 수도 있고, 단일 서비스로 모아주는 도구를 활용하면 더 쉬움
- 메트릭: 메트릭을 잘 수집하면 사업 현황에 관한 유용한 정보를 얻을 수 있고, 시스템의 현재 상태를 손쉽게 파악할 수 있음
- 자동화: 시스템이 크고 복잡해지면 생산성을 높이기 위해 사용해야 함

### 9. 백만 사용자, 그리고 그 이상

시스템의 규모를 확장하는 것은 지속적이고 반복적인 과정

### 10. 마무리

- 웹 계층은 무상태 계층으로
- 모든 계층에 다중화 도입
- 가능한 한 많은 데이터를 캐시할 것
- 여러 데이터 센터를 지원할 것
- 정적 콘텐츠는 CDN을 통해 서비스할 것
- 데이터 계층은 샤딩을 통해 그 규모를 확장할 것
- 각 계층은 독립적 서비스로 분할할 것
- 시스템을 지속적으로 모니터링하고, 자동화 도구들을 활용할 것
