## 단일 서버
모든 컴포넌트가 한 대의 서버에서 실행되는 간단한 시스템 설계를 하기 위해서는 사용자 요청 처리 흐름을 알아야 함.
1. 사용자는 도메임 이름을 이용하여 웹사이트에 접속
2. DNS 조회 결과로 IP 주소 반환
3. 해당 IP 주소로 HTTP 요청 전달
4. 요청을 받은 웹 서버는 HTML/JSON 응답 반환



## 데이터베이스
사용자가 늘면 서버 하나로는 부족하기에 여러 서버를 두어야 함. 서버 한 대는 웹/모바일 트래픽 처리 용도고 다른 하나는 데이터베이스용임.
- 웹/모바일 트래픽 처리 용도(웹 계층)와 데이터베이스용(데이터 계층) 서버를 분리하면 각각을 독립적으로 확장해 나갈 수 있음.

어떤 데이터베이스를 사용할 것인가?
대부분의 경우 관계형 데이터베이스가 최선의 선택이며, 특수한 경우엔 비-관계형 데이터베이스를 선택할 수 있음. (ex. 아주 낮은 응답 지연시간이 요구됨, 다루는 데이터가 비정형임, 데이터를 직렬화하거나 역직렬화 할 수 있기만 하면 됨, 아주 많은 양의 데이터를 저장해야 함)



## 수직적 규모 확장 vs 수평적 규모 확장
수직적 규모 확장 vs 수평적 규모 확장
수직적 규모 확장: 스케일 업이라고도 하며 서버에 고사양 CPU, RAM을 추가하는 행위
- 한계: 한 대의 서버에 CPU나 메모리를 무한대로 증설할 수 없음. 장애에 대한 자동 복구 방안이나 다중화 방안을 제시하지 않기 때문에 서버에 장애가 발생하면 웹사이트/앱은 중단됨.
  수평적 규모 확장: 스케일 아웃이라고도 하며 서 많은 서버를 추가하여 성능을 개선하는 행위
  -> 결론: 로드밸런스를 도입하자!

로드밸런서: 부하 분산 집합에 속한 웹 서버들에게 트래픽 부하를 고르게 분산
- 사용자는 로드밸런서의 공개 IP 주소(Public IP)로 접속하며, 웹 서버는 클라이언트의 접속을 직접 처리하지 않음.
- 보안 강화를 위해 로드밸런서와 웹 서버 간의 통신에는 사설 IP 주소(Private IP)를 사용함.
- 장애 자동 복구(Failover): 서버 1이 다운되면 모든 트래픽이 서버 2로 전송되므로 웹사이트 전체가 다운되는 일을 방지함. 트래픽이 가파르게 증가할 때도 웹 서버 계층에 서버만 추가하면 로드밸런서가 알아서 트래픽을 분산함.

데이터베이스 다중화: 서버 사이에 주-부 관계 설정
주 데이터베이스에서 쓰기 연산을 지원하고 부 데이터베이스에서 그 사본을 전달받아 읽기 연산만을 지원함.
- 대부분의 애플리케이션은 읽기 연산의 비중이 쓰기 연산보다 훨씬 높으므로, 부 데이터베이스의 수가 주 데이터베이스보다 많게 설정함.
- 장점: 1) 더 나은 성능: 병렬로 처리될 수 있는 질의의 수가 늘어나므로 성능이 좋아짐. 2) 안정성: 자연 재해 등의 이유로 데이터베이스 서버 가운데 일부가 파괴되어도 데이터는 보존됨. 3) 가용성: 데이터를 복제해둠으로써 하나의 데이터베이스 서버에 장애가 생겨도 다른 서버에서 가져와 서비스를 이어나갈 수 있음.
- 장애 대응: 부 서버가 한 대뿐인데 다운되면 읽기 연산은 일시적으로 주 서버로 전달되고 즉시 새 부 서버가 장애 서버를 대체함. 주 서버가 다운되면 부 서버가 새로운 주 서버로 승격됨.



## 캐시
캐시: 값비싼 연산 결과 또는 자주 참조되는 데이터를 메모리 안에 두고, 뒤이은 요청이 보다 빨리 처리될 수 있도록 하는 저장소

캐시 계층: 데이터가 잠시 보관되는 곳으로 데이터베이스보다 훨씬 빠름
- 장점: 1) 성능 개선 2) 데이터베이스의 부하 감소 3) 캐시 계층의 규모를 독립적으로 확장시킬 수 있음

캐시 우선 읽기 전략:
- 요청을 받은 웹 서버는 캐시에 응답이 저장되어 있는지 확인(Cache Hit). 저장되어 있다면 해당 데이터를 즉시 클라이언트에 반환함.
- 데이터가 캐시에 없다면(Cache Miss) 데이터베이스 질의를 통해 데이터를 찾아 캐시에 저장한 뒤 클라이언트에 반환함. (주도형 캐시 / Read-Through 전략)

캐시 사용 시 유의할 점:
1) 캐시는 어떤 상황에 바람직한가?
- 데이터 갱신은 자주 일어나지 않지만 참조가 빈번하게 일어날 때 바람직함.
2) 어떤 데이터를 캐시에 두어야 하는가?
- 캐시는 휘발성 메모리에 데이터를 두므로 영속적으로 보관해야 하는 데이터는 캐시에 두지 말아야 함.
3) 캐시에 있는 데이터는 어떻게 만료(expire)되는가?
- 이에 대한 정책을 마련해야 함. 만료 기한이 너무 짧으면 데이터베이스를 너무 자주 읽게 되고, 너무 길면 원본 데이터와 차이가 날 가능성이 높아짐.
4) 일관성(Consistency)은 어떻게 유지되는가?
- 데이터 저장소의 원본과 캐시 내의 사본이 같은지 확인해야 하며, 저장소와 캐시 갱신 연산이 단일 트랜잭션으로 처리되지 않는 경우 일관성이 깨질 수 있음.
5) 장애에는 어떻게 대처할 것인가?
- 캐시 서버를 한 대만 두는 경우 해당 서버가 단일 장애 지점(SPOF)이 될 가능성이 있으므로, 여러 지역에 걸쳐 캐시 서버를 분산해야 함.
6) 캐시 메모리는 얼마나 크게 잡을 것인가?
- 캐시 메모리가 너무 작으면 데이터가 캐시에서 너무 자주 밀려나(Eviction) 캐시의 성능이 저하되므로, 넉넉하게 잡는 것이 바람직함.
7) 데이터 방출(Eviction) 정책은 무엇인가?
- 캐시가 꽉 찼을 때 새 데이터를 넣기 위해 기존 데이터를 내보내는 알고리즘으로, 가장 널리 쓰이는 LRU(Least Recently Used), LFU(Least Frequently Used), FIFO(First In First Out) 등이 있음.



## 콘텐츠 전송 네트워크(CDN)
CDN:
정적 콘텐츠를 전송하는 데 쓰이는, 지리적으로 분산된 서버의 네트워크. 이미지, 비디오, CSS, JavaScript 파일 등을 캐시할 수 있음.

CDN 과정:
1. 사용자 A가 이미지 URL을 이용해 image.png에 접근함. URL의 도메인은 CDN 서비스 사업자가 제공한 것임.
2. CDN 서버의 캐시에 해당 이미지가 없는 경우(Cache Miss), 서버는 원본(Origin) 서버에 요청하여 파일을 가져옴.
3. 원본 서버가 파일을 CDN 서버에 반환하고, 응답의 HTTP 헤더에는 해당 파일이 얼마 동안 캐시될 수 있는지 나타내는 TTL(Time to Live) 값이 들어있음.
4. CDN 서버는 파일을 캐시하고 사용자 A에게 반환함.
5. 이미지 파일이 만료(TTL 경과)되기 전까지 사용자 B가 같은 이미지에 대해 보내는 요청은 CDN 캐시에서 바로 서비스됨.

CDN 사용 시 고려해야 할 사항:
1) 비용
- 제3자 제공업체에 의해 운영되므로 CDN으로 들어가고 나가는 데이터 전송 양에 따라 요금을 냄. 자주 사용되지 않는 콘텐츠를 캐싱하는 것은 이득이 크지 않으므로 캐시에서 제외하는 것을 고려해야 함.
2) 적절한 만료 시한 설정
- 시의성이 중요한 콘텐츠의 경우 만료 시한을 잘 정해야 함. 너무 길면 신선도가 떨어지고, 너무 짧으면 원본 서버에 빈번히 접속하게 됨.
3) CDN 장애에 대한 대처 방안
- CDN 자체가 죽었을 때 웹사이트/애플리케이션이 어떻게 동작해야 하는지 고려해야 함. 가령 CDN이 응답하지 않으면 문제를 감지하여 원본 서버로부터 직접 콘텐츠를 가져오도록 클라이언트를 구성하는 것이 필요함.
4) 콘텐츠 무효화 방법
- 아직 만료되지 않은 콘텐츠라 하더라도 CDN 서비스가 제공하는 API를 사용하거나, 오브젝트 버저닝(Object versioning, 예: `image.png?v=2`)을 통해 무효화할 수 있음.



## 무상태(stateless) 웹 계층
상태 정보 의존적인 아키텍처
- 클라이언트로부터의 요청을 처리할 때 서버가 사용자 세션 데이터나 상태 정보를 유지하는 방식임.
- 예를 들어 사용자 A의 세션 정보가 서버 1에 저장되어 있다면, 사용자 A의 다음 요청은 반드시 서버 1로 가야만 인증이 정상 처리됨.
- 로드밸런서가 이를 지원하기 위해 고정 세션(Sticky Session) 기능을 써야 하는데, 이는 로드밸런서에 큰 부담을 주며 서버 장애 시 대응이나 규모 확장이 까다로워짐.

무상태 아키텍처
- 웹 계층에서 상태 정보를 완전히 제거하고, 세션 데이터와 같은 상태 정보를 웹 서버 외부의 공유 저장소(RDB, NoSQL, Memcached/Redis 등)에 보관하는 방식임.
- 클라이언트의 요청은 어떤 웹 서버로든 전달될 수 있으며, 웹 서버는 필요할 때 공유 저장소에서 상태 정보를 읽어옴.
- 상태 정보가 웹 서버들로부터 물리적으로 분리되어 있으므로 웹 계층의 수평적 확장(스케일 아웃 및 오토스케일링)이 훨씬 단순해지고 안정성이 높아짐.



## 데이터 센터
다중 데이터 센터 아키텍처를 만들기 위해 해결해야 할 기술적 난제
- 전 세계 어디서든 사용자가 쾌적하게 이용하고 장애 발생 시 가용성을 높이기 위해 둘 이상의 데이터 센터를 지원하며, 평상시에는 지리적 라우팅(GeoDNS)을 통해 사용자에게 가장 가까운 데이터 센터로 안내함.
1) 트래픽 우회: 올바른 데이터 센터로 트래픽을 보내는 효과적인 방법을 찾아야 함 (GeoDNS 활용 등).
2) 데이터 동기화: 서로 다른 데이터 센터마다 별도의 데이터베이스를 사용하고 있는 경우, 장애 발생으로 트래픽이 다른 센터로 우회되더라도 찾는 데이터가 있도록 데이터를 다중화하고 동기화해야 함.
3) 테스트와 배포: 웹사이트나 애플리케이션을 여러 데이터 센터에서 동일하게 테스트해보고, 자동화된 배포 도구를 통해 모든 데이터 센터에 동일한 서비스가 배포되도록 해야 함.



## 메시지 큐
- 시스템을 더 큰 규모로 확장하기 위해 시스템의 컴포넌트들을 분리하여 각기 독립적으로 확장될 수 있도록 돕는 핵심 전략임.
- 메시지의 무손실(Lossless, 메시지 큐에 보관된 메시지는 소비자가 꺼낼 때까지 안전함)을 보장하고, 비동기 통신을 지원하는 컴포넌트임.
- 발행자/생산자(Producer/Publisher)가 메시지를 만들어 메시지 큐에 발행하면, 소비자/구독자(Consumer/Subscriber)가 메시지를 받아 그에 맞는 작업을 수행함.
- 생산자와 소비자 사이에 결합이 느슨해져(Decoupled), 소비자가 다운된 상태에서도 생산자는 메시지를 발행할 수 있고, 생산자가 가용하지 않아도 소비자는 수신할 수 있음.
- 트래픽 급증 시 버퍼 역할을 하여 작업이 밀려도 큐에 쌓아두고 작업 서버(워커) 프로세스 수를 유연하게 조절해 비동기적으로 처리할 수 있음.



## 로그, 메트릭 그리고 자동화
- 서비스 규모가 커져 수백 대 이상의 서버를 운영하게 되면 필수적으로 도입해야 하는 도구들임.
  로그:
- 시스템의 오류와 문제를 찾아내는 데 핵심적임. 에러 로그를 모니터링하는 것은 중요하며, 서버 단위로 모니터링하기보다 로그를 단일 서비스로 모아주는 도구를 활용하면 검색과 조회가 편리해짐.
  메트릭:
- 사업 현황에 관한 유용한 정보와 시스템의 현재 상태를 손쉽게 파악할 수 있도록 도와줌.
    - 호스트 단위 메트릭: CPU, 메모리, 디스크 I/O 등
    - 종합(Aggregated) 메트릭: 데이터베이스 계층의 성능, 캐시 계층의 성능 등
    - 핵심 비즈니스 메트릭: 일별 능동 사용자(DAU), 수익, 재방문(Retention) 등
      자동화:
- 대규모 시스템이 안전하고 신속하게 운영되도록 생산성을 높여주는 도구임. 지속적 통합(CI) 도구를 통해 개발자가 작성한 코드가 자동으로 검증을 거치게 하고, 빌드·테스트·배포 절차를 자동화하여 개발 생산성을 크게 향상시킴.



## 데이터베이스의 규모 확장
수직적 확장
- 기존 DB 서버에 고성능 CPU, 대용량 RAM이나 디스크를 추가하는 스케일 업 방식.
- 하드웨어적 한계로 무한 증설이 불가능하며, 비용이 많이 들고 단일 장애 지점(SPOF) 위험이 큼.

수평적 확장
- 데이터베이스의 규모를 확장하기 위해 서버를 추가하는 스케일 아웃 방식으로, 대규모 데이터베이스에서는 **샤딩(Sharding)**을 사용함.
- 샤딩은 대규모 데이터베이스를 **샤드(Shard)**라고 부르는 작은 단위의 독립적인 데이터베이스로 쪼개는 기술임.
- 모든 샤드는 같은 스키마를 쓰지만 샤드에 보관되는 데이터 사이에는 중복이 없으며, 샤딩 키(파티션 키)를 기준으로 어떤 샤드에 저장할지 결정함.

샤딩 도입 시 풀어야 할 새로운 문제
1) 데이터의 재 샤딩
- 데이터가 너무 많아져 하나의 샤드로는 감당하기 어렵거나, 샤드 간 데이터 분포가 균등하지 못해 특정 샤드의 공간 소모가 빠르게 진행될 때(샤드 소진) 샤드 키 함수를 변경하고 데이터를 재배치해야 함. (안정 해시 기법 활용 가능)
2) 유명인사 문제
- 핫스팟 키(Hotspot Key) 문제라고도 부르며, 특정 샤드에 질의가 지나치게 집중되어 서버에 과부하가 걸리는 문제임. 유명인사 각각에게 샤드 하나씩을 할당하거나 더 잘게 쪼개어 해결함.
3) 조인과 비정규화
- 여러 샤드 서버로 쪼개고 나면 여러 샤드에 걸친 데이터를 조인(JOIN)하기가 매우 까다로워짐. 이를 해결하기 위해 데이터베이스를 비정규화하여 하나의 테이블에서 질의가 수행될 수 있도록 설계함.



## 백만 사용자, 그리고 그 이상
시스템 규모 확장을 위해 살펴본 기법들
- 웹 계층은 무상태 계층으로
- 모든 계층에 다중화 도입
- 가능한 한 많은 데이터를 캐시할 것
- 여러 데이터 센터를 지원할 것
- 정적 콘텐츠는 CDN을 통해 서비스할 것
- 데이터 계층은 샤딩을 통해 그 규모를 확장할 것
- 각 계층은 독립적 서비스로 분할할 것
- 시스템을 지속적으로 모니터링하고, 자동화 도구들을 활용할 것
