## 📌 1. 핵심 요약 (TL;DR)
- 시스템 규모 확장은 단일 서버부터 시작하여 사용자 수와 요구사항 증가에 맞춰 단계별로 확장해 나가는 과정이다.
- 수직적 확장(Scale-up)보다는 **수평적 확장(Scale-out)**, **무상태(Stateless) 웹 계층**, **캐시/CDN**, **DB 분리 및 샤딩** 등이 대규모 트래픽 처리의 핵심이다.

---

## 💡 2. 주요 개념 및 단계별 규모 확장 과정

### 2.1. 단일 서버 & 데이터베이스 분리
- **단일 서버**: 웹, DB, 캐시 등이 하나의 서버에서 동작 (시작 단계)
- **DB 분리**: 웹 서버와 DB 서버를 분리하여 각각 독립적으로 리소스 확장

### 2.2. 수직적 확장 (Scale-up) vs 수평적 확장 (Scale-out)
| 구분 | 수직적 확장 (Scale-up) | 수평적 확장 (Scale-out) |
| :--- | :--- | :--- |
| **개념** | 서버의 CPU, RAM 성능을 향상 | 더 많은 서버를 추가하여 분산 처리 |
| **장점** | 구조가 단순함 | 한계 없는 확장성, 고가용성(HA) 확보 |
| **단점** | 하드웨어 한계 및 고비용, SPOF 위험 | 복잡성 증가 (로드밸런서, 무상태 관리 필요) |

### 2.3. 로드밸런서 & 다중화 (Load Balancer)
- 로드 밸런서
    - 웹 서버 단일 장애 지점(SPOF) 해소 및 트래픽 분산
    - 가용성(Availability) 증대
    - 스위치와 비슷한 느낌 -> 트래픽을 적절하게 분배
    - 웹 계층의 트래픽을 분산
- 다중화
    - 주(원본)-부(사본) 관계 설정
    - write in master, read in slave
    - 읽기 연산의 비중이 높으므로 slave DB를 다중화
    - 병렬로 처리될 수 있는 쿼리의 수가 늘어나 성능 향상
    - 데이터 계층 트래픽 분산
    - 안정성 , 가용성 확보

### 2.4. 캐시 (Cache) & CDN
- **캐시 (Cache)**: 자주 참조되는 데이터(동적 테이터)를 메모리에 저장하여 DB 부하 감소 및 응답 속도 향상 (예: Read-through, Write-through 전략)
- **CDN (Content Delivery Network)**: 정적 콘텐츠(이미지, JS, CSS 등)를 지리적으로 가까운 에지 서버에 캐싱하여 로딩 속도 최적화(디스크 기반)

### 2.5. 무상태(Stateless) 웹 계층
- 세션 상태 정보를 웹 서버에 저장하지 않고 외부 전용 저장소(Redis, Memcached, NoSQL 등)에 저장
- 위의 저장소는 RAM 기반
- 저장소에 저장하지 않는 JWT토큰 방식도 무상태를 구현하는 방법
- 서버 증설/감축 시 자유로운 스케일 아웃 가능

### 2.6. 데이터베이스 확장 (Master-Slave / Sharding)
- **주-부(Master-Slave) 복제**: Write는 Master, Read는 Slave 서버로 분산
- **샤딩 (Sharding)**: 데이터베이스를 파티셔닝하여 여러 DB 서버에 분산 저장 (샤딩 키 선정 중요)

## ❓ 3. 공부 중 질의 (Q&A)

### 3.1. 클라이언트, 서버 및 웹 애플리케이션
* **Q. 웹 애플리케이션과 모바일 앱의 예시와 차이점은?**
  * **웹 앱**: 크롬/사파리 등 웹 브라우저로 접속하는 서비스 (`naver.com`, `coupang.com`). 서버에서 HTML/JS 화면을 전달하거나 연결되어 작동함.
  * **모바일 앱**: 앱스토어에서 스마트폰에 직접 설치하는 앱 (카카오톡, 배달의민족). 서버와 HTTP/JSON 데이터만 주고받음.
* **Q. 프론트엔드와 백엔드를 각자 배포하면 단일 서버가 아닌가?**
  * 맞음. 단일 서버는 1대의 EC2 안에 프론트+백엔드+DB가 몽땅 들어간 상태를 말하며, Vercel/CloudFront(프론트)와 EC2(백엔드), RDS(DB)로 따로 배포하는 것은 이미 **계층이 분리된 분산 아키텍처**임.

### 3.2. 로드밸런서 및 인프라
* **Q. 로드밸런서는 스위치 같은 역할인가?**
  * 맞음. 몰려드는 트래픽을 뒤에 있는 여러 대의 서버로 분산 연결(스위칭)해 주는 지능형 스위치 (L4/L7 스위치).
* **Q. EC2 서버의 공개 IP 접속은 단일 서버 개념인가?**
  * 맞음. EC2 1대의 공개 IP로 직접 접속하는 것은 단일 장애 지점(SPOF)이 있는 단일 서버 구조임. 로드밸런서 적용 시 로드밸런서에만 공개 IP를 부여하고 백엔드 EC2는 사설 IP(Private Subnet)로 숨김.
* **Q. Auto Scaling이 가져오는 서버는 어디서 나오나?**
  * AWS 데이터센터의 거대한 자원에서 개발자가 미리 만들어 둔 **서버 복사본 템플릿(AMI 이미지)**을 복제해서 1~2분 만에 자동 생성/삭제함.

### 3.3. 캐시 (Cache) & CDN
* **Q. 캐시 Overprovisioning(과다 할당)이란?**
  * 갑작스러운 트래픽 폭주(Spike)나 캐시 데이터 강제 삭제(Eviction)로 인한 DB 과부하를 막기 위해 캐시 메모리 용량을 일부러 넉넉하게 잡는 운영 전략.
* **Q. 캐시 서버와 일반 DB 서버의 저장 매체 차이는?**
  * **캐시 서버 (Redis 등)**: 100% RAM 메모리 기반 (초고속, 휘발성, 임시 데이터).
  * **일반 DB 서버 (MySQL 등)**: Disk(SSD) 기반 (영구 보존, 원본 데이터).
* **Q. CDN도 캐시 개념인가? 이미지/동영상만 저장되는가?**
  * 맞음. CDN은 전 세계 에지 서버에 정적 콘텐츠(이미지, 영상, JS/CSS)를 지리적으로 가깝게 캐싱해 물리적 거리를 줄여주는 네트워크 캐시임.
  * 스프링 부트 같은 백엔드 로직은 실행되지 않고, 대용량 파일 특성상 **SSD 디스크 기반(+일부 RAM)**으로 운영됨. (S3 저장소 + CloudFront CDN 조합 사용).

### 3.4. 무상태(Stateless) 웹 계층 & 인증 (JWT)
* **Q. Stateful에서 '서버에 상태 저장'이란 RDBMS 저장을 뜻하나?**
  * 아님. DB가 아니라 **특정 웹 서버(Spring) 본인의 RAM 메모리**에 세션을 보관하는 것을 의미함. 이 때문에 특정 서버에 묶이는 현상(Sticky Session)이 발생함.
* **Q. NoSQL(Redis)도 DB인데 매번 세션 조회해도 괜찮은가?**
  * NoSQL(Redis)은 RAM 기반 Key-Value 구조($O(1)$)라 초당 수십만 건 조회를 0.0001초 만에 가뿐히 버티므로 RDBMS와 달리 세션 저장소로 적합함.

### 3.5. 비동기 처리(메시지 큐) & 데이터베이스 확장
* **Q. 메시지 큐(MQ)로 웹 서버와 작업 서버를 분리한다는 것은?**
  * 웹 서버(Spring Boot)는 0.1초 만에 빠른 사용자 응답만 전담하고, 무겁고 오래 걸리는 작업(동영상 변환, 이메일 발송 등)은 메시지 큐(RabbitMQ/Kafka)를 거쳐 작업 서버(Worker)로 넘겨 비동기 처리하는 아키텍처.
  * OpenAI API 호출 구조도 무거운 AI 딥러닝 연산을 외부 OpenAI 작업 서버로 위임한 유사한 역할 분리 개념으로 볼 수 있음.
* **Q. DB 샤딩(Sharding) 시 어느 샤드로 갈지 어떻게 판단하나?**
  * `샤딩 키(user_id) % 샤드 개수` 모듈러 연산이나 해시 함수, 또는 라우팅 지도를 통해 쿼리를 날릴 샤드 DB 위치를 즉시 계산함.
* **Q. DB 정규화와 비정규화의 차이는?**
  * **정규화**: 데이터 중복 제거 및 무결성을 위해 테이블을 쪼개는 것 (RDB 기본).
  * **비정규화**: JOIN 비용을 줄이고 읽기(SELECT) 속도를 극대화하기 위해 일부러 테이블을 합치거나 중복 저장을 허용하는 것 (NoSQL 및 대규모 읽기 시스템 기본).
