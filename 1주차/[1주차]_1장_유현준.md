# [1주차] 1장 - 사용자 수에 따른 규모 확장성

정리: 유현준 / 홍익대 2026-2 대규모 시스템 설계 스터디

## 한 줄 요약

한 대의 서버로 시작한 서비스가 사용자 수가 늘어나며 겪는 문제들을, 단일 서버에서 DB 분리, 다중화, 캐시와 CDN, 무상태화, 샤딩 순으로 하나씩 풀어가는 장이다. 각 단계는 앞 단계에서 생긴 병목을 해결하려고 도입된다는 흐름이 핵심이다.

## 1. 단일 서버 구성에서 출발

웹앱, 데이터베이스, 캐시가 전부 서버 한 대에 올라가 있는 구성이다. 사용자 요청이 처리되는 흐름은 다음과 같다.

1. 도메인 이름을 DNS에 질의해 IP 주소를 받는다
2. 그 IP로 HTTP 요청을 전달한다
3. 서버가 HTML 또는 JSON 응답을 반환한다

여기서 웹과 모바일 트래픽 계층에서 데이터베이스 계층을 분리하는 것이 첫 번째 확장이다. 둘을 떼어놓아야 각각을 독립적으로 확장할 수 있기 때문이다.

## 2. 데이터베이스 선택

데이터베이스에는 관계형과 비관계형(NoSQL)이 있고, 보통은 관계형을 사용한다. 관계형은 40년 이상 시장에서 살아남아온 시스템이라 대부분의 개발자에게 최선의 선택이 된다.

NoSQL은 크게 네 부류로 나뉜다. 키-값 저장소, 그래프 저장소, 칼럼 저장소, 문서 저장소다.

다만 몇몇 경우에는 비관계형이 바람직할 때도 있다.

- 아주 낮은 응답 지연시간이 요구될 때
- 다루는 데이터가 비정형이라 관계형 데이터가 아닐 때
- 데이터를 직렬화하거나 역직렬화만 할 수 있으면 될 때
- 아주 많은 양의 데이터를 저장해야 할 때

느낀 점: 무조건 관계형이 아니라, 기본값을 두되 그것을 의심할 조건도 같이 알아야 한다는 뜻으로 읽었다.

## 3. 수직적 규모 확장과 수평적 규모 확장

수직적 확장(scale up)은 서버에 CPU나 메모리 등을 증설하는 방식이다. 구성이 단순하다는 장점이 있지만, 증설에는 한계가 있고 자동복구나 다중화가 없어서 서버가 죽으면 서비스 전체가 중단된다. 즉 단일 장애 지점(SPOF)이 된다.

수평적 확장(scale out)은 서버를 여러 대로 늘리는 방식이다. 구성은 복잡해지지만 한계 없이 늘릴 수 있어서 대규모 서비스에는 이쪽이 적절하다. 여러 관점에서 봤을 때 수평적 규모 확장으로 얻는 이득이 더 많다.

### 로드밸런서

수평적 확장을 하려면 늘어난 서버들에 트래픽을 나눠줄 장치가 필요한데, 그것이 로드밸런서다.

- 사용자는 로드밸런서의 공개 IP에 접속하고, 로드밸런서와 웹 서버는 사설 IP로 통신한다. 웹 서버가 외부에 직접 노출되지 않아 보안상 유리하다
- 서버 한 대가 죽으면 트래픽을 남은 서버로 보낸다 (가용성)
- 트래픽이 늘면 서버를 추가하기만 하면 된다 (확장성)

느낀 점: 컴퓨터네트워크 수업에서 배운 공유기가 하는 역할과 비슷하다는 생각이 들었다.

## 4. 데이터베이스 다중화

웹 계층은 위 방식으로 확장했으니 이제 데이터 계층 차례다. 데이터베이스는 주-부(master-slave) 관계로 다중화한다.

- 주(master) 서버는 쓰기 연산만 처리한다
- 부(slave) 서버는 주 서버의 사본을 갖고 읽기 연산만 처리한다

일반적인 서비스는 읽기가 쓰기보다 훨씬 많으므로, 부 서버를 늘려 읽기를 분산시키면 성능이 올라간다.

장점은 세 가지다.

- 성능: 읽기 연산이 여러 부 서버로 분산된다
- 안정성: 자연재해 등으로 일부가 파괴돼도 데이터가 보존된다
- 가용성: 한 대에 장애가 생겨도 다른 서버가 요청을 받는다

장애가 났을 때의 처리는 다음과 같다.

- 부 서버가 죽으면 읽기 연산을 주 서버로 돌리거나 다른 부 서버로 보낸다
- 주 서버가 죽으면 부 서버 중 하나를 새 주 서버로 승격시킨다. 다만 부 서버의 데이터가 최신이 아닐 수 있어서, 복구 스크립트로 부족한 데이터를 채워야 한다

## 5. 응답 시간 개선 1 - 캐시

웹 계층과 데이터 계층을 정리했으니 응답 시간 개선으로 넘어간다. 응답 시간은 캐시와, 정적 콘텐츠를 CDN으로 옮기는 것을 통해 개선한다.

캐시는 값비싼 연산 결과와 자주 참조되는 데이터를 메모리 안에 두고, 뒤이은 요청이 보다 빨리 처리될 수 있도록 하는 저장소다.

읽기 주도형 캐시 전략(read-through)은 요청이 오면 캐시를 먼저 보고, 있으면 바로 반환하며, 없으면 데이터베이스에서 읽어 캐시에 채운 뒤 반환하는 방식이다.

캐시 사용 시 유의할 점은 다음과 같다.

- 언제 쓸 것인가: 데이터 갱신은 드물고 참조는 잦을 때 적합하다
- 만료 정책: 너무 짧으면 데이터베이스를 자주 읽게 되고, 너무 길면 데이터가 실제와 어긋난다
- 일관성: 데이터 저장소와 캐시를 한 트랜잭션으로 묶을 수 없어 불일치가 생길 수 있다
- 장애: 캐시 서버 한 대는 단일 장애 지점이 되므로 여러 대에 분산한다
- 메모리 크기와 방출 정책: 메모리가 차면 무언가를 밀어내야 한다. LRU, LFU, FIFO 등이 쓰인다

느낀 점: 컴퓨터구조론 수업에서 배운 캐시와 같은 역할을 하는 것 같다. 다만 캐시가 무엇인지는 짧게 끝나는데 유의할 점이 길게 붙어 있는 걸 보면, 정작 어려운 건 캐시를 두는 게 아니라 운영하는 쪽인 듯하다.

## 6. 응답 시간 개선 2 - CDN

CDN은 정적 콘텐츠(이미지, 비디오, CSS, JavaScript)를 전송하는 데 쓰는, 지리적으로 분산된 서버망이다.

동작 방식은 이렇다. 사용자가 요청하면 가장 가까운 CDN 서버가 응답한다. 해당 콘텐츠가 없으면 원본 서버에서 가져와 캐시에 저장한 뒤 반환하고, 이후 요청은 원본까지 가지 않는다. 저장 기간은 TTL로 관리한다.

고려할 점은 다음과 같다.

- 비용: 제3자 사업자가 운영하므로 데이터 전송량만큼 과금된다. 자주 쓰이지 않는 콘텐츠는 이득이 적다
- 만료 시한 설정: 너무 길면 최신성이 떨어지고, 너무 짧으면 원본 요청이 늘어난다
- CDN 장애 대처: CDN이 죽으면 원본 서버에서 직접 받도록 우회할 수 있어야 한다
- 콘텐츠 무효화: API를 쓰거나 오브젝트 버저닝(URL에 버전 번호를 붙이는 방식)으로 캐시된 콘텐츠를 밀어낸다

느낀 점: 캐시와 비슷한 개념이라고 생각한다. 컴퓨터네트워크 강의에서 넷플릭스 같은 OTT 기업이 사용한다고 들었는데, 동영상을 빠르게 보여주려면 꼭 필요한 시스템인 것 같다.

## 7. 무상태(stateless) 웹 계층

상태 유지(stateful) 서버는 클라이언트의 정보(세션 등)를 서버가 직접 들고 있다. 그래서 같은 클라이언트의 요청은 항상 같은 서버로 전송되어야 한다는 한계가 생긴다. 로드밸런서가 고정 세션(sticky session)을 지원해야 하고, 서버를 추가하거나 제거하기 어려워지며, 서버가 죽으면 그 서버가 들고 있던 상태도 함께 사라진다.

그래서 보통 무상태 아키텍처를 사용한다. 상태 정보를 웹 서버에서 빼내 공유 저장소(관계형 데이터베이스, Redis, NoSQL 등)에 두는 방식이다.

이렇게 하면 사용자로부터의 요청은 어떤 웹 서버로도 전달될 수 있다. 구조가 단순하고, 안정적이며, 규모 확장이 쉽다. 서버를 트래픽에 따라 자동으로 늘리고 줄이는 것도 가능해진다.

## 8. 데이터 센터

규모가 매우 커지면 여러 개의 데이터 센터를 두게 된다. 사용자는 geoDNS를 통해 가장 가까운 데이터 센터로 안내되고, 한쪽에 장애가 생기면 트래픽을 다른 센터로 우회시킨다.

이와 같은 아키텍처를 만들려면 다음 난제들을 이겨내야 한다.

- 트래픽 우회: 장애가 난 센터의 트래픽을 정상 센터로 돌리는 방법
- 데이터 동기화: 각 센터가 서로 다른 데이터를 갖지 않도록 맞추는 방법
- 테스트와 배포: 여러 센터에 걸쳐 일관되게 배포하고 검증하는 방법

느낀 점: 넷플릭스가 여러 데이터 센터에 걸쳐 데이터를 어떻게 다중화하는지 관심이 있어 주석에 달린 사이트를 들어가서 공부해보았다. 동부와 서부 두 리전에서 서비스를 동시에 돌리고, 들어온 트래픽을 정리하는 것까지는 책의 내용과 같다. 재밌는 점은 데이터를 맞추는 방식인데, 주-부 서버가 아닌 주-주 서버로 양쪽 리전이 모두 쓰기를 받는다. 그 대신 완벽한 동기화를 포기하고 일관성을 한 리전 안에서만 챙긴다(그래봤자 차이는 0.5초 정도이지만). 캐시는 오래된 데이터를 내보내는 것을 막기 위해, 한쪽에서 쓰기가 발생하면 그 데이터를 다른 쪽 캐시에서 버리라고 알리는 방식을 쓴다고 한다.

## 9. 메시지 큐

메시지 큐는 메시지의 무손실을 보장하는, 비동기 통신을 지원하는 컴포넌트다. 메시지의 버퍼 역할을 하며 메시지를 비동기적으로 전송한다.

구조는 생산자(producer)가 메시지를 큐에 넣으면, 소비자(consumer)가 큐에서 꺼내 처리하는 형태다.

이렇게 하면 다음 이점이 생긴다.

- 결합도가 낮아진다: 생산자는 소비자가 살아 있는지 몰라도 된다
- 독립적으로 확장할 수 있다: 처리량이 밀리면 소비자만 늘리면 된다
- 소비자가 죽어도 메시지는 큐에 남아 있다

책에서는 사진 보정 애플리케이션을 예로 든다. 크롭, 샤프닝, 블러 처리 같은 작업은 시간이 걸리므로, 웹 서버가 직접 처리하지 않고 큐에 작업을 넣어두면 별도의 작업 프로세스가 꺼내서 처리한다.

느낀 점: 재밌게도 내가 최근 중앙 해커톤에서 진행한 프로젝트에서 정확히 똑같이 사진 보정 기능을 개발했는데 비동기 처리를 구현했다. 직접 구현해본 부분에 대한 예가 나와서 이해하기 쉬웠다.

## 10. 로그, 메트릭, 자동화

서비스 규모가 커지면 선택이 아니라 필수가 되는 것들이다.

- 로그: 에러 로그를 모니터링한다. 서버마다 흩어진 로그를 중앙 서비스로 모아 검색과 조회가 가능하게 만든다
- 메트릭: 호스트 단위 지표(CPU, 메모리, 디스크 입출력), 종합 지표(데이터베이스 계층의 성능 등), 핵심 비즈니스 지표(일간 활성 사용자, 수익, 재방문율 등)를 수집한다
- 자동화: 빌드, 테스트, 배포 과정을 자동화해 생산성을 높인다

느낀 점: 현재 백엔드 배포 과정에서 직접 개발해봤던 부분이라 흥미롭게 보았다.

## 11. 데이터베이스의 규모 확장

수직적 확장은 데이터베이스 서버에 고성능 자원을 증설하는 방식이다. 앞에서 본 것과 마찬가지로 증설에 한계가 있고, 단일 장애 지점 위험이 있으며, 비용이 많이 든다.

수평적 확장이 샤딩(sharding)이다. 대규모 데이터베이스를 샤드(shard)라고 부르는 작은 단위로 분할하는 기술이다. 모든 샤드는 같은 스키마를 쓰지만 각 샤드에 저장되는 데이터는 서로 중복되지 않는다.

어떤 데이터를 어느 샤드에 넣을지는 샤딩 키(파티션 키)로 결정한다. 예를 들어 샤드가 네 개일 때 user_id를 4로 나눈 나머지로 샤드를 정하는 식이다. 샤딩 키는 데이터가 고르게 분산되도록 신중히 골라야 한다.

샤딩을 도입하면 새로운 문제들이 따라온다.

- 재샤딩(resharding): 샤드가 꽉 차거나 데이터 분포가 한쪽으로 쏠리면 샤드 수를 바꾸고 데이터를 재배치해야 한다. 안정 해시 기법으로 완화할 수 있다(5장에서 다룸)
- 유명인사 문제(hotspot key): 특정 샤드에 질의가 집중되어 그 샤드만 과부하가 걸린다
- 조인과 비정규화: 여러 샤드에 걸친 조인이 어려워, 데이터를 비정규화해서 한 번의 질의로 끝내도록 바꾸게 된다

느낀 점: 여러 개의 데이터베이스에 데이터를 일관성 있게 보관하는 규칙을 만들고, 분배하는 프로그램을 짜는 것이 샤딩이라고 생각한다.

## 12. 백만 사용자, 그리고 그 이상

장 전체를 관통하는 정리는 다음과 같다.

- 웹 계층은 무상태 계층으로 만든다
- 모든 계층에 다중화를 도입한다
- 가능한 한 많은 데이터를 캐시한다
- 여러 데이터 센터를 지원한다
- 정적 콘텐츠는 CDN을 통해 서비스한다
- 데이터 계층은 샤딩을 통해 규모를 확장한다
- 각 계층은 독립적인 서비스로 분할한다
- 시스템을 지속적으로 모니터링하고 자동화 도구를 활용한다

느낀 점: 백만 이상 규모의 서비스를 진행하려면 위의 기술들이 종합적으로 구축되어야 한다는 것을 알게 되었다.
